# AA-993 — slice V1: CIS post-deploy verify workflow

Design: AA-Ecosys root `docs/audits/2026-10-26-S252-aa993-delivery-pipeline/design.md` (ADR 0016 draft, D3; slice
plan Phase A → V1) and the critic notes next to it (points 12, 13).

## Decisions

- **Concurrency.** The dispatched verify uses the job-level group `post-deploy-verify-cis` (`cancel-in-progress:
  false`). The verify that Deploy Dev calls uses a group of its own per run (`post-deploy-verify-cis-deploy-<run id>-
  <attempt>`), selected by the `workflow_call`-only input `from_deploy`. Reason: GitHub keeps one pending job per
  group and cancels the older pending one when a new one queues. If both paths shared one group, a dispatch could
  cancel the pending verify job of a Deploy Dev run, which then turns that run red for no real reason. Deploy Dev
  runs are already serialized by `deploy-dev-cis`, so their verify jobs need no further group. Neither group is
  `deploy-dev-cis`, so a dispatch never takes the pending slot of a Deploy Dev run (critic 12).
- **Rows format.** `name|auth|METHOD path|expected HTTP|jq assertion` (one column more than the design's
  `name|method url|expected http|jq assertion`): `auth` = `public` | `admin`, explicit instead of guessed from the
  path. Only `GET` is allowed; a row with another method fails red.
- **Fixed checks in the script, not rows**: the ECS checks (api + worker: service ACTIVE, desired ≥ 1, running =
  desired, one deployment, PRIMARY `rolloutState == COMPLETED`, running image = `<registry>/<repo>:dev-<sha>`, both
  on one image) and the worker checks (a live worker on the deployed SHA; caps of those workers = registered kinds).
  They need more than one call, which a one-call row cannot express.
- **Expected version and required schema come from the expected commit** (`git show <sha>:.release-please-manifest.json`
  and `<sha>:api/core/readiness.py`), not from the checked-out tree, so a dispatch on `main` for an older SHA compares
  against what that SHA shipped. The script and rows come from the ref the workflow runs on.
- **The verify job declares `environment: dev`** (the same OIDC subject `...:environment:dev` that the deploy role
  trusts) and receives secrets with `secrets: inherit`; no Terraform/IAM change.

## Changed (vs. the brief and the design)

- **"schema_version == required" became `required_schema == REQUIRED_CIS_SCHEMA of the deployed commit` and
  `schema_version >= required_schema`.** The DB is often ahead of the code (MIG-4: the migration is applied before
  the code PR, and other migrations can land first), so an equality on `schema_version` would go red on a healthy
  deploy. The equality on `required_schema` proves the running code is the deployed commit; `>=` is the readiness
  rule itself (`api/core/readiness.py`).
- **Worker caps are compared for the live workers on the deployed SHA only** (before: the union of every live
  worker). An old-revision worker that is still draining no longer makes the caps differ when a kind is removed.
- **A live worker on the deployed SHA is required** (before: only a warning while no worker reported a SHA, the
  AA-884 first-deploy case, which is long past).
- **A missing worker service is red** (before: warning, "AA-CIS-Infra not applied"). The deploy steps still skip a
  missing worker service as before; only the verify is strict.
- **Missing `ADMIN_SECRET` is red** (before: warning, admin rows skipped). Every other required input missing
  (`ECS_*`, region, expected image) is red too.
- **Desired count 0 is red** (design Q6; no automatic scale-up). The deploy sets desired 1, so this only bites a
  dispatched verify while Dev is scaled down.
- The D1 "released on shutdown" count is not printed: the endpoint does not exist yet (slice G1).

## Tradeoffs

- One job in the verify workflow instead of separate ECS / HTTP jobs: one OIDC sign-in, one summary table.
- PATH-stub tests (fake `curl` and `aws` reading fixture JSON) instead of a test-only branch in the script: the
  script under test is exactly what CI runs.
- Each row gets 3 tries, 10 s apart (`VERIFY_TRIES`, `VERIFY_RETRY_DELAY`): a real failure costs ~30 s more per
  row, a slow first request after the roll does not turn the deploy red.
- `result` is red for any non-`success` need on every event (the design asks this for `push`). No job in Deploy Dev
  is conditional, so a skip always means something did not run.

## Should know

- The `result` job ("Deploy Dev result") is the one to read: `verify` is skipped when `deploy` fails, and GitHub
  shows a skipped job as grey, not red.
- Public repo: the summary prints the image **tag** (`dev-<sha>`) only, never the registry; admin response bodies
  are never printed (Actions logs are public).
- `tests/unit/test_aa725_image_pin.py`, `test_aa891_release_version.py` and `test_aa882_staff_authz.py` asserted
  strings that moved out of `deploy-dev.yml`; they now read the verify files.
- The verify job uses `secrets: inherit` + `environment: dev`, so it reads the same `AWS_ROLE_ARN`, `ECR_*`, `ECS_*`
  and `ADMIN_SECRET` the deploy job reads, and assumes the same deploy role (only `ecs:DescribeServices` /
  `DescribeTaskDefinition` are used).
- actionlint was not available locally; the workflows were checked by YAML parse + the structure tests in
  `tests/unit/test_post_deploy_verify.py`. CI's first real run is the syntax proof for the expressions.
- `CONTEXT.md` "Deploy & CI" has a new bullet for the verify.
- Live proof (orchestrator): (1) the next push-triggered Deploy Dev shows `Post-deploy verify` green with the table;
  (2) a dispatch with `expected_sha=<previous sha>` goes red on `health`, `health-ready`, the image rows and
  `worker-sha`; (3) the dispatch does not cancel or replace a pending Deploy Dev run.

# AA-993 — slice H1: pre-push hook (local only)

Design: root `docs/audits/2026-10-26-S252-aa993-delivery-pipeline/design.md` D5 and Phase B → H1. No workflow file
changes; H2 makes CI call the same script.

Files: `scripts/pre-push.sh`, `scripts/install-hooks.sh`, `.githooks/pre-push`.

## Decisions

- **Check ids** (`resource_ids text_guard quality_lint flake8 unit frontend_tsc frontend_lint portal_tsc portal_lint`),
  each with its verbatim `ci.yml` line in `CI_CMD`, printed under a failure next to the command that ran locally.
- **Fast-mode selection** (diff `origin/main...<pushed sha>`):
  - always: `check_resource_ids.py` and the golden-set `text_guard scan` (2.7 s + 0.4 s; both scan every tracked
    file, so a docs-only push is covered too);
  - any non-docs file: `services.quality.lint --report` (~3.5 s; it scans Python and TS);
  - `.py` under `api/ services/ shared/` (the CI flake8 scope): flake8 on the changed files only, same flags. flake8
    checks are per file, so this equals the CI result for those files; `tests/` and `worker/` are outside the CI
    flake8 scope;
  - any `.py`, anything under `tests/unit/`, `tests/acp/`, `.github/`, `api/migrations/`, plus `requirements.txt`,
    `requirements-dev.txt`, `pyproject.toml`, `.trivyignore`: unit tests (the unit tests read fixtures, Q0 cases,
    workflows, CI scripts, the ratchet config and migrations);
  - `frontend/` or `portal/`: `npx tsc --noEmit -p .` + `npm run lint`. Never `next build`.
- **Unit tests in fast mode** = changed test files + for every other changed file the test files under `tests/unit` /
  `tests/acp` that name it (file name, fixed-string grep) + for a `.py` (also helpers under `tests/`) the test files
  that import it (`a.b.c` or `from a.b import c`) + extra rules: a sub-folder `conftest.py` runs its tree; the root
  `tests/unit/conftest.py` is a WARN with the `--full` hint; a data file under `tests/` runs the tests in its folder and
  the folder above (`quality/cases/*.json` -> `quality/test_*.py`); `.github/workflows/*` adds the tests that read the
  workflows folder; a migration `.sql` adds the tests that glob the migrations. Plus the `.pytest_cache` lastfailed
  list. The union replaces `pytest --lf`: with explicit paths, `--lf` would drop the passing changed-module tests.
  Above 30 grep matches (`AA_PREPUSH_MAX_TEST_FILES`) only the name-matched `test_*<module>*.py` run; above 30
  last-failed files they are dropped; both print the `--full` hint. Unit planned with no target found is a WARN
  (`run --full`), never a quiet SKIP.
- **Full mode** (`--full` / `AA_PREPUSH=full`): flake8 on the whole CI scope, the exact CI unit command with
  coverage, then `coverage_ratchet.py coverage.xml --base <base>` (CI uses `HEAD^1`; locally the base is
  `origin/main`).
- **`--ci`** (reserved for H2): implies full, never selects by diff, a missing tool or `node_modules` is a failure, the
  text guard runs with the CI env as given (no `GOLDEN_GUARD_REQUIRE_KEY=false`), and output streams instead of being
  captured. `--only a,b` lets H2 call the script once per CI job (Lint vs Unit).
- **Python**: `AA_PREPUSH_PYTHON`, else the active venv, else `./.venv`, else the main checkout's `.venv` (linked
  worktrees have none), else `python3`. flake8 runs as `python -m flake8` when that interpreter has it.
- **Output**: each check writes to a temp log that is printed (last 150 lines) only on failure; the summary lists
  PASS / FAIL / WARN / SKIP with seconds. Logs are kept on failure and removed on success.
- **Hook**: reads the pushed refs from stdin, skips branch deletions and tags. Every pushed branch must be the
  checked-out commit (the checks read the working tree): pushing another branch by name, or two branches where one is
  elsewhere, is blocked with a hint to check that branch out or use `--no-verify`. Runs the script with `bash` (a lost
  +x bit does not skip the checks). A branch without `scripts/pre-push.sh` pushes unchecked (message on stderr).
- **Tool parity**: flake8 must report `flake8-bugbear` in `--version` (CI installs it; without it the B checks do not
  run), and pytest must import; otherwise FAIL in every mode with the install line. A Python other than 3.12.x is a
  WARN; in full mode a coverage version other than the `requirements-dev.txt` pin is a WARN with the reinstall line.
  The unit env carries `COVERAGE_CORE=sysmon` as in CI (it only matters with `--cov`, i.e. full mode).
- **Changed-file list**: `git -c core.quotePath=false diff --name-only -z`, read with `mapfile -d ''`, so non-ASCII
  names and spaces reach the `case` patterns unquoted.

## Changed (vs. the design)

- `npm run lint` is report-only (WARN, never blocks): CI runs Frontend Lint / Portal Lint with `continue-on-error`
  (74 legacy errors, AA-601), so blocking here would be stricter than CI. `tsc` blocks, as in Frontend Build.
- No base to diff against (no `origin/main`) blocks with "run git fetch origin" instead of silently checking nothing.
- Not run locally: Security Audit (`pip-audit` needs the network), Integration Tests (Postgres + Redis), Docker
  Build / Trivy, Q0 red on base (PR labels), `next build`. They stay CI-only.

## Tradeoffs

- File-name and import grep for test selection, not coverage-based impact analysis: no new dependency, runs in
  milliseconds, misses indirect importers (CI still runs everything).
- Missing `node_modules` is a SKIP locally (the hook never runs `npm ci`: RAM and time) and a FAIL in `--ci`. A
  missing Python tool is not a SKIP: a skipped flake8 would pass code that CI rejects.
- Helpers under `tests/`: the review suggested a `\b<leaf>\b` grep over all tests; for `chain` that matches 30 test
  files (the word is common), so the word grep is limited to the helper's own folder and the tree-wide search uses
  the import pattern and the file name (`chain.py`), which find `test_q0_corpus.py` and `test_red_on_base_script.py`.
- `ci.yml` is named by one test only (`test_aa919_golden_text_guard.py`); the CI gate tests build the path in segments
  (`REPO / ".github" / "workflows" / ...`), so a workflow change also selects every test that mentions `workflows`
  (11 today).
- Checks read the working tree while the push sends commits; the script prints a note when tracked files are dirty.

## Should know

- `scripts/` is in `.gitignore` as a whole directory (the tracked files there were added with `-f`), so the two new
  scripts were added with `git add -f`. Once tracked, edits show up normally.
- Install once per clone: `scripts/install-hooks.sh` (`git config core.hooksPath .githooks`; a relative path, so each
  worktree uses its own `.githooks/`). It warns about any non-sample hook in `.git/hooks`, which stops running once
  `core.hooksPath` is set (the current clone has none). Undo: `git config --unset core.hooksPath`. Bypass a blocked
  push once with `--no-verify`.
- Review fixes (second commit, after the rebase onto slice 6): shellcheck 0.11.0 `-S warning` clean and `bash -n` on
  all three files; `--self-test` 33/33 (22 plan fixtures + 11 helper checks, among them root / sub-folder conftest,
  `quality/chain.py`, a Q0 case JSON, `ci.yml` -> `test_aa879_ci_gates.py`, a migration `.sql`, and a throwaway git
  repo with a non-ASCII file name listed raw); a stub interpreter without bugbear / pytest gives two FAILs with install
  lines and a Python-version WARN; `--base` without a value exits 2; the hook blocks a second ref at another commit
  and passes tags and deletions; a temporary commit touching `tests/unit/conftest.py` gives the unit WARN (reset
  afterwards). The full suite was not run (RAM).
- Verified locally (first commit): shellcheck 0.11.0 `-S warning` clean on all three files; `--self-test` 21/21 (17
  plan fixtures + 4 helper checks; no lint or test tool runs); a temporary commit with an E501 line in `services/quality/lint.py`,
  fed to `.githooks/pre-push` with simulated push stdin (nothing was pushed): exit 1, flake8 FAIL with the CI line,
  17 s wall on that one-file diff (resource_ids 2.7 s, text_guard 0.4 s, quality_lint 3.3 s, flake8 0.2 s, unit
  10.3 s on 3 test files). The planted commit was reset before the real commit.
- H2 still owes: CI steps calling `scripts/pre-push.sh --full --ci`, CODEOWNERS for `scripts/pre-push.sh` and
  `.githooks/`, pinning flake8 in `ci.yml` (`pip install flake8 flake8-bugbear` is unpinned), and the
  `GOLDEN_GUARD_KEY` rule on `main` / `merge_group`. The aa-ship note on installing the hook lives in the root repo.

# AA-993 — slice G1: CIS worker drain hardening — 27/10/2026

Design: root `docs/audits/2026-10-26-S252-aa993-delivery-pipeline/design.md` (ADR 0016 draft D1, Phase C → G1, Q1, Q2)
and critic points 14 and 15. Files: `shared/jobs/{worker,queue,registry}.py`, `services/jobs/noop_sleep_job.py`,
`api/routers/admin_job_runner.py`, `api/core/staff_authz.py`, `.github/verify/cis.rows`, tests, `CONTEXT.md`.

## Decisions

- **Drain window.** `worker_grace_seconds()` reads `JOB_WORKER_GRACE_SECONDS`. **Absent = 20 s** (the pre-G1 value), not
  the design's 100: the brief asks for a safe default without the Infra change, and 20 s is today's known-good
  behaviour. AA-CIS-Infra sets 100 on the worker task (Q1). The check: `grace + 15 <= stopTimeout`, with the
  stopTimeout from `JOB_WORKER_STOP_TIMEOUT_SECONDS` (default 120 = the worker container in `modules/ecs`). The task
  metadata endpoint does not expose stopTimeout, hence the env. 100 s leaves 20 s (Q1); the maximum accepted is 105.
- **A bad value raises `ValueError` in `_main` before the pool opens** (not an `assert`, which `-O` strips). The worker
  does not start, and the V1 post-deploy verify goes red on `worker-sha`; a quietly clamped window would hide the
  misconfiguration. Non-numbers, negatives, NaN/inf are refused the same way.
- **Only the service worker reads the env.** `Worker(grace_seconds=20)` stays the class default, so the in-API loop
  (local/dev, `JOB_WORKER_IN_API`) is unchanged.
- **"Newer worker alive" is read at release time** (`Worker._newer_worker_alive_safe` → `queue.newer_worker_alive`), not
  from `self.yielding`: the old worker's loop has already stopped when the release runs, and the deploy's new task
  may have registered after the last loop pass. A failed read returns False, i.e. the release counts (as before G1),
  so a job that kills its own worker still ends after MAX_RELEASES.
- **`queue.release(count_release, delay_seconds)`.** `count_release=False` adds 0 to `progress.releases` and the
  `failed` branch requires `$5` (counted), so an uncounted release can never fail a job. `delay_seconds` sets
  `run_after = now() + delay`. Cancel-requested still wins (→ `cancelled`).
- **Release record in `progress` JSON, no column.** `progress.release_log` (`{at, counted, worker}`, last
  `RELEASE_LOG_KEEP = 20`, oldest dropped), `progress.shutdown_releases` (all releases), `progress.last_released_at`.
  Reasons: critic 6 (an ADD COLUMN on hot `shared.job` breaks the running `RETURNING *` claim), no migration in this
  slice, and `progress` is in the job-table template that Booking/Partner share (G4 can port the same SQL). A
  non-array `release_log` (never written by the runner) is replaced, not an SQL error.
- **`GET /admin/job-runner/released?since=`** (default: 24 h ago; a naive `since` is read as UTC; a bad one is 422)
  returns `{since, released, counted, jobs, by_kind{kind:{released,counted,jobs}}, max_releases}` from
  `queue.released_since`. Machine GET: added to `MACHINE_ROUTES` (no POLICY entry, like `/summary` and `/workers`), and
  a row `job-runner-released` in `.github/verify/cis.rows` checks the shape after every deploy.
- **Registry fields:** `release_delay_seconds: int = 0`, `deploy_blocking: bool = False`. `job_kind()` refuses a
  negative delay and `deploy_blocking` together with `deploy_gate_exempt`. No existing kind sets either (G3 sets the
  delay on `a3_atomize`; G4/G5 use `deploy_blocking`). `GET /summary` lists `deploy_gate_exempt`, `deploy_blocking`,
  `release_delay_seconds` per kind. The Deploy Dev guard is unchanged (G5).
- **`noop_sleep`:** a module `services/jobs/noop_sleep_job.py` imported by `services/jobs/__init__.py`; it registers only

# AA-993 — slices G2 + G3: drain-safe `s1_rewrite` and `a3_atomize` — 27/10/2026

Design: root `docs/audits/2026-10-26-S252-aa993-delivery-pipeline/design.md` (ADR 0016 draft D1.3, Phase C → G2, G3)
and critic points 9 and 10. Builds on G1 (#1072: drain window, uncounted deploy releases, `release_delay_seconds`).

## Decisions

### G2 — `s1_rewrite` persist stages

- **Stage list** (`services/content_generation/s1_checkpoint.py`, written to `shared.job.progress.persist_stage`):
  `writer_done` → `rewritten` → `content_inserted` → `scored` → `fix_pass_saved` → `routed` → `accounted`. The job's
  early return fires **only on `phase == "done"`** (critic 9); a bare `version_id` now means "persist steps may be
  owed", and the resumed run continues from the recorded stage.
- **Writer resume is NOT the `batch_text` seam** (design D1.3 said it would be). Reason: the S1 writer v2 is the
  default writer (`S1_WRITER_V2` on), and the Bedrock Batch seed path is v1-only: `s1_writer_v2_live.applies()` is
  False whenever `batch_text` is set, `seed_generated_node` parses the v1 JSON shape, and the draft would lose its
  `writer_version = "v2"` stamp — so validate (v2 report-only codes), the judge (v2 brand-fit report-only) and the
  retries would treat a resumed v2 draft as a v1 draft and could decide differently. Instead `_rewrite_tour` reports
  the graph-state **delta** each writer node produced (`writer_state_delta`: every key the node changed vs the initial
  state — draft, cost, model, `writer_version`, `retry_count`, feedback ...), the job saves it as
  `progress.s1_writer_state`, and a resume enters a new graph `build_graph_resumed()` whose entry node
  (`resume_writer`, no LLM call) merges that delta back and continues at `validate`. Every node and edge after that is
  the same as `build_graph()`, retries included.
- **The delta is taken against a deep copy of the initial state** (`state_baseline`): a node that appends to a list of
  the state in place (e.g. `degraded`) mutates the initial state too, and a shallow diff would miss that entry.
- **`rewritten` saves the whole rewrite result** (`progress.s1_rewrite_result`, after the sonnet-upgrade decision and
  `_brand_forbidden_words`), so a resume past it pays nothing again: no writer, no judge, no fix pass, no SEO call.
  `dataforseo_used` and `auto_upgraded` are saved with it (the INSERT metadata and the return dict need them).
- **Only plain JSON is checkpointed.** A value that does not survive `json.dumps` / `json.loads` unchanged (a set, a
  tuple, an object) disables that checkpoint (logged `s1_checkpoint_result_not_json`); never `default=str`, which
  would hand a resumed run different values to decide on.
- **The INSERT is idempotent through the domain row, not only the checkpoint.** With a checkpoint the version's
  `metadata` gets `s1_job_id = <job id>`; before inserting, a run with a checkpoint reuses `checkpoint.version_id` or
  the newest version of the tour carrying its job marker (`_version_of_job`, `metadata @> {...}`, tour index + the
  existing metadata GIN index). So a release between the INSERT commit and the `content_inserted` write cannot make
  a second version. No migration.
- **Score insert:** `quality_scores` has no unique key on `generated_content_id` (schema reference), so the old
  `ON CONFLICT DO NOTHING` never fired. The insert is now `INSERT ... SELECT ... WHERE NOT EXISTS (row for this
  version)` for every caller (a fresh version has no row, so the sync path is unchanged).
- **Brand audit / fix-pass UPDATEs** write the same values again, so they are naturally idempotent; the stages skip
  them anyway. **Review entry:** `_enqueue_review` already guards with NOT EXISTS (`pending`/`dismissed`).
  **Publish:** `process_export` is skipped after `routed`; its `a3_atomize` enqueue is keyed on the version anyway.
  **pipeline_runs cost** (`+=`, the one non-idempotent write) is skipped after `accounted`.
- **Checkpoint writes never raise** (logged `s1_checkpoint_write_failed`): the checkpoint saves money on a resume and
  must not fail an otherwise good run. The worst case of a lost write is one repeated paid step, never a duplicate row.
- **`_run_tour_safe` passes the same checkpoint to its three internal attempts**, so an internal retry after a failed
  persist step resumes too (before, it rewrote and inserted a second version).
- **Bulky keys are cleared** in the same write that sets `phase = "done"` (`s1_writer_state`, `s1_rewrite_result` →
  null), so finished rows do not carry ~10-40 KB of draft text in `progress`.
- New params are passed **only when a checkpoint exists** (`_rewrite_tour(resume_state=, on_writer_state=)`,
  `_execute_run_tour(checkpoint=)`): the sync `/admin/run-tour` path and the Bedrock Batch ingest are unchanged, and the
  existing executor tests (mocked `_rewrite_tour` / `_execute_run_tour`) keep their exact call shapes.
- **The stage never moves back.** A resumed run passes the earlier steps again (e.g. `content_inserted` when it
  reuses the version) and `mark()` ignores a stage below the recorded one; caught by the release-at-`scored` test,
  which re-ran the brand audit before this rule.
- **A rewrite result that cannot be checkpointed stops all later marks** (`_stopped`), so the row never claims a stage
  past `rewritten` without the result to resume from. The marker lookup runs only on a resume from `rewritten`
  (same result as the released run), never after a fresh rewrite (that content is new, so it is a new version).

- **Review fix — a real failure does not keep the checkpoint.** (1) A version INSERT that fails with a data error
  (`asyncpg` `DataError` = SQLSTATE class 22, e.g. `StringDataRightTruncation` on `seo_title varchar(70)` with no
  write-time trim since AA-740; also NOT NULL / CHECK violations) calls `S1Checkpoint.forget_rewrite()`: stage, result
  and writer state are dropped in memory and in `progress`, so the next internal attempt of `_run_tour_safe` rewrites
  as before G2. Other INSERT errors (connection lost, a `version_num` race on the unique key) keep the saved rewrite.
  (2) When `_run_tour_safe` gives up (`result is None`), the job writes `persist_stage`, `s1_writer_state`,
  `s1_rewrite_result` = null before raising. `queue.retry` (Jobs page Retry) resets attempt/status/result but keeps
  `progress`, so without this a Retry replayed the stale checkpoint; now Retry rewrites, as before G2. A release
  never reaches that line (the handler is cancelled), so deploy resumes and admin cancel → Retry still resume.
- **Review fix — the polled Jobs list does not carry the checkpoint payloads.** `_SUMMARY_COLUMNS` selects
  `(j.progress - 's1_writer_state' - 's1_rewrite_result') AS progress`; the drawer (`get()`, `_LIST_COLUMNS`) still
  returns the whole progress.

### G3 — `a3_atomize` overlap

- **`threading.Event`** in `a3_atomize_job.run`, set in `except CancelledError` around `asyncio.to_thread` (worker
  shutdown release, admin cancel, lost lease all cancel the handler). `run_a3_atomize(should_stop=)` checks it before
  each day's read (the day being read finishes whole: atoms + fingerprint commit together) and before the legacy
  whole-tour read; `_a3_atomize_chain` checks it before Segment/Score/Route, the place-card relink and the place
  extract. A stop raises `AtomizeStopped` (new, in `services/acp_contract/a3_atomize.py`), which the chain re-raises
  even with `reraise=False` (a stop is not a failure to swallow). `_report` drops progress writes once the event is
  set, so the old thread never writes `step` fields onto a row a new worker has re-claimed.
- **Tour lock** (`handler.a3_tour_lock`): a session `pg_try_advisory_lock(hashtext('a3_atomize'), hashtext(tour_id))`
  on a **dedicated connection** (`_connect_tour_lock`, `application_name=cis-job-a3-lock`), not a pool connection
  (`JOB_POOL_MAX = 5` is sized for the concurrent `decide()` calls), held for the whole chain and unlocked in
  `finally`; Postgres drops it when the connection ends with the old process. **Polling `pg_try_advisory_lock` every
  2 s** instead of a blocking `pg_advisory_lock`: a blocking call inside the thread's own loop could not be
  interrupted, so a waiting run could not honour its own stop; the waiter gives up after 1800 s (`TourLockTimeout`,
  retryable; = the kind's `expected_seconds`). Two int4 keys, so it never collides with the one-key advisory locks
  (`segment_gc`, the brand / version-edit locks).
- **Opt-in** (`_run_a3_atomize_background(tour_lock=True, should_stop=...)`): only the job passes them; other callers
  and the many existing tests that call the chain with a mocked pool are unchanged. The old body moved, unchanged,
  into `_a3_atomize_chain`.
- **`release_delay_seconds = 120`** on the kind (`RELEASE_DELAY_SECONDS`, the worker container's stopTimeout): the
  released row is due again after the old task is gone, so the lock wait is the exception, not the rule.
- **Review fix — a forced job does not pay twice for the days it already re-read.** `force=True` (promote path) used
  to re-ask every day on every attempt, so a release (or an `AtomizeIncomplete` retry) of a forced job paid again for
  each day the stopped thread had finished. The job now records `progress.force_since` once (first attempt, UTC,
  `_force_since`) and passes it down (`_run_a3_atomize_background` → `_a3_atomize_chain` → `run_a3_atomize` →
  `_atomize_per_day`, only when set, so other callers keep their call shape). Under force a day is skipped when its
  fingerprint matches AND `atomize_day_fingerprint.atomized_at >= force_since`; a day read before the job started is
  still re-read, a changed day is always re-read.

## Changed (vs. the design)

- G2 writer resume uses a saved graph-state delta + `build_graph_resumed()`, not the `batch_text` seam (v2 writer, see
  Decisions). Stage names: the design's `queued_for_review` is `routed` (it covers the publish path too), and two more
  stages exist: `rewritten` (whole result, skips judge/fix pass/upgrade too) and `accounted` (pipeline_runs `+=`).
- G2 also fixes the `quality_scores` insert for every caller (`ON CONFLICT DO NOTHING` → `WHERE NOT EXISTS`): the
  table has no unique key on `generated_content_id`, so the old clause never prevented a duplicate.
- G3: the lock waits by polling with a stop check and a 1800 s cap (design: plain session `pg_advisory_lock`).
- No migration (the version marker lives in `generated_content.metadata`, which has a GIN index already).

## Tradeoffs

- `progress` carries the draft while the job runs (`s1_writer_state` ~10-30 KB; `s1_rewrite_result` ~20-40 KB) and
  each checkpoint write rewrites the whole `progress` jsonb. Six or seven writes per tour; both keys are nulled at
  `phase = "done"` and when the job fails (review fix; the post-mortem copy is lost, the logs keep the error). A job
  failed by the reaper (lease lost, MAX_RELEASES cap) never runs that line and keeps them; a Retry of such a row
  resumes from its checkpoint, which is the intended release behaviour. The polled list never returns them.
- `force_since` is the worker's clock, compared with the DB's `now()` in `atomized_at`. ECS clocks are NTP-synced; a
  skew costs at most one day read twice, or skips a day re-read in the skew window just before the job started.
- A data-error INSERT now pays a fresh rewrite on the next attempt (≈ the writer cost again) instead of failing three
  times on the same content; that is the pre-G2 behaviour for this case.
- The sonnet-upgrade rewrite (`_trigger_hard` / opt-in, haiku only) is not checkpointed on its own: a release during
  it resumes after the primary rewrite's writer and re-runs the upgrade. The live A1 writer is sonnet (writer v2), so
  the upgrade does not trigger today.
- A writer call cut mid-flight is paid twice (accepted in ADR 0016 D1 consequences; visible in `llm_call_log`). The
  SEO step (DataForSEO, cached per country in Redis) runs again on a resume before `rewritten`; skipped after it.
- The re-entered graph re-runs validate + judge (+ brand audit, grounding, flag-fix) after the writer: the judge is a
  paid call, but far cheaper than the writer, and checkpointing mid-judge would need a stage per node.
- G3 stop granularity is one day: a deploy during a slow day read waits for that read (one gateway call, retried at
  most once) before the thread stops; the lock keeps the new attempt out meanwhile.
