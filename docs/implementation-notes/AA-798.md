# AA-798 — Real LLM cost in tenant usage/billing

Status: migration half + app half written (S235, lane B, branch `feat/aa-798-real-llm-cost`,
PR #703). Rebased on main after AA-797 (#702) and AA-796 (#705). The tenant `/v1/billing` cost
drop shipped in AA-796, so the apply-order prerequisite below is met once #705 is deployed.

## Decisions

- **Migration 223 is a baseline capture, not a patch.** The live `shared.v_tenant_monthly_usage`,
  `shared.membership_plans` and `shared.tenants.plan_id` were created by hand on Dev and exist in no
  migration (synthesis R4). The repo's only view definition is `007_tenant_usage.sql`, which has
  other columns (`month`, `total_calls`, ...). 223 was written from a read-only live dump taken
  14/10/2026 (`.tmp-session/s235/view_dump.json`: viewdef, owner, grants, dependents, plans DDL +
  rows, `plan_id` + FK).
  - `membership_plans`: `CREATE TABLE IF NOT EXISTS` with the live columns, defaults, PK and
    `UNIQUE (plan_name)`. The five live plans are seeded with their live ids, `ON CONFLICT
    (plan_name) DO NOTHING`. This is a no-op on Dev.
  - `tenants.plan_id`: `ADD COLUMN IF NOT EXISTS plan_id UUID REFERENCES shared.membership_plans(id)`.
    The FK gets the live name `tenants_plan_id_fkey` and is created only together with a new
    column, so Dev gets no duplicate FK (checked: two runs leave one FK). This is a no-op on Dev,
    and there is no backfill: Dev was backfilled in S234, and a fresh DB has no tenants.
  - View: `DROP VIEW IF EXISTS` + `CREATE VIEW`. `CREATE OR REPLACE` cannot turn the 007 shape
    (CI) into the live shape. The 16 columns keep the live names, types and order, and every
    expression except `llm_cost_usd` is the live one unchanged. A `DO` block fails the migration
    if the column list differs from the live list.
- **`llm_cost_usd` definition.** It is `SUM(shared.llm_call_log.cost_usd)` where `tenant_id` = the
  tenant, `created_at` falls in the current calendar month (the same `date_trunc('month', now())`
  boundary as the other columns, written as a range so `idx_llm_call_log_tenant_created` is used),
  and `quality_signal` does not contain `{"shadow": true}`. It is rounded to 4 dp and COALESCEd to
  0, as the live column was.
  - Jev is included: `decide()` logs every TypeSafe call to `llm_call_log` (role `validate`,
    model `jev-latest`). The issue scope says "incl. Jev".
  - Shadow rows are excluded. `llm_call_log` has no shadow column, but `shared/llm_client/shadow.py`
    always writes `quality_signal = {"shadow": true, "shadow_of": ...}`. Shadow runs are AA's own
    model experiments (ADR 0006), not the cost of serving the tenant.
  - Rows with `tenant_id IS NULL` (A-series/platform) are not attributed to any tenant, including
    aa_internal. Platform spend already has its own place (`/admin/overview` `_MTD_LLM_SQL`).
- **No GRANT statements.** The live ACL is owner-only: `information_schema` lists only
  `aa_cis_admin`'s implicit owner privileges. DB Migrate runs as the CIS api `DATABASE_URL`, which is
  the master user `aa_cis_admin`, so DROP + CREATE reproduces the same owner and ACL. An explicit
  `GRANT ... TO aa_cis_admin` would also fail on CI, where that role does not exist. `aa_app_user`
  never had access to this view, and none is added because billing data stays on the admin path.
- **Plain `DROP VIEW` (no CASCADE).** The live dump found no dependents. If one appears before
  apply, the migration fails loudly instead of silently dropping it.

- **App half: one definition of tenant LLM cost = the view column.** Every admin read of a
  tenant's month-to-date LLM cost takes `shared.v_tenant_monthly_usage.llm_cost_usd` as-is:
  `GET /admin/billing` (`admin_pipeline.get_admin_billing`, Tenant 360 Billing tab) and
  `GET /admin/tenants` (`this_month.llm_cost_usd`). No Python formula. The fabricated
  `pipeline_runs + 0.018 x versions` estimate only ever lived in the hand-made view, so 223 is
  what removes it; the app has no copy (unit test scans the billing read paths and `_billing.py`).
  Querying `llm_call_log` directly from the app was rejected: it would be a second definition
  that can drift from the view's shadow / NULL-tenant filter.
- **No invented plan.** New `api/routers/_billing.py` (`usage_row_to_dict`, `no_plan_usage`) is
  shared by admin billing and tenant `/v1/billing`:
  - `plan_attached` is derived from the row: every `membership_plans` column is NOT NULL, so a
    NULL `tours_quota_monthly` from the LEFT JOIN means exactly "no plan". It is not a view
    column, so the app works on the old live view and on 223 alike (no new view column).
  - When no plan: quotas, price, overage rate, quota %, tours_overage and overage_usd are `null`
    (the view gives 0 % and 0 tours for those, which would read as "0 % of something").
  - `GET /admin/billing` for an unknown tenant -> 404 (was the Starter $299 / 50 tours block).
  - Tenant `/v1/billing` with no usage row -> `no_plan_usage()` (nothing counted, plan null)
    instead of 404: an authenticated tenant always has a view row (the view is
    `FROM shared.tenants`), and keeping 200 keeps plans / daily / rate limit for the portal.
  - `GET /admin/tenants`: the plan columns are no longer `COALESCE(.., 0)`; `plan_attached` added,
    `plan.*` null when no plan.
- **Frontend.** Admin Tenant 360 Billing tab: label "LLM cost (MTD, llm_call_log)" shown to 2 dp,
  "No plan attached", "—" for null price / overage / quota (no "∞" for a null quota). Portal
  Billing (`PlaceholderTabs.tsx`): no `?? "starter"`; "No plan attached / Contact us to set up
  your plan", amount due "—". Portal Dashboard: dropped the `?? "growth"`, `?? 200`,
  `?? 20000` fallbacks; null totals render "—". No cost field was added to any tenant type.

## Changed (vs. the issue text)

- The issue says "new view". The migration keeps the same view name and shape, so all six readers
  keep working (admin_pipeline billing, `/v1/billing`, admin_overview `_QUOTA_SQL`, admin_settings,
  the admin.py tenant list `:277` and tenant details `:636`). The migration does not depend on
  the app change, but it must be applied **after** the `/v1/billing` change is live (see "Should
  know" → apply order): applying it first would expose real AA LLM spend to tenants.
- `shared.pipeline_runs` is no longer read by the view.
- App half (done on this branch): starter defaults removed in `get_admin_billing` and tenant
  `get_my_billing`; "no plan" is explicit (`plan_attached`). The `/v1/billing` cost-key drop
  (reversal of AA-636's "kept in response") landed in AA-796 (#705, `_tenant_projection.
  TENANT_HIDDEN_BILLING_FIELDS`), so this PR leaves the tenant cost projection as AA-796 left it.
  `GET /admin/tenants/{id}/usage` was fixed by AA-797 (#702, computed from `tenant_api_usage`).
- Admin tenant `/details` keeps its own `total_llm_cost_usd` (all time) and
  `llm_cost_window_usd` (rolling 30 d): both are real `llm_call_log` sums (AA-702/AA-718), a
  different window from the billing month, so they are not the view's number. They include
  shadow rows and, for aa_internal, NULL-tenant rows (they reconcile with External Spend). Left
  unchanged; only the month-to-date billing figure is defined by the view.

## Tradeoffs

- **NUMERIC precision of `membership_plans`.** The dump recorded `data_type = numeric` only, not
  precision/scale. The live values (`299.00`, `4.0000`) imply scale 2 and 4. The file uses
  `NUMERIC(10,2)` / `NUMERIC(10,4)`, so precision 10 is inferred. This only matters on a fresh DB
  (`IF NOT EXISTS` skips it on Dev). A read-only check before merge would confirm it (see "Should
  know").
- **Shadow exclusion and the AA-766 "±$0.01" check.** A raw `SUM(cost_usd)` over a tenant's rows
  includes shadow rows. The verify query must use the same shadow filter as the view.
- Per-month history is not kept: the view stays "current month only", as live. A history view is
  out of scope.

- **`_get_tenant_plan_limit` (v1_tours, quota enforcement) still falls back to the starter
  row's quota** when the tenant's `plan_tier` has no plan row. It is not displayed (it only
  decides when a rewrite counts as overage, never blocks) and keys on `plan_tier`, not `plan_id`;
  changing it changes overage logging, so it is left for a follow-up if Nghiệp wants it.
- **`admin_settings.get_settings` keeps `COALESCE(.., 0)`** for aa_internal's quota/price: it
  only reads aa_internal, which always has the internal plan; the settings page already renders
  0 as "∞" / "—".
- Tenant `/v1/billing` with a missing row returns 200 + no plan (not 404) - see Decisions.

  `gold_aa_internal.tenant_tour_versions` (107/108/109 already warn "does not exist" in CI), and the
  live view joins it. conftest's own run of 223 therefore logs a warning and rolls back, and the CI
  DB keeps the 007 view. This follows lesson S231 (conftest swallows migration errors).

  - It runs the 223 body itself, twice, to prove idempotency.

  - It asserts the view column exists before reading any value, then checks the column order, the
    llm_call_log sum and the plan quotas.
