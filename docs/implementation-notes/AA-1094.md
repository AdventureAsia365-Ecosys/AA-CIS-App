# AA-1094: tenant tour view, agency branding off AA pages, source_id on the trip page

S278 system audit items M20 (no `catalog.v_tenant_tour_v1`), M21 (agency brand and Sign in on the wrong pages) and
M12 (the CIS trip page has no catalogue key, so "Book now" can book another tour). Root ADR 0019 d10 / d11.
The CIS side is two PRs: migration 403 (the view, contract) and this one (the trip page key).

## Decisions

- **What goes public in the view (migration 403, revised after review).** A tenant row exists for a live AA tour when
  the tenant has a version publishable on its site: status `approved` (the tenant approved it), the agency's own edit
  as the portal writes it (`edit_source = 'tenant_edit'`, status `pending`: the edit route's insert; the portal has no
  approve button), or a model's rewrite at `ai_generated` whose `qa_status = 'passed'`. `needs_review` is NOT only the
  score signal: it also marks a T3 hard code that survived, a held fallback writer (`t2_orchestrator.linear_status`)
  and the elephant-riding policy hold (`t2_rewrite_job`, qa `escalated`), so it never goes public; nor does
  `ai_generated` text whose QA gate did not clear (`escalated` / `failed` / `pending`). The tenant still gets all of
  it in its portal; this is only what is shown under its brand, in line with AA-side held content needing the owner's
  audited publish. The served version of a key: the tenant's own (approved or edited) first, then the latest
  (`created_at`, then `version_number`), so a newer unreviewed model rewrite never replaces the agency's text.
  Widening it (needs_review / escalated text public, or an explicit agency "show on my site" step) is a tech-lead
  decision on the S278 list.
- **qa_status only inside the policy.** The policy reads `qa_status`; catalog_owner gets no grant on it (a policy's
  column references need none) and the view exposes no gate column. The view's WHERE repeats the status /
  `edit_source` arms; the QA arm is the policy's alone.
- **Itinerary shape.** `rewritten_content.itineraries` is a string or the writer's JSON day list
  (`t2_orchestrator.stored_text`). The view renders a day list like `day_parse.written_itinerary_text` ("Day N —
  Title" + body, body falling back to description, blocks separated by a blank line) and a list of strings joined by
  lines; nested non-string elements of a non-day list are dropped (Python would join a dict's values).
- **The key, not the tour id.** A version points at one `published_tours` row; the view maps it to the catalogue key
  (`raw_tours.source_key`) and joins `catalog.v_tour` by key, so an AA source re-upload keeps the tenant's text and AA
  liveness (ADR 0015) still wins: a retired or paused AA tour leaves the view at once.
- **Tenant scope inside the view.** Only tenants in service (trial, active, past_due), not kind internal, with a
  TripPlanner subscription: the same scope as `catalog.v_tenant_tripplanner_v1` (379). TripPlanner still checks
  `served` before it reads the view.
- **How catalog_owner reads tenant versions.** A column grant (the eight content columns, never the gate columns of
  the tenant projection rule) and a policy `catalog_owner_tenant_text_read` (SELECT, publishable versions only). The
  policy is a status condition, not `true`, so the RLS catalogue guard rule t needs no allowlist entry.
- **Trip page key.** `GET /v1/trip/{id}` returns `source_id` = `COALESCE(source_group_id, tour_id)`, the
  `catalog.v_tour` key (CIS 258 `source_key` rule). The expression, not the stored `source_key` column, because the
  integration replay skips 258.

## Changed

- Migration 403 (separate migration-only PR, class contract): `catalog.v_tenant_tour_v1`, SELECT to `tripplanner`
  only; column SELECT for `catalog_owner` on `gold_aa_internal.tenant_tour_versions` and its read policy.
- `api/routers/v1_trip_page.py`: `source_id` in the page answer (the route is untyped, so `openapi.json` does not
  change).

## Tradeoffs

- The view joins the full `catalog.v_tour` (security_barrier, so it is not flattened): every read computes the live
  tours once (~900 on Dev). Acceptable for a per-tenant list; a later minor can join `catalog._live_tour` and compute
  the few derived columns itself if it shows up in the browse Lambda's timings.
- Conservative publish rule: on Dev many versions are `needs_review` or QA-escalated, so an agency's site lists
  fewer tours until it edits (or, later, approves) them. The alternative (unreviewed or held text under the agency's
  brand) is what review flagged; the tech lead can widen it.
- The agency's text wins over a newer model rewrite: after a re-rewrite the site keeps the agency's edit until the
  agency saves an edit of the new text. A portal approve / "show on my site" control would make that explicit.
- No AA-text fallback: a tenant whose rewrites are still running shows fewer tours. The alternative (AA text under the
  agency brand) is what the audit called a leak.
