# AA-1094: tenant tour view, agency branding off AA pages, source_id on the trip page

S278 system audit items M20 (no `catalog.v_tenant_tour_v1`), M21 (agency brand and Sign in on the wrong pages) and
M12 (the CIS trip page has no catalogue key, so "Book now" can book another tour). Root ADR 0019 d10 / d11.
The CIS side is two PRs: migration 404 (the view, contract) and this one (the trip page key).

## Decisions

- **What goes public in the view (migration 404, revised after review).** A tenant row exists for a live AA tour when
  the tenant has a version publishable on its site: status `approved` (the tenant approved it), the agency's own edit
  as the portal writes it (`edit_source = 'tenant_edit'`, status `pending`: the edit route's insert; the portal has no
  approve button), or a model's rewrite at `ai_generated` whose `qa_status = 'passed'`. `needs_review` is NOT only the
  score signal: it also marks a T3 hard code that survived, a held fallback writer (`t2_orchestrator.linear_status`)
  and the elephant-riding policy hold (`t2_rewrite_job`, qa `escalated`), so it never goes public; nor does
  `ai_generated` text whose QA gate did not clear (`escalated` / `failed` / `pending`). The tenant still gets all of
  it in its portal; this is only what is shown under its brand, in line with AA-side held content needing the owner's
  audited publish. The served version of a key: the tenant's own (approved or edited) first, then the latest
  (`created_at`, then `version_number`), so a newer unreviewed model rewrite never replaces the agency's text.
  Widening it (needs_review / escalated text public, or an explicit agency "show on my site" step) is a tech-lead
  decision on the S278 list.
- **qa_status only inside the policy.** The policy reads `qa_status`; catalog_owner gets no grant on it (a policy's
  column references need none) and the view exposes no gate column. The view's WHERE repeats the status /
  `edit_source` arms; the QA arm is the policy's alone.
- **Itinerary shape.** `rewritten_content.itineraries` is a string or the writer's JSON day list
  (`t2_orchestrator.stored_text`). The view renders a day list like `day_parse.written_itinerary_text` ("Day N —
  Title" + body, body falling back to description, blocks separated by a blank line) and a list of strings joined by
  lines; nested non-string elements of a non-day list are dropped (Python would join a dict's values).
- **The key, not the tour id.** A version points at one `published_tours` row; the view maps it to the catalogue key
  (`raw_tours.source_key`) and joins `catalog.v_tour` by key, so an AA source re-upload keeps the tenant's text and AA
  liveness (ADR 0015) still wins: a retired or paused AA tour leaves the view at once.
- **Tenant scope inside the view.** Only tenants in service (trial, active, past_due), not kind internal, with a
  TripPlanner subscription: the same scope as `catalog.v_tenant_tripplanner_v1` (379). TripPlanner still checks
  `served` before it reads the view.
- **How catalog_owner reads tenant versions.** A column grant (the eight content columns, never the gate columns of
  the tenant projection rule) and a policy `catalog_owner_tenant_text_read` (SELECT, publishable versions only). The
  policy is a status condition, not `true`, so the RLS catalogue guard rule t needs no allowlist entry.
- **Trip page key.** `GET /v1/trip/{id}` returns `source_id` = `COALESCE(source_group_id, tour_id)`, the
  `catalog.v_tour` key (CIS 258 `source_key` rule). The expression, not the stored `source_key` column, because the
  integration replay skips 258.

## Changed

- Migration 404 (separate migration-only PR, class contract): `catalog.v_tenant_tour_v1`, SELECT to `tripplanner`
  only; column SELECT for `catalog_owner` on `gold_aa_internal.tenant_tour_versions` and its read policy.
- `api/routers/v1_trip_page.py`: `source_id` in the page answer (the route is untyped, so `openapi.json` does not
  change).

## Tradeoffs

- The view joins the full `catalog.v_tour` (security_barrier, so it is not flattened): every read computes the live
  tours once (~900 on Dev). Acceptable for a per-tenant list; a later minor can join `catalog._live_tour` and compute
  the few derived columns itself if it shows up in the browse Lambda's timings.
- Conservative publish rule: on Dev many versions are `needs_review` or QA-escalated, so an agency's site lists
  fewer tours until it edits (or, later, approves) them. The alternative (unreviewed or held text under the agency's
  brand) is what review flagged; the tech lead can widen it.
- The agency's text wins over a newer model rewrite: after a re-rewrite the site keeps the agency's edit until the
  agency saves an edit of the new text. A portal approve / "show on my site" control would make that explicit.
- No AA-text fallback: a tenant whose rewrites are still running shows fewer tours. The alternative (AA text under the
  agency brand) is what the audit called a leak.

## Lane l19 (S278): serving a synthetic agency for the live Done-when

The S278 live check could not show "a synthetic tenant path lists only its adopted tours": the only served synthetic
tenant is a `demo` one (AA catalogue), and the synthetic agencies with publishable tenant text have no TripPlanner
subscription, so `catalog.v_tenant_tripplanner_v1` has no row for them and TripPlanner answers `tenant not found`.

### Decisions

- **The staff path already exists; only the agent could not use it.** A TripPlanner subscription is made by the
  `tenant_provision` saga's attach mode (`POST /admin/tenants/{id}/provision`, Tenant 360 › Subscription "Add an
  add-on"), audited (`acp_shared.audit_log` row naming the request key, `subscription.changed` /
  `entitlement.changed` feed rows, the AA-884 `staff.request` row). The plan `tripplanner.hosted` carries `tp.hosted`
  and `tp.launcher` (CIS 355), so the view's `served` becomes true. No new route, no UI change, no migration.
- **No maker-checker.** The TripPlanner plans have no price (`price_usd_monthly` NULL, CIS 355 "price to set"), and the
  billing tick moves synthetic tenants only on Dev; the attach is the same single-admin write it is for any admin.
- **A10b-4: the Dev-only E2E CIS admin may attach / cancel a TripPlanner add-on of a synthetic tenant.** Same pattern as
  A10b-1..3: the two routes on `E2E_ALLOWED_WRITES` + their concrete paths (middleware), and a route-level check
  (`admin_tenant_provision._refuse_e2e`) before the job is enqueued: every product in `E2E_ADDON_PRODUCTS`
  (`tripplanner` only: a CRM add-on carries seats, a licence count) and the tenant synthetic
  (`e2e_staff.is_synthetic_tenant`: `is_canary IS TRUE` and not the pilot). The create route stays refused.
- **Book now needs no code.** The agency's own switch is Settings › Payments "Online booking" (AA-Partner
  `PUT /settings/online-booking`, owner only, audited); the orchestrator signs in as the synthetic CRM agency's owner
  as in the S278 verify scripts. A bookable tour needs a Booking fixed departure sold to that agency: the lane l18
  fixture runbook (`python -m app.e2e_fixtures --apply --run <run> --agency-tenant <id>` in AA-Booking) makes one; no
  second seeder here.

### Changed

- `api/core/e2e_staff.py`: `E2E_TRIPPLANNER_ADDON_WRITES`, `E2E_ADDON_PRODUCTS`, two concrete paths.
- `api/routers/admin_tenant_provision.py`: `_refuse_e2e` on attach and cancel (log `tenant_provision_e2e_refused`).
- Tests: `tests/unit/test_aa1094_a10b_tp_addon.py`; the reviewed allow-list in `test_aa816_e2e_cis_admin.py`.
- Agent-only evidence spec `tests/e2e/admin-evidence/tp-addon.spec.ts` (E2EADMIN=1, never CI).
- `CONTEXT.md` (A10b paragraph).

### Tradeoffs

- Allowing the whole attach route but checking the product in the route (rather than a new narrower route) keeps one
  staff path: the evidence shows the real drawer, not a test-only endpoint.
- A future priced TripPlanner plan would still be attachable by A10b on a synthetic tenant. Acceptable: synthetic
  tenants only, Dev only, and A10b is removed at go-live with the A10 family.

### Should know

- Root ADR 0006a gets the A10b-4 amendment in the root PR of this lane.
- The A10b session must be the one doing the write; the A10d customer_success identity stays fully read-only.
- Clean-up after the evidence: `E2E_CANCEL=1` on the same spec cancels the add-on (the row stays, `canceled`).

### Live steps (orchestrator, in order)

The live Done-when has two separate halves: (A) a synthetic agency served by TripPlanner lists only its adopted tours,
(B) "Book now" on an AA tour page creates the line for that page's `source_id`. They use different synthetic agencies:
(A) a CIS tenant with publishable tenant text (`audit-atlas-hearth`), (B) the synthetic CRM agency whose owner the
S278 verify scripts sign in as (`sen-vang`). Tenant ids are looked up live (Tenant 360), never written here.

1. **Ship.** Merge the root PR (ADR 0006a A10b-4), then the CIS PR (no migration). Deploy the CIS api, wait for the
   rollout COMPLETED, then `GET https://api-cis.lumiguides.it.com/health` 200 with `git_sha` = the merge commit. CIS
   migration 404 (`catalog.v_tenant_tour_v1`) and the TripPlanner browse code that reads it are already on main; the
   migration-apply run must show `cis/404` applied (class contract) before step 4 means anything.
2. **Dry run.** `E2EADMIN=1 E2E_DRY_RUN=1 TENANT_SYNTHETIC=<audit-atlas-hearth tenant id> npx playwright test
   --project admin-evidence tp-addon` (AWS_PROFILE=aa365-admin, from `apps/AA-CIS-App`). The log line must show kind
   `agency` and account_status `trial`, `active` or `past_due`; otherwise the view's scope excludes the tenant and the
   attach proves nothing: stop and pick another synthetic agency with tenant text.
3. **Attach.** The same command without `E2E_DRY_RUN` (add `TENANT_REAL=<a real tenant id>` for the 403
   `e2e_read_only` check). Expect the drawer's job `succeeded`, a `tripplanner` subscription `active`/`trialing` and
   the `tp.hosted` / `tp.launcher` entitlements; screenshots `aa1094-tp-addon-*`.
4. **TripPlanner serves the agency.** Wait at least 30 s (the TripPlanner BFF caches a browse 404 that long,
   `frontend/lib/tenantSite.ts`), then rerun the S278 lookup on `/browse/tenant/audit-atlas-hearth` and
   `/browse/tenant/audit-atlas-hearth/tours`: both 200, source `tenant`, only tours the agency adopted, each with the
   tenant's own text (not the AA catalogue text). Then the tour-list Playwright check on
   `https://tripplanner.lumiguides.it.com/audit-atlas-hearth/plan` (List of tours) and one
   `/audit-atlas-hearth/tours/{slug}` page 200, at 1440 and 390, light and dark. An empty tours list means the tenant
   has no publishable version (see Decisions of the view): note it, cancel the add-on (step 9) and repeat 2-4 on a
   synthetic agency that has one.
5. **A bookable tour for (B)** (needs the AA-Booking E2E fixture PR of lane l18 merged and deployed). In the Booking
   api container (ECS exec on `aa-booking-dev-api`): `python -m app.e2e_fixtures --run <run> --agency-tenant <sen-vang
   tenant id>` (DRY RUN). It exits 3 `refused: no confirmed booking of a synthetic agency on a departure ...` when
   sen-vang has never booked a departure: then first confirm one booking for sen-vang on any open fixed departure
   (the agency's own Booking path, as in the S278 crm-13 check) and rerun the DRY RUN. Then `--apply` with the same
   run. Note `tour_source_id` and `departure_id` from its JSON. The departure starts 60+ days ahead, inside the
   widget's 365-day window.
6. **The trip page of that tour.** The Book now widget (AA-Partner `GET /crm/public/v1/book/{key}?tour=`) lists only
   the open fixed departures of the page's own tour, so the page must be the fixture's tour, NOT the S278 verify page
   (`/trip/a26bdf3f…`, a different `source_id`). Read the page id in the same container:
   `SELECT tour_id::text, slug FROM catalog.v_tour WHERE source_id = '<tour_source_id>'` (role `booking` has SELECT).
   Check `GET https://api-cis.lumiguides.it.com/v1/trip/<tour_id>` answers `source_id` = `<tour_source_id>`.
7. **Online booking on.** As the sen-vang owner (`signInCrm` of the S278 verify lib), `PUT /crm/v1/settings/online-
   booking` `{"enabled": true}`, 200. The CRM product cache keeps the agency's offer 5 minutes
   (`api/app/booking/products.py` TTL_S): if the widget says the tour is not bookable right after step 5, wait and
   reload once.
8. **Book now.** Open `https://go-dev.lumiguides.it.com/trip/<tour_id>?f=<sen-vang intake form key>` (form key masked
   in every output), pick the fixture departure, a party of 2 adults, invented traveller details on the E2E mailbox
   domain, submit. Expect the widget's `tour` = `<tour_source_id>`, the submit
   (`POST /crm/public/v1/book/{key}/bookings`) 201, and in the agency CRM the new trip whose proposal line carries
   `tour_source_id` = `<tour_source_id>` and the fixture `departure_id`. Screenshots at 1440 and 390, light and dark.
9. **Clean-up.** Online booking off again (`PUT ... {"enabled": false}`); `E2E_CANCEL=1` on the tp-addon spec for
   audit-atlas-hearth (subscription `canceled`, the row stays); cancel the fixture departure with the l18
   `e2e-writers` cancel test (A10e-1, `{"status": "cancelled"}`), which also shows the agency CRM's cancel case.
