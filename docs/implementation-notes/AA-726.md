# AA-726 — Idempotent T11 publish

## Step 0 — current state (11/10/2026, read from code + `db-schema-reference.md`)
- `acp_shared.publish_log` (migration 116) had **no dedup**: no unique key, no pre-call state.
  `publish()` called WordPress/Facebook first and wrote the row afterwards.
  - Timeout after WordPress returned 201 → exception → row `failed` with no `external_id` → the
    retry posted a **second** article.
  - Two quick clicks (or bulk publish re-run) on the same piece → two posts. Re-publishing an
    already-published piece also inserted a new row and posted again.
- Credentials: already in Secrets Manager (`acp/cms/{tenant_id}`, `acp/social/...`), the DB row
  holds only the secret's key name; `GET /v1/integrations/*` never returns the secret; publish
  logs only the key name on read failure. **Scope item 5 needed no change.**

## Decisions
- **Revision = sha256(content_text)[:16]** — `content_piece` has no revision column, and the
  text is what gets posted. Key `"<piece_id>:<channel>:<hash>"`. Edited text → new key → a new
  post (deliberate re-publish).
- **`requested` row before the remote call** + partial unique index on `idempotency_key` where
  status is `requested`/`published` (migration 215). The index is what stops concurrent clicks;
  the `FOR UPDATE` on the piece's rows only orders sequential ones.
- **Same revision already published → replay** the stored row (`replayed: true`, no remote call).
  Fresh `requested` → **409**. `requested` older than 120 s (adapters time out at 30 s) → stale,
  reclaimed as a prior attempt.
- **Read-before-retry only when there was a prior attempt** of this revision (stale requested,
  failed row of the same key, or a pre-215 failed row with no key). WordPress: the publish now
  sets a slug unique to the revision (`<title-slug>-<hash8>`) and looks it up with
  `GET /posts?slug=…&status=…&context=edit`. Facebook: Graph API has no idempotency key, so the
  last 25 Page feed posts are matched on the exact message. **A lookup that fails raises** →
  attempt recorded `failed`, nothing posted blind.
- The remote post id stays in the existing `external_id` column (no `remote_post_id` rename).
- Failed rows are still reused in place (pre-AA-726 behaviour), now as the claimed row.

## Changed vs. the issue
- Scope 4 (bulk publish through `shared.job`, one child job per piece) **not done here**. With
  the endpoint idempotent, the portal's sequential bulk loop can no longer double-post; moving it
  to the job runner is a separate change (UI progress, job kind, caps) — proposed as follow-up.
- Migration file lives in `api/migrations/215_*.sql` (numbering + integration tests) and is
  applied to Dev from the identical copy in AA-CIS-Infra `db/migrations/cis/` via the new
  `db-migrate` workflow (Nghiệp, S225: migrations go through the Infra repo).

## Tradeoffs
- Facebook lookup by message can miss if the post is not in the last 25 feed items or Facebook
  altered the text; acceptable for a retry window of minutes. WordPress lookup is exact.
- `list_pending` now also hides pieces with an in-flight `requested` row, so a piece does not
  flicker back as "pending" while it is being published.
