# AA-1025 slice C1 (S263 lane gw-c1-providers) — the Providers page: switches, latency / error rate, new rows

Plan: root `docs/audits/2026-11-01-S263-gateway-gap-audit/plan.md` slice C1 (+ the UI of B1). No migration, $0.

## Decisions

- **Latency and error rate per connection come from the ledgers, two windows (24 h and 7 d).** One grouped query per
  ledger, both windows in the same scan (`FILTER`), bounded by `created_at >= now - 7 d` (the `created_at` indexes):
  - LLM connections and Jev: `shared.llm_call_log` grouped by `coalesce(connection_key, account)` (Jev rows carry
    `connection_key = 'typesafe'` since B1, CIS #1218). Only ledger v2 rows (`status IS NOT NULL`, since 31 Oct 2026).
  - DataForSEO: `shared.dfs_call_log` (cache hits left out: no provider call).
  - Geoapify: `geo.geocode_call` (`requests`, `failed_requests`; it stores no latency, so p50 / p95 stay null).
- **What counts.** `calls` = attempts that reached the provider (status other than `refused`); `errors` = `error`,
  `billed_unusable`, `truncated` (a cut answer is a failure, plan E1); `refused` is counted apart (our own guard or a
  switch said no, nothing sent) and is not in the error rate. p50 / p95 = `percentile_cont` over the non-refused
  attempts' `latency_ms`. The row's top-level `latency_p50_ms`, `latency_p95_ms`, `error_pct` are the 24 h figures
  (the Done-when curl); `stats` carries both windows.
- **CRM rows through crm.ops.v1 with the staff member's own token** (the Calls tab pattern, no cross-schema read): one
  `GET /llm/usage` (month to date: spend today / this month, split by stage) and one `GET /llm/calls` page (last 7 days,
  newest 500 rows: latency and error rate computed here with the same interpolation as `percentile_cont`). The CRM's
  guard rows (stage `crm_scrub`, provider `bedrock_guardrails`) make the **Bedrock Guardrails** row; every other stage
  makes the **Partner CRM AI** row. When the 7 d window holds more than one page, `stats["7d"].sampled = true`.
- **Guardrails row** takes the registry facts of `bedrock-guardrails` (failure domain, access state, balance source)
  but not its `enabled` (seeded off; the CRM's client reads its own settings, not this switch, so "Off" would be
  wrong). Both CRM rows say `switch = "crm_settings"` and have no toggle.
- **Mapbox row is static** (T-13): TripPlanner's map tiles, free tier, nothing logged; `status = "untracked"` (not
  counted in "Need a look"), a link to the Mapbox console for usage. No call, no key read.
- **Real switch for Jev / DataForSEO / Geoapify** (B1 made the clients read it): `enabled` is the registry row's value
  for all three (Geoapify too: "configured as the geocoder" moved to its own `configured` field and still turns the row
  Off with its own reason). `switchable` is true for those three when the registry row exists; the page shows a
  Switch off / Switch on button with a confirm dialog that calls the existing `PATCH /admin/llm-connections/{key}`
  (`{enabled}`), no new write route.
- Off wins over the other statuses for these rows (reason `switched_off_in_registry`), except Circuit open / Cap reached
  which never apply to them.

## Changed

- `api/services/ai_gateway.py`: stats queries + pure builders, CRM / Guardrails / Mapbox rows, registry overlay
  (switchable, Geoapify `configured`), `read_providers(..., crm_usage_rows=, crm_calls=)`.
- `api/services/platform_apps.py`: `crm_llm_usage_rows` (the raw `/llm/usage` rows with their stage).
- `api/routers/admin_ai_gateway.py`: the providers route relays the caller's token to the two CRM reads.
- Frontend: `lib/aiGateway.ts` (types, `untracked`, `guard` group, stats helpers), `ProvidersTab.tsx` (Errors ·
  latency column, access badge, switch + confirm, Guardrails section, CRM / Mapbox cells), `messages.ts`, `guide.ts`,
  `guide.vi.ts`.

## Tradeoffs

- The CRM's 7 d stats read one page (500 rows) rather than paging to the end: the page loads every 2 minutes and the CRM
  has very few calls today; the flag says when it is a sample.
- LLM connection status is not changed by the error rate (the circuit already says Degraded / Open); only the CRM rows,
  which have no circuit here, turn Degraded when most of the last 24 h failed.
- The CRM spend is added to the page totals (the page is "every paid source"); it depends on the caller's sign-in, so a
  session without a Cognito token sees the totals without the CRM (its rows say why).
