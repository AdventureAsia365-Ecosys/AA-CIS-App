# AA-1026 — lane gw-acc2-333: stage parsers read the first complete JSON value

S263 (01/11/2026). The live acc2 contract smoke (job `llm_contract_smoke`) passed 11 of 12 stages on Dev;
`t9_faq_filter` failed on both acc2 models in `faq_filter.parse_verdicts`:

- nova-lite: `invalid JSON: Extra data: line 7 column 6 (char 134)`
- llama4-scout: `invalid JSON: Extra data: line 1 column 89 (char 88)`

The companion migration (333, acc2 before the OpenAI API hop on the judge / validate routes) is a separate PR and
is written up in `AA-1026-gw-acc2-fallback.md`.

## Decisions

- **Root cause read from the error positions, not guessed.** Both positions are exactly what the old parser
  (first `{` to last `}`, then `json.loads`) reports for a BARE list of verdict items whose first item is
  `{"n": 1, "label": "KEEP", "reason_code": "on_subject", "confidence": "high", "note": ""}`: Nova Lite printed the
  list with `indent=4` (item 1 closes at line 7 column 5 of the slice, the `,` after it is char 134), Llama 4 Scout
  on one line (item 1 is 88 characters, the `,` is char 88). The slice started at item 1 because the reply had no
  `{"items": ...}` wrapper. So the fix needs two things: read the first complete JSON value (not first-brace to
  last-brace), and accept the bare items list as the items list. `test_aa1026_json_reply.py` rebuilds both replies
  and asserts the old parser's exact messages, then that the new parser reads them.
- **One shared helper**: `shared/llm_client/json_reply.first_json_value(raw, kinds=(dict,) | (dict, list),
  scan=True|False)` built on `json.JSONDecoder().raw_decode`. More than one parser needed it (see Changed), and
  `places.locate` already had its own copy (AA-990), now replaced by the shared one.
- **Scan only top-level brackets.** With `scan=True`, a bracket that does not decode (a `{n}` in leading prose) is
  skipped up to its matching close (strings respected) and the next bracket after it is tried. A bracket that is
  never closed (a cut-off reply) ends the scan. So a value NESTED inside the real answer is never returned as the
  answer: a truncated `{"items": [{...}, {...` stays an error instead of reading item 1 as the reply.
- **`scan=False` before a json_repair salvage** (`source_facts._parse_json`, `place_cards._parse_json`): only the
  first bracket is decoded; when it does not decode (trailing comma, cut-off reply) the reply goes to json_repair
  exactly as before.
- **Shape checks are not loosened.** Every item is still checked (label / verdict, number in range, one answer per
  question); a dict without `items` is still "no items list". The only envelope change: a top-level list is read as
  the items list in `faq_filter` and `faq_answer_fit` (the sibling stage, same prompt shape, same risk).
- **Fences are not stripped** in the helper: the bracket after a fence is found as is and the closing fence is
  trailing text. Stripping all ``` (the old locate helper did) could alter a JSON string value.

## Changed

- `services/acp_content_writing/faq_filter.py` `parse_verdicts`, `faq_answer_fit.py` `parse_fit_verdicts`: the
  helper with `kinds=(dict, list)`; error texts kept (`no JSON object in the reply`, `invalid JSON: ...`,
  `no items list`, `bad item`, ...).
- `services/places/days.py` `parse_llm_days`: the helper with `kinds=(dict, list)` (it already accepted both); leading
  prose and trailing text no longer fail the day block (was `json.loads` after a whole-reply fence strip).
- `services/places/locate.py` `json_object`: delegates to the helper (same `AnswerUnreadable` and message prefix).
- `services/acp_shared/atom_extraction.py` `atoms_from_reply` (new): the atomize reply's `atoms` list; used by
  `a3_atomize` (was `json.loads(strip_json_fence(...))["atoms"]`, so a note after the fence failed the day) and by the
  smoke's atomize case (which now runs the stage parser itself). `a3_atomize` catches `ValueError` (the helper's
  `JsonReplyError` is one; `JSONDecodeError` was one too).
- `services/content_generation/source_facts.py`, `services/acp_shared/place_cards.py` `_parse_json`: the helper
  (scan off) before json_repair. Before, "object + a note holding an object" went to json_repair, which returns a
  LIST for two values, and the parsers read a list as nothing (no facts / empty card) — silently.
- `tests/unit/test_aa1002_no_behaviour_change.py`: `json_reply.py` classified in `CALL_PATH` (pure, no I/O).
- CONTEXT.md: "Reply parsing" sentence in the gateway / contract smoke paragraph.

## Tradeoffs

- Not touched: the schema-forced stages (`s1_brand_audit` / `t2_brand_audit`, `t10_claims`,
  `a3_place_dedupe_check`) keep `json.loads`: their reply is the forced tool input on Converse (or OpenAI strict
  `response_format`), always one JSON object; dedupe also has its own regex fallback. Changing them would hide a
  broken structured-output path instead of surfacing it.
- `days.RULE_VERSION` is not bumped: a reply that parsed before parses to the same value now; only replies that
  failed before (and fell back to the rules) now read. Bumping would re-run (and pay for) every tour's skeleton.
- Locate: the old copy also tried braces nested inside a cut-off wrapper (`{"places": {"A": [...], "B": [`) and could
  return the inner map as a partial answer; now that reply is unreadable and goes to the AA-990 "ask again as two
  halves" path, which is the designed recovery for a cut-off answer.
- Accepting a bare items list is an envelope change on a customer-facing filter. The items are still checked one by
  one, so a list that is not exactly one valid verdict per question is refused as before.
