# AA-977 — CRM-B5: AA-authored content in CIS (prep packs, starter templates, campaign blocks)

Source: Linear AA-977; root design `docs/audits/2026-10-21-S246-crm-design-v3/design-v3.md` §5.9 and §6.3 (card
CRM-B5: "AA-authored content: Before you go prep packs (R38), starter templates (R9), campaign content blocks (R14);
versioned, EN + VI, editor + publish; served over catalog.http.v1. R: draft content is never served. E: a newer
version is published and the CRM still fetches the version it uses"); root contract
`docs/contracts/catalog.http.v1.openapi.yaml` 1.2 (AA-977 S0: `group_key`, `limit`, ETag / 304 on the list).

Slices: S1 migration 275 (this file's first PR), S1b the Infra byte copy, S2 the backend (store, served routes, admin
API), S3 the admin editor page, S4 the seed.

## Decisions

- **One `content_id` per locale.** The contract's version path `/aa-content/{content_id}/versions/{version}` returns one
  body in one locale, so the EN and VI copies of a pack are two items. They are paired by `group_key`
  (`^[a-z0-9][a-z0-9-]{1,79}$`, UNIQUE with the locale), the additive field of contract 1.2.
- **Two tables + one view in `gold_aa_internal` (CIS 275).** `aa_content_item` (kind, locale, group_key, retired) and
  `aa_content_version` (draft | published, title, body_markdown, applies_to, content_hash, published_at / by). The
  served reader reads only `v_aa_content_published`, which has no draft row, so rule R is enforced in SQL, not only in
  code.
- **Rule E is a trigger, not a convention.** `aa_content_version_guard` (BEFORE INSERT OR UPDATE OR DELETE):
  a version is inserted only as a draft numbered `max(version) + 1`; a published row never changes and is never
  deleted (`restrict_violation`, asyncpg `RestrictViolationError`); a draft may be edited, discarded (DELETE) or
  published once. With the partial unique index "one draft per item", the draft is always the newest version.
  `aa_content_item_guard` keeps `content_id`, `kind`, `locale`, `group_key` and `created_*` fixed: a published
  version is served with its item's kind / locale / group_key, and its `content_hash` covers them.
- **The migration proves the trigger on the real DB.** Guard 3 runs a probe item in a sub-block that always ends in a
  private SQLSTATE (`ZZ275`) and is therefore rolled back: draft not in the view, published row in it, update /
  delete / direct insert of a published row refused, second draft refused, locale change refused.
- **Grants: `cis_app` only, explicit.** The Dev default ACL of `cis_owner` gives `cis_app` full DML on every new table
  (CIS 245); the file REVOKEs ALL first, then grants item SELECT / INSERT / UPDATE (an item is retired, never deleted),
  version SELECT / INSERT / UPDATE / DELETE (DELETE = discard a draft; the trigger refuses a published row), view
  SELECT. Nothing for `aa_app_user` (AA-859 invariant v3: no tenant-pool privilege on a relation without RLS),
  `catalog_owner` or PUBLIC. Guard 2 checks the exact set.
- **No RLS.** No tenant column and no personal data: AA-authored marketing text, the same reasoning as 272's lifecycle
  record. Writers are labels (`admin:<shared.admin_users id>`, `seed:AA-977`), at most 64 characters, as in
  `api/routers/admin.py::_admin_actor`.
- **`applies_to` is checked against the contract shape in SQL**: a JSON object whose keys are at most `country_codes`
  and `tours` (AaContent.applies_to has `additionalProperties: false`). The values are validated in code (S2:
  ISO2 codes from the AA country list, tour keys `{source_system: cis, source_id}`).
- **`content_hash` format is fixed in SQL** (`^sha256:[0-9a-f]{64}$`), set exactly when the row is published, with
  `published_at` and `published_by` (one CHECK).
- **Seed size (S4), the plan contradiction resolved.** The plan's S4 text lists 10 prep-pack groups (VN, TH, KH, LA, MM,
  ID, JP, KR, NP, BT) + 2 starter templates + 2 campaign blocks, each in EN and VI, while its test line says
  "24 groups × 2 locales = 48 items". The listed content is the decision: **14 groups × 2 locales = 28 items**
  (20 prep-pack items, 4 template items, 4 campaign-block items). The S4 DRY RUN must print 28 to create; on Dev one
  of them stays a draft for the rule R check, so the live EN prep-pack list shows 9 or 10 items depending on which
  locale the draft is.

## Tradeoffs

- **Trigger vs. code-only immutability.** A trigger costs one `max(version)` read per insert and makes a mistaken
  `UPDATE` of a published row fail loudly; code-only rules would leave rule E to every future writer (seed script,
  editor, a hand-run fix). The cost is negligible at this table's size (tens of rows).
- **Kind consistency inside a group is not enforced in SQL.** EN and VI items of one group should share the kind; an
  exclusion constraint would need `btree_gist`. The store (S2) refuses a second locale of a group with another kind.
- **No `updated_at` trigger.** The store sets `updated_at` explicitly, because the editor uses it for optimistic
  concurrency (expected `updated_at` → 409); a trigger would hide the value the client must echo back.
