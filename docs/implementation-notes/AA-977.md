# AA-977 — CRM-B5: AA-authored content in CIS (prep packs, starter templates, campaign blocks)

Source: Linear AA-977; root design `docs/audits/2026-10-21-S246-crm-design-v3/design-v3.md` §5.9 and §6.3 (card
CRM-B5: "AA-authored content: Before you go prep packs (R38), starter templates (R9), campaign content blocks (R14);
versioned, EN + VI, editor + publish; served over catalog.http.v1. R: draft content is never served. E: a newer
version is published and the CRM still fetches the version it uses"); root contract
`docs/contracts/catalog.http.v1.openapi.yaml` 1.2 (AA-977 S0: `group_key`, `limit`, ETag / 304 on the list).

Slices: S1 migration 275 (this file's first PR), S1b the Infra byte copy, S2 the backend (store, served routes, admin
API), S3 the admin editor page, S4 the seed.

## Decisions

- **One `content_id` per locale.** The contract's version path `/aa-content/{content_id}/versions/{version}` returns one
  body in one locale, so the EN and VI copies of a pack are two items. They are paired by `group_key`
  (`^[a-z0-9][a-z0-9-]{1,79}$`, UNIQUE with the locale), the additive field of contract 1.2.
- **Two tables + one view in `gold_aa_internal` (CIS 275).** `aa_content_item` (kind, locale, group_key, retired) and
  `aa_content_version` (draft | published, title, body_markdown, applies_to, content_hash, published_at / by). The
  served reader reads only `v_aa_content_published`, which has no draft row, so rule R is enforced in SQL, not only in
  code.
- **Rule E is a trigger, not a convention.** `aa_content_version_guard` (BEFORE INSERT OR UPDATE OR DELETE):
  a version is inserted only as a draft numbered `max(version) + 1`; a published row never changes and is never
  deleted (`restrict_violation`, asyncpg `RestrictViolationError`); a draft may be edited, discarded (DELETE) or
  published once. With the partial unique index "one draft per item", the draft is always the newest version.
  `aa_content_item_guard` keeps `content_id`, `kind`, `locale`, `group_key` and `created_*` fixed: a published
  version is served with its item's kind / locale / group_key, and its `content_hash` covers them.
- **The migration proves the trigger on the real DB.** Guard 3 runs a probe item in a sub-block that always ends in a
  private SQLSTATE (`ZZ275`) and is therefore rolled back: draft not in the view, published row in it, update /
  delete / direct insert of a published row refused, second draft refused, locale change refused.
- **Grants: `cis_app` only, explicit.** The Dev default ACL of `cis_owner` gives `cis_app` full DML on every new table
  (CIS 245); the file REVOKEs ALL first, then grants item SELECT / INSERT / UPDATE (an item is retired, never deleted),
  version SELECT / INSERT / UPDATE / DELETE (DELETE = discard a draft; the trigger refuses a published row), view
  SELECT. Nothing for `aa_app_user` (AA-859 invariant v3: no tenant-pool privilege on a relation without RLS),
  `catalog_owner` or PUBLIC. Guard 2 checks the exact set.
- **No RLS.** No tenant column and no personal data: AA-authored marketing text, the same reasoning as 272's lifecycle
  record. Writers are labels (`admin:<shared.admin_users id>`, `seed:AA-977`), at most 64 characters, as in
  `api/routers/admin.py::_admin_actor`.
- **`applies_to` is checked against the contract shape in SQL**: a JSON object whose keys are at most `country_codes`
  and `tours` (AaContent.applies_to has `additionalProperties: false`). The values are validated in code (S2:
  ISO2 codes from the AA country list, tour keys `{source_system: cis, source_id}`).
- **`content_hash` format is fixed in SQL** (`^sha256:[0-9a-f]{64}$`), set exactly when the row is published, with
  `published_at` and `published_by` (one CHECK).
- **Seed size (S4), the plan contradiction resolved.** The plan's S4 text lists 10 prep-pack groups (VN, TH, KH, LA, MM,
  ID, JP, KR, NP, BT) + 2 starter templates + 2 campaign blocks, each in EN and VI, while its test line says
  "24 groups × 2 locales = 48 items". The listed content is the decision: **14 groups × 2 locales = 28 items**
  (20 prep-pack items, 4 template items, 4 campaign-block items). The S4 DRY RUN must print 28 to create; on Dev one
  of them stays a draft for the rule R check, so the live EN prep-pack list shows 9 or 10 items depending on which
  locale the draft is.

### S2 backend (served routes, admin API)

- **Served reads on the main pool (cis_app), not AA-976's tenant pool.** The tables are in gold_aa_internal, where
  `aa_app_user` has no grant (AA-859 invariant), so the tenant-pool semaphore does not apply. Each read is one
  statement in a READ ONLY transaction; an acquire waits at most 5 s, then 503 `unavailable` + `Retry-After: 5` (the
  `services/catalog_http` pattern).
- **Answers.** Bad `kind` / `locale` / `limit` / cursor, a `content_id` that is not a uuid or a `version` that is not
  1..2^31-1 → 400 `invalid`. A draft, an unknown version or an item never published → 404 `not_found` without
  `reason` (contract 1.2 sample `aa-content-draft-not-found-valid.json`). A published version of a retired item →
  200: the CRM keeps the version it uses; only the list hides a retired item (contract 1.2 description).
- **Caching.** A version's ETag is its stored `content_hash`; the list's ETag hashes the page body (as `listTours`).
  `Cache-Control: private, max-age=60`, `Vary: Authorization`, 304 on `If-None-Match` (the AA-976 helpers).
- **Cursor** `v1.<b64 content_id>.<fingerprint>` (the AA-976 format), the fingerprint bound to kind, locale and
  limit, so a cursor reused with other filters or another page size is 400.
- **`content_hash`** = `services.catalog_http.mapping.content_hash` (the AA-976 function) over the served AaContent
  body without the hash, computed once at publish and stored. `published_at` is serialized with its microseconds
  (`2026-10-24T08:00:00.654321Z`), so the body rebuilt from the row hashes to the stored value (unit + integration
  tests check it).
- **Admin concurrency token = the item's `updated_at`** for every write (save, discard, publish, retire, restore);
  every write moves it (`clock_timestamp()`). One token per item, not per version: the editor reads one item at a
  time and any write by someone else should make it reload.
- **Admin error body** `{detail, code[, field]}` (the AA-913 shape): 422 field rules (with `field` for the editor),
  409 `stale` / `retired` / `no_draft` / `duplicate` / `already_retired` / `not_retired`, 404.
- **Admin list `status` filter**: `draft` = a draft is waiting (also on a published item), `published` = some version
  published and not retired, `retired`. Each row carries `state` (draft | published | retired), `published_version`,
  `draft_version`, the newest version's title and country codes. `country` filters on the newest version's
  `applies_to.country_codes`. Server-side `limit` (1-100) / `offset` with `total` (lesson S218).
- **Visa rule** (`validate.publishable`; widened in the review round below): the body is cut into blank-line
  separated sections, a section of headings only joins the next one; a section matching `visa`, `visas`, `e-visa`,
  `eVisa` or `thị thực` needs an `https://` link (`http://` does not count). Only for `prep_pack`, only at publish (drafts may be incomplete).
- **Actor** = `admin:<shared.admin_users id>` of the verified Cognito identity, else of `x-admin-user-id` (the BFF
  sends it), else `admin:unknown`; cut to 64 characters (CIS 275 CHECK).

### S2 review round (independent reviewer, S250)

- **Visa rule widened.** The text is NFC-normalized first (some input methods type Vietnamese decomposed, which the
  pattern missed), and the pattern also matches `eVisa` / `evisa` / `e-visas` (no word boundary before the `v`).
  "Visa card", "Visa debit/credit" and "Visa/Mastercard" are a payment card and are blanked before the match, so a
  payment line no longer needs an official link. A section with both a card and a real visa mention is still refused.
- **Storage missing = 503, not 500.** `asyncpg.UndefinedTableError` (code deployed before CIS 275 is applied) maps to
  503 `unavailable` + `Retry-After: 5` on the served routes (`reader.content_connection`) and on every
  `/admin/aa-content` route. A safety net only: the merge order below still applies.
- **Discard refuses the only version** (409 `only_version`) when nothing was ever published: the item cannot be
  deleted by cis_app, so an empty item would hold its (group_key, locale) slot forever. The editor edits the draft
  or retires the item instead.
- **`PUT .../draft` is a full replace**: `body_markdown` and `applies_to` are required (`""` / `{}` allowed), so a
  client that omits a field gets 422 rather than a silent wipe. Starting draft n+1 takes exactly what is sent; the
  S3 editor pre-fills it from the published version.
- **Group lock in `create_item`**: `pg_advisory_xact_lock(hashtext('aa_content_group:' || group_key))` before the
  group read, so concurrent EN / VI creates with different kinds cannot both pass the kind check.
- **Served version path refuses leading zeros** (`/versions/01` → 400): one spelling, one cache key per version.
- **Store unit tests** (`tests/unit/test_aa977_store_unit.py`, scripted connection): store.py unit coverage 38% →
  99%; full unit total 85.78% → 86.06% (floor 85%).

## Tradeoffs

- **Trigger vs. code-only immutability.** A trigger costs one `max(version)` read per insert and makes a mistaken
  `UPDATE` of a published row fail loudly; code-only rules would leave rule E to every future writer (seed script,
  editor, a hand-run fix). The cost is negligible at this table's size (tens of rows).
- **Kind consistency inside a group is not enforced in SQL.** EN and VI items of one group should share the kind; an
  exclusion constraint would need `btree_gist`. The store (S2) refuses a second locale of a group with another kind.
- **No semaphore on the served reads.** The main pool has 10 connections per api task and every read is one indexed
  statement; a per-process gate like AA-976's would add a second limit to tune for no measured need. The acquire
  timeout still turns starvation into a fast 503.
- **The admin unit tests stub the store**; the store's SQL and the trigger run on real Postgres in
  `tests/integration/test_aa977_aa_content_store.py` (as cis_app). An in-memory SQL fake would have tested the fake.
- **No `updated_at` trigger.** The store sets `updated_at` explicitly, because the editor uses it for optimistic
  concurrency (expected `updated_at` → 409); a trigger would hide the value the client must echo back.

### S4 seed (`data/aa_content/seed_v1.json`, `scripts/aa977_seed_aa_content.py`)

- **Size: 14 groups x EN + VI = 28 items** (the decision above): 10 prep packs (VN, TH, KH, LA, MM, ID, JP, KR, NP,
  BT; `applies_to.country_codes` = the one country), 2 starter templates (welcome message, pre-departure checklist;
  R9) and 2 campaign blocks (newsletter intro, seasonal highlight; R14), `applies_to` = `{}` for those four groups.
  Hand-written, no LLM, $0. Each prep pack has the same seven sections: entry and visa, health and insurance (a
  reminder only), money, power plugs, dress code, weather and seasons, local etiquette.
- **The deliberate draft is `prep-pack-bhutan:vi`** (`keep_draft` in the file): the rule R check uses its version 1
  (404), and the live EN prep-pack list still shows all 10 packs (VI shows 9).
- **Visa and entry links are the governments' own sites**, written as Markdown links so a sentence's full stop never
  becomes part of the URL: evisa.gov.vn, thaievisa.go.th + tdac.immigration.go.th (the Thailand Digital Arrival
  Card), evisa.gov.kh, laoevisa.gov.la, evisa.moip.gov.mm, evisa.imigrasi.go.id, mofa.go.jp (visa page), k-eta.go.kr
  + visa.go.kr, immigration.gov.np + nepaliport.immigration.gov.np (online arrival form), immi.gov.bt +
  bhutan.travel (Department of Tourism). Checked on 25/10/2026 with curl: 200 for all but three, which refuse
  automated clients and were judged by their government domain: evisa.gov.kh (a bot challenge page), mofa.go.jp
  (403 to scripts) and evisa.imigrasi.go.id (202 with a script-only page). `tests/unit/test_aa977_seed.py` pins every
  prep-pack link to a government host list. The texts avoid claims that change often (visa-free lists, fee amounts):
  they send the reader to the official page instead.
- **Template placeholders** are `{{traveller_first_name}}`, `{{trip_name}}`, `{{agency_name}}`, `{{agent_name}}`,
  `{{destination}}`, `{{departure_date}}`. The CRM has no merge-field convention yet; AA-963 (library) decides the
  rendering and may map these names.
- **The script goes through `services.aa_content.store`** (the admin API's own code and checks), as actor
  `seed:AA-977`. DRY RUN by default (SELECT only, READ ONLY transaction) after validating every item with the create
  and publish rules. `--apply` creates only missing `(group_key, locale)` pairs (idempotent, never touches an
  existing item); `--publish` publishes only items the seed created, never published, still at draft v1 (a human's
  later draft is never published by the script); a refused publish is listed in `failed` (exit 1) instead of
  stopping the run. `--expect N` guards the create count; `--edit-demo G:L` is the rule E check (draft v2 = the
  published text + one "Last reviewed" line, then publish; v1 keeps its hash).
- **Tracked with `git add -f`**: `.gitignore` ignores `scripts/` and `data/` (every tracked script is force-added,
  e.g. aa983). The seed is hand-written AA content, not a data export, so it is safe in this public repo. Neither
  path is in Deploy Dev's `paths`, so merging this PR restarts nothing.
- **Runs from /tmp in the api container**: the image has `services/` under /app but no `scripts/` or `data/`, so the
  script adds /app to `sys.path` and takes the seed with `--seed /tmp/seed.json` (both files via S3 presign; the
  commands are in the script's docstring). It prints the seed file's sha256 to compare with the repo file.
