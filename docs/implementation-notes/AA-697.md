# AA-697 — Docs reader shows the bundle's SVG diagrams

Session S256 (2026-10-28). The root repo branch `docs/aa-697-aws-diagrams` adds the architecture diagrams (Python
`diagrams` with the official AWS icons, rendered to self-contained SVG) and rule 9 of the docs bundle builder: a
checked SVG is published byte for byte under `docs-reader/assets/<repo>/<path>.svg` and listed in the manifest's
`assets`. This branch lets `/admin/docs` show them.

## Decisions

- **`GET /admin/docs/asset?repo=&path=`**, same policy (`ops.read`, admin only) and same lookup model as `/page`: only an
  asset the manifest lists for the caller, read by the manifest's key after a shape check (`assets/<repo>/<path>.svg`,
  type `image/svg+xml`), never by a caller path. Owner tier honoured although the builder only emits `staff`.
- **Re-check on every read** (`docs_reader.svg_is_safe`, same rule as the builder's `svg_problems`): an SVG that fails is
  refused with 503 and logged (`docs_reader_asset_refused`), never served or "cleaned". No redaction: a marker inside
  the base64 icons would corrupt them, and the builder already fails the build on an ID in the text.
- **Shown through `<img>`**, not inlined: an SVG used as an image cannot run script or load anything, so no DOMPurify
  pass is needed on the client. Opened on its own (the figure links to it), it is a document, so the API sends a sandbox
  CSP (`default-src 'none'; img-src data:; style-src 'unsafe-inline'; sandbox; frame-ancestors 'none'`) + nosniff, and
  the BFF re-adds them (`lib/upstreamHeaders.ts`) because it forwards Content-Type only.
- **Only relative paths that resolve to a listed asset** load (`resolveImage`); remote, protocol-relative, `data:` and
  other schemes stay alt text, so the old "no remote image" rule (viewer IP) still holds.
- **White frame in dark mode too**: the diagrams are drawn on Graphviz's white canvas.
- Cache: 32 assets for 5 minutes per process, keyed by (key, sha256), like pages.

## Tradeoffs

- The safety rule is duplicated (root builder and this API). Both have tests with the same bad cases, and the real
  diagrams were checked against both. A shared package is not worth it for ~15 lines across two repos.
- `<img>` cannot show hover or selectable text in the diagram; acceptable for static architecture views.

## Should know

- Order: merge the root branch first (Docs sync uploads `assets/` and a manifest with `assets`); this API ignores a
  manifest without `assets`, and an older API ignores the new field, so either order is safe.
- Not verified in a browser in this lane (light lane: no `next build` / Playwright). Unit tests, eslint and a type check
  of the changed files ran; the orchestrator should run the UI smoke on the preview and open
  `/admin/docs?path=docs/architecture/diagrams/README.md` after the Docs sync run.
- Independent review (S256): the regex-only re-check let namespace-prefixed elements (`<s:script>`, XHTML
  `<h:iframe>`), a prefixed `x:href` to an outside URL, XML character references in style values, CSS escapes,
  `<?xml-stylesheet?>` and `xml:base` through. `svg_is_safe` now also parses the SVG and allowlists the element tree
  (mirror of the root `svg_tree_problems`). The `<img>` path and the sandbox CSP already kept those inert; the check now
  matches its docstring. After the deploy, confirm on the preview that `GET /api/admin/docs/asset` answers with the
  sandbox CSP and not only the global one from `next.config.ts` (both share the header name).
- CI fixes (S256): CodeQL `py/redos` flagged the one-regex prolog check (`(?:<!--.*?-->\s*)*` backtracks exponentially
  on `<!--` + many `--><!--`); the prolog (XML declaration, comments, at most one DOCTYPE, then `<svg`) is now walked by
  `_svg_starts_ok()` with the same acceptance, plus a linear-time test. The root builder's `svg_problems` may carry the
  same pattern: worth the same change there. The 12-digit fixture is built at run time (the resource-ID guard refuses
  the literal), the CSS comment in `MarkdownView.tsx` no longer names the issue (it ships inside the style text), and
  `docs/api/openapi.json` is regenerated with the new `/admin/docs/asset` route.
