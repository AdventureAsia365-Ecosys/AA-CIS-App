# AA-451 — T7 slot-grid không persist Slot, khiến angle_gate_request.cta luôn NULL

## STEP0 (investigation, before build)

Confirmed by reading the real code (not assumed):
- `GET /v1/planning/slot-grid` (`api/routers/v1_planning.py::get_slot_grid()`) is explicitly
  documented "Compute (read-only)" — `compute_slot_grid()` is pure, no DB write. This was a
  **deliberate AA-448 design choice**, not an oversight: it exists specifically so the
  tenant-scoped fetchers (`fetch_tenant_trips`/`fetch_tenant_atoms_by_trip`,
  `services/acp_planning/tenant_pool.py`) never get entangled with the *separate*,
  already-known-buggy platform-wide persist path (`allocate_month()` →
  `runway.fetch_trips()`/`quarter.fetch_atoms_by_trip()`, the functions AA-445-02 flagged for
  the `owner_scope` tenant-scoping bug).
- The only existing persist path (`create_weekly_produce_run`/`persist_slot_grid`/
  `allocate_and_persist_week`, `services/acp_planning/allocator.py`) is wired through
  `allocate_month()`, which calls the buggy platform-wide fetchers — reusing it as-is for the
  tenant self-service flow would silently persist a *different* (wrong) slot set than what the
  tenant actually sees in `GET /v1/planning/slot-grid`'s response.
- Frontend reality check: `AngleGateTab.tsx` (T8 UI) picks an atom straight from T6's atom list
  (`GET /api/tenant/admin/atoms`) — it does **not** route through T7's slot-grid page at all.
  There is no existing "year/month" UI context for T8 to inherit today.

Presented 3 options to Nghiep (A — persist inline in T7's GET; B — T8 persists on demand;
C — new explicit tenant "confirm slot grid" action mirroring quarter-plan preview/finalize).
**Nghiep confirmed Option B.**

## Decisions

- **Option B, as specified by Nghiep**: `services/acp_angle_gate/service.py::create_request()`
  gains optional `year`/`month` params. When given, and no persisted slot is already found via
  the existing `_fetch_slot_cta()` lookup, compute that tenant's month slot-grid using the
  SAME tenant-scoped fetchers `GET /v1/planning/slot-grid` uses
  (`fetch_tenant_planning_config`/`fetch_approved_quarter_plan`/`fetch_tenant_trips`/
  `fetch_tenant_atoms_by_trip`/`compute_runway_map`/`compute_slot_grid`) — never
  `allocate_month()`/`allocate_and_persist_week()` (those still call the buggy platform-wide
  fetchers; reusing them here would reintroduce the exact cross-tenant bug T7 was written fresh
  to avoid). New helper lives in `services/acp_angle_gate/service.py` itself (not
  `acp_planning/`), since it's this module's own concern and keeps zero-diff on the
  already-verified `acp_planning`/T7 code.
- **Persist trigger stays scoped to real usage, not browsing**: persist only fires inside
  `create_request()` (a T8 write, "tenant is actually starting this content"), never from a GET.
  Avoids the Option-A risk flagged during STEP0 (a GET creating rows on every idle preview view,
  and `ON CONFLICT DO NOTHING` silently locking in stale atom picks from the first view).
- **`ON CONFLICT (slot_id) DO NOTHING` kept as-is** (same semantics `persist_slot_grid()` already
  has for the admin path) — verified safe for this call site specifically because the compute-
  and-persist branch only runs when `_fetch_slot_cta()` already found nothing, i.e. this is the
  first time this (tenant, year, month, week, trip, channel) slot is ever persisted from any
  path. No existing row to go stale against.
- **Re-read after persist, not trust-the-in-memory-value**: after `persist_slot_grid()`, the
  code re-calls `_fetch_slot_cta()` rather than returning the freshly-computed
  `Slot.cta_target` directly — matches AA-448's own "stale in-memory object" lesson (re-fetch
  from DB after a write, don't hand-carry pre-write state) and doubles as a correctness check
  that the persist actually landed.
- **Backward compatible**: `year`/`month` default to `None`. Omitted → identical behavior to
  before this change (`cta` may be `None`, T9's existing fallback still asks the tenant).
- **Frontend month inference**: `AngleGateTab.tsx` has no existing month-picker UI (the atom
  picker is generic, T6-sourced, not tied to any T7 month view). Per Nghiep's "infer from
  existing UI context, don't make the tenant type it" instruction, and since there genuinely is
  no explicit month context in this component, the natural inference is **the current calendar
  month** (`new Date()`) — this is also what real production timing means in practice (content
  is written for the current/imminent month, not an arbitrary future one). Documented here as a
  self-chosen default since the issue didn't specify it.

## Changed

- `services/acp_angle_gate/service.py`: `create_request()` new optional `year: int | None`,
  `month: int | None` params; new `_compute_and_persist_slot_cta()` helper.
- `api/routers/v1_angle_gate.py`: `CreateRequestBody` gains optional `year`/`month`.
- `frontend/.../AngleGateTab.tsx`: `startRequest()` now sends the current year/month.
- No migration — reuses `acp_shared.acp_v2_runs`/`acp_v2_slots` (migration 096/103) and
  `acp_shared.angle_gate_request.cta` (migration 114) unchanged.

## Tradeoffs

- If the atom doesn't land in any slot for the inferred current month (e.g. its trip is on
  cooldown, or its destination isn't in this month's quarter-plan share), the compute-and-persist
  branch finds no matching slot and `cta` stays `None` — T9's existing ask-the-tenant fallback
  still covers this. Not solved further here; out of scope (T9's fallback already exists exactly
  for this class of gap, per AA-450).
- No quarter plan finalized yet for that tenant/year/quarter → `fetch_approved_quarter_plan`
  returns `None` → treated as "can't compute, cta stays None", not an error surfaced to the
  tenant at T8 create time. T8 should still work even if the tenant hasn't touched T7 at all.

## Should know

- This does **not** touch `GET /v1/planning/slot-grid`'s response shape or add any DB write to
  it — per the issue's explicit "not in scope."
- Does **not** touch `allocate_month()`/`allocate_and_persist_week()`/`admin_produce.py`'s N7
  trigger path — zero risk to the already-verified admin-trigger flow (AA-377/378/410).
- T9's existing CTA-fallback UI (ask tenant, 422) is intentionally left in place, not removed —
  it now fires less often, not never.
