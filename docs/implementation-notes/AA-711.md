# AA-711 — Draining ECS task keeps claiming jobs after a deploy

## Decisions
- The worker yields (stops claiming, keeps running its jobs) while a live worker of a **newer ECS
  task-definition revision** exists. Revision comes from the task metadata endpoint v4
  (`$ECS_CONTAINER_METADATA_URI_V4/task` → `Revision`); `JOB_WORKER_TASK_REVISION` overrides it.
- "Live" = `stopped_at IS NULL` and seen in the last 45 s (workers write every 15 s). If the new task
  fails its health check and dies, its row goes stale and the old worker resumes claiming.
- Unknown revision (local / standalone without metadata) never yields and never makes others yield.
- Stored in a new column `shared.job_worker.task_revision` (migration 199), not inside `caps`
  (`caps` is the kind → concurrency map the Jobs page reads).

## Changed
- Nothing else in the claim path; the reaper and heartbeats keep running on a yielding worker.

## Tradeoffs
- Comparing revisions (not "latest started") keeps a future multi-task service (AA-651) working:
  two tasks of the same revision both claim.
- A rollback to an older revision makes the rolled-back (lower) task yield to the faulty one until
  the faulty task stops; acceptable — ECS stops it within the drain window.

## Should know
- **Migration 199 must be applied before this code is deployed**: otherwise the yield query fails
  every cycle and the worker claims nothing (the cycle error is caught and logged). Applied on Dev
  01/10/2026 before the PR.
- Evidence of the bug: deploy :417 COMPLETED 06:03:29 UTC; job 0c81e8fe (s1_seo_prefetch, 06:04:34)
  ran on the :416 worker `ip-10-2-10-49` (stopped 06:08:07) and wrote the old keywords.
