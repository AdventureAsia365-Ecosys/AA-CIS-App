  AA-546/548/551/554 all used).
- **Tested against production, not local dev.** The issue only requires real UI evidence, not a
  specific environment; production was already confirmed live (task def `:238`) and needs no
  tunnel/local build step, so it was the faster path to real screenshots.
- **DB reads used the same S3-mediated ECS exec pattern** (`aa365-admin` profile, cached STS
  session, no MFA prompt needed this session) to confirm real row counts before and after the
  live-verify, and to resolve 2 schema surprises the browsing turned up (see Should know).

## Findings — per surface

### Surface 0 — naming correction (blocks everything else if skipped)

The issue's own surface list ("T4 Browse Pool", "T9 Write/My Catalog") doesn't match the actual
T-numbering in the shipped code/CONTEXT.md. Real mapping, confirmed by reading
`frontend/app/(tenant)/portal/_components/Sidebar.tsx`'s `NAV1` array and each route's own
top-of-file comment:

| Sidebar label | Route | Real T-stage | What it is |
|---|---|---|---|
| **Browse Pool** | `/portal/t1-rewrite` | **T1** | platform-wide A3 pool, tenant picks a tour + fires rewrite |
| **My Catalog** | `/portal/t4-pool` | **T4** | tenant's own rewritten-tour catalog (T3-approved) |
| Slate | `/portal/t7-planning` | T7 | per-tenant Segment/Route/Score → Subject proposals |
| Write Content | `/portal/t8-angle-gate` | T8+T9 (one wizard) | Goal → 3 Angles → Write (fires automatically) |
| Review | `/portal/t10-review` | T10 (tenant-facing half) | ready/not-ready + full atom/goal/angle/DFS-PAA context |
| Publish | `/portal/t11-publish` | T11 | WordPress connect + per-piece publish (blog only) |

So "T4 Browse Pool" in the issue is really **T1** (browse the platform pool) — T4 is the
*separate*, already-rewritten catalog. Both were screenshotted below since the issue's intent
(what a tenant sees/picks from before content-planning starts) spans both.

### 1. T1 Browse Pool / T4 My Catalog

**Real, live, working — genuinely platform-wide pool.** Screenshot `01_t1_browse_pool.png`: 31
tours, real search/country/duration/sort filters, real quality-score badges, 2-page pagination,
an "In progress" badge on tours mid-rewrite. Screenshot `02_t4_my_catalog.png`: 15 tenant-owned
catalog entries with `Queued`/`In Catalog`/`Ready to Review`/`New Version Requested` tab filters,
version numbers (`v1`/`v2`), an `EXTRA QA PASS` badge on 2 rows. Both match the real DB counts
independently confirmed via RDS (`gold_aa_internal.tenant_tour_versions` = 15 rows for this
tenant; the platform pool backing T1 draws from 763 total `v_trip_registry` rows platform-wide).

**Route metadata: NOT shown on either page — confirmed absent in source, not just missed in the
screenshot.** `grep -in "route\|hub" PoolTab.tsx CatalogTab.tsx` returns zero matches. Neither
component receives or renders `route_id`/`hub_name` at all. **This is not classified as a gap**:
Route/Hub are content-planning concepts derived from an atomized, segmented tour (T5→T7+); T1/T4
are about picking/tracking a *tour* (pre-content), where a Route (a multi-day, multi-Segment
itinerary slice) has no data to render yet. Route metadata legitimately first appears at T7
(Slate) and downstream — see below — which is the correct place for it, not a hole at T1/T4.

Subjects, screenshot `09_slate_tiktok_tab.png`), then clicked "Chọn viết" on "Don Det and Don
Khone islands — cross French colonial-era bridge" (a Segment-backed Subject, rank 5). This made a

Classified: **đã build đúng, chỉ thiếu polish** — the mechanism (8 real Goals, real subtitles)

### 3. T9 Write / "My Catalog" (content-history question)

**Confirmed: there is no separate T9 route, and the CLAUDE.md note is accurate.** T9 fires
automatically as step 3 of the same `/portal/t8-angle-gate` wizard the instant an Angle is chosen
— confirmed by reading `AngleGateTab.tsx` and by the empty-state copy itself ("Choose a content
goal, then pick 1 of the 3 angles the system generates... Write Content always starts from
[Slate]"). Direct-navigating to `/portal/t8-angle-gate` with no context shows a "Nothing to write
yet" empty state (screenshot `04_t8_write_wizard.png`); appending a bare `?subject_id=` query
param does **not** resume the wizard (screenshot `11_t8_write_wizard_with_subject.png` — same

Slate's own "Chọn viết" navigation) works. Minor, real finding: a bare `subject_id` deep link is
not a supported entry point today; not blocking, since the only real UI path (Slate → click) does
work.

**"My Catalog" is NOT a content-piece history view** — despite the label, it is T4's tour catalog
(rewritten tours), unrelated to written social/blog Pieces. **The actual Piece history view is
T10 Review** (see below), which is the closer match to what AA-501/AA-555 mean by "tenant sees
their own written content." This is a real naming-overlap point worth flagging for whoever specs
the next round: "My Catalog" (tours) and "Review" (Pieces) are two different lists that could
easily be conflated by a spec-writer working from the sidebar labels alone.

## Comparison to Ms. Thư's `aa-social-media` reference repo

Read `docs/AI-gent-for automation works/aa-soscial-media-main/CLAUDE.md` and
`src/aa_social/{subjects,cli,sinks/base}.py`. The reference pipeline is 6 CLI stages (`ingest →
atoms → research → score → slate → write`), with exactly **4 human decisions between `slate` and
`write`**:

```
aa subjects offered [--channel Blog]   # what Slate proposes
aa subjects pick <id>                  # the human's pick
aa subjects goal <id> [<Goal>]         # 1 of 8 Goals
aa subjects angles <id> [--again]      # 3 ranked Angles generated
aa subjects angle <id> <1|2|3>         # the human's angle choice
```

This maps almost exactly 1:1 onto what was live-verified in AA-CIS-App's T7→T8→T9: Slate's
per-Channel proposal list = `offered`; "Chọn viết" = `pick`; the Goal-card step = `goal`; the
3-angle step (not screenshotted this round, but confirmed reachable from the wizard's own step
indicator `1·Goal > 2·Angle > 3·Write`) = `angles`/`angle`; T9's automatic write = `write`. **The
tenant-operable core of T7/T8/T9 in AA-CIS-App is a faithful, real port of the origin's own
human-decision sequence — this is not a regression or an incomplete port.**

**T11 has no equivalent in the reference repo at all** — confirmed by grep: every "publish" hit
in the reference source (`sinks/base.py`, `cli.py`) refers to a Piece file being written to
`output/pieces/` and marked "live" (not superseded) inside the local SQLite state, never an
external channel/CMS integration. The origin pipeline's own last stage is `write`; there is
nothing to compare T11 against — it is a genuinely new capability AA-CIS-App added beyond the
origin, not a port of anything, so "gap vs. Ms. Thư" doesn't apply to T11 the way it does to
T1/T4/T7/T9/T10.

## Tradeoffs

- **Production vs. local dev**: chose production since it needed no tunnel/build step and the
  issue only asked for real UI evidence, not a specific environment. AA-554's own local-dev
  precedent was for testing not-yet-deployed endpoints; nothing this investigation needed was
  undeployed.
- **Stopped the Write wizard at the Goal-selection step** rather than completing a full write, to
  avoid an additional real Bedrock spend beyond what was needed to prove the T7→T8 hand-off is
  real (a full write was already proven working in AA-554's own Round 2 live-verify on this same
  tenant 2 days ago — re-proving the entire chain again here would have been redundant spend for
  no new evidence value).
- **Did not screenshot the 3-Angle selection step** or a full write cycle, for the same reason —
  the wizard's own step indicator (`1·Goal > 2·Angle > 3·Write`) plus AA-554/AA-450's prior
  live-verifies of that exact step were treated as sufficient existing evidence; re-deriving it
  here would not have changed any surface's classification.
