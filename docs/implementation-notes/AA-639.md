# AA-639 — T3 repair rounds re-rolled blind

## Finding (code-level; log confirmation pending an AWS MFA refresh)
- Live (AA-637 check, version ba4db187): 1 write + 3 full rewrites, ~4 min. The progress trace
  shows the first draft PASSED the graph's judge (it went on to flag_fix/"Polishing"); the extra
  writer calls came after that, i.e. from `run_t3_qa_gate` repair rounds (qa_repair_count=2) plus
  one graph retry inside a round.
- `run_t3_qa_gate` regenerated with `_rewrite_tour(...)` and **no feedback** — `_rewrite_tour`
  always seeded `feedback=""`, although `generate_node` already appends
  "PREVIOUS ATTEMPT FEEDBACK … Please fix these issues" when state.feedback is set. So each
  repair was a random re-roll hoping the next draft happened to pass.
- T3 grounding flags numbers the source never states (`find_novel_numeric_claims`). A writer
  adding outside knowledge ("30-minute flight", ft conversions) is a real catch — the gate is
  right; the repair loop just never told the writer what to remove.

## Changed
- `_rewrite_tour(..., feedback="")` → seeds graph state.
- `t3_repair_feedback(structural, grounding)` builds a capped feedback block (novel numbers + the
  sentence they came from + what to do; structural codes). Passed on every repair round.
- `t3_qa_repair_attempt` log now carries the structural codes and novel numbers (so the next
  investigation can read the cause straight from CloudWatch).

## Not changed
- The gates themselves, MAX repairs (2), the graph's own judge retry loop.
