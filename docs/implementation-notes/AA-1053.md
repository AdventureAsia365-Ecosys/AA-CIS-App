# AA-1053 — One owner for the token-budget retry and one effort rule per provider

W1 contradictions #13 and #14 of the S271 writing-quality audit (root ADR 0020). Lane l7-gateway-retry, S273.

## What was built

**#13, retry ownership.** Since S271 W0 the gateway (`LLMClient._call_key_logged`, rules in
`shared/llm_client/token_floor.py`) owned the truncation retry for every stage except `a3_atomize`, which sat in
`token_floor.NO_RETRY_STAGES` and re-asked a cut read itself at `_TRUNCATION_RETRY_MAX_TOKENS` (8192). That was the
last second owner (the audit's T8 / T9 owners went in W0).

- `token_floor.NO_RETRY_STAGES` = `{"adhoc_conn_test"}` (the connection probe, whose cut is its expected answer).
- New `token_floor.NO_FLOOR_STAGES` = `{"adhoc_conn_test", "a3_atomize"}`: the floor opt-out, split from the retry
  opt-out (they were one set).
- `services/acp_contract/a3_atomize._ask_atoms`: no ceiling of its own; a reply still cut after the gateway's retry
  (or a cut that raised: `token_floor.is_cut_failure`) ends the loop with a failed read. A non-cut parse failure or a
  non-cut error is still asked once more at the same ceiling (AA-645 unchanged).
- Guard `tests/unit/test_aa1053_one_retry_owner.py`: an AST scan of api / services / shared / worker / scripts
  (gateway excluded) that fails on (a) a loop that calls the gateway, reads a cut signal and rebinds max_tokens,
  (b) an `if <cut>:` that calls the gateway, (c) a new loop that calls the gateway and reads a cut without a
  registered reason (`CUT_AWARE_LOOPS`, one entry: a3, backed by a behaviour test). Red on base: it names
  `a3_atomize.py:_ask_atoms (a loop raises max_tokens after a cut)`. Plus the registry test
  (`NO_RETRY_STAGES == {"adhoc_conn_test"}`) and the a3 behaviour tests.

**#14, effort per provider.** New `shared/llm_client/effort_rule.py`, the one module that maps a stage's effort (the
`shared.stage_model_params` row, `stage_params.effort_for`) to each provider kind:

| kind | field |
|---|---|
| Anthropic Messages API | `output_config.effort` via the deployment's `effort_by_stage[stage]` (unchanged) |
| OpenAI / Azure Chat | `reasoning_effort`: low / medium / high as is, xhigh / max as high; reasoning models only |
| Bedrock Converse | `additionalModelRequestFields` only in the form the catalog row states in `capabilities.converse_effort` (`output_config` / `reasoning_effort`); unset = nothing (every row today) |

- `client._call_anthropic_messages`, `_call_openai` and `_call_bedrock_converse` call the rule;
  `stage_params.openai_reasoning_effort` / `OPENAI_REASONING_EFFORTS` are gone (moved into the rule).
- Converse: `LLMResponse.effort` (and the billed-unusable reply facts) = the effort sent; a ValidationException on
  the effort field drops it and retries once (`_converse_dropping_rejected_effort`, not billed), and the reply then
  records no effort.
- Guard `tests/unit/test_aa1053_effort_rule.py`: only effort_rule.py / stage_params.py read `effort_for`, and the
  field names `reasoning_effort` / `effort_by_stage` / `additionalModelRequestFields` appear only in the rule module,
  stage_params.py and the Anthropic adapter (red on base: client.py built `reasoning_effort` and read
  `effort_for`). One test per provider path for one stage (t9_write at medium).

## Decisions

- **a3 keeps its first ceiling (NO_FLOOR_STAGES).** Moving the retry into the gateway without the floor gives the same
  ceilings as before: 4096, then the gateway's retry at double = 8192 (= the old `_TRUNCATION_RETRY_MAX_TOKENS`).
  With the floor, a3 on GPT-6 Luna (catalog `min_output_tokens` 8192, CIS 382) would start at 8192 and retry at
  16000, a request change this issue does not ask for. Flooring a3 is its own measured change.
- **A cut read is not re-asked even when the gateway could not retry** (request already at the model's cap): a second
  ask at the same ceiling would bill the same cut again.
- **Rows stay per model.** The effort rule is the stage x model row; a fallback rung with no row of its own keeps its
  model's default (migration 381's decision: "a fallback never inherits the primary's effort"). #14 is about the same
  (stage, model) getting different efforts on different provider paths, which the explicit map closes.
- **Converse is mapped but gated by a catalog capability.** No probe has shown which Converse field each model takes
  (AA-803), and an unknown field is a 400 that would cost the attempt and move the route. The map exists and is
  tested; a model gets it when a forward migration sets `capabilities.converse_effort` on its catalog row after a
  probe. Until then Converse requests are byte-identical (test `test_converse_without_a_stated_form_is_unchanged`).
- **xhigh / max on OpenAI ask high** (before: nothing sent, the model's default). Every GPT reasoning model takes
  high; no live row sets xhigh / max on an OpenAI model (only CIS 381 writes effort, all on Anthropic models), so no
  live request changes.
- **Ledger effort = the value sent.** No new ledger key: the `effort` column already carries
  `LLMResponse.effort` through `billed_fields` on the caller's row and on every gateway attempt row of the route
  trace. NULL = nothing sent (the model's default).
- The deployment's own `request_defaults.effort` / `effort_by_stage` stay readable by the adapter (a connection fact,
  none set per stage in any migration); the stage row beats them for its stage, as before.

## Changed vs the issue

- Done-when "the live ledger shows at most one truncation retry per attempt over one T9 batch" and "live by the
  ledger effort column on a probe run" are live checks for the orchestrator (live_steps). The Converse half of #14
  sends nothing live until a probe-backed catalog capability exists (follow-up).

## Tradeoffs

- The static guard is a heuristic (names of gateway entry points and cut predicates). It catches the shapes that
  existed (a3) and the obvious new ones; a retry hidden behind a helper function would pass it. The registry
  (`NO_RETRY_STAGES`) and `budget_retry` guards (test_s271_gateway_token_budget.py) cover the gateway side.
- a3 cut reads now count in the `route_cut.<stage>` alert (route_watch leaves out `NO_RETRY_STAGES`). That is
  correct (the gateway retries them now) but may raise a new alert for a3_atomize if GPT-6 Luna cuts > 5 % at 4096.

## Should know

- No migration, no API change, no new table.
- Live behaviour on Dev: a3_atomize cut reads are retried by the gateway (same ceilings, one gateway cut row with
  `budget_cut: true` + the retry's reply with `truncation_retry: true` instead of a3's billed_unusable row + a second
  request); OpenAI xhigh / max: no live rows; Converse: unchanged; Anthropic: unchanged.
- Lesson recorded for the session: a stage opt-out set that does two jobs (retry AND floor) hides a second owner;
  split the sets when moving one job.
