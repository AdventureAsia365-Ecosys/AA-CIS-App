# AA-652 — Long work onto the job runner; job-based status in the portal

Planned with Nghiệp on 28/09 (S201). Split into PRs, one per kind of work:
- **PR-A (this): T2 tenant rewrite** — the source of the stuck "Writing…" report.
- PR-B: T9 write (`content_piece`, Social Content wizard).
- PR-C: A3 atomize (after publish). A1 run-tour / revalidate stay on `shared.pipeline_jobs`
  (AA-223, already has its own table + startup sweep) unless Nghiệp wants them moved too.

## Decisions
- `t2_rewrite` job kind (`services/jobs/t2_rewrite_job.py`): the router creates the pending
  version (quota, audit log unchanged), enqueues the job with idempotency key
  `t2_rewrite:{version_id}`, stores `tenant_tour_versions.job_id`, and returns at once.
- The rewrite code was moved, not rewritten: `_prepare()` (tour dict + brand rules) and
  `_rewrite_and_save()` (SEO, `_rewrite_tour`, T3 QA gate, save) are the pre-AA-652 router code.
- New job-runner hook `on_terminal(pool, job_row)`: runs when a job ends without success
  (failed / stopped_budget / cancelled) — from the worker, the reaper, or an admin cancelling a
  queued job. `t2_rewrite` uses it to set the version `status='failed'` (new CHECK value,
  migration 175).
- The worker now hands shared clients to handlers (`JobContext.resources`, e.g. `redis`), so the
  live-writing view (ADR 0004) works unchanged from inside a job.
- Portal: `job_status` is added to `/v1/tours/my-versions` and `/v1/tours/versions/{id}` (status
  only — no job error text, tenant-safe per AA-613). "Writing…" shows only while the job is not
  finished unsuccessfully; "Queued…" while queued; "Writing failed" + **Retry** otherwise.
- `POST /v1/tours/versions/{id}/retry` re-queues the same job with fresh attempts and sets the
  version back to `pending`. No second quota charge.

## Changed (vs. the Linear issue)
- Root cause found besides deploys: when `_rewrite_tour()` returned a non-success result (no
  exception), the old code wrote nothing and the version stayed `pending` forever. The job now
  raises in that case, so it is retried and finally marked `failed`.
- The old code's catch-all marked a crashed rewrite `needs_review` ("so polling detects
  completion"). Now the job retries once, then the version becomes `failed` with Retry — a
  crashed rewrite is not a draft that needs review.

## Tradeoffs
- `t2_rewrite` concurrency 4 (Bedrock writer), max 2 attempts: one retry covers a throttle or a
  deploy; more would multiply Sonnet cost on a genuinely bad input.
- `services/jobs/t2_rewrite_job.py` imports `_rewrite_tour` from `api.routers.v1_pipeline` (a
  service importing a router module), exactly as the old router code did. Moving `_rewrite_tour`
  into services is a separate refactor.

## Should know
- Migration 175 is additive → apply before the deploy.
- Rows written before AA-652 have `job_id = NULL`; the portal treats them exactly as before.
- Tests: `tests/unit/test_aa652_t2_rewrite_job.py` (handler outcomes, hook, retry endpoint);
  `test_aa469_viec1_t4_t5_split.py` now drives endpoint → enqueued job → handler end to end;
  integration `test_worker_runs_the_terminal_hook_when_a_job_finally_fails`.

## PR-B — T9 write
- `t9_write` job kind (`services/jobs/t9_write_job.py`): the router keeps `start_write()` (the
  fast 404/409/422 pre-flight + placeholder piece) and the audit log, then enqueues the job
  (idempotency key `t9_write:{piece_id}`) and stores `content_piece.job_id` (migration 176).
- Moved, unchanged: `T9_STEPS` and `_run_write_with_progress()` (live progress, AA-637).
  `run_write_background()` itself is untouched.
- `run_write_background()` already turns its own errors into piece status `failed`, so the only
  stuck case was an interrupted process. The job adds a re-queue for that and `on_terminal` →
  piece `failed` when the job itself ends without success.
- No portal change needed: a `failed` piece is already `ready_state="not_ready"`, which the
  wizard and My Content show with their existing Retry.
- A re-run skips a piece that is no longer `processing` (finished before the process died).

## PR-C — A3 atomize
- `a3_atomize` job kind (`services/jobs/a3_atomize_job.py`, concurrency 1, max 2 attempts) runs
  the existing `_run_a3_atomize_background()` (atomize + platform Segment/Score/Route recompute)
  with the new `reraise=True`, so a failure is retried and shows on the Jobs page instead of only
  being logged. Default `reraise=False` keeps the function's old best-effort contract.
- Two triggers now enqueue instead of `asyncio.create_task`:
  - `process_export()` (publish): keyed `a3_atomize:{generated_content.id}` so re-exporting the
    same version does not atomize twice. The enqueue itself is best-effort (logged, never fails
    the already-committed publish) — same contract as the task it replaced.
  - `POST /admin/atoms/atomize`: one job per tour, no key (it exists to re-run un-atomized
    tours). Returns `job_ids`. The kind's concurrency 1 keeps tours sequential, as the old
    single looping task did; one tour failing no longer depends on a try/except in a loop.
- Re-running is safe: `run_t5_atomize()` skips unchanged days by fingerprint and UPSERTs atoms.
- No migration: atomize has no tenant-facing row to mark; the job itself is the status.
- The export Lambda package has no `services/jobs` (and no `services/acp_produce`, which the old
  task needed too). That Lambda has never been invoked (no log streams); `process_export` runs in
  the ECS API.

## Incident during PR-C verification (29/09/2026 00:24–01:02 UTC, Dev only)
- Verification enqueued one `a3_atomize` job for an already-atomized tour (fingerprints skipped
  all 9 days, 0 atomize LLM calls). The chain then ran the platform-wide Segment/Score/Route
  recompute, where `atom_matching` calls `compute_embedding()` straight from async code and that
  function paces Cohere calls with a blocking `time.sleep(3.5)` (AA-610).
- With the worker inside the API process, those sleeps starved the event loop: `/health` timed
  out and ECS replaced the task twice ("Task failed ELB health checks", 00:46 and 00:59 UTC).
- Each replacement is a graceful SIGTERM, so the worker *released* the job (attempt not
  counted) and the new task claimed it again — a loop. Stopped by an admin cancel at 01:02; the
  service went back to steady state, `/health` 200.
- The blocking call itself predates AA-652: the in-process task on publish did the same, but it
  died with the task instead of coming back.

Fix (hotfix PR):
- `a3_atomize` runs the chain in its own thread and event loop (`asyncio.to_thread` +
  `asyncio.run`); it already used its own DB connection, so nothing is shared with the worker's
  loop. Trade-off: cancel/shutdown cannot interrupt that thread; the job is released and the
  thread ends with the process.
- `queue.release()` now counts releases in `progress.releases`: at `MAX_RELEASES` (3) the job
  fails ("stopped mid-run N times") instead of looping; a release of a cancel-requested job ends
  it `cancelled`. The worker runs the terminal hook for both.
