# AA-1064 — Docs reader shows PNG / WebP screenshots

Session S275 (2026-11-10), lane l6. Root repo branch `feat/aa1064-guide-images-lint` adds rule 10 to the docs bundle
builder (a PNG / WebP a published page links is published under `docs-reader/assets/`), the docs lint
`tools/docs/check_images.py`, the Docs sync upload of the new types and the first real screenshot in a guide. This
branch lets `/admin/docs` show them.

## Decisions

- **Same route, more types.** `GET /admin/docs/asset` accepts `.svg`, `.png` and `.webp` paths; the manifest `type` must
  be the type of the suffix (`docs_reader.ASSET_TYPES`), so a PNG listed as SVG (or the other way round) is dropped.
  Lookup unchanged: only an asset the manifest lists for the caller, read by the manifest key, never a caller path, so
  traversal (`../`, `./`, `//`, backslashes, absolute paths) is a 404 with no storage read.
- **Re-check on read** (`raster_is_valid`): the 300 KB cap of docs/STYLE.md (`MAX_RASTER_BYTES`, also the S3 read limit)
  and the PNG / WebP signature; anything else is 503, never served. The builder already checked the metadata for IDs.
- **Headers**: one set for every image (`_IMAGE_HEADERS`, was `_SVG_HEADERS`): type of the suffix, `private,
  max-age=300`, nosniff, inline, the sandbox CSP (harmless on a PNG).
- **Binary through API Gateway**: the CIS REST API Gateway has no `binaryMediaTypes`; the lessons log records it
  corrupting binary uploads (S229). Raw PNG bytes on the way back would be mangled the same way. Instead of an Infra
  change, the route also answers `?encoding=base64` with JSON `{repo, path, type, bytes, sha256, data}` (no-store), and
  the admin BFF catch-all asks for that form on `GET docs/asset` and sends the decoded bytes with the image headers
  (`frontend/lib/docsAsset.ts`). The BFF checks the type, the size cap per type, the length, the sha256 and the
  signature (502 otherwise). SVG goes the same way now, so all docs images share one path.
- `resolveImage` accepts `.svg`, `.png`, `.webp` (and still only a listed asset).
- **AI gateway Guide tab (review fix pass).** The first pass left the tab's `MarkdownView` without `resolveImage`,
  because `/admin/docs/asset` is `ops.read` (admin only) while the tab is `spend.read` (admin, finance, ai_ops):
  pointing the tab at it would show broken images to finance and ai_ops. The review asked for the tab to be delivered,
  so the tab now has its own image route, scoped to its one page:
  - `GET /admin/ai-gateway/guide` adds `doc.assets`: the staff-tier bundle images the guide page or its translation
    links (`docs_reader.linked_images`, a Python twin of the builder's `image_links` / `resolve_image` and of
    `lib/docsReader.ts resolveImage`: fenced code and inline code skipped, remote / other-scheme / climbing paths
    ignored). Only computed when the page links an image (no extra manifest read otherwise; the manifest is cached).
  - `GET /admin/ai-gateway/guide/asset?path=&encoding=` (POLICY `spend.read`): re-reads the guide by its fixed id,
    recomputes that list and serves the path only when it is in it, through `docs_reader.load_asset(..., owner_read=
    False)` (staff tier, re-checked on read). Any other path, an owner-tier image, or a guide that is owner tier is
    404 with no image read. Same raw / base64 answer as `/admin/docs/asset` (`admin_docs.asset_response`, body from
    `docs_reader.asset_json`).
  - Frontend: `imageTarget` split out of `resolveImage` (`lib/docsReader.ts`), `guideImage` + `GUIDE_ASSET_API` in
    `lib/aiGatewayGuide.ts`, `GuideTab` passes it to `MarkdownView`; the BFF decodes `ai-gateway/guide/asset` like
    `docs/asset` (`lib/docsAsset.ts GUIDE_ASSET_PATH`). BFF rule unchanged: `API_READ_RULES` prefix `ai-gateway`
    already covers it.

## Tradeoffs

- base64 JSON costs ~33 % more bytes between API and BFF (a 300 KB screenshot is ~400 KB of JSON) and a decode in the
  BFF. Adding `binaryMediaTypes` to the REST API instead would be a shared Infra change that also alters how every other
  route's bodies are handled; not worth it for a few screenshots. Revisit if the reader ever serves large files.
- The raw form stays (default) for a caller that reaches the service directly and for tests; the BFF never uses it.
- The API does not re-check metadata for IDs (the builder does, and the bundle only comes from Docs sync).

## Should know

- Deploy order is free: an older API drops PNG / WebP manifest entries (its shape check is `.svg` only); an older bundle
  has no such entries.
- The Guide tab route widens nothing beyond the tab's own page: finance and ai_ops already read that page's text there
  (AA-1042); now they also get the images that page links, and still no other bundle image (`/admin/docs/asset` stays
  `ops.read`). `docs/architecture/ai-gateway.md` has no image today, so `doc.assets` is `[]` on Dev until a picture is
  added to that page; the path is covered by unit tests with invented images.
- `linked_images` must resolve like the root builder and `resolveImage`; the three are kept in step by their tests
  (same cases: relative, `./`, `../`, leading `/`, query / fragment, percent-decoding, climbing above the root).
- Not checked in a browser in this lane (no login). After deploy (API and admin) and the root Docs sync run, open
  `/admin/docs?path=docs/guides/cis-admin-runbook.md`, section 6, in EN and VI.
- Local `tsc --noEmit` errors in `MarkdownView.tsx` / `MermaidDiagram.tsx` came from a stale shared `node_modules`
  (missing `react-markdown`, `remark-gfm`, `mermaid`, `dompurify`); the changed files type-check and lint clean.
