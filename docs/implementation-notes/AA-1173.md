Session S290, lane d-compliance-evidence. The whole picture (Infra bucket and role, the root collector, the hand step
for the read-only GitHub App) is in the root repo `docs/implementation-notes/AA-1173.md`; this file covers AA-CIS-App.
Two CIS PRs (MIG-4): the migration-only PR (CIS 481, `compiled_defaults.json`, its integration test) and this code PR
(branch from `origin/main`, without the migration; chain: cis/481 applied before it).

## Decisions

- **Sealed evidence is read by the API, not pushed into it.** The collectors write write-once objects and a
  hash-chained manifest per source into the Object Lock bucket; `api/services/compliance_store.py` reads the newest
  manifest of each sealed source (this month, else last month), checks the bundle's SHA-256 and the link to the
  previous manifest, and only then ingests the bundle with `object_key` / `object_sha256` on every row. A mismatch is
  state `broken` (error log, nothing ingested). One chain step is checked per read; a full chain walk is a follow-up
  (it is cheap, but the page read should stay a few GETs).
- **The docs reader file stays a second path** for `root_daily` until the root workflow stops writing it; the
  unique key `(source, check_id, collected_at)` makes the second copy of the same run add nothing, and the sealed copy
  is read first so the stored row names its object.
- **Bucket name never in the repo**: `COMPLIANCE_EVIDENCE_BUCKET`, else `aa-cis-dev-compliance-evidence-<account>`
  from STS (the bronze bucket pattern). Unit and integration conftests set the variable, so no test asks STS.
- **DB checks reuse the X2 catalogue rules.** `db_rls_policies` (rules a b c d t) and `db_grants` (p g e) run the
  same rules and allowlist the CI guard and the nightly Infra dump use, on the live catalog (pg_catalog views every
  role reads, so `cis_app` sees booking / tripplanner / crm without a grant). The rules file is not in the Docker image
  (tests/ is not copied), so `shared/compliance/rls_catalogue_rules.py` is a byte copy, kept equal by
  `tests/unit/test_aa1173_compliance_db_checks.py`; `.flake8` ignores E501 for that one file so the bytes can stay
  identical. A finding is a fail with no threshold: the allowlist (with a one-line reason) is the reviewed exception
  path, a security invariant, not a tolerance.
- **The job** `compliance_db_checks` is daily (03:00 UTC, idempotency key per day, ops metrics sampler part, switch
  `COMPLIANCE_DB_CHECKS` default on, background, deploy-gate exempt, max 2 attempts). The Refresh action still collects
  `cis_db` on demand (the 10-minute bound stays). `cis_db` joins the heartbeat sources; `prowler_weekly` does not (a
  weekly source is graded by its own validity window, 216 h by default).
- **Exceptions follow the Platform › Settings maker-checker rule**: the proposer approves only while
  `cis.settings.two_person_approval` is off (tech lead S287 Q13: one tech lead for now), recorded as `self_approved`;
  the proposer cannot "reject" their own proposal (CIS 481 CHECK), they withdraw it (revoke of an open proposal). A
  rejection needs a note. The expiry window (`cis.compliance.exception_max_days`) is checked at proposal and again at
  approval. Exceptions never change a score; the control keeps its state and shows "Accepted risk".
- **Monthly review** records the overview numbers the page shows at that moment (scores per framework, control and
  check counts, failing / stale check ids, silent collectors, exception counts) plus notes and actions; one per month
  (current or previous month only). Its date feeds `monthly_review_recent`, graded by
  `cis.compliance.review_max_age_days`.
- **Writes need a verified Cognito sign-in** (not E2E read-only, not view-as), like the settings registry, because
  maker-checker needs a real identity. The list answer carries `viewer` so the page can mark "your" proposals.
- **Body model names are prefixed** (`ComplianceExceptionBody`, `ComplianceDecisionBody`, `ComplianceReviewBody`): a
  second `DecisionBody` made FastAPI rename the settings registry's schema in openapi.json (a 1,800-line diff).

## Changed

- New: `api/services/compliance_store.py`, `api/services/compliance_exceptions.py`,
  `services/jobs/compliance_db_checks_job.py`, `shared/compliance/rls_catalogue_rules.py` (copy),
  `frontend/app/admin/platform/compliance/GovernanceTabs.tsx` + `governance.messages.ts` (EN + VI).
- `compliance.py`: sealed read in the cached sync, `object_key` / `object_sha256` on insert and reads, exceptions on
  control rows, drawer and overview; `compliance_db.py`: three checks; `compliance_settings.py`: five keys (CIS 481).
- Router: seven routes (two GET, five POST), route policy + snapshots, openapi.json, readiness raised to 481.
- Job registry lists (deploy gate exempt, background kinds, capacity).
- Page: tabs Exceptions and Reviews, "Accepted risk" badge, sealed-store lines in Collectors, "sealed" tag on evidence
  history, the banner note no longer says "not tamper-proof".

- Code-health ratchets kept (S290 resume): the Exceptions and Reviews tabs are split into small components
  (`ExceptionActions`, `DecisionModal`, `ExceptionsSummary`, `RecordReviewModal`, `ReviewStatus`, column builders), the
  new policy routes join the existing compliance lines of `staff_authz.py` (file size back to its baseline), the sampler
  note is one line (800 lines), and `shared/compliance/rls_catalogue_rules.py` is excluded from the complexity ratchet
  like the other vendored byte copy (its source is under tests/, outside the ratchet).

## Tradeoffs

- Prowler and AWS results are graded mostly in the collector (security invariants: logging on, MFA, no open admin
  port); only the critical / high Prowler count is a setting (`cis.compliance.prowler_critical_high_max`), because a
  known finding is meant to go through an exception, not a higher number.
- Staff ids are shown shortened on the page (no staff name lookup yet).
- No manual evidence upload, risk register, SoA entries or CSV exports in this slice (issue scope phase 3; follow-up).
