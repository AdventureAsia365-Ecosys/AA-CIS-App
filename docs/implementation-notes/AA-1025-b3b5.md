# AA-1025 slices B3 and B5 (S264 lane l5-cis-providers-b3b5) — a shared circuit for Jev / DataForSEO / Geoapify, a credit ledger for the vendor APIs

Plan: root `docs/audits/2026-11-01-S263-gateway-gap-audit/plan.md` rows B3 (PC-8) and B5 (OPS-08), section B. Builds on
B1 (the provider switch and access state, CIS #1218) and C1 (the Providers page, CIS #1242). $0: no provider call.

## Decisions

- **B3 storage: a new table `shared.provider_health` keyed by `connection_key`** (migration 342), not rows in
  `shared.llm_provider_health`. That table's PK is (connection_key, model_key) and model_key is a foreign key to the
  model catalog; writing a provider row there needs either fake catalog rows (they would show in routing UIs and the
  catalog checks) or dropping / loosening the FK and the PK (a contract change on a routing table that every LLM call
  reads). The new table has the same columns minus `model_key`, an FK to the connection (CASCADE: derived state) and
  is a pure expand. The breaker's pure transitions (`after_failure`, `after_success`, `claimed`, `state_of`) and
  `RULES` are reused as they are (a provider row is a `Health` with `model_key "*"`), so the thresholds and open
  periods are the LLM breaker's: access_denied / quota_exhausted open at once, throttled after 3, other after 5; open
  60 s doubling to 10 min for an outage.
- **Async module `shared/provider_circuit.py`**, not inside `shared/llm_client`: the three clients are async, and the
  LLM gateway's registry guard (`test_aa1002_no_behaviour_change`) stays untouched. Its own short DB connection per
  write (reads cached 10 s; a healthy success written at most once a minute per process), like the breaker; a DB
  error or a missing table falls back to the in-process copy with a 30 s / 300 s back-off.
- **What counts** (`failure_class`): HTTP 401 / 403 access_denied, 402 quota_exhausted, 429 throttled, 404 / 405 /
  408 / 410 / 5xx / timeout / transport other; any other 4xx (400, 409, 413, 422) is the request's own fault and is not
  counted (a held probe lease is released). DataForSEO's body codes by their first three digits (40100 → 401, 40501 → not counted,
  50000 → other). 404 counts so a wrong base URL path (the live step) opens the circuit; the Geoapify details 404 ("no
  such place") is an answer.
- **One outcome per logical call, after the client's own retries** (Jev: 3 attempts in `_call_jev`; Geoapify:
  `max_retries`; DataForSEO: one attempt), so "5 failures" = 5 calls that each failed every retry.
- **Open = nothing is sent**, and each client fails the way it already fails on an outage: Jev writes its 0 USD
  refused `llm_call_log` row (error_class = the circuit's class) and the stage keeps its own rule (fail-open);
  DataForSEO writes a refused `dfs_call_log` row (meta `refused: circuit_open`) and raises a fatal `DFSCallError` (the
  run stops, as on the switch); Geoapify raises `GeocoderUnavailable` (the run stops, names stay pending, no try
  counted), in the geocoder and in the place-details client.
- **Jev's check order**: switch → per-process credit breaker → daily budget → circuit → call. The circuit is asked last
  so a call the budget refuses never takes the half-open probe lease. The per-process 402 breaker stays (the fast local
  stop; the canary resets it).
- **Alert**: one bell `provider_circuit_open` (entity `provider_connection:<key>`, admins, one unread per connection per
  24 h under an advisory lock) and one `ops_alert_email` job (`provider_circuit_open`, key per connection, class and
  UTC day), raised only by the task whose row-locked write opened the circuit. A `typesafe` circuit opened by
  `quota_exhausted` raises none: the Jev 402 already has its exhausted bell + e-mail (AA-720 / AA-845).
- **B5 ledger: `shared.provider_credit_topup`** (migration 342) per connection, with `kind` `topup` (> 0) or
  `opening_balance` (≥ 0, a balance read on the provider console). The estimate re-anchors on the newest balance
  read: anchor = newest opening balance, else the first top-up; recorded = anchor + later top-ups; spent =
  `llm_call_log` cost since the anchor where `coalesce(connection_key, account)` = the key (the C1 attribution).
  `effective_at` is a timestamp (default now), not a date like Jev's, so a balance read at 14:00 does not subtract the
  morning's spend. Entries are never edited (cis_app has SELECT, INSERT, DELETE only); the FK has no CASCADE (money
  records never go with a registry edit).
- **Which connections**: `balance_source = 'topups_minus_spend'`, except kind `typesafe` (Jev keeps its own ledger,
  table and page). Migration 343 (contract) sets that source on the anthropic / openai rows that had `none`.
- **Threshold = the connection's `low_balance_usd`** (already admin-editable through PATCH
  /admin/llm-connections/{key} since 322; NULL = no alert). The Credit view saves it through that PATCH; no new write
  path for it.
- **Low-credit alert**: bell `platform.provider_credit.low` (entity `llm_connection:<key>`, admins), one real bell per
  connection per 24 h read or not (the Jev rule: the estimate does not recover on its own), and one
  `provider_credit_low` e-mail per connection and UTC day. Checked by the api sampler on the Jev check's schedule (30
  min), right after an entry is added (so the live step sees the bell at once), and by POST /admin/ai-gateway/credit/check.
- **Providers page**: Jev / DataForSEO / Geoapify rows carry `circuit` (open or half-open → status `open`, reason
  `circuit_open`, unless switched off); a ledger connection's LLM row carries `balance` (the Jev row's shape) and turns
  `low` / `cap_reached` only from `ok` / `unknown` (a circuit-open or disabled row keeps its status).

## Tradeoffs

- A new table rather than a nullable `model_key`: two circuit tables to read on the admin side, against no change to
  the LLM breaker's table, its FK and its 10 s snapshot (which every LLM call reads).
- The circuit is per connection, not per endpoint: a DataForSEO outage of one API family (SERP vs keywords) pauses all
  of it for one short open period; the probe reopens it. Accepted for a single-account provider.
- The spend read is raw `llm_call_log` only (180-day raw window): an anchor older than that would under-count spend.
  A balance read every few weeks keeps the anchor recent; the rollup (`llm_call_daily`) has no `connection_key`.
- No "send a test alert" button for the credit ledger: the live check is real (an opening balance under a threshold),
  and the bell is throttled per connection, so a test does not hide a real alert for more than the 24 h it would have
  lasted anyway.
