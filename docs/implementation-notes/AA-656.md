# AA-656 — Staff auth hardening: JWT for every staff role, one RBAC matrix

## Decisions
- **Content staff become `shared.admin_users` rows** with role `content` (enum value added by
  migration 218) and log in through `/auth/admin-login`. The BFF-only `CONTENT_PASSWORD` login (no
  JWT, `cis_role=content` cookie trusted as-is) is removed. Accounts are created with
  `scripts/create_staff_user.py` (getpass + bcrypt, run inside the api container) — no hashes in git.
  (Retired at AA-816 D1, S244: staff are created on the Staff page as Cognito users.)
- **The role comes from the verified token, not the cookie.** Middleware picks the identity from
  whichever session token is present (`cis_admin_token` → `/auth/verify-admin`, else
  `cis_tenant_token` → `/auth/verify-tenant`) and checks the verified role against the page rule.
  Before this, a reviewer with a valid token could set `cis_role=admin` by hand and open admin-only
  pages (the token was verified, its role was not compared). A staff role not allowed on a page goes
  to its own landing page (admin → Overview, others → Review Queue), which every role may open.
- **One matrix, `frontend/lib/rbac.ts`**: `PAGE_RULES` (moved from middleware's `PROTECTED_ROUTES`),
  `API_RULES` (per BFF proxy), `landingPage`, `ROLE_LABEL`. The nav (`app/_kit/adminNav.tsx`, Sidebar,
  CommandPalette) filters with `canSeePage(role, href)` — the `adminOnly` flags are gone, so the nav
  can no longer disagree with what the middleware allows. Documented in CONTEXT.md "Staff roles and
  permissions", with the AA-Booking mapping (admin → admin, sales → reviewer tier, content_creator →
  content).
- **Every BFF proxy verifies.** `requireAdmin(req, roles)` → 401 on a bad/missing token, 403 on a
  valid staff token with the wrong role. `/api/tenant/[...path]` decides staff vs tenant by token
  presence (was the `cis_role` cookie; reviewer was wrongly sent down the tenant branch) and now
  verifies the tenant JWT too; `/api/playground/proxy` verifies the tenant JWT (was presence only).
- **Backend:** `/auth/verify-admin` accepts `STAFF_ROLES = ("admin", "reviewer", "content")`
  (`api/routers/auth.py`), still rejects tenant tokens and unknown roles.

## Changed (vs the issue)
- The "ADMIN" nav tag the issue mentions was already gone (AA-752 shell); what remained was the
  `adminOnly` flag deciding visibility separately from the middleware. Replaced by the matrix.
- The Topbar role line shows `ROLE_LABEL[role]` (Reviewer was shown as "Content Team").

## Tradeoffs
- Reviewer and content share the backend admin secret through the proxy, so `API_RULES` gates by
  proxy route, not by backend path. Narrowing which backend `/admin/*` paths a non-admin may call
  would need a per-page audit of the calls (or the backend reading a role header); left as a known
  limit in CONTEXT.md rather than a deny-list that breaks shared components.
- Content users gain working API access they never had in practice (their proxy calls all 401'd
  without a token), at the same tier as reviewer — the pages they could already open now work.
