# AA-143 — Synthetic Canary S0→S1 Skeleton (Wave 0)

## Decisions

- **S0 step uses direct DB seed, not XLSX upload.** The existing `/admin/ingest-s3` endpoint requires an S3 XLSX key, which would make the Lambda heavyweight. The canary bypasses S0 XLSX pipeline and inserts the fixture tour directly into `silver_aa_internal.raw_tours` with `review_status='approved'` — clean and fast.
- **Tour dedup by name suffix "Canary Fixture".** Each invocation deletes any existing row with that suffix before inserting, preventing unique constraint violations on re-runs.
- **S1 completion polling via DB, not SSE.** The existing SSE stream (`/acp/s1/run/{id}/stream`) is good for UI but awkward in a Lambda. The canary polls `acp_shared.acp_runs.status` directly via asyncpg every 10s, timeout 5 minutes.
- **`stage_status = "completed"` interpreted as `acp_stage_runs.completed_at IS NOT NULL`.** Migration 057 adds `completed_at` to `acp_stage_runs`; the canary requires it to be non-NULL for stage `s1`. If 057 not yet applied, this assertion will raise a missing-column error — document in README.
- **S1 run status terminal values include `completed` and `published`.** The `acp_runs.status` enum in the current code uses strings; Wave 0 accepts both as success.
- **asyncio.run() for DB calls inside Lambda handler.** Lambda doesn't have an event loop; each DB call uses a fresh connection via `asyncio.run()`. Not ideal for many calls but acceptable for a low-frequency canary.
- **EventBridge Terraform `state = DISABLED`.** Lambda is not deployed yet; scheduler is created disabled so Terraform apply won't trigger the canary prematurely.
- **infrastructure/ at repo root.** The task specifies `infrastructure/canary/eventbridge_scheduler.tf` — this path is at the repo root (not inside `api/` or `services/`).

## Changed

- **No new API endpoint.** Original spec says "POST /acp/s0/ingest" but that endpoint doesn't exist. The canary seeds data directly into DB instead — functionally equivalent, simpler.
- **Fixture is JSON, not XLSX.** The Lambda reads `canary_fixture.json` and constructs the DB insert directly. No XLSX generation needed.
- **`run_id` returned from S1, not S0.** The task spec says S0 returns `run_id` — in reality S1 creates the `acp_runs` row and returns `run_id`. The canary reflects reality.

## Tradeoffs

- **Direct DB seed vs. API-driven S0:** Direct seed is faster and simpler but doesn't exercise the XLSX ingest pipeline. Wave 1+ could add a full XLSX upload step if needed.
- **asyncio.run() per DB call vs. shared pool:** Each DB operation opens/closes a connection. For a weekly canary this is fine; for high-frequency it would need refactoring.
- **asyncpg in Lambda layer:** Requires asyncpg to be bundled in the Lambda package. The Lambda must have asyncpg + boto3 (boto3 is already present in Lambda runtime).

## Should Know

- Migration 057 must be applied before canary's `acp_stage_runs` assertion works. Without 057, `completed_at` column doesn't exist → assertion will skip with a warning.
- The canary tenant (`CANARY_TENANT_ID`) must exist in `shared.tenants`. The default is the aa_internal tenant (`00000000-0000-0000-0000-000000000001`).
- Migration 058 adds `is_canary` and `skip_hitl` to `shared.tenants`. These flags are referenced in the fixture and README but not yet enforced in the API code — enforcement is Wave 1 work.
- `STEP_FUNCTIONS_ARN` must be set in the Lambda environment for S1 to actually trigger rewrites. If missing, the run creates `started_count = N` but Step Functions are not triggered (the API treats this as a no-op).
- `ADMIN_SECRET` must be set in the Lambda environment to authenticate against the API.
