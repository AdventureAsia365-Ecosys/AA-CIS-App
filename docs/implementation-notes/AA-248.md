# AA-248 — S1 Rewrite: switch to async job polling

## Problem
`frontend/app/admin/s1-rewrite/page.tsx` called `POST /api/admin/run-tour` (sync),
which the ALB kills at 29s. Tours taking 30s–3min showed as "failed" in the UI
while the backend kept running and succeeded minutes later — status lied to the user.

## Decisions
- Switched to the existing `POST /admin/run-tour-async` (202 + job_id + poll_url) and
  `GET /admin/jobs/{job_id}`. No backend changes — both endpoints already existed
  (AA-223, migration 071, verified applied before starting).
- Replaced the old chunk-of-3 `Promise.all` throttle with a proper 3-worker pool
  (`queueRef` + `runWorker`), because chunk-and-await no longer throttles anything
  once `runSingleTour` returns immediately after the 202 (it used to block on the
  full sync response).
- Worker/job completion signaling uses a resolver-map (`waitersRef`) rather than
  polling a ref in a spin-loop: a promise is registered synchronously right before
  each dispatch, and resolved either immediately (dispatch failure) or by the
  polling effect (job settles). Avoids the stale-ref race that a naive
  `while (ref.current[id] === "running") await sleep()` loop would hit, since ref
  sync via `useEffect` lags one commit behind the state write inside `runSingleTour`.
- Finalization (reload tours, clear transient state, flip `runComplete`) is driven
  by a separate `useEffect` keyed on `tourStatuses`, gated on a snapshot
  (`runTourIdsRef`) of the tour_ids in the run — not on `jobIds` being non-empty.
  Gating on `jobIds` would strand the run in "running" forever if every dispatch
  failed immediately (network down before any 202), since `jobIds` only gets an
  entry on dispatch success.
- Polling effect mirrors CatalogTab.tsx: `pollingRef` guard, 5s interval, 5min
  safety cutoff, refs (`jobIdsRef`/`tourStatusesRef`/`toursRef`) read inside the
  interval callback to avoid closing over stale state.

## Changed
- `runSingleTour`: now POSTs to `run-tour-async`, stores `job_id` in `jobIds`,
  returns immediately. No longer sets terminal status itself (except on dispatch
  failure).
- `startRun`: seeds `queueRef`/`runTourIdsRef`, spins up `min(3, N)` workers,
  no longer awaits full completion or does end-of-run cleanup itself.
- Added: `jobIds`/`toast` state; `queueRef`, `activeWorkersRef`, `runTourIdsRef`,
  `waitersRef`, `pollingRef`, `jobIdsRef`, `tourStatusesRef`, `toursRef`; polling
  `useEffect`; finalize `useEffect`; toast UI block.
- Not touched: `POST /admin/run-tour` (still exists, just unused from this file),
  `frontend/app/admin/pipeline/s1/page.tsx`, all backend files.

## Tradeoffs
- `activeWorkersRef` is incremented/decremented but not read anywhere outside the
  worker itself — kept because the plan called for it and it costs nothing, but
  it's not load-bearing; `queueRef.current.length === 0` is what actually stops
  spawning new work.
- Quality score lookup after a job succeeds requires a second fetch
  (`GET /admin/tours/{id}/history`) since `GET /admin/jobs/{id}` only returns
  `result_version_id`, not the score. Matches the existing history endpoint shape
  (`history[].id` / `history[].score_overall`) — no backend change needed, but it's
  an extra round trip per completed tour every poll tick until the entry is found.

## Should know
- Verified against live backend before writing any code: confirmed migration 071
  applied, and read `admin_pipeline.py` + `jobs_repo.py` directly to confirm the
  202 response shape (`{job_id, status, poll_url}`), job status lifecycle
  (`queued → running → succeeded | failed | interrupted`), and the
  `history[].id === result_version_id` / `score_overall` field names — plan's
  assumptions matched the real code exactly, no surprises.
- Frontend has a generic catch-all proxy (`app/api/admin/[...path]/route.ts`) that
  forwards any `/api/admin/*` path to `{API_URL}/admin/*` — so `run-tour-async` and
  `jobs/{id}` needed zero new proxy route code.
- `tsc --noEmit` and `eslint` both pass on the changed file. The one eslint error
  in the file (`react-hooks/set-state-in-effect` on the `loadTours(); loadBrandList()`
  effect) is pre-existing on an untouched line, not introduced by this change.
