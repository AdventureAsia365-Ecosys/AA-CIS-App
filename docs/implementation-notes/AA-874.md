# AA-874 — Redis TLS + AUTH from env (CIS app slice S1)

AA-874 moves the CIS Redis to an ElastiCache replication group with in-transit TLS (required), an AUTH
token and at-rest encryption, and adds tenant-pool alarms. This repo's part (S1) only teaches the app to
connect to such a node from env, backward compatible, so it can merge and deploy before the infra switch.
The infra side (new group, secret, alarms, task-definition env) lives in AA-CIS-Infra.

## Decisions

- **One helper, `shared/cache/redis_conn.py` `redis_conn_args() -> (url, kwargs)`.** All three client
  sites (api lifespan, worker `run()`, SEO handler singleton) use it, so TLS / AUTH cannot be missed in one
  of them. A unit test fails if any of these files builds an inline `redis://` f-string again.
- **Env names:** `REDIS_HOST` (existing), `REDIS_PORT` (default 6379), `REDIS_TLS` (`true/1/yes/on`),
  `REDIS_AUTH_TOKEN` (ECS `secrets` entry from Secrets Manager).
- **Token as the `password=` kwarg, never in the URL.** A URL can end up in a log line or an exception
  message; the kwarg does not. A test checks the token is absent from the URL and from the client repr.
- **TLS verification explicit:** `ssl_cert_reqs="required"`, `ssl_check_hostname=True`, system CA store.
  redis-py changed the `ssl_check_hostname` default between 5.x (False) and 6+ (True); setting it keeps the
  behaviour identical whatever version `redis[asyncio]>=5.0.0` resolves to in the image.
- **Token without TLS:** one ERROR `aa874_redis_auth_without_tls` per process and the token is dropped.
  ElastiCache only accepts AUTH over TLS, and sending AUTH to the old node (no AUTH) would fail every
  command, while the plain connection still works. This is a config mistake to see, not to crash on.
- **Fallback host is `localhost`**, not the old ElastiCache host name that was hard-coded in `api/main.py`
  and the SEO handler (public repo hygiene, DM-6.10). Every ECS task definition sets `REDIS_HOST`, so the
  fallback only matters locally and in tests.
- **Worker keeps "no `REDIS_HOST` → no Redis client"** (unchanged behaviour), and keeps its client without
  the api's 0.5 s bounds (out of scope here).

## Changed

- New `shared/cache/redis_conn.py`.
- `api/core/redis_client.py`: `build_api_redis(url, **conn_kwargs)` forwards the TLS / AUTH kwargs; the
  S241 timeouts and single retry are unchanged (the connect timeout also bounds the TLS handshake).
- `api/main.py`, `shared/jobs/worker.py`, `services/seo_intelligence/handler.py`: use the helper; the
  hard-coded host name is gone (and the now-unused `os` import in the handler).
- `shared/secrets.py`: removed the dead `get_redis_url()` (no caller; it read a `REDIS_URL` nothing sets).
- `api/core/aa544_tenant_pool.py`: the comment at `aa817_tenant_pool_unavailable` said the logs are console
  lines and promised an alarm that did not exist; logs are JSON (AA-871) and the alarm is now in AA-CIS-Infra.
- `CONTEXT.md` (tenant-pool section): Redis connection env + the new alarms. `README.md` env table.
- Tests: `tests/unit/test_aa874_redis_conn.py`.

## Tradeoffs

- **No env switch to turn host-name checking off.** If the ElastiCache certificate did not match the
  endpoint, every Redis call would fail (fail open for rate limiting, fail closed to the tenant pool for
  flags, SEO cache misses). Accepted because the TLS endpoint is verified from the api task with this exact
  helper before the task definitions are switched (cutover step in AA-CIS-Infra), and an extra knob would
  invite turning verification off.
- **`REDIS_URL` stays in `ci.yml`** (integration-test env). Nothing reads it any more, but editing the CI
  workflow is a risky-area change for no behaviour gain; it can go with the next CI edit.

## Should know

- Order: this PR deployed (api + worker on one SHA) **before** the AA-CIS-Infra PR that sets
  `REDIS_TLS` / `REDIS_AUTH_TOKEN` and points `REDIS_HOST` at the TLS endpoint. Old code would ignore
  `REDIS_TLS` and fail against a TLS-only node.
- Deployed alone, this PR changes nothing at runtime: the task definitions set only `REDIS_HOST`, so the
  helper returns the same plain URL as before.
- Pre-switch check from the api task (ECS exec): `from shared.cache.redis_conn import redis_conn_args`
  with `REDIS_HOST=<tls endpoint> REDIS_TLS=true REDIS_AUTH_TOKEN=<from the secret>` in the script's env,
  then PING through `redis.asyncio.from_url(url, **kwargs)` → True. Same kwargs as production.
