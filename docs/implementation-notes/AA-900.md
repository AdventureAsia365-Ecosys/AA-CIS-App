# AA-900 — LLM operations: prompt register, eval runbook, change-eval label (CIS part)

Scope as narrowed by decisions N-4 / N-5 (engineering handbook §5.7): prompt register + eval runbook, a generated
route table (root repo), evals by hand through `LLMClient` under `stage = adhoc_aa900` with a cost cap, run ID in the
PR. Out of scope: the `prompt_version` ledger column (AA-804), a per-PR eval trigger.

## Decisions

- **The eval is the existing R2 runner, not a new script.** R2 (AA-919 WM-19) already runs a writer on the AA-729
  golden set through `LLMClient`, logs every call, has a hard per-run cap from `shared.llm_call_log`, calibrates its
  judge against the golden labels and stores one `shared.prompt_eval_runs` row (the run ID). A second eval runner
  would duplicate the stop rules and the cap. AA-900 adds only a label option: `R2Config.log_stage` /
  `--stage adhoc_aa900` (`cfg.EVAL_LOG_STAGES`), so a change eval is traced to this issue as the handbook asks.
- **Default unchanged.** Release evidence runs from the Releases tab keep `writing_memory_eval`; nothing in the API or
  the admin UI passes the new field.
- **`adhoc_aa900` counts against the writing-memory month cap** (added to `MEMORY_STAGES`): a change eval spends the
  same budget as any other eval.
- **Run after deploy.** R2 regenerates through the code running on the worker, and its control (the active release's
  stored output, release 0 = frozen AA-729 baseline) already exists, so the eval of a merged change is one paid run.
  Dev has no users; a failed verdict means revert.
- **By hand, not a workflow.** The legacy `eval-regression.yml` dispatch workflow measures only `s1_old`. Adding an
  R2 input to it is a CI/workflow change (risky) and N-4 keeps per-PR runs off; the runbook uses ECS exec
  `--enqueue` (the paid run is the worker job `writing_memory_r2`, never an exec session, lesson S234).
- **Register = Markdown table with a guard test.** `docs/` tracks only Markdown, and a table is what reviewers read.
  `tests/unit/test_aa900_prompt_register.py` parses the rows between the register markers and fails on a missing file,
  an undefined symbol, an unknown stage or role, a duplicate id, or a SAFE_DEFAULTS stage with a prompt and no row.
- **Version column describes where the version is recorded today** (sha8 `prompt_version_of`, a version constant,
  `PROMPT_SHA`, `judge_version()`, or `git`). Computing every prompt hash would mean importing every prompt module
  (app dependencies) and most prompts are built per input; AA-804 adds the ledger column.
- **Report script outside the image.** `scripts/llm_ops/eval_run_report.py` is stdlib + asyncpg, read-only
  (`default_transaction_read_only`), run through the S3-mediated pattern; it prints the run row and the logged spend
  by stage so the PR quotes the real cost.

- **Review fixes (independent review, S257).**
  - The report's spend query casts its bound (`$3::timestamptz - interval '10 minutes'`): without the cast Postgres
    typed `$3` as an interval and every real run failed (`UndefinedFunctionError`, reproduced on local Postgres). The
    unit test asserts the cast; `tests/integration/test_aa900_eval_run_report_sql.py` runs the report on real rows.
  - `--latest` picks only a FINISHED run of the asked label (`--stage`, default `adhoc_aa900`); the runbook's
    preferred input stays the run id from the job result.
  - A run with a release refuses `log_stage != writing_memory_eval` in `R2Config.validate` (an adhoc-labelled run must
    never become release evidence; the release evidence check reads the run's release_id, not its label).
  - `run_with_pool` has a real test (fake `run_r2` captures the store: `stages == (conf.log_stage,)`); reverting the
    line to `PgStore(pool)` was checked to fail it.

## Tradeoffs

- R2 cannot evaluate T10 (the T9 gate / repair loop is not run in an eval) or the A3 / place prompts: the register
  marks those `Q0` / `Q2` / `R0` or `none` and the runbook asks for the quality-system tier or a described manual check.
  A golden set for them is new work, not AA-900.
- A change eval after merge means the PR shows the run ID as a comment, not before merge. Running the candidate before
  merge would need a one-off task on the PR image; not worth it on Dev.

# AA-900 slice 2 — LLM availability signal + fail fast on account-level refusals (S258)

Situation: since 29/10/2026 every Bedrock model on the LLM account answers "Error 002: Access to Bedrock models is not
allowed for this account". Nothing in the admin showed it, and LLM jobs retried into the same refusal.

## Decisions

- **One classifier, text-based, no SDK imports** (`shared/llm_client/errors.py`): `access_denied`, `quota_exhausted`,
  `throttled`, `other`. An OpenAI `insufficient_quota` 429 is `quota_exhausted` (a retry cannot add credit), checked
  before the rate-limit patterns. Both `access_denied` and `quota_exhausted` count as "account-level".
- **The gateway decides, the job runner obeys.** `LLMAccessDenied` (a `RuntimeError` subclass, so every existing
  `except RuntimeError` behaves the same) is raised only when every model the request actually tried (skipped
  disabled keys are not attempts) was refused at account level: route (`_call_route`), single key (`_generate`) and the
  legacy Haiku/Sonnet chain (`_legacy_chain`, which before lost its tier errors: its final error now carries the last
  one as `__cause__`). A route with one throttled or timed-out model keeps the plain `RuntimeError`, marked
  `llm_error_class` so its last cause cannot be reread as a denial.
- **Retry decision reads the type, never the text** (`is_llm_access_denied`). An aggregate message can name a denied
  model next to a throttled one; text alone must not stop retries. `worker.failure_outcome(exc)` returns the job error
  (prefixed `llm_access_denied`), `retryable=False` and the reason; other exceptions keep "retry unless NonRetryable".
- **S1/T2 path propagates the typed error.** The writer nodes swallowed every LLM error into `state["error"]`, and
  `_rewrite_tour` into a `failed` dict, so the job never saw it (and S1's `_run_tour_safe` retried 3x). Only the typed
  error now leaves: `graph.generate_node` and `s1_writer_v2_live._call` re-raise it when nothing was billed,
  `_rewrite_tour` re-raises it, `_run_tour_safe` breaks its loop, still marks `pipeline_runs` failed, then raises it;
  `s1_rewrite_job` clears the checkpoint (same as any final failure) and re-raises. T2's job already re-raises.
- **Availability without a probe** (`api/services/llm_availability.py`, `GET /admin/llm-availability`, `hours` 1-168,
  default 24). `llm_call_log` holds only billed calls (AA-927), so a refusal never writes a row there; the card
  combines (a) answered calls per provider / account / embeddings from `llm_call_log` and (b) errors of failed or
  re-queued jobs from `shared.job`, classified with the same `classify_text`. Status: newest outcome wins —
  `blocked` (account-level refusal newer than the last answered text call), `degraded` (throttle newer), `ok`,
  `unknown`. Embeddings run on the main account and never clear a block of the LLM account. Jev rows (`typesafe`) are
  left out: Jev has its own credit card.
- **No new table, no migration, no logging of unbilled rows into `llm_call_log`.** Writing a zero-cost row per refused
  call would change every call count of Cost Operations, wave reports and ok-rates (the AA-927 contract).
- **Open read** (no `POLICY` entry, like `/admin/llm-config` on the same tab); snapshot `aa882_staff_route_policy.json`
  updated.
- **UI on the kit only**: `Section`, `Badge`, `DataTable`, `DateText`; accounts named through `lib/awsAccounts`
  (`accountName`); EN + VI messages in `models.messages.ts`; refetch every 60 s.

- **Review fixes (independent review of #1148, S258).**
  - `docs/api/openapi.json` regenerated (`scripts/export_openapi.py`, FastAPI 0.161.1 / Pydantic 2.14.1 as pinned):
    the new route was missing and the required Unit Tests job failed `test_aa899_openapi_export`. The branch first
    merged `origin/main` (its two newer commits also changed the document) so the regenerated file matches the queue.
  - A refusal after a paid draft keeps the draft. The S1 sonnet upgrade goes through `_sonnet_upgrade`, which
    returns None on `LLMAccessDenied` (the primary result is kept, `auto_upgraded` false, not marked
    `_sonnet_retried`); any other error still propagates. In writer v2, `_call(raise_access_denied=False)` for the
    meta calls: a refused meta call records `access_denied`, the meta retry is skipped, and the writer draft goes on
    as after any failed meta call. Only the first (writer) call fails the job at once.
  - `JOBS_SQL` dates a failure when it happened: a failed row by `finished_at` (set once by `_finish` / `reap`), a
    row queued for a retry by `updated_at` (written by `queue.fail` with the error; nothing touches a queued row
    before a claim). Running rows are left out: their error is the previous attempt's and `updated_at` is the
    heartbeat, so a throttled-then-running job kept the card `degraded` while calls succeeded. Their next outcome
    (a call-log row, a re-queue or a failure) is counted when it happens. The two branches read the existing
    `job_finished_idx` and `job_queued_due_idx` (partial on `status = 'queued'`) instead of a full scan on
    `updated_at`, which has no index.
  - `s1_writer_v2_live._call` docstring now says when it raises.

## Tradeoffs

- A job that ran before this deploy and failed in S1 has only "run_tour failed after retries (see logs)" as its error,
  so history before the deploy shows few refusals; the card is accurate from the first refused job after it.
- An LLM call made outside a job (an API request path) is not seen on the refusal side; most LLM work runs in jobs.
- `a3_atomize` swallows LLM errors per day and fails the attempt with `AtomizeIncomplete` (retryable, max 2): one extra
  attempt 30 s later, no cost (refused calls are not billed). Not changed here to keep the slice small. The same holds
  for other per-item loops (any kind that catches the gateway error per item); a follow-up can let each loop re-raise
  `LLMAccessDenied` the way `graph.generate_node` does, so every LLM job kind fails at once.
- Other `_rewrite_tour` callers now get the exception instead of a `failed` dict on an account-level refusal:
  `services/eval/regression.py`, `services/writing_memory/eval_writers.py` and
  `services/acp_produce/tenant_pipeline.run_t3_qa_gate`. An eval run aborts instead of recording one refused tour after
  another, which is what the provider state means (every next tour would be refused too); the paid run's cost so far
  stays in `llm_call_log`.
- `is_llm_failure`'s marker regex (`bedrock|invokemodel|converse|anthropic|openai|llm|error 002`) is a broad substring
  match on older, untyped job errors. Accepted for a display-only signal; S3 / Cognito / SES / Geoapify errors are
  filtered out by the test cases, and new refusals carry the `llm_access_denied` prefix.
- A display-only misread: an older untyped job error that names a denied model next to a throttled one is shown as
  `access_denied`. Jobs failed after this deploy carry the prefix only when the gateway decided.
