# AA-900 — LLM operations: prompt register, eval runbook, change-eval label (CIS part)

Scope as narrowed by decisions N-4 / N-5 (engineering handbook §5.7): prompt register + eval runbook, a generated
route table (root repo), evals by hand through `LLMClient` under `stage = adhoc_aa900` with a cost cap, run ID in the
PR. Out of scope: the `prompt_version` ledger column (AA-804), a per-PR eval trigger.

## Decisions

- **The eval is the existing R2 runner, not a new script.** R2 (AA-919 WM-19) already runs a writer on the AA-729
  golden set through `LLMClient`, logs every call, has a hard per-run cap from `shared.llm_call_log`, calibrates its
  judge against the golden labels and stores one `shared.prompt_eval_runs` row (the run ID). A second eval runner
  would duplicate the stop rules and the cap. AA-900 adds only a label option: `R2Config.log_stage` /
  `--stage adhoc_aa900` (`cfg.EVAL_LOG_STAGES`), so a change eval is traced to this issue as the handbook asks.
- **Default unchanged.** Release evidence runs from the Releases tab keep `writing_memory_eval`; nothing in the API or
  the admin UI passes the new field.
- **`adhoc_aa900` counts against the writing-memory month cap** (added to `MEMORY_STAGES`): a change eval spends the
  same budget as any other eval.
- **Run after deploy.** R2 regenerates through the code running on the worker, and its control (the active release's
  stored output, release 0 = frozen AA-729 baseline) already exists, so the eval of a merged change is one paid run.
  Dev has no users; a failed verdict means revert.
- **By hand, not a workflow.** The legacy `eval-regression.yml` dispatch workflow measures only `s1_old`. Adding an
  R2 input to it is a CI/workflow change (risky) and N-4 keeps per-PR runs off; the runbook uses ECS exec
  `--enqueue` (the paid run is the worker job `writing_memory_r2`, never an exec session, lesson S234).
- **Register = Markdown table with a guard test.** `docs/` tracks only Markdown, and a table is what reviewers read.
  `tests/unit/test_aa900_prompt_register.py` parses the rows between the register markers and fails on a missing file,
  an undefined symbol, an unknown stage or role, a duplicate id, or a SAFE_DEFAULTS stage with a prompt and no row.
- **Version column describes where the version is recorded today** (sha8 `prompt_version_of`, a version constant,
  `PROMPT_SHA`, `judge_version()`, or `git`). Computing every prompt hash would mean importing every prompt module
  (app dependencies) and most prompts are built per input; AA-804 adds the ledger column.
- **Report script outside the image.** `scripts/llm_ops/eval_run_report.py` is stdlib + asyncpg, read-only
  (`default_transaction_read_only`), run through the S3-mediated pattern; it prints the run row and the logged spend
  by stage so the PR quotes the real cost.

- **Review fixes (independent review, S257).**
  - The report's spend query casts its bound (`$3::timestamptz - interval '10 minutes'`): without the cast Postgres
    typed `$3` as an interval and every real run failed (`UndefinedFunctionError`, reproduced on local Postgres). The
    unit test asserts the cast; `tests/integration/test_aa900_eval_run_report_sql.py` runs the report on real rows.
  - `--latest` picks only a FINISHED run of the asked label (`--stage`, default `adhoc_aa900`); the runbook's
    preferred input stays the run id from the job result.
  - A run with a release refuses `log_stage != writing_memory_eval` in `R2Config.validate` (an adhoc-labelled run must
    never become release evidence; the release evidence check reads the run's release_id, not its label).
  - `run_with_pool` has a real test (fake `run_r2` captures the store: `stages == (conf.log_stage,)`); reverting the
    line to `PgStore(pool)` was checked to fail it.

## Tradeoffs

- R2 cannot evaluate T10 (the T9 gate / repair loop is not run in an eval) or the A3 / place prompts: the register
  marks those `Q0` / `Q2` / `R0` or `none` and the runbook asks for the quality-system tier or a described manual check.
  A golden set for them is new work, not AA-900.
- A change eval after merge means the PR shows the run ID as a comment, not before merge. Running the candidate before
  merge would need a one-off task on the PR image; not worth it on Dev.
