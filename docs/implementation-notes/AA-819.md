# AA-819 — AUP 2026-11: tenant AI notice, T9 testimonial guard, daily publish limit

S237 splits the issue across two lanes (decision D3): **cis-backend** owns the T9 guard, the
publish limit in `v1_publish.publish()` and migration 230; **cis-portal** owns the tenant notice
line and the Tenant 360 field. The TripPlanner AI badge audit (part 4) is in the TripPlanner lane.
Each lane appends its own section here.

## Portal slice (cis-portal lane, branch feat/aa-819-portal-ai-notice)

### Decisions
- **One component, one sentence.** `frontend/app/(tenant)/portal/_components/AiContentNotice.tsx`
  renders the issue's wording verbatim: "This content was generated with AI. Review it before
  publishing; you are responsible for what you publish." The sentence is exported as
  `AI_CONTENT_NOTICE` so the AA-668 writer panel reuses it rather than retyping it.
- **Kit tokens, portal folder.** The component reads `K`/`sans` from `app/_kit` (the portal is
  pinned `data-theme="light"`, so `K` resolves to the light palette). It lives with the portal
  components rather than in the kit because it is tenant-portal wording, not a generic primitive;
  adding a kit primitive would also mean a UI Kit tab entry for one sentence.
- **Same wording on the tour catalog export.** The issue wording says "content", which covers
  T2-rewritten tours too, so My Catalog Tours uses the same line rather than a tour-specific
  variant (one sentence to keep in step with the Terms, AA-820).
- **Placement** (one line per surface the tenant acts on):
  - T10 My Content: under the page subtitle (covers the list's bulk export/publish) and in the
    piece drawer above Edit/Export (the drawer covers the page line). Shown only when the piece has
    content (`content_text !== null`), same condition as the actions.
  - T11 Publish: inside the "Ready to Publish" card, under the sticky header, above the Publish
    buttons (shown even when WordPress is not connected; it is information, not a gate).
  - My Catalog Tours: under the "My Catalog Tours · N tours" line (covers bulk CSV/XLSX) and in the
    tour drawer footer next to Export DOCX.
- **Admin field contract** (built against the cis-backend half, not yet on main):
  - `PATCH /admin/tenants/{id}` body `{"daily_publish_limit": <int>}` sets the override;
    `{"daily_publish_limit": null}` clears it (the publish route then uses the code default 20).
    The field is sent alone, in its own form, so it never rides along with a plan change.
  - The response may carry `daily_publish_limit`; if the key is absent the UI keeps the value it
    sent. `changed` is shown in the success toast as today.
  - `GET /admin/tenants` rows may carry `daily_publish_limit` (int or null). Absent = treated as
    "no override" and shown as "20/day (default)".
- **UI validation:** empty = no override; otherwise an integer 1–1000 (`DAILY_PUBLISH_LIMIT_MAX`, a
  typo guard like `RATE_LIMIT_RPM_MAX`). 0 is not allowed: blocking a tenant is suspend, not a
  limit of 0. The server stays the authority; its 422 text shows in the error toast.

### Changed
- New `AiContentNotice.tsx`; wired into `t10-review/page.tsx`, `ReviewDrawer.tsx`,
  `PublishPendingList.tsx`, `CatalogTab.tsx`, `CatalogDrawer.tsx` (footer row now wraps so the line
  sits left of the buttons on desktop and above them on phones).
- Tenant 360 Settings: new "Daily publish limit" section (`PublishLimitForm` in
  `Tenant360Settings.tsx`) with placeholder "default 20", Save limit, Use default (clears the
  override) and "Current: …". Optimistic like the plan form, rolls back with an error toast.
- Tenant 360 header: a "Publish Limit" stat next to Rate Limit.
- `tenant360.ts`: `DAILY_PUBLISH_LIMIT_DEFAULT` (20, mirrors the backend code default),
  `DAILY_PUBLISH_LIMIT_MAX`, `validateDailyPublishLimit`, `parseDailyPublishLimit`,
  `fmtDailyPublishLimit`.
- No backend change, no migration in this branch.

### Tradeoffs
- The notice appears twice on T10 and on My Catalog (page + drawer). Reading the issue as "a line
  wherever the tenant reviews/publishes/exports", the drawer hides the page line, so both are
  needed; still one short sentence each.
- The front-end default (20) duplicates the backend code default. It is display-only (placeholder
  and "(default)" label); if the backend default changes, change `DAILY_PUBLISH_LIMIT_DEFAULT` too.
- No new Playwright spec: portal pages need a tenant test login that the smoke suite skips today;
  verification is the aa-ui-verify pass on the Vercel preview (screenshots).

### Should know
- **Backend contract points the cis-backend PATCH must honour** for the field to work:
  1. accept `daily_publish_limit` alone (add it to the "Nothing to update" guard);
  2. treat an explicit `null` as "clear the override" — with `Optional[int] = None` that needs
     `"daily_publish_limit" in body.model_fields_set`, not `is not None`;
  3. return `daily_publish_limit` in the PATCH response and in the `GET /admin/tenants` rows
     (otherwise the header shows "20/day (default)" even when an override is stored);
  4. audit the change like `RATE_LIMIT_CHANGED`.
- Until migration 230 is applied, the PATCH for this field fails (or is refused by the
  missing-column guard); the UI shows the server message in a toast and rolls back. The tenant
  notice has no backend dependency and can ship first (Vercel only).
- Both lanes create this file; on merge, keep both sections.
