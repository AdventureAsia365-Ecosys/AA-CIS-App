# AA-819 — AUP 2026-11: tenant AI notice, T9 testimonial guard, daily publish limit

S237 splits the issue across two lanes (decision D3): **cis-backend** owns the T9 guard, the
publish limit in `v1_publish.publish()` and migration 230; **cis-portal** owns the tenant notice
line and the Tenant 360 field. The TripPlanner AI badge audit (part 4) is in the TripPlanner lane.
Each lane appends its own section here.

## Portal slice (cis-portal lane, branch feat/aa-819-portal-ai-notice)

### Decisions
- **One component, one sentence.** `frontend/app/(tenant)/portal/_components/AiContentNotice.tsx`
  renders the issue's wording verbatim: "This content was generated with AI. Review it before
  publishing; you are responsible for what you publish." The sentence is exported as
  `AI_CONTENT_NOTICE` so the AA-668 writer panel reuses it rather than retyping it.
- **Kit tokens, portal folder.** The component reads `K`/`sans` from `app/_kit` (the portal is
  pinned `data-theme="light"`, so `K` resolves to the light palette). It lives with the portal
  components rather than in the kit because it is tenant-portal wording, not a generic primitive;
  adding a kit primitive would also mean a UI Kit tab entry for one sentence.
- **Same wording on the tour catalog export.** The issue wording says "content", which covers
  T2-rewritten tours too, so My Catalog Tours uses the same line rather than a tour-specific
  variant (one sentence to keep in step with the Terms, AA-820).
- **Placement** (one line per surface the tenant acts on):
  - T10 My Content: under the page subtitle (covers the list's bulk export/publish) and in the
    piece drawer above Edit/Export (the drawer covers the page line). Shown only when the piece has
    content (`content_text !== null`), same condition as the actions.
  - T11 Publish: inside the "Ready to Publish" card, under the sticky header, above the Publish
    buttons (shown even when WordPress is not connected; it is information, not a gate).
  - My Catalog Tours: under the "My Catalog Tours · N tours" line (covers bulk CSV/XLSX) and in the
    tour drawer footer next to Export DOCX.
- **Admin field contract** (built against the cis-backend half, not yet on main):
  - `PATCH /admin/tenants/{id}` body `{"daily_publish_limit": <int>}` sets the override;
    `{"daily_publish_limit": null}` clears it (the publish route then uses the code default 20).
    The field is sent alone, in its own form, so it never rides along with a plan change.
  - The response may carry `daily_publish_limit`; if the key is absent the UI keeps the value it
    sent. `changed` is shown in the success toast as today.
  - `GET /admin/tenants` rows carry `daily_publish_limit` (int or null). `null` = no override,
    shown as "20/day (default)". **Absent** (key missing: backend not deployed) is shown as "—" and
    the editor is read-only (review fix): before the backend ships no limit is enforced, so the
    header must not claim "20/day", and a save would only 422.
- **UI validation:** empty = no override; otherwise an integer 1–1000 (`DAILY_PUBLISH_LIMIT_MAX`, a
  typo guard like `RATE_LIMIT_RPM_MAX`). 0 is not allowed: blocking a tenant is suspend, not a
  limit of 0. The server stays the authority; its 422 text shows in the error toast.

## Backend slice (cis-backend lane, branches feat/aa-819-mig-230 + feat/aa-819-aup-t9-guard-publish-limit)

Lane cis-backend item 3 (S237), decision D3 (cis-backend owns the T9 guard, the publish limit and
migration 230) and D8 (migration-file-only PR first). Anthropic AUP effective 12/11/2026 (Bedrock
acc3). Review: AA-Ecosys docs/audits/2026-10-14-S236-design-review/aup-2026-11-review.md.

### Decisions

**T9 guard**
- **New gate `F19_authenticity`** (blocking, sentence-repairable), not an extension of
  `F13_hygiene`. F13_hygiene is a warn and its `SOCIAL_PROOF_RE` targets unsourced social proof
  ("travellers love"), which hygiene.autofix deletes only below a seed-overlap threshold. The AUP
  rule is absolute (no seed carve-out): a testimonial, a first-person customer/traveller voice or an
  independence claim is never acceptable, sourced or not. Its own gate name keeps the evidence
  countable in `gate_ledger` (CONTEXT: count failures from the ledger, never `held_reason`).
- **Detection lives in `services/acp_content_writing/authenticity.py`** (pure, no I/O), three
  families: `testimonial` (attributed quotes "— Sarah, UK", "one guest told us", star ratings,
  "5/5", "verified review", review-platform names, "testimonial"), `first_person` ("I booked",
  "my wife and I", "my trip with", "I'd recommend", "would book again", "best trip of my life"),
  `independence` ("independent review", "unbiased", "honest review", "not sponsored", "not
  affiliated", "we were not paid"). The brand's own "we / our team / our guides" voice is never
  matched: "we" only matches in a customer frame ("we booked with", "we travelled with").
- **Ledger order: right after `F11_brand_name`** (another deterministic content-safety gate), so a
  testimonial is the `first_failure` ahead of the scope / hygiene / style gates.
- **Repair path = the existing sentence repair** (`_ELIGIBLE_GATES` / `_QUOTED_GATES`) on the cheap
  `t9_repair` stage (`CHEAP_REPAIR_GATES`): the violation reads `"<problem>: '<sentence>'"`, and the
  problem tells the repair model to rewrite in the brand's own voice or return "" to cut.
- **Fail closed by a cut, not a hold.** A held piece still reaches the tenant and can be published
  (AA-770), so a hold alone would not keep a testimonial off a tenant's channel. After the loop,
  `_enforce_authenticity` cuts every F19-flagged body sentence still there (the hook too:
  compliance wins over shape; never the CTA), re-runs the deterministic shape gates on the cut text,
  and stores the F19 entry `blocking: false, waived: true` with `sentences_cut` / `cut_sentences`
  (pattern: AA-786 `_cut_truth_items`). A title/meta hit is refused by the SEO fit (`title_ok` /
  `meta_ok` also require no F19 hit); if one is still left, F19 stays blocking and the piece is held.
- **Prompt rule** added to the T9 `SYSTEM_PROMPT` (one FORBIDDEN line next to social proof) and to
  the sentence-repair system prompt. The blog-prompt hash guard (`test_aa771_s234_voice_contract.py`)
  is updated on purpose: only `SYSTEM_PROMPT` changes, `single` / `route` hashes stay.
- **`claim_rules.py` untouched**: F9 v2 is still not wired into `run_quality_gates` (S234 status),
  so a tripwire there would be dead code. The admin replacement check
  (`sentence_repair.check_replacement`) also runs F19, so an admin edit cannot put a review back.

**Daily publish limit**
- **Code default 20 per UTC day** (`services/acp_publish/daily_limit.py`), so the guard is live the
  moment the code deploys, before migration 230 is applied (D3).
- **Override `shared.tenants.daily_publish_limit`** (migration 230): nullable, no column default,
  CHECK `>= 1`. NULL = the code default. The 1000 upper bound is an API typo guard
  (`DAILY_PUBLISH_LIMIT_MAX`, Pydantic), not a DB constraint. 0 is refused: blocking a tenant is
  suspend.
- **Missing column tolerated**: `override_column_exists()` probes `pg_attribute` once and caches a
  "present" answer for the process; a "missing" answer is re-probed every 300 s, so the override
  starts working after the apply without a redeploy. An `UndefinedColumnError` on the read resets the
  cache and falls back to the default (never a 500).
- **What counts** (`COUNT_TODAY_SQL`): the tenant's `acp_shared.publish_log` rows whose attempt
  started today (UTC, `COALESCE(requested_at, published_at, created_at)`) with status `requested` or
  `published`, plus `unpublished` rows that did publish (`published_at` set): unpublish only flips our
  row, so it must not hand the slot back (publish → unpublish → publish would bypass the limit).
  `failed` rows never count.
- **What never counts / is never refused**: an AA-726 replay (same revision already published), a
  409 in-flight retry, a stale `requested` row reclaimed by its own retry. `idempotency.claim()`
  checks the limit only on the two paths that make a NEW counted row (a fresh INSERT, or a failed row
  turned back into `requested`), under a per-tenant `pg_advisory_xact_lock`, so two concurrent
  publishes of different pieces cannot both take the last slot.
- **429 body**: `"Daily publish limit reached: this account can publish N post(s) per day and has
  published M today. The limit resets at 00:00 UTC (in X h Y min). Contact Adventure Asia if you
  need a higher limit."` plus a `Retry-After` header (seconds to 00:00 UTC). No gate or quality
  wording.
- **Admin PATCH** (`PATCH /admin/tenants/{id}`, AA-766 rate_limit_rpm pattern): accepts
  `daily_publish_limit` alone; explicit `null` clears the override (`model_fields_set`); audited
  `tenant.daily_publish_limit_changed` with before/after/default; the response carries
  `daily_publish_limit` + `daily_publish_limit_effective` when the request set it. Before 230 it
  returns 409 with "needs migration 230 … every tenant has the default 20/day".
  `GET /admin/tenants` rows and `GET /admin/tenants/{id}/usage` `limits` carry
  `daily_publish_limit` (null before 230 or with no override), `daily_publish_limit_effective`, and
  (usage) `publishes_today`. This matches the four contract points the portal slice listed.

### Tradeoffs
- Regex detection has false negatives (a paraphrased testimonial without a quote, name or rating);
  the prompt rule is the first line, the gate the backstop. False positives are bounded by the
  brand-voice tests ("we recommend", "our guides") and real S232–S236 pieces passing.
- Cutting the hook can leave a weaker opening; compliance wins. The shape gates are re-run on the
  cut text, so a broken shape still holds the piece for the admin.
- The limit counts per UTC day (not the tenant's local day): one simple, testable boundary; the 429
  message says "00:00 UTC" explicitly.
- The count query uses `publish_log (tenant_id, …)`; no new index. Volume per tenant per day is tiny
  (≤ the limit plus failures).
- The override read is a separate query before the claim transaction (an `UndefinedColumnError`
  would abort the transaction it runs in).

- Review fixes (adversarial review, S237): the detector no longer flags trip facts that the fail-closed
  cut would have deleted. "Transfers from Hanoi add an hour" used to match the bare "<Name> from <Place>
  <verb>" frame; that frame now takes speech-only verbs. Trek grades and prices ("graded 3/5 for
  difficulty", "Difficulty: 4/5", "5/10 USD") are no longer read as review scores, and "third-party
  websites" is no longer read as an independence claim (only "third-party reviews / ratings" is). A cut
  FAQ question now takes its answer with it, and the cut re-runs F16_faq, so a blog cut under
  FAQ_MIN_PAIRS is held for the admin.
- A title or meta hit that the SEO fit could not replace keeps F19 blocking and holds the piece. Under
  AA-770 a held piece still reaches the tenant, so in that rare case (the fit refused it twice) the
  tenant can see a flagged title. The body is always cut.
