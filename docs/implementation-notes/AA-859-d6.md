# AA-859 PR-D6 — PATCH /v1/tours/versions/{id} on the tenant pool (W6)

Plan: `AA-Ecosys/docs/audits/2026-10-16-S240-aa859/aa859_plan.md` § PR-D6 (+ D2, D7, D8).
Flag: `T2_VERSION_WRITE_FLAG` = `aa859:t2_version_write_pool` (declared in PR-S, wired here). No migration.

## Decisions
- **Flag off is the old code path, statement for statement.** Same SQL text (now module constants
  `_VERSION_*_SQL`), no transaction, no advisory lock, a duplicate `version_number` still surfaces as the
  UniqueViolation it was. The lock and the 409 exist only on the tenant-pool path (flag on), so a
  rollback (`DEL` the key) returns exactly the pre-AA-859 behaviour.
- **One scoped transaction on the tenant pool:** own-row SELECT (404) -> edit: two-int
  `pg_advisory_xact_lock(AA859_TTV_LOCK_CLASS, hashtext(tenant || ':' || published_tour_id))`, then the
  existing `MAX(version_number) + 1` (no `FOR UPDATE`: 0A000 on aggregates), then INSERT; otherwise the
  status UPDATE. `AA859_TTV_LOCK_CLASS = 859`. The two-int key space never overlaps the one-bigint form,
  which every other advisory lock in the repo uses (t2_rewrite, slate, publish limit, Jev alert, job claim).
- **Backstop:** `asyncpg.UniqueViolationError` on the INSERT -> 409 `version_conflict` (flag on only).
  The transaction is already aborted; the 409 propagates out of the `async with`, which rolls back.
- **One log event per request:** `aa859_t2_version_write` with `used_tenant_pool=`, `action`, ids.
- **No MAIN exception needed:** the route writes no audit row and enqueues nothing.
- **`PATCH /v1/tours/{tour_id}/approve` deleted** (no caller, see Should know).

  three RLS tests fail, as it should.

## Tradeoffs
- Two-int lock key (plan) vs reusing the rewrite route's `hashtext('t2_rewrite:<tenant>:<tour>')` key:
  the plan's form keeps the key spaces apart, but it does not serialise an edit against a concurrent
  POST `/pool/{id}/rewrite` (MAIN, unchanged), which also computes `MAX + 1` for the same pair. That
  race is caught by the UNIQUE constraint: the edit side answers 409, the rewrite side keeps its old
  500. Sharing the rewrite key would close it; left as a follow-up note, not done (plan text).
- Keeping flag-off identical means the flag-off path keeps its two latent bugs (see Should know).

## Should know
- Frontend grep for `PATCH /v1/tours/{tour_id}/approve` (`frontend/`, `tests/e2e`): **no caller.**
  `frontend/lib/api.ts::approveVersion` posts to `${API_BASE}/versions/{id}/approve` (another, long-gone
  path) and is itself imported nowhere. The only historical caller, `(internal)/catalog/page.tsx`, was
  removed in AA-663 (bd8b0d41). The route updated `published_tours WHERE tenant_id = <tenant>`: 0 rows
  for every real tenant (published_tours is 100% the AA master sentinel), still answered `ok: true`.
  Deleted. `TourEditRequest` (`v1_tours.py:714`) is now unused; left in place because it sits inside
  PR-D5's region (`:610-743`) — delete it after D5 merges.
- Old behaviour kept on both paths: `action=edit` with an empty/absent `edited_content` falls through to
  the status branch and **rejects** the version (`"approved" if approve else "rejected"`). The portal
  always sends content, so not reachable from the UI; not fixed here (behaviour change).
- A malformed `version_id` is still a 500 (asyncpg DataError on `$1::uuid`) on both paths, as before.
- Live defaults of `rewrite_language`, `seo_mode`, `qa_*` are not in the schema dump (no defaults
  column); the stand-in gives them defaults because the live edit INSERT omits them and works. The
  live-verify edit step is what proves the live table accepts the tenant-role INSERT.
