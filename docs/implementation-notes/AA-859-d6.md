# AA-859 PR-D6 — PATCH /v1/tours/versions/{id} on the tenant pool (W6)

Plan: `AA-Ecosys/docs/audits/2026-10-16-S240-aa859/aa859_plan.md` § PR-D6 (+ D2, D7, D8).
Flag: `T2_VERSION_WRITE_FLAG` = `aa859:t2_version_write_pool` (declared in PR-S, wired here). No migration.

## Decisions
- **Flag off is the old code path, statement for statement.** Same SQL text (now module constants
  `_VERSION_*_SQL`), no transaction, no advisory lock, a duplicate `version_number` still surfaces as the
  UniqueViolation it was. The lock and the 409 exist only on the tenant-pool path (flag on), so a
  rollback (`DEL` the key) returns exactly the pre-AA-859 behaviour. [S241 D-12: superseded -- rollback is `SET <key> false`; DEL now means ON]
- **One scoped transaction on the tenant pool:** own-row SELECT (404) -> edit: two-int
  `pg_advisory_xact_lock(AA859_TTV_LOCK_CLASS, hashtext(tenant || ':' || published_tour_id))`, then the
  existing `MAX(version_number) + 1` (no `FOR UPDATE`: 0A000 on aggregates), then INSERT; otherwise the
  status UPDATE. `AA859_TTV_LOCK_CLASS = 859`. The two-int key space never overlaps the one-bigint form,
  which every other advisory lock in the repo uses (t2_rewrite, slate, publish limit, Jev alert, job claim).
- **Backstop:** `asyncpg.UniqueViolationError` on the INSERT -> 409 `version_conflict` (flag on only).
  The transaction is already aborted; the 409 propagates out of the `async with`, which rolls back.
- **One log event per request:** `aa859_t2_version_write` with `used_tenant_pool=`, `action`, ids.
- **No MAIN exception needed:** the route writes no audit row and enqueues nothing.
- **`PATCH /v1/tours/{tour_id}/approve` deleted** (no caller, see Should know).

## Tradeoffs
- Two-int lock key (plan) vs reusing the rewrite route's `hashtext('t2_rewrite:<tenant>:<tour>')` key:
  the plan's form keeps the key spaces apart, but it does not serialise an edit against a concurrent
  POST `/pool/{id}/rewrite` (MAIN, unchanged), which also computes `MAX + 1` for the same pair. That
  race is caught by the UNIQUE constraint: the edit side answers 409, the rewrite side keeps its old
  500. Sharing the rewrite key would close it; left as a follow-up note, not done (plan text).
- Flag-off is identical except one review fix (below): the empty-edit 400 applies to both paths, because the
  old behaviour was a silent data change, not a contract worth preserving behind a rollback switch.

## Live verify (flag on, orchestrator)
State traps: the route can only set `approved` / `rejected` and always overwrites `edited_at`, so a flip on an
`ai_generated` / `pending` / `needs_review` version cannot be undone through the API; an inline edit inserts a
`pending` version the tenant role cannot delete, and while it is pending `POST /v1/tours/pool/{id}/rewrite`
answers 409 "already in progress" for that tour. So:
0. Read (MAIN, ECS exec) one of E2E tenant A's versions with `status = 'approved'`: `id` (V), `published_tour_id`,
   `version_number`, `edited_at`; tenant B is any other E2E tenant JWT. Record them. Set
   `aa859:t2_version_write_pool` = `true` in Redis.
1. A: `PATCH /v1/tours/versions/V {"action":"reject"}` -> 200 `{"status":"rejected"}`; then `{"action":"approve"}`
   -> 200 `{"status":"approved"}`. Status restored; `edited_at` is now newer (recorded, not restorable).
2. A: `PATCH /v1/tours/versions/V {"action":"edit","edited_content":<V's rewritten_content, unchanged>}`
   -> 200 `{"status":"edited","new_version_id":N,"version_number":max+1}`, row N `pending`, parent V,
   `tenant_edit`; then `PATCH /v1/tours/versions/N {"action":"approve"}` -> 200. No `pending` row is left and
   the newest approved version has V's content, so what the tenant sees does not change. Record N and its
   number (left in place as a normal edit; removing it = MAIN, DRY-RUN destructive-ops procedure).
3. A: `PATCH /v1/tours/versions/V {"action":"edit","edited_content":{}}` -> 400, nothing written.
4. B: `PATCH /v1/tours/versions/V` with edit, approve, reject -> 404 each; V unchanged.
5. q3: `aa859_t2_version_write used_tenant_pool=True` once per request of steps 1, 2, 4 (step 3 is
   refused before the acquire and logs none), no
   `aa817_tenant_pool_unavailable`, no `aa817_*` errors, no `aa859_t2_version_conflict`.
6. DEL the flag, or leave it on per the flip ritual. [S241 D-12: superseded -- rollback is `SET <key> false`; DEL now means ON]
