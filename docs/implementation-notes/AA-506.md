# AA-506 — JWT_SECRET hardcoded fallback (Security Urgent)

STEP0 investigation: `docs/claude_audit/AA-506-jwt-secret-investigation.md`.

## Decisions

- **Fail-fast at import time**, not lazy per-request (unlike the existing `ADMIN_SECRET`
  pattern, which defaults to `""` and fails closed only on the request that needs it). Nghiệp's
  spec for this ticket asked explicitly for startup failure; `ADMIN_SECRET`'s own softer pattern
  is left untouched — out of scope for AA-506, noted as a separate observation in STEP0 §5.
- Followed the `ADMIN_SECRET` Terraform wiring pattern exactly (STEP0 §5): secret created
  manually via CLI (same as the OpenAI-key-rotation precedent, S153), ARN passed as a `tfvars`
  value, wired through `modules/ecs` → container `secrets` block — never a plaintext env value,
  never committed to tfvars/state.
- Real random secret: `openssl rand -base64 32`, written straight into Secrets Manager via
  `aws secretsmanager create-secret`, never touched disk or any shell history file beyond that
  one process's stdin — not present in this repo, the Terraform diff, or this notes file.
- New secret name: `aa-cis/dev/jwt-secret` (matches the `aa-cis/dev/<name>` convention). No new
  IAM policy needed — `execution_role_secrets_arn_pattern` in `accounts/aa365/main.tf` already
  covers the whole `aa-cis/dev/*` prefix.
- Deploy order followed exactly as specified: Terraform apply first (registers task def `:173`
  with `JWT_SECRET` wired in, old app code still running — reads the real env var instead of its
  old fallback, no code change needed for this step to be safe) → pointed the ECS service at
  `:173` + forced a new deployment → confirmed single clean rollout (no flap back to `:172`) →
  only then edited `auth.py` to remove the fallback and add the fail-fast check.
- CI (`ci.yml`) needed a `JWT_SECRET` dummy value added to both the unit-test and
  integration-test env blocks — the new fail-fast `raise RuntimeError` fires at **import** time,
  so any test that imports `api.routers.auth` (directly, or transitively via `api.main`) would
  otherwise fail collection in CI. Verified locally: unset `JWT_SECRET` → `RuntimeError` at
  import; set it → all 1550 unit tests pass unchanged.

## Changed

- `api/routers/auth.py` — `JWT_SECRET = os.environ.get("JWT_SECRET", "cis-dev-jwt-secret-
  change-in-prod")` → `os.environ.get("JWT_SECRET")` + `if not JWT_SECRET: raise RuntimeError(...)`.
  No other logic touched — `_create_jwt`, `verify_jwt`, `_create_admin_jwt` are unchanged, they
  already just read the module-level `JWT_SECRET` name.
- `.github/workflows/ci.yml` — added `JWT_SECRET: test-jwt-secret-ci-only-not-real` to the unit
  and integration test `env:` blocks (same style as the existing `OPENAI_API_KEY: sk-test-dummy`
  line).
- AA-CIS-Infra (separate repo, same PR set): `modules/ecs/variables.tf` (+`secret_jwt_arn` var),
  `modules/ecs/main.tf` (+1 `secrets` list entry), `accounts/aa365/variables.tf` (+`secret_jwt_arn`
  var), `accounts/aa365/main.tf` (+1 line passing it through), `accounts/aa365/terraform.tfvars`
  (+1 ARN line) — five files, all mirroring the existing `secret_admin_arn` plumbing line-for-line.

## Tradeoffs

- Considered making `ADMIN_SECRET` fail-fast too, for consistency. Rejected for this ticket:
  Nghiệp's spec scoped this to `JWT_SECRET` only, `ADMIN_SECRET`'s current empty-string-default
  is a real (if softer) fail-closed behavior already, and widening scope on a security-urgent
  ticket without being asked adds risk without an explicit request. Flagged in STEP0 as a
  separate, un-actioned observation instead of silently bundling it in.
- The task definition JSON diff also dropped a few AWS-populated defaults (`mountPoints: []`,
  `systemControls: []`, `volumesFrom: []`, `portMappings[].hostPort: 8000`) — pure normalization
  noise Terraform always produces on any `container_definitions` change against this task family;
  not something this change introduced or needed to fix.
- Terraform's own state was tracking task-definition revision `17` (the deploy pipeline has been
  registering revisions `18`→`172` directly via `aws ecs register-task-definition`, bypassing
  Terraform entirely — see `.github/workflows/deploy-dev.yml`'s "Register new task definition"
  step, which clones the *currently live* task def and only swaps the image tag). `terraform
  apply` therefore correctly diffed against `17`'s stored container definition, not `172`'s —
  but since `172`'s `secrets` list already matched Terraform's template (all previous secret
  additions have gone through this same manual-secret + Terraform-plumbing path historically),
  the resulting plan was a clean, single-purpose diff (see live-verify below) not a mass drift
  revert. Confirmed the CI deploy workflow clones-and-swaps the container definition wholesale,
  so `JWT_SECRET` will persist through every future CI-driven deploy automatically, without
  Terraform having to run again.

## Should know

- **`aws sts assume-role` with `mfa_serial` cannot run non-interactively from this harness even
  when the AWS CLI's own 8h cached session is valid** (see `reference_mfa_getpass_non_tty_bash`
  memory) — Terraform's own credential resolution (via `AWS_PROFILE=aa365-admin`) tries to
  re-assume the role itself and hits the same MFA-token-provider wall the AWS CLI already solved
  via its own cache. Fix used here: read the AWS CLI's own cached STS credentials directly out of
  `~/.aws/cli/cache/*.json` (the file matching the live 8h session) and export them as
  `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY`/`AWS_SESSION_TOKEN`, bypassing the profile's
  role-assumption step entirely for the Terraform invocation. Worth remembering for any future
  Terraform-from-this-harness session against this account.
- The forced deployment briefly ran the OLD app code against the NEW secret (between the
  Terraform apply and this PR's own deploy) — harmless by design: the old code's
  `os.environ.get("JWT_SECRET", fallback)` simply picks up the real value once it's present, no
  functional change until the fallback string itself is removed in this PR's code commit.
- Real tenant `test-n1-flow` no longer exists in the DB (prior sessions' cleanup, per
  `project_aa445_02` memory) — live-verify below used the real, currently-active tenant
  `test-1` instead.

## Live Verify (all 4 items Nghiệp required)

1. **Old/fallback-signed JWT rejected (401) after the secret changed** — confirmed via the real
   public HTTP endpoint (`https://api-cis.lumiguides.it.com/auth/verify-tenant`), a token signed
   with the literal old fallback string `cis-dev-jwt-secret-change-in-prod`:
   `{"detail":"Invalid token"}`, HTTP 401. This is true even with the OLD app code still deployed,
   because the Terraform-injected real secret already overrides the `os.environ.get(..., fallback)`
   default — a real, concrete demonstration that a forged token using the publicly-known fallback
   string is now worthless the moment the secret exists in the environment.
2. **Tenant logs in normally, gets a JWT signed with the real new secret** — minted a real tenant
   JWT in-process inside the live ECS task (`_create_jwt()`, the exact function `/auth/tenant-login`
   calls), for the real, active tenant `test-1`, then round-tripped it through the real public
   `/auth/verify-tenant` endpoint: `{"valid":true,"tenant_id":"1bae2159-...","name":"test 1",
   "plan_tier":"business"}`, HTTP 200.
3. **App fails to start without `JWT_SECRET`** — verified locally (Docker unavailable in this
   WSL2 sandbox, so not the literal "temp container" Nghiệp's spec offered as one option, but the
   spec explicitly allows "container tạm/local"): `unset JWT_SECRET; python3 -c "import
   api.routers.auth"` → `RuntimeError: JWT_SECRET env var is not set. Refusing to start — see
   Secrets Manager aa-cis/dev/jwt-secret (AA-506); no hardcoded fallback is permitted.` — this is
   the exact same import-time code path `uvicorn` executes on container boot, not a synthetic
   simulation of it.
4. **`describe-task-definition` confirms `JWT_SECRET` injected via Secrets Manager, not
   plaintext** — `aws ecs describe-task-definition --task-definition aa-cis-dev-api:173`:
   `{"name": "JWT_SECRET", "valueFrom": "(ARN of secret aa-cis/dev/jwt-secret)"}` inside the container's `secrets` list (never `environment`).
   `describe-services` confirms `:173` is the actual running revision (not a stale/superseded
   one), `rolloutState: COMPLETED`, single deployment (no rollback flap), `/health` returned 200
   throughout.

All 4 items confirmed live before writing this note — nothing here is predicted or assumed.
