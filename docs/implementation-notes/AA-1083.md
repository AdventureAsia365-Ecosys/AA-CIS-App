# AA-1083 — a recompute asks Jev only for what changed, with a spend estimate and a cap

Lane l14 of S277. Code in `services/recompute/jev_scope.py`, `services/acp_contract/atom_ranking.py`,
`services/recompute/stages.py`, `services/jobs/recompute_job.py`, the job runner router and the Jobs drawer.

## Decisions

1. **The Jev scope of a run is the Segment scope its trigger declared.** A platform recompute that carries
   `segment_ids` (an `a3_atomize`, a research run, a status change, the lifecycle or landing sweep) asks Jev only about
   those Segments plus the ones `segment_catchup` touched in the same pass. A tour-scope recompute asks only about the
   tour's current Segments. A run without `segment_ids` (a backfill, a script's from-scratch pass) asks about every
   Segment, as before. Switch: env `RECOMPUTE_JEV_SCOPE` = `changed` (default) | `all` (the old behaviour, every
   Segment asked).
2. **What "keep their stored verdicts" means per Jev stage, for a Segment outside the scope:**
   - `a3_segment_type` — the stored transit / experience pick only (`resolve_exclusions(cached_only)`, the read the
     landing sweep already used). A moment shared with a Segment in scope is asked once and applies to both.
   - `a3_demand` — the walk runs on stored verdicts only (`stored_decisions`, the reads the decide() cache would
     serve): a Segment whose candidates all have a stored verdict gets exactly what the full pass gave, at today's
     volume. When the walk reaches a candidate with no stored verdict (a newly bought keyword, an expired verdict),
     the Segment keeps the demand of its current `atom_ranking` row in that market (`demand_volume`, NULL = nothing
     claimed). A Segment with no current ranked row there (new, or excluded last time) is asked like a Segment in
     scope.
   - `a3_question_scope` / `a3_question_landing` — a Segment outside the scope with a cached `questions_count` is read
     from the cache, as before (AA-610). A Segment outside the scope whose cache was reset (`questions_count IS NULL`,
     reset by a research PAA write) is landed with stored verdicts only: a question counts only when every active
     question has a stored verdict that keeps it; an unverified question does not count. Its count is used for this
     run's Score but NOT written back, so it stays NULL and the nightly landing sweep (or the research run's own
     recompute) lands it with Jev later.
3. **The cap is a spend budget row, no migration.** `shared.spend_budget` provider `jev`, scope `job:recompute`,
   `per_run_usd`; no row = 0.50 USD and a hard stop. `hard_stop = false` on the row = alert only (the estimate is
   recorded, the run is never held). Staff edit it in Settings → Budgets (`PUT /admin/budgets/jev/job:recompute`).
4. **Held = `stopped_budget`.** A run whose estimate is above the cap ends `stopped_budget` with an error that starts
   with `recompute_jev_cap`, the estimate in its result, and one admin bell (`recompute_jev_held`). It reuses the job
   runner's existing budget stop: no new status, no migration, not counted as queued/running by the deploy gate.
5. **Release = a payload flag.** `POST /admin/job-runner/jobs/{id}/release-jev-cap` re-queues a held recompute with
   `payload.jev_release = {by, at, estimate_usd}`; a released run still records its estimate but is not held. A
   released job is never coalesced with new enqueues, so the approval covers what the staff member saw. The generic
   Retry re-estimates (it may hold again; the stored verdicts may cover it by then).

6. **Kit UI in the Jobs drawer.** A recompute's drawer shows a "Jev spend" block (scope, estimate, cap, released
   by, spent calls / USD, by stage: estimated vs spent). A held recompute shows a note and a "Release and run" button
   (confirm names the estimate). The table keeps Retry only: its rows are the summary shape without `result`.

## Changed

- `resolve_demand`, `resolve_exclusions`, `filter_candidates_by_country_scope`, `filter_candidates_by_landing`,
  `precompute_question_landings` and `run_atom_ranking` take an optional Jev scope; the default (None) is the old pass.
  The landing SQL and the PAA parse moved to module constants (`LANDING_SEGMENTS_SQL`, `PAA_ROWS_SQL`,
  `paa_tuples_of`) so the estimate reads the same rows.
- `decide.active_questions()` (new, read-only) lets a stored-only read tell "no stored verdict" from "question off".
- The filters' stats gained `scope_asked` / `landing_asked`; `recompute_rankings_and_routes` returns `jev_segments`.
- Route policy + role matrix snapshots and `docs/api/openapi.json` carry the new release route.

## Tradeoffs

- No migration: the cap is a `spend_budget` row and "held" is the existing `stopped_budget` status. A dedicated
  `held` status would read better on the Jobs page but needs a CHECK change on `shared.job` and every status list.
- The estimate is read before the run under the recompute lock (one extra pass over the Segment / PAA / demand rows
  and the stored verdicts, seconds). It counts the first new ask of each demand walk and assumes a country-scope pair
  with no verdict is kept, so a run can ask somewhat more than estimated; decide()'s daily Jev cap still applies.
- An out-of-scope Segment whose landing cache was reset is landed with stored verdicts only and its count is not
  written back, so it is re-landed (free, no Jev) on every scoped run until the landing sweep or its own research
  run lands it with Jev.

## Should know

- Done-when evidence lives in `tests/unit/test_aa1083_jev_changed_only.py` (one atomized tour -> only its Segments
  asked; replay: with every verdict stored the scoped Score writes the same rows as the full pass; estimate = asks;
  held / release) and `tests/integration/test_aa1083_jev_recompute_sql.py` (the SQL on Postgres). Route detection
  reads only `atom_ranking` + atoms, so an identical Score means an identical Route for unchanged Segments.
- A held job keeps its Segment scope; a later enqueue starts a new job (it is not folded into a stopped job), which
  estimates on its own. Releasing the held one later still lands its Segments.
- Switch `RECOMPUTE_JEV_SCOPE=all` on the worker restores the old ask-everything pass without a deploy of code.
- Live check: `SELECT stage, count(*) FROM shared.llm_call_log WHERE job_id = '<recompute job>' AND
  provider = 'typesafe' GROUP BY stage` against the 09/11 run (111k calls); the job's `result.jev.spend` shows the same.
