# AA-920 — Inject approved rules into the four writers, with a post-activation check (WM-23, WM-24, WM-26; WM-25 part)

Writing memory group 6 (root `docs/audits/2026-10-20-S245-writing-learning-loop/issues/README.md`), under app ADR 0010,
on the AA-919 release state machine (CIS 287 / 292). Branch `feat/aa-920-writer-rule-injection` (S255). No migration.

## Decisions

- **One builder, in `services/writing_memory/insertion.py`.** The four writers already called the AA-919 slot
  functions (`a1_house_rules`, `t2_block`, `t9_platform_block`, `t9_tenant_lines`), which rendered "" for every
  release. They now render from one code path: `render_rules` / `rule_line` (one rule = one line, whitespace folded so
  a rule cannot open a heading), `_block` (heading + lines of one part), `repair_hints`. No writer formats a rule
  itself (lesson S218: one value, one function).
- **The view carries the rule items.** The prompt builders are sync (`build_t2_system_prompt`, `write_content` in a
  thread) and never read the DB, so `resolve` loads the items once per write (`load_items`, the only loader; the R2 /
  shadow `PgStore` use it too). A part renders only when its items are complete, belong to the part's writer and owner
  (defence in depth over the release CHECK / trigger) and hash to the release's `items_sha256` (the approved text is
  the text sent). Otherwise it renders "" and the stamp says `ignored: true` (fail open: memory never blocks a write).
- **Rule kinds per slot.** `writer_instruction`, `lexicon` (as "Never write \"X\"." / "Write \"Y\" instead of
  \"X\".") and `preference_summary` ("Voice: …", tenant only by CHECK) render in the writing slots; `repair_hint` never
  does: it goes only to the repair pass of a failed gate whose qtax class equals the hint's `gate_class`
  (`mining.gate_class`, the same mapping the miner used to label the cluster). A hint without a `gate_class` never
  fires (documented limit).
- **Placement.** A1: the HOUSE RULES lines after the forbidden-words line of the S1 writer v2 system prompt (the v1 /
  batch path stays frozen, AA-919 plan Q12). T2: platform then tenant blocks at the end of the T2 system prompt. T9:
  platform block appended to `SYSTEM_PROMPT` (cached across tenants), tenant lines after the brand words line of the
  user prompt; both filtered by the rule's `applies_to` channels. Repair hints: A1 flag-fix after AUDIT ISSUES (only
  the acting codes), T9 `rewrite_with_feedback` feedback (only the failed blocking gates).
- **The stamp carries the release fingerprint** = the part's `items_sha256` (ids + hash, never text), next to the
  release id / number already stamped by AA-919. This is what the post-activation check compares.
- **Activation by writer** (`releases.WIRED_CLASSES`, replaces AA-919's `{"empty"}`): A1 and T9 take `rules` and
  `repair_hint_only`; T2 stays `empty` only; `lexicon_only` goes live for no writer (its evidence is an R0 replay
  only, too weak for a prompt change; lexicon reaches T9 through L0 or inside a `rules` release). T2 waits for WM-25:
  its `generation_meta` column needs a CIS migration, and this lane has no migration number (S255: only AA-850 may
  add one, 294). The T2 slot already renders through the builder (pinned by tests), so WM-25 is the migration, the
  tenant projection denylist / regex and one line in `WIRED_CLASSES`.
- **Post-activation check (WM-26)** in `services/writing_memory/post_activation.py`, $0, no model call:
  - reads the writes of the release's writer (and owner) since `activated_at` (until `retired_at`), newest
    first, up to 200 (review S255: oldest first re-read the same first 200 forever): A1 `silver_aa_internal.generated_content` (S1 writer v2 rows, `metadata.writing_release`), T2
    `gold_aa_internal.tenant_tour_versions` + `shared.job.result.writing_release`, T9 `acp_shared.content_piece`
    (approved / held, blog vs not blog, `writer_input.writing_release`); every tenant read filters the owner.
  - per write: carriage (`carried` / `not_carried` / `not_rendered` / `fingerprint_mismatch`), the QA-artefact grep
    (`eval_checks.qa_artefacts` with the release's rule texts: the same function R2 and the shadow use) and the
    isolation probe (`eval_checks.isolation_probe` against every other live tenant's brand-pack fingerprint).
  - verdict: `violation` (any carried write fails), `pass` (>= N = 20 carried, none fails), `pending`,
    `not_applicable` (release 0 / empty).
  - with `apply`, a violation moves the pointer back in one transaction with its audit row: `releases.rollback`;
    a tenant release with no previous is retired alone (`releases.retire_without_previous`, new); a platform release
    with no previous turns the writer's memory off. Then the admin bell (`shared.notifications`) and the operator
    e-mail (`ops_alert_email`, template `writing_memory_rollback`, one per release per UTC day). Ids, codes and
    counts only, never text.
  - callers: job kind `writing_memory_post_activation` (background, concurrency 1, max_attempts 2: $0 and
    idempotent), queued hourly by the api ops sampler only while an active release with content exists (one EXISTS;
    idempotency key per hour), and `POST /admin/writing-memory/releases/{id}/post-activation-check` (`ai.admin`,
    DRY RUN unless `apply`; `apply` needs a signed-in admin id).
- **"Next N generations"** = every write since the activation, checked as they come (the hourly job re-reads them):
  the spec's WM-26 says every piece, the task says the next N; both hold, `pass` is reported at N.

## Tradeoffs

- The view (with rule items) rides in the T9 job payload instead of being re-read in the job: one resolve per piece,
  the first write and every rewrite use the same items. The payload already holds the tenant's brand context; the
  stamp in `writer_input` keeps ids and the hash only.
- The isolation probe is n-gram only (brand name + 6-word runs of the brand pack), not the F10 >= 0.92 embedding
  check of the spec: an embedding call per write would be a paid model call, and WM-26 must add none.
- Hourly, not inline after every write: no extra latency or failure mode in the writers, and a rollback lands within
  the hour. The route lets an admin check at once.
- A platform release with no previous turns the writer's memory off rather than leaving the bad release serving;
  today every platform release has release 0 before it, so this branch is a fence only.
- A `repair_hint` without `gate_class` never fires (no way to know its gate); the miner sets it on every hint.

## Review (S255, independent reviewer)

- **Scan order**: `writes_since` read the OLDEST 200 writes since the activation, so after 200 writes every hourly run
  re-read the same rows and a later violation was never seen. It now reads the newest 200 per run (ADR / CONTEXT
  say so).
- **Refused rollback**: `rollback` can refuse (the previous release fails its own check, or the DB refuses the swap);
  the check then returned `refused:<code>` and left the violating release serving. The rollback now runs in a
  savepoint and any refusal turns the writer's memory off (`action: memory_off`, `rollback_refused: <code>`).
- **No hash, no render**: `load_items` skipped the items-hash check when a row had no `items_sha256`; it now
  refuses (the column is NOT NULL, so this is defence in depth only).
- **Considered, not changed**: a render-time fence for T2 (the AA-919 "second fence"). It would make R2 / shadow of a
  T2 candidate compare identical prompts and record a meaningless pass that WM-25 could later activate on; the
  activation refusal (`WIRED_CLASSES`) stays the T2 fence until WM-25.

### Decisions

- **Migration 297** (reserved for AA-920): `gold_aa_internal.tenant_tour_versions.generation_meta jsonb NULL`, no

  `None` with memory off: the column stays NULL. `shared.job.result.writing_release` is kept (AA-919 readers).
- **Tenant projection**: `generation_meta` in `TENANT_HIDDEN_VERSION_FIELDS`; `TENANT_FORBIDDEN_KEY_RE` extended

  column of the four tenant-read tables / view contains `release` or `memory` (schema reference), so nothing a
  tenant sees today disappears.
- **T2 activation**: `WIRED_CLASSES["t2"] = {empty, rules}`. Not `repair_hint_only`: a hint-only release changes
  no T2 writing slot and the T2 repair passes have no test for hints; a T2 hint goes live inside a `rules` release.
  The refusal text names no issue id (admin-visible).
- **Post-activation T2 read**: `coalesce(v.generation_meta->'writing_release', j.result->'writing_release')` with a
  LEFT JOIN on the job and `WHERE generation_meta IS NOT NULL OR job IS NOT NULL`: a version whose job row was
  deleted (retention) is still checked by its own stamp; a tenant edit (no job, no stamp) is not a T2 write.
- **Check now**: the Releases drawer shows a "Post-activation check" card for any release that was ever active
  (`activated_at`), for `ai.admin` only. It POSTs `{apply: false}` (DRY RUN) and shows the verdict badge, the
  cost, one plain sentence, the counts and, on a violation, the codes and up to 10 violating refs (ids). The UI
  never sends `apply`. The report is dropped when another release opens in the drawer.
- **WM-26 Dev drill, $0**: `scripts/writing_memory/wm26_dev_drill.py`. A1 platform, on the real Dev schema as
  `cis_app`, in ONE transaction that is always rolled back: memory on, an invented approved rule, release N+1 with
  R2 / shadow runs marked `wm26_dev_drill`, approval with a non-admin drill UUID, activation, two v2 writes under the
  real stamp (one clean, one with `gate_ledger:`), DRY RUN (violation, nothing moves), `apply` (rolled back to N,
  audit row, bell, e-mail job), the next `resolve` stamps N, the sweep no longer lists N+1; then ROLLBACK and a read
  outside the transaction (pointer unchanged, no N+1 row). `llm_guard` makes any model call raise. Refuses when A1
