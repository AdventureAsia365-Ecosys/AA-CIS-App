# AA-668 — Writer panel (Social Content): Goal → Angle → auto-write in a right-side drawer

Session S237, lane cis-portal item 3. Scope this session: Social Content only. The tour-rewrite
writer (CatalogDrawer + LiveWriter) moving into the same panel is a follow-up.

Two branches, stacked:

1. `fix/aa-668-brand-default-cta` (small PR, merge first) — the extra CTA step.
2. `feat/aa-668-writer-panel` (stacked on 1) — the drawer.

## Decisions

- **CTA (part 1):** the write-step effect in `AngleGateWizard.tsx` used to ask the tenant for a
  CTA whenever `angle_gate_request.cta` was NULL, which is every real request. The server already
  falls back to the brand's `default_cta` (AA-771, `service.py` `start_write`: `req.cta or
  cta_override or brand default_cta`). The effect now always calls `write`; the inline CTA field
  only shows on the server's 422 `MissingCTAError` (brand has no default CTA). No backend change.
- **Panel (part 2):** the Writer panel is `WriterPanel.tsx`, a kit `Drawer` (720 px on desktop;
  the Drawer's `maxWidth: 100%` makes it a full-screen sheet on a phone). It reuses
  `AngleGateWizard` in `embedded` mode rather than a new state machine: the wizard already owns
  every fetch/poll (request status, `t8_angles` progress, write, piece poll, LiveWriter progress).
  `embedded` now means "inside the panel": the panel owns the context header (Subject title,
  Channel, Segment/Route), the close action and the finished-piece view + actions, so the wizard
  hides `SubjectHeader`, "Start over", the "Content ready" line and `WriteDonePopup`.
- **One click per angle:** each Angle card carries its own "Write with this angle" button, which
  chooses the angle and starts the write at once. This replaces the AA-469 pick-then-confirm pair
  (in both the panel and the standalone T8 page). Goal stays select + "Generate 3 angles", because
  generating angles costs an LLM call and a mis-click there should not spend it.
- **Goal cards:** a 2-column grid (1 column on a phone) so all 8 goals fit the panel without
  scrolling at 1440x900.
- **"Streaming":** no new transport. The panel polls the existing job endpoints the wizard already
  used (`GET /v1/angle-gate/requests/{id}`, `GET /v1/content-writing/pieces/{id}`,
  `GET /v1/progress/piece/{id}` via `LiveWriter`). No LLM call runs inside an HTTP request; T8 and
  T9 stay background jobs (AA-764 / AA-652).
- **Closing keeps the job:** `useWriteWatcher` (in WriterPanel.tsx) takes over a piece the panel
  closed while `ready_state === "in_progress"`, polls it every 4 s (10 min ceiling) and raises a
  kit toast when it is ready or failed. Reopening the same request hands it back to the panel.
- **Reopen:** a Subject picked during this visit gets a "Continue" button. The Slate API does not
  return a picked Subject's `request_id`, so after a reload the shortcut is gone; the piece is in
  My Content either way. No backend change was made for this (scope: no backend change).
- **Result actions:** Export text (+ Export HTML for blog), Open in My Content, Publish (blog and
  facebook only, the channels `v1_publish` supports) behind a `ConfirmModal`; "Change angle" stays
  in the wizard's stepper (it is the "regenerate angle" action — reopens the 3 angles, no new LLM
  call). The AA-819 `AiContentNotice` sits above the actions and inside the publish confirm.
- **Tenant sees content only:** the finished view shows the text and nothing about gates, holds or
  scores. It is copy-locked like My Content's drawer (export is the audited way out, AA-613).

## Changed

- `AngleGateWizard.tsx`: CTA effect (part 1); `onReset` prop removed (its only caller was the
  old inline accordion), `onPieceChange` added; embedded-mode trims listed above; goal grid; angle
  one-click; `LiveWriter compact` inside the panel; the 422 CTA field links to Brand Identity.
- `SlateTab.tsx`: inline accordion replaced by the panel; wrapped in the kit `ToastProvider`.
- `reviewListApi.ts`: `publishPiece` returns the result and treats `success: false` (the endpoint's
  200 for a failed remote post) as an error; `exportPiece` takes only the fields it reads, so the
  panel can export a piece that is not a `ReviewItem`; `PUBLISHABLE_CHANNELS`.
- `_kit/Toast.tsx`: toast z-index 9999 -> 10001, above Drawer/Modal (10000). A toast fired from
  inside an open drawer was painted under the drawer backdrop. Affects every kit toast (only the
  stacking order).
- Tour rewrite (CatalogDrawer + LiveWriter) is NOT moved into the panel this session (lane plan:
  Social Content only). The issue's "same panel for tour rewrite" stays open as a follow-up.
- No Brand Identity change: `default_cta` already exists in Brand settings (AA-771).

## Tradeoffs

- Reusing the wizard inside the panel keeps one state machine (fewer bugs, the standalone T8 page
  keeps working) at the cost of `embedded` branches in the wizard.
- The watcher is client-side only, so a toast needs the Slate page to stay open; if the tenant
  navigates away, the piece still lands in My Content (the job runs server-side).
- The panel is 720 px, wider than the kit default (480), so angle cards and the text read
  comfortably; the Slate behind stays visible on the left at 1440 px.

  `page.route`, no LLM spend). Run against a local `next dev` whose API URL points at a dead port
  (middleware fails open in dev). 5/5 pass; screenshots in the root repo

- The real end-to-end check (real T8 + T9 jobs on a test tenant with `default_cta`, Vercel preview
  1440x900 + phone) is still to do on the preview — paid window approved (~$0.20-0.50).
- Escape inside the publish confirm closes only the confirm: both kit components listen on
  `window`, so the panel holds the confirm state and ignores its own close while it is open
  (review fix).
- Closing the panel in the ~1-2 s between "Write with this angle" and the write call answering:
  the wizard keeps an `aliveRef`; a placeholder (or in-progress latest piece) that arrives after

  is started on an unmounted wizard (review fix; it used to leak a 180 s interval and lose the

## S239 — part 2: the tour rewrite in the same panel (Claude Code, branch `feat/aa668-tour-rewrite-panel`)

Done-when (b) "same panel used for tour rewrite". Frontend only, no backend change.

### Decisions
- **Generic shell:** `WriterDrawer` in `WriterPanel.tsx` is the kit `Drawer` (720 px, full-screen
  sheet on a phone) with the context header (title + a list of `{label, value}` context items), a
  body slot and a footer slot for the result actions. The Social Content panel and the new
  `TourRewritePanel.tsx` both render it; the body keeps `data-testid="writer-panel"` and the title
  `writer-panel-title`, so the S237 spec runs unchanged (5/5).
- **Generic watcher:** `useWriteWatcher` now watches `WatchItem`s that bring their own `check()`
  and messages (`watchPiece` for T9, `watchTourRewrite` for T2, which reads
  `GET /v1/tours/versions/{id}` and the same `isAiWriting` / `isRewriteFailed` helpers as the list).
  `unwatch(group)` takes the angle request id (Social) or the version id (tour).
- **Tour-rewrite header:** tour title, "Rewriting in <language>", "for Tour catalog" (the channel a
  T2 rewrite writes for — the tenant's own tour catalog). **Market is left out**, on both panels:
  a T2 version carries a language, not a market, and the Slate API has no per-Subject market field.
  Adding one is a backend change for a separate issue, only if Nghiệp wants it (S239 audit default).
- **Flow:** "Request Rewrite" in the version drawer closes that drawer and opens the panel on the
  new version (`requestRewrite` now returns the `version_id` the API already sent back; 409 "already
  in progress" is a readable toast). The panel shows LiveWriter compact (steps + typed text), then
  "Your new version is ready…" with **Open in My Catalog** (opens the version drawer on the new
  version) and **Export DOCX**, or on a failed job "Writing didn't finish" + **Retry writing**
  (`POST /versions/{id}/retry`, no extra plan usage — unchanged copy).
- **One source of status:** the panel does not poll the version itself. CatalogTab's my-versions
  query already refetches every 5 s while any version is writing; the panel gets its row by id.
  Before the list has the new row the panel shows LiveWriter's "Starting…".
- **Writing / failed rows open the panel, not the version drawer.** The version drawer now only
  opens on a finished version (`openGroup` filters), and its inline LiveWriter + failed branches are
  removed. A writing row gets a "View progress →" action (it had none), a failed row keeps "Retry"
  and a row click opens the panel with Retry.
- **LiveWriter `untilInactive`:** a retried T2 job first reads the previous run's "failed" Redis
  snapshot until the worker restarts it; LiveWriter used to stop polling at the first terminal
  snapshot. With `untilInactive` it keeps polling while the owner says the job is running
  (`active`), and the panel keys it per retry. Social Content does not pass it (unchanged).
- **Kit only:** the shell and the tour panel use the kit `Button` / `K` tokens; the Social result
  actions moved from the portal `Btn` to the kit `Button` too, so both panels look the same
  (secondary = gold outline instead of grey).

### Changed
- `WriterPanel.tsx` (shell + generic watcher), `TourRewritePanel.tsx` (new), `CatalogTab.tsx`,
  `CatalogDrawer.tsx` (writing/failed branches and the `retrying` / `onRetry` props removed),
  `LiveWriter.tsx` (`untilInactive`), `SlateTab.tsx` (`watchPiece`), `catalogApi.ts`
  (`requestRewrite` returns the version), `CONTEXT.md` (Writer panel line under live progress).
- `tests/e2e/aa668-writer-panel.spec.ts`: a "tour rewrite" block (mocked `/api/tenant`, My Catalog
  Tours): Request Rewrite → panel (title, `en-US`, Tour catalog) → live steps → ready → Open in My
  Catalog shows the new summary; failed → Retry → ready; close mid-write → "View progress" reopens

  full-width sheet. 9/9 pass locally (5 Social + 4 tour), screenshots 10-17.

### Tradeoffs

- The watcher's toast needs My Catalog Tours to stay open (client-side), the same as Social Content;

### S239 review fixes (Claude Code, same branch, new commit)
- **Stale "failed" snapshot after Retry.** `/v1/progress/tour/{id}` keeps the previous run's
  "failed" snapshot (up to an hour) until the worker claims the re-queued `t2_rewrite` job and
  calls `progress.start()`; with a queue that can take minutes. LiveWriter with `untilInactive`
  now treats a "failed" snapshot as "not started yet" (`Starting…`, no red message, no failed step)
  while the owner says the job is running (`active`) **and** this mount has not yet seen a live
  snapshot of the new run. Once a live snapshot arrives, a later "failed" one is the new run's own
  and shows as usual (the panel then switches to its failed view on the next list refetch).
  Chosen over comparing `updated_at` with the retry time: no client/server clock dependency.
- **Version drawer pinned to the version id, not the tour id.** Before, `openGroup` was "latest
  version of the open tour, unless writing/failed", so a rewrite of that tour started elsewhere
  (second tab, Browse Tours batch Rewrite) closed the drawer silently (unsaved edits lost) and
  popped it open again when the rewrite finished. Now the drawer stays on the version it was opened
  on; a save (which creates a new `tenant_edit` version, `new_version_id`) refetches the list first
  and then moves the drawer onto the new version, so the save flow looks the same as before.
  "Open in My Catalog" from the panel opens the rewrite's version id.
- **Mock matches the backend contract.** The failed version in the spec is `status: 'failed'` +
  `job_status: 'failed'` (what `on_terminal=mark_version_failed` writes); the mocked `/retry`
  answers 409 unless the version is failed, like `retry_rewrite` in `api/routers/v1_tours.py`.
- **Tests:** the Retry case now keeps serving the old failed snapshot for 3 s after Retry and
  asserts `Starting…` and no failure text during that window (screenshot 18); a new case opens
  v1's drawer, makes an unsaved summary edit, starts a rewrite of the same tour "elsewhere" (another
  tour is writing so the 5 s poll runs), and asserts the drawer and the edit stay, then closes it
  and asserts it does not reopen after v2 finishes. Both new assertions fail on the previous
  commit (checked by stashing the fix). 10/10 pass.

### Should know (review fixes)
- While the drawer is open on an older version and a newer one exists, the drawer still shows the
  version it was opened on (no "a newer version exists" hint). Request Rewrite there answers the
  readable 409 "already in progress" while the other rewrite runs.
- A rewrite left `pending` with a `cancelled` / `stopped_budget` job still shows Retry
  (`isRewriteFailed`), and the backend answers 409 for it ("Retry failed (409)" toast). This is
  older than AA-668; not changed here.

## S239 — live-run fixes (Claude Code, branch `fix/aa668-tenant-stream-clean`)

Found in the live Dev run (root repo `docs/audits/2026-10-16-S239-in-progress-audit/aa668-verify`).

### Decisions
- **Root cause of the JSON in the stream (BLOCKER, tenant-sees-content-only):** the T9 attempt-2
  sentence repair (`generate.repair_sentences`) runs on the writer stage `t9_write` by default and
  answers with a JSON patch `{"replacements": [...]}`. The job's stream sink streams every
  `t9_write` call, so `on_call_start` counted the repair as a new draft (revision 2), dropped the
  post and streamed the patch; `plain_text_view` showed it as text. Nothing streamed after it, so
  the final snapshot (`finish(True)`) kept the 165-char JSON.
- **Fix at the source, not in the view:** `stream_sink.suppressed()` (new) hides the bound sink
  for the calls inside it; `repair_sentences_detailed` makes its call under it (the reply is never
  tenant text, whatever the stage — `t9_write` or `t9_repair`). Inside, nothing streams and the
  call is not a writer call, so the live view keeps the post it had and the revision stays.
- **The job publishes the text it keeps:** `WritingProgress.show(raw)` + the
  `progress_show(content)` helper replace the displayed text without a new revision (the portal
  swaps it in place). T9 calls it after a repair splice (the spliced post) and right before the
  save (`_show_live_text`: plain text, or the `{seo_title, meta_description, body}` envelope for a
  blog); `progress_step("revise")` is now set explicitly before the repair call, since the muted
  call no longer moves the steps. T2 calls `progress_show(rewritten)` right before its save: T3
  can keep an earlier draft or repair sentences (`t2_flag_fix`, not streamed) and the em-dash fix
  runs after the last streamed draft, so before this the final tour snapshot was the last streamed
  draft, not the saved version. Every final snapshot is now the saved text.
- **Defence in depth:** `plain_text_view` returns "" for a reply that is a JSON object, so a future
  structured call on a text writer stage cannot show its JSON either (the blog / tour views
  already only show labelled keys).
- **Raw keys (item 2):** the Write card showed `Goal: introduction_awareness · Channel: linkedin`.
  The goal now reads from the goal list the wizard already loads (`GET /v1/angle-gate/goals`,
  `name`), the channel from the Channel labels the panel header already used, moved to
  `channelLabels.ts` (shared by `WriterPanel` and `AngleGateWizard` without a circular import;
  `WriterPanel` re-exports `channelName`). An unknown key reads as words, never raw. The
  standalone T8 page's `SubjectHeader` uses the same label.
- **Reopen (item 3) was real:** `r06` shows a highlight cut mid-word and an empty Itinerary with
  the caret after "View progress". A remounted `LiveWriter` started with no snapshot ("Starting…")
  and then typed the whole text from empty. Now it remembers the last snapshot per kind + job id
  for the tab (module `Map`) and starts from it (lazy `useState` init, no effect), and the first
  snapshot a mount sees is shown at once; only text that arrives later is typed. A remembered
  "failed" snapshot is not used while the owner says a retried job runs (`untilInactive` +
  `active`), and the cache never sets `seenLiveRef`, so the S239 retry rule is unchanged.

### Changed
- `shared/llm_client/stream_sink.py` (`suppressed`), `services/acp_shared/writing_progress.py`
  (`show`, `progress_show`, JSON guard), `services/acp_content_writing/generate.py` (repair call
  muted), `services/acp_content_writing/service.py` (`_show_live_text`, revise step),
  `services/jobs/t2_rewrite_job.py` (final text), `CONTEXT.md` (live progress line).
- Frontend: `LiveWriter.tsx`, `AngleGateWizard.tsx`, `WriterPanel.tsx`, new `channelLabels.ts`.
- Tests: `tests/unit/test_aa668_live_text_clean.py` (11); the aa668 spec asserts the goal/channel

### Tradeoffs
- Muting inside `repair_sentences_detailed` (one place, every caller) rather than in each caller;
  the admin sentence-suggest route has no sink bound, so it is unchanged.
- The snapshot cache is per tab and in memory only: after a reload the first poll still shows
  "Starting…" for one round trip (~0.8 s) — the server snapshot is the source either way.
- The first text a fresh mount sees jumps in instead of typing (one poll's worth on a fresh write).

### S239 review fixes (same branch)
- **Retry under the same id (minor, real):** the snapshot cache is keyed by kind + job id, and a
  T2 Retry keeps the version id. Watch run 1, close the panel, run 1 fails, Retry (in the panel or
  on the row), then open the live view: it mounted on run 1's remembered "running" snapshot (half
  the summary, "Checking facts" active) as if it were live, then flipped to "Starting…", and the
  primed revision could make the new run's text jump in. Fix: `forgetLiveSnapshot(kind, jobId)`
  (exported by `LiveWriter.tsx`), called by My Catalog's retry mutation on send and on success.

  writes a new piece (new id), so it needs nothing. Chosen over a `runKey` prop because the
  `retries` counter is page-wide, not per version: keying on it would also drop the remembered
  text of other versions after any retry.
- **T9 job path not pinned (minor, real):** new `test_t9_job_live_view_ends_on_the_saved_post_after_a_repair`
  drives `t9_write_job._run_write_with_progress` → `run_write_background` with a bound tracker and a
