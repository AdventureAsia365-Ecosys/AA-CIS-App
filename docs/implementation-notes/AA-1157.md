# AA-1157 — View as a lower role (CIS side)

Read-only "view as a lower staff role" for an owner: logged start and end, every write refused before the route, the
sign-in untouched. The Booking side is its own PR in AA-Booking (its notes live there).

## Decisions

- **One table, two kinds (CIS 470).** `shared.staff_view_as_session` now holds either a tenant session (`tenant_id`) or
  a role session (`view_role`, `tenant_id` NULL); a CHECK keeps exactly one. The guard trigger gained an explicit NULL
  branch: without it `shared.tenant_account_closed(NULL)` is true and any role row could be deleted.
- **Retention.** The guard lets an ended role row older than 24 months be deleted (the DM-7.1 window); nothing purges it
  yet. Tenant rows keep their rule (deleted with the tenant only).
- **Who may start.** Capability `staff.view_as_role` joins `OWNER_PERMS`: an owner (`is_owner`) on a Cognito session
  holding the built-in admin role (and staff.read), re-read from the DB in the start transaction. The business-owner
  marker alone does not qualify. Preview, legacy and E2E sessions never qualify. A custom role never qualifies, even
  one that holds `staff.read` (`custom_allowed()` keeps it and the custom-role CHECK does not stop an owner from holding
  a custom role): `may_start` checks `role == "admin"`, the same rule the BFF uses to honour the view cookie
  (`VIEW_FROM_ROLE`), so the two sides cannot disagree (review fix). A session whose owner moves to a custom role ends
  as `owner_lost` on its next request.
- **Downward (Q6).** `read_surface(perms)` = every GET/HEAD POLICY route the perms pass (owner-only entries skipped),
  the unlisted GETs (`content.read`), and every read capability a handler checks itself (`*.read`, `tenant.view_as`,
  `learn.preview`, with a small implication map). Downward = target surface ⊆ viewer surface. A capability that gates a
  GET route counts even if it is named like a write (`wave.run` opens the waves page). The refusal names no
  capability (the log lists the missing entries).
- **Effective rights = target ∩ viewer.** `resolve()` swaps the identity (role = view role, capabilities = target ∩
  viewer, `is_owner` False); `principal_from_role` and `staff_roles.role_perms` read the swapped capabilities for a
  view role, built-in or custom (critique correction 3).
- **Token.** HS256 with the tenant JWT secret but its own `aud` (`cis-staff-view-as`) and `typ`; `verify_jwt` (no
  audience) refuses it. `vcp` (the effective capabilities) is a UI hint for the BFF page gate only.
- **Write block.** In the browser flow the staff BFF refuses every write of a view first (`requireAdmin`, fail
  closed) and never forwards it. Round-2 review: that left no trace, because the API never saw the request. Chosen
  fix (option b): the BFF writes one structured log line per refusal, `[view-as] staff_view_as_write_refused app=cis
  session=<id> staff=<owner id> view_role=<role> method=<M> path=<path, no query>` (admin web log). Option a
  (forward the write so the API gate audits it) was rejected: a write off the staff API prefixes is sent with the admin
  secret and no view header, so forwarding needs a second refusal path in the BFF anyway, and the BFF refusal stays the
  one that cannot be bypassed by a proxy bug. `StaffViewAsGateMiddleware` (inside the staff audit middleware, inside
  the bearer middleware) still refuses every non-GET/HEAD/OPTIONS that reaches the API with the view header (403
  `view_as_read_only`, route-agnostic, logged as a `staff.request` row with `details.view_as`); `denial_reason` repeats
  it. The unit test walks `app.routes` for every staff write.
- **Transient read error is not a revocation.** A custom target role whose row cannot be read
  (`staff_roles.STATE_UNREADABLE`) makes `target_role` raise `StaffViewAsRefused(503)`: the request is refused, the
  session stays open and no `staff.view_as_ended` row is written. Only an unknown, archived or empty role ends the
  session (`role_unavailable`). The start answers the same 503.
- **One start at a time.** Both starts (role and tenant) take `pg_advisory_xact_lock(hashtext('staff_view_as:' ||
  staff_id))` before `END_OTHERS_SQL`, so two tabs cannot both commit an open session (the same lock key as Booking).
- **End row for a view left to time out.** The owner's read of an own role session that is past its expiry and not yet
  ended (`GET /admin/view-as/sessions/{id}`) closes it as `expired` with one `staff.view_as_ended` row (cause
  `expired`). The banner checks once when its countdown reaches 0 (and every 60 s); the httpOnly token cookie lives 5
  minutes past the view (`STAFF_VIEW_CLOSE_GRACE_S`, never honoured as a view: `ownStaffView` checks `exp`), so that
  check can still name the session. New start, sign-out and staff disable already closed expired rows. A view whose
  cookie is gone entirely (tab closed, grace over) is closed by the member's session list
  (`staff_view_as.close_expired_own`, one UPDATE that usually matches nothing, best effort): the BFF's sign-out reads
  that list first, so sign-out always writes the end row.
- **Relays.** During a view the bearer middleware does not keep the access token; `relay_authorization` answers None and
  every crm.ops.v1 relay answers its existing "unavailable" (`cognito_session_required`), never a 500 and never the
  owner's token. No staff GET was found that enqueues a job or calls a paid API (POST does that), so no GET deny-list.
- **Side-effect GETs accepted during a view** (inventory, round-2 review): `GET /admin/platform/compliance` runs
  `compliance.sync(pool)`, a system-side, cached, idempotent ingest of S3 evidence rows that any normal reader triggers
  too and that is not tied to the viewer; `GET /admin/view-as/sessions/{id}` closes the caller's own expired role
  session and `GET /admin/view-as/sessions` closes the caller's own expired role sessions (bookkeeping of a view
  that is already over; the view role cannot call either). None writes on behalf of the viewed role.
- **Session read and end.** No new GET: the BFF reads and ends the role session through the existing
  `GET /admin/view-as/sessions/{id}` and `POST .../end`, WITHOUT the view header (as the owner). Both now serve role
  rows (`LEFT JOIN`, `kind`, `view_role`); the session list stays tenant-only (`tenant_id IS NOT NULL`).
- **Ended audit by kind.** `view_as.ended_audit(view_role=...)` writes `staff.view_as_ended` (no tenant) for a role
  session; every closing path passes `view_role` (end route, new start, sign-out / disable, per-request close).
- **BFF.** `requireAdmin` honours the httpOnly cookie only for the signed-in member's own, unexpired view and only on a
  Cognito admin session (an owner can only start from admin; a forged cookie of anyone else is ignored). Rules are then
  checked with the view role and claimed capabilities ∩ verified ones; every write is refused 403
  `view_as_read_only` unless the route acts as the owner (`allowDuringViewAs`: Back and sign-out). The decision is
  the pure `staffViewStep` (lib/staffViewAs.ts) and fails closed: an own, unexpired view cookie refuses every write
  even when the view is not honoured (a stale cookie after a role change, any non-admin session); a read then keeps the
  verified rights but still forwards the token, so the API ends the session (409) and the proxy clears the cookies.
- **Ended view in every staff proxy (round-2 nit).** The 409 `staff_view_as_ended` handling (clear both view
  cookies) moved from the admin proxy into `lib/staffViewCookies.ts answerStaffUpstream`, used by `/api/admin`,
  `/api/tenant` and `/api/pipeline` (the proxies that forward the view header on staff paths). `/api/tour-full` sends
  no view header (not a staff API path).
- **Settings.** No new setting. The 60-minute ceiling is the root ADR 0019 d5 bound and the CIS 364 table CHECK (reused
  `view_as.MAX_MINUTES`). The per-start length (15 / 30 / 60, default 30) is the owner's choice under that bound, as
  for the tenant view; deliberately not a setting.

## Changed (vs. the plan)

- No `GET /admin/view-as/roles/current` route (the existing session read serves it, see above).
- No "View in Booking" link on the CIS roles page: the platform apps registry holds no Booking admin URL and hard-coding
  one is not allowed. Booking has its own "View as" on its Roles page.
- The retention branch in the guard (critique option A) instead of a "not enforced" note.
- The CIS integration test of the code PR relies on the replayed schema (conftest applies 470 once main has it); it
  does not read the migration file, so the code PR imports nothing from the migration PR.

## Tradeoffs

- Data scoped to assignments (customer_success / support books) follows the owner's own assignments while viewing:
  the view may show an empty book. Simulating another person's book would need a target person, which the issue does
  not ask for. The banner says so.
- A view left to time out with the tab open gets its end row from the banner's check at 0 minutes. A view whose tab
  was closed gets it when the owner next starts a view, signs out, is disabled, or reads the session or the session
  list (closed as `expired`); until then the row reads as expired (`expires_at`). No periodic job closes rows (not
  worth a job).
- Reads are not audited row by row (the hash-chained log would flood). Refused writes: a structured log line in the
  admin web (the BFF refusal, the normal flow) or a `staff.request` 403 row (a write that reached the API).
