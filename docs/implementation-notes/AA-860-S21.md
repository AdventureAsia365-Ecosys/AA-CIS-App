root `docs/audits/2026-10-17-S241-x1/x1-plan.md` S21, the S242 and S243 amendments blocks (S243: "245 must handle

Companion lanes: AA-CIS-Infra `chore/x1-s21-introspect` (read-only run-script that lists what 245 moves), root

## Decisions
- **Catalog-driven object transfer (option b), not a generated list (option a).** The plan says "explicit
  statements generated from a live introspection (~120 objects)". This lane cannot query Dev, and the schema
  reference (Verified 19/10 06:00 UTC, CIS 250) lists tables, views, functions and enum *names*, but not standalone
  sequences, type owners, domains / ranges / composite types, extended statistics, collations or text search
  objects. A list generated from it would have gaps that only the last guard would find, at apply time, inside the
  CIS freeze. 245 step 4 therefore reads the catalog at apply time with fixed filters: owner = `aa_cis_admin`
  (literal), the 11 runtime schemas (not `catalog`: only that schema moves, its views stay `catalog_owner`'s),
  extension members excluded (`pg_depend` deptype `e`), owned / identity sequences excluded (they follow their
  table). One `NOTICE` per object plus a total, so the DB Migrate log is the explicit list. Strict post-guards
  (below) make a missed or unexpected object fail the file. The Infra run-script
  `db/scripts/x1_245_cis_owner_objects.py` runs the **same query verbatim** (an Infra unit test compares them once
  the copy lands) and prints the list from Dev before the apply, plus every condition a 245 guard would refuse.
  Locally its `move` lines equalled the 245 NOTICE lines, in order (128 objects in the CI-shaped DB).
- **RLS design pass: policies `TO cis_owner` on the 8 FORCE tables, not `NO FORCE`.** The master reads the FORCE
  tables unfiltered through `rds_superuser` (AA-817 probe v2). `cis_owner` is a plain NOLOGIN role, so as the new
  owner it is filtered by FORCE: every later `cis/` file (DB Migrate `SET ROLE cis_owner`) and every owner-rights
  view (`acp_contract.v_active_tour_atoms` and `v_trip_registry` over `published_tours` / `raw_tours`, the
  `shared.v_*` views, the `catalog_owner` views that read them) would read 0 rows without a GUC. 245 adds
  `<table>_cis_owner_all FOR ALL TO cis_owner USING (true) WITH CHECK (true)` on the 8 FORCE tables, the same shape
  as 244's `cis_app` policies. FORCE stays (SEC-7 follow-up wants it); the policy reaches only `cis_owner` and its
  members, which guard 0 / 8g limit to the master and `db_migrator`. `NO FORCE` was rejected: it would exempt every
  member of the owner from `tenant_isolation` with nothing in `pg_policy` to show it, and the SEC-7 follow-up would
  have to re-add FORCE.
- **Parity measured before the policies (lesson S243).** The master is a member of `cis_owner`, so a policy
  `TO cis_owner` reaches it: step 2 counts every FORCE table + `tenant_tour_versions` and every view of the 12
  schemas the master can read, without a GUC and under a forged one, before step 5. The last block compares: views
  as the master (now running with their new owner's rights), the tables as `cis_owner` and as `cis_app`.
- **Catalog views (XD9).** No `SET ROLE catalog_owner` anywhere (the master is not a member and must never become
  one). The catalog views are counted as the master directly when it can read them (on Dev through
  `pg_read_all_data` from `rds_superuser`, plan §1.1); a view the master cannot read is skipped with a NOTICE (the
  file still applies; the run-script prints `readable_by_login` per view beforehand). Guard 8f checks
  `catalog_owner` keeps USAGE + SELECT on every relation its views read (from `pg_rewrite` dependencies), and the
  privilege snapshot (8c) covers its grants exactly.
- **Privilege snapshot, owner-independent (bk-014 pattern, widened).** Every ACL entry of every non-owner role on
  the 12 schemas, their relations, columns, routines and types, grantor left out; after the transfer it must be
  byte-equal. This is what proves `aa_app_user`, `tripplanner`, `booking`, `catalog_owner`, `bk_owner`, `tp_owner`,
  `cis_app` and PUBLIC lost and gained nothing; the 244 `schema_versions` REVOKE is restated and checked too.
- **Locks up front.** One dynamic `LOCK TABLE … IN ACCESS EXCLUSIVE MODE` on every table of the 11 runtime schemas
  (`shared.job` first) before anything changes, as bk-014 did with an explicit list: all-or-nothing under
  `lock_timeout 5s`, and no concurrent write can change a count between step 2 and step 9.
- **Guard 0 refuses any run not as the master before the transfer** (`current_user` and `session_user` =
  `aa_cis_admin`). After 245 DB Migrate would run the file as `cis_owner`; a redo or the undo is a `roles/` file.
- **CI: `cis_owner` and `db_migrator` created in conftest with rl-002's attributes**, like rl-001's roles; the
  memberships / `CREATE` on the database that rl-002 adds are set up by the test that needs them (catalog_owner,
  one of db_migrator's memberships, only exists after the replay ran 225).

## Changed (vs the plan text)
- Plan "explicit statements … ~120 objects" → catalog-driven loop + verbatim introspection script (Decisions).
- Plan RLS effect "FORCE tables: unchanged for everyone" was based on §1.4 (corrected in S243): 245 adds the 8
  `cis_owner` policies instead.
- Plan guard "behavioural counts as in 244 (runtime, `aa_app_user` via its own policies)": `aa_app_user` cannot
  be reached inside the file (the master must never be its member), so its side is covered by the policy snapshot
  (every policy but the 8 new ones byte-equal) and the privilege snapshot; the isolation probe's tenant matrix
  (its own DSN) is the behavioural check. `cis_app` and `cis_owner` are checked behaviourally.
- Guards are stricter than the plan: every object in the 12 schemas must end `cis_owner`'s (catalog relations
  `catalog_owner`'s), not only "0 owned by the master"; FORCE set exactly the 8; default ACL exactly 33 rows FOR ROLE
  `cis_owner` to `cis_app`; members of `cis_owner` only the master and `db_migrator`.
- **conftest**: skips 245 in the replay (like 244), adds `x1_245_undo`, and now also drops the four empty CIS
  schemas at the start of a session. Left over from `x1_244_ci_shape` in a reused local DB, they let migration 019
  create `acp_silver_s4.social_content` (RLS on) on the next replay — a table CI's fresh DB never has, which the
  244 / 245 exact-set guards refuse.
- New standing check `test_standing_a_new_force_table_has_a_cis_owner_policy`.

## Tradeoffs
- Catalog-driven DDL is less reviewable in the diff than 120 explicit lines; the run-script output (before) and the
  NOTICE list (during) are the reviewable list, and the guards make any surprise fail closed.
- The view counts (all views of the 12 schemas, two GUC states, before and after) lengthen the time the file holds
  ACCESS EXCLUSIVE on every CIS table: a few seconds on Dev (`catalog.v_tour_place` scans every live tour,
  ~1 s per count). Accepted on Dev (no real users); the alternative was no behavioural check of owner-rights views.
- 244 left `UPDATE` / `DELETE` on `acp_shared.audit_log` to `cis_app` (248's triggers refuse both) and marked it a
  candidate for 245; kept out to keep 245 an ownership-only file.
