# AA-1003 — Report core R1 (CIS engine)

Slice R1 of the report catalog (root `docs/audits/2026-10-29-S258-report-catalog/`, README §6-7, `automation-plan.md`).
The registry itself (root `docs/reports/catalog.yaml` + `kpis.yaml`, lint `tools/docs/report_registry.py`) is in the
root repo PR; its notes are root `docs/implementation-notes/AA-1003.md`.

## Decisions

- **Vendored registry.** `services/reports/registry/{catalog,kpis}.yaml` are byte copies of the root files (the root
  repo is separate; the docs-bundle sync to S3 would need a root workflow and an Infra permission). The root lint
  compares them with `check --copy`; `tests/unit/test_aa1003_report_registry.py` compares them when the root checkout
  sits next to this repo.
- **One scope column, not app / tenant columns.** `shared.kpi_daily` keys on `(kpi_id, day, scope)` with `scope` NOT
  NULL (`all`, `app:<app>`, `provider:<provider>`): a nullable app/tenant pair would need `NULLS NOT DISTINCT` in the key
  and a `tenant_id` column makes the table a tenant table (ADR 0017: RLS ENABLE + FORCE, erasure inventory entry). The
  R1 KPIs are platform numbers; tenant KPIs (CIS-04, CRM-*) belong to later slices and can add their own table or a
  `tenant:` scope with RLS through a contract migration.
- **Expand migration (305).** Only new tables, indexes, grants, comments; no DO block (the expand lint treats it as
  opaque), plain `CREATE TABLE` (an `IF NOT EXISTS` on an existing relation is exit 15). `python3
  db/run_migration.py --inspect` and `check_migration_ownership.py` of AA-CIS-Infra main pass locally; the runtime
  classify runs in CI (Migration preflight).
- **Number 305.** 303 is main's max; another S258 lane holds 304 (LLM gateway) in a worktree. Strict prefix (ADR 0017)
  means 305 cannot apply and readiness (`REQUIRED_CIS_KEYS` includes 304) cannot go green before 304 is registered.
- **ICT days.** Every KPI day and report period is an ICT (UTC+7) day; bounds are computed in Python
  (`services/reports/periods.py`) and bound as timestamptz, so no SQL depends on the DB time zone.
- **Schedule in the ops sampler**, like the AA-917 / AA-920 daily kinds (no Infra Lambda path needed): one indexed
  EXISTS per tick, the INSERT only when the day's snapshot is not queued yet. Day D is snapshotted from 00:30 UTC of
  D + 1 (07:30 ICT, automation-plan §2).
- **Chain, not a second schedule.** A scheduled snapshot that wrote every KPI queues `report_generate` for the CIS
  reports with schedule daily/live (EX-04, EX-06), one scheduled run per report and period (partial unique index).
- **Failures are loud.** A KPI computer that raises does not stop the others; their values are written, then the job
  raises (runner retry, max 3) and no report is chained. `report_generate` marks its run failed and re-raises; its
  `on_terminal` hook fails a run left queued/running by a cancelled or exhausted job.
- **Run row and job in one transaction.** `enqueue_report_run` creates the `report_run` row, queues its
  `report_generate` job and links them in one transaction. A failed enqueue rolls the row back, so the snapshot job's
  retry chains the report again (with the row kept as failed, `report_run_schedule_uq` would refuse the retry's
  scheduled row and that day's report would only come back through a manual run).
- **Point-in-time KPI** (K-CAT-LIVE) counts `gold_aa_internal.v_tour_liveness` rows with state `served` (the view's
  states are served / paused / retired, CIS 272; there is no `live` state, which the advisory text used). It is
  written only for the newest day, never back-filled. Backfill window: 90 days (failed `shared.job` rows are kept 90
  days).
- **Alert bounds.** `generate.alert_status` reads only `amber_gte` / `red_gte`; `registry.parse` refuses any other key
  in an `alert` block (as the root lint does), so a future `red_lte` fails loudly instead of showing "ok".
- **EX-06 names its own run.** The register is rendered while its own run is `running`; its row says "this run"
  (`last_status: this_run`) instead.
- **Statuses.** `report_run.status` has `draft / approved / posted` reserved for the semi-automatic reports; R1 uses
  queued → running → succeeded | failed.
- **Admin API**: the register returns all 63 reports at once (fixed registry; the page filters the full list, so the
  "client paging over a server page" lesson does not apply); runs are paged on the server. Admin only (ops.read /
  ops.write), BFF read and write rules `reports`.
- **UI** uses the kit only (DataTable, FilterBar in the URL, KpiTile, Drawer, Checkbox, Badge, MarkdownView). Registry
  text goes through `stripIssueIds()`.

## Changed (vs the issue text)

- `kpi_daily` has `scope` instead of separate app / tenant columns (see above); `kpi_version`, `data_as_of`, `job_id`
  added. `report_run` also has `trigger`, `job_id`, `output_markdown`, `approved_by/at`, `created_at/updated_at`.
- Extra read route `GET /admin/reports/runs/{run_id}` (one run with its output) so the list stays light, and
  `POST /admin/reports/snapshots` {day?} (admin): a manual `kpi_snapshot_daily` for one day (the back-fill path; the
  job runner has no generic enqueue route). API only, no button yet.
- No S3 write in R1 (`s3_key` stays NULL): delivery to the reports bucket prefix is a later slice (needs the prefix and
  the task role permission in Infra).
- The DATA-05 request form is not built; a manual run accepts a period (`period_start` / `period_end`, at most 31
  days, within 90 days), which is the "run for another period" half of DATA-05.

## Tradeoffs

- KPIs of Booking / TripPlanner / CRM (K-TP-*, K-BK-*, K-COST-FCST) are listed by EX-04 but not measured yet; the
  scorecard names them under "Not measured yet" rather than guessing from cross-schema reads `cis_app` may not hold.
- The register's due rule covers only CIS-generated daily/live reports; every other report shows "not generated here".
- `cis_app` keeps DELETE on the new tables through cis_owner's default privileges (an expand file cannot REVOKE); the
  code never deletes.

## Should know

- **Merge order.** 305 needs 304 first: open CIS PRs #1158 / #1159 claim 304. `REQUIRED_CIS_SCHEMA = 305` is a strict
  prefix (304 must be registered too) and the CI Migration preflight wants "main max + 1", so this PR merges only after
  the 304 PR has landed. If the 304 lane is dropped, renumber this one to 304: file name, header, `Number.` paragraph,
  registration `VALUES ('305', ...)`, `api/core/readiness.py`, the integration test's `version = '305'`, `CONTEXT.md`
  and the "CIS 305" comments (grep `305`), plus the root retention row.
- **Known gaps (accepted for R1, visible as overdue / failed):** if `kpi_snapshot_daily` fails all 3 attempts, its
  idempotency key `kpi_snapshot_daily:<day>` stops the sampler from queuing it again: that day has no snapshot and no
  chained reports. Recovery: `POST /admin/reports/snapshots {"day": "<day>"}` (re-computes and, as a manual trigger,
  does not chain), then "Generate now" on EX-04 / EX-06 for that day.
- **DELETE grant follow-up.** `cis_app` holds DELETE on `shared.kpi_daily` and `shared.report_run` through cis_owner's
  default privileges; an expand file cannot REVOKE. Track a later contract migration that narrows it to SELECT,
  INSERT, UPDATE.
- **OpenAPI.** `docs/api/openapi.json` is regenerated with the pinned fastapi / pydantic of `requirements.txt` (the
  five `/admin/reports*` paths, `RunRequest`, `SnapshotRequest`; additions only).

# R2 — daily safety net (OPS-12, TP-03, DATA-01; OPS-04 in the root repo)

Branch `feat/aa1003-r2-daily-safety-net`, rebased on `main` after R1 (#1161) merged. No migration. Root companion
branch `docs/aa1003-r2-postmortems` (registry edits, postmortem folder, template, first postmortem).

## Decisions

- **Registry first.** Root `docs/reports/catalog.yaml`: OPS-12 and TP-03 `generator: cis`, status `partial`; TP-03
  `schedule: daily` (was `hourly`): the report run is the daily summary, the hourly part is a job
  (`inquiry_handoff_check`), not a report run (report_run_schedule_uq allows one scheduled run per period). DATA-01
  stays `generator: null`: it is a section of OPS-12 and its numbers are KPI snapshots. OPS-04 points at the updated
  `docs/templates/postmortem.md`. `kpis.yaml`: snapshot blocks for K-TP-HANDOFFGAP, K-BK-PARKED, K-BK-INQ2CASE,
  K-DATA-PROBES, K-DATA-LIVENESS, K-DATA-STALE (alert `red_gte: 1` where 0 is the target); K-BK-PARKED's name
  "Parkedfailed" fixed. The CIS copy is byte-identical.
- **TP-03 reads the contract views only.** `cis_app` has SELECT on `tripplanner.v_ops_traffic_daily` and
  `booking.v_ops_funnel_daily` (tp-015, bk-017), not on `tripplanner.v_inquiry_outbox` or `booking.inbox_events`. So
  the gap is a count per UTC day, not a list of keys; the per-inquiry 15-minute rule, the age of parked rows and
  "received but no trip case after 24 h" wait for key-level contract views (request below, "R2 follow-up
  requests"). Never read with another login.
- **Alert rule = "still there at the next hourly check".** A gap at one check may be an inquiry in flight; a gap at
  two consecutive hourly checks (an hour apart, past the catalog's 15-minute allowance) raises the bell and the
  e-mail. The previous check is found by its idempotency key (`inquiry_handoff_check:<previous UTC hour>`).
- **Window = last 7 UTC days, today included**, summed: a day-boundary shift (sent 23:59, received 00:01) cancels out
  inside the window instead of alerting.
- **DATA-01 source = CloudWatch Logs.** The two ECS probes CIS could otherwise only re-implement (tour liveness gate,
  freshness probe) already print a `SCRIPT verdict` line that the Infra gates parse; CIS reads the same line with
  `FilterLogEvents` (streams `migrate/migrate/*`, filter on the run-script line or the verdict), last run per probe
  wins, `missing` / `no_verdict` count as not passed. GitHub-only workflows are named "not visible", not counted.
  Needs one IAM statement (below, "R2 follow-up requests"). Without it: `kpis.Unavailable`, no value, reason in the
  job result.
- **`kpis.Unavailable` does not fail the snapshot.** R1 raises on any failed computer so the runner retries; an
  outside source that is down (or a permission still pending) must not hold back EX-04/EX-06/OPS-12 every day. The
  reason is kept in the result (lesson: best-effort steps leave a trace).
- **OPS-12 e-mail to an opt-in list, not the alert recipients.** New kind `report_email` (SES via
  `shared/aws_client/ses_mailer.py`, the existing sender and configuration set); recipients only from
  `OPS_DIGEST_EMAIL_TO` (comma-separated, set on the worker task definition). Empty = skipped with the reason. Only
  scheduled OPS-12 runs are mailed ("Generate now" is not).
- **Digest probes CIS like an outsider**: `GET https://api-cis.lumiguides.it.com/health` + `/health/ready` from the
  worker (the worker's own SHA is not the API's). Alarms: `DescribeAlarms` only (already granted), not
  `GetMetricData` (no traffic numbers in the digest, $0).

- **Review fixes (S258, after the independent review).**
  - *Bounded CloudWatch Logs read.* `probes._client()` is the ops overview client (`cloudwatch.aws_client`: connect
    2 s, read 5 s, standard retries, at most 3 tries a call) instead of botocore's 60 s defaults and legacy retries;
    the paged search has a 20 s budget (checked between pages) and the 20-page cap. Both jobs that read it hold a
    pool connection (kpi_snapshot_daily via compute_day, report_generate via digest.collect), so a slow or
    unreachable CloudWatch could have kept a connection busy past the lease and got the job reaped and re-run.
  - *No partial probe verdicts.* A search that still has a next page at the cap or after the budget raises
    `LogsUnavailable("incomplete")`: counting a partial read could call a probe that ran "missing".
  - *LLM `unknown` is not green.* Since #1160 an idle route reads `unknown` once its last answer is older than 6 h,
    and the failed jobs leave the 24 h window after a day (29/10: Dev idle after 14:11). The digest now lists
    "LLM route unknown: no answered text call in the last 24 h" when status is `unknown` and no text call was
    answered in the window (embeddings do not count). `unknown` with answered text calls 6–24 h ago is not flagged.
  - *Contract views fail soft in the snapshot.* `handoff.CONTRACT_ERRORS` (InsufficientPrivilege, UndefinedTable,
    UndefinedColumn) become `kpis.Unavailable` in `inquiry_handoff`, so a revoked grant or an owner migration that
    replaces a view cannot stop EX-04 / EX-06 / OPS-12 / TP-03. The hourly check and the TP-03 run still fail on it
    (visible in the OPS-12 jobs and reports sections).
  - *Kill switch.* `INQUIRY_HANDOFF_ALERTS` on the worker (default on; `off` / `false` / `0` / `no`) turns the TP-03
    bell and ops e-mail off; the check still runs and its result says `alert.disabled`. OPS-12 e-mail stays opt-in
    (`OPS_DIGEST_EMAIL_TO`).
  - *Worker parity only with a known API commit.* When the CIS probe gets no answer, `same_commit_as_api` is `None`
    (not compared) instead of `False`, so the digest does not add a misleading second item.
  - *Reuse.* The digest probes apps with `platform_apps.http_health_card` (new public form of the card probe, with
    `base` / `paths` for CIS) and uses `cloudwatch.aws_client` / `cloudwatch.is_denied` (public wrappers), not the
    private helpers.
  - *Environment.* `app_registry.cis_api_origin()` reads `PUBLIC_API_BASE` (already read by `services/photos/sync.py`
    for the same origin), Dev default; `probes.log_group()` uses `cloudwatch.environment()` (test / local -> dev).
  - *Bug found by the new integration test.* `handoff.build_days` kept the last `inquiry_sent` row of a day instead of
    summing (the contract allows several rows per day and metric; the ops overview sums them). Fixed and covered in
    unit and integration tests.

# R3 — money: weekly and monthly cost reports (EX-01, FI-01, FI-02, FI-03, FI-04, FI-05, FI-06, OPS-08)

Branch `feat/aa1003-r3-money-reports` (from `main` after R2 #1162). No migration (308 left unused).

## Decisions

- **One module, many reports.** `services/reports/money.py` (pure computations + renderers, unit-tested on fixture
  rows) over `services/reports/money_sources.py` (readers + `collect_week` / `collect_month`). Registered in
  `generate.RENDERERS` like R1/R2; registry copy: the 8 reports get `generator: cis` (FI-02 status missing -> partial).
  The root lint (`tools/docs/report_registry.py check`) passes on the edited copy (run against a scratch root).
- **Schedule from the daily chain, no new job kind or sampler part.** `periods.scheduled_period(schedule, day)`:
  daily/live = the day; weekly = the ISO week when the snapshot day is its Sunday (chain at 00:30 UTC Monday,
  catalog says 01:30: the snapshot is the existing hook); monthly = the previous month when the next day is business
  day 2 (chain at 00:30 UTC of BD2, catalog 02:00). `report_jobs.chain_reports` and the register's due rule
  (`generate.due_state` via `periods.latest_scheduled`) use the same function, so "overdue" means exactly "the chain
  should have created it". Manual "Generate now" defaults to the last closed ISO week / month
  (`periods.default_period`).
- **Money days are UTC days.** Cost Explorer, `shared.llm_call_daily` and the cost pages count UTC days; an ICT
  window would split every ledger day. The ISO week / month of the period is read as those UTC dates; only K-CAT-LIVE
  and the job KPIs come from `shared.kpi_daily` (ICT).
- **Reuse the cost modules, never recompute spend another way** (platform_cost docstring, S243): per-App numbers
  from `platform_cost.cost_by_app(..., redis=None, refresh_if_stale=False)`, month-to-date / forecast / budgets from
  `cost_ops.cost_forecast`, per-service from `cost_explorer.read_cost_range`. They were written for a pool;
  `money_sources.ConnPool` runs them on the job's one connection (sequential, lesson S219: never concurrent on one
  connection).
- **No Cost Explorer call from a report** (task brief: no paid call; automation-plan §5 allowed one FI-01 refresh).
  The AWS part reads the stored snapshots and labels the month `missing` / `partial` / `provisional` (fetched before
  month end + 3 days, platform_cost FINAL_AFTER) / `final`, with the refresh path in the text (open Platform › Cost
  per app for that month once, ~0.01 USD, then Generate now). A scheduled FI-01 on business day 2 is therefore
  provisional by design; re-run it from day 4.
- **OPS-08 reads CloudWatch RDS metrics** (CPUUtilization avg, DatabaseConnections max, FreeStorageSpace min; hourly,
  30 days) with one GetMetricData call through the ops overview client (`cloudwatch:GetMetricData` already granted
  for /admin/overview; ~0.00003 USD a month). Denied / failed = "CloudWatch not readable", never a failed run.
  Instance from env `RDS_INSTANCE_ID` (default as `/admin/pipeline`). Database size, largest relations, connection
  limits from the catalog (free).
- **"not wired" vs "not readable".** A KPI whose source the platform does not hold (K-DEL-SHIPPED Linear, K-REL-SEV
  incidents, K-VEND-HEADROOM free-plan usage, K-VEND-DPA legal register, K-UNIT-AGENCY CRM tenants, K-CAP-TRIGGERS)
  is `not wired` with what to fill in; a part that failed is `not readable` with the error. Neither fails the run.
- **acc3 Bedrock counted once.** FI-02's week total uses the LLM account's Cost Explorer bill when stored for all 7
  days, else the gateway estimate (both are shown as lines).
- **Budgets.** Per-App AWS Budgets mirrored in `cost_ops.APP_MONTHLY_BUDGET_USD` (cis 90, tripplanner 10, booking 25,
  crm 35, identity 10, shared 120; Terraform `per_app_monthly_budgets`), env `COST_OPS_APP_BUDGETS_USD` overrides,
  like `AWS_MONTHLY_BUDGET_USD`. The acc3 AWS Lift credit has no API: env `COST_OPS_CREDITS_USD=acc3=<usd>@<date>`
  (unset = K-RUNWAY-ACC3 / K-VEND-EXPIRY `not wired`).
- **Hard stops (K-FIN-HARDSTOP)** = budget bells (`shared.notifications` `spend_budget_alert`) whose message is not the
  threshold sentence (`cost_guard.maybe_alert` with a reason). The gateway keeps no refusal log; documented proxy.
- **Forecast accuracy (K-FIN-FCSTACC)** re-computes `cost_forecast` as of the end of day 15 from the stored rows and
  compares it with the month; it is not the number the page showed on day 15 (no forecast history is stored).
- **FI-02 e-mail** goes to `OPS_DIGEST_EMAIL_TO` (catalog decision 5: the tech lead gets OPS-12 and FI-02). Split the
  variable when someone wants only one.
- **A missing source never reads as a number** (review fix). `money.app_lines` turns the AWS amounts of a month with
  no stored App-tag snapshot (`cost_by_app` `aws.has_data` false: it still returns every App row at 0.0) into None,
  and `total_usd` with them (it includes the AWS part), so K-COST-APP / FI-06 App lines / K-FIN-VAR / 3-month
  averages / K-UNIT-TOUR say no_data instead of "0 USD, ok" or an AI-only unit cost; the LLM-ledger AI amounts stay.
  `credit_outlook` gives no amount at expiry and no flag when the burn is unknown (`per_day` None); a known 0 burn
  still warns.
- **FI-06 reads the LLM ledger** (`MONTH_NEEDS["FI-06"]` includes `llm`): its Credits section needs the acc3 burn
