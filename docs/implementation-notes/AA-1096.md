# AA-1096 — Every threshold, limit and cap editable on an admin page (lane L1, CIS)

Tech lead decision (S279): every threshold, limit, cap and policy value is editable on an admin page by the
administrator; the eleven defaults of the S279 thresholds audit are approved (root
`docs/audits/2026-11-13-S279-session/thresholds-audit/`, sections 5 and 6, lane L1). This lane builds the mechanism in
AA-CIS-App and moves the high-impact CIS values onto it.

Two PRs, in order:

1. **Migration-only** (CIS 407, expand): `shared.setting_definition` + `shared.setting_value`, the trigger, RLS, the
   seed of 25 settings, the compiled-defaults generator and its seed-parity test, the migration integration test,
   the X2 allowlist entry for `shared.setting_value` (rule a: it has a `tenant_id` column), the two tables in the
   conftest post-244 / post-245 RLS lists (the 244 / 245 replays know only their own set) and the erasure inventory
   entry (`shared.setting_value`, delete: the tenant backup catalogue follows it). These ride with the migration
   because the migration PR's own integration CI fails without them.
2. **Code**: the reader library, the API, the readers switched, the Platform › Settings page, tighten-only on the
   delegated pages, the CI guard (settings-lint), the audit 3.3 fixes.

## Decisions

- **Tables (audit 5.1).** `setting_definition` rows come only from migrations; widening a bound is a reviewed
  migration. cis_app is granted SELECT only, but CIS 245's default privileges give it DML on every new `shared` table
  and an expand file cannot REVOKE, so a trigger (`shared.setting_definition_guard`, the CIS 400 pattern) refuses every
  write by a role outside `cis_owner` (review fix: otherwise the app role could widen the bounds the value trigger reads). `setting_value` is append-only: an insert is always a proposal; the trigger lets an
  update change only the decision columns (`proposed -> approved | rejected`, `approved -> superseded`) and never
  deletes a platform row (a tenant row is deleted by the offboarding erasure, the only reason cis_app holds DELETE;
  FK cascade as the backstop). One open proposal per key and scope (partial
  unique index), versions unique per key and scope. The same value rules exist twice on purpose: in SQL
  (`shared.setting_value_problem`, the backstop) and in Python (`shared/settings/reader.validate`, so the API answers
  422 with the reason before the trigger would).
- **Reader (audit 5.2).** `shared/settings/reader.py` is standard library only (structlog optional) so AA-Partner and
  AA-TripPlanner-Web can vendor a byte copy. One snapshot of every approved value of the app, refreshed every 30 s by a
  background task in the API (lifespan) and the worker (`_main`); `get()` never touches the DB, so sync code (a
  LangGraph node, a dataclass default) can read it. A DB error keeps the last good snapshot, else the compiled
  defaults. A stored value that breaks its definition is refused (default served) and one ops e-mail per key and UTC
  day is queued (`setting_out_of_bounds`). Env overrides win when valid (warning once per process, badge on the page);
  an invalid env value is ignored, never served.
- **Compiled defaults.** `shared/settings/compiled_defaults.json` is generated from the migration seed block
  (`-- settings-seed:begin/end`, a JSON array) by `scripts/settings/gen_compiled_defaults.py`;
  `tests/unit/test_s279_settings_seed_parity.py` fails when the two differ. A later migration may re-seed a key (later
  rows replace earlier ones).
- **Seed = today's effective value** (audit 5.5): `T7_BLOG_MIN_SEED_WORDS` 600 (Terraform; the code default was 0),
  `t7.blog_chars_per_seed_word` 5.8 (its description names the S279 replay: 3.364, floor 1,398 words, to be proposed
  with that replay as evidence), `t9.repeat_drop_near_exact` 0.9, T9 3 attempts, A1 3 retries, T2 version budget
  2 / 3 / 1 / 0.25 USD, writing memory 25 USD a month, segment research 50 USD a run, place backfill 50 tours, rerun wave
  2,000 tours, question top-up 3 USD, the DataForSEO price table, 20 posts a day, the soft over-quota rule, the 7-day
  retirement notice, retention 180 / 90 / 30 / 90 days, erasure 30 days, trash 30 days (`enforced=false`) and
  `cis.settings.two_person_approval` off.
- **Permissions (Q1).** `settings.write` (propose) and `settings.approve` (decide), admin only; reads need `ops.read`
  (admin only) and the BFF lets only the admin role reach `settings/registry`. Delegated pages keep their roles but are
  **tighten-only** for a role without `settings.write`: ai_ops on spend budgets (`PUT/DELETE /admin/budgets/...`) and
  tenant AI budgets, customer_success on a tenant's RPM and daily publish limit (`PATCH /admin/tenants/{id}`). Lower a
  cap, add one or turn a hard stop on: allowed; raise, remove, soften (hard stop off, a later alert / approval
  percentage): 403. Review fix, the rest of the audit's list: ai_ops on the app profile (switching AI on, un-pausing
  bulk work, raising or clearing the default daily budget: 403; `degrade_mode` is failure handling, not a limit), on
  capacity limits (raising or dropping `tpm_limit`, widening `bulk_pct` / `dev_pct`, prod guard off, DELETE: 403; a new
  row only adds a limit) and on the connection limits and cost policy (`rpm_limit`, `max_concurrency`,
  `monthly_budget_usd`, `daily_credit_limit` as caps, `max_retries` / `budget_alert_pct` up is looser,
  `low_balance_usd` down is looser, hard stop off; `enabled` is routing and `timeout_s` is not a limit, both stay
  editable); customer_success on a tenant's `posts_per_week` (raise: 403).
- **Maker-checker in the dev phase (Q2).** `approval=maker_checker` keys need a second person unless
  `cis.settings.two_person_approval` is off: then the proposer may approve their own change (`self_approved` is
  recorded) and a high-impact change queues an e-mail to the ops recipients (`setting_self_approved`). Turning the flag
  on is the "first prod or paying tenant" switch. The flag is **maker_checker** itself (review fix): while it is off the
  administrator may apply it alone; once on, turning it off needs a second person. The API reads the flag in the
  decision transaction (latest approved platform row in force, else the default; fail closed on a read error), never
  from the 30 s process cache, and the DB trigger refuses a self-approval while the flag is on (backstop).
- **Who the actor is (review fix).** Every write of `/admin/settings/registry` needs a verified Cognito session; the
  proposer / approver is `admin:<shared.admin_users.id>` of the verified identity and `can_approve` follows the verified
  role, never the `x-admin-*` headers (the same rule as `staff.write` and the alert recipients).
- **Evidence (Q3).** `evidence_required` keys (the measured ratio and the repeat-drop share) refuse a proposal without
  an `evidence_ref`. The quality registry YAML itself is lane L2; only the two S279 keys named in this lane moved out of
  `thresholds.yaml`, with the change-control `gates` lock accepted on `parity:tests/unit/test_s279_settings_readers.py`
  (the readers return the same values).
- **Audit 3.3.** Tenant AI budget `DEFAULTS.hard_stop` is now true (fail closed, as the PUT body). `policy.notice_days`
  (plan entitlement) is now read: agency row, else the plan value, else the platform setting; the platform row of
  `acp_shared.tour_retirement_policy` (no writer) is no longer read. Trash 30 days is a setting with `enforced=false`
  (badge "not enforced yet") until a purge job exists. `api.calls_monthly` is **not wired** (see Should know).
- **T9 attempts (review fix).** The setting only stops the loop earlier; the attempt numbers keep their structural
  meaning (1 write, 2 repair, 3 the legacy sentence repair). Stop-and-label mode: attempt 2 is the last paid one at
  2 and at 3 (the third step is the $0 label); legacy mode: 2 drops the paid attempt 3. `paid_attempts_for` /
  `is_last_try` carry the rule and are unit-tested in both modes.
- **Scripts read the approved values (review fix).** A process without the background refresher (an ECS exec script
  with its own pool) calls `settings.ensure_fresh(pool)` at each paid-run entry point (`run_topup`, `run_r2`,
  `r2.estimate`, `run_shadow`); the run holds the month cap it read. `scripts/aa779_serp_topup.py` no longer hard-codes
  the $3: `--cap` defaults to the setting and `run_topup` refuses a larger one.
- **DataForSEO price table (review fix).** `dfs_call_estimate_usd()` lays the stored table over the compiled default:
  a label an edit left out keeps its seeded price, a non-positive entry is ignored; the definition's minimum is
  0.0001 (an entry of 0 is refused by the API and the trigger).
- **T7 Blog minimum seed has no env override (review fix).** `T7_BLOG_MIN_SEED_WORDS` was set on the worker task only;
  the page (served by the api) could not see it, so an approved value would have been silently overridden by 600. The
  definition's `env_override` is null and the worker's env var is no longer read; the seed equals it (600).
- **Geocoder backfill cap.** The code copy of the spend_budget row (`GEOCODER_BACKFILL_CAP_USD` 50) is gone: the batch
  reads the `geocoder / job:place_geocode` per-run value (editable on AI gateway › Budgets); the cost guard's safe
  defaults carry the 226 seed (50 USD) so an unreadable table keeps the cap.

## Changed (vs. the issue text)

- API path is `/admin/settings/registry` (as the issue says), not under `/admin/platform/*`; the BFF has its own
  admin-only read and write rules for `settings/registry`.
- The CRM / TripPlanner tabs are on the page but list nothing until lanes L4 / L5 seed their rows; the Booking tab links
  to Booking's Pricing › Policy (it keeps its own maker-checker page, audit 5.1).
- Request bounds that were literals (`BackfillRequest.limit le=50`, `WaveCreate.tour_ids max_length=2000`, segment
  research `max_usd le=50`) now take the setting's bound; the route checks the value in force (422 / plan cap).

## Tradeoffs

- One snapshot per process (not a per-key query): reads are free and sync-safe; a change takes up to 30 s (cache_s) to
  reach another process. The approving process invalidates at once.
- `VersionBudget` reads the T2 caps when a budget is made (new version or a checkpoint resumed by a retry), so a change
  never moves a version mid-run.
- Values that a request validator needs at import (Pydantic `le=`) use the definition's bound, not the value in force;
  the route re-checks the value in force.
- The settings-lint baseline (133 policy-looking constants of the governed modules) is a list that only shrinks; it
  makes new literals fail without blocking main on the existing ones.

## Follow-up (S280): settings-lint over the whole CIS code

Branch `chore/aa1096-cis-settings-lint-whole-package`. Booking, Partner and TripPlanner already scan their whole
backend; this brings AA-CIS-App to the same shape.

### Decisions

- **Rule 4, a ratchet beside rule 1.** `tests/unit/test_s279_settings_lint.py` keeps rule 1 (the S279 governed
  modules, their 13/11 baseline, unchanged at 131 entries) and adds rule 4: the same AST scan over every Python module
  of `api/`, `services/`, `shared/` and `worker/` outside the governed list, minus any path with a `tests`, `scripts`
  or `migrations` directory part. Its findings must be marked or listed in
  `tests/unit/snapshots/aa1096_settings_lint_rest_baseline.json` (14/11/2026, 503 entries, keyed `<path>:<NAME>`,
  no line numbers, shrink-only).
- **Governed modules stay stricter.** A test fails if the rest baseline ever lists a governed module, so a new
  constant there can only be a setting or a marked engineering constant.
- **`worker/` is in scope** (two files, no finding today) because the dead-settings check already reads it; cheap,
  and a policy constant added there later is caught.
- **No vendored copies to exclude.** AA-CIS-App owns the copies the other repos vendor (`shared/aa_llm/`,
  `api/core/identity_verifier.py`, `shared/settings/reader.py`; `COPY_SOURCES`). They are scanned here (the consumers
  exclude their copies and rely on this lint) and their findings are baselined, not marked: a marker changes the byte
  copy in three repos, so it belongs to a copy-refresh PR.
- **Marked 66 obvious engineering constants in 41 modules** (`# technical-constant: <reason>`), only of these kinds:
  cache refresh and failed-read back-off TTLs (the gateway's DB snapshots, admin page caches, secret re-reads), lock leases,
  pagination loop guards, `SDK_MAX_RETRIES` / `SDK_MAX_ATTEMPTS` (the gateway owns retries), and two length bounds
  that are a standard or a column size (RFC 5321 e-mail, `admin_users.username varchar(100)`). An existing trailing
  comment became the reason. Login throttles, staff state TTLs, job attempts, LLM token caps, report flags and every
  `*_USD` stay in the baseline: some of them are business policy.

### Changed

- The `__main__` tool rewrites both baselines (each only to remove entries).
- `shared/settings/__init__.py` docstring names the wider guard.

### Tradeoffs

- 503 unclassified entries is a large baseline; classifying each one (setting vs marker) is per-area work, out of scope
  of a lint widening. The ratchet makes every new literal fail now without blocking main on the old ones.
- No CI change: the file already runs in the required "Unit Tests" job (the other repos also have a "Settings Lint"
  job; CIS keeps one job, as asked).

### Should know

- Every marker edit is a comment-only change; 4282 tests of the touched modules pass, flake8 120 clean, code_health ok.
- A marker on a constant of `shared/aa_llm/`, the identity verifier, the settings reader or the job table shape needs
  the consumers' copy
  refresh (`check_vendored_copies.py` / `*.lock.json` in Booking, Partner, TripPlanner) in the same wave.

## Fix round (S280): review findings on the lint widening

### Changed

- **`api/middleware/rate_limit.py:_TENANT_META_TTL_S` is back in the rest baseline, unmarked.** Its comment block says
  this Redis TTL is the tenant revoke window (`shared.tenants.is_active=false` blocks the tenant only after it
  expires) and that 30 s is not load-tested. That makes it an access policy value, the same class as the login
  throttles and staff state TTLs the first pass kept in the baseline. The file is byte-identical to `main` again; the
  rest baseline has 503 entries (sorted). The marker count is 66 in 41 modules.
- **The reason text matches the cache.** Six markers said "in-process cache refresh of a read" on a Redis TTL
  (`redis.set(..., ex=...)` or `cache.cached_section(redis, ...)`). They now say "cache refresh of a read (Redis TTL)":
  `api/routers/admin_overview.py:_CACHE_TTL_S`, `api/routers/admin_pipeline/metrics.py:_INFRA_STATUS_CACHE_TTL_S`,
  `api/services/platform_apps.py:CACHE_TTL_S`, `api/services/platform_audit.py:VERIFY_CACHE_TTL_S`,
  `api/services/app_health.py:HEALTH_TTL_S`. `shared/alert_recipients.py:RECONCILE_TTL_S` caches both in process and
  in Redis, so it says "(in-process + Redis TTL)". Every other "in-process" marker was checked: its module never
  touches Redis with that constant. Comment-only change.
- **`COPY_SOURCES` lists `shared/jobs/job_table_shape.py`.** AA-Booking and AA-Partner vendor it byte for byte
  (`check_vendored_copies.py` `COPIES`, compared with CIS `main`). It sits in governed `shared/jobs`, so rule 1 scans
  it; `test_the_rest_scope` now fails if it ever leaves the governed list.
- **"Never mark a copy source alone" is enforced, not only documented.** `COPY_SOURCE_MARKS` pins the marked lines of
  the copy sources on 14/11/2026 (one: `shared/settings/reader.py:REFRESH_TIMEOUT_S`, already on `main`).
  `test_no_copy_source_is_marked_on_its_own` fails on a new marker until it is listed there, and on a listed one that
  is gone. A planted-marker test proves it catches one. The consumers' locks cannot be read from CIS CI, so the test
  pins the CIS side; the person who extends the set refreshes the copies in the same change.
