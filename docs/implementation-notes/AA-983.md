# AA-983 — revalidation keeps `published_tours.quality_score_id`

## Root cause

`_revalidate_tour` (api/routers/admin_pipeline.py, run by the `revalidate` job) re-scored a version with
`DELETE FROM quality_scores WHERE generated_content_id = $1` and then a fresh `INSERT` (new row id). Since migration
268 the FK `published_tours_quality_score_id_fkey` is `ON DELETE SET NULL`, so the DELETE nulled the pointer of every
published tour of that version, and nothing re-pointed it at the new row. Before 268 the same code left a dangling id.
The three statements were also three autocommit statements: a failure between them left the version with no score row.

## Decisions

- **Order inside one transaction: INSERT new row → re-point `published_tours` → DELETE the old rows**
  (`id <> new_id`). Because nothing points at the old rows any more when they are deleted, the FK's
  `SET NULL` never fires and the pointer is never NULL, not even inside the transaction. It also takes the locks in
  the same order as the export upsert (published_tours row, then the score row it references), so a concurrent
  export and revalidation cannot deadlock on each other.
- **"Accepted score" = the version's latest score row** (`generated_content_id = published_tours.generated_content_id`,
  `ORDER BY evaluated_at DESC, id DESC LIMIT 1`). There is no "accepted" flag on `quality_scores`; this is the
  same definition migration 268 step 1 and the admin tour view (`v1_tours.py`) use.
- **The published `quality_score` number is left as published.** Only the pointer moves (same rule as 268).
  The number is the score of the text that was exported; the revalidated text only reaches the catalogue on the
  next export, which writes both together.
- **Export picks the same row deterministically.** `process_export` joined `quality_scores` without an ORDER BY,
  so a version with more than one score row got an arbitrary one. It now uses a LATERAL `ORDER BY evaluated_at
  DESC, id DESC LIMIT 1`, the same definition as above.
- **Backfill script** `scripts/aa983_backfill_quality_score_id.py`: DRY RUN by default (SELECT only), `--apply`
  updates inside one transaction, re-counts before COMMIT and refuses to commit when the number changed counts
  differ from the dry-run list (expected count passed as `--expect N`). Rows only, no schema change.

## Changed

- `api/routers/admin_pipeline.py::_revalidate_tour`: the write block is one `conn.transaction()`; INSERT ...
  RETURNING id; UPDATE `gold_aa_internal.published_tours` SET quality_score_id; DELETE old rows; UPDATE
  `generated_content.revalidate_passed`. Result dict carries `quality_score_id` and `published_repointed`.
- `services/export/handler.py::process_export`: LATERAL latest score row.
- New `scripts/aa983_backfill_quality_score_id.py` + unit tests for its SQL/flow.
- Tests: `tests/unit/test_aa983_revalidate_keeps_quality_score_id.py` (statement order + transaction, fake conn),
  `tests/integration/test_aa983_revalidate_quality_score_id.py` (real Postgres with the 268 FK).

## Tradeoffs

- Re-pointing inside `_revalidate_tour` (app code) vs a DB trigger on `quality_scores` INSERT: the trigger would
  catch any future writer, but it hides behaviour in the DB, needs a migration (DB Migrate + Infra copy), and the
  only DELETE + re-INSERT writer is this one function. App code + regression test chosen.
- Keeping DELETE (vs keeping history rows): the revalidation contract is "overwrite the version's scores" (AA-234,
  AA-723 job idempotency); history is out of scope.

## Review round 1 (S248) — Done-when evidence

The independent review noted that nothing in the branch produces the Done-when evidence yet (before/after count,
one live revalidated tour). The evidence can only come from Dev after the deploy, and the lane agent cannot run
ECS exec (subagent hook), so the branch now makes each piece of evidence one read-only command with a pasteable
JSON result, and the decisions the evidence needs are made here instead of left open.

### Decisions

- **Live check is a script mode, not a hand-written SELECT.** `--tour <tour_id>` (SELECT only) prints the
  published row's pointer, the version's latest score row, `pointer_is_latest`, and the version's last
  `revalidate` job from `shared.job` (status, `result.quality_score_id`, `result.published_repointed`).
  `ok = true` only when the pointer is non-NULL, equals the latest row, and agrees with the job result
  (`published_repointed >= 1`). This is exactly the Done-when line, in one JSON block for the Linear comment.
- **The dry run names the tour to revalidate.** `revalidate_candidate` = one live (not soft-deleted) published
  tour whose pointer is already the latest row, with the admin revalidate path. No guessing which tour to use.
- **`stale_pointer` is decided now, not left silent.** After this change no code path can make a stale pointer:
  the only `quality_scores` writers are the first validation of a NEW version (not published yet) and the
  revalidation (re-points), and the export now reads the latest row. So a stale pointer on Dev is history from the
  old export JOIN (arbitrary row when a version had more than one). It is the same defect class as the NULLs,
  under the same accepted-score rule (268 step 1, revalidation, export), so `--apply --include-stale` re-points
  those rows in the same transaction (expect = `to_fix + stale_pointer`), recording each row's previous pointer
  in the restore list. The published `quality_score` number stays as published (same rule as 268).
- **What is NOT auto-fixed and needs its own follow-up if non-zero:** `stale_no_target` (pointer set, the
  version has no score row) and any `stale` row with `pointer_same_version = false` (pointer names another
  version's row). Neither can come from the paths above; if the dry run shows one, it is a different bug and goes
  into a new issue with the rows from the dry run, not into this backfill.
- **Apply touches exactly the dry-run rows.** The UPDATE is restricted to the listed published ids and only
  while each row's pointer is still what the dry run saw (NULL, or the stale id); a row that changed between the
  dry run and the apply makes the count differ and the transaction rolls back.

### Changed

- `scripts/aa983_backfill_quality_score_id.py`: `stale` list (pointer vs target version / evaluated_at / score,
  `version_score_rows`), counts split into `stale_pointer` (has a target) and `stale_no_target`,
  `revalidate_candidate`, `--include-stale`, `--tour`, restore rows with the previous pointer
  (`published_ids` kept for compatibility).
- `tests/integration/test_aa983_revalidate_quality_score_id.py`: +6 tests (stale listed and untouched without
  the flag; `--include-stale` re-points and records the previous pointer; candidate; `--tour` ok after a real
  revalidation + job row; `--tour` flags a NULL pointer and a disagreeing job; `--tour` refuses `--apply`).
