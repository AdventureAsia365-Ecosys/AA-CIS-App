# AA-515 — Ranking/Atom Score stage (rank-sum + multi-market research loop)

Sub-issue of epic AA-507 (T5-T11 redesign per aa-social-media, Ms. Thư), discovered as a
blocking prerequisite during AA-510 STEP0. 4 rounds of STEP0 evidence, read first, not
re-derived here: `docs/claude_audit/AA-515-step0-ranking-investigation.md`,
`AA-515-step0b-demand-research-loop.md`, `AA-515-step0c-multimarket-schema.md`. Build prompt:
`docs/claude_tasks/AA-515-ranking-build.md`.

## Decisions

1. **`search_demand`/`segment_research_log` are NOT tenant-scoped**, unlike every other
   AA-508/509 table. Deliberate: a keyword's search volume in a market is a fact about the
   outside world, not one tenant's own content — two tenants researching "Kyoto" share one row
   and one real DataForSEO purchase, saving cost rather than risking any cross-tenant leak
   (nothing tenant-identifying is stored in either table). Matches Ms. Thư's own reference
   schema shape (PK on `(keyword, market)` alone).
2. **`atom_ranking` is rebuilt WHOLE per tenant (DELETE+INSERT) on every run**, not
   UPSERT-append like `atom_segment`. Matches the AA-510 STEP0 finding that Ms. Thư's own
   `routes`/`atom_scores` tables are "derived, never accumulated" — no downstream table has an
   FK into `atom_ranking` yet expecting stability across re-runs, so there's no alias mechanism
   to build (unlike `atom_segment_alias`, which exists for a real reason at that layer).
3. **`atom_ranking` grain is (tenant_id, tour_id, segment_id), not per-atom.** Ms. Thư's own
   `atom_scores` is written per-Atom "because that is the grain the slate reads." AA-CIS's own
   consumer (Route, AA-510) reads per-TOUR, in day order — so a Segment spanning 3 tours of one
   tenant gets 3 rows here, one per tour it actually touches, same rank values on each (ranking
   itself is Segment-level; only the row multiplicity is per-tour).
4. **`questions_rank` uses the same word-overlap claim-by-name test as `demand_rank`, never
   embedding-match** — Ms. Thư's own `_questions()` lands PAA via `atom_matches`
   (embedding-based, `match_queries_to_atoms()`), infrastructure this codebase doesn't have (no
   `Embedder`, no `atom_matches` table). Rather than build a parallel embedding subsystem for
   one axis, `compute_questions()` extends the exact mechanism the build prompt already
   mandated for demand to the PAA questions carried alongside each bought keyword.
5. **`said_rank` reads `SUM(LENGTH(tour_atoms.text))`** — the only per-atom text-length signal
   that exists. Real, disclosed limitation: AA-509's own Decision 1 changed `text` from an
   LLM-written narrative to a terse `f"{place} — {action}"` join, so this axis currently carries
   little real variance. Not fixed here — flagged for whoever next touches T5's `text`
   derivation, same "disclosed, not measured" pattern AA-509 itself used for the same column.
6. **`_about_something_else()`/`elsewhere`-refusal (score.py's off-topic-PAA suspect-claim
   check) is NOT ported** — a secondary refinement on top of `_demand()`, depends on a
   `trips`/country-word table shape this codebase doesn't share. Deferred, disclosed.
7. **Multi-market fan-out confirmed as N separate DataForSEO requests, never combinable** — the
   Live search_volume endpoint accepts exactly 1 task/call, 1 location/task (STEP0c, official
   DataForSEO docs). `serp` fans out per market too (PAA genuinely differs by market, cheap);
   `suggestions` uses only the tenant's single top-priority market (`resolve_buyer_market()`,
   singular) to bound its cost — a decision this build made, since the reference repo never had
   >1 market to choose between for that tool.
8. **Threading -> asyncio for coalescing.** Ms. Thư's `CoalescingSearchDemand` gathers OS-thread
   workers behind a `threading.Condition`. `_VolumeBatcher` (segment_research.py) is the
   asyncio-native equivalent (`asyncio.Lock` + a linger `asyncio.sleep`) — same "one request per
   market for however many loops are asking at once" shape, different primitives, since AA-CIS
   runs one event loop per ECS task, not an OS thread pool.
9. **Research + ranking are fired in the background** (`asyncio.create_task()`, strong-ref
   pattern — this file's own AA-425 precedent, same shape AA-466 used elsewhere), not awaited
   inline in `atomize_version()`'s response. Real DataForSEO + Bedrock calls per new place can
   run well past the ~29s API Gateway timeout this repo has already documented for T8/T9
   (CLAUDE.md's AA-452 entry) — the tenant's atomize response must not block on it.
10. **`resolve_buyer_markets()` (plural) is a NEW function**, `resolve_buyer_market()` (singular)
    is UNCHANGED. Grepped every real call site first (3: `handler.py:58`,
    `admin_pipeline.py:2296`, `admin_pipeline.py:2507`) — all 3 destructure exactly one 3-tuple;
    changing the return shape would break all 3 for no reason, since none of them need more
    than one market.
11. **`DFS_LOCATION_MAP`/`MARKET_RANK` extended with DE/FR/NL**, confirmed via a live query
    against `shared.tenant_seo_config` (STEP0c) before writing the codes — all 3 real tenants
    already declare 3 countries each; `exploreasia-co`'s DE/FR/NL specifically were previously
    unmapped and silently fell back to US.
12. **`_demand()`/`compute_demand()` loads the whole `search_demand` table ONCE per ranking run**,
    not re-queried per Segment the way Ms. Thư's own SQLite-backed `_demand()` does (a Postgres
    round-trip per Segment isn't free the way a local SQLite file's is) — same output, fewer
    round trips.
13. **The research loop does NOT skip transit/unnamed-place Segments** — matches score.py's own
    explicit docstring: "Nothing here ranks anything. A transit Segment is researched like any
    other and what comes back is stored; deciding what reaches the slate happens in `score`."
    Exclusion is applied only at ranking time (`classify_exclusion()`), never at research time.
14. **`rank_segments()` hoists `_demand_ranks(candidates, market)` out of the per-candidate
    loop** the reference `rank()` runs it inside — that call's result depends only on
    `candidates`/`market`, never on which candidate is currently scored, so the reference was
    recomputing it identically once per (candidate × market) pair. Same algorithm, same output,
    a straightforward hoist.

## Tradeoffs

- `said_rank`'s near-inert real variance post-AA-509 (Decision 5) — disclosed, not fixed here.
- `_about_something_else()` off-topic-PAA refinement not ported (Decision 6) — `_demand()`/
  `compute_questions()` read every measured row unfiltered by it.
- `CONCURRENCY = 4` (place-loop concurrency) is a conservative starting constant, not measured
  against AA-CIS's own DataForSEO account allowance the way Ms. Thư's `WORKERS = 16` was
  measured against hers (STEP0b) — revisit if a tenant's per-run place count grows large.
- `suggestions` tool bound to the tenant's single top-priority market only (Decision 7) — a
  real, disclosed narrowing versus a literal "fan out everything" reading of the build prompt,
  chosen for cost-boundedness on a fallback-only tool.
