## Build Step 1: choose_angle() unset-others prerequisite fix

**Scope of this PR:** ONLY the `choose_angle()` bug fix identified as AA-494's mandatory
prerequisite (Decision 3 of `docs/claude_tasks/AA-494-design-atom-angle-piece-reuse.md`).
No schema changes, no status-value redesign, no other part of AA-494's design. See that
design doc for the full plan this is step 1 of.

## Decisions

- Fixed via an explicit second `UPDATE ... SET chosen = false WHERE request_id = $1 AND
  idx != $2` in the same transaction as the existing `SET chosen = true`, rather than a
  single `SET chosen = (idx = $2) WHERE request_id = $1` statement. Kept as two
  statements so the existing "no angle option idx=N for this request" existence check
  (via the first statement's `UPDATE 0` result) stays intact unchanged — a single
  combined statement would always report a row count equal to however many options
  exist for the request, losing that specific error signal.
- Did not touch the `status == 'pending_choice'` guard at the top of `choose_angle()`.
  That guard is what makes this bug currently harmless (nothing can call `choose_angle()`
  a second time for the same request in the live code path today) — loosening it is
  explicitly Decision 3's job, a separate future PR, not this one.

## Changed

- `services/acp_angle_gate/service.py::choose_angle()` — added the unset-others UPDATE.
- `tests/unit/test_aa449_angle_gate_service.py`:
  - `TestChooseAngle::test_happy_path_sets_chosen_and_approved` — updated
    `conn.execute.side_effect` from 2 to 3 items (the new unset call is now a 3rd
    `execute()` call) and added an assertion that the unset call fired with the correct
    `(request_id, idx)` args.
  - New `TestChooseAngle::test_choosing_twice_unsets_previous_choice` — the build task's
    required "exercise `choose_angle()` twice" test. The existing status guard blocks a
    real second call today, so this test uses a new stateful fake connection
    (`_StatefulAngleOptionConn`) that tracks `angle_gate_option.chosen` state directly
    across two calls (resetting `request_status` back to `pending_choice` between them,
    simulating a future loosened guard) — verifies only the most-recently-chosen idx
    ends up `chosen=True` after the second call. This is a data-state assertion, not a
    call-count assertion, since that's what the bug actually was.

## Tradeoffs

- The new test double (`_StatefulAngleOptionConn`) is a different mocking style than
  this file's existing `AsyncMock` + `side_effect` convention. Necessary because the
  bug is about final DB state across 2 sequential calls, which a call-count/args-only
  mock can't express — accepted the inconsistency in mocking style for a meaningfully
  stronger test rather than force-fitting the existing pattern.
- No migration, no live schema touch — this is a pure logic fix, matches the build
  task's explicit requirement.

## Should know

- This PR does NOT unlock re-choosing a different angle after `approved` — that still
  requires Decision 3's status-value work (a new `reusable` status value + widening
  `acp_content_writing/service.py::start_write()`'s guard), not built here. This PR only
  removes the landmine that would otherwise corrupt T9's angle-read once that future
  work ships.

### Decisions

- **`angle_gate_request.status` new value name: `reusable`** — the design doc's own proposed
  name (Decision 3), adopted verbatim; no existing status-value convention in this table or
  `content_piece`'s own set conflicts with it.

- **`fetch_used_atom_ids()` placed in `services/acp_planning/tenant_pool.py`**, not

  owns tenant-scoped atom queries, per `fetch_tenant_atoms_by_trip()`'s existing home") and is
  called from the same router (`v1_planning.py`) as its sibling tenant-pool functions.
- **The availability rule collapses to exactly `status = 'approved'`**, not an ordinal "at or

  (migration 118) is `processing`/`approved`/`held`/`failed`, with nothing after `approved`. The
  design doc's wording ("at or beyond approved") was written before migration 118 shipped;
  `approved` is the only value that means "passed T10" today.
- **`GET /v1/planning/slot-suggestions` is a new endpoint, not a rewrite of `GET .../slot-grid`**
  — kept the existing endpoint's exact contract untouched (no caller of it needs to change) and
  added the enriched atom/free-atom data as a separate, additive read. Both endpoints share the
  same `compute_slot_grid()` call; not factored into a shared helper in this PR to keep the diff
  minimal against a function neither endpoint owns exclusively.
- **A slot's suggested atoms are never filtered out of the grid even if already used** — the UI
  needs the full slot (design doc: "flips to a success/green state, showing which atom was used")
  rather than a hole where a written slot used to be; `used_atoms` is returned separately so the
  frontend can layer that state on top.

### Should know

- **Genuine gap found, flagged rather than silently patched**: `content_piece` has
  `UNIQUE(angle_gate_request_id, attempt_number)` (migration 115) — modeling "one write session
  per request," where `attempt_number` 1-2 happens inside a SINGLE row's lifecycle (an UPDATE, not
  a second INSERT — confirmed by reading `_insert_placeholder_piece()`/`_finalize_piece()` in
  `services/acp_content_writing/service.py`). Once `reusable` status ever lets a tenant start a
  SECOND real write on the same request, `start_write()`'s current `_insert_placeholder_piece()`
  (hardcoded `attempt_number=1`) would collide with that UNIQUE constraint the moment a second
  write session is attempted. Decisions 1-3's text does not address this — it's a genuine,
  separate schema question (does `attempt_number` need a second "write session" dimension? does
  the UNIQUE constraint need to drop or change scope? does "the current piece for a request" stop
  being "highest attempt_number" once there can be multiple sessions?) with real architectural
  consequence, not something to guess at while touching a live production table. Needs its own
  decision before any future session wires up the actual second-write flow — do not build that
  wiring against the schema as it stands today without resolving this first.
- **Decision 3's status-transition code (guard widening in `start_write()`, the
  `approved`→`reusable` flip itself) was deliberately NOT built in this PR** — the build task's
  own Step 2 was scoped to "schema changes" only, and wiring live behavior changes into the
  already-shipped T8/T9 request flow ahead of the second-write-flow question above (previous
  bullet) risks shipping a status value nothing can safely act on yet. Adding `reusable` to the
  CHECK constraint is inert until code sets it — safe to ship now, real wiring is separate future
  work.
- **Decision 4 (prior-piece prompt) and Decision 5 (embedding similarity call) were not built** —

  Bedrock Titan Embed integration from scratch is a separate, substantial task, not a same-PR
  add-on to a schema migration — the column exists now (see Decisions above) so that future work
  doesn't need its own migration.

### Item 1 — debug-line leak, a real bug, confirmed and fixed

**Investigation (before touching anything):** grepped for `capacity_note` across the codebase.
Found two, same field name, different models, different design intent:
- `QuarterPlan.capacity_note` (`services/acp_planning/quarter.py`) — already rendered in the
  existing Trips section of `PlanningTab.tsx`. Its actual content is a genuine one-line,
  tenant-appropriate sentence: `"{N} eligible trips at {M} posts/wk — focusing on {K} trips
  (applied)."` No jargon, no concatenation.
- `SlotGrid.capacity_note` (`services/acp_planning/allocator.py::compute_slot_grid()`) — an
  internal reasoning trail built by `_add_note()`, joined with `" | "` across every trip the
  allocator had to drop or shrink that month. Real example content: `"Trip 'X' atom floor: 7
  live atoms < 2x4 planned slots for blog — capacity implicitly reduced, no silent atom repeat.
  | Trip 'Y' has no eligible atoms left for blog this month (atom floor reached or all on
  cooldown) — slot dropped, not repeated."` — pipe-joined, internal jargon ("atom floor",
  "cooldown"), the module's own docstring calls these "a note logged", i.e. written as an
  internal/debug/audit trail, not display copy.
- Confirmed via grep that **nothing in this codebase — admin or tenant — had ever rendered
  `SlotGrid.capacity_note` before this session's own `SlotPickerPanel.tsx` (Step 5, prior
  session).** There is no prior precedent treating this specific field as tenant- or even
  admin-facing; this session's own Step 5 build was the first and only renderer, and it
  incorrectly assumed the two same-named `capacity_note` fields shared the same design intent as
  `QuarterPlan`'s. That assumption was wrong — this is a real bug this session introduced, not a
  pre-existing one being newly discovered.
