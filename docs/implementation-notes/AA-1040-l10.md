# AA-1040 (lane l10): close the two machine-mark gaps of the AI Use Register

EU AI Act Art. 50(2), root ADR 0019 d19 (deadline 02/12/2026). The register's "Coverage limits" named two surfaces
with a visible notice but no machine-readable mark: the catalog tour JSON served to other apps, and the Booking
hotel / service descriptions drafted by `supply_content_writer`. This repo has two PRs of the lane.

## Decisions

- **catalog.http.v1 1.3 (code PR).** `Tour.ai` is `services.acp_content_writing.ai_marking.tour_mark(text_updated_at,
  published_at)`, the object the tenant tour reads already serve, so one definition covers every CIS tour read.
  `reader._TOUR_COLS` adds `published_at` and `text_updated_at` (CIS 359).
- **`generated_at` is the text time, not `v_tour.updated_at` (review fix).** `v_tour.updated_at` is
  GREATEST(published_at, master_updated_at, photos_updated_at) (273 / 289), so a photo change moved the mark's
  generation time and it differed from the tenant reads (`published_tours.updated_at`). CIS 359 appends
  `text_updated_at` = COALESCE(master_updated_at, published_at) to `v_tour` (append-only, catalog recipe). The
  reader probes `pg_attribute` for the column (`reader.has_text_updated_at`; a true answer is kept per process, a
  false one is asked again on the next read) and selects `NULL::timestamptz AS text_updated_at` before 359, where
  the mark falls back to `updated_at`. So the code PR and the migration PR ship in either order.
- **The mark is inside the hashed body.** The contract says `content_hash` is over the served body; leaving `ai` out
  would make the ETag lie about the body. Cost: every tour's hash changes once when this deploys, so the CRM's
  `crm_catalog_sync` re-reads each tour once (at most 100 details per hourly run).
- **`TourSummary` gets no mark.** The list is the CRM's re-sync index (key, title, hash); the content the CRM copies
  is the `Tour` body, which carries the mark.
- **Supply content (migration PR, CIS 358).** The storage already exists: `shared.supply_content_version.origin`
  (`llm` / `human`), `based_on_version_id` (a human edit names the version it edited) and `created_at`. No new
  column; `catalog.v_supply_content` appends `ai_generated`, `ai_generated_at`, `ai_human_edited` for Booking (the
  only reader). The model is not exposed: it is on the CIS ledger (`llm_job_id` -> `shared.llm_call_log.job_id`),
  which `catalog_owner` may not read (column grant only), and widening that grant is not worth it for a field the
  tour mark also leaves null.

## Tradeoffs

- A recursive walk of `based_on_version_id` (bounded depth) instead of "any earlier llm version of the entity": a
  human version written from scratch (no base) is not marked AI, and an edit of an edit of a draft still is.
- `ai_generated_at` of a human edit is the AI draft's `created_at` (when the AI text was generated), not the edit.
