## Decisions

- Gate A bypass closed at the **backend**, not just hidden in the UI (defense in depth — the
  route is reachable by anything holding `X-Admin-Secret`, not only this page):
  `PATCH /tenants/{id}` now rejects `is_active=true` with 400 unless
  `acp_shared.tenant_onboarding.approval_status = 'approved'` for that tenant. Deactivation
  (`is_active=false`) stays unrestricted — suspending an active tenant must always be possible.
  Reactivating a tenant that already cleared Gate A once (approved, then later deactivated) is
  allowed — that's not a bypass, Gate A's own checks were already satisfied for it. Only a
  never-onboarded or still-`pending` tenant is blocked, and must go through
  `POST .../gate-a/approve` instead.
- Frontend: added a new **"Onboarding" tab** (first tab, before Tours) in the existing tenant-row
  expand panel — not a new top-level page. Houses seed-atoms input, angle-assign buttons, and
  Gate A status/approve, laid out as 4 numbered steps (locked/greyed until the prior step
  completes) matching AA-309's exact order: seed-atoms → angle assign → *(Mirror, its own
  untouched tab — a note in step 3 points there)* → Gate A approve. A new/never-onboarded
  tenant's detail panel opens on this tab by default instead of Tours.
- `approved_by` is read from the `cis_user` cookie, same convention `AdminSidebar.tsx` and
  AA-388's Gate B page already use — no free-text input, no default value.
- Fixed a latent bug in the existing toggle handler while touching it: it previously updated
  local UI state (`setIsActive`) without checking `res.ok`, so a failed PATCH looked like it had
  succeeded. Now surfaces the backend's error message (relevant here since activation can now
  legitimately fail with the new Gate A guard).

## Tradeoffs

- Onboarding tab bundles all 4 actions into one tab rather than spreading them across separate
  tabs (e.g., a dedicated "Gate A" tab next to "Mirror"). Chosen because AA-309's flow is a strict
  linear sequence (seed → angle → Mirror → approve) and one tab with numbered, lock-gated steps
  enforces that order visually more directly than tab-bar ordering would (nothing stops an admin
  clicking tabs out of order). Mirror itself was left as its own untouched tab per the issue's
  explicit instruction, with a one-line pointer from the Onboarding tab instead of duplicating its
  logic.
- No hard technical block preventing Gate A approval before viewing Mirror (the backend doesn't
  require it, matching AA-309's original spec) — only a text hint. Approve is a business decision
  the admin makes; the UI doesn't second-guess whether they looked at runway data first.
- Backend guard checks `tenant_onboarding.approval_status = 'approved'` rather than also
  requiring `assigned_angle IS NOT NULL` again on the activation path — redundant, since a row
  can only reach `approval_status='approved'` by having passed `approve_gate_a()`'s own
  angle-required check in the first place.

## Reopened (2026-08-12) — pending tenants invisible in the real UI

### Context

Nghiep ran the N1 flow through the actual browser for the first time (not the verify-script/
direct-function-call path the session above used) and hit a hard blocker: New Tenant → Create, and
the tenant vanished from `/admin/tenants` even after Refresh. A second create attempt with the same
slug returned "Slug already exists" — proving the row existed in the DB but was invisible in the
UI. Confirmed live: `shared.tenants` row for `test-n1-flow` existed with `is_active=false` (correct
by Gate A design), but `GET /admin/tenants`'s own query filtered `WHERE t.is_active = true`
(`admin.py:229` at the time) — so a brand-new tenant had no path back into the UI to finish
onboarding at all. This directly blocked the "done when" bar this issue was opened for: run the
full N1 flow through the UI, not just backend function calls — so it's reopened, not a new issue.

### Decisions

- Extended the same `GET /admin/tenants` endpoint rather than adding a new route — the tenants page
  already re-fetches this one endpoint on refresh/create/approve, so a second round-trip wasn't
  warranted.
- Response gained `pending_tenants` (`is_active=false`) alongside the unchanged `tenants` (active)
  array, each carrying real onboarding progress — `seeded`/`seeded_tour_count` from
  `acp_shared.tenant_atom_state`, `angle_assigned` from the same table, `gate_a_status` from
  `acp_shared.tenant_onboarding.approval_status` (or `"not_started"` when no onboarding row exists
  yet, i.e. before seed-atoms). Not inferred from `is_active` alone — `is_active` stays `false` for
  the entire pending window regardless of which of the 3 steps a tenant is actually on.
- Frontend reuses `TenantDetail`/`OnboardingTabContent` as-is (already defaults to the Onboarding
  tab when `isActive=false`, from the slice above) — `PendingTenantCard` just wraps it in a
  per-tenant card with a local expand toggle; no new onboarding logic.
- "Continue onboarding" is the only action on a pending card — no activate/deactivate shortcut, so
  Gate A stays the single approval path (the `update_tenant()` guard from the slice above is
  untouched).
- `onGateAApproved` on a pending card triggers a full list refetch (`load()`) rather than local
  optimistic state — simplest correct way to move a tenant into the active table, since the active
  row shape (usage/lifecycle stats) isn't present on a pending row and would need re-fetching
  anyway.

### Changed

- `api/routers/admin.py`: `list_tenants()` — added a second query for `is_active=false` tenants
  (LEFT JOIN `tenant_atom_state` + `tenant_onboarding`), added `pending_tenants` + `pending_total`
  to the response. Active-tenant query/response unchanged.
- `frontend/app/admin/tenants/page.tsx`: new `PendingOnboardingSection` + `PendingTenantCard` +
  `pendingStep()` helper, rendered above the Summary cards on `/admin/tenants`; `TenantsPage` gained
  `pendingTenants` state from the same `load()` call. Section renders nothing at zero pending.
- `tests/unit/test_aa309_tenant_onboarding.py`: added `TestListTenantsPending` (3 tests —
  never-seeded, seeded+angle+gate-a-pending, empty-pending). 32/32 pass in that file (29 pre-existing
  + 3 new); full suite 1117/1117.

### Tradeoffs

- The "Step N of 3 · …" label is computed client-side from the 3 raw fields the backend returns,
  not a single precomputed string — keeps the response a plain state snapshot; a copy change later
  is frontend-only.
- No pagination on `pending_tenants`, matching the existing active `tenants` list (also returns
  everything in one call). Fine at current scale (6 pending / 9 active); would need revisiting if
  the onboarding backlog grows much larger.
