# AA-1122 — Search demand always ready (S282, lane l16-dfs-ready)

Tech lead decision (16/11/2026): items 1-5 in scope; per-agency Search Console, rank tracking, SEO reports and
native-language keywords are out of scope (agencies buy a bundle). Design: the S282 root audit `dfs-readiness/design.json`
slices S1-S6 (S7 market registry and S8 agency-market reads are not in this card) with the two critics' required
changes, and `dfs-commercial/findings.json` (T1.2 seasonality, C3, C5 variants, C6 refresh).

PRs (MIG-4 chain): migration-only PR CIS 450-452 (450 expand, 451 and 452 contract) -> Infra copy + Migration Apply ->
this code PR. Root PR: the DM-7.1 retention row of `acp_contract.search_volume_monthly`.

## Decisions

- **History (item 1)** keyed (keyword, market, month), written once (`ON CONFLICT DO NOTHING`): Google revises the last
  month a little; keeping the first answer means a reader never sees a month move. `source` keeps the endpoint label.
  Capture = the DataForSEO client / queue parse (`MonthlyBuffer` per location and keyword); write = the research cache
  `put_volumes(history=...)` after the volumes, plus the S1 ideas task and the S1 per-tour fetch
  (`write_client_history`). A history write never fails a paid purchase (logged `search_history_write_failed`).
- **Season = MAX over the place's keywords per month**, never the sum (close variants carry the same number). Peak =
  calendar month of the highest volume of the latest 12 months; YoY = latest 12 vs the 12 before, else latest month vs
  the same month a year earlier, else None (a first purchase has 12 months; YoY appears after the next refresh).
- **Variant groups (item 2)**: identical volume in every measured market (and > 0 somewhere) = one demand group
  (`research_select.demand_groups`). The SERP keyword comes from the strongest group; inside it: a fresh SERP in the
  store first (nothing to buy), then map order (plain name first, then the LLM's natural phrasing), then fewer words.
  The deduped estimate uses the same rule.
- **Refresh windows (item 3)**: both 180 days, maker-checker (CIS 452 edit); bounds unchanged.
- **Monthly cap (item 4)**: one `SharedCap` over DataForSEO + keyword LLM + Jev, attached to both run budgets
  (`shared/research_budget.with_caps` -> `CappedRunBudget`; `shared/cost_guard.py` unchanged). The month spend is read
  once per job attempt from the ledger **by job** (critic C1: research rows never carry stage `segment_research`), fail
  closed. Jev keyword questions reserve `cis.spend.research_jev_ask_estimate_usd` each before asking and charge the
  real cost after. An automatic run also has a run cap = setting minus what earlier attempts of the job spent (critic
  C3). 0 = no spend (critic C9). Refused up front by `/run`, the PAA `/tour-paa/run` and the tick (409 / skip).
- **Jev in the scope**: a real run reads the stored Jev picks only (like the preview): the whole-scope Jev asks were
  paid outside every cap and made preview and run differ (critic). The recompute keeps asking and storing picks.
- **Selection order**: `research_plan.py` (new, stale oldest, refresh-ahead on refresh runs through narrowed windows so a
  refresh buys before it stamps the log, requalify last and capped: critics' blockers). Manual runs use it too;
  uncapped manual runs select the same places as before except requalify beyond `cis.seo.research_requalify_max_places`.
- **Markets**: only kind `agency`, active, not cancelled, `account_status` in `cis.seo.research_market_tenant_statuses`
  (default `active`) plus the platform default (critic C5). A market with more than
  `cis.seo.research_auto_activation_stale_pct` stale is a new market: never bought automatically (no activation cap).
- **Tick**: hourly, right after the landing sweep (same cadence; keeps `Worker.run` under its complexity baseline).
  One `segment_research` job per kind per UTC day (idempotency key), `system:auto`, the endpoint from
  `cis.seo.research_auto_dfs_queue` (standard, critic C7); an auto payload with no / an unknown scope is refused
  (critic C8); pause after `cis.seo.research_auto_max_consecutive_failures` failed / stopped auto runs until a run
  succeeds (critic C9).
- **Rename carry**: only proven same-entity changes (a relabel the run may make, an alias merge) AND the same plain
  keyword (case / accents / punctuation). A real rename carries nothing (critic: a fresh log over keywords that no
  longer name the place would hide its demand for a whole window).
- **Tour PAA (item 5)**: store first ($0; the S1 rule `paa_from_rows`, US + US-PAA2 rows naming the tour's places), then
  one live SERP per distinct place keyword whose SERP is not fresh, through the research cache, under
  `cis.spend.tour_paa_backfill_max_usd_per_run` and the month cap. `none` is written only by paid runs (critic C4: an
  answered-but-empty SERP is never re-bought in a loop); `fetched_at` never touched; a list S1 / T2 wrote never
  overwritten. Freshness: rows the backfill filled are refreshed after the SERP window; a research run that bought
  SERPs enqueues the free store derive once per UTC day. `question_topup` is not used (its cap is lifetime and it must
  not run from a job: critic).

- S282 review fix 1, one paying research lane: the month cap reads the ledger once per attempt and then counts its
  own charges, which holds only while ONE paying research job runs. `concurrency=1` is per kind, so a segment research
  run and a paid tour PAA backfill could run together and both spend the same month remainder. Now both run endpoints
  refuse with 409 while any paying research job (every `segment_research`, a `tour_paa_backfill` whose payload asks
  `paid`) is queued or running, and both handlers call `research_budget.wait_for_lane` at attempt start, before the
  month read: another paying job running = `Reschedule` (the attempt is not counted). The runner marks a job running
  at claim, before the handler, so two attempts can both wait but never both pay. A store-only backfill ($0, enqueued
  by a research run) is outside the lane. Chosen over a pg advisory lock: a session lock would pin a pool connection
  for a whole run (up to an hour), and the job row is already the lock the runner keeps.
- S282 review fix 2, PAA row ownership: the S1 upsert (`seo_context_repository.insert`) moves `fetched_at` and keeps
  `paa_source` / `paa_filled_at`, so a stale provenance would have let the backfill overwrite a list S1 bought later
  (a paid run could write [] 'none' over it). The backfill now owns a row only when `paa_source` is set AND
  `fetched_at <= paa_filled_at` (`tour_paa.OWNED_SQL`, in both CANDIDATES_SQL and WRITE_SQL). Chosen over clearing
  `paa_source` in the S1 upsert: that would put the CIS 451 columns into the shared S1 write path, which this code PR's
  own CI (and any rollback of it) would run before or without 451; the SQL rule needs no change outside this module.

## Tradeoffs

- History is not back-filled for the volumes bought before this change; it fills as the rolling refresh re-buys.
- Requesting 24 or 48 months (`date_from`) at the same price would give YoY at once; not done (it changes every volume
  task's payload) — follow-up.
- The cap holds as long as `cis.spend.dfs_call_estimate_usd` is at or above the real price (the pre-call check reads the
  worst-case table; the charge is the real cost). A ledger write that fails (fire-and-forget) is not seen by the next
  attempt's month read; the in-attempt counter is exact.
- The 5 USD cap covers research only; the S1 fetch / prefetch buy DataForSEO outside it (shown per stage on the tab).
- Literals moved out of scope here (landing sweep window / gap / max, IMMEDIATE_RECOMPUTE_MAX_SEGMENTS, the research
  stale share, S1_SEO_REUSE_DAYS, the Redis SEO TTL, MIN_CACHED_IDEAS) stay as they were: follow-up settings.
