# AA-222 — `_execute_run_tour` INSERT crash: status="pending" invalid for `content_status_enum`

## Bug
`_execute_run_tour` (`api/routers/admin_pipeline.py`) writes a new `generated_content`
row with `status = "pending"` whenever the tour is **not publishable**. The column is typed
`content_status_enum`, which has **no `'pending'` member**. The INSERT cast
`$13::content_status_enum` therefore raises:

```
invalid input value for enum content_status_enum: "pending"
```

→ the whole `_execute_run_tour` call raises (re-raised at the `version_insert_failed` handler),
so any tour scoring < 7.0, flagged `manual_check`, or otherwise blocked by `_is_publishable`
**crashes at persist time** instead of being routed to HITL.

## Root cause
`'pending'` belongs to a **different** enum — `review_status_enum` (used by
`review_queue.review_status`). The not-publishable branch conflated the two enums.

- Crash site: `admin_pipeline.py:410`
  `status = "approved" if _is_publishable(result) else "pending"`
  This `status` flows into the `generated_content` INSERT (`$13::content_status_enum`).

## Fix
Single-line change at `admin_pipeline.py:410`: `"pending"` → `"hitl"`.

`content_status_enum` valid values (from migration `003_schema_v3.sql`, frozen — no later
`ALTER TYPE ... ADD VALUE`):

```
draft, passed, hitl, approved, rejected, published
```

`'hitl'` ("needs human review") is the semantically correct value for a validated-but-blocked
tour: it matches the existing routing of the not-publishable branch into
`review_queue` via `_enqueue_review`.

## Decisions
- Chose `'hitl'` over `'draft'`. The content has already been validated + judged; it is not an
  un-validated draft. `'hitl'` also aligns with the HITL review-queue routing.

## Changed
- Only the INSERT-bound `status` (line 410).

## Tradeoffs
- **Did NOT touch line 543** (`status = "approved" if _is_publishable(result) else "pending"`).
  That `status` is recomputed and used **only for a Python branch** (`== "approved"` → export;
  `== "pending"` → `_enqueue_review`); it is never written to an enum column, so it does not
  crash and changing it would be scope creep. Left as-is intentionally.
- No other INSERT/UPDATE writes a literal `"pending"` into a `content_status_enum` column
  (other `'pending'` occurrences are `review_status_enum` / `user_staging.decision` /
  `pipeline_runs.status` — different columns).

## Should know
- Discovered during **AA-193 Phase B** verification (S75) — the WildKind "sonnet" matrix cell
  fell into the not-publishable branch and the in-ECS driver surfaced the enum crash.
- This is a **container-side** fix (`_execute_run_tour` runs in ECS), so it requires a real
  deploy: `develop` → CI → Deploy Dev. A monkeypatch in a driver script cannot fix it.
- Cells that previously hit this bug crashed **at** the INSERT → **no `generated_content` row
  was persisted** for them, but the LLM rewrite had already run (cost was spent before the
  INSERT).

## Verification
- Re-run a not-publishable cell (score < 7.0 or `manual_check`) → INSERT succeeds with
  `status = 'hitl'`, row is routed to `review_queue` via `_enqueue_review`, no enum crash.
- Publishable path (`_is_publishable` true) unchanged → still `status = 'approved'` → export.
