## PR-A: disconnect without holding the tenant connection across Secrets Manager (item 6)

### Decisions
- **`_disconnect` is two short transactions around the tombstone** (plan PR-A):
  1. `acquire_scoped_conn` #1 reads `secret_key, updated_at`; released. No row -> 200 `disconnected=false`.
  2. Tombstone (`PutSecretValue {"disconnected": true}`, bounded client, `asyncio.to_thread`) with **no
     connection held**. Failure -> 502, nothing deleted.
  3. `acquire_scoped_conn` #2: `DELETE ... AND updated_at = $3 RETURNING secret_key`. A row -> 200 `true`.
     0 rows -> re-SELECT in the same transaction: gone -> 200 `false` + `aa859_integration_disconnect_raced`
     (double click); still visible -> 503 `aa817_integration_disconnect_row_mismatch` (RLS refused the
     DELETE, or a reconnect / test changed `updated_at`).
  4. Audit on MAIN after commit (unchanged, best-effort).
  5. Step 3 fails after a tombstone (acquire 503, connection drop, COMMIT error) ->
     `aa859_integration_disconnect_tombstoned_not_deleted`; the row keeps dead credentials and a retry heals it.
  The old event `aa817_integration_disconnect_commit_failed` is gone (its window no longer exists in that form).
- The re-SELECT reuses `_SELECT_INTEGRATION_SQL` (no third constant), so the forgotten-WHERE integration test
  patches every tenant filter the route runs.
- Flag off (admin pool): each of the two blocks opens its own `conn.transaction()`, as the single block did.
- **Tombstone check** lives in `v1_integrations` (`_TOMBSTONE`, `is_tombstoned_secret()`, `reconnect_detail()`);
  `v1_publish` imports the two helpers (it already imports `get_tenant` across routers). The match is exact
  (`creds == {"disconnected": true}`), so a real credential blob that happens to carry a `disconnected` key
  is not refused. 422 detail: "<WordPress|Facebook> was disconnected — reconnect it and try again".
  Publish checks it **before `claim()`**, so no publish_log row is written for a tombstoned connection.
- **`acquire_scoped_conn` UUID validation** only on the fail-closed path with the flag on (the only path that
  sets the GUC); flag off is unchanged (admin pool, a malformed id still fails in the route's own `$1::uuid`).
  The check parses with `UUID(str(x))` as the plan says; it does **not** require the canonical lower-case
  form (see Should know). The 503 event is the existing `aa817_tenant_context_unavailable`, with a new
  `tenant_id_valid` field.
- **Pool timing**: `aa859_tenant_pool_timing flag_key wait_ms hold_ms` (INFO, ms, 1 decimal) is logged in a
  `finally` after the connection is released, so a block that raises is timed too. Nothing is logged when the
  tenant pool was not used (flag off, Redis fallback, acquire failure). The acquire-failure event
  `aa817_tenant_pool_unavailable` gained `wait_ms` (time until the failure, e.g. ~5000 on an acquire timeout).

### Tradeoffs
- **Double-click interleaving uses a `threading.Barrier(2)`, not an `asyncio.Event`** (plan wording). The
  tombstone runs in a worker thread (`asyncio.to_thread`), so the hook that holds both requests between step 1
  and step 3 is a sync function; a barrier there is the direct way to say "both passed step 1". The test seeds
  committed rows on a separate connection (two real connections must see each other's commits) and deletes
  audit_log / tenant_integrations / tenants rows in `finally`.
- The row_mismatch 503 now leaves a row whose secret is already tombstoned (the old order guaranteed live
  credentials on 503). Accepted by the plan: the row reads as "connected" but every credential reader answers
  422 "reconnect", and a retried disconnect deletes it. Avoiding it would need a probe DELETE in a rolled-back
  savepoint before the tombstone (rejected in the plan as more clever than needed).
- `updated_at = $3` (not `IS NOT DISTINCT FROM`): the column is NOT NULL (db-schema-reference.md), and every
  writer in this router sets it (`updated_at = now()` on upsert / test UPDATE), so a concurrent reconnect or
  connection test between steps 1 and 3 turns into a 503 row_mismatch rather than deleting a fresh connection.

### Should know
- **Mutation check done**: with the old single-transaction `_disconnect` swapped back in, 4 of the 10
  integration tests in `test_aa817_tenant_pool_routes.py` fail (zero-row/tombstone, tombstone failure x2,
  double click), so they test the new design, not just pass along.
- **Local integration runs**: the shared local Postgres runner (`cistest`, port 5432) is not superuser and has
  no `aa_app_user` role, so every tenant-pool integration test there fails with `role "aa_app_user" does not
  exist` (8/9 already failed on `main` before this PR). I ran them on a throwaway superuser PG16 cluster in the
  session scratchpad (`CIS_TEST_DB_PORT=55433`), which matches CI's superuser `postgres:15` service:
  tenant-pool related integration files 76 passed, 1 skipped (`test_aa544_stage1_tenant_pool_leak.py:81`,
  real-RDS-only by design).
- UUID validation accepts non-canonical forms (upper case, braces, no hyphens) because Postgres `::uuid` does
  too and today's policies cast. Wave 4 adds text policies (`tenant_tour_pages`, `tour_atoms.owner_scope`)
  where a non-canonical id would silently match nothing (not a leak). If that matters, tighten to
  `str(UUID(x)) == x` in the PR that adds those policies.

  the live race only if `aa859_integration_disconnect_raced` appears in q3; otherwise cite the interleaved
