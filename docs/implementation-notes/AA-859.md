## PR-A: disconnect without holding the tenant connection across Secrets Manager (item 6)

### Decisions
- **`_disconnect` is two short transactions around the tombstone** (plan PR-A):
  1. `acquire_scoped_conn` #1 reads `secret_key, updated_at`; released. No row -> 200 `disconnected=false`.
  2. Tombstone (`PutSecretValue {"disconnected": true}`, bounded client, `asyncio.to_thread`) with **no
     connection held**. Failure -> 502, nothing deleted.
  3. `acquire_scoped_conn` #2: `DELETE ... AND updated_at = $3 RETURNING secret_key`. A row -> 200 `true`.
     0 rows -> re-SELECT in the same transaction: gone -> 200 `false` + `aa859_integration_disconnect_raced`
     (double click); still visible -> 503 `aa817_integration_disconnect_row_mismatch` (RLS refused the
     DELETE, or a reconnect / test changed `updated_at`).
  4. Audit on MAIN after commit (unchanged, best-effort).
  5. Step 3 fails after a tombstone (acquire 503, connection drop, COMMIT error) ->
     `aa859_integration_disconnect_tombstoned_not_deleted`; the row keeps dead credentials and a retry heals it.
  The old event `aa817_integration_disconnect_commit_failed` is gone (its window no longer exists in that form).
- The re-SELECT reuses `_SELECT_INTEGRATION_SQL` (no third constant), so the forgotten-WHERE integration test
  patches every tenant filter the route runs.
- Flag off (admin pool): each of the two blocks opens its own `conn.transaction()`, as the single block did.
- **Tombstone check** lives in `v1_integrations` (`_TOMBSTONE`, `is_tombstoned_secret()`, `reconnect_detail()`);
  `v1_publish` imports the two helpers (it already imports `get_tenant` across routers). The match is exact
  (`creds == {"disconnected": true}`), so a real credential blob that happens to carry a `disconnected` key
  is not refused. 422 detail: "<WordPress|Facebook> was disconnected — reconnect it and try again".
  Publish checks it **before `claim()`**, so no publish_log row is written for a tombstoned connection.
- **`acquire_scoped_conn` UUID validation** only on the fail-closed path with the flag on (the only path that
  sets the GUC); flag off is unchanged (admin pool, a malformed id still fails in the route's own `$1::uuid`).
  The check requires the canonical lower-case form, `str(UUID(x)) == x` (review fix, see Changed). The 503 event is the existing `aa817_tenant_context_unavailable`, with a new
  `tenant_id_valid` field.
- **Pool timing**: `aa859_tenant_pool_timing flag_key wait_ms hold_ms` (INFO, ms, 1 decimal) is logged in a
  `finally` after the connection is released, so a block that raises is timed too. Nothing is logged when the
  tenant pool was not used (flag off, Redis fallback, acquire failure). The acquire-failure event
  `aa817_tenant_pool_unavailable` gained `wait_ms` (time until the failure, e.g. ~5000 on an acquire timeout).

### Tradeoffs
- **Double-click interleaving uses a `threading.Barrier(2)`, not an `asyncio.Event`** (plan wording). The
  tombstone runs in a worker thread (`asyncio.to_thread`), so the hook that holds both requests between step 1
  and step 3 is a sync function; a barrier there is the direct way to say "both passed step 1". The test seeds
  committed rows on a separate connection (two real connections must see each other's commits) and deletes
  audit_log / tenant_integrations / tenants rows in `finally`.
- The row_mismatch 503 now leaves a row whose secret is already tombstoned (the old order guaranteed live
  credentials on 503). Accepted by the plan: the row reads as "connected" but every credential reader answers
  422 "reconnect", and a retried disconnect deletes it. Avoiding it would need a probe DELETE in a rolled-back
  savepoint before the tombstone (rejected in the plan as more clever than needed).
- `updated_at = $3` (not `IS NOT DISTINCT FROM`): the column is NOT NULL (db-schema-reference.md), and every
  writer in this router sets it (`updated_at = now()` on upsert / test UPDATE), so a concurrent reconnect or
  connection test between steps 1 and 3 turns into a 503 row_mismatch rather than deleting a fresh connection.

  and the whitespace form (22P02 -> 500), and the wave 4 text policies (`tenant_tour_pages`,
  `tour_atoms.owner_scope`) would silently match none of them. A real JWT `sub` is `str(uuid)`, so nothing
  valid is refused.

## PR-B: migration 241 (item 5 + W3 + W9 grants), migration-only

### Decisions
- **Migration-only PR.** No app code. 241 reaches Dev only through the Infra byte copy
  (`AA-CIS-Infra/db/migrations/cis/241_...sql`) and the DB Migrate workflow (`check` -> `apply`), with
  `shared.job` idle. Nothing in this PR is applied by hand to Dev; the local applies below are the
  integration-test DB only.
- **One revoke scope, computed once.** Guard 0 computes the set of relations to revoke and stores it in
  `aa241.scope` (oid[]); the loop revokes exactly that set. The plan's sketch had the loop re-run its
  own query; one query means guard 0's grantor check and the loop can never disagree.
- **Scope = plan D1 + the other apps' schemas.** Besides "runner can act for the owner" and "owner not
  catalog_owner / tripplanner / booking", the loop also skips schemas `tripplanner` and `booking`. The
  live dump shows their tables owned by `aa_cis_admin` (DB Migrate runs every owner's files as it), so
  the owner rule alone would let a CIS migration revoke grants in another app's schema (schema-ownership
  rule 1). An aa_app_user grant there makes guard 0 raise instead (a human looks). Dev has none.
- **Grantor check is `grantor = owner`, not `pg_has_role(runner, grantor)`.** A REVOKE by the owner, or
  by a member of the owner role, or by a superuser, runs as the owner and removes only the aclitems
  whose grantor is the owner. An aclitem granted by another role (through WITH GRANT OPTION) would
  survive even if the runner can act for that grantor. Guard 4 would catch it afterwards anyway.
- **The invariant query merges both levels with UNION ALL.** The plan's draft (`LEFT JOIN pg_attribute
  ... COALESCE(att.attacl, c.relacl)`) hides table-level grants of any relation that also has a column
  grant. The catalog exception uses `relowner IS NOT DISTINCT FROM to_regrole('catalog_owner')`: with a
  plain `=` a missing role would make the predicate NULL and `NOT (NULL)` would drop the row, i.e.
  hide a violation. Column grants are never part of the contract.
- **PUBLIC: system schemas excluded.** `pg_catalog.pg_settings` has PUBLIC UPDATE by design; the PUBLIC
  write check and the PUBLIC SELECT notice skip pg_catalog / information_schema. Any non-SELECT PUBLIC
  privilege (also REFERENCES / TRIGGER) raises, not only I/U/D/T.
- **Guard 3 seeds on an empty table** (CI) one request (tenant = first `shared.tenants` row, status
  `pending_choice`) and one option inside a PL/pgSQL sub-block, then raises SQLSTATE `AA241` to roll
  the seed back. The INSERT check runs under the own tenant's GUC for an own request, so the WITH CHECK
  would pass and only the missing grant can refuse it; the message must be "permission denied" (an
  RLS refusal or a unique violation means the grant exists).
- **Review round 1 (S240).**
  - *The apply records what it revoked in `shared.schema_versions.description`.* DB Migrate
    (`AA-CIS-Infra/db/run_migration.py`) runs the file with `conn.execute(sql)` and registers no asyncpg
    log listener; asyncpg's `_process_log_message` returns at once without listeners, so every NOTICE
    (revoked relations, PUBLIC SELECT list) was lost. Guard 0 now stashes `rel (PRIV, PRIV(col))` per
    relation of the scope in `aa241.revoked` and the PUBLIC SELECT list in `aa241.public_select`; the
    row's description appends both ("nothing" / "none" when empty). The NOTICEs stay for psql runs. An
    Infra-side `add_log_listener` would also help every later migration, but it is an Infra PR.
  - *Guard 0a also refuses aa_app_user as a member of any role* (`pg_auth_members.member = app`). The
    scope, the out-of-reach check and guard 4 all read aa_app_user's own aclitems; an inherited role's
    grants would pass every guard. Dev's 15/10 dump: member of no role. The suggested behavioural guard
    4 (`has_table_privilege` on every non-RLS relation) was not added: it would also fire on PUBLIC
    SELECT, which this file deliberately keeps (NOTICE + description only, pending the probe), and the
    membership guard plus the PUBLIC write guard already cover the other two paths.
  - *Guard 2 pins WITH CHECK to USING* (`with_check = qual`; one CREATE POLICY text, so the deparse is
    identical). Guard 3 cannot reach WITH CHECK (INSERT has no grant; its UPDATEs touch 0 rows), and the
    ILIKE pattern ends in `%`, so `WITH CHECK (... OR true)` passed every guard. Consequence: the old
    USING-only `OR true` mutation now trips guard 2 first, so `test_guard_3_catches_a_policy_that_leaks`
    mutates USING and WITH CHECK alike (still only guard 3 can catch that one); the WITH-CHECK-only
    mutation is a new test. Both new guards were mutation-checked (tests fail with the guard disabled).
  - *P0 preflight aligned with 241* (`AA-Ecosys/docs/audits/2026-10-16-S240-aa859/p0_preflight.py`, root
    repo, not this PR): class (c) for any item in schemas tripplanner / booking (241 skips them, guard 0
    raises); "foreign grantor" = grantor <> owner (241's rule, was `pg_has_role(runner, grantor)`);
    `D1_INVARIANT_SQL` = `NO_PRIVILEGE_WITHOUT_RLS_SQL` (was the plan's LEFT JOIN / COALESCE draft);
    new verdict `item1_member_of_no_role` in `gate_241_ready`.
- **Guard 4 checks the exact privilege sets** of aa_app_user on angle_gate_option ({SELECT,
  UPDATE(chosen)}) and tenant_integrations ({SELECT, DELETE, 5 x INSERT(col), 5 x UPDATE(col)}), as
  sets (array order would depend on collation).
- **The 239 test fixture stops at the pre-241 state.** Plan: "both 239 re-apply fixtures call the undo,
  re-apply 239, then re-apply 241". For `test_aa817_migration_239.py` that does not work: nearly every
  test there re-applies 239 again inside the test (idempotency, guard refusals, the RDS-like runner),
  and with 241 on top 239's guard 1 refuses `angle_gate_option` with RLS first (e.g.
  `test_guard_refuses_output_rules_readable_by_tenant_role` would raise the wrong message,
  `test_guard_refuses_rls_on_a_revoke_table` would pass for the wrong table). So that fixture runs the
  undo + 239 only; 241 on top of 239 is covered by the isolation fixture (undo, 239, 241) and the new
  test file. `test_guard_refuses_rls_on_a_revoke_table` stays valid (year_plan triggers it).
- **`CHILD_RLS_TABLES` maps a table to (primary key, key expression)**, not only the key expression
  (plan). The tenant role returns the visible primary keys; the superuser maps them to tenants. If the
  tenant role evaluated the key expression itself, its RLS on the parent would turn a leaked row's
  tenant into NULL and hide the leak.
- **`DELETE_ONLY_TABLES` became `COLUMN_WRITE_TABLES`** (still subtracted from `WRITE_TABLES`): the
  generic write test runs `UPDATE ... SET tenant_id = tenant_id`, which the column grants refuse with
  42501 by design.
