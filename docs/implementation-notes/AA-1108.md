# AA-1108 — Platform › Delivery: CI/CD and DORA per app (AA-CIS-App part)

Lane l7-delivery, S282. Design approved by the tech lead (S282: rework and hotfix within 48 h count, CFR and rework rate
kept apart; bot pull requests out of lead time but listed; hourly refresh plus an admin Refresh button; starting
thresholds at the DORA "high" band, editable). The collector, the definitions guide and the report registry change
live in the root repo (its `docs/implementation-notes/AA-1108.md`).

Two PRs here (MIG-4): the migration-only PR (CIS 433 + the compiled defaults + `services/reports/delivery_settings.py`
+ its integration test), then the code PR (this note, the API, the page, DEV-01 / DEV-03).

## Decisions

- **Read the published summary, never GitHub.** `api/services/delivery_metrics.py` reads
  `<docs-reader prefix>/delivery/summary.json` like `product_catalogue.py` reads `catalogue.json`: same read-only grant,
  same cache (`docs_reader.CACHE_TTL_S`, `?refresh=1` floored at `docs_reader.MIN_REFRESH_S`), same size cap, same
  12-digit mask. No table, no write path, no GitHub token in CIS.
- **Colours are computed here, not in the root.** The summary carries raw numbers with `n`; the API grades them with
  the settings of area `delivery` (CIS 433), so an administrator's change shows on the next request without waiting
  for the hourly collector. Rule: green / amber by a green and an amber value per metric (direction per metric in
  `delivery_settings.BANDS`), `few` when `n < cis.delivery.min_sample`, `none` without a value. The main branch: red
  after `cis.delivery.main_red_hours` of a red newest run, amber before.
- **Fourteen settings** (CIS 433): green / amber pairs for deployment frequency, lead time, change failure rate,
  recovery time, rework rate and the slowest CI p95, plus `main_red_hours` and `min_sample`. Defaults: DORA "high" band
  where DORA has one (deploys weekly, lead time and recovery under a day — the design's example of a 1-day lead-time
  p50 — and the design's CFR 15 %, main red 2 h); rework 10 / 20 % and CI p95 15 / 30 min are starting values.
- **DEV-01** reads the month row of every app (`trend.months`) and grades it with the same settings: pooled where a
  pool is meaningful (green deploys a week, CFR, rework rate, main failure rate), the slowest app for the medians (lead
  time, recovery) with the app named in the note. The old `CFR_FLAG = 0.15` literal is gone. Without the summary
  (storage down, a month older than the summary's 3 months) DEV-01 falls back to the CIS worker rows as before and the
  GitHub keys say why they are missing.
- **DEV-03** adds a "Delivery per app (GitHub, Dev numbers)" table from the ISO-week row (`trend.weeks`, matched by
  its Monday) next to the worker deploys and migrations. Its KPI lines (Linear, open PRs) are unchanged.
- **Page**: kit only (PageFrame, PageHeader, Tabs, Section, KpiTile, DataTable, Badge, InfoTip, EmptyState,
  ErrorState) plus recharts as on the overview page; the app tab in the URL (`?app=<id>`); EN / VI; "Dev numbers"
  badge; n next to every number; links only to `https://github.com/` (the summary is data, not markup).

## Changed (against the issue)

- Five DORA keys (rework rate added), not four; K-DORA-MTTR is now the failed deployment recovery time from deploys,
  not the OPS-04 postmortem time. The vendored report registry (`services/reports/registry/`) is the root copy of this
  wave (K-DORA-RW new, five KPIs at version 2).
- `K-CI-MAINFAIL` has no threshold setting yet: DEV-01 shows it as information. Follow-up: a `cis.delivery.*` key if
  the tech lead wants a colour there.

## Tradeoffs

- One settings read per request (14 `aget` calls, cached by the reader) against reading them into the cached bundle:
  a changed setting shows at once.
- Pooled DEV-01 lines hide a slow app behind fast ones; the per-app table under the KPI lines keeps them visible.
