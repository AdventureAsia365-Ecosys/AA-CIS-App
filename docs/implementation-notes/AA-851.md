# AA-851 — shared.countries (ISO 3166-1), country_iso2, catalog.v_country (CIS 279)

Linear AA-851 (split from AA-807, S239) + the S241 scope extension (D-24: `country_iso2` column, backfill, orphan
report). Data standards X5, DM-2.4, NAM-11. Session S250, lane C.

## Decisions

- **Seed source.** Debian `iso-codes` 4.16.0 (`/usr/share/iso-codes/json/iso_3166-1.json`): 249 entries, alpha-2,
  alpha-3, numeric, ISO short name, and `common_name` where ISO's short name is not the everyday one. `name` =
  `common_name` else the ISO short name, so every value of `chk_raw_tours_country` ("Vietnam", "South Korea",
  "Laos", "Taiwan") is a `name`; `iso_name` keeps the ISO spelling ("Viet Nam", "Korea, Republic of").
- **Aliases.** Lower-case: the ISO official name, a short list of common English names iso-codes lacks
  (`turkey`, `russia`, `ivory coast`, `uk`, …) and every spelling `services/places/guards.py` maps today
  (`_ALIASES` + `tibet` → CN). A guard in the migration refuses a lookup key that names two countries.
- **One resolver, in SQL.** `shared.country_iso2(text)`: case- and space-insensitive on name / iso_name / alias,
  else the code itself (iso2 / iso3). The integration test asserts it answers exactly like `guards.iso2()` for
  every spelling guards.py knows, so the Python and SQL lists cannot drift silently.
- **Which tables get `country_iso2`.** The two CIS systems of record that carry a free-text country:
  `silver_aa_internal.raw_tours` (tours) and `shared.destinations` (places). The other CIS country columns
  (`geo.*`, `shared.place_photo`, `acp_*`, run logs) are copies derived from these two; they keep their text and
  can join through the record they came from. Booking already keys countries by ISO (`country_code char(2)` →
  `booking.countries`), TripPlanner's `residence_country` is ISO-checked; neither is CIS's to migrate.
- **Kept in step by a trigger, not by code.** `BEFORE INSERT OR UPDATE OF country` fills a NULL `country_iso2` on
  insert and re-derives it when `country` changes and `country_iso2` was left as it was; an explicit value wins (a
  manual override); an unknown name leaves NULL and never fails the write. So no code PR is needed, every writer
  (pipeline, admin, scripts) is covered, and the column cannot go stale.
- **`v_destinations` = the existing `catalog.v_destination`.** The issue (written S239) predates CIS 225/228's
  `catalog.v_destination`, which is the destinations contract view Booking and TripPlanner already read. 279 appends
  `country_iso2` to it (256's statement restated, one column appended) instead of a second destinations view.
- **`v_countries` is named `catalog.v_country`.** Every catalog view is singular (`v_tour`, `v_destination`, …) and
  data standards DM-2 names it `catalog.v_country`. Done-when query: `SELECT * FROM catalog.v_country LIMIT 5`.
- **Grants.** `v_country` SELECT to `booking` and `tripplanner` (the Done-when roles); not to `aa_app_user` until
  `catalog.http.v1` serves countries (AA-859: nothing a reader does not use). `shared.countries` SELECT to `cis_app`
  and `catalog_owner`; resolver EXECUTE to `cis_app` only; the trigger function no EXECUTE (not needed to fire).

## Tradeoffs

- **Trigger vs. code writes.** A trigger is a hidden write path; code writes would need every insert site
  (`services/places/store.py`, ingest, admin) touched and a later site could forget. The trigger is small, only on
  `country`, and documented in both column comments and CONTEXT.md.
- **Privileges at fire time.** The resolver is SECURITY INVOKER (CIS rule: no SECURITY DEFINER), so a role that
  writes raw_tours / destinations needs SELECT on `shared.countries` and EXECUTE on the resolver. On Dev that is
  `cis_app` (granted) and `cis_owner` (owner); the master reaches it through its `cis_app` membership. A new writer
  role fails loudly (42501) rather than writing a wrong code.
- **Forward-only view change.** `v_destination.country_iso2` cannot be dropped by CREATE OR REPLACE; consumers that
  feature-detect columns ignore it.

## Should know

- Apply order: merge CIS PR → Infra copy PR → DB Migrate `check` → `apply` (job tables idle: the backfill takes
  ACCESS EXCLUSIVE on raw_tours / destinations for a second; do not run it during an S1 wave or a place job) →
  merge the schema-reference bot PR. The root registers PR (DM-7 row, schema-ownership, contract) merges before
  the Infra copy (DM-7.1 order).
- After apply, the live check: `SELECT count(*) FROM shared.countries` = 249;
  `SELECT * FROM shared.v_country_unmapped` (expected empty; a row = an alias to add in a new migration or a
  hand-set `country_iso2`); `SELECT * FROM catalog.v_country LIMIT 5` as `booking` and as `tripplanner`. The
  migration's NOTICE prints mapped / total per table and the unmapped values.
- A later change of the country list or aliases is a new migration (the seed is `ON CONFLICT DO NOTHING`).
- `shared.country_iso2()` maps a bare two/three-letter code too (`'IN'` → India): free text that is exactly a code
  is read as that code.
