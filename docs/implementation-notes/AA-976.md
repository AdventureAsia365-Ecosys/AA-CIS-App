# AA-976 — CRM-B4: CIS catalog over HTTP (`catalog.http.v1`)

Source: Linear AA-976; root design `docs/audits/2026-10-21-S246-crm-design-v3/design-v3.md` §5.9 and §6.3 (card
CRM-B4: "published views (tour, days, places, exclusions, facets, tz); scope `cis.catalog/read`; ETag. R: an
unpublished tour → 404. E: a removed tour → 410, and the CRM marks lines 'no longer offered'"); root ADR 0010
decision 4, ADR 0008a decision 1, ADR 0006b decision 7, ADR 0015 decisions 1 and 5; root contract
`docs/contracts/catalog.http.v1.openapi.yaml`.

## Decisions

- **Scope of this PR: tours and destinations.** `/aa-content` (prep packs, starter templates, campaign blocks) needs
  new CIS tables, an editor and a publish step: that is CRM-B5 / AA-977 (blocked by this card). The router, the M2M
  dependency and the Problem body are built so AA-977 only adds its routes.
- **Database role: `aa_app_user` on the existing tenant pool, no migration.** The catalog contract views are granted to
  `aa_app_user`, `booking` and `tripplanner` (CIS 225 / 228 / 274), and the CIS runtime `cis_app` has no `USAGE` on
  `catalog` (root ADR 0015 decision 3 records it). Options were (a) a migration granting `cis_app` USAGE + SELECT,
  (b) reading the views as `aa_app_user` through `app.state.tenant_pool`. (b) needs no grant change, no DB Migrate
  run and no change to the `rls_catalogue_rules` cross-schema allowlist, and `aa_app_user` is already a declared
  reader of every view. Each read runs in one READ ONLY transaction with `app.tenant_id` set to '' (the views run
  with `catalog_owner`'s rights and ignore the GUC; clearing it keeps a pooled connection from carrying a tenant).
- **Connection budget.** The tenant pool has 2 connections per api task (role `CONNECTION LIMIT 15`, shared with every
  tenant route). A per-process semaphore lets at most one catalog read hold a tenant connection at a time (5 s wait,
  then 503 + `Retry-After: 5`), so a CRM sync can never starve the portal.
- **M2M auth reuses the shared verifier** (`api/core/identity_verifier.py`, unchanged) with the AA-Booking AA-972
  profile: `groups_claim="scope"`, one pinned client (the CRM), `sub == client_id` enforced (no user tokens), scope
  `cis.catalog/read` checked per route. Outcomes: 401 + `WWW-Authenticate`, 403, 503. Config = code constants with an
  env override (`COGNITO_M2M_ISSUER`, `COGNITO_M2M_CRM_CLIENT_ID`), like `identity_config.py`, so the ECS task
  definition needs no new variable; the M2M issuer may not equal the WORKFORCE issuer (fail closed → 503).
- **Liveness answers (ADR 0015 decision 5, AA-Partner row).** `catalog.v_tour` row → 200. Otherwise
  `catalog.v_tour_retired`: `retired` → 410 `gone` with `reason`; `paused` → 404 `not_found` with `reason` (hidden,
  lines not marked: "temporary"); `restored` without a live row, or no row → 404 without reason (never served).
  A live row always wins over an old tombstone row.
- **`content_hash` = `sha256:<hex>` over the canonical JSON of the served body** (not `v_tour.content_hash`): the HTTP
  body also carries places, time zones, facets and photos that `v_tour`'s md5 does not cover, so the CRM re-syncs
  exactly when what it copies changes. The tour's ETag is that hash; list and destination ETags hash their body.
  The list therefore assembles the full tour per item (5 statements per page), so a summary's `content_hash` equals
  the tour's.
- **Detail views are filtered by `tour_id = ANY($1::uuid[])`, not by `source_id`** (review follow-up, lesson S238).
  EXPLAIN on the CIS 274 integration state showed a `source_id` filter (`=` or `ANY`) staying ABOVE
  `catalog._tour_day_text`'s `DISTINCT ON (tour_id, day)` and above `v_tour_place`'s window functions, so every call
  would parse the itinerary and resolve the places of every live tour (~0.9 s measured in S238). A `tour_id` filter
  is pushdown-safe (it is the DISTINCT ON / PARTITION BY column) and reaches the `raw_tours` (`place_photo` for
  photos) scan. The tour is read by `source_id` first (one row, primary lookup), then the details by that row's
  `tour_id`. The whole request runs in one REPEATABLE READ, READ ONLY transaction, so a Master swap committing
  between the statements cannot hand the detail views a `tour_id` the `v_tour` row no longer has.
  `test_detail_filter_is_pushed_down_to_the_tour_scan` (integration) guards the plan shape.
- **Caching:** strong ETag, `Cache-Control: private, max-age=60`, `Vary: Authorization`; If-None-Match (list, `W/`,
  `*`) → 304 without body. 60 s staleness is acceptable for a CRM sync; a retirement shows within a minute.
- **Paging:** keyset by `source_id` (stable key, ADR 0008 decision 9), `limit` 1–50 (default 20). Cursor
  `v1.<base64url source_id>.<8 hex fingerprint of the filters>`: opaque, ≤ 184 chars for a 128-char key, and a cursor
  reused with other filters is 400 `invalid` instead of a silently wrong page. `updated_since` filters
  `v_tour.updated_at` (moves on Master edits since CIS 273) only: place, time-zone, photo and component changes move
  `content_hash` without moving it. The contract's `updated_since` description says so and tells an incremental CRM
  sync to run a periodic full pass comparing `content_hash` (review follow-up).
- **Country code and time zones** are derived, never stored (`services/catalog_http/geo.py`): ISO codes from
  `services/places/guards.iso2` (the `chk_raw_tours_country` list) plus a few neighbour countries; one IANA zone per
  country, split by longitude for Indonesia, Malaysia (Borneo from 109° E) and Mongolia (Hovd west of 96.5° E).
  Indonesia (review follow-up): WIB / WITA at 114.42° E (Java's east tip Banyuwangi / Ketapang stays WIB, Bali's
  Gilimanuk is WITA); WITA / WIT at 125° E, except north of 1° N where it is 127° E, so North Sulawesi (Bitung, the
  Lembeh Strait, Sangihe, Talaud) stays WITA and Ternate / Halmahera are WIT. Without a latitude the line is 125° E.
  The test table pins the stops nearest each line. A place's zone uses the place's country, else the tour's; a day's zone is its last
  place's (overnight approximation), else the tour country's; last resort `UTC`.
- **Country spellings for the filter** come from the public `services/places/guards.country_spellings` (review
  follow-up; `geo.py` no longer imports the private `_ALIASES`).
- **Places:** only `v_tour_place` rows that resolved to a destination (contract `Place.destination_id` is required),
  in `position` order, each destination once per day.
- **Exclusions** are split into lines and classified by ordered regex rules (R25): `visa_on_arrival`, `tips`,
  `permit`, `camera_fee`, `entrance_local`, `single_supplement` suggest pay-on-arrival; `visa`, `international_flights`,
  `flights`, `travel_insurance`, `drinks`, `meals`, `personal_expenses` do not; anything else is `code: null`.
- **Facets:** activities = source `v_tour.activities` JSON (list / objects / string, normalised lower-case) ∪
  `v_tour_component.activity`; intensity = the highest component `intensity_level`, mapped leisurely→easy,
  moderate→moderate, active→challenging, strenuous→strenuous (the contract's names).
- **Day 0** (pre-tour text) is dropped (contract `day_no` minimum 1); a missing `duration_days` falls back to the
  highest day, else 1. Titles are clipped to 300 characters with an ellipsis.
- **Contract additions (root, v1.1, additive per contracts README rule 2):** Problem `unavailable` + optional
  `reason`; 400/401/403/503 on every operation; ETag + Cache-Control + 304 + If-None-Match on list and destination;
  `limit`; `TourDay.time_zone`; `Destination.country_code` nullable; the list of exclusion codes. Samples added.

## Tradeoffs

- Tenant pool vs a `cis_app` grant: the tenant pool is small; the semaphore keeps the CRM to one connection per task.
  If the CRM ever needs more throughput, a migration granting `cis_app` the catalog views (and an
  `rls_catalogue_rules` entry) moves the reads to the main pool without changing the router.
- Full assembly per list item costs 5 statements per page instead of 1, in exchange for one change key the CRM can
  trust. Page size is capped at 50.
- Longitude splits for time zones are approximate at province borders; no AA stop sits on one today, and an exact
  answer would need a polygon dataset.
- Rule-based exclusion codes can miss phrasings; the CRM only *suggests* a pay-on-arrival line, and an unknown line
  is `code: null`.

## Should know

- **Deploy order:** the Infra PR must be applied before a live check: without the API Gateway route `/catalog/*`
  answers the gateway's 403/404; without the `cis.catalog` resource server Cognito refuses a token request asking for
  `cis.catalog/read` (`invalid_scope`). The CIS deploy itself needs no env var. The CRM's stored credentials JSON
  (`aa-crm/<env>/m2m-booking-client`) lists its scopes; add `cis.catalog/read` there if the CRM requests scopes
  explicitly.
- No migration. Every statement was run against real Postgres as `aa_app_user`
  (`tests/integration/test_aa976_catalog_http_reader.py`, on the RDS-like state of the CIS 274 test).
- Lesson S238: the detail statements filter by `tour_id` (see Decisions); their plan shape is checked on real
  Postgres in the integration test. Timings on Dev data are still to record: run `EXPLAIN (ANALYZE, BUFFERS)` of the
  four detail statements with 20 `tour_id`s through DB Migrate `mode=run-script` as `aa_app_user`, before or right
  after merge, and add the numbers here.
- Time zones near a line: to confirm no live stop sits near an Indonesian line, list
  `SELECT DISTINCT destination_name, lat, lng FROM catalog.v_tour_place WHERE country = 'Indonesia' AND (lng
  BETWEEN 114.2 AND 114.7 OR lng BETWEEN 124.5 AND 127.5)` (read-only, same run-script) and compare with
  `services/catalog_http/geo.py`.
- The contract copy is pinned: `tests/unit/test_aa976_catalog_http_contract.py::ROOT_CONTRACT_SHA256` must equal the
  root file's sha256, and the root checker's rule M1 compares the app copy with the root file in the workspace.
- `docs/contracts/catalog.http.v1.openapi.yaml` must stay byte-identical to the root contract; change the root file
  first, copy it, then update `ROOT_CONTRACT_SHA256`.
- Card E's CRM half ("the CRM marks lines 'no longer offered'") is AA-Partner work: AA-Partner has no proposal-line code
  yet. CIS answers 410 `gone` with `reason`; the CRM side moves to the CRM proposals card AA-949 (CRM-21a proposal

- Live check: mint a CRM token (client credentials, scope `cis.catalog/read`), then
