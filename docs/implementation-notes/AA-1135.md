# AA-1135 — Platform › Delivery v2 (CIS part)

Lane l8-aa1135, S284. The collector part (engine split, presets, parity) is in the root repo
`docs/implementation-notes/AA-1135.md`.

## Decisions

- **Presets from the collector, custom from the day files, one engine.** `GET /admin/platform/delivery` takes
  `range=7d|28d|90d|custom` (+ `from`, `to`, whole UTC days, both included). A preset is the app's `ranges.d<N>` block in
  `summary.json`; custom is recomputed from `docs-reader/delivery/events/yyyy/mm/dd.ndjson` with
  `api/services/delivery_engine.py`, a byte copy of the root `tools/delivery/delivery_engine.py` (lock file
  `delivery_engine.lock.json`). The chosen block replaces the windowed keys of each app, so the page renders every
  range with the same code.
- **Never two different numbers for one window.** The published summary names its engine (`definitions.engine_sha256`);
  while it differs from this copy, custom ranges answer 409 "paused" and the presets keep working. The parity test
  (`tests/unit/test_aa1135_delivery_range.py`) recomputes the 7 / 28 / 90-day presets of the fixture the root collector
  publishes for its invented demo repo (`tests/unit/fixtures/delivery_range/`, written by the root
  `tools/delivery/sync_engine.py`) and requires identical JSON.
- **The data matches too (review fix).** The summary also publishes `definitions.store_fingerprint` (per repo: event
  count and sha256 of the store the presets came from); the engine copy refuses day files that do not rebuild it
  (`StoreMismatch`), the worker exits `OUT_OF_STEP` (3) and the API answers 409 `out_of_step` ("day files out of step";
  presets keep working, nothing is cached). The root workflow now saves its store only after the upload succeeded and
  writes every day file on a cold store or a repair run (`full_day_files`).
- **Presets never depend on the new setting key (review fix).** `view()` reads `custom_range_max_days` for the picker
  through `_custom_max_days`: on a preset, a key the registry does not know yet gives `max_days: null` and a warning
  instead of a 500 (code deployed before its settings rows); a custom range still needs it.
- **The window is said, not implied (review fix).** `lib/deliveryRange.ts windowNote()` + `WindowLabel` (RangeCharts):
  the app tab and the queue / git repo views show "Last N days" for a preset or the from – to dates for a custom range
  (never "Last 6.5 days"), and when the range starts before the app's complete history they add "the complete history
  covers N days of it, from <day>"; the Overview, queue and git cards show that note alone. The git activity is served
  unclipped, so its note clips at `git.range.complete_since`.
- **A child process per computation.** The stored history is about 50 MB of events (about 250 MB in memory while
  computing, measured on a read-only copy of the Dev day files). The API task has 1 GB, and CPython does not give freed
  arenas back reliably, so `api/services/delivery_range_worker.py` runs as `python -m` with the payload on stdin and the
  answer on stdout; one computation at a time (asyncio lock); 8 parallel S3 GETs; wall-clock guard 180 s (technical
  constant). Measured: about 1 s to compute all six apps, plus the reads.
- **Validation** (422): to before from, longer than `cis.delivery.custom_range_max_days`, before
  `definitions.store_from` (the first day the collector keeps), after the newest collection. 409: engine mismatch, a
  summary from before AA-1135, or a preset that is not published yet (28d then falls back to the headline keys).
- **Cache** per (summary `generated_at`, from, to), least recently used dropped beyond
  `cis.delivery.custom_range_cache_entries`; a newer summary empties it. A custom request re-reads the summary when the
  cached copy is older than 30 s (`docs_reader.MIN_REFRESH_S`), so the day files and the summary are from the same run.
- **The child's answer passes the account-ID mask** of the summary (pull request titles are free text).
- **UI.** One range picker above the tabs (kit `SegmentedControl` + `DateField`), in the URL; card sorting (worst
  first / name / a metric worst first, `?sort=`) on Overview and Merge queue; DORA trend (every app on one key on
  Overview, the four keys of one app on its tab; a week table in a `details` for screen readers); the delivery flow
  (an ordered list of the six points with median, p95 and n per step, slowest highlighted, a one-line summary);
  queue charts (wait histogram, ejection reason bars, weekly ejection rate, each with a text list); the churn treemap
  (squarified, kit `Pressable` boxes with an aria label, drill-down through `?dir=`). The commit graph with pull
  request links already existed (AA-1125) and stays.

## Changed

- `docs/api/openapi.json`: the three new query parameters.
- `.github/code-health.json`: the vendored engine is exempt from the complexity and file-size ratchets (measured in
  the root repo), like other vendored code.
- Git map: the 30 / 90-day period switch shows only for an older summary; with presets the page range sets the
  window (`git.range`), the 90-day calendar stays.
- App deploy table: shows the deploys of the chosen range (was always the 12-week list).

## Tradeoffs

- Byte copy instead of a package: the root repo and CIS deploy separately; a shared package would need a registry.
  The copy plus the runtime sha guard plus the parity fixture keeps the two from drifting silently, at the cost of one
  CIS sync PR after a collector engine change.
- Histogram bins live in the root `apps.json` (presentation edges of a chart, the collector has no settings registry);
  the custom range cap and cache size are CIS settings (CIS 450).
- Treemap boxes are sized in a 1000 × 420 virtual box stretched to the page width: on a phone the boxes get narrow, the
  table under it stays the full list.

## Should know

- MIG-4: CIS 450 (two settings) ships first as its own PR; this code PR reads the keys through
  `services/reports/delivery_settings.py` and needs main with 450 merged (compiled defaults) before its tests run.
- `next build` locally compiled and generated every page, then stopped at Next.js's own "known security vulnerability"
  check of the pinned version; no dependency changed in this PR, so CI / Vercel decide that as for main.
- To change a definition: edit the root engine, run `python3 tools/delivery/sync_engine.py --cis <checkout>` and ship
  both PRs; until the CIS PR deploys, custom ranges say "paused".

## S284 follow-up — fixes from the live check (lane l13)

Evidence of the live check: root `docs/audits/2026-11-18-S284-session/aa1135-delivery-v2/`.

### Decisions

- **Apply covered by the "To" box: a kit core bug, fixed in the canonical core.** `DateField` gave its text box no
  `min-width`, so as a flex item it kept its intrinsic width (350 px live) inside a 150 px wrapper and covered the
  button after it. The text box now has `min-width: 0` before the page's `style` (a page can still set its own). Kit
  Sync then copies it to Booking, Partner and TripPlanner. The range picker also passes the kit control look
  (`controlStyle("sm")`, width 100 %) to both boxes; they were unstyled.
- **Recent queue entries bounded in the engine, before the list cap (review fix).** The engine listed an entry when
  it was still queued or left after the window start, with no upper bound, and cut the list at `list_cap` (30) first.
  For a past custom range the entries that left after its end took every place, so a clip after the engine emptied
  the list. The root engine now applies `recent_in_window(e, a, b)` (left in [start, end), or still queued and
  entered before the end) before the cap; the CIS copy, lock and parity fixture come from
  `tools/delivery/sync_engine.py --cis` (the fixture only changes its `engine_sha256`: the presets end at the
  collection time, so their lists are the same). `delivery_range.clip_recent` keeps the same bound in `_range_view`
  as a guard; it removes nothing from a block of the current engine.
- **Range sentence instead of "the last 4 weeks".** `lib/deliveryRange.ts rangeWhen()` + `useRangeWhen()`
  (RangeCharts): "over the last N days" for a preset, "from <day> to <day>" (kit day format, EN / VI) for a custom
  range. Used by the Merge queue intro and Recent entries, and by the app tab's CI health and Failed deploys
  descriptions (both are range blocks too); the deploys-a-week tip now says "over the chosen time range".
- **Series colours.** `SERIES_VARS`: accent, info, purple, green, red, slate. kit-amber was the sixth series and sits
  next to the accent in both themes (CIEDE76 about 7 apart); the nearest pair now is about 20 apart in dark (info /
  slate), 26 in light. The lead-time segment bars had the same accent / kit-amber pair next to each other: slate there
  too.
- **Histogram axis room.** The horizontal small bar charts had a -16 px left margin with a 36 px axis, so three-digit
  ticks were cut (Recharts ends a tick at margin.left + width - 8 and draws nothing left of the chart). Review fix:
  one constant `lib/deliveryRange.ts Y_AXIS` (left margin 0, width 40: five characters) now drives every numeric Y
  axis of the page: the queue histogram, the DORA trend lines (were -12 / 40), the queue throughput and the git weekly
  bars (were -16 / 36, the same cut). Guards: `deliveryRange.test.mjs` (yTickSlack bites on the old -16 / 36; a source
  scan refuses a negative left margin or a numeric YAxis without `Y_AXIS.width` in the delivery folder) and smoke (d)
  (every Y tick text of the histogram and throughput charts starts inside its svg).

## S284 follow-up — the cold custom range (lane l18)

Live check: the first custom range after a summary rebuild (`range=custom&from=2026-11-09&to=2026-11-15`) took 28-31 s
on the API (request log `duration_ms`), so API Gateway answered 504 at 29 s; the next identical request was cached.

### Decisions

- **Where the time went (measured, not guessed).** The child started as `python -m api.services.delivery_range_worker`.
  `-m` imports the parent packages first, and `api/__init__.py` is `from .main import app`: every child built the whole
  FastAPI app (about 2,700 modules, 210 MB, Sentry set-up with a Secrets Manager read) before reading one day file. On a
  read-only copy of the Dev store (99 day files, 77,035 events, 55 MB) the old child took 5.9 s locally, 9.1 s at a 50 %
  CPU quota and 18.8 s at 25 %; the import alone was 2.6 / 5.0 / 11.3 s of it. The rest: decoding the day files 0.4 s,
  the store fingerprint 0.45 s, the six app contexts 0.6 s, the window 0.15-0.4 s (100 % CPU). The Dev task has 0.5 vCPU
  shared with the API process; the live 29 s matches about a quarter of this machine's core.
- **The child never imports the app.** `delivery_range._BOOT` (run with `python -c`) registers an empty `api` package
  (just its folder) before importing the worker, so `api/__init__.py` never runs; the worker needs only the engine
  (standard library) and, for S3, `docs_reader` + boto3. Start-up: 0.25 s / 57 MB instead of 3-4 s / 210 MB. It also
  removes a latent fault: the app's import logs to stdout, the channel of the child's JSON answer.
- **Two phases, one engine.** `delivery_range_worker.prepare` is the window-independent half of
  `engine.custom_range` (day files, prune, fingerprint check, every `app_context`); `ranges` is the other half
  (`range_block` per app). Both call the byte-copied engine for every number; the engine file is unchanged (lock and
  root parity untouched). The parity tests run both: the preset parity test goes through `run` (= prepare + ranges), and
  `test_two_phases_equal_the_engine_custom_range` compares with `engine.custom_range` itself for three windows from ONE
  prepared summary (so `range_block` does not change the contexts it is given).
- **Snapshot per summary.** With a `snapshot` path in the payload the child pickles the prepared contexts there; a later
  child of the same summary (generated_at + engine sha256 checked inside the file) only cuts its window: no day file
  read, no fingerprint. The folder is the API process's own `tempfile.mkdtemp` (0700), one file (the newest summary;
  older files are removed when a new path is made), about 55 MB on the task's ephemeral disk. Pickle is safe here
  because only this module writes those files, in a folder only the process user can open.
- **Prepared in the background on a preset.** `delivery_metrics.view` calls `delivery_range.warm(bundle)` after a
  preset answer: when the summary offers custom ranges and is not prepared, one background task runs a prepare-only
  child under the same lock (one child at a time). The page always loads a preset first unless opened on a custom URL,
  so a custom range picked afterwards waits at most for the end of that preparation.
- **A prepared summary is not re-read for a custom range.** The custom path re-read the summary when the cached copy
  was older than 30 s so the day files and the summary match. With a snapshot no day file is read, so a prepared summary
  is served from the cache like the presets (the range then always matches the presets on the page); an unprepared one
  still re-reads first.
- **Out of step is remembered.** A summary whose day files fail the fingerprint (child exit 3) is kept in
  `_snap["refused"]`: the next custom range of that summary answers 409 at once instead of re-reading 99 files.
- **Indexed store.** `IndexedStore.of` answers from an index built once (same events, same (time, id) order, a new
  list per call; an event without a repo name falls back to `Store.of`, which fails the same way). `app_context` asks
  `of` about 36 times; the contexts went from 0.62 s to 0.35 s. Test: every (kind, repo) pair of the fixture equals
  `Store.of`, before and after a prune.
- **GC off in the child.** A short-lived child building a large graph of small objects: the cyclic collector only
  rescanned it (about 10 %). Reference counting still frees what is dropped.

### Measured (scripts/aa1135_delivery_range_bench.py, read-only copy of the Dev store, range 9-15/11)

| CPU quota | before (old child) | new cold (prepare + range) | new warm (snapshot) |
|-----------|--------------------|----------------------------|---------------------|
| 100 %     | 5.9 s              | 2.2 s                      | 0.56 s              |
| 50 %      | 9.1 s              | 3.9 s                      | 1.0 s               |
| 25 %      | 18.8 s             | 8.9 s                      | 2.0 s               |

Dev was 28-31 s for the old child (about 25 % of this machine plus the S3 reads). Scaled by the same ratios, a cold
range opened directly on a custom URL should take about 11-14 s on Dev (0.4-0.5 of the old), and a custom range picked
after the page loaded (the usual way, prepared) about 3 s (0.1 of the old): under the 29 s gateway limit in both cases,
under 5 s in the usual one. The live check after deploy measures both.

### Changed

- `api/services/delivery_range_worker.py` (two phases, snapshot, indexed store, answer()),
  `api/services/delivery_range.py` (boot, snapshot path, warm, refused summary, `_child`),
  `api/services/delivery_metrics.py` (warm on a preset, no re-read of a prepared summary), `CONTEXT.md`,
  `scripts/aa1135_delivery_range_bench.py` (new).
- Tests: `tests/unit/test_aa1135_delivery_cold_range.py` (import budget of the child boot, parity of the two phases,
  indexed store, read budget: a cold range reads each day file once, a prepared one none; the real child answering from
  a snapshot through stdin / stdout; snapshot of another summary or engine refused; out of step remembered; warm on a
  preset and its no-ops). `test_aa1135_delivery_range.py` switches the background preparation off (`dr.WARM`).

### Tradeoffs

- A cold range opened directly on a custom URL still prepares inline (about 11-14 s on Dev): a 202 "building" answer with
  page polling would hide that too, but needs a UI state and a second request path; not needed under the 29 s limit.
  An hourly background preparation without a visitor was rejected (CPU and 55 MB of S3 reads every hour for a page used
  a few times a day).
- The snapshot write (about 0.5 s at full CPU) stays inside the cold request; writing it after the answer would need
  the parent to read the answer before the child exits.

### Should know

- The snapshot lives on the task's disk: a new task (deploy, restart) prepares again on its first preset load.
- `dr.WARM` is a test switch only (module constant True); the existing range tests turn it off, the cold-range tests
  exercise it.
