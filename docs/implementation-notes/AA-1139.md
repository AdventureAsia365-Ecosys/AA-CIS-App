# AA-1139 — TripPlanner module of the agency app (CIS side)

Lane l19 of S285. The agency app (AA-Partner CRM web + API) gets a Trip planner page. CIS owns the site settings
(`shared.tenant_tripplanner_site`: lead route, theme, locale) and the custom domains, so the CRM reads and edits them
through CIS over M2M; TripPlanner serves the leads, usage and the webhook key (its own PR).

## Decisions

- **Extend `tenant.addons.v1` to 1.1** (same client, same scope `cis.tenant/addons`) instead of a new contract and a
  new M2M scope: the module is part of the agency's add-ons and the CRM already holds this scope. Three operations:
  `GET /tenant/v1/tenants/{id}/tripplanner`, `PUT .../tripplanner/lead-route`, `PUT .../tripplanner/appearance`.
- **The CRM decides who** (reading: owner and agent; writing: owner) and names the member; CIS audits the write as
  `crm-member:<id>` (as the add-on request does).
- **Same checks as Tenant 360** (`validate_route`), plus one new rule for staff and agency alike: an e-mail address
  whose domain is plainly internal (`.local`, `.internal`, `localhost`, ...) is refused (`lead_email_not_public`). The
  CIS 390 CHECK accepted `desk@printer.local`.
- **Theme = brand tokens only** (`THEME_TOKENS` = `brandTheme.ts BRAND_TOKENS`), `#rrggbb`, stored lower case. The
  379 CHECK accepts any token-shaped name; the editor is stricter so a typo never silently does nothing.
- **CRM channel**: unchanged resolution (crm whenever `crm.core` is live). The module shows the stored route and the
  channel in force (`effective_channel`); the stored email / webhook route is the fallback when the CRM add-on ends.
- **Domains**: every state but `removing` (the agency sees pending / validating / failed hosts too); adding a host
  stays a staff action (DNS + certificate job).
- No migration: every column exists (379, 390, 428, 438 entitlements).

- **Studio routes for an agency without the CRM** (fix pass; review finding: the e-mail / webhook route and the
  signing key only matter for an agency without the CRM add-on, and such an agency has no CRM agency, CIS creates one
  only for a live `crm` subscription). `api/routers/v1_account_tripplanner.py` serves the same module to the Content
  studio with the studio's own tenant token: `GET /v1/account/tripplanner`, `PUT .../lead-route`, `PUT .../appearance`.
  Same service functions, same checks and audit rows; the actor is the studio membership (`membership:<id>`, as the
  add-on request). The tenant role middleware already limits `/v1/account` writes to the owner. Not a contract (CIS's
  own tenant API, in `docs/api/openapi.json`); not in the view-as read list (staff use Tenant 360).

## Changed

- `services/tenant_account/tripplanner_site.py`: `email_problem` domain rule, `validate_appearance`, `set_appearance`,
  `set_agency_lead_route`, `module_view`.
- `services/acp_shared/audit_log.py`: `TRIPPLANNER_APPEARANCE_CHANGED`.
- `api/routers/tenant_addons.py`: the three routes and their models; `docs/api/openapi.json` regenerated.
- `docs/contracts/tenant.addons.v1.openapi.yaml`: byte copy of the root 1.1.
- `api/routers/v1_account_tripplanner.py` (new, registered in `api/main.py`), `docs/api/openapi.json` regenerated
  (fastapi 0.161.1 / pydantic 2.14.1, the pins), `tests/unit/test_aa1139_studio_tripplanner.py`.

- Review pass (lane l27): `set_agency_lead_route` no longer checks the active Trip planner before
  `set_lead_route`'s transaction; `set_lead_route(..., require_active_planner=True)` runs `_require_active_planner`
  inside the transaction, right after `set_config('aa.actor')`, so the tenant row is locked (`TENANT_LOCK_SQL`) before
  the subscription is read and a cancel cannot land between the check and the write (as `set_appearance` does). The
  staff route (`admin_tenant_subscription.py`) keeps its own checks (no active planner needed there). Tests:
  `test_agency_route_edit_checks_the_planner_after_the_lock_in_one_transaction` and the refusal cases.

## Tradeoffs

- A write answers the whole module (one round trip for the CRM page to refresh).
- `module_view` reads the resolved entitlements itself (`shared.v_tenant_entitlement_resolved`), not the catalog
  view, which is granted to `tripplanner` only.

## Should know

- The CRM shows CIS's reason code per field (`lead_webhook_url_*`, `lead_email_*`, `theme_*`, `locale_invalid`).
- Independent of the TripPlanner and Partner PRs at deploy time: the CRM answers "not available" until this is live.
