# AA-1052 (lane l21-aa1052-fanout-uigate, S273) — Quality W6: source-change fan-out and the runtime edit gate

Follows lane l10 (`AA-1052-l10.md`, CIS #1390: lineage, the change-control lock, the route-migration lint). This lane
builds the two Done-when parts l10 left: (1) the $0 source-change fan-out "shown on one tour", (2) "UI edits on gated
stages require an eval run id or a break-glass reason and are frozen during waves". No model call anywhere.

## Decisions

- **A new table, not a jsonb key on the writer objects** (`shared.source_change_mark`, CIS 392, expand). The objects'
  jsonb (`generated_content.metadata`, `tenant_tour_versions.judge_breakdown`, `content_piece.writer_input`) is
  rewritten whole by some exits (the T9 finalize writes `writer_input = COALESCE($15, writer_input)`), so a mark there
  could be lost or race the writer; `review_queue` is the S1 human queue (no T2 / T9 id, its rows show up for
  reviewers); `writing_signal` has a fixed action CHECK. A separate table keeps the fan-out out of every tenant table,
  gives one open mark per (object, source) by a partial unique index, a hit count and a clear. No tenant column (an
  object's tenant is read from the object), ids and field names only.
- **Re-check, not only mark.** For an S1 / T2 object of a raw-tour change that names a FactSheet (`fs_id`, CIS 386)
  the job rebuilds the tour FactSheet from the raw tour now (`factsheet.build_tour_factsheet`, pure) and compares the
  rendered text with the stored `render_text`; equal = the writer read exactly these facts and the object stays
  unmarked (`unchanged` in the job result). The text is compared, not `fs_sha`: the sha includes the caller's `meta`
  (T2 puts its published_tours id there), the render does not. Every other dependent is marked (no stored sheet, or a
  source that is not a FactSheet line set: Master, atom, place card).
- **Hooks on the existing write paths, one job kind.** The codebase's change events are best-effort enqueues after
  the commit (the `recompute` job after an atom delete, `a3_atomize` after a publish), so the fan-out does the same:
  `source_fanout.enqueue_safe` (never raises) after the admin raw-tour edit (PATCH `/admin/tours/{id}/raw` and
  `/country`), `process_export` (every Master publish / promote), PATCH `/admin/atoms/{id}` (text or delete), and the
  admin place card status / facts / merge routes. One job per source and minute (idempotency key), max_attempts 3,
  one transaction per run (a retry starts over). Not deploy-gate-exempt and not background: it is cheap and only
  reported in the deploy gate's `active` count (non-blocking kinds no longer block, AA-993 G5).
- **Dependents.** `raw_tour` -> S1 (the live Master version and the newest version), T2 (each tenant's newest version
  of the tour, not rejected / failed), T9; `master` -> T2, T9 (S1 is the Master's own origin); `atom` -> T9 citing that
  atom; `place_card` -> T9 citing an atom linked to the card (`atom_place_card`; only T9 reads place cards). A T9 piece
  cites an atom by `angle_gate_request.atom_id` or `writer_input.route_moments[].atom_id`; only approved / held pieces.
  Only objects written BEFORE the change (`created_at <= changed_at`); the CHECK `object_created_at <= changed_at`
  pins it.
- **published_tours has one row per tour** (`ON CONFLICT (tour_id) DO UPDATE` in `PublishedCatalogRepository`): a
  re-publish keeps the id, so the master fan-out cannot tell old and new Master by id; it uses the time (T2 versions
  written before the publish). Found by the integration test (the first cut left "the new Master's row" out by id).
- **The edit gate reuses the AA-1026 D7 evidence** (`route_evidence.require`: a finished, valid, passing eval run, or a
  break-glass reason of 20+ characters; audit row `details.evidence`, admin bell on a break glass). `needs_evidence`
  now also takes the stage: a stage of `change_control.GATED_STAGE_PREFIXES` needs evidence whatever its role (before:
  writer / judge only). The wave freeze is the deploy gate's check (`shared.rerun_wave.status = 'open'`), read through
  `edit_gate.read_open_waves`; an unreadable wave table refuses (503), never waves through.
- **Surfaces and what counts as a gated edit** (module docstring of `edit_gate.py`): stage model (frozen for any write
  to a gated stage's row, evidence when the primary model changes), stage chain (frozen incl. a shadow-only change, a
  shadow adds paid calls mid-wave; evidence when the fallback chain changes, as D7), route control save / preset /
  revert (the preview's `evidence_stages` now include gated-prefix stages; frozen when that list is non-empty; the
  preview returns `frozen_by_waves` so the page says it before Save), catalog on / off (gated when the model serves a
  gated stage as primary or fallback; GET `/admin/llm-catalog` returns `gated_stages` per model), route policy (gated
  only when the hold switch `hold_fallback_writes` of a gated stage or of `*` moves: the only policy field that
  changes what a writer stores; threshold edits are alerts). DELETE of a policy row takes the evidence as query
  parameters (`eval_run_id`, `break_glass_reason`; a DELETE body is unreliable through the BFF / API Gateway).
- **Not gated**: the stage kill switch (the incident lever; it stops calls rather than changing what answers them), a
  provider connection on / off (the gateway's own failure handling covers an outage), `shared.stage_model_params`
  (no runtime write path exists; migrations only, covered by the l10 lint).
- **Frontend**: kit only, no new page. `lib/editGate.ts` mirrors the prefixes (its node test reads
  `change_control.py` and fails on drift); `needsEvidence(role, stage, gated)` prefers the API's `gated` flag on each
  stage row; the catalog switch of a model with `gated_stages` opens a ConfirmModal with `ChangeEvidenceFields`; the
  route policy drawer asks for evidence when the hold switch of a gated stage moves, and the reset of such a row opens
  a ConfirmModal; the route control dialog shows the open waves that would refuse the save.

## Tradeoffs

- A raw-tour edit marks objects without a stored FactSheet even when the edited field is not one the writer reads:
  without the sheet the job cannot prove the facts are the same. Objects written before W1 (no `fs_id`) therefore
  always mark on a raw edit.
- The Master fan-out marks by time, not by text diff: a re-publish of the same text still marks the T2 / T9 objects
  written before it. Diffing the Master text would need the previous published text, which the in-place upsert does
  not keep.
- Not hooked (yet): the place card rebuild job (`place_cards_build` rebuild mode re-drafts facts with a model) and the
  A3 atomize job's atom replacements (covered by the master event that precedes every atomize). A rebuild's fan-out
  can be queued by hand through the recheck route of a tour.
- The edit gate now asks evidence of validate stages with a gated prefix (e.g. a T9 check stage). That is stricter
  than AA-1026 D7 by design (ADR 0020 d12 names the stage prefixes, not roles).
- The minute idempotency key folds a burst of edits of one source into the first edit's job; the objects it marks are
  the same ones a later edit in that minute would mark.

## Should know

- **Migration and readiness.** CIS 392 is expand and ships in this code PR (ADR 0017 d1). Readiness is NOT raised to it
  (like CIS 386 / 388): every reader degrades without the table (the fan-out read answers 503, a `source_fanout` job
  fails and is retried with backoff, the hooks never fail their write), so a deploy that lands before the auto-apply
  loses nothing but a few retried jobs. 391 is held by a parallel S273 lane: the preflight refuses 392 until 391 is on
  main; if that lane does not land first, renumber to 391 (`git grep '392_'` and `git grep 392`).

- Live demo on one tour (Done-when "the fan-out is shown on one tour"): POST
  `/admin/quality/lineage/fanout/{tour_id}/recheck` with `{"source_kind": "raw_tour", "dry_run": false}` queues the
  job (reason `manual_recheck`), then GET `/admin/quality/lineage/fanout/{tour_id}` lists the marks. A dry run
  returns the would-be marks in the job result only.
- Clearing a mark is a plain UPDATE of `cleared_at` / `cleared_by` for now (no admin route yet); a later fan-out of the
  same source then opens a new mark.
- Retention row (DM-7.1) for `shared.source_change_mark` goes in the root data standards (Part B section 7) in a root
  PR merged before the Infra copy of CIS 392.
