# AA-756 (item 5) — write `shared.decision_log.outcome` from human actions

Scope item 5 of the Jev effectiveness audit: start recording the ground truth a human later
establishes, so Jev precision can be measured per question without a manual labelling sample.
`decision_log.outcome` was never written (0%) before this.

## What `outcome` holds

A JSON object stamped on every logged row of a `(question_key, subject_key)`:

```json
{"truth": true, "source": "review_approve", "ref": null, "at": "2026-10-10T...+00:00"}
```

`truth` is the answer to the question **as asked** — e.g. `a1_claim_supported` `truth=true` means
"the sentence IS supported". A later action overwrites an earlier one (the UPDATE touches all rows
of that subject, with no date guard).

### Schema note (TEXT, not jsonb)

`decision_log.outcome` is a **TEXT** column (migration 181), despite the task brief describing it as
jsonb. To avoid a schema change (brief standard rule: "no schema change unless the contract says
so"), the object is stored as a JSON string (`json.dumps`) and read back with `outcome::jsonb`
casts (`GET /admin/decisions/outcomes/summary`). If a native jsonb column is wanted, that is a
follow-up migration — see Open questions.

## Helper — `shared/llm_client/decide.py::record_outcome`

```python
async def record_outcome(conn_or_pool, question_key, subject_key, truth, source, ref=None) -> int
```

Best-effort by contract: never raises into the caller, never blocks the user action (log + return 0
on failure), no Jev call. Returns the number of `decision_log` rows updated. Accepts a Pool /
`_SingleConn` (anything with `.acquire()`) or a bare connection.

## Hooks (best-effort, after the action commits)

### 1. Review Queue approve → `a1_claim_supported` truth=True (`review_approve`)

`api/routers/admin_pipeline.py::admin_approve_review` calls `_record_grounding_approved_outcome`
after the approve commits. It rebuilds the exact `source` the S1 grounding run judged against (the
raw `tour` dict in the SOURCE_FIELDS shape `_execute_run_tour` uses) and the approved grounded
fields (`generated_content.aa_subtitle/aa_summary/aa_highlights/aa_itineraries`), then
`grounding.record_approved_outcome` splits them with the **same** `sentence_units` +
`subject_key(source, sentence)` the run used and stamps each unit truth=True. A sentence whose key
no longer matches a logged row simply updates 0 rows (harmless).

### 2. Atom soft-delete `PATCH /admin/atoms/{atom_id}` → `a3_atom_in_text` (`admin_atom_delete`)

`api/routers/admin_atoms.py::_record_atom_delete_outcome`: `deleted=true` → truth=False (the atom
is NOT in the day's text); `deleted=false` (undo) → truth=True. The `a3_atom_in_text` subject_key
has no stored builder — it was inline in `tenant_pipeline.ground_day_atoms`. That inline logic was
extracted into **one** reusable builder `tenant_pipeline.atom_subject_key(day_text, place, action)`
(`atom:<md5(day_text)[:10]>:<label[:200]>`), reused by both the write (ground_day_atoms) and this
read hook, so the key format cannot diverge. `day_text` is rebuilt from the published tour's
`aa_itineraries` via the same `parse_canonical_itinerary_days` parser and the atom's
`itinerary_day`; `place`/`action` come off the atom row.

### 3. Source tour restore → NOT IMPLEMENTED (blocked, see Open questions)

## Read API — `GET /admin/decisions/outcomes/summary`

`api/routers/admin_decisions.py` (same `verify_admin_secret` auth as the file's other routes). Per
question, over the window: `with_outcome`, and among the confident verdicts that have a truth:
`agree` (accept&truth or reject&!truth), `disagree` (accept&!truth or reject&truth), `grey`
(zone grey — Jev not confident), plus a `precision = agree / (agree+disagree)`. Orphan outcomes
(question no longer in `decision_question`) are listed separately.

## Out of scope (per the contract)

`a3_activity_type`, `a3_same_place` (no admin override UI exists), any backfill of old decisions,
any UI.

## Open questions / risks

- **Restore hook is blocked and not implemented.** The brief wants a source-tour restore
  (`PATCH /admin/tours/{id}/restore`) of a tour the A0 gates dropped to write the A0 verdict's
  truth. Two findings make it impossible as specified:
  1. A tour the A0 gate confidently drops is added to `in_file_drops` and **never inserted** into
     `silver_aa_internal.raw_tours` (`services/ingestion/handler.py`). The restore route only
     restores a `source_status='trashed'` raw_tour — a row that was ingested and later trashed.
     The two row-sets are disjoint: an A0-dropped tour has no `tour_id` to restore.
  2. Even for an ingested-then-trashed tour, the A0 verdict subject_key is
     `raw:{filename}:{row_index}:{src_name[:80]}` (`services/ingestion/jev_gates.py`), built from
     the upload filename and the batch-subset row index at ingest time. Neither is stored on
     `raw_tours` in a recoverable form, so the key cannot be rebuilt from a `tour_id` without
     guessing. Per the brief ("if it cannot be rebuilt exactly, stop and report") this hook was
     left out. Options for a follow-up: persist the A0 subject_key (or filename + row index) onto
     the inserted `raw_tours` row at ingest, then this hook becomes feasible for the trash→restore
     case only (A0-drop can never be "restored").
- **`outcome` is a TEXT column, not jsonb** (see Schema note). Writing/reading JSON over TEXT works
  without a schema change but is less ergonomic than a native jsonb column; a follow-up migration
  could `ALTER ... TYPE jsonb USING outcome::jsonb` if wanted.
- **Approve/atom key drift:** both hooks rebuild the subject_key from the *current* master content
  (`generated_content.aa_itineraries`). If that text changed since the Jev run (a re-atomize /
  re-grounding would have re-logged under new keys anyway), the stamp updates 0 rows. This is
  non-destructive but means a stamp is only written when the current content still matches the run
  that produced the verdict.

# AA-756 (grounding token trim) — cut `a1_claim_supported` input tokens

Follow-up from the S223 Jev outage: `a1_claim_supported` (S1 grounding) was ~80% of all Jev spend
because `grounding.py` asked Jev once per sentence with the WHOLE tour source (`source_text(tour)`,
avg 2,408 input tokens, up to ~7k). The fix sends a per-unit source instead, in
`services/content_generation/grounding.py`, with no threshold / question / prompt / migration
change. Measured on 50 real India tours (AA-747 wave-2, 2,444 units): source chars 20.3M → 7.8M
(**−62%**), with 5 of 50 tours falling back to the full source (no day markers), as designed.

## Per-unit source for itinerary sentences

`sentence_units(generated)` now carries a `day` number on each unit. For `itineraries` the splitter
tracks the current `Day N` title line and tags every sentence under it; subtitle / summary /
highlights units carry `day=None`.

`unit_source(tour, unit)` builds the source a single unit is judged against:

- **itineraries unit with a known day** → a compact header (`NAME` / `COUNTRY` / `DURATION`), that
  day's own source text, the previous and next day's source text (a writer often moves a detail one
  day), and `INCLUSIONS` / `EXCLUSIONS` (meals, transport, services live there).
- **subtitle / summary / highlights, or a unit with no day, or when the source days cannot be
  split** → the full `source_text(tour)`. Never guess a slice.

The source itinerary is split by the existing day parser `prompts.parse_source_day_word_counts`
(its `day_text` map + `used_fallback` flag) — **not** a second day splitter. When that parser falls
back (fewer than 2 `Day N` markers, or an even split), `unit_source` returns the full source for
every day, so a tour whose source has no clean markers is grounded exactly as before.

`subject_key(source, sentence)` is unchanged but is now called with the per-unit source, so verdicts
cache per unit. The deterministic numeric check (`source_number_parts` →
`find_novel_numeric_claims`) still runs on the FULL source — unchanged.

## No skip rule — every unit is asked

A first cut also tried a keyword "skip" rule (drop a sentence with no digit, no proper noun and no
promise-cue word). It was removed after measurement: on the 50-tour wave it skipped ~13% of units,
and among those exactly the tour promises the policy forbids (background about a named place is
allowed; a promise the source never states is not), e.g. "Afternoon wildlife cruise … offers
sightings of wild elephants", "Full-day excursion to two medieval centers.", "Riders are evaluated
… and receive structured feedback". A keyword list will always miss these. So **every** unit with
≥ `MIN_WORDS` words is asked, exactly as before this change — only the source each unit is asked
against got smaller.

## Outcome write-back stays consistent (PR #630)

`record_approved_outcome` builds its keys with the **same** `unit_source` + `subject_key` over
every unit, so a review-approve stamp still lands on exactly the `decision_log` row the S1 run
wrote. (Updated test: `tests/unit/test_aa756_decision_outcome.py`.)

## Offline estimate

`scripts/aa756_grounding_tokens.py` (pure Python, no DB / network) takes a JSON list of
`{tour, generated}` and prints the units asked and total source chars before/after the per-unit
change. Its `estimate()` core reuses the grounding module's own functions, so the estimate cannot
drift from pipeline behaviour. Unit-tested on two fixtures (clean day markers + no markers) in
`tests/unit/test_aa756_grounding_trim.py`.

## Out of scope

No Jev threshold, question wording, migration or prompt change. T3 (`tenant_pipeline.py`) grounding
is unchanged.

## Merge gate (S224) — live agreement on 200 units

The AA-691 labelled set could not be reused: 199/200 of its sentences no longer exist after
regeneration, so their day cannot be recovered. Instead, 200 current itinerary units from the
S223 wave-2 tours (only units whose per-unit source differs from the full source) were asked fresh
(`use_cache=False`, stage `adhoc_aa756`) against both sources.

- Source chars on these units: 1.83M → 0.51M (−72%). Errors 0.
- Same zone 167/200. Accept (≥ 0.85): full 90, per-unit 85, both 76.
- 9 grey→accept read by hand: 7 supported, 1 borderline, 1 not supported (puja ritual details the
  source does not give). It has no number, so no decision changes: for `a1_claim_supported`
  accept only clears `UNSUPPORTED_NUMBER`, and there is no reject ceiling.
- 14 accept→grey: more conservative (a numeric sentence may go to flag_fix more often).
- Verdict: precision at accept is in line with the ≥ 97% baseline; merged.

## Follow-up (S224): source SUMMARY in the per-unit source

Live pilot after #631: 2 of 25 low-p units were false lows because the detail was stated only in the
source summary (e.g. a temple "at 8,000 feet" — a number, so it also triggered one flag_fix). The
per-unit source now carries `SUMMARY:` after the header. Cost: source summaries average 851 chars
(p50 666, p90 1,616) against ~2,570 chars per sliced unit → about +33% on sliced units; the saving
vs the full source goes from ~−72% to ~−63%.
