# AA-257 — Live infra state endpoint (ECS/RDS/NAT/Redis)

## Decisions
- New endpoint lives in `api/routers/admin_pipeline.py`, right next to the existing
  `GET /admin/metrics/spot-workers` — same auth (`verify_admin_secret`, `X-Admin-Secret`
  header only), same graceful-degradation shape (`try/except` per AWS section, never a
  bare 500), same file the codebase already uses for this class of endpoint.
- Cache: `request.app.state.redis` (the existing `aioredis` client set up in `main.py`,
  same one `middleware/rate_limit.py` uses), one JSON blob under `admin:infra_status:v1`,
  60s TTL — matches the issue's own ask, avoids a new caching mechanism.
- `running_reminder` (the "AWS đang chạy — nhớ tắt cuối session" badge) defaults to
  **true** whenever any underlying describe call fails or a value is missing — a false
  "everything's stopped" reading costs real money if it stops someone from running
  `cis-stop`; a spurious badge costs one glance.
- IAM: split into its own AA-CIS-Infra PR (#39), not bundled into this one and not
  auto-merged — matches the repo's IAM-change convention. Every AWS section here degrades
  to `{"error": "..."}` independently, so this endpoint ships real and useful the moment
  that PR is reviewed/applied, instead of blocking on it.

## Changed
- New: `GET /admin/infra/status` in `api/routers/admin_pipeline.py` — ECS service state +
  running-task-digest-vs-`:latest` comparison, RDS instance status, NAT instance state,
  ElastiCache Redis status, all cached together.
- New: `tests/unit/test_aa257_infra_status.py` (4 tests — cache hit, cache miss/real field
  mapping, partial-AWS-failure graceful degradation, digest-mismatch flagging).

## Tradeoffs
- No frontend page. The issue's own scope is endpoint-only ("Endpoint duy nhất trả trạng
  thái sống..."); no Command Center UI exists yet to hang this off of, and building one
  wasn't asked for here.
- No WebSocket/polling — issue's own "Không scope" section rules it out. Refresh-on-load +
  a manual refresh (once a frontend consumer exists) is enough for one operator.
- The digest-mismatch check only compares the running task's container digest to the ECR
  `:latest` tag's digest — it doesn't cross-check against the ECS *service's* target task
  definition family/revision beyond what `describe_services` already reports in
  `taskDefinition`. Good enough for "did the last Deploy Prod actually land," which is the
  issue's stated use case.

## Should know
- **Real, pre-existing bug found and fixed by the same IAM PR**: `GET /admin/metrics/
  spot-workers` (already shipped, unrelated to this issue) has been returning
  `AccessDeniedException` on `ecs:ListTasks` in prod since it was built — confirmed via a
  real live call before writing any code here. It was never wired to a frontend, so this
  never surfaced as a visible bug; it'll start actually working once AA-CIS-Infra PR #39 is
  applied, no code change needed on this side.
- **Stale constant caught**: the issue text hardcodes NAT instance id `i-…` (old id)
  — that instance no longer exists. Real current one, confirmed via `aws ec2
  describe-instances --filters Name=tag:Name,Values=*nat*`: `i-…` (current id)
  (`aa-cis-dev-nat-instance`). Used as the default, override-able via `NAT_INSTANCE_ID` like
  every other resource id here (`ECS_CLUSTER`/`ECS_SERVICE`/`ECR_REPO`/`RDS_INSTANCE_ID`/
  `REDIS_CLUSTER_ID`).
- Until AA-CIS-Infra PR #39 is applied, every section of this endpoint's real response will
  read `{"error": "...AccessDeniedException..."}` in prod — expected, not a bug, matches
  `spot-workers`' existing (if previously invisible) behavior exactly.
