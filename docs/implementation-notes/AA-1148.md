## Decisions

- **A hand-made tour is a normal source tour.** It enters through the tour lifecycle service like an Excel row
  (`supersede(decision="create_new")`, the only writer of a raw_tours INSERT), so liveness, the catalog key, the
  retire / restore flows, Rewrite (S1), the re-validation, atomize and every reader work unchanged. It is marked
  `entry_origin = 'manual'` (CIS 478); a new batch id per tour (no raw_sources row: the Upload page does not list it).
- **Structured facts are kept, text is rendered.** `raw_tours.manual_facts` holds the form (day cards with title,
  places, meals, overnight, description; inclusions; exclusions; nights; group size; tour type; guide languages; best
  time). Every save renders the text columns from it in the Excel shapes (`src_itineraries` as canonical
  "Day N — Title" blocks with Places / Meals / Overnight lines, `duration` "3 days 2 nights", one item per line for
  inclusions / exclusions). No reader had to change.
- **The wording uses the AA-1146 draft.** Create writes the first `generated_content` row as a human draft (version
  1, origin human, `parent_version_num` NULL) from the facts (name, summary, one "Day N — Title" block per day). The
  editor's Customer wording tab embeds the existing `TourDraftEditor` (save with a reason, run the checks, publish
  through the one gate). The first draft passes through the REPORT-mode final contract like a draft save (exit
  `human_edit`, listed in `final_contract.EXITS`).
- **One more gate item, not a new gate.** `publish_tour_draft` calls `store.publish_check` after the two-person rule:
  a hand-made tour publishes only with its required list complete (409 `required_missing` with the missing items).
  A sheet tour is not checked. Before CIS 478 the check skips itself (the entry origin is read through `to_jsonb`, so
  the probe is NULL, not an error).
- **The required list holds on every exit (review fix pass).** The draft publish was not the only way a hand-made
  tour reaches `process_export`: the S1 auto publish, the Review Queue approve, the promote and the recompose do too.
  `process_export` now runs `store.export_guard` after the hand-edit lock guard, on the version it publishes
  (its own name / summary / day text, not the open draft): an incomplete hand-made tour's version goes back to `hitl`
  and `RequiredMissingError` is raised before any publish write (the AA-1146 / AA-1049 refusal pattern). Callers: the
  S1 auto publish logs a warning and files the version in the Review Queue (`_enqueue_review`); the approve answers
  409 `required_missing` and puts the claimed review back to `pending` (so it can be approved once the facts are
  complete); promote and the draft publish answer 409. Listed in the final-contract topology `NOT_EXITS` (no text,
  no publish).
- **Facts writers count for the two-person rule (review fix pass).** A hand-made tour's facts are staff-written
  content that the public API serves from the raw columns, so the people who saved them are writers of what goes
  live: `store.facts_editors` = the actors of the tour's `raw_tour_revision` `staff_edit` rows since its last publish
  (`published_tours.updated_at`, which every new version's publish sets) plus its creator (audit
  `raw_tour.manual_created`) while it was never published. The draft publish, the Review Queue approve
  (`review_publish_gate`) and the promote add them to the editors they pass to `enforce_publish_gate` (no read while
  the switch is off). While the switch is on, a facts save of a **published** hand-made tour is refused (409
  `facts_two_person`) and the page shows the facts read-only with a note: such a save would go live with no second
  person. Never-published tours keep the autosave (nobody outside sees them; their savers are counted at publish).
- **Automatic exits keep the two-person rule (review fix pass 2).** A content user could create a complete hand-made
  tour and run Rewrite (S1): with no Master there is no hand-edit lock, and the S1 auto publish put the facts that
  person typed live with no second person. `export_guard` now takes the exit: on an automatic exit (`auto_publish`,
  `recompose`, `lambda`, `human_lock.AUTOMATIC_EXITS`) while `cis.content.publish_two_person` is on, a complete
  hand-made tour whose facts a person wrote since its last publish (`facts_editors`), or that was never published, is
  refused with `FactsReviewRequiredError` (version approved -> hitl, before any publish write). Both refusals share the
  base `HandMadeRefusal`; the S1 auto publish catches the base and files the version in the Review Queue
  (`_enqueue_review`: pending for a never-published tour), where `review_publish_gate` counts the facts writers. A
  person's exit (draft publish, approve, promote) is not touched: it already runs the publish gate with the facts
  writers. The guard keeps one call line in `process_export` (the exit is passed as a sixth argument).
- **The drawer does not edit a hand-made tour's facts (review fix pass 2).** `PATCH /admin/tours/{id}/raw` answers 409
  `manual_tour_use_workspace` when the tour is hand-made (origin read through `to_jsonb`, NULL before 478) and the body
  holds any field but `price_raw`: those columns are rendered from `manual_facts`, so a drawer edit would bypass the
  workspace's two-person and required-list rules and be overwritten by the next workspace save. The price text is not
  in the workspace form, so it stays in the drawer (reference_price.write). `GET /admin/tours/{id}/detail` returns
  `raw.entry_origin`; the drawer's Original tab shows the fields read-only with a note and a link to the workspace (EN +
  VI). The reason check of the route moved to `_raw_edit_reason` (the route is at the complexity limit).
- **A live facts save keeps the required list (review fix pass 2).** With two-person off, `save_facts` on a published
  (live or paused) hand-made tour runs the same checklist as the publish on the new facts, country and supplier, with
  the open wording draft else the live version (`_refuse_incomplete_live`), and answers 409 `required_missing` with the
  items before the UPDATE. A never-published tour keeps saving incomplete drafts. The page shows a toast for it (EN +
  VI) instead of the "someone else saved" notice: the kit's `ApiError` now carries the router's `detail.code`
  (`app/_kit/api.ts`, not kit core), and only `facts_changed` is the stale-save notice.
- **Reasons and the concurrent save (review fix pass 2, minor findings).** A facts save's reason is stripped first
  (blank = no reason; otherwise 3..500 characters, 422 `reason_length`), so a short reason on a draft no longer reaches
  the history CHECK as a 500. The link bodies strip their strings before the 3-character minimum. Once the stored facts
  carry a `saved_at`, a save without `expected_saved_at` is 422 `expected_saved_at_required` (the page always sends
  the one it loaded). When the draft publish loses the race (the list became incomplete between its check and
  `process_export`), the version goes back to `draft` (unless another draft opened), so the person keeps editing it.
- **Option lists are admin data (review fix pass).** The tour types and the one-click included / not included items
  were code lists; they are now settings an administrator edits (CIS 478 seeds them, Platform › Settings, audited,
  single approval): `cis.content.manual_tour.tour_types` (json `[{code, label, label_vi}]`, private / join-in),
  `cis.content.manual_tour.quick_inclusions` and `…quick_exclusions` (list). Settings rather than a new option table
  (the Booking bk-067 pattern): same audit and approval, no new table and retention row, and the lists are short.
  `policy.form_options` reads them and skips a malformed entry (a typo hides one option, never breaks the form). A save
  accepts a listed code or the code the tour already holds; the label is stored with the facts
  (`manual_facts.tour_type_label`) and rendered "Tour type: <label>", so removing or renaming a type never breaks a
  tour (a rename reaches the text on the tour's next save).
- **Facts saves.** Before the first publish the page autosaves (1.5 s after the last change): nobody outside sees a
  draft tour. Once published, a facts save is a change of a live tour: it needs a reason and runs the source fan-out,
  exactly like the drawer's raw edit (`PATCH /admin/tours/{id}/raw`), which is how every tour's facts change today.
  Two people: the save carries the `saved_at` it loaded (stored in `manual_facts`); a different one is 409
  `facts_changed`.
- **The supplier is Booking's.** Booking opens `booking.v_supply_suppliers` (identity only) to cis_app (bk-073,
  the bk-040 pattern); CIS stores the id as a soft key and keeps `provider` as the sheet text (a hand-made tour's
  provider is the supplier's name, so legacy readers keep showing a name). Every read fails soft.
- **The suggestion is strict on purpose.** A sheet text suggests a supplier only when its normalised name (accents,
  case, punctuation, company-form words removed) equals exactly one active / pending supplier in a compatible country.
  Anything else stays for a person (bulk link from the report).
- **Permissions.** Create, save and link: content.write (content, content_lead, admin). Link every suggestion:
  content.publish (content_lead, admin), with a DRY RUN first. Reads: content.read.
- **Limits are settings** (CIS 478, Platform › Settings, single approval, low impact): most day cards (21), fewest
  inclusions (3) and exclusions (1) for the required list, most tours per link action (100). The UI reads them from
  `GET /admin/content-workspace/options`, with the three option lists; it has no threshold of its own (the 1.5 s
  autosave pacing is UI timing).

## Tradeoffs

- Columns on `raw_tours` instead of a new table: a hand-made tour is one row like any other, no join for readers; the
  JSON form is only read by the workspace.
- Direct facts writes on a live hand-made tour (with a reason) rather than a fact draft: it matches how every other
  tour's facts change today (the drawer), and `raw_tour_fact_draft` is shaped for the Excel merge (its publish writes
  only the merge fields and records `excel_merge`). With two-person publishing on, those direct writes are refused
  (above) instead of built as a facts draft in this slice. **Remaining gap / follow-up**: a facts draft for live
  hand-made tours that a second person publishes; until then, with the switch on, the facts of a published (or
  paused) hand-made tour cannot be changed in the workspace; its wording still changes through a draft.
- Adding a day to a live hand-made tour: the required list counts the wording's "Day N —" blocks, so the live save is
  refused until the wording has the new day. Order: open a wording draft with the extra day first (the draft is not
  checked against the facts), then save the facts, then publish the draft. Accepted for this slice; the facts draft
  follow-up removes the ordering.
- "Since the last publish" uses `published_tours.updated_at`; anything else that bumps it (a pause) narrows the window.
  It can only matter while the switch is off (live facts saves are refused while it is on), so it was not worth a
  new column.
- The S1 refusal files a review row rather than only logging (as the lock refusal does): a never-published hand-made
  tour has no Master, so a person should see the S1 text; the approve stays refused until the facts are complete.
- In-CIS preview instead of the TripPlanner page: usable today without a cross-app change; it is a close, not exact,
  rendering.
- The unlinked report computes suggestions in Python over every unlinked live tour (~1k rows, hundreds of suppliers):
  cheap now; a SQL-side match is a later step if the catalogue grows a lot.

## Follow-ups (review fix pass 2)

- The Excel fact-draft publish (`raw_tour_fact_draft`) does not check `entry_origin`: if a sheet row ever matched a
  hand-made tour, its merge would write the text columns and leave `manual_facts` stale. No sheet row can match today
  (a hand-made tour has its own batch and catalog key); refuse it there too when the matcher can reach such tours.
- A recompose (`recompose`) refused by the two-person rule leaves the version in `hitl` with no review row (the
  recompose's generic per-Master refusal path); only S1 files a review. A recompose only re-assembles a served
  Master's text, so this is rare; file it if it shows up in the recompose report.
- The draft publish writes its `tour_version.published` audit row before `process_export`; a refusal after it (the race
  above, the policy review, a dead source) leaves that audit row without a publish. Pre-existing for every refusal of
  the draft publish.
