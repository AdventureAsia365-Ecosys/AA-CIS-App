# AA-1025 slices D3 and H1a (S264 lane l15-ledger-d3-app-profile) — the ledger contract read federated, and the app profile

Plan: root `docs/audits/2026-11-01-S263-gateway-gap-audit/plan.md` rows D3 (OPS-01, tech lead T-14 option b) and H1
(RW-12 app part, X-2, OPS-11 app part; this lane is H1a, the CIS part). Root ADR 0009 decisions 4 and 8, data
standards DM-10.4. $0: no provider call.

## Decisions

- **D3, option b (federated read)**: the ledger contract is not one physical table. LLM and Jev calls stay in
  `shared.llm_call_log`; DataForSEO and Geoapify keep their domain ledgers (`shared.dfs_call_log`, `geo.geocode_call`),
  each carrying the contract's facts; the admin reads them together (Calls tab, trace, Providers). The root ADR 0009 §8
  and DM-10.4 text is amended to say so (root PR of this lane).
- **`geo.geocode_call` gets `status`, `latency_ms`, `app`, `stage`** (migration 346). All nullable, no default: rows
  before 346 keep NULL and the readers keep their derivation (status: every request failed = error; app: cis). CHECKs
  match `llm_call_log`'s shapes. `status` allows `refused` for the contract, although today no geocoder refusal writes
  a row (a run refused before any request has `requests = 0` and the writer writes nothing, as before).
- **`latency_ms` = the sum of the batch's HTTP request times** (one row per run and endpoint, so a per-request latency
  does not fit); the Providers p50 / p95 for Geoapify are percentiles of `latency_ms / requests` per batch (the mean
  request time of each batch). Measured in `GeoapifyGeocoder.search` and `GeoapifyDetails`; Overpass (free) is not
  timed.
- **`stage` = the job kind** (`place_geocode`, `place_relocate`, `place_shape`) or `adhoc_conn_test` for the probe:
  there is no stage registry row for the geocoder, and the job kind is what an admin filters by.
- **Readers use `to_jsonb(geocode_call) ->> '…'`** for the four columns, so the Calls tab, the trace and the Providers
  stats run before 346 is applied (readiness is not raised: MIG-4 for a contract file; the code PR follows the apply,
  but a deploy before it does not break). The writer has a v3 → v2 (319) → v1 fallback on `UndefinedColumnError`.
- **Jev rows: role `decide`** (answered asks, refused / failed asks, the daily canary). The CHECK of CIS 319 already
  allows it. No reader filters Jev by role (they filter `provider = 'typesafe'`), checked by grep.
- **Jev outcome on the Calls tab**: `decision_log` has no status column, so the status is derived. New rule
  (`ai_gateway.jev_verdict_status` / `JEV_STATUS_SQL`): an ask refused before an answer (`… nothing was sent to the
  provider`: the Jev switch, the app profile, the circuit; `budget_exceeded`; `credit_exhausted` and its breaker text;
  a `skipped` verdict with a reason = the tenant guard) is `refused`; another error is `error`; else `ok`. A unit test
  ties every refusal text `decide.py` writes to the reader.
- **H1a table `shared.llm_app_profile`** (migration 345, contract): one row per app, the four apps CHECKed and seeded
  (AI on, not paused, no budget, the T-21 degrade mode). `cis_app` has SELECT and column UPDATE only (no INSERT /
  DELETE / TRUNCATE, the key `app` not editable: apps are added by migration). `degrade_mode` takes `llm_role_config`'s
  values plus `none` (Booking).
- **345 is contract, not expand (review fix)**: on Dev DB Migrate creates the table as `cis_owner`, whose default
  privileges in `shared` (CIS 245) give `cis_app` SELECT, INSERT, UPDATE, DELETE on every new table. A runtime-role
  DELETE of the `cis` row would switch CIS AI back on (no row = AI on, fail open). 345 therefore REVOKEs ALL from
  PUBLIC, `cis_app`, `aa_app_user`, `catalog_owner` before its grants (the 321 pattern); REVOKE is refused by the
  expand lint, so the file has no `-- migrate: expand` line. The REVOKE sits in 345 itself (not in 346) so the wide
  grants never exist, not even between two applies. The integration test grants the table-wide privileges Dev's
  default privileges give, re-runs 345 and proves INSERT / DELETE / TRUNCATE / key UPDATE are refused (CI creates the
  table as the superuser, so without that step the default privileges never apply and the test proved nothing).
- **AI off = the stage kill switch for every stage of the app**: `LLMAppDisabled` subclasses `LLMStageDisabled`, its
  message names the stage (`stage '<stage>' is switched off by an admin: AI is off for app 'cis' …`), so the job
  runner (no retry), the T2 / T9 hold (`is_stage_switch_hold`), the availability card and the ledger outcome
  (`refused` / `disabled`) need no change. The bulk re-queue holds those jobs while the app is off:
  `queue.disabled_stages` returns `EveryStage` (a frozenset where every stage is a member).
- **Where the gateway checks it**: `_generate_with` first (before the stage switch and the budgets), `probe` (the
  connection test: AI off means no AI spend at all, and it gives the live step a cheap call to refuse), `embed()`
  and the daily embedding probe (`embed.probe`; its 0 USD row says `refused`),
  Jev `decide()` (first refusal check; fail-open like the Jev switch) and the Jev canary (skipped like the switch).
  Kept in its own module (`app_profile.py`); `client.py` gets one gate method and two calls (lane l13 edits the core).
- **Fail open**: no table, no row or an unreadable table = AI on, with a warning log. The same rule as the Jev and
  connection switches; a database blip must not stop every AI call. 20 s cache per process (the stage switch's), so a
  switch reaches the other task within that window; the writer invalidates its own process at once.
- **Admin**: `GET /admin/ai-gateway/app-profiles` (spend.read; adds the central cap `llm/app:<app>` of A7 next to each
  row and `enforced_here`), `PATCH /admin/ai-gateway/app-profiles/{app}` (ai.admin, like the stage switch; only the
  fields sent; a reason of 3-500 chars to switch off; switching on clears it; audited `llm_app_ai_switched_off` /
  `llm_app_ai_switched_on` / `llm_app_profile_updated` in the same transaction). Page access action `app_profiles`.
- **UI**: an "App profiles" kit Section at the top of Providers › overview (`AppProfilesCard.tsx`), Edit in a kit
  Drawer with a confirm (destructive when switching AI off), shown only when `usePageAccess().can("app_profiles")`.
  Updated-by is not shown (it is a staff id); the date is.

## Changed

- `bulk_paused` and `default_daily_budget_usd` are stored, edited and shown, but not enforced in this slice: bulk
  pause belongs to H2 (capacity: wave auto-pause, job claim back-pressure); for CIS the enforced daily cap stays the
  central cap `llm/app:cis` (A7), and TripPlanner / the CRM take their default budget from their row in H1b / H1c.
- The catalog contract view was not extended with the profile (the brief said "only if trivial"): it needs a contract
  migration on `catalog.*` plus a `catalog_owner` column grant; it belongs to H1b, where TripPlanner reads it.
- The Guide line "Geoapify stores no answer time" changed to the per-request mean of each batch.

## Tradeoffs

- Federated read vs one physical ledger: one ledger would need dual writes or a migration of 400k+ Jev / DFS rows; the
  federated read gives the same admin view at $0 with small additive columns.
- Deriving the Jev status from error texts is fragile; a `status` column on `decision_log` (434k rows, 446 MB) would be
  a bigger contract change. The test that pins every refusal text of `decide.py` to the reader is the guard.
- Fail open on an unreadable profile means a switched-off app can run AI while the database is unreadable; the same
  outage stops the ledger and the jobs, and failing closed would stop every AI call on a blip.
