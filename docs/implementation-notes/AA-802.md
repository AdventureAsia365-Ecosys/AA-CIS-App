# AA-802 — Silent correction (remaining slice: published-copy indicator + T2 path)

S237, lane cis-portal item 5. T9 in-place sentence edit already existed (AA-769 `sentences/apply`);
this slice adds what was left.

## Decisions

- **T2 correction is an in-place UPDATE of the tenant's row, not a new `tenant_tour_versions` row.**
  The UPDATE writes `rewritten_content` only (same id, version_number, status, edit_source,
  edited_at). A new row would (1) count as a rewrite in the tenant's monthly quota
  (`v_tenant_monthly_usage` counts distinct `ttv.id`), (2) show up in the tenant's version list,
  and (3) move the version id the portal has open. Each of those breaks the AA-770 "silent" rule.
- **Version history is the audit row.** `acp_shared.audit_log` with
  `resource_type='tenant_tour_version'` and actions `tenant_tour_version.admin_sentence_{cut,rewritten,edited}`.
  `details` holds the sentence before/after, the whole section before/after **and the whole
  version before/after** (`content_before` / `content_after`, so the history has both versions as
  the Done-when asks), plus the version number and status at edit time. Tenants never read `audit_log`.
- **What an admin may correct:** only finished AI text the tenant has not decided on
  (`status IN ('ai_generated','needs_review')`), only the tenant's latest version of that tour,
  and never a version the tenant wrote (`edit_source='tenant_edit'`, which
  `v1_tours.update_version` inserts as a new `pending` version). Anything else is a 409 with the reason.
  "Latest" ignores `failed` versions (a failed re-rewrite has no text, so the older version is still
  the tenant's copy).
- **Editable sections** are the prose T3 gates: `subtitle`, `summary`, `itineraries` (string form)
  and each `highlights[i]`. An itinerary stored as a list of day objects is left out. Cutting a
  whole highlight drops the item. Emptying a text section, or removing every highlight, is a 422.
- **Checks on the new sentence** (`t2_check_replacement`): the T9 `sentence_repair.check_replacement`
  set against the source tour (F1 grounding / F2 brand forbidden / F11 brand name / near-verbatim
  repeat), plus T2's own rules: a number T3's reading finds outside the source
  (`find_novel_numeric_claims`) and the validate forbidden list. After the splice, the edit must not
  add a T3 hard code (`_t3_structural_issues` before vs after). F12/F13 are warnings, as in T9.
- **The "flagged sentences" list for a T2 version is computed now and deterministically** (no LLM):
  numbers outside the source + forbidden words. These are candidates only (T3's Jev step may have
  cleared a number).
- **"Tenant has an older copy" uses one function for T9 and T2** (`tenant_copy_state`): the latest
  publish (`publish_log.status='published'`) or export (audit `*.exported`). If an admin edit
  comes after it, `older_copy=true`. T2 versions have no publish path, so only the DOCX export counts.
  To get that signal, the tenant DOCX export now writes a best-effort
  `tenant_tour_version.exported` audit row (same pattern as the AA-613 T9 export row).
- **The AI suggestion for a T2 sentence** reuses `repair_sentences_detailed` on the cheap `t9_repair`
  stage (mode `admin_suggest_tour`). It is logged to `llm_call_log` with the tenant and costs about
  $0.001–0.006. Nothing is saved until the admin applies.
- `source_tour_dict(pt)` was extracted from `t2_rewrite_job._prepare`. The admin checks then read
  exactly the source the T2 writer and T3 gate read, so the two cannot drift.

## Changed (vs the lane spec)

- (a) Indicator: besides the pre-edit amber note (now "published **or exported**"), the drawers show
  a `TenantCopyNotice` once an admin edit is newer than the tenant's copy. The notice names the
  delivery time and the number of later edits.
- (b) The T2 drawer moved from `page.tsx` into `TourVersionDrawer.tsx`. It lists the flagged
  sentences with Cut / Rewrite / Edit actions, shows every section with clickable sentences, the
  admin edit history, escalations and cost. It reuses `RewritePanel` / `AdminEdits` from `SentenceActions.tsx`.
- (c) The AA-796 key-walk is extended in `test_aa796_tenant_projection.py`: `get_version` +
  `list_my_versions` on an admin-corrected version stay free of gate/score keys, and they never read `audit_log`.
- The optional tenant-facing "updated version available" marker is **deferred**, as the spec allowed.
- `API_WRITE_RULES` in `frontend/lib/rbac.ts`: `content-quality/tour-versions/` writes are admin-only
  (the backend re-checks `X-Admin-Role` too).

- Review (S237): audit `resource_id` is the canonical `ttv.id` text (apply and DOCX export), so an
  upper-case id in a path cannot orphan the row from the drawer's `ttv.id::text` lookup. The admin
  drawers tolerate an API without the AA-802 fields (Vercel can go live before ECS): the T2 drawer
  then renders read-only and the older-copy notice stays hidden, instead of a crash.

## Tradeoffs

- In-place UPDATE loses a row-level "previous version". The full section before/after lives in
  the audit row, so the history is reconstructable, but not as a `tenant_tour_versions` row. I chose
  this because the quota and the tenant version list must not change.
- The CatalogTab CSV/XLSX exports run client-side from list data, so no server-side audit row records them.
  Only the DOCX export marks "tenant has a copy" for T2. The indicator can therefore miss a
  CSV/XLSX download.
- The T2 flag list is a deterministic re-read, not the stored T3 verdict. It may show a number that
  Jev already accepted. The admin decides.

## Should know

- **D2 / AA-817 (migration 229):** the UPDATE names the row by `id AND tenant_id AND status = ANY(editable)`.
  A 0-row result is a **409, never a silent success**. Both are unit-tested:
  `test_apply_cut_updates_the_tenants_row_in_place_and_audits`, `test_apply_targets_the_rows_own_tenant_not_another`
  and `test_apply_zero_rows_updated_is_a_409_not_a_silent_success`. 229 is ENABLE without FORCE, so the
  admin path as `aa_cis_admin` keeps working (lessons: on RDS `aa_cis_admin` also reads under FORCE).
  **Re-verify after 229 is applied:** GET `/admin/content-quality/tour-versions/{id}` returns the row,
  and one apply on a test tenant's held version returns 200 with the text changed.
- `SELECT … FOR UPDATE OF ttv` locks only the version row (the joined tenants / published_tours /
  raw_tours rows are not locked). The tenant approving at the same moment is serialized by that lock,
  and the UPDATE's status filter catches it.
- No migration and no new table. The new audit action strings are in `services/acp_shared/audit_log.py`.
- Live verify (Done-when): pick a `needs_review` version of a test tenant. Cut or edit a sentence in
  the Content Quality → Tour versions drawer. Then `curl` the tenant `GET /v1/tours/versions/{id}` and
  check that it shows the new text, that the version number and status are unchanged, and that there are no gate keys.
  Check that the audit row has `section_before/section_after`. For a published T9 piece, edit a sentence
  and screenshot the "older copy" notice.

# AA-802 — S238 scope addition: latest-piece rule on every tenant read

S238, lane E. Linear comment "Scope addition (S238 backlog audit)", from the S237 UI verify D1.

## Decisions

- **`/pending` picks the latest piece per `angle_gate_request_id` first, over every status, and
  filters after.** `_PENDING_SQL` (`api/routers/v1_publish.py`) uses a `latest` subquery
  (`DISTINCT ON (angle_gate_request_id) … ORDER BY angle_gate_request_id, created_at DESC`), the same
  key and order as My Content (`_TENANT_REVIEWS_QUERY`, AA-497/AA-501). The status, channel and
  publish filters run on that one piece. If you filter first and dedupe after, an older approved piece
  comes back whenever the newest piece is processing, failed or already published. My Content shows
  the newest piece, so the two pages would disagree.
- **Published / in-flight check is `NOT EXISTS` instead of `LEFT JOIN … IS NULL`.** It returns the same
  rows, and two live `publish_log` rows on one piece can never duplicate a card.
- **`publish()` refuses a superseded piece with a 409.** The piece lookup returns `superseded` (a newer
  piece exists for the same request). This applies "never publishable" to the write path as well,
  so a stale page cannot still publish an old version. The 422 for "not written yet" is still checked first.
- **Other tenant reads checked (no change needed):**
  - My Content list (`fetch_review_list`) already returns one row per request, the latest piece.
  - Review detail (`fetch_review`) and the wizard resume (`fetch_latest_piece_for_request`) use `LIMIT 1` latest.
  - The dashboard (`DashboardTab`, `GettingStarted`) counts no pieces. Getting Started only checks
    whether `/content-writing/reviews` is non-empty, which is already one per request.
  - Export (`GET /pieces/{id}/export`) and `GET /pieces/{id}` read one piece by id; they do not list.
    My Content only offers the latest piece's id. I left them as they are, since refusing an export of
    an old version the tenant can still link to is a product choice, not duplication.
  - `services/acp_planning/tenant_pool.py` (atom lock per month) counts approved pieces per atom
    for locking, not for display. The earliest piece is the intended semantics there.

## Changed (vs the comment)

- Done-when 2 ("after a repair on an unpublished held piece, `/pending` returns only the new piece_id"):
  admin and AI repair on a T9 piece is an **in-place UPDATE** of the same `piece_id` (AA-769
  `sentences/apply`, see the first section). So the "new piece" is the same row with new text, and
  `/pending` shows it once. A new `piece_id` only comes from a re-write (reopen / tenant edit). The
  integration test covers that path: 3 pieces under one request give 1 row, the latest.

## Tradeoffs

- **The newest piece wins even when it is not ready.** For example, an approved v1 plus a v2 that is
  still processing gives no card until v2 finishes. This matches My Content, which shows v2 as "in
  progress". The tenant asked for the re-write, so publishing v1 meanwhile would ship content they chose
  to replace.
- **An older piece published + a newer piece unpublished → the newer piece is a card.** I took this
  literally from the comment ("a request whose *latest* piece is published shows nothing"). A re-write
  after a publish is new content, and the old post stays on the channel. Live count today: 0 such
  requests for atlas-hearth and terra-family.
- There is no shared SQL helper between `/pending` and My Content. That is codebase precedent: each
  read keeps its own SQL (`fetch_review_list` docstring). Alignment is pinned by a unit test (same key
  and order) and an integration test (the `/pending` set equals My Content's ready-and-not-live set).
