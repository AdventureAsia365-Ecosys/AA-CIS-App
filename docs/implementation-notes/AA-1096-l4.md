# AA-1096 lane L4 (S279): the CRM tab of Platform › Settings

Plan: root `docs/audits/2026-11-13-S279-session/thresholds-audit/README.md` sections 5.3 and 6 (lane L4). The CRM's own
registry, API and wiring are in AA-Partner (crm-064, crm.ops.v1 1.13); this repo only relays the CRM tab.

## Decisions

- **Relay, never read.** The CRM keeps its settings in `crm` (root ADR 0008a): CIS calls the CRM's `crm.ops.v1`
  `/settings` routes through `crm_console.crm_ops_call` with the staff member's own Cognito token (the L1 console and
  app-profile pattern), so the CRM checks the group itself (crm-platform-admin writes). `crm_console.ALLOWED` gains the
  four settings routes and nothing else.
- **Same page, same API.** `/admin/settings/registry?app=crm`, `/{crm.* key}/history`, `/{crm.* key}/proposals` relay
  to the CRM; a decision names its app (`{note, app: "crm", tenant_id?}`), because a value id does not say which
  registry holds it. The CRM's `pending` key (crm.ops.v1 forbids "proposal" in a key) becomes the page's `proposals`.
- **CIS audits the relayed write** (`acp_shared.audit_log`, the same `setting.*` actions, `details.app = crm`, the CRM
  agency id in `resource_id` / `details` and `tenant_id` NULL: a CRM agency id need not be a CIS tenant row). The write
  happens after the CRM answered; a failed audit write is logged (`crm_setting_audit_failed`), never reported as a
  failed change.
- **Permissions**: the CIS capabilities stay the gate (`settings.write` / `settings.approve`, admin only, verified
  Cognito caller); `apply` on a CRM change needs `settings.approve`, as for a CIS key.

## Tradeoffs

- Pending changes of one agency's own CRM value are not on the list (the CRM sees them only in that agency's
  context); the history with `tenant_id` shows them. A per-agency editor (Tenant 360) is a follow-up.

## Should know

- Before crm-064 is applied and the CRM code deployed, the CRM tab answers 503 `settings_unavailable` (the page shows
  "not available yet"); a 404 `crm_path_not_allowed` means this relay is older than the CRM routes.
- The E2E CIS admin is read-only on CRM writes (`e2e_read_only`): the write check needs a crm-platform-admin staff token.

## After CIS 416 / #1486 (operator guides)

- **Merge**: main's Settings page (guide line, Explain panel, decimal comma, staff names) merged with the CRM relay;
  the two conflicts were import lists (`decisionBody` kept beside main's `valuesInForce` / `ValueOf`) and the two
  test blocks (both kept).
- **Decision**: the CRM tab shows its guides with no CIS change: the page reads `guide` from each definition and the
  relay hands the CRM answer on untouched. AA-Partner now serves `guide` for its 27 keys
  (`api/app/platform_settings/guides.json`, its own guide lint); `test_the_crm_guide_reaches_the_page` pins the
  pass-through (list and history). The CIS guide lint reads only the CIS compiled defaults, so it needs nothing for CRM
  keys.
- **Gaps**: the "In force now" line (`nowExample`) covers CIS keys only (no CRM key is a sum of others). A CRM row's
  actor is `platform:<staff sub>`, not `admin:<uuid>`, so `proposed_by_name` / `decided_by_name` are absent and the
  page shows the id (the CRM keeps no staff names).
