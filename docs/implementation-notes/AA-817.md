# AA-817: RLS for tenant paths (S237, step 1: role matrix + CI guard)

Lane cis-backend item 4, step 1. This step adds no migration and moves no route. Decisions D2 and
D8 from the S237 orchestrator journal apply. Migration 229 uses ENABLE without FORCE, owner exempt,
on the 115/116/145 pattern. Migrations go through a file-only PR, then an Infra byte copy, then DB
Migrate, then the code PR.

## Decisions
- **The probe is a one-off script outside the repo**: `AA-Ecosys/.tmp-session/s237/aa817_probe.py`.
  The orchestrator runs it in the api container through S3-mediated ECS exec. It is read-only by
  construction: `BEGIN READ ONLY`, rolled back at the end; every `SET LOCAL ROLE` and
  `set_config(..., true)` sits in a savepoint that is also rolled back. If the runner may not
  `SET ROLE aa_app_user`, the probe logs in through the existing `aa-cis/dev/rds-app-user` secret
  instead of granting membership.
- **The probe also discriminates the S236 mechanism.** It counts every FORCE-RLS table, not only
  published_tours. If the runner sees foreign rows on published_tours/raw_tours only, the cause is
  inherited `catalog_owner` (policy `catalog_owner_aa_master_read`, 225). If it sees them on every
  FORCE table, the cause is a real bypass. `row_security_active()` and the recursive membership
  chain are recorded too.
- **The CI guard ships now, ahead of 229**: `tests/integration/test_aa817_rls_tenant_isolation.py`.
  It covers the 4 acp_shared tables behind the tenant content-piece routes. tenant_tour_versions
  joins the test with 229, because it has no RLS before 229 and the CI DB does not create it.
- **First route group to move after 229 (proposed, Nghiệp confirms per the AA-544 rule)**:
  `GET /v1/content-writing/requests/{id}/latest-piece`, then `PATCH /pieces/{id}`. They touch only
  content_piece (RLS) and angle_gate_option, both already granted. `/reviews` and
  `/requests/{id}/review` need grants on tour_atoms, subject, atom_segment and route first, and
  the trips lookup must stay on the main pool.

## Changed
- New `tests/integration/test_aa817_rls_tenant_isolation.py` (11 tests: 10 pass, 1 strict xfail).
  Nothing in `api/` or `services/` changed.
  - Read side: WHERE-less `SELECT DISTINCT tenant_id` under own / other / forged / `''` GUC.
  - Write side (added in review, because the proposed second route is `PATCH /pieces/{id}`): a
    WHERE-less UPDATE touches only the own tenant's row; handing a row to another tenant, or
    INSERTing one for another tenant or under `''`, is refused by the implicit WITH CHECK.
  - Strict xfail `test_tenant_role_cannot_write_platform_facts`: pins a real gap (see Should know).
    When the fix lands the xfail turns into a failure, so the fix PR must drop the marker.

## Tradeoffs
- The test seeds as the CI superuser and reads under `SET LOCAL ROLE aa_app_user` in one
  rolled-back transaction, so nothing needs cleaning up. It does not reproduce an RDS-like
  non-superuser owner (as `test_aa679_catalog_views.py` does for 225). That matters for 229's
  owner-exemption check, so the 229 PR should add it, not this guard.
- A WHERE-less `SELECT DISTINCT tenant_id` is the strongest form of "the app forgot its filter":
  it proves RLS alone holds the boundary.

## Should know
- **acp_shared.facts write gap (found in review, latent).** Policy 145 is FOR ALL with
  `USING (scope = 'platform' OR tenant_id = GUC)` and no separate WITH CHECK, and 147 grants
  INSERT/UPDATE on facts to aa_app_user. The tenant role can therefore update every platform fact
  and insert new `scope = 'platform'` facts that every tenant's T9 cites (verified on PG16). No
  tenant-pool route writes facts today. Fix in its own migration before any facts write moves to
  the tenant pool: split the policy (SELECT keeps the platform branch, INSERT/UPDATE check
  `scope = 'tenant' AND tenant_id = GUC`) or revoke INSERT/UPDATE.
- The CI DB has no `gold_aa_internal.tenant_tour_versions`, because migration 001 is skipped. So
  107/108/109/128/175/223 never applied in CI, and 229 would fail silently there (conftest swallows
  migration errors). The 229 PR should pre-create the table in conftest in its live shape.
- Policies 004/008 (generated_content, seo_context, quality_scores, content_exports,
  webhook_deliveries, pipeline_runs) still cast the GUC without NULLIF. A non-exempt reader on a
  pooled connection, where the GUC is `''`, gets "invalid input syntax for type uuid" instead of 0
  rows. Nothing on the tenant pool reads them yet.
- Moving `/v1/tours*`, marketplace, route hub or slate to the tenant pool hides every AA-master
  published_tours/raw_tours row from aa_app_user (the AA-578 "never move to RLS pool" comments).
  Stage 2 needs a master-read policy for aa_app_user, mirroring catalog_owner's, or reads through
  `catalog.v_tour*`.
- The design notes, the inventory with file:line, the draft 229 (dry-run on a throwaway PG16:
  passes as owner, raises as non-owner, raises when FORCE is added) and the CI-guard follow-up are
  in `AA-Ecosys/.tmp-session/s237/aa817_design.md`.

# AA-817 step 2a: migration 229 (S237, branch feat/aa-817-mig-229-rls)

Migration-only branch (D8): `api/migrations/229_tenant_rls_policies.sql` + tests. The code that moves a
route to the tenant pool is the stacked branch `feat/aa-817-tenant-pool-content` (step 2b below).
Inputs: `docs/audits/2026-10-14-S237-lane-backlog/aa817/` (probe.json, aa817_design.md) and the data
architecture review (P2, P3, N2, N7) in the root repo.

## Decisions
- **Scope = the five tenant-pool tables**: `acp_shared.angle_gate_request`, `content_piece`,
  `publish_log`, `facts` and `gold_aa_internal.tenant_tour_versions`. These are the tables
  aa_app_user reads or will read (AA-544 stages 1/5, AA-815, the next route groups). They are all
  ENABLE without FORCE live, owned by aa_cis_admin, and no other role has a grant on them, so moving
  their policies to `TO aa_app_user` changes nothing for any other role.
- **The FORCE tables stay out** (published_tours, raw_tours, generated_content, quality_scores,
  seo_context, content_exports, webhook_deliveries, pipeline_runs). tripplanner and catalog_owner read
  published_tours/raw_tours through `tenant_isolation TO public`; `test_aa679_catalog_views.py`
  reproduces an RDS-like owner under FORCE through those same PUBLIC policies; and on Dev the
  runner's exemption on FORCE tables is observed (probe) but unexplained. Scoping their policies to
  aa_app_user would deny every non-aa_app_user reader. Their missing NULLIF (P3) is a follow-up.
- **Template** (data standards 4.4): `FOR ALL TO aa_app_user USING (tenant_id =
  NULLIF(current_setting('app.tenant_id', true), '')::uuid) WITH CHECK (same)`. Every old policy is
  dropped by name; the file is re-runnable.
- **facts gets two policies**, not one: `tenant_isolation` FOR ALL restricted to `scope = 'tenant'`
  (USING and WITH CHECK), plus `facts_platform_read` FOR SELECT `USING (scope = 'platform')`. An
  UPDATE/DELETE uses only the FOR ALL policy's USING, so a platform row can be neither changed nor
  re-scoped; an INSERT of a platform row fails WITH CHECK. Chosen over revoking INSERT/UPDATE because
  a tenant facts route is planned and the grant is already there (147).
- **Drift**: `DROP POLICY IF EXISTS tenant_tour_versions_isolation` (TO public, text compare, live
  only) and `output_rules_rls` (app.current_tenant, live only; guarded by `to_regclass`, the table is
  not created by any repo migration). acp_output_rules keeps RLS on with no policy: only the owner
  reads it (v1_rules.py, rule_adapter.py, main pool). It stays on the retirement list (review L1).
- **Grants**: `USAGE ON SCHEMA gold_aa_internal` (no-op on Dev, needed in CI) and `SELECT, INSERT,
  UPDATE ON tenant_tour_versions` for the stage-2 routes. No DELETE (offboard runs on the main pool).
  No grant on tour_atoms/subject/atom_segment/route (needed only by /reviews and
  /requests/{id}/review, not by the route moved in step 2b).
- **N7**: `ALTER DEFAULT PRIVILEGES IN SCHEMA shared|silver_aa_internal|gold_aa_internal REVOKE SELECT
  ON TABLES FROM aa_app_user`, same form as 007b (no FOR ROLE: the default ACL belongs to the role
  that ran 007b, aa_cis_admin, which also runs DB Migrate). Existing grants are untouched.
- **Guards** (lesson S236, behaviour not attributes): (1) each table exists, the runner owns it (or
  is superuser/BYPASSRLS), none is FORCEd; (2) after: RLS inactive for the runner and it counts every
  row under a foreign tenant; (3) as aa_app_user: foreign and '' GUC return 0 rows (facts: the
  platform rows), the busiest tenant gets exactly its own rows, a platform fact can be neither
  updated nor inserted; (4) the policy set of each table is exactly the expected one, all TO
  aa_app_user (catches an unknown live-only permissive policy); (5) no default privilege of the runner
  grants aa_app_user. For (3) the runner gets `GRANT aa_app_user` for this transaction only when it
  cannot already `SET ROLE aa_app_user` (detected by trying it), and it is revoked before COMMIT, the
  catalog_owner pattern of 225.

## Changed
- `api/migrations/229_tenant_rls_policies.sql` (new).
- `tests/integration/conftest.py`: `TTV_STANDIN_DDL`; the migration loop creates the stand-in just
  before 229 and drops it right after, so 229 really applies to the acp_shared tables in CI while
  every other test sees the same DB as before (a global stand-in broke `test_aa687`, whose
  `domain_links()` selects `version_number`; the live shape would make `test_aa766` skip).
- `tests/integration/test_aa817_migration_229.py` (new, 15 tests): applied by conftest; template
  shape per table; grants; tenant_tour_versions read/write isolation; facts platform rows read-only;
  re-run drops both drift policies and the 007b default privilege, idempotent; guard refuses FORCE,
  an unknown extra policy, and a non-owner runner; applies as an RDS-like runner (owner, NOSUPERUSER,
  NOBYPASSRLS, CREATEROLE, cannot SET ROLE aa_app_user) through the transaction-scoped membership and
  leaves no membership behind.

## Tradeoffs
- The RDS-like runner test uses `SET LOCAL SESSION AUTHORIZATION`, not `SET ROLE`: SET ROLE
  permission is checked against the session user, which would still be the test superuser, so the
  GRANT path of guard 3 would never run. On PG16 (local) the runner also gets `ADMIN TRUE, INHERIT
  FALSE, SET FALSE` on aa_app_user, because PG16 CREATEROLE may grant only roles it administers; RDS
  and CI run PG15, where CREATEROLE grants any non-superuser role.
- Guard 3 writes nothing that survives: the platform-fact INSERT is refused (caught), the UPDATE
  touches 0 rows, the whole check runs inside the migration transaction.
- Mutation checks run locally: drop the transaction GRANT → RDS-like test fails; `WITH CHECK (true)`
  on facts → guard raises "aa_app_user inserted a platform fact"; `TO public` → guard 4 raises;
  no NULLIF → 9 tests fail ('' GUC raises invalid uuid).

## Should know
- Apply 229 only with no `t2_rewrite` / `t9_write` job queued or running. On Dev the runner is not
  a member of aa_app_user (probe: `members: []`), so guard 3 does the GRANT/REVOKE dance; aa_cis_admin
  has CREATEROLE (probe), which PG15 needs for it.
- Review fix (S237): guard 1 now takes `LOCK TABLE ... IN ACCESS EXCLUSIVE MODE` on each table before
  counting it. Without it a row written between guard 1's count and the first DDL (a tenant POST
  write, a T9 job) aborted the apply on a false "runner sees n of m rows". The locks are the ones the
  DDL takes anyway, held to COMMIT; they are taken one table at a time, so a worker transaction that
  holds content_piece and then reads angle_gate_request can still deadlock with the apply (Postgres
  aborts one side after deadlock_timeout): another reason for the no-jobs window.
- After apply: rerun the probe (expect aa_app_user `tenant_tour_versions` foreign 0/0, empty 0/0,
  own n/1; facts foreign = platform rows only) and smoke the admin tour-versions list.
- Regenerate `docs/architecture/db-schema-reference.md` (policies are not in the dump yet: P8/N1).
- `shared.v_tenant_monthly_usage` (owner aa_cis_admin, SELECT to aa_app_user) reads
  tenant_tour_versions with the owner's rights, so it is not filtered for aa_app_user. Unchanged by
  229; no tenant-pool route reads it.
- The branch `chore/aa-817-role-matrix` (step 1: guard test + these notes' first part) is superseded:
  its guard test moves into the code branch with the facts xfail removed. Do not open a PR for it.

# AA-817 step 2b: first route group on the tenant pool (S237, branch feat/aa-817-tenant-pool-content)

Stacked on `feat/aa-817-mig-229-rls`. Code PR of the D8 train: merge only after 229 is applied, although
the code works with or without it.

## Decisions
- **Route group = tenant content-piece reads that touch only RLS-protected, already-granted tables**:
  `GET /v1/content-writing/requests/{id}/latest-piece` (`service.fetch_latest_piece_for_request`),
  as the step 1 design proposed. `/reviews` and `/requests/{id}/review` stay on the main pool: they
  read acp_contract.tour_atoms / subject / atom_segment / route (no grant to aa_app_user, by AA-544
  stage-0 choice) and `fetch_tenant_trips` joins FORCE-RLS published_tours. `GET /pieces/{id}` (and
  its export) is already on the stage-5 flag. PATCH /pieces/{id} is the next write route.
- **New flag `aa817:content_piece_reads_pool`, default off** (`CONTENT_PIECE_READS_FLAG`). Turning it
  on in Dev is Nghiệp's call (AA-544 report-then-confirm).
- **Fail closed** (`acquire_scoped_conn(..., fail_closed=True)`): with the flag on, a missing tenant
  pool, an empty tenant id, or a `set_config` that did not return the tenant id is a 503. It never
  falls back to the admin pool, which RLS does not filter (owner exempt). Flag off is unchanged.
  Existing callers (stages 1/5, AA-815) keep the old fallback (keyword defaults to False) so their
  behaviour does not change in this PR.
- **The chosen-option lookup is tenant-scoped too**: it now joins `angle_gate_request` and filters
  `r.tenant_id = $2`. angle_gate_option has no tenant_id and no RLS, so before this the tenant pool
  could read another tenant's option id by request id (no content leaked: the piece query is
  tenant-filtered, but the id was readable). Same result for the owning tenant.
- Both reads run on one connection inside the tenant transaction (`_latest_piece_for_request`), so
  the GUC applies to both.

## Changed
- `api/core/aa544_tenant_pool.py`: `CONTENT_PIECE_READS_FLAG`, `fail_closed` keyword (503 paths,
  logs `aa817_tenant_context_unavailable` / `aa817_tenant_guc_not_applied`).
- `services/acp_content_writing/service.py`: `fetch_latest_piece_for_request(..., request=None)`
  routes through `acquire_scoped_conn` when `request` is passed; logs `aa817_latest_piece` with
  `used_tenant_pool` (Done-when 4 evidence); tenant-scoped `_CHOSEN_OPTION_QUERY`.
- `api/routers/v1_content_writing.py`: `get_latest_piece` passes `request=request`.
- Tests:
  - `tests/unit/test_aa817_tenant_pool_fail_closed.py` (12): flag off → admin pool; flag on → tenant
    pool + LOCAL GUC; 503 without tenant pool / tenant id ('' and None) / applied GUC; Redis error =
    off; old callers keep the fallback; latest-piece on the tenant pool, same shape on both pools,
    503 path. `test_aa450_content_writing_service.py`: the option query is tenant-scoped.
  - `tests/integration/test_aa817_tenant_pool_content.py` (6 = 3 × policies before/after 229): own
    tenant same piece on both pools; foreign tenant gets nothing; with the tenant filters stripped
    from both queries (a forgotten WHERE), the tenant pool still returns nothing while the admin
    pool leaks (proves the check bites).
  - `tests/integration/test_aa817_rls_tenant_isolation.py` (from `chore/aa-817-role-matrix`,
    extended, 16): tenant_tour_versions added (stand-in + 229 re-applied per test); write checks on
    all five tables (WHERE-less UPDATE only own rows; hand-over refused; INSERT for another tenant or
    under '' refused, own INSERT allowed); the facts xfail is now a real test (no update, no insert,
    no re-scope of platform facts).

## Tradeoffs
- `fail_closed` is opt-in per call instead of a new default, so this PR changes no existing route.
  Moving stages 1/5 and AA-815 to fail-closed is a one-line change each, worth doing when each is
  confirmed on Dev.
- The integration test emulates the tenant pool with `SET LOCAL ROLE aa_app_user` on the test
  connection (CI's aa_app_user has no LOGIN). The policies only look at current_user and the GUC, so
  this is the same check RLS does for the real login.

## Should know
- Rollout: (1) 229 applied (D8), (2) this PR merged + Deploy Dev COMPLETED (flag off: no behaviour
  change), (3) Nghiệp confirms, then `redis-cli SET aa817:content_piece_reads_pool true`, (4) curl the
  route as the owning tenant (200, same shape as before), as a foreign tenant with the same request id
  (`{"piece": null}`), and check CloudWatch `aa817_latest_piece used_tenant_pool=true`. Revert:
  `redis-cli DEL aa817:content_piece_reads_pool`.
- The 503 is visible to tenants only if the tenant pool fails to boot (secret
  `aa-cis/dev/rds-app-user` missing/unreachable) while the flag is on: check
  `aa544_tenant_pool_create_failed` in the api logs before flipping the flag.

# AA-817 scope addition 1: migration 237, shared.tenant_integrations on the 229 template (S239, branch feat/aa817-mig237-tenant-integrations-rls)

Migration-only branch (D8): `api/migrations/237_tenant_integrations_rls.sql` + tests. Input: the S238
scope-addition comment on AA-817 (191e259d), the S237 design (`docs/audits/2026-10-14-S237-lane-backlog/aa817/`)
and migration 229. Turning on `aa544:integration_disconnect_pool` is a later, observed window (Nghiệp approves).

## Decisions
- **Number 237**: highest on CIS origin/main (802b5920) and AA-CIS-Infra `db/migrations/cis` is 236; no
  open PR or branch in either repo holds 237. (232 is a gap on both, not reused.)
- **Template = 229's, one table**: ENABLE without FORCE (D2, owner exempt), one policy `tenant_isolation`
  `AS PERMISSIVE FOR ALL TO aa_app_user USING/WITH CHECK (tenant_id = NULLIF(current_setting('app.tenant_id',
  true), '')::uuid)`. FOR ALL rather than per-command policies, as 229, so a later INSERT/UPDATE grant for
  the connect routes is covered by the same WITH CHECK without a policy change.
- **Grants = SELECT, DELETE** (what 229 did per route need: it granted SELECT/INSERT/UPDATE on
  tenant_tour_versions for the stage-2 routes, no DELETE). The disconnect path (`v1_integrations._disconnect`)
  runs a `SELECT secret_key ... WHERE tenant_id AND integration_type`, then a `DELETE ... WHERE` (which also
  needs SELECT on the filtered columns). Connect / test-connection (INSERT/UPDATE) and the publish/unpublish
  secret lookups (`v1_publish.py`) stay on the main pool, so no INSERT/UPDATE. SELECT already exists on Dev
  (007b default privileges); the GRANT makes it explicit and gives it to CI, which skips 007b/008.
  `GRANT USAGE ON SCHEMA shared` for the same reason (no-op on Dev).
- **Guards** (229's set, one table) plus two that 229 did not need:
  - guard 1 refuses any grantee other than the owner and aa_app_user (PUBLIC included): with RLS on and the
    policy TO aa_app_user only, such a reader would silently read 0 rows. Dev (S239 probe): only
    `aa_cis_admin` (owner) and `aa_app_user` (SELECT).
  - guard 4 also checks the policy by **shape** (FOR ALL, USING and WITH CHECK start with
    `tenant_id = (NULLIF(current_setting('app.tenant_id'...`): Dev has **0 rows** in the table (S239 probe),
    so guard 3's behavioural counts cannot catch a `USING (true)` there.
  - guard 5: aa_app_user has SELECT + DELETE and **no TRUNCATE** (TRUNCATE is not filtered by RLS).
  - guard 3 adds a WHERE-less `DELETE` as aa_app_user under a foreign and an empty GUC that must delete 0
    rows (never under the own tenant: the guard must not remove a real row; a failure raises and rolls the
    whole apply back).

- Guard 1's "no other grantee" is strict on purpose: a missed reader would fail silently (0 rows), an
  aborted apply fails loudly. The cost was one line in conftest for the CI-only `app_user`.

  ''app.tenant_id''%'`). Same deparse on PG15 (Dev, CI) and PG16 (local run); if a future server deparses
  differently the apply aborts (rolled back), it never passes a wrong policy.
- Mutation checks, run locally (PG16): no ENABLE → 6 tests fail; no DELETE grant → guard 5 aborts the
  apply; no NULLIF → guard 3 aborts (`invalid input syntax for type uuid: ""`); `TO public` → guard 4;

  TRUNCATE grant → guard 5.
