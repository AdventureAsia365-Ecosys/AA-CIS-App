## Decisions

- **On-demand computation, not a scheduled job** — per the issue's own recommendation ("Đề xuất
  on-demand trước — đơn giản hơn, không cần thêm hạ tầng scheduler"). `GET /admin/a4/trust-ramp`
  now computes `engagement_ok`/`weeks_active`/`suggested_mode` fresh on every call, no caching, no
  new EventBridge schedule, no new table. Matches this repo's existing precedent
  (`suggest_trip_reallocation()`, AA-448 round 6 — same "never writes, recomputed live" shape).
  Nghiep is not available to re-confirm before build (background/async task); going with the
  issue's own explicit recommendation rather than blocking on a round-trip, and flagging this
  choice clearly in the Linear comment so it can be revisited.
- **`weeks_active` = `COUNT(*) FROM acp_deliver.packets GROUP BY tenant_id`** — real production
  cadence (how many real weekly packets exist for this tenant), not calendar time since account
  creation. Reuses `packets`' own `UNIQUE(tenant_id, year, month, week)` guarantee (migration 106)
  directly — no new column.
- **`engagement_ok` = tenant-wide average `engagement/reach` (from the LATEST snapshot per piece,
  same "DISTINCT ON piece_id ORDER BY entered_at DESC" shape `content_metrics.py`'s own
  `rollup_atom_weights()` already uses) >= `ENGAGEMENT_RATE_BASELINE`** (0.05,
  `services/acp_planning/constants.py` — reused as-is, not a new magic number), gated on
  `>= CONFIDENCE_ATOM_MIN_POSTS` (3) real reach-bearing snapshots for that tenant. Below the
  confidence gate: `engagement_ok=False` — "no data yet" is NOT the same as "engagement is good",
  same fail-closed law `_piece_score()` already establishes for the underlying data.
  New functions added to `trust_ramp.py` (not `content_metrics.py`) since these are Trust-Ramp-
  specific derived signals, consumed only here — `content_metrics.py`'s own public surface
  (`record_metric_snapshot`/`rollup_atom_weights`) is unchanged, no shared helper extracted since
  the two modules use the same raw data for genuinely different purposes (atom weight vs. ramp
  eligibility) with different aggregation scopes (per-atom vs. tenant-wide).
- **Suggestion surfaced per PACKET, not collapsed to one tenant-level flag** — matches
  `admin_a4.py`'s own existing decision #3 (AA-437: "no per-tenant single ramp level ... this
  returns every packet with its own level, never collapsed") and the current UI's per-packet-row
  table. `GET /admin/a4/trust-ramp` gains `engagement_ok`/`weeks_active`/`suggested_mode`/
  `eligible` per row; `eligible = (suggested_mode != publish_mode)`. The issue's own UI text says
  "Tenant X đủ điều kiện lên bậc Y" (tenant-level phrasing) but the existing data model is
  per-packet — kept the existing per-packet shape rather than inventing a tenant-collapse (which
  AA-437 explicitly decided against), and render the badge per eligible packet row, grouped
  visually by tenant exactly as the page already groups them.
- **Two new mutating endpoints**, both requiring an explicit admin click (per ADR-2026-038 §0.2 —
  never auto-transition):
  - `POST /admin/a4/trust-ramp/{packet_id}/approve` — re-computes the suggestion fresh (not
    trusting a client-supplied `suggested_mode`, same "never stale" principle
    `confirm_trip_reallocation()` already uses), then calls the EXISTING
    `trust_ramp.confirm_ramp_transition()` unchanged — this is that function's first real caller.
    BOFU hard-block and the 3-state validation inside `confirm_ramp_transition()` apply exactly as
    before; a blocked attempt still gets a `publish_mode_transition` audit_log row (already built
    into `confirm_ramp_transition()`) and this endpoint surfaces it as 409, not a silent no-op.
  - `POST /admin/a4/trust-ramp/{packet_id}/skip` — new. Re-computes the suggestion fresh, writes
    ONE `acp_shared.audit_log` row (`action='ramp_suggestion_skipped'`, same table every other
    real gate/approval decision in this repo already uses — no new logging shape), does NOT touch
    `packets.publish_mode`. Closes the issue's #4 ask ("log mỗi lần admin duyệt/bỏ qua") for the
    "bỏ qua" (skip/dismiss) half, which had no existing mechanism at all.
  Both actions reuse the exact `x-admin-user-id` → `actor="admin:<id>"` convention
  `admin_a4.py::force_unpublish()` (AA-455) already established — no new identity mechanism.
- **`GET /admin/a4/trust-ramp` itself does NOT write to `audit_log` on every page view** — logging
  every read as a "suggestion given" event would be a new precedent this repo's read endpoints
  don't follow anywhere (every other A4 read endpoint uses `structlog.logger.info` for
  observability, `audit_log` is reserved for actual gate/approval DECISIONS). The issue's #4 ask
  ("ghi log mỗi lần gợi ý được đưa ra") is read as "log the decision made about a surfaced
  suggestion" (approve/skip, both now logged) rather than "log every time an admin's browser
  happens to fetch the page" — flagged explicitly in the Linear comment as an interpretation
  choice in case Nghiep meant literal view-logging.
- **No new migration.** Reuses `acp_deliver.packets` (094/106), `acp_shared.content_metric_snapshot`
  (112), and `acp_shared.audit_log` (030) — all already live. Latest migration in this repo remains
  144 (`route_versioning.sql`).

## Tradeoffs

- Computing `engagement_ok` tenant-wide (not per-packet/per-week) means a tenant with one
  excellent week and several mediocre ones gets one blended signal, same coarseness the aamc
  prototype's own G3 gate had (a single tenant-level `engagement_ok` bool, never per-period) — not
  a regression introduced here, this build stays at the same granularity the ported design
  already had.
- On-demand computation means opening the Trust Ramp panel triggers 1 extra read query per
  distinct tenant on the page (weeks_active) + 1 more (engagement_ok) — at current real data
  volumes (few tenants, few packets) this is negligible; flagged in case tenant count grows large
  enough to warrant caching later (no premature optimization added here).

## Should know

- `suggest_ramp_transition()` and `confirm_ramp_transition()` are BOTH unchanged — this build is
  entirely new callers + new signal-computation, no edits to the ramp logic itself.
- The BOFU hard-block (`packet_has_bofu_piece()`) is untouched and still applies inside
  `confirm_ramp_transition()` — a BOFU-carrying packet can be "eligible" per the suggestion (the

  approve it into `veto_window_auto`, exactly as it already would for any other caller.

  don't go looking for it if touching this area again; that was AA-365's own aspirational note,
