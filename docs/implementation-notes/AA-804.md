# AA-804 — AI providers page, part 1 (Providers tab + job Trace), root ADR 0009

Design: the approved S261 AI gateway design v2 (root repo `docs/audits/2026-10-31-S261-ai-gateway-design-v2/`,
section "Giao diện (UI)"), slice C1 of the S262 build plan (wave 1). One PR, branch `feat/aa-804-ai-gateway-page`.
No migration, no paid call, no change to `shared/llm_client/**`.

What ships:

- `GET /admin/ai-gateway/providers` and `GET /admin/ai-gateway/trace?job_id=` (`api/routers/admin_ai_gateway.py`,
  logic in `api/services/ai_gateway.py`), POLICY `spend.read` (admin only), route-policy snapshot regenerated.
- `/admin/ai-gateway` (Platform › AI & spend › **AI providers**, first in the group): tabs Providers + Guide, the
  Trace drawer (`?trace=job:<id>`), kit only.
- Jobs drawer: "Open trace" link. Cost Operations › Budgets: the provider picker lists every provider the backend
  accepts (adds geocoder, anthropic, azure_openai). Apps board: TripPlanner "AI paused (spend unreadable)".

## Decisions

- **One aggregate endpoint, sources read independently.** `read_providers` runs six reads in parallel (connection
  registry + health + monthly budgets, the month LLM ledger, spend budgets, Jev, DataForSEO, Geoapify). A failing
  read turns only its rows to `unknown` with a public error text (`error_ref`), never a 500 for the page.
- **Spend per LLM connection = `llm_call_log.account = connection_key`**, the same attribution the monthly connection
  budget uses (`cost_guard.connection_budgets`), so the row and its budget never disagree. Rows whose account names no
  connection (older rows before the S6 connection keys) are shown as one "Other LLM calls (no connection)" line and
  counted in the totals, so the page total matches the ledger.
- **Jev spend** is read from the ledger (`provider = 'typesafe'`) in my own month query, not through
  `cost_guard.day_spend('jev')`: that entry is added by the parallel A1a slice and this PR must not depend on it.
  After A1a both read the same rows.
- **Jev health** = the last 24 h of `shared.decision_log` (calls, errors, mean latency of uncached calls), read with
  the `created_at` index. It is the only source with a latency today.
- **Geoapify credits** use the geocoder's own rule (`coalesce(credits, requests)`, UTC day) and its own limit
  (`GEOAPIFY_DAILY_CREDIT_LIMIT` via `services/places/geocoder`), so the page says exactly what the guard enforces.
- **DataForSEO balance** = the newest stored snapshot (daily check); never a live call. The threshold is the same env
  value as `GET /admin/dfs-balance`.
- **Trace bounded by the run window.** `decision_log` (no `job_id` index until 319) and `geo.geocode_call` (no job
  index) are read only between `job.started_at` and `finished_at` (or now) + 1 minute; `started_at` keeps the first
  attempt's start, so retries are covered. A job that never started reads neither. `count(*) OVER ()` gives the true
  totals even when a source is cut at 500 rows.
- **Jev shows once in the trace (review fix).** `decide()` logs one Jev call twice under the job: a `typesafe`
  `llm_call_log` row with the whole call cost and one `decision_log` row per question with its share
  (`shared/llm_client/decide.py`). The trace LLM read drops `provider = 'typesafe'`, so Jev events and cost come
  only from `decision_log` (per question, with zone and latency) and the job total counts Jev once. Same rule as the
  Providers tab, which keeps Jev out of the LLM rows.
- **TripPlanner "AI paused"**: CIS cannot read TripPlanner's own counter (`tripplanner.llm_spend_daily`), so the only
  read-only signal today is CIS's own spend read failing. The card now carries `ai = {paused, reason}`
  (`spend_unreadable`), default `{paused: false}`. `card.status` keeps its ok/degraded/down/unknown meaning (the
  overview copies it), so `ai_paused` is a field, not a status value. Cache key bumped to v4.
- **Trace link format** `?trace=job:<uuid>` (design: `job:` / `tour:`), parsed strictly; a tour trace comes later.
- **Bedrock rows are named by account ID** through `lib/llmConnections.connectionName` + `useAwsAccounts`, trace
  accounts through `lib/awsAccounts.accountName`; no account key or ID in code.

## Changed (vs the plan text)

- Plan said "`platform_apps` TripPlanner card status `ai_paused`". Implemented as `card.ai.paused` (see Decisions),
  because `status` feeds the shared health rule of the overview.
- The page has a Guide tab (guide.ts + guide.vi.ts) so the guides test covers it; registered in `guides.test.mjs`.
- No provider detail drawer and no "Test" button yet: those belong to the Providers tab of step 3/5 with the registry
  v2 columns (failure domain, last probe). Mapbox and Guardrails rows are not shown: they write no ledger yet.

## Tradeoffs

- One month-range scan of `llm_call_log` per page load (grouped by provider and account; the created_at index serves
  it). The existing connection-budget read already does the same scan; the page refreshes every 2 minutes only while
  visible.
- `decision_log` 24 h aggregate on each load: bounded by the created_at index, a few thousand rows a day today.
- No per-call latency or refused rows until ledger v2; the UI says so (guide + trace note) instead of hiding it.

## Should know

- Integration test `tests/integration/test_aa804_ai_gateway_sql.py` runs every query on the migrated schema (July 2024
  fixture rows, deleted after). Passed locally on a scratch PostgreSQL 16 without pgvector (conftest swallows the
  migrations that need it; every table this test reads was created). CI runs it on its postgres:15 service.
- `docs/api/openapi.json` regenerated with the pinned fastapi 0.161.1 / pydantic 2.14.1 (only the two new paths).
- The Apps-board note "serves the simple, non-AI version" is true once TripPlanner's fail-closed change (AA-642 S0,
  lane B1a) is deployed; until then TripPlanner may still fail open.
- Live check: the trace drawer needs a real job id with calls (Jobs › a finished S1 or place job › Open trace).

## Decisions

- **`GET /admin/ai-gateway/budgets` reads, never writes.** Tiers: `provider` (spend_budget scope `global`), `job`

  `job:place_extract` "Cap reached" while the guard still let it run.

- **Kit rebuild:** raw `<select>`/`<input>`/`<button>`/`<table>` replaced by kit `Select`, `Input`, `IconButton`,
  `Switch`, `ChipButton`, `SegmentedControl`, `DataTable`, `KpiTile`, `Field`, `DateField`; the eslint-suppressions

# AA-804 UI part 3 + AA-1015 Done-when 3 — Calls tab, tour trace, kit timeline, Paid sources tile, merged spend tab (slice C3, S262 wave 3)

Branch `feat/aa-804-ai-gateway-calls`. Plan: S262 build plan §2 Wave 3 "C3". Root PR (report catalog FI-03 channel) on
branch `docs/aa-804-report-catalog-spend-tab`. No migration (needs 319, applied), no paid call, no change to
`shared/llm_client/**`.

## Decisions

- **Calls API in its own module** (`api/services/ai_gateway_calls.py`), reusing the trace's row columns and event
  builders (`ai_gateway._LLM_COLS` …, `EVENT_OF`), so a Calls row and a trace event have the same shape plus `id`
  and `tenant_id`.
- **Sources:** `llm` (llm_call_log without Jev's `typesafe` rows), `jev` (decision_log), `dfs`, `geocoder`, `crm`.
  Jev is read from decision_log only, the same rule as the trace (one call listed and counted once). The geocoder is
  included although the plan named only DFS + decision_log: it is a paid ledger with a job id and a tiny table.
- **A filter a ledger cannot answer leaves that ledger out** (`sources_for`): `stage` drops the geocoder,
  `status=truncated` keeps only the LLM log, `provider=jev` keeps only Jev, `app=crm` keeps only the CRM, a job or
  tour filter drops the CRM (its rows carry crm.job ids). decision_log / geocode_call have no status column: derived
  `error` (zone error or an error text; every request failed) else `ok`.
- **Keyset on (at, id) descending, id = `<source>:<row id>` compared byte-wise.** Every key expression is
  `COLLATE "C"` and Python sorts plain `str`, so SQL and the merge agree; one transaction's batch rows share
  `created_at` (now()), so ties are real and are never skipped or repeated (integration test walks a job one row per
  page). Each ledger reads `limit + 1` rows from the cursor down with its created_at index; the merge cuts to
  `limit` and returns `next_cursor` only when a source had more.
- **CRM rows** through crm.ops.v1 1.6 `GET /llm/calls` with the staff member's own token
  (`platform_apps.crm_llm_calls` → `_crm_ops_get`, the jobs-summary pattern). The CIS cursor maps onto the CRM keyset
  (`<at>~<call id>`): `crm:` sorts before every other source, so a cursor on another source at time T asks the CRM
  with the max uuid at T. On any problem the list has no CRM rows and `crm` carries the reason plus the CRM's
  aggregate for the window (`GET /llm/usage`, `crm_llm_usage`). The provider filter is applied to CRM rows after the
  read (the contract has no provider parameter).
- **CRM rows stay inside the window (review fix).** The contract's `from` / `to` are whole UTC days, so the first
  page also sends a cursor at the window's end (`<until>~<max uuid>`) and every CRM row is checked against
  `[since, until]` before the merge; rows older than `since` only ever come last (newest-first keyset), so dropping
  them never hides a later in-window row. When the provider filter leaves a CRM page short and the CRM has more rows
  in the window, the next CRM page is read, at most `CRM_MAX_PAGES` (5) reads; at the cap (or when a later read
  fails) the merged page stops at the last CRM row read (the "floor": rows of other ledgers below it wait) and
  `next_cursor` resumes right after it. `crm.rows` counts the CRM rows on the merged page.
- **CRM `account` only for a vendor connection (review fix).** The CRM's connection keys (`bedrock`, `bedrock_role`,
  `bedrock_guardrails`, `stub`) are not CIS account keys and `accountName()` would show "Retired account"; a CRM row
  names its account only for `openai-direct` / `anthropic-direct` (`VENDOR_CONNECTION_LABELS`), the key stays in
  `detail.connection_key`.
- **The CRM aggregate is labelled with its whole UTC days** (`from` .. `to` in the payload): it can cover more than
  the selected period, and the tab and the guide say so.
- **Tour trace** (`GET /trace?tour_id=`, exactly one of job_id / tour_id): the tour's jobs
  (`shared.job.payload ->> 'tour_id'`, newest 200, one seq scan of a small table), then per ledger: LLM = union of
  `tour_id`, `job_id = ANY(jobs)` and `content_piece_id` of the pieces those jobs wrote (three index reads); DFS =
  `tour_id OR job_id`; decision_log and geocoder by the jobs. No 404 for a tour (the id is not checked against a
  catalog table); an empty trace says so.
- **Job trace now reads decision_log by its job index (319)**, no run window; only the geocoder (no job index) keeps
  the window. Events carry the ledger v2 `status`, `error_class`, `latency_ms`, `attempt_no`, `job_id`, `app`; the
  outcome is the v2 status when not ok. The old note `refused_calls_not_logged` became `rows_before_ledger_v2`
  (shown only when a listed LLM / DFS row has no status).
- **Kit core:** `TraceTimeline` (ordered list, tone dot on a rail, offset from the first event, label / title /
  detail / amount / duration, optional button rows, scroll box) and `LatencyStrip` (one bar per call, role=img with
  the p50 / p95 / slowest summary as its label, `latencyStats` nearest rank). Their words are in
  `kit.messages.ts` (EN + VI). MANIFEST regenerated; `kit-sync.sh --dry-run --from-local` checked for portal,
  crm-web, booking (full) and tripplanner (tokens: only MANIFEST changes).
- **Calls tab filters live in the address** under `c_` keys (kit `useUrlFilters` + `FilterBar`), so they never meet
  the page's own `tab` / `view` / `trace`. Job and tour filters are set from a row ("Only this job") or a link
  (`callsHref`), never typed (lesson S254: no UUID inputs).
- **Trace links:** tour panel (`TourDetailPanelV2`, admin only, since AI providers is admin only) → `?trace=tour:`;
  decisions log renders `job_id` (first 8 characters) linking `?trace=job:`; the trace drawer links the job's Calls.
- **Overview:** the provider cost table became the "Paid sources" tile: three numbers with their sources (spent
  today over every provider, this month, providers at or past a daily cap's alert level) and a link to AI providers.
  The aa858 count stays at 21 (three columns → three tiles); the overview raw-table suppression shrank by one.
- **Cost Operations:** `llm`, `dfs`, `jev` tabs → one tab `spend` ("AI & data spend") with a SegmentedControl view
  (`?view=llm|dfs|jev`, default llm). Old `?tab=llm|dfs|jev` links are replaced in the browser
  (`RETIRED_COST_OPS_TABS` → `costOpsSpendHref`, exactly one `tab`); `/admin/llm-usage` without a tab now goes

- **AA-1015 Done-when 3:** the TripPlanner card's `spend_today` gained `stage_caps` (one row per online stage with

# AA-804 / AA-1016 / AA-1017 / AA-1018 / AA-900 UI follow-ups + the 10 live UI findings (slice C4, S262 wave 4)

Branch `feat/aa-804-gw-ui-followups` (from `feat/aa-804-ai-gateway-calls`, PR #1205; rebase on `main` after it merges).
Plan: S262 build plan §2 Wave 4 "C4"; findings F1–F10: root `docs/audits/2026-10-31-S262-evidence/AA-804/findings.md`.
No migration (reads 321 / 322 defensively), no paid call, no change to `shared/llm_client/**`.

## Decisions

- **Tenant AI budget API in the gateway router** (`api/services/tenant_ai_budget.py`): `GET` (spend.read), `PUT` and
  `DELETE` (spend.write) `/admin/ai-gateway/tenant-budgets/{tenant_id}`. A PUT replaces the whole row (every field,
  defaults of migration 321 when left out); a DELETE puts the tenant back to "no budget" (the plan names only a PUT:
  without a DELETE the live "set then revert" could not return to the starting state, which is no row). Each write is
  one transaction: tenant check, the old row `FOR UPDATE`, the write, one `acp_shared.audit_log` row
  (`tenant_ai_budget_set` / `tenant_ai_budget_cleared`, details `{before, after}`). Table missing or the column grant
  missing → 503 with "CIS migration 321 is not applied; nothing was saved"; unknown tenant → 404.
- **Column names** of `shared.tenant_ai_budget` / `shared.prompt_version` come from migration 321 itself (PR #1204):
  the live schema reference does not list them until 321 is applied.
- **Month spend of a tenant** = Tenant 360 › Cost's rule (`admin_tenant360._COST_WHERE`: this UTC month, shadow rows
  out by `is_shadow` with the older `quality_signal` flag as fallback), one grouped query for the whole tier.
- **State of a tenant budget**: `unlimited` (no amount), `ok`, `alert` (≥ alert %), `approval` (≥ approval % with
  hard stop on: new T-stage jobs would wait once enforcement ships), `over` (≥ approval % without hard stop).
  Stored and shown only: the gateway check is a later slice (plan A4).
- **"Last changed" (F5)**: `ai_gateway.actor_view` classifies `updated_by`: an admin_users id → the directory's
