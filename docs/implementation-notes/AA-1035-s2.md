# AA-1035 — R2 slice 2 (S268 lane aa1035-r2s2): view-as, Assignments page, logged Lab read, staff bell

Sources: root ADR 0019 d4 / d5 and "Settled by the tech lead" item 1, the matrix in root
`docs/audits/2026-11-03-S265-ecosystem-restructure/clarifications.md` section 3, Linear AA-1035 (slice 1 comment of
S267), `docs/implementation-notes/AA-1035.md` "Follow-ups (slice 2)". Slice 1 (roles, `require_tenant_scope`, CIS
362-364) is live. **No migration in this slice**: CIS 364 already created `shared.staff_tenant_assignment` and
`shared.staff_view_as_session`; request rows go to `acp_shared.audit_log`. The Booking notes need nothing from Booking
for slice 2.

## Decisions
- **View as = a short-lived, read-only tenant token + a gate, not a proxy of staff routes.** "View as partner" must show
  what the partner's own API answers. `POST /admin/tenants/{tenant_id}/view-as` (capability `tenant.view_as`: admin,
  customer_success, support; `require_tenant_scope`) writes the session row and mints a tenant JWT
  (`api/core/view_as.py mint_token`): `role` tenant, `csr` viewer, `client` portal (never metered as the tenant's API
  calls), `amr` staff_view_as, `vas` = session id, `stf` = staff id, `exp` = the session expiry. The existing tenant
  read routes accept it unchanged.
- **The gate is an allow-list, not "GET only".** `GET /v1/slate` enqueues a paid `t7_slate` job, exports stream files,
  `/v1/integrations/*` show channel credentials. `view_as.READ_ROUTES` holds 12 side-effect-free reads (quota,
  marketplace, my tour versions, one version, content reviews, one piece, publish log, pending, notifications, facts,
  members, activity). Every other method or path: 403 `view_as_read_only`, before any route runs
  (`api/middleware/view_as.py`, pure ASGI around the tenant role middleware and the rate limiter). Defence in depth:
  `tenant_role.enforce` (called by the two dependencies that accept a tenant JWT) refuses a view-as payload outside the
  list too.
- **Per-request re-check.** Each allowed request re-reads the session (open: not ended, not expired), the staff row
  (active, CURRENT role from the DB, which must still be the start role, see below) and the scope
  (`tenant_scope.in_scope`): removing a customer success member's assignment ends their view at the next request (401
  `view_as_ended`, outcome `refused_out_of_scope`). An expired-but-open row is closed as `expired` the first time it
  is touched.
- **The session is bound to the role it was started with (S268 fix round 3, review finding).** Staff authorisation
  takes the role from the Cognito group (ADR 0006; drift with `shared.admin_users.role` is only logged as
  `staff_role_drift`), but the gate read the DB role: a member demoted in Cognito whose row still said admin kept a
  view whose assignment had been removed (scope `all`). Now the start signs its authorised role (the x-admin-role the
  bearer middleware rewrote from the groups) into the token as `srl`; the gate computes scope and `ROUTE_CAPS` from
  `srl` only and ends the session (`revoked`, cause `role_changed`; `role_lost_view_as` when the new role lacks
  `tenant.view_as`) when the DB role (reviewer alias read as content) or the role the BFF forwards differs from it. The
  start refuses (409, before any row) a member whose DB row already differs from the sign-in role: that session would
  end at its first read. A token without a valid `srl` (missing, not a staff role) is refused like bad claims (401).
- **The BFF forwards the reader's verified role on every read** (`x-view-as-staff-role`, `lib/viewAs.ts
  VIEW_AS_ROLE_HEADER` = `auth.role` from `requireAdmin`). It is not a credential: it can only END a session (a role
  other than `srl`), never widen one, since scope and reads come from the signed `srl`. A session whose member's
  group changed mid-session (DB row unchanged) is thus ended and logged at the next read. When the role differs from
  `srl`, the BFF forwards any allowed read path (`viewAsForward`), even one the new role may not make, so the API ends
  and logs the session instead of the BFF answering a silent 403.
- **"Every request logged" means no unlogged read.** The audit row of a served read is written BEFORE the read runs;
  if it cannot be written the read is refused (503). Refusals are logged best effort (the refusal is answered
  anyway). Rows: `acp_shared.audit_log`, action `tenant.view_as_request`, resource `staff_view_as_session` / session id,
  actor `admin:<staff>`, `actor_type` staff, `route` = the matched allow-list template, `status` NULL for a served read
  (not known yet) or the refusal status, `details` {method, path, outcome, query_keys} (never query values).
  `http_method` stays NULL: the column's CHECK (CIS 248) takes only write methods. Start / end:
  `tenant.view_as_started` / `tenant.view_as_ended` (session, minutes, ticket, end reason; never the reason text,
  which is free text and stays in the session row).
- **One open session per staff member.** Starting a new one ends the caller's other open sessions (`ended`, or
  `expired` when past). The BFF holds one cookie, so an older token would be orphaned anyway.
- **End**: own session `ended`; an admin ending another member's session `revoked`; another member's session is a 404
  for non-admins (same as unknown). Idempotent.
- **Refused targets**: the AA internal tenant (409, not a partner) and an offboarded tenant (409). The machine (main
  secret, no role) never reaches the view-as routes (POLICY); a staff call without a staff id gets 403.
- **The reads depend on the role (S268 fix pass, review finding).** One list for every role let support read
  `/v1/billing` (plan price, overage, quotas) and `/v1/quota` (plan tier, rewrites used), which its own staff pages never
  show (S265 role table: support may not see billing; `staff_authz.py`: "never plans, billing, usage, cost").
  `/v1/billing` left the list (no view-as page read it). `view_as.ROUTE_CAPS` names the extra capability a read needs on
  top of `tenant.view_as`: `/v1/quota` needs `tenant.read` (admin) or `tenant.book.account.read` (customer_success).
  The gate checks it against the session's start role (`srl`, kept equal to the current DB role since round 3;
  `session_open(conn, claims, template)`),
  answering 403 `view_as_not_for_role` (logged, outcome `refused_route_not_for_role`). The start answers
  `allowed_reads` for the caller's role; the BFF mirror (`VIEW_AS_ROUTE_ROLES`) refuses the same reads and the page hides
  the plan card for support. Rule: view-as never shows a role more than its own staff pages.
- **The token never reaches the browser.** The admin BFF (`frontend/app/api/view-as/route.ts`) strips it from the API
  answer and keeps it in the httpOnly cookie `aa_view_as` (path `/api/view-as`, SameSite=Strict, Secure in production,
  at most 60 minutes). `frontend/app/api/view-as/v1/[...path]/route.ts` exports GET only, forwards only
  `VIEW_AS_READ_ROUTES` (a mirror of the backend list; a unit test keeps them equal), and only for the signed-in staff
  member whose id is the token's `stf` (a shared browser never reuses another member's view).
  S268 fix pass (review finding): the generic `/api/admin/[...path]` proxy also forwarded `POST tenants/{id}/view-as`
  (the "tenants" write rule lets the tenant desk through) and streams the body back, so a page could get the raw token.
  Two guards now: the generic proxy refuses that path for every method and role (`lib/viewAs.ts isViewAsStartPath`,
  before any upstream call), and the backend answers the start only with the request header `x-view-as-client: bff`
  (403 `view_as_bff_only` before any row otherwise). The generic proxy builds its upstream headers from a fixed list and
  never sets it, so a future proxy that forgets the path check still gets no token.
- **One tenant rule for the start and every request (S268 fix round 2, review finding).** `view_as.tenant_refusal`:
  the AA internal tenant (sentinel id or `kind = internal`) -> `internal`; `cancelled_at` set or status offboarding /
  closed -> `offboarded`; `is_active` false or a status outside trial / active / past_due (suspended, lead, applied) ->
  `inactive`. The start answers 409 with the matching sentence; the gate reads the tenant columns in the same session
  query (`SESSION_STATE_SQL` joins `shared.tenants`) and ends the view (401 `view_as_ended`, outcome
  `refused_tenant_inactive`). A suspended tenant is now refused at the start too: its reads only ever answered the
  tenant limiter's 403 "Tenant is deactivated", so a session there showed nothing.
- **A lost right ends the session for good.** Before, staff_inactive / role lost / out of scope refused the request but
  left the row open (the session list still showed it open, and a restored assignment brought the view back). Now
  every such refusal closes the row (`view_as.close_session`, `CLOSE_SQL`: `revoked`, or `expired` past its expiry)
  and writes one `tenant.view_as_ended` row in the same transaction (actor `system:view_as_gate`, details
  `end_reason`, `cause` = the refusal reason, `session_staff`). The `end_reason` column keeps its CIS 364 vocabulary
  (ended / expired / revoked; no migration in this slice): the precise cause lives in the audit row. The row-level
  `WHERE ended_at IS NULL` makes the close happen once: two racing requests write one ended row. A close that fails
  (DB blip) is best effort: the request is refused anyway, the next request retries. `view_as_not_for_role` (403)
  does not end the session (the role may make the other reads).
- **Every path that ends a session writes one `tenant.view_as_ended` row under that session's id** (`view_as.ended_audit`
  builds it): the end route (cause `ended_by_staff` / `revoked_by_admin`), a new start closing the caller's other open
  sessions (`END_OTHERS_SQL` now returns each closed session's tenant and end reason; cause `replaced`,
  `replaced_by` = the new session; their rows are written before the start row, all last in the transaction for the
  audit chain lock), the gate (expiry and lost rights, above). A session that expires and is never touched again has
  no end row (nothing ends it; it reads as expired).
- **Desk-role bell is tenant scoped.** `_NOTIF_ROLE_SCOPE` adds `notifications.tenant_id IS NULL OR = AA internal OR
  <scope>`; `<scope>` comes from `tenant_scope.tenant_scope_sql(scope, staff_id, column)`, the SQL form of `in_scope`
  (same book and pool subqueries; `all` -> TRUE for finance; no / invalid staff id -> FALSE). The staff id is
  `staff_id_of(request)` (the verified Cognito id, or `x-admin-user-id` under the main secret), read only for a desk
  role. It is inlined as a literal after re-validation as a UUID (the four routes number their parameters
  differently; a constant predicate keeps `notification_scope` a plain string as before). Mark one / read-all use the
  same predicate, so a desk member never marks another book's row.
- **Gate order: the gate stays outermost; it gets its own per-session rate limit first.** `rate_limited` (Redis
  `view_as_rl:<session>:<minute>`, `VIEW_AS_RPM` = 120) runs before the allow-list check, the session query and any
  audit row: over the limit -> 429 `view_as_rate_limited` with Retry-After, no audit row (a refused request may be
  limited before it is logged), one warning line per session and minute. Redis down: fail open (checks and audit rows
  still run). A served read is still logged before it runs; the tenant limiter inside may answer 429 after that row
  (logged, not served: never the reverse). Moving the gate inside the tenant limiter was rejected (see Tradeoffs).
- **Banner**: sticky, amber, `role=status`: tenant, read-only sentence, live countdown, reason, ticket, End view. The
  page `/admin/tenants/view-as` shows the partner's reads in tabs (overview: quota + marketplace; tours, content,
  published, notifications, members, activity). No control on the page writes.
- **Logged Lab read for ai_ops = its own capability `lab.tenant_text.read`**, not `tenant_content.read` (which would
  open Tenant QA, Content Trace, the A4 logs and Tenant 360 text). It sits only on the tenant-text GETs of
  `/admin/writing-memory/*` (POLICY `_LAB_TEXT_READ` = any_of(tenant_content.read, lab.tenant_text.read)); the Tenant
  360 voice route (`/admin/writing-memory/tenants/{tenant_id}/voice`) stays `tenant_content.read` (not a Lab page).
  Each such route declares `LAB_TEXT_LOGGED`; for a caller that passes only through the Lab capability (ai_ops) it
  writes `lab.tenant_text_read` (role, route, path, tenant filter, query keys) before the read, 503 when it cannot.
  admin / content_lead / tenant_qa read tenant text in their own right and are not logged here (unchanged).
- **Bell**: new capability `notifications.read`, held by every role, on GET `/admin/notifications`,
  `/admin/notifications/count` and the two PUTs (the viewer still never marks read: read-only role). The scope: ops.read
  roles every staff row, content.read roles the content rows (as before), the desk roles (customer_success, support,
  finance) only rows whose `target_roles` name their role and never a platform.* or spend alert. No writer targets
  them yet, so their bell is empty, but it no longer answers 403.
- **Assignments page** (Tenants › Assignments, admin / customer_success / support): `GET /admin/tenant-assignments`
  (tenant.read | tenant.book.read, filtered by `tenant_scope_filter`: every partner tenant of the scope with owner /
  backup / support and the pool flag) and `GET /admin/tenant-assignments/staff` (tenant.assign: active admin /
  customer_success / support staff, name + e-mail). Writes stay the slice 1 per-tenant PUT / DELETE (admin only); the
  drawer shows add / remove only to `tenant.assign`, offers `owner` only when the tenant has none.
- **E2E A10b (proposed A10b-2)**: the Dev-only E2E CIS admin may start / end a view-as session on a synthetic tenant
  only (`is_canary IS TRUE`, checked in the routes before any row), so the orchestrator's admin-evidence run can show
  the banner and the audit row. The session it opens is read-only like any other.

## Changed (vs. the slice brief)

  member whose role works no tenant book (content, finance, ai_ops...): such an assignment granted nothing and showed
  as noise on the page.

  the new routes, the Lab reads for ai_ops and the bell for the desk roles changed) plus

  which calls EVERY route of the app (all methods, all prefixes, 400+) with a view-as token and expects 403 + one audit
  row each, and `test_every_new_staff_route_x_every_role_matches_the_matrix`.
- `docs/api/openapi.json` regenerated with the pinned fastapi 0.161.1 / pydantic 2.14.1 (additive only).

- S268 fix pass: `/v1/billing` dropped from the view-as reads; reads per role (`ROUTE_CAPS`); start only through the
  BFF (header) and refused by the generic admin proxy. No openapi change (no route signature changed).
- S268 fix round 2: the gate re-checks the tenant (the start's rule) and ends the session on any lost right; every end
  path writes a `tenant.view_as_ended` row per closed session; the desk-role bell is tenant scoped; the gate has a
  per-session rate limit in front. The start now also refuses a suspended / not-live tenant and a `kind = internal`
  one (409). No route signature changed: no openapi or snapshot regeneration.
- S268 fix round 3: the session is bound to its start role (`srl` claim), the gate ends it on `role_changed`, the
  start refuses a DB / sign-in role mismatch (409), the BFF forwards `x-view-as-staff-role`. `mint_token` takes
  `start_role`; `STAFF_ACTIVE_SQL` became `STAFF_STATE_SQL` (is_active + role). No route signature changed: no
  openapi or snapshot regeneration.

## Tradeoffs
- The BFF-only header is not a secret: anyone who can call the API with a staff credential could set it. It closes
  the path that matters (a page or script on the admin origin going through the generic proxy, which never forwards
  it); the staff credential itself never reaches the page (httpOnly session). Moving the token to a response header
  the proxies strip was weighed and left out: it changes the API Gateway response path for no extra safety here.
- The view-as page is an admin page over the partner's own API reads, not the partner portal itself (AA-Partner
  `portal/` / `web/` have no staff session; root ADR 0019 d6 merges them in R3). It shows the same data the partner
  sees for the allowed reads, without the partner's layout. A portal-side staff session would need a Partner change
  and a cross-app session; out of this lane.
- The rate limiter still looks up the tenant (revocation) and counts view-as reads in the tenant's own RPM bucket. Since
  round 2 a suspended tenant cannot be viewed at all (start 409, an open view ends), so the limiter's 403 no longer
  meets a view-as read; a staff page load (about ten reads) in the partner's bucket is negligible. Exempting view-as
  tokens from the tenant bucket was not worth a new bypass in the limiter.
- Gate order (round 2, review finding 4): putting the gate inside the tenant limiter would rate limit refused requests
  before they are logged, but the tenant role middleware sits between the two (AA-979: it wraps the limiter), so a
  view-as write would get its 403 `studio_role_forbidden` (csr viewer) unlogged, and the tenant bucket would let the
  partner's traffic 429 the staff view and the staff view spend the partner's budget. A per-session limit at the gate's
  entry bounds the same work (session query + audit insert, which the chain trigger serializes) without either cost.
- Start role in the token, not in `shared.staff_view_as_session` (round 3): the table has no role column and this
  slice ships no migration; the claim is signed with the tenant JWT secret, so it cannot be changed without minting a
  new token, and the session row is still the authority for open / ended. A column would also let the end route and
  the sessions list show the role; left for a later migration if wanted.
- Ending on any role change rather than "evaluate with the lower of the two roles" (round 3): roles are not totally
  ordered (support has the pool, customer_success the plan read), so "lower" is not defined; ending the view is the
  simple, safe answer, and the member starts a new one under the new role.
- Per-request DB checks (session + role + scope, 2-3 small queries) and one audit insert per read: view-as traffic is
  a handful of staff page loads, so the cost is negligible; the audit chain trigger serializes inserts, fine at this
  volume.
- support sees, on a pooled tenant, the names of other staff assigned as backup / support there (internal staff
  names only).
