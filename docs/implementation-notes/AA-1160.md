# AA-1160 — Planner leads fall back when the CRM agency does not exist yet (CIS part)

Linear: AA-1160 (S289). Evidence of the gap: root `docs/audits/2026-11-19-S285-session/aa1139/` (S285 live check of
the agency app's Trip planner module). Other repos of the lane: AA-TripPlanner-Web (route, re-route, planner locale and
theme), AA-Partner (the module's CRM note), root (contracts, DM-7.1 retention row).

## Decisions

- **How CIS knows a CRM agency exists without reading CRM tables (root ADR 0008a).** The CRM's entitlement feed
  (`crm_entitlement_pull`) reads the tenant.entitlements.v1 snapshot `GET /tenant/v1/tenants/{id}/account` only for an
  agency it holds (active or locked; AA-Partner `app/cis/entitlement_feed.py` `held()`), on every account event that
  names the tenant and in an hourly pass over all of them. So a snapshot read by the CRM M2M client is CIS's proof of
  the agency. The CIS CRM onboarding (AA-1116, `crm_onboarding.onboard`) is the second source: it sees the agency exist
  (CRM `GET /tenants/{id}` 200) or creates it. Both write `shared.tenant_crm_agency` (CIS 474, source `crm_pull` /
  `crm_onboarding`).
- **Liveness, not "seen once" (review fix pass, S289).** Reviewers found that a marker with no expiry kept a deleted,
  offboarded or locked CRM agency on crm forever: TripPlanner then refused new leads (stale beacon, 503) and its daily
  re-route counted the pending crm leads as `kept_crm`, so they expired undelivered (the S285 failure again). Fixed on
  both sides:
  - TripPlanner routes each lead on its CRM pull beacon only (the CRM lists only an agency it can serve: active and
    routed to it; a locked, offboarding or deleted agency raises before the list call). It needs no CIS marker, so the
    catalog view no longer carries `crm_agency` (only the fallback route), and catalog_owner holds nothing on the table.
  - CIS counts a sighting only while `last_seen_at` is inside the setting `cis.tenant.crm_agency_seen_hours`
    (Platform › Settings, area tenant, int hours 2-168, default 3, maker-checker; seeded by 474; the S279 rule: no
    window literal in a view or in code). The CRM re-reads every agency it holds at least hourly, so a live agency
    stays inside and a deleted or offboarded one ages out. `REFRESH_AFTER_S` (300 s) stays a write throttle only
    (`technical-constant`).
  - Known gap: a locked CRM agency is still read hourly by the CRM (it must see the CIS account to unlock it), so CIS
    keeps showing crm for it while TripPlanner already takes the fallback. Closing it needs the CRM to say the
    agency's status on its snapshot read (a contract change), left as a follow-up.
- **The view keeps `lead_channel`'s 390 meaning** (crm while crm.core is live) and appends the fallback route
  (`fallback_channel`, `fallback_webhook_url`, `fallback_email`). Changing `lead_channel` itself would flip every CRM
  tenant to its fallback the moment 474 is applied. TripPlanner decides: crm only with a fresh CRM pull (its beacon),
  else the fallback.
- **`effective_channel` in the module (tenant.addons.v1 1.2)** is crm only with crm.core AND a sighting inside the
  window. No new field
  (the contract's `TripPlannerModule` is `additionalProperties: false` and the CRM validates it); `crm_core` keeps its
  meaning. Tenant 360's lead route answer gains `crm_agency` (admin-only dict, no contract) and the section says
  "no live CRM agency lately: the route below applies".
- **Migration split for the replay**: Part A (the table and the setting seed) is replayed by the conftest (`_replay_parts.py`), so every
  integration test that runs `module_view` has the table; Part B (the catalog view) only in
  `tests/integration/test_aa1160_migration_474.py`, like 429 / 438.

## Tradeoffs

- A snapshot GET now writes (one throttled upsert, at most one row every 5 minutes per tenant). Accepted: the CRM is the
  only reader of this route, the write is best effort and the alternative (a new CRM → CIS call) needed a new contract
  operation and a CRM change for the same fact.
- Up to one CRM entitlement slot (2 minutes) after a new agency, or one reconcile pass (1 hour) after the deploy for
  agencies that already exist, before `crm_agency` is true. TripPlanner does not wait for it (its beacon), so only the
  agency app's "Now:" badge can say the fallback for that hour.
- A window means a deleted agency still shows crm in CIS for up to `cis.tenant.crm_agency_seen_hours`; TripPlanner
  already takes the fallback within its beacon window (about 10 minutes), so no lead waits on the CIS label.
