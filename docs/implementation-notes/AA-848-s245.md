# X2 RLS catalogue guard (CIS side), S245

Rules module `tests/integration/rls_catalogue_rules.py` (canonical; AA-CIS-Infra keeps a byte copy at
`db/rls_catalogue_rules.py`), integration guard `tests/integration/test_rls_catalogue_guard.py`, unit tests
`tests/unit/test_rls_catalogue_rules.py`.

## Decisions

- **One rules module, two inputs.** The rules are pure functions over the format-2 schema dump shape that
  AA-CIS-Infra `db/schema_dump.py` already writes. CIS CI builds that shape from the replayed DB with
  `CATALOG_SQL` (the same SQL shapes as the dump's `QUERIES`, only the keys the rules read) and `dump_from_rows()`.
  The nightly Dev run feeds the real dump. No new catalog query was needed on the Infra side.
- **Canonical copy lives here, Infra copies the bytes.** It follows the migration-copy pattern (owner repo first,
  byte-identical copy in Infra, Copy Guard compares). CIS CI needs the rules at PR time, so CIS owns the file.
- **Rules beyond a–e.** The S241 scope extension added `p` (no grant to PUBLIC on a schema, relation or column)
  and `g` (a grant to another owner's role, with a temporary allowlist until the owners.yaml registry and rule f).
  The lane brief also asked for an allowlist of the `cis_app` `USING (true)` set. That became rule `t`: a
  permissive policy whose USING or WITH CHECK is just `true`. It allows the X1 parity policies
  `<table>_cis_app_all TO cis_app` and `<table>_cis_owner_all TO cis_owner` in CIS schemas by name pattern, and
  any other one must be allowlisted.
- **Rule a needs one `app.tenant_id` policy, not all.** The `cis_app` / `cis_owner` USING(true) parity policies
  sit next to the tenant policy and do not count against rule a.
- **Rule a cannot be allowlisted for a table the tenant pool can read.** If `aa_app_user` holds any grant on a
  tenant_id table without a tenant policy, the finding is `hard` and no allowlist entry covers it. The 31 Dev
  rule-a entries are all `cis_app`-only today. The reason text claims "no tenant-pool grant", and this keeps that
  claim true.
- **Rule b "new schema"** is a policy-name allowlist that grandfathers the 8 legacy `tenant_isolation TO PUBLIC`
  policies. Every other TO PUBLIC policy fails.
- **Rule d** flags each `current_setting('app.tenant_id' …)` call that is not the first argument of `NULLIF(`.
  It does not try to parse SQL.
- **Rule e** keys include the target (`schema.table:constraint->ref_schema.ref_table`), so the 10 TripPlanner FKs
  are one precise wildcard entry (`tripplanner.*->shared.destinations`). A schema that is in no owner's list fails
  rule e when it has an FK, so a new schema must be added to `SCHEMA_OWNERS` (mirrors owners.yaml).
- **Allowlist keys may use `*`** (fnmatch). This keeps the column grants of 180/216 and the `catalog.*` contract
  grants to one line each. Stale entries (matched nothing) are reported, not fatal: the shared allowlist covers
  Dev, and some Dev objects are absent from the CI replay.
- **CI-only allowlist** lives in the test file, not the shared module. It covers the 6 legacy tables the replay
  keeps and Dev dropped (`X1_CI_ONLY_LEGACY_RLS`: pre-NULLIF `tenant_isolation TO PUBLIC`). A CI-only entry
  that stops matching fails `test_ci_only_entries_are_used`.
- **Seeded violations in test code, not migrations.** One parametrised test per rule creates a violating object
  inside a transaction, checks the guard reports it, and rolls back. The red-run evidence for the Done-when uses
  a separate throwaway commit with a seed migration that is never merged.
- **Isolation probe on an RLS-touching PR.** No new trigger. The CIS Integration Tests job already runs
  `test_aa817_rls_tenant_isolation` and `test_x1_cis_app_privileges` on every PR, and this guard joins them. This
  PR's Integration Tests run is the evidence.

## Changed

- Nothing in `api/`, `services/` or `shared/`; no migration. Tests only.
- Out of scope, as the issue says: rule f (owners.yaml grant registry, after AA-826), the PII-tag lint (needs
  Nghiệp's OK), and function `EXECUTE TO PUBLIC` (the PostgreSQL default; functions' ACLs are not in the dump).

## Tradeoffs

- `ROLE_OWNERS` / `SCHEMA_OWNERS` are hand-mirrored from owners.yaml. The Infra registry test checks the
  schema map against owners.yaml. Roles that belong to no app (master, db_migrator, the CI-only `app_user`) are
  ignored by rule g.
- The rule-a reasons for the 31 Dev tables describe what the table is from its name and grants. The guard
  enforces only the "no tenant-pool grant" part. Owners can make them more precise later.

## Should know

- Dev baseline (dump of 2026-10-19 13:00Z, CIS 250 / tp-015 / bk-017): 0 violations; allowlisted a 31, b 8,
  e 10, g 74, p 1; no stale entries.
- CI replay baseline: 0 violations after the CI-only entries. The full integration suite passed locally
  (731 passed, 1 skipped) on a scratch PostgreSQL 16 superuser cluster, which is the shape of the CI service.
- A change to `rls_catalogue_rules.py` must be copied to AA-CIS-Infra `db/rls_catalogue_rules.py` in the same
  session, or the Infra Copy Guard goes red (lesson S241, AA-852).
