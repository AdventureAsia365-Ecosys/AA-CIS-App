# AA-850 — Dead Table Registry wave 1: quarantine (CIS 294) and drop (CIS 296)

Source: AA-Ecosys `docs/audits/2026-10-28-S255-aa850-dead-tables/` (registry.md, wave1-quarantine-plan.md, the
migration drafts). Data standards DM-3.8 / DM-3.9: candidate → quarantine (`ALTER … SET SCHEMA retired`) → drop
after >= 14 days. Step 1 (quarantine, 294) is live on Dev since 28/10/2026 10:27 UTC; step 2 (drop, 296) is the
section at the end of this file.

## Decisions

- **Migration 294 is the audit draft with three changes.** (1) NNN → 294 (reserved for AA-850 in S255). (2) Step 4
  revokes from *every* grantee found in the ACLs of the schema, the relations and their columns (PUBLIC included),
  instead of a fixed role list: on Dev that is cis_app, but the CI replay also has legacy roles (app_user, …) from
  the early migrations, and a role added later cannot slip through. (3) The post-check reads the ACLs directly (no
  entry but the owner's) on top of the draft's membership-aware `has_*_privilege` checks, column privileges included.
- **The guard's row counts come from DRY RUN T0** (`.tmp-session/S255/runscript_aa850_dead_table_dry_run.log`, DB
  Migrate run-script as the master, 28/10/2026 07:52 UTC, verdict `quarantine_ready=true`): 0 everywhere except
  `acp_shared.marketplace_portfolios` 11 (last write 24/08/2026; the registry had "n/a") and
  `shared.tenant_brand_rules_deleted_aa404` 6 (platform tenant only). Written into the file and its header. The
  guard refuses `-1` (not filled in) and any count that moved since; `test_aa850_migration_294.py::
  test_dry_run_counts_filled_in` keeps a `-1` from ever reaching `main`.
- **The guard accepts the DRY RUN count or 0.** The file carries Dev's counts (11 and 6 for two tables); every fresh
  replay (CIS CI's conftest, the AA-CIS-Infra DB Schema Dump drift replay `db/replay_migrations.py`) has empty
  tables. An exact-only guard would fail 294 in the Infra replay every night (verdict `open`: `failed == 0` is part
  of a clean verdict) and take the later drop file down with it. So `n = rows OR n = 0` passes; any other count
  (an insert into a table the DRY RUN found empty, a partial delete) is refused. CI applies the file as committed:
  no conftest rewrite of the counts (an earlier draft of this branch had one, `w294_with_counts`; removed).
- **Erasure: `retired` is not a runtime schema.** `inventory.QUARANTINE_SCHEMAS = ("retired",)`. The plan said only
  "remove the five entries", but the erasure planner walks FKs *into* any schema: retired.route_pick /
  tenant_atom_state / tenant_brand_rule_versions → shared.tenants, s1_from_atom_runs / tenant_atom_state → raw_tours,
  acp_runs → pipeline_runs. Under the old code each became a `foreign_owner` check whose count cis_app cannot read
  (no USAGE on `retired`) — a blocker on every tenant erasure on Dev after the apply. `plan.py` now makes them
  `quarantined_child` checks: counted when readable (CI's superuser: > 0 blocks), reported as information when not.
- **RLS catalogue allowlist keeps both names for the five tenant_id tables**: `retired.<t>` (the post-294 state, used
  by CIS CI) and the old `<schema>.<t>` (Dev until 294 is applied). Stale entries are reported, not fatal, so the
  nightly Dev dump never shows a violation in the window between the Infra rules copy and the apply. The old names go
  with the wave-1 drop.
- **`SCHEMA_OWNERS["retired"] = "cis"`** (rule e: the outbound FKs `retired.* → shared.*` stay same-owner).
- **Old-migration re-apply tests**: `_rls_fixture_helpers.undo_294_for_reapply` moves a quarantined object back to its
  source schema inside the test's rolled-back transaction (239 names `acp_shared.tenant_atom_state`; 281 recreates
  `shared.v_pipeline_summary`). Same pattern as `undo_241_for_239_reapply` / `undo_265_year_plan`.

## Changed (vs the plan)

- `services/erasure/plan.py` gained the `quarantined_child` check kind (not in the plan; see Decisions).
- `test_aa859_migration_241.py`: the column-grant probe table is `acp_shared.audit_log` (no RLS, never granted), not
  `acp_shared.year_plan` as the plan proposed: year_plan already carries the test's table-level grants, so a column
  grant there would change the counted set and the description format the test pins.
- `test_aa817_migration_239.py` is unchanged: `REVOKE_239_TABLES` keeps `tenant_atom_state`, because the fixture
  (`undo_241_for_239_reapply`) now brings the table back to `acp_shared` before re-applying 239 (239's own SQL names
  it; dropping it from the tuple alone would not let 239 run).
- `conftest._apply_schema` also drops schema `retired` at the start (a reused local DB kept the quarantined tables and
  the next replay's 294 found the names taken).
- Comments: `api/main.py`, `api/routers/admin.py` (an endpoint docstring: `docs/api/openapi.json` carries the same one-line
  change, edited by hand because the local venv's older FastAPI/pydantic would rewrite unrelated parts),
  `services/acp_contract/route_detection.py`, `services/export/handler.py`; `CONTEXT.md` one bullet on `retired`. The
  `api/routers/admin_pipeline.py` docstring the plan listed is left as is (it names the column historically, and it
  is an endpoint description too).

## Tradeoffs

- Dynamic REVOKE loop vs the draft's fixed role list: the loop is invisible to the ownership lint (warning, like the
  draft's comment loop), but it is the only way to guarantee "no grantee left" without knowing every role name.
- Accepting 0 misses one case on Dev: every row of marketplace_portfolios (11) or tenant_brand_rules_deleted_aa404
  (6) deleted between DRY RUN T0 and the apply. The quarantine itself is then still right (nothing reads them), only
  the rows to archive are gone; DRY RUN T1 before the drop would show it. The alternative (exact count only on Dev,
  detected by database name or a replay session setting) needs a change in the Infra replay for one file.
- The "counts filled in" test is a hard failure, not a skip: a skip would let a file with `-1` merge and fail only at
  the Dev apply, after the Infra copy (fix-after-merge costs a second PR + copy).
- The erasure deploy window: the five inventory entries are removed in this PR. Between the CIS deploy and the 294
  apply on Dev those tables are still in their old schema with a tenant_id and no entry, so an erasure *apply* would
  list them as `unregistered` (blocker); the DRY RUN mode still works. Keeping the entries would have left dead
  registry rows after the apply ("missing", skipped). Dev has no real tenant; keep the window short (apply 294 right
  after the Infra copy).

## Should know

- Order: CIS PR (migration commit first) → merge → Infra PR (owners.yaml + mirrors + `db/rls_catalogue_rules.py`
  byte copy + `db/migrations/cis/294_aa850_quarantine_wave1.sql` byte copy) → DB Migrate `check` then `apply` of
  `cis/294_aa850_quarantine_wave1.sql` while the job tables are idle. Without the Infra owners change the ownership
  lint refuses the file ("schema retired belongs to no owner in db/owners.yaml"); with it, lint passes with three
  dynamic-SQL warnings and the runner's `--inspect` reports no error.
- The Infra Copy Guard compares `db/rls_catalogue_rules.py` with CIS `main`: the Infra PR goes green only after the
  CIS PR is merged.
- No `REQUIRED_CIS_SCHEMA` bump: no code needs 294.
- If anything writes to a wave-1 table between DRY RUN T0 and the apply, the apply is refused ("has N rows, the
  approved DRY RUN counted M"): re-run the DRY RUN, find the writer, then update the count in a new commit (and the
  Infra copy).
- Before the drop (step 2): archive the 11 rows of `retired.marketplace_portfolios` and the 6 of
  `retired.tenant_brand_rules_deleted_aa404` (the plan named only the second).
- After the apply: the `bot/db-schema-reference` PR shows schema `retired`; the AA-Ecosys ERD design pages that list
  the moved tables (if any is `enforce=true`) need the same change (lesson S250, Design ERD drift).
- Tested locally on a scratch PostgreSQL 16 (CI runs 15; nothing used is 16-only): full `tests/integration/` suite,
  unit tests of the erasure and the RLS rules, Infra `db/tests`, Infra ownership lint and `--inspect`.

# Step 2 — drop (CIS 296, branch `chore/aa-850-drop-wave1`)

## Decisions

- **The 14-day wait is waived (Nghiệp, S255, in chat).** No service reads or writes the ten objects (0 code
  references in CIS, Booking, TripPlanner, Partner and Infra), and since 294 no app role can reach them. The draft's
  `now() - applied_at(294) < 14 days` check is replaced by a comment that records the waiver; the "294 is registered"
  check stays (nothing is ever dropped from a source schema). The schema_versions description says "waived" too, so
  the waiver is visible in the catalog.
- **Number 296, not 295**: 295 is reserved by another open PR. Neither the CIS repo nor the Infra lint
  (`check_migration_files.py`: unique number per owner only) requires contiguous numbers.
- **Counts verified after the 294 apply** (all ten `where = retired`): 0 everywhere except
  `marketplace_portfolios` 11 and `tenant_brand_rules_deleted_aa404` 6. Same guard rule as 294: the exact count or
  0 (a fresh replay: CIS CI, the Infra nightly drift replay), anything else refused; -1 refused.
- **The archive is the DB Migrate pre-apply snapshot.** The file starts with `-- migrate: destructive`, so DB
  Migrate snapshots RDS before the apply (`db-migrate-296-<run>-<attempt>`), which holds the 17 rows and every
  dropped definition. No separate export of the 17 rows (they are drafts/backups of the platform tenant, no reader).
- **RESTRICT, views first**: no CASCADE; the ten have no FK between each other (checked in the creating migrations
  081/088/097/098/009/019/104/132), only outbound FKs, which go with the tables.
- **The schema `retired` stays**, empty, for the next waves; `SCHEMA_OWNERS["retired"]`, `QUARANTINE_SCHEMAS` and
  the erasure `quarantined_child` check kind stay.
- **Tests that need the objects rebuild them as stand-ins.** After the replay runs 296 none of the ten exists, so
  `_rls_fixture_helpers.wave1_standins()` creates minimal versions (the columns the tests touch, Dev's outbound FKs)
  inside the test's rolled-back transaction: in their source schemas for `test_aa850_migration_294.py` (the 294
  guard/move/revoke tests keep running) and for the 239 re-apply (`acp_shared.tenant_atom_state`), in `retired` for
  the new `test_aa850_migration_296.py`. `undo_294_for_reapply` is gone (nothing left to move back); the 281 test
  no longer needs the two views (281's recreate path runs over the other views).

## Changed (vs the draft / the 294 notes)

- RLS catalogue allowlist (rule a): the pre-294 names (`shared.acp_runs`, …) are removed now (294 is applied on
  Dev); the five `retired.<t>` keys stay until 296 is applied on Dev (stale in CIS CI from this PR, reported, not
  fatal), so the nightly Dev dump has no violation in the window between the Infra copy and the apply. Remove them in
  the next change of the rules file after the apply.
- Comments that named the tables as existing: `api/main.py`, `api/routers/admin.py` (+ the same one-line change in
  `docs/api/openapi.json`, by hand as for 294), `services/acp_contract/route_detection.py`,
  `services/export/handler.py`, `services/erasure/inventory.py` / `plan.py`, `tests/unit/test_aa751_no_acp_runs_reader.py`
  (docstring), `CONTEXT.md` (the `retired` bullet, the route-hub line, the tenancy table row).
- `docs/runbooks/clean-rerun-reset.sql` + `clean-rerun.md`: the lines for `tenant_atom_state`, `route_pick` and
  `s1_from_atom_runs` are removed (they would fail with "relation does not exist" since 294 already).
- Old implementation notes and audits that name the tables are history and are left as they are.
- Independent review (S255) added tests to `test_aa850_migration_296.py`: nothing outside the ten is dropped (every
  relation, constraint, function, type and schema outside `retired` survives, and a later-wave object in `retired`
  stays), a wave-1 name moved back to its source schema is never dropped there, the kind guard, a count one off the
  verified one (10, 12), and a contract check that the ten DROP lines are the file's only DROP / TRUNCATE / DELETE /
  ALTER. Mutating the file (no 0 exemption, no count guard, CASCADE, an extra DROP, no 294 check, no re-run skip, no
  destructive header, a wrong count) makes at least one test fail each time.

## Tradeoffs

- Waiving the 14 days loses the "a forgotten reader shows up as 42501 within two weeks" window. Accepted: the audit
  found 0 references, Dev has no real tenant, and the snapshot restores any of the ten.
- Stand-ins vs deleting the 294 tests: the stand-ins are not Dev's full tables, but 294's logic (guard, move,
  revoke, comment, post-check) only needs names, kinds, row counts, grants and FKs, which they have.
- Keeping the `retired.<t>` allowlist keys one more change vs removing them now: removing them now would show five
  rule-a violations in the nightly Dev dump until 296 is applied.

## Should know

- Order: this CIS PR → merge → Infra PR `chore/aa-850-drop-copy` (byte copy of `296_aa850_drop_wave1.sql` and of
  `db/rls_catalogue_rules.py`; the Copy Guard compares with CIS `main`, so it goes green after the CIS merge) →
  DB Migrate `check`, then `apply` of `cis/296_aa850_drop_wave1.sql` while the job tables are idle. DB Migrate takes
  the pre-apply snapshot (destructive header): record its id in AA-Ecosys `docs/architecture/dead-table-registry.md`
  and move its `aa:retain-until` tag to apply + 180 days.
- If a count moved since the 294 apply, the apply is refused ("has N rows, the verified count is M"): find the
  writer first.
- After the apply: the `bot/db-schema-reference` PR shows `retired` empty; then remove the five `retired.<t>`
  allowlist keys (CIS + Infra byte copy).
- No `REQUIRED_CIS_SCHEMA` bump: no code needs 296.

# Step 3 — the four empty legacy schemas (CIS 299, branch `chore/aa-850-drop-empty-schemas`)

## Decisions

- Migration 299 drops `acp_gold_output`, `acp_silver_s2`, `acp_silver_s3` and `acp_silver_s4` straight away, with no
  quarantine: they hold no object (schema reference: 0 objects each, owner `cis_owner`, `cis_app` USAGE), so there is
  nothing to wait for. The tech lead approved the drop in S255. Number 299 was reserved (295, 297 and 298 are taken by
  other PRs).
- Guard: each schema must hold no relation, function, type, collation, operator, conversion or text search object.
  Otherwise the file is refused and the error names what was found. An absent schema is skipped (a re-run). The
  statement is `DROP SCHEMA IF EXISTS … RESTRICT`, with no CASCADE. The schema ACL and the `pg_default_acl` rows of 244
  / 245 (`FOR ROLE aa_cis_admin` / `cis_owner` IN SCHEMA s) are not objects in the schema: PostgreSQL drops them with
  the schema, and the schema's owner may do this even for another role's row (tested as `cis_owner`).
- `-- migrate: destructive`: DB Migrate takes the pre-apply snapshot. There are no rows to keep.
- The `/v1/social` router (`api/routers/v1_social.py`) is removed. Its four routes read and wrote only
  `acp_silver_s4.social_content`, which 121 dropped, so every call has failed since then (42P01). No caller exists:
  no admin page, BFF route or job uses it. Removed with it: its `POLICY` entry
  (`POST /v1/social/batch-review`), the two top-level tests `tests/test_social_batch_review.py` /
  `test_social_context.py`, its cases in the S241 / AA-816 C9 / AA-882 unit tests, its rows in the two route
  snapshots, its paths and the two schemas only it used (`BatchReviewRequest`, `BatchDecision`) in
  `docs/api/openapi.json` (edited by hand, as for 294), and the unused pydantic model `shared/models/social_content.py`.
- `/v1/social` stays in `STAFF_PATH_PREFIXES` and the BFF list (`frontend/lib/auth-server.ts`, kept equal by
  `test_aa816_c9_bff`): the prefix stays staff-only and fails closed, and no frontend change or deploy is needed.

## Changed

- `tests/integration/conftest.py`: new `X1_LEGACY_EMPTY_SCHEMAS`. `x1_244_ci_shape` still creates the four, because
  244 / 245 grant on them and their tests apply them in the Dev order. `x1_244_undo` now drops them again
  (RESTRICT), because the replay state after 299 has none of them. `X1_CIS_SCHEMAS` stays at 244's 11 (history).
- `services/erasure/inventory.py`: `CIS_SCHEMAS` has 7 runtime schemas; the `acp_silver_s2.competitor_inputs` entry
  is gone (208 had dropped the table, 299 drops the schema).
- `tests/integration/rls_catalogue_rules.py` `SCHEMA_OWNERS`: the four are removed (byte copy in AA-CIS-Infra).
- `CONTEXT.md`: a bullet for the drop; the `cis_app` bullet says 7 runtime schemas since 299.
- New `tests/integration/test_aa850_migration_299.py`. It checks that the replay applied 299, that a rerun is a
  no-op, the drop from the pre-299 state (default privileges included), the drop as `cis_owner`, that an absent
  schema is skipped, that the guard refuses each object kind, and the file contract.
- Old migrations, audits and implementation notes that name the schemas are history and stay as they are.

## Tradeoffs

- Removing `/v1/social` in this PR vs leaving it: leaving it would keep code that names a schema that no longer
  exists. The routes already failed on every call, so removing them changes nothing for any caller.
- Keeping the `/v1/social` prefix vs removing it: removing it would need a frontend change for no gain.

## Should know

- Order: this CIS PR, then the Infra PR `chore/aa-850-drop-empty-schemas-copy`, then DB Migrate `check` and `apply` of
  `cis/299_aa850_drop_empty_schemas.sql`. The Infra PR carries the byte copy of 299 and of `rls_catalogue_rules.py`,
  and removes the four from `owners.yaml` and its mirrors (new key `dropped_schemas`, which the ownership lint reads).
  Apply 299 soon after the Infra merge: until then the four exist but are unlisted. The isolation probe and the RLS
  catalogue ignore them in that window, and the ERD shows them as owner "unknown".
- If the guard refuses on Dev, an object appeared in one of the four since the 28/10 dump. Find out who created it
  before you do anything else.
- No `REQUIRED_CIS_SCHEMA` bump.
