# AA-850 — Dead Table Registry wave 1: quarantine (CIS 294)

Source: AA-Ecosys `docs/audits/2026-10-28-S255-aa850-dead-tables/` (registry.md, wave1-quarantine-plan.md, the
migration drafts). Data standards DM-3.8 / DM-3.9: candidate → quarantine (`ALTER … SET SCHEMA retired`) → drop
after >= 14 days. This branch is step 1 (quarantine) only; the drop is a later migration.

## Decisions

- **Migration 294 is the audit draft with three changes.** (1) NNN → 294 (reserved for AA-850 in S255). (2) Step 4
  revokes from *every* grantee found in the ACLs of the schema, the relations and their columns (PUBLIC included),
  instead of a fixed role list: on Dev that is cis_app, but the CI replay also has legacy roles (app_user, …) from
  the early migrations, and a role added later cannot slip through. (3) The post-check reads the ACLs directly (no
  entry but the owner's) on top of the draft's membership-aware `has_*_privilege` checks, column privileges included.
- **The guard's row counts come from DRY RUN T0** (`.tmp-session/S255/runscript_aa850_dead_table_dry_run.log`, DB
  Migrate run-script as the master, 28/10/2026 07:52 UTC, verdict `quarantine_ready=true`): 0 everywhere except
  `acp_shared.marketplace_portfolios` 11 (last write 24/08/2026; the registry had "n/a") and
  `shared.tenant_brand_rules_deleted_aa404` 6 (platform tenant only). Written into the file and its header. The
  guard refuses `-1` (not filled in) and any count that moved since; `test_aa850_migration_294.py::
  test_dry_run_counts_filled_in` keeps a `-1` from ever reaching `main`.
- **The guard accepts the DRY RUN count or 0.** The file carries Dev's counts (11 and 6 for two tables); every fresh
  replay (CIS CI's conftest, the AA-CIS-Infra DB Schema Dump drift replay `db/replay_migrations.py`) has empty
  tables. An exact-only guard would fail 294 in the Infra replay every night (verdict `open`: `failed == 0` is part
  of a clean verdict) and take the later drop file down with it. So `n = rows OR n = 0` passes; any other count
  (an insert into a table the DRY RUN found empty, a partial delete) is refused. CI applies the file as committed:
  no conftest rewrite of the counts (an earlier draft of this branch had one, `w294_with_counts`; removed).
- **Erasure: `retired` is not a runtime schema.** `inventory.QUARANTINE_SCHEMAS = ("retired",)`. The plan said only
  "remove the five entries", but the erasure planner walks FKs *into* any schema: retired.route_pick /
  tenant_atom_state / tenant_brand_rule_versions → shared.tenants, s1_from_atom_runs / tenant_atom_state → raw_tours,
  acp_runs → pipeline_runs. Under the old code each became a `foreign_owner` check whose count cis_app cannot read
  (no USAGE on `retired`) — a blocker on every tenant erasure on Dev after the apply. `plan.py` now makes them
  `quarantined_child` checks: counted when readable (CI's superuser: > 0 blocks), reported as information when not.
- **RLS catalogue allowlist keeps both names for the five tenant_id tables**: `retired.<t>` (the post-294 state, used
  by CIS CI) and the old `<schema>.<t>` (Dev until 294 is applied). Stale entries are reported, not fatal, so the
  nightly Dev dump never shows a violation in the window between the Infra rules copy and the apply. The old names go
  with the wave-1 drop.
- **`SCHEMA_OWNERS["retired"] = "cis"`** (rule e: the outbound FKs `retired.* → shared.*` stay same-owner).
- **Old-migration re-apply tests**: `_rls_fixture_helpers.undo_294_for_reapply` moves a quarantined object back to its
  source schema inside the test's rolled-back transaction (239 names `acp_shared.tenant_atom_state`; 281 recreates
  `shared.v_pipeline_summary`). Same pattern as `undo_241_for_239_reapply` / `undo_265_year_plan`.

## Tradeoffs

- Dynamic REVOKE loop vs the draft's fixed role list: the loop is invisible to the ownership lint (warning, like the
  draft's comment loop), but it is the only way to guarantee "no grantee left" without knowing every role name.
- Accepting 0 misses one case on Dev: every row of marketplace_portfolios (11) or tenant_brand_rules_deleted_aa404
  (6) deleted between DRY RUN T0 and the apply. The quarantine itself is then still right (nothing reads them), only
  the rows to archive are gone; DRY RUN T1 before the drop would show it. The alternative (exact count only on Dev,
  detected by database name or a replay session setting) needs a change in the Infra replay for one file.
- The "counts filled in" test is a hard failure, not a skip: a skip would let a file with `-1` merge and fail only at
  the Dev apply, after the Infra copy (fix-after-merge costs a second PR + copy).
- The erasure deploy window: the five inventory entries are removed in this PR. Between the CIS deploy and the 294
  apply on Dev those tables are still in their old schema with a tenant_id and no entry, so an erasure *apply* would
  list them as `unregistered` (blocker); the DRY RUN mode still works. Keeping the entries would have left dead
  registry rows after the apply ("missing", skipped). Dev has no real tenant; keep the window short (apply 294 right
  after the Infra copy).

## Should know

- Order: CIS PR (migration commit first) → merge → Infra PR (owners.yaml + mirrors + `db/rls_catalogue_rules.py`
  byte copy + `db/migrations/cis/294_aa850_quarantine_wave1.sql` byte copy) → DB Migrate `check` then `apply` of
  `cis/294_aa850_quarantine_wave1.sql` while the job tables are idle. Without the Infra owners change the ownership
  lint refuses the file ("schema retired belongs to no owner in db/owners.yaml"); with it, lint passes with three
  dynamic-SQL warnings and the runner's `--inspect` reports no error.
- The Infra Copy Guard compares `db/rls_catalogue_rules.py` with CIS `main`: the Infra PR goes green only after the
  CIS PR is merged.
- No `REQUIRED_CIS_SCHEMA` bump: no code needs 294.
- If anything writes to a wave-1 table between DRY RUN T0 and the apply, the apply is refused ("has N rows, the
  approved DRY RUN counted M"): re-run the DRY RUN, find the writer, then update the count in a new commit (and the
  Infra copy).
- Before the drop (step 2): archive the 11 rows of `retired.marketplace_portfolios` and the 6 of
  `retired.tenant_brand_rules_deleted_aa404` (the plan named only the second).
- After the apply: the `bot/db-schema-reference` PR shows schema `retired`; the AA-Ecosys ERD design pages that list
  the moved tables (if any is `enforce=true`) need the same change (lesson S250, Design ERD drift).
- Tested locally on a scratch PostgreSQL 16 (CI runs 15; nothing used is 16-only): full `tests/integration/` suite,
  unit tests of the erasure and the RLS rules, Infra `db/tests`, Infra ownership lint and `--inspect`.
