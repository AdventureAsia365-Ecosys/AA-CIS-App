# AA-916 — Capture writing signals (WM-03..WM-08)

Writing memory, Group 2 (root `docs/audits/2026-10-20-S245-writing-learning-loop/issues/README.md`), under app ADR 0010.
Delivered in slices: the CIS 277 storage PR (this branch, WM-03), the Infra byte copy, then the code PR (WM-04 / 05 /
06 / 08, stacked on the AA-926 quality registry). WM-07 (admin reason chips UI) is the S250 cut line and is not built.

## Decisions

- **Migration key 277** (S250 schedule §1; the plan said 275, which went to AA-977).
- **FORCE RLS plus a `writing_signal_cis_owner_all` policy.** ADR 0010 decision 10 asks for FORCE. Since X1 S21 (CIS 245)
  every later cis/ file runs as `cis_owner`, which FORCE filters too; the standing check
  `test_standing_a_new_force_table_has_a_cis_owner_policy` requires a `<table>_cis_owner_all` policy on any new FORCE
  table, and rls_catalogue_rules rule t exempts that name. The plan only named the `cis_app` parity policy.
- **Explicit REVOKE / GRANT** (S250 §5 point 3): REVOKE ALL from PUBLIC, `cis_app`, `aa_app_user`, `catalog_owner`
  first (it removes what the Dev default ACL of `cis_owner` gives `cis_app`), then `cis_app` SELECT / INSERT / UPDATE /
  DELETE and `aa_app_user` SELECT / INSERT. Guard 2 checks the exact privilege set and the AA-859 invariant v3.
- **`tenant_isolation` reads `scope = 'tenant' AND tenant_id = <guc>`**: the tenant pool never sees or writes a platform
  row, even one that (wrongly) named its tenant.
- **Extra CHECKs beyond the plan**: a hash is required whenever its text is stored, and both hashes are lower-case
  64-hex; `locator` must be a JSON object; text columns are capped (200 000 chars for before / after, short caps for the
  labels); `source_table` / `source_id` 1..128 chars. They keep the tenant-pool INSERT (the only non-admin writer) from
  storing junk.
- **`problem` column (review round 1).** The gate's diagnostic quotes tenant text (an F1 fact, an F9 claim, the T2
  "number(s) [...]" list) and the apply body lets the admin send up to 1000 free characters. ADR 0010 decision 11 keeps
  all of that out of the append-only audit_log, so the signal stores it (`pii:free_text`, capped at 2000 characters)
  and the audit row keeps only `problem_sha256`. Added before 277 was applied anywhere, so it is still one migration.
- **Erasure inventory row ships with the migration PR**, not the code PR: `test_aa839_erasure_job` fails on any table
  with a tenant key that the inventory does not list, and the planner already tolerates a registered table that does not
  exist yet (`plan.missing`), so a deploy between merge and DB Migrate apply is harmless.

- **Code PR stacked on AA-926** (`feat/aa-926-quality-registry-s250`, S250 §2): `suggested_reason` reads gate names from
  the registry constants (`qr.*`); a gate without an explicit entry falls back to its taxonomy classes, then
  `style_only`. The branch also merges the 277 migration branch, so CI replays 277 for the integration tests.
- **Best-effort only where the user's own action must not fail.** The tenant T9 edit (WM-04) and the reason-only
  signals (reject / dismiss / regenerate) use `record_writer_feedback_safe`: a SAVEPOINT (`conn.transaction()` nested
  in the tenant-pool transaction keeps the `app.tenant_id` GUC set before it) and a `aa916_signal_failed` warning.
  The admin sentence applies (WM-06) and the A1 field edit (WM-05) write the signal in the edit's transaction and
  fail with it: since the audit row no longer holds the text, the signal is the edit's history.
- **The tenant edit signal uses the row's owner** (`RETURNING tenant_id`), equal to the caller by the WHERE and RLS.
- **A1 field edits of a tenant's own tour are tenant scope.** `generated_content.tenant_id` is NOT NULL; the AA master
  tenant's versions are platform signals, any other tenant's are tenant signals (ADR 0010 decision 10: platform rows
  never hold tenant text). `seo_keywords_used` is not writer text (DataForSEO keywords) and gives no signal. JSONB
  fields are stored as canonical JSON (`sort_keys`).
- **Audit rows of the admin sentence applies** (T9 and T2) keep: offsets, mode, gate, problem, suggestion model / cost,
  `suggestion_sha256`, `warning_gates` (gate names only), the signal id + hashes + reason code. They drop the
  sentence before / after, the suggestion text and the warning texts. The T2 row also drops `section_before/after`
  and `content_before/after` (the whole-version copy AA-802 kept) for their sha256 values. **Flagged for review:**
  the previous whole version is no longer stored anywhere as text; the sentence pair + locator is in the signal.
- **fact_not_in_source on a T2 sentence** labels `a1_claim_supported` (the T3 question) with
  `subject_key(source_text(tour), sentence.strip())`, after the edit committed, on the pool (record_outcome is
  best-effort; it labels 0 rows when T3 never asked Jev about that sentence). On a T9 piece there is no Jev claim
  question, so the code lives on the signal only (`fact_status = 'fail'`).
- **Reject / dismiss bodies are optional** (`ReviewReasonBody | None`): the current admin UI sends none and keeps
  working. Regenerate takes `review_id` + `reason_code` on `TourRunRequest`; both are excluded from the job payload,
  and the signal is written only when a new job was created (a dedup double click writes none).
- **WM-08**: `discarded_attempts` lists every attempt that did not become the final text, oldest first, each once
  (`attempt_number`, `ledger_index` = len(repair_log) when the attempt's outcome was captured, `content_text`,
  `gate_ledger`). `content_from` tracks which attempt the current text came from, so a revert never mislabels.
  `writer_input.writer_prompt_version` = `prompt_version_of(prompts.SYSTEM_PROMPT)` (the A1 formula).

## Tradeoffs

- FORCE + an owner policy `USING (true)` gives the owner the same rows as no FORCE. It is kept for the ADR invariant and
  the X1 convention (a future member of `cis_owner` shows up as a policy, not as a silent bypass).
- No FK to the edited object (polymorphic source, free erasure order); the cost is that a signal can outlive a deleted
  piece. Tenant rows go with the tenant anyway.

- The T2 whole-version copy in the audit row (AA-802 "history holds both versions") is traded for ADR 0010 decision
  11. A restorable history would need the section text in the signal; not done (the sentence is the learning unit).
- The signal insert in the tenant edit costs one extra statement inside the tenant transaction (no model call).
