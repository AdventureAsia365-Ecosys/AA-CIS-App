# AA-828 — e-mail alerts for spend budgets (CIS app side)

S238 add-on to AA-828 (Nghiệp: "làm luôn"). Infra side: AA-CIS-Infra branch
`feat/aa-828-cis-alert-email-env` (env vars on the CIS api + worker task definitions).
A ledger-wide v2 (reconciliation with Cost Explorer) stays under AA-804.

## Decisions
- **Trigger = the bell row.** `shared.cost_guard.maybe_alert` is the only place that writes
  `spend_budget_alert` notifications; right after the INSERT it calls
  `shared.ops_alerts.enqueue_spend_budget_email`. No new scheduler or poller.
- **Queue a job, never SES inline.** New job kind `ops_alert_email` (concurrency 1, 5 attempts,
  not background). `maybe_alert` runs inside job handlers (segment_research, place_extract,
  place_geocode) — not the LLM client — but a job that just hit its budget should not wait on SES,
  and the runner gives retries/backoff for free. Same shape as AA-Booking `bk_notify_email`.
- **Dedupe = job idempotency key** `ops_alert_email:spend_budget:<provider>:<scope>:<threshold>:<UTC day>`
  (`shared.job` unique index), with threshold `<alert_pct>pct` or `stop` (a run stopped by the
  budget). On top, the bell's own throttle (one unread per provider per 24 h) gates the enqueue, so
  e-mails are never more frequent than bell rows.
- **Unset env = no-op.** `ALERT_EMAIL_TO` or `SES_FROM_ADDRESS` empty → nothing queued, log
  `ops_alert_email_not_configured`; a job that runs after the env was removed returns `skipped`.
- SES helper `shared/aws_client/ses_mailer.py` mirrors AA-Booking `app/mailer.py` (sesv2
  `send_email`, lazy boto3, `to_thread`, permanent vs retryable error codes) but is CIS code.
- Link target: `<ADMIN_BASE_URL>/admin/llm-usage` (nav "External Spend", Budgets tab).
  `ADMIN_BASE_URL` defaults to `https://aa-cis.lumiguides.it.com`; not set in Terraform.

## Changed (vs. the request)
- The request says "per-app/per-stage" budgets. `shared.spend_budget` is keyed by
  **provider + scope** (`global` | `job:<kind>`), not app/stage; the e-mail reports exactly that
  (provider / scope, daily + per-run limits, provider-wide axis when present).
- No migration, no UI change.

## Tradeoffs
- Enqueue is best-effort after the bell INSERT (not one transaction): an enqueue failure must
  never lose the bell row or break the job. Cost: a crash between the two statements loses one
  e-mail; the bell still shows it.
- Delivery is at least once (worker dies after SES accepted → reaper re-queues → second e-mail).
- Because the bell throttle is per provider, two budgets of the same provider crossing within 24 h
  (while the first bell is unread) produce one bell and one e-mail. Unchanged existing behaviour.
