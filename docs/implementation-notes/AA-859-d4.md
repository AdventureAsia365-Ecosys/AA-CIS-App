# AA-859 PR-D4 — unpublish on the tenant pool (W4)

Route: `DELETE /v1/publish-log/{publish_id}` (`api/routers/v1_publish.py::unpublish`). Flag `UNPUBLISH_FLAG`
(`aa859:unpublish_pool`, declared in PR-S). No migration (229 publish_log RLS + I/S/U grant, 237 tenant_integrations
RLS + SELECT).

## Decisions
- Three `acquire_scoped_conn(..., UNPUBLISH_FLAG, fail_closed=True)` blocks, exactly as the plan says: (1) publish_log
  SELECT, (2) tenant_integrations SELECT, (3) `UPDATE ... AND status = 'published' RETURNING`. Blocks 1 and 2 were not
  merged: the 422 "no post ID / unsupported channel" check sits between them and skips the integration read, and the
  plan fixes three blocks.
- SQL lifted into module constants `_UNPUBLISH_SELECT_SQL`, `_UNPUBLISH_INTEGRATION_SQL`, `_UNPUBLISH_UPDATE_SQL`
  (text unchanged apart from whitespace), so the forgotten-WHERE tests can mutate them.
- Secrets Manager read: `await asyncio.to_thread(_get_secret, ...)` in both flag states (no observable difference for
  flag off; the old code also held no connection there). `_get_secret` now builds its client on a fresh
  `boto3.session.Session()` (same reason as `v1_integrations._sm_client`: the default Session is not thread-safe).
- One `aa859_unpublish` INFO line per request, logged inside block 1 (so 404 / 422 / 502 requests log it too), with
  `used_tenant_pool` of that block — same shape as disconnect's `aa817_integration_disconnect`. The success line
  `tenant_self_unpublish` additionally carries `used_tenant_pool` of the UPDATE block.
- Audit row on MAIN after block 3 committed, best-effort, comment `# AA-859 MAIN exception: ...`.
- Double unpublish keeps the old answer: 404 (status guard in block 1 for a later request; in block 3 for an overlapping
  one). Not 409 — the response contract stays as it was.

## Changed
- `api/routers/v1_publish.py`: `unpublish` on the tenant pool behind the flag; SQL constants; `asyncio.to_thread` for the
  secret read; `_get_secret` Session per call; docstring.
- New tests: `tests/unit/test_aa859_unpublish_pool.py` (the AA-817 fail-closed matrix re-run for this route by calling
  the matrix functions of `test_aa817_fail_closed_routes.py` with this route's param, plus block order, admin-pool shape
  with flag off, audit on MAIN, 404/422/502 branches, concurrent UPDATE 0 rows), `tests/unit/test_aa859_reentrancy_d4.py`
  (reentrancy entry, 3 acquires; no tenant connection held during the secret read or the remote delete),
  `tests/integration/test_aa859_unpublish_pool.py` (real Postgres as aa_app_user).

## Tradeoffs
- The matrix entry lives in a new file instead of `ROUTES` in `test_aa817_fail_closed_routes.py`, to avoid conflicts with
  the sibling PRs. The wrappers take the matrix's own extra params (`error,reason`, `bad_id`) from the matrix functions'
  `pytestmark`, so they stay in sync. When the wave lands, the param can be folded into `ROUTES` and the file trimmed.
- Each block reads the Redis flag itself, so a flip mid-request can run block 1 on one pool and block 3 on the other.
  Both paths filter on `tenant_id`, so this is safe; the per-request log line reports block 1's pool.
- `BotoCoreError` on the secret read (endpoint / credential errors) still propagates as a 500, as before (only
  `ClientError` -> 502). Not changed, to keep flag-off behaviour exact.
