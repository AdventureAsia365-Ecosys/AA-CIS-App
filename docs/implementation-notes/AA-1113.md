# AA-1113 — Free-text PII scrub in the shared LLM gateway, fail closed (lane l6, CIS)

Scope of this lane: the first bullet of the issue only (the F3 scrub moves into the shared CIS gateway for free-text
stages, failing closed). The CRM ledger routing, the over-cap flag column and the acc3 budget are other slices.

## ADR status (root ADR 0009 decision 10)

Accepted S283 (17/11/2026, tech lead, session decision page): root ADR 0009 decision 10 ("Data scopes: maker,
geography and tenant rules per provider") is accepted together with its data-class bullet "scrubbed traveller text":
a stage that carries tenant free text sends only a scrubbed copy of its prompt, and a scrub that cannot run refuses
the call. This repo does not hold the ADR (it lives in the root repo, `docs/adr/0009-ai-platform-and-provider-gateway.md`),
so the status line there (and the "Not covered by the three answers, still Proposed: decision 10" sentence of its
decision record) is edited by the orchestrator in a root PR; this note is the CIS record. The rest of decision 10
(makers and geography per stage, the per-provider tenant rule, "a scope change happens only by migration") is not
built here: the stage list below is a code allow-list for this slice.

## Decisions

- **Which stages.** Every tenant stage, by name, fail safe: `is_free_text_stage(stage)` is true for `^t\d+_` (the
  rule `batch_lane.TENANT_STAGE_RE` already uses; a test pins the two together) unless the stage is in
  `NOT_FREE_TEXT_STAGES`, a deny-list for a tenant stage proven free of tenant text (empty today). The first build had
  a writer-only allow-list (`t9_write`, `t2_generate`, `t8_angle_gen`); review S283 showed the repair, FAQ and judge
  stages re-read the same unscrubbed input: `repair_sentences_detailed` (`t9_repair`, the admin Rewrite suggestion)
  sends `SOURCE:` content seed + `FACTS:` agency facts (the tenant's own title and body, `facts.py` `_fact_entry`);
  `t9_faq_filter`, `t9_faq_answer_fit`, `t10_judge`, `t10_claims`, `t10_adjudicate` read the seed and facts;
  `t2_flag_fix`, `t2_judge`, `t2_brand_audit`, `t7_debate_judge` re-read brand rules and the tour input. The measure
  (root `docs/audits/2026-11-17-S283-session/aa1113-provider-stage-30d.psv`) shows tenant rows on all of them. The
  catalogue stages (`s1_*`, `a3_*`, `tp_compose`) carry none (tenants = 0) and are not scrubbed. No existing column
  fits: `shared.llm_role_config.pii_class` (CIS 373) is `content | pii`, and `pii` means the opposite rule (the stage
  needs the personal data, so it runs only on US AWS deployments, unscrubbed). A `free_text` flag in the stage row is
  a migration (decision 10: "a scope change happens only by migration") and the lane brief said no migration unless
  unavoidable.
- **Where it runs.** `LLMClient._generate_with`, after the app switch, stage switch, tenant budget and central budget
  gates and before the first provider attempt; `request` is rebound to the scrubbed copy, so the single-model call,
  the route (every rung), the legacy `haiku` / `sonnet` keys, the gateway truncation retry, the A/B shadow and the
  cassette only ever see the scrubbed request. The admin `probe` runs it too. Lesson S260 (a gate placed in
  `deployment_plan` missed the legacy chain): the gate sits above the chain split, and a test covers a legacy key.
- **Fail closed.** Any exception inside the scrub, or a scrubbed text that still holds an e-mail or a `+` phone (a
  self-check), raises `FreeTextScrubFailed`: the gateway writes one 0 USD row (status `refused`, `error_class`
  `other`, `quality_signal.pii_scrub = {version, status: failed, error_type}`) and raises. `other` because the CHECK
  on `shared.llm_call_log.error_class` has no scrub class; a dedicated class is a contract migration (follow-up).
  Not account-level: a job retries with its normal backoff, each retry 0 USD.
- **What is redacted.** The CRM log scrub (`AA-Partner api/app/observability/scrub.py` `scrub_text`) with its F3
  detectors (`api/app/privacy/patterns.py` + the folding of `api/app/privacy/text.py`), copied, never imported: JWTs,
  Bearer / Basic credentials, key-like `name=value`, Postgres key details, e-mails, `+` phones, then signed links,
  cards (Luhn), CCCD numbers, passports, phones without `+` (VN mobiles / landlines, NANP, after a cue) and OTPs after
  a code cue. Dates are left alone (prompts are full of trip dates), as in the CRM log scrub. Bracket labels, no
  restore step (the CRM's own LLM gateway uses `<KIND_n>` placeholders and restores them; that pass and the
  known-value pass are not ported, root ADR 0008a section 5 keeps the CRM gateway separate).
- **Receipt.** Counts per label on the request's attempt scope (`quality_signal.pii_scrub` of the gateway's own rows)
  and the log line `llm_free_text_scrubbed`; never a value. The call site's success row (written with
  `**billed_fields(resp)`) is unchanged: its `prompt_hash` is still the hash of the system prompt the call site built
  (the scope is made before the scrub), so prompt versions keep one hash.

## Changed

- `shared/llm_client/free_text_scrub.py` (new): the scrub, the stage allow-list, `FreeTextScrubFailed`.
- `shared/llm_client/pii_patterns.py` (new): the F3 detectors. One structural change from the CRM: `_classify` is
  split in three functions in the same rule order (the CIS complexity ratchet, AA-1097: the CRM function scores 12,
  the limit is 10). Behaviour is unchanged; nothing to port back to the CRM.
- `shared/llm_client/client.py`: the gate, `attempt_outcome` maps the refusal to `refused / other`, and a few long
  comments shortened so the file stays at its code-health baseline (2964 lines, the file-size ratchet).
- `tests/unit/test_aa1002_no_behaviour_change.py`: the two new modules are listed in the call path.
- Review fix (S283): the stage allow-list became the fail-safe `t<n>_` rule with a deny-list; a test sends a planted
  e-mail and phone in `facts_text` through `repair_sentences_detailed(stage="t9_repair")` and checks the fake model
  gets them scrubbed.
- `CONTEXT.md`: the "Free-text PII scrub" bullet next to "Data class per stage".

## Tradeoffs

- Name rule now vs a stage-row flag: the `t<n>_` rule ships without a migration and is fail safe (a new tenant stage
  is scrubbed without a code change; a reviewer only has to remember the deny-list, never an allow-list). The cost:
  every tenant call pays the regex pass (linear, no I/O) and a tenant stage that really needs a value (none today)
  must be added to `NOT_FREE_TEXT_STAGES` with evidence. The follow-up migration can move the flag into
  `shared.llm_role_config`.
- Scrubbing the repair / judge stages too: their prompts get the same bracket labels as the writer's, so a judge
  compares a scrubbed seed with a draft written from the scrubbed seed (consistent). A tenant's own edited text that
  holds a contact value comes back from `t9_repair` with `[email]` / `[phone]` in the repaired sentence, and a claim
  quote with a label no longer matches the raw text verbatim; both are the rule (d10), not a bug. The earlier note
  ("their input is the scrubbed writer's output plus the same seed") was wrong: the seed and facts in those calls were
  never scrubbed.
- Out of this gateway: the Jev decisions (`shared.llm_client.decide`, e.g. `t8_angle_rank`, `t3_grounding`) go to Jev
  over HTTP, not through `LLMClient._generate_with`, so they are not scrubbed here; TripPlanner's `tp_plan_chat`
  (tenant rows in the measure) runs in TripPlanner's own gateway. Both are follow-ups.
- Brackets instead of placeholders with restore: the content a tenant gets never contains a traveller's contact
  value anyway (no CIS prompt carries brand contact details; the CTA rules are text); a restore step would put the
  value back into model output.

## Should know

- The scrub runs on every tenant-stage call; it is pure regex (linear, CPU only, no I/O). The platform's own static
  prompts of the tenant stages (writers, repair, FAQ, judges, T3 repair, debate) scrub to themselves (a test guards
  it), so a prompt edit that trips a detector fails CI
  instead of silently losing words.
- Live check without a paid call: a one-off script in the API container that builds an `LLMRequest` for `t9_write`
  with a planted e-mail and phone and prints `free_text_scrub.scrub_for_stage(...)` (no model call).

# AA-1113 — lane l7 of S284: the free-text registry, the scrubbed-prompt hash and one connection cap for every caller

Scope: what the S283 slices left open. (1) the stage list as data, not a code literal; (2) CRM calls under the
connection caps; (3) an over-cap flag in `catalog.v_llm_gateway_config_v1`; (4) the acc3 budget and Marketplace spend.

## Decisions

- **Registry column, floor kept.** CIS 451 adds `shared.llm_role_config.free_text` (boolean, default false,
  migration-only like `pii_class`, root ADR 0009 d10 "a scope change happens only by migration") and marks every
  existing tenant stage. The gateway scrubs a stage when its row says `free_text` OR it is a `t<n>_` stage: the name
  rule stays as a fail-safe floor a row cannot lower, so a new tenant stage shipped before its row is never sent raw.
  The empty code deny-list `NOT_FREE_TEXT_STAGES` is gone (taking a tenant stage out would need a new rule and the
  tech lead; none is needed today). A CHECK keeps a `pii` stage from being marked (a pii stage needs its data).
- **Cold-cache read failure = scrubbed.** `role_config._read_failed_default` sets `free_text` from the stage's last
  successful read in this process (`_free_text_known`, kept across `invalidate()` like `_pii_known`), else True. Same
  reasoning as AA-1039 for `pii_class`: a stage is never downgraded because its row could not be read.
- **Ledger evidence = `scrubbed_hash`.** The receipt gains the sha256 of the scrubbed system prompt, user prompt and
  few-shots (canonical JSON). The live probe recomputes it from the text it expects the model to get. `VERSION` is
  `aa1113-2`. The call site's success row still carries the call site's `prompt_hash` (system prompt as built), so
  prompt versions keep one hash; putting the receipt on success rows too is a follow-up (it needs a `billed_fields`
  key and the record_call plumbing).
- **$0 live probe.** `scripts/llm_ops/aa1113_scrub_probe.py` sends a planted e-mail and phone on `t9_write` with a model
  key the catalog does not hold: the gateway runs the gates and the scrub, refuses the key before any provider attempt
  and writes one 0 USD row; the script reads it back by `route_trace` and checks status, counts, hash, absence of the
  planted values and cost 0. No provider is called, so the adhoc stage cap is not needed.
- **One connection cap for every caller (CIS 452).** `catalog.v_llm_connection_cap_v1` publishes, per connection with
  a monthly budget, this UTC month's ledger spend (`shared.llm_call_log`, account = the connection, the exact sum
  `cost_guard` makes), the policy (`alert_pct`, `hard_stop`, code defaults when no row), `over_cap` and `stops`.
  `tripplanner` may read it (the CRM never does: see lane l7b below; the `crm_app` grant first planned as CIS 453 was
  withdrawn by the tech lead in S284 and 453 is now the provider budget setting). The gateway
  view appends `free_text` and `over_cap_connections` (the model's deployments whose connection `stops`; one
  MATERIALIZED CTE so the cap view is read once per query).
- **acc3 budget and Marketplace.** No Terraform change: `aa3-llm-monthly-total` (Infra `accounts/acc3-bedrock/cost_guard.tf`)
  has no cost filter, and AWS Budgets' Billing entity dimension (AWS | AWS Marketplace) only narrows a budget when a
  filter names it, so the unfiltered budget counts Marketplace lines (Claude on Bedrock). Limit 100 = the gateway's acc3
  cap since S283. An Infra guard test pins "no filter that drops Marketplace" (acc1 keeps its LinkedAccount filter only).

## Changed

- `shared/llm_client/free_text_scrub.py`: `is_free_text_stage(stage, stage_cfg)` (registry OR floor),
  `scrub_for_stage(request, scope, stage_cfg)`, `scrubbed_hash`, receipt `scrubbed_hash`, `VERSION = "aa1113-2"`.
- `shared/llm_client/role_config.py`: `StageConfig.free_text`, the optional column read (fallback before 451),
  `_free_text_known`, the cold-read default.
- `shared/llm_client/client.py`: `_free_text_gate` gets the stage row (the probe reads it); file size unchanged.
- `api/routers/admin_llm_ops.py`: `GET /admin/llm-config` rows carry `free_text` (read-only; untyped dict, no OpenAPI
  change). Frontend: AI gateway › Routing › Routing by data class lists "Free text, scrubbed first" (EN + VI).
- `services/quality/change_control.lock.json`: `route_defaults` re-locked with parity evidence
  (`tests/unit/test_aa1113_free_text_registry.py::test_the_safe_defaults_gain_only_an_unset_mark`): the SAFE_DEFAULTS
  hash moved only because the dataclass gained a field that is False on every row.
- `scripts/llm_ops/aa1113_scrub_probe.py` (new), tests `tests/unit/test_aa1113_free_text_registry.py` (new),
  `tests/unit/test_aa1113_free_text_scrub.py` (deny-list test replaced, receipt hash).
- Migration-only PR: `api/migrations/451_aa1113_stage_free_text.sql`, `452_aa1113_connection_cap_views.sql`,
  `tests/integration/test_aa1113_migration_452.py`, conftest skips 452 (catalog recipe).

## Tradeoffs

- Floor + registry instead of registry only: a row cannot take a tenant stage out. Costs nothing today (no tenant stage
  needs raw contact values) and keeps the S283 fail-safe property.
- Scrubbing a never-read stage on a cold-cache DB failure may bracket a phone number in catalogue text for that one
  call; the alternative (send raw) breaks fail closed for a registry-only stage.
- The cap view counts the CIS ledger only (CIS + TripPlanner rows): it is the CIS share of the connection (lane l7b).
- (Withdrawn S284.) A `crm_app` grant on the view, amending root ADR 0008a, was proposed and refused by the tech lead;
  the CRM keeps its own cap per connection instead (lane l7b).

## Should know

- Review S284 fixes. (1) The batch lane (`batch_lane.stage_refusal`) refuses a stage the registry marks, not only a
  `t<n>_` stage: its adapters send `item.system` / `item.user` as built, so a marked stage stays on the scrubbed
  on-demand path (a cold-cache read failure marks a never-read stage too, so a batch submit is refused and retried by
  its job; fail safe). (2) `tests/integration/test_aa1113_free_text_registry_db.py` now runs `LLMClient.generate` on
  `t9_write` with a planted e-mail and phone and an unknown model key against Postgres with the real `call_log` writer:
  the row is status `error` / `other` (an unknown key fails before any attempt; the reviewer expected `refused`), 0 USD,
  the receipt says scrubbed with the scrubbed request's hash, and no column holds a planted value.
  (3) The $0 probe script is registered in the three repo guards it trips (model_tier override allow-list, LLM
  call-site registry exclusion: the gateway writes the refusal row itself, sub-floor ceiling `PROBE_MAX_TOKENS`), and
  the two unit tests of `LLMClient.probe` (stage `adhoc_conn_test`, a MagicMock request) patch the stage read to
  "no row": without a database the cold-read default marks a never-read stage free text and scrubs the mock.
- **Not covered: TripPlanner's planning chat (`tp_plan_chat`).** It carries traveller free text (tenant rows in the
  S283 measure) but has no `shared.llm_role_config` row (it borrows `tp_compose`, which 451 leaves false) and runs in
  TripPlanner's own gateway, which does not read `v_llm_gateway_config_v1.free_text` yet. TripPlanner's call-site
  `scrub_text` redacts e-mails and `+` phones only (no F3 set) and does not fail closed. Follow-up: a CIS migration
  seeds a `tp_plan_chat` row with `free_text = true`, and TripPlanner refuses a call on a marked stage unless the
  F3-equivalent scrub ran. AA-1113's Done claim covers the CIS gateway (and every caller routed through it) only.
- Order (MIG-4): migration-only PR (451 + 452) → Infra copy → Migration Apply (class contract, job tables idle) → this
  code PR and the Partner code PR. Code before the apply also works (column missing = false + floor; the CRM treats a
  missing view per its spend environment).
- Numbers: 447 is on main (AA-1126); 448-450 are held by other S284 lanes' open migration PRs. If they do not land
  first, renumber 451/452/453 to main max + 1/+2/+3 (migrations, their tests, conftest, compiled_defaults.json, and the
  CIS 451 / 452 / 453 mentions in this PR, the Partner crm-077 header and the root ADR 0009 note).

# AA-1113 — lane l7b of S284: each app its own cap per connection, the split visible on the Budgets tab

Tech lead redesign (S284, ~10:05): the CRM does not read any CIS view. Each app has its OWN monthly cap per model
connection; the shares together stay under the connection's provider budget, so the provider total is never exceeded.

## Decisions

- **CIS share = the existing connection budget.** `shared.llm_provider_connection.monthly_budget_usd` (the CIS
  gateway's connection budget, enforced on the CIS ledger, CIS + TripPlanner rows) is the CIS share. Nothing in the
  gateway changes.
- **Provider budget = a setting (CIS 453).** It was nowhere. `cis.spend.connection_provider_budget_usd`, json
  `{connection key: USD per month}`, entries 0..1000000, default `{}` (nothing declared, nothing checked), area spend,
  impact medium, single approval. Informational: no call path reads it. One json key instead of one key per connection
  so a new connection needs no migration (the registry's json type checks every entry is a number in bounds). Its
  reader and the pure rule (`api/services/llm_connection_split.py`) ship in the migration PR, as CIS 447 shipped
  `spend_environment.py` (the settings lint wants a reader for an enforced key in the same PR).
- **CRM share through the existing relay.** The CRM setting `crm.ai.connection_monthly_cap_usd` (AA-Partner crm-077,
  same json shape, keyed by the CIS connection key) is read with `crm_console.crm_ops_call("GET", "/settings",
  area=ai)` and the staff member's own token: the path Platform › Settings already uses for its CRM tab
  (`crm_settings_relay`). No grant, no new CRM route, no M2M client. The relay's `list_settings` is not reused as is
  because it also asks `/console` and the staff names (two extra calls this page does not need).
- **The rule** (`llm_connection_split.split_row`): `over_allocated` when a provider budget is set and the shares that
  are set add up to more than it (an unknown CRM share counts 0, so CIS alone above the budget is still red). States,
  worst first: `no_provider_budget` (nothing to check), `over_allocated` (red), `crm_unknown` (amber: the relay
  refused or the CRM has not published the key yet), `unbounded` (amber: an app has no cap on a budgeted connection and
  could spend all of it), `ok`. Unit tests pin the flag at, above and below the budget.
- **Own query on the page.** `GET /admin/ai-gateway/connection-split` (spend.read, like `/budgets`) and its own
  section (`ConnectionSplitSection.tsx`) under "LLM connection budgets": a CRM that does not answer never blanks the
  Budgets tab. Links go to the two settings on Platform › Settings (`?app=&area=&key=`). The I/O read lives in
  `api/services/ai_gateway_split.py` so `ai_gateway.py` keeps its size baseline.

## Changed

  `shared/settings/compiled_defaults.json`, `api/services/llm_connection_split.py`,
  `tests/unit/test_aa1113_connection_split.py`, `tests/integration/test_aa1113_migration_453.py`; CIS 452's comments
  no longer name a CRM reader (no SQL change).
- Code PR: `api/services/ai_gateway_split.py`, `api/routers/admin_ai_gateway.py` (route),
  `api/core/staff_authz.py` (POLICY), snapshots (`docs/api/openapi.json`, route policy, role matrix),

  `frontend/lib/connectionSplit.ts` (+ `.test.mjs`), `frontend/app/admin/ai-gateway/ConnectionSplitSection.tsx`,
  `BudgetsTab.tsx`, `CONTEXT.md` ("Connection budget split", the 452 bullet).

## Tradeoffs

- A flag, not a write-time refusal: the two shares live in two registries (CIS, CRM) and neither app reads the other's
  data; refusing a proposal that over-allocates would need a synchronous cross-app read on every proposal. The
  over-allocation shows red on the Budgets tab instead; the tech lead fixes it by editing either share.
- Two shares instead of one shared total: an app can stop while the other app's share still has room. That is the
  price of no cross-app read; the headroom column shows where to move room.
