# AA-1087 — Dev-only write-capable E2E staff identities (CIS half: A10b-3)

The S278 system audit (gap B2) found no test identity that can write on the staff side. The tech lead chose to build
write identities before the synthetic pilot rehearsal. Root ADR 0006a A10b-3 (CIS) and A10e (Booking) record it; the
migration half is `AA-1087-migration.md` (CIS 401, for Booking); Booking and AA-CIS-Infra carry their own notes.

## Decisions
- **No new CIS identity: the A10b admin gains one synthetic-only write.** A10b (`e2e-cis-admin@`) is already the
  Dev-only E2E CIS admin with allow-listed writes on synthetic tenants (A10b-1 invitations, A10b-2 view-as), codes in
  the MFA-admin-only prefix. A second CIS admin address would need a CIS CHECK migration, a directory row, a trigger
  entry and a mailbox recipient for the same reach.
- **"CIS review approve" = the Compliance release of a held piece.** The Review Queue approve
  (`/admin/review-queue/{id}/approve`) only claims rows of the AA master tenant and publishes AA master content: there
  is no synthetic master record, so an E2E identity must never get it. The staff review that approves a TENANT's
  content is Tenant content QA > Compliance > Release (an open subject_gate flag): tenant-scoped, so it can be held to
  synthetic tenants (`is_canary IS TRUE` and not the pilot, `e2e_staff.SYNTHETIC_TENANT_SQL`).
- Piece labels (`/admin/content-quality/pieces/{id}/label`) were weighed and dropped: a label by the E2E admin would
  feed the writing-quality ground truth.

## Threat note (for the independent review)
- **Who can use it:** whoever reads an A10b sign-in code (MFA admin role; whoever controls mail for the E2E domain).
- **What is added:** release of an open subject_gate flag of a synthetic tenant. The release only lets exactly the
  checked text of a synthetic tenant's piece publish to that tenant's (test) channels. No AA master content, no real
  tenant, no pilot.
- **Covered by tests:** real / NULL-canary tenant (403 before any write, the AA-884 row still written), unknown flag
  (404), the A10d identity (403, no synthetic read), outside Dev (403), the concrete path matched in full, a normal
  admin unaffected.
- **Residual:** a CIS admin can mark a real tenant synthetic (`is_canary`), the same trust as A10b-1 / A10b-2.
- **Revoke at any time:** drop `E2E_COMPLIANCE_RELEASE_WRITES` and `_refuse_e2e` (update the guard test), deploy; or
  disable the A10b user. Removal with the A10 family at go-live (AA-1054).

## Should know
- The smoke needs the id of an OPEN subject_gate flag of a synthetic tenant; it does not create one.

## S278 lane l18: fixtures for the live write run

The S278 live verify found no open subject_gate flag on Dev (the release spec had nothing to release) and the CRM's
E2E agency (sen-vang, CRM-seeded under a UUIDv5 id) missing from `shared.tenants`, so Booking's guard read it as real.

### Decisions
- **Register, do not UPDATE.** The agency becomes a CIS tenant through the tenant provisioning saga (the system path
  for every tenant), with one new create field: `tenant_id`, accepted only when `ENVIRONMENT` is exactly `dev` and
  `kind` is `demo` (checked in `parse` and again in the job), refused `tenant_exists` when CIS holds the id. A `demo`
  tenant is `is_canary` (synthetic) and its content plan gives `trade.book`, so `bk_tenant_pull` adopts the Booking
  partner row as active. No CRM add-on is attached, so the CRM's own L1 features of the agency stay (adoption guard).
  The admin API bodies do not carry the field; only the fixture module sets it.
- **The flag comes from the real gate.** `subject-gate-flag` inserts one new attempt (status approved, marked
  `E2E fixture (synthetic) run <run>` in `content_summary`) on the latest request of a synthetic tenant with an
  invented text holding a booking link to a `.invalid` host, then runs `subject_gate.run`; the gate writes the open
  flag. No LLM call. The output gives the flag id and the text's sha256 the release needs.
- **A module in the image, run by ECS Exec** (`scripts/` is not in the image). Dev only (exact `dev`), DRY RUN first.

### Changed
- `services/tenant_account/provision.py` (`register_id`), `services/tenant_account/e2e_fixtures.py` (new), CONTEXT.md.
- Tests: `tests/unit/test_aa1087_e2e_fixtures_cis.py`, `tests/integration/test_aa1087_e2e_fixtures_cis.py`.

### Tradeoffs
- The fixture piece is a new attempt of a real request of the synthetic tenant, so its Content studio shows it as the
  latest attempt (a synthetic tenant on Dev; the text says what it is).
- Registering names the tenant with the CRM's display name, so Booking's partner name changes from the hand label to
  that name once the pull adopts the row.

  Booking's guard accepts sen-vang's records.
