# AA-1152 — TripPlanner window for an agency's own prices (AA-CIS-App part)

Slice L9 of the root `docs/audits/2026-11-19-S285-session/advisory-r2-plan.md` (S285 decision B2 option C). The CRM
computes an agency's own "from" prices and publishes them to TripPlanner (`tripplanner.agency_prices.v1`); the
AA-Partner, AA-TripPlanner-Web, AA-Booking and root PRs of the same wave hold the feature. CIS only seeds one setting.

## Decisions

- **CIS 476** seeds `tripplanner.prices.agency_stale_hours` (int hours, 2..168, default 6, app `tripplanner`, area
  `prices`): TripPlanner hides every price of an agency whose last list arrived longer ago (a review of the lane found
  that a CRM that stops publishing left old prices up for good). TripPlanner settings live in the CIS registry and are
  read through `catalog.v_app_settings_v1` (CIS 415), so the seed is a CIS migration.
- Default 6 hours: the CRM publishes every hour, so a few missed runs do not hide prices; bounds 2..168 (never below
  two runs, never more than a week).

## Changed

- Nothing in CIS code: the key is another app's (the settings-lint reader check covers `cis` keys only).

## Tradeoffs

- Platform scope only (no per-agency override): the window is a freshness rule of the platform, not an agency choice.

## Should know

- Migration-only PR (contract, MIG-4), applied before the TripPlanner code PR; that code falls back to its own default
  (6, pinned equal to this seed in `backend/tests/test_s279_settings.py`) until the view lists the key.
- Tests: `tests/integration/test_aa1152_migration_476.py`, the TripPlanner seed tables in
  `tests/unit/test_aa1096_tp_settings_seed.py` and `tests/integration/test_aa1096_migration_414.py` (23 keys) and the served-row count in
  `tests/integration/test_aa1096_migration_415.py` (23: + 1 of 476, the per-migration increment earlier seeds used).

## S292 follow-up: the tour day's overnight destination on catalog.http.v1 (contract 1.4)

The partner CRM's add-on drawer offers only the add-ons sold at the AA tour day's places (AA-Partner S291 follow-up),
but `TourDay.places` lists the day's stops only, so a night away from those stops was never offered. TripPlanner's
day cards already read the night's place from `catalog.v_tour_day_route`; the CRM holds no grant on `catalog` (root
ADR 0008a), so CIS serves it on the HTTP contract.

### Decisions

- **One new nullable field, `TourDay.overnight_destination_id`** (root contract 1.4, additive; not required): the CIS
  destination id (`shared.destinations.id`, the same ids as `places[].destination_id` and `getDestination`). An id,
  not a `Place` object: the CRM compares ids with Booking's add-on places and reads the name from its own cache or
  `getDestination` when it needs one.
- **Source**: `catalog.v_tour_day_route.overnight_destination_id`, already granted to `aa_app_user` (CIS 228 / 253),
  read like the other detail views by `tour_id = ANY($1::uuid[])` (lesson S238; the EXPLAIN guard in
  `tests/integration/test_aa976_catalog_http_reader.py` is parametrized over `_DETAIL_SQL`, so it covers the new read).
  Only rows with a night are read (`overnight_destination_id IS NOT NULL`). No migration.
- **Day numbering**: `v_tour_day_route.day_index` is matched to `TourDay.day_no` (the place pipeline numbers days like
  the itinerary; `v_tour_place` joins `geo.tour_place.day_index = day_number` the same way). A route row of a day that
  is not served (day 0, past the last day) is ignored.
- **Same value as TripPlanner**: stale route rows (`is_stale`, built from an older Master) are served like
  TripPlanner's `day_addons.OVERNIGHT_SQL` reads them; the view already nulls a suspect or merged destination.
- **The key is on every day** (null when there is no night), so the body shape does not depend on the data.

### Changed

- `services/catalog_http/reader.py`: a fifth detail read (`routes`); `services/catalog_http/mapping.py`:
  `overnights()` and the day field. `api/schemas/public_api.py` `CatalogTourDay` (docs model) and
  `docs/api/openapi.json` gain the field; `docs/contracts/catalog.http.v1.openapi.yaml` is the root 1.4 copy.

### Tradeoffs

- Every served tour's `content_hash` / ETag changes once when this ships (the key is in the hashed body): the CRM's
  hourly sync re-reads each tour once (at most 100 tour reads per run, so a few runs). Emitting the key only when set
  would have spared the tours without a night, at the price of a body whose shape depends on the data.
- A night on a line destination (a river) is served as is (TripPlanner does the same); the graph's stop choice skips
  those, the add-on rule does not need to.

### Should know

- Root contract PR first (1.4 + sample), then this PR (copy byte-identical, `ROOT_CONTRACT_SHA256`), then the
  AA-Partner PR that reads the field. A CRM that is not updated stores the field in its cached body and ignores it.
- Tests: `tests/unit/test_aa1152_catalog_http_overnight.py`; counts updated in `tests/unit/test_aa976_catalog_http.py`;
  `tests/integration/test_aa976_catalog_http_reader.py` (`test_overnight_destination_comes_from_the_day_route_view`,
  statement count 7, the EXPLAIN guard over `routes`).
