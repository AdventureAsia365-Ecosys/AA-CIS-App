# AA-918 — Writing memory: R0 replay engine ($0) and the L0 lexicon fast path (WM-15, WM-16)

Writing memory, Group 4 (root `docs/audits/2026-10-20-S245-writing-learning-loop/issues/README.md`), under app ADR 0010.
Stacked on `feat/aa-917-writing-memory-mine` (the rule store, CIS 280, and the miner). No migration: the R0 result
lives in `shared.writing_rule.lint` (`lint.r0`), and `match_phrases` (CIS 280) was added for this replay.

## Decisions

- **No migration.** R0 results go into `lint.r0` (jsonb object, CIS 280 `writing_rule_lint_check` only asks for an
  object). An admin edit replaces `lint`, so it drops a stale R0 by itself. Freshness is a `rule_sha` over kind,
  writer, owner, text, replacement, phrases and channels — not `updated_at`, which activation and rollback also move.
- **k IS the mining threshold.** `mining.cluster_threshold(basis)` returns {signals, pieces, tenants, reviewers} from
  `config.py`; `build_clusters` now reads it for every basis (behaviour unchanged: same numbers, the 917 tests still
  pass) and the R0 candidate filter reads the same function with the rule's `lint.basis`. Recurrence = the rule's
  matching non-`fail` signals of the last 30 days, held against that threshold (`r2_eligible`). A rule under it stays
  visible (nothing is deleted or rejected by R0).
- **What R0 replays.** For a T9 writer: the newest 300 stored pieces (approved / held) of the writer's channels and the
  rule's owner (a platform rule: every tenant's pieces, counts and ids only in the result), and per piece up to 6
  texts — the final text, each discarded attempt, and the writer's text before each human edit (the signal's
  `before_text`): an edited piece's final text no longer holds the phrase the human removed, so counting only final
  texts would hide exactly the evidence. Prevented failures = stored failed findings (final ledger, every repair_log
  attempt and its ledger snapshot, discarded attempts' ledgers) whose violation quotes a rule phrase. For A1 / T2 R0
  is signals-only (no stored writer context to replay; those writers have no L0 reader either).
- **The gate replay** rebuilds the T9 gate inputs from `writer_input` the way the writer does (same steps as
  `scripts/aa729/score.py::t9_gate_replay`, in `replay.PieceReplay`) and calls the real `run_quality_gates`. The F9
  judge is never called: a new keyword `run_quality_gates(f9_results=…)` passes the piece's stored F9 verdicts
  (patching `gate_brand_voice` would race with real T9 writes in the same worker process). F9 and F10 (cross-tenant
  lookup, not run) are not compared in the baseline.
- **L0 verdict** (`l0_ok`): a lexicon rule of `t9_blog` / `t9_social`; a usable phrase (≤ 6 words, no mask token: a
  masked `[NAME]` never matches written text); a replacement that adds nothing; the phrase occurs in stored text
  (`before` ≥ 1: "the target phrase drops" needs it to be there); 0 occurrences in the counterfactual (phrase
  replaced, or cut for a ban); and no blocking gate failing in the counterfactual (rule on) that passed in the base
  (rule off) — "0 new hard stops". `fires` = texts where the rule-on gate quotes the phrase the base did not.
- **Replacement check** (ADR 0010 decision 3): `lint.lexicon_specifics` (new_specifics numbers / clock times, names,
  promise words, mask tokens) plus, for L0: any capitalised word the phrase lacks (fails closed on a capitalised
  first word), time-of-day words, and the AA-800 service nouns (now exported as `signature_vocabulary.SERVICE_NOUNS`).
- **How a rule reaches the writer**: at T9 `start_write`, the active lexicon rules of the piece's writer and owner
  (`rules.rules_for`: platform + own tenant) join the brand pack's `forbidden_words`. That one list already feeds the
  prompt (brand block "Never use these words or phrases") and the F2_lexicon gate (source F2_brand_forbidden,
  blocking, sentence-repairable, with the seed exemption), so no new gate, no registry change, and the admin sentence
  Apply (which reads the stored pack) enforces it too. A replacement rule also adds "Write 'X' instead of 'Y'." to the
  T9 WORDS line. `pack.learned_lexicon` and `writer_input.writing_rules` (applied + skipped, with reasons) record it.
- **Precedence (decision 4)**: a rule is skipped when its phrase is a signature word the tenant declared (the
  tenant-authored brand rule wins), or when it is in the CTA, the brand name or the trip name (the writer keeps those
  verbatim: a ban there could never be repaired and would hold every piece). A tenant rule wins over a platform rule
  with the same phrase. `applies_to` channels are respected when set.
- **Release 0 no-op**: no active rule → `l0_for_write` returns the same pack object and `None`; the prompt lines and
  `writer_input` keys are exactly the pre-918 ones (unit-tested). A read failure (table missing, DB error) also gives
  no rule: the write never fails on writing memory.
- **Activation** = `POST …/candidates/{id}/activate`: candidate / approved → active with `approved_by` = the admin's
  UUID (403 `no_actor` without one; an approval is a human's), after `l0.activation_problem` (409 with a code:
  not_lexicon, no_l0_reader, not_activatable, lint, phrase, replacement_adds, r0_missing, r0_stale, r0_failed;
  token_cap when the CIS 280 trigger refuses). **Rollback** = `POST …/rollback {reason}`: active → rejected with
  `rollback: <reason>` (the approval stays on the row; the cluster may be mined again). Both ai.admin, like every
  writing-memory write. No release table yet (AA-919), so the rule row is the pointer.
- **R0 runs as a job** (`writing_memory_r0`, background, cap 1, $0): a T9 gate run costs ~0.3 s of CPU (measured on the
  S234 export), so a rule over 300 pieces is minutes, not a request. The job caches the rebuilt inputs and rule-off
  runs of each text across its rules. `POST /run {kind: r0_baseline}` runs the sanity check alone.

### Review round (independent reviewer, S250)

- **Activation is atomic.** `activate_rule` now reads the row with `get_rule(..., for_update=True)`, runs
  `activation_problem` and the `activate_l0` UPDATE in one transaction. Before, an admin edit (PATCH) landing between
  the unlocked read and the UPDATE kept the status `candidate`, so the UPDATE still matched and text that R0 never
  replayed went active. A row lock was chosen over an `updated_at` guard: it also orders a concurrent `store_r0`, and
  the edit simply waits for the click (or the click for the edit, which then answers 409 r0_missing / r0_stale).
- **Precedence reads every declared phrase.** The tenant's declared set is `signature_words(pack)` (POSITIONING words
  named in its brand text) plus every phrase in `pack["signature_words"]` (custom_validators). A platform rule banning
  "off the beaten path" no longer lands on a tenant that listed it as its own.
- **A replacement never uses a word the same write forbids** (`l0.replacement_forbidden`): its own phrase, a
  PLATFORM_TRUTH or STOCK_SUPERLATIVES word, the tenant's forbidden list (checked per rule in `select_rules`), and the
  other applied phrases (chains, `_drop_chained_replacements`: drop every conflicting entry to a fixpoint, then add
  back in precedence order what no longer conflicts, so A -> B -> C with C banned keeps A). Activation also refuses
  the fixed-word case (`replacement_forbidden`, checked after R0, so a platform-truth replacement still reports R0's
  own `r0_failed` first). R0 alone could not catch this: its counterfactual replays one rule on the stored pack.
- **R0's rule-off base is the tenant's pack.** `apply_to_pack` now records `added` per `learned_lexicon` entry, and
  `l0.without_learned` removes the phrases it added; `PieceReplay.pack` is that pack, `PieceReplay.stored_pack` the
  stored one. The baseline still compares the stored ledger with a run on the stored pack (what the writer ran), so
  pieces written under an active rule neither under-count `fires` nor disagree in the sanity check.
- **One exemption predicate.** `quality_gates.forbidden_exempt` (plain case-insensitive substring of the seed) is what
  `_forbidden_hits` and R0's `source_exempt` both call.
- **Function-word phrases are refused** (`phrase_problem`): a phrase made only of the lint's STOPWORDS ("the",
  "and you") would block ordinary sentences whenever the seed lacks it.
- **R0 and the wave worker**: R0 sleeps `R0_YIELD_SECONDS` (20 ms) between pieces so the worker's event loop gets the
  GIL; the job's `expected_seconds` is 1800 (a cold two-writer baseline); the drawer says to run R0 / the baseline
  outside a wave.

## Tradeoffs

- Reusing the forbidden-word layer instead of a new learned-lexicon gate: no registry / taxonomy / snapshot churn and
  the admin Apply path enforces it for free, but the finding reads "which the brand forbids" and a learned word is
  indistinguishable from the tenant's own in the stored pack (the `learned_lexicon` key and `writing_rules` say which).
- Cutting the phrase as the counterfactual of a ban is a proxy (the writer would rephrase, not delete); the gates are
  mostly lexical, so a cut cannot hide a new hard stop a rephrase would cause only in rare grammar-sensitive gates.
- Platform R0 reads every tenant's stored pieces in the worker; it keeps only counts and ids, never text.
- The baseline on old texts disagrees where the gates changed since the text was written (on the S234 export:
  88.9% of 1 232 gate checks agree; F2_banned_patterns accounts for 79 of the 137 disagreements, the AA-778 em-dash
  rule those texts predate — the same effect the AA-924 replay documented). It is reported per gate, not used as a
  pass / fail threshold.

## Should know

- **Order**: needs CIS 280 applied and the AA-917 code merged first (this branch is stacked on it); no new migration,
  no new readiness number. The `t9_write` path reads `shared.writing_rule` only through `l0.load_active`, which fails
  open, so a deploy before 280 writes exactly as before.
- **Dev evidence still to do after deploy** (done-when of WM-15 / WM-16): run "R0 baseline" (sanity check numbers in
  a comment); R0 on 3 real candidates ($0: llm_call_log shows no `writing_memory_*` row from it); activate one T9
  social lexicon rule, write one piece (writer_input.writing_rules lists it, the phrase is gone), roll it back, write
  the next piece (writer_input no longer lists it). Real candidates exist only after an AA-917 mining run.
- `masking.tokens` keeps a closing quote on a word (`special'`), so `contains_phrase` misses a phrase inside quotes;
  R0 strips quotes before matching (`replay._unquoted`). The miner's PREDICT check has the same blind spot on quoted
  text (AA-917) — worth a one-line fix there.
- An older piece's stored pack keeps a learned word after its rule is rolled back, so the admin sentence Apply on that
  piece still refuses the phrase; new pieces are clean.
- `without_learned` leaves `forbidden_words: []` on a tenant with no list of its own (the gates treat it as absent).
- The race test (`test_an_edit_racing_the_activation_click_never_goes_active`) uses two committing connections and
  deletes its own row; it fails on the pre-review router (checked).
