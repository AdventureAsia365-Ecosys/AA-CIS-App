# AA-927 — one `shared.llm_call_log` row per billed LLM call

Issue: the AA-729 baseline (S245) counted 216 `LLMClient.generate()` returns vs 100 logged rows in
score-only run `8f07b98f`, and 815 vs 627 in regenerate run `dab254c4`. Dollars matched; row counts did not.

## Root cause (from the two result JSONs, bronze bucket, `scripts/out/aa729/<run>/`)

The harness counts "made" = `evalpatch.SPEND.calls` (generate() returns) and "logged" = rows with role
writer/judge/validate and provider != typesafe.

Score-only, per stage (rows logged): s1_judge 55, t2_judge 10, t10_judge 35 (s1_grounding 16 are Jev rows,
excluded). Calls made: s1_judge 55 + 2 x 48 near-band AA-714 repeats = 151, t2_judge 10 x 3 (median3) = 30,
t10_judge 35. Total 216; gap 96 + 20 = 116, exactly.

Root cause #1: `brand_fit.score_brand_fit` makes 3 calls per verdict on the AA-714 near-band path and on the
AA-801 median3 path; `aggregate_runs` sums them and `judge_node` wrote ONE row. Dollars matched, rows did not.

Regenerate, per stage (rows logged = 627): s1_flag_fix 78, s1_generate 64, s1_itinerary_nudge 97, s1_judge 85,
t10_judge 82, t2_flag_fix 21, t2_generate 24, t2_itinerary_nudge 21, t2_judge 29, t9_repair 54, t9_write 72
(f10_embed 82 rows are role `embed`, s1_grounding are Jev). The gap of 188 is consistent with the same cause:
about 65 near-band S1 verdicts x 2 + 29 T2 verdicts x 2 = 188. This stays an estimate until the orchestrator's

runs — the stored `brand_fit_score` is the MEDIAN, not the first score that triggered the repeat, so only the
log events are exact.

The evalpatch relabel does NOT drop rows: it keeps all 15 parameters (`test_aa729_golden_set` asserts it).

## Decisions

- **Invariant: one row per BILLED provider response.** Returned to the caller → the caller writes the row
  (unchanged). Billed but unusable inside the gateway (a route attempt that raised after the provider billed
  it, or a single-model generate() that raised) → the gateway writes the row itself. Gateway-internal retries
  that end in a usable reply (the Converse schema retry) fold into that one row, with the cost of both
  requests and `LLMResponse.provider_requests = 2`.
- **Exclusions, documented:** a Jev verdict-cache hit (no provider call; `decide` logs only what it asked), a
  streaming call that broke before usage metadata arrived (cost unknown; it stays a warning event), S1 Bedrock
  Batch (never ran, AA-624; registered in the guard test as an exclusion that must log once enabled), and a
  malformed embedding response inside `embed()`'s route (billed, a fraction of a cent; it falls to the next
  model as before — noted, not fixed here).
- **Failure / extra rows never carry an ok-rate key.** `admin_llm_ops._TREE_SQL` counts a row as ok-eligible
  when its `quality_signal` HAS any of passed / status / json_parsed / output_parsed / landed_in_clamp /
  meta_landed_in_band / required_markers_present / produced_statement (even with a null value). Billed-failure
  rows carry `billed_unusable: true` + `error`; extra judge runs carry `verdict_row: false`. So the admin
  ok-rates do not move. `call_log.OK_RATE_KEYS` holds the list; `billed_unusable_rows` strips them.
- **Every writer goes through the module `_INSERT_SQL` looked up at call time** (`record_call`, and the new
  `record_calls` with `executemany`), so the AA-729 relabel covers billed-failure and batch rows too.
- **`record_call_sync` under a running loop** (resumed work): a short-lived non-daemon thread running its own
  `asyncio.run()`, inside a COPY of the caller's contextvars (job id + tenant are row fields), with a strong
  reference held in `_PENDING_THREADS` until it ends. Chosen over the plan's "keep a reference to the
  `ensure_future` task": a task on the caller's loop is still cancelled when the caller's `asyncio.run()`
  closes that loop; a thread is not. `wait_for_pending_writes()` joins them (tests, scripts).
- **Gateway rows are fire-and-forget** (same background helper), so a slow or down DB never delays the next
  model of a route. Role = the stage config's role, else `writer`. `quality_signal` = `{gateway_attempt: true,
  billed_unusable: true, error, position, model, account[, provider_requests][, shadow]}`.
- **The billed usage is found through the exception chain** (`_billed_usage_of`): the legacy chain wraps a T3
  OpenAI failure in its own `RuntimeError(...) from e`.
- **Judge rows**: one verdict → one `record_call_sync` row exactly as before (no shape change, single-call
  tests untouched); several calls → `record_calls_sync` (one connection, one transaction). The verdict row has
  the unchanged `quality_signal` plus `judge_calls: n` and run 1's billing; runs 2..n are
  `{judge_run, of, verdict_row: false, brand_fit, distinct, mission}`; median3 calls billed then dropped are
  `billed_unusable` rows with `judge_run_failed: true`.
- **State `cost_usd` unchanged.** The judge's verdict cost still sums every call (incl. median3 billed
  failures). A judge that fails entirely still returns the state unchanged (its billed cost is in the log, not
  added to the tour's `cost_usd`) — kept as before to avoid moving `score_overall`-adjacent numbers in this PR.
- **F9 wrapper instead of re-indenting 130 lines**: `gate_brand_voice` is now a thin wrapper around
  `_gate_brand_voice` holding a `ledger` (`raw`, `logged`); a raise after the billed reply writes a
  `billed_unusable` row (gate under `f9_gate`, no `passed`/`status`/`gate`) and re-raises, as before.
- **evalpatch embed counter counts `_call` RETURNS, not attempts**: one return per successful `embed()`, which
  is exactly one caller row; a failed embedding attempt raises and is not counted (it writes no row either).

## Tradeoffs

- **Row-count discontinuity, on purpose.** s1_judge and t2_judge `call_count` and cost-per-call change from
  this deploy on (≈3 rows per near-band / median3 verdict instead of 1); total cost per verdict is unchanged.
  t7_debate_judge does not change (single call). Logged cost and tokens_in go UP for stages that hit the Converse
  schema retry (the first request is now priced) and for stages with route fallbacks after a billed failure
  (gateway-attempt rows). Historical comparisons across this deploy shift.
- **Broad AST detection** in the registry (any `.generate` load in a module importing LLMClient) gives a few
  false positives, each allow-listed with a reason; narrowing by receiver type would miss
  `to_thread(llm.generate, …)` and `LLMClient().generate` passed as an argument.
- **Gateway rows on a background thread**: never slow the route, but a process that exits within milliseconds
  of a failed attempt could lose the row (non-daemon threads make the interpreter wait at normal exit).
- **Judge verdict row shape unchanged** for AA-793 / AA-801 readers (they filter by `passed` / `judge_runs`);
  extra rows have no ok keys. admin_llm_ops is the only SQL reader of the ok keys (checked).
