## PR A — migration 248

### Decisions

- **Hash chain in a BEFORE INSERT trigger** (`acp_shared.audit_log_chain()`), serialized by
  `pg_advisory_xact_lock(884, 1)`; `chain_seq` = last + 1 read under the lock, no sequence (a rolled-back insert leaves
  no gap; nothing for X1 to grant). Canonical text = `concat_ws('|', prev_hash, id, chain_seq, tenant_id, actor,
  actor_type, action, resource_type, resource_id, details::text, created_at UTC to µs, http_method, route, status)`,
  NULLs as `''`, sha256 hex. `details::text` is jsonb's normalised text, so the Python verifier reads it from the DB
  (no attempt to re-serialise jsonb in Python).
- **Append-only** = one function raising SQLSTATE 42501 for BEFORE UPDATE / DELETE (row) and BEFORE TRUNCATE
  (statement). Not SECURITY DEFINER, `search_path = pg_catalog, acp_shared`, EXECUTE revoked from PUBLIC (SEC-4, same
  shape as 243's key guard). The chain trigger runs as the inserting role, so that role needs SELECT + INSERT on the
  table (master today; X1 244 gives cis_app SELECT/INSERT/UPDATE/DELETE on all tables — the triggers refuse the last
  two).
- **Enum** gets `staff`, `machine` (ADD VALUE IF NOT EXISTS inside the transaction; neither used in the file).
- **The type / `actor_type` column did not exist in CI**: 021 runs before 030 creates `audit_log`, so the whole 021
  file fails when files replay in number order (conftest swallows it). 248 creates the type (all five values) and the
  column when missing — a no-op on Dev, where both exist. Found by the first local run (the type-owner guard raised).
- **`shared.cost_explorer_app_snapshot`** is a new table, not a column on `shared.cost_explorer_snapshot`: the old
  table's readers and its retention rule key on (account, service, day); adding a tag dimension would change both.
  Index `(period_start, app_tag, service, fetched_at DESC)` serves the "newest fetch per key" read and the future
  superseded-fetch retention rule. `REVOKE ALL … FROM aa_app_user` (SEC-3, 007b default ACL); the guard allows only
  the owner and cis_app (244's default privileges may land first on another DB).
- **Test cleanup**: `tests/integration/_audit_cleanup.py` `delete_audit_rows(db, where_sql, *args)` deletes in one
  transaction with `SET LOCAL session_replication_role = replica` (superuser test DB only). The 7 teardowns the plan
  listed were all the DELETEs on `audit_log` in `tests/` (grep `-B2` for multi-line ones found no more).

### Changed (vs the plan)

- Guard 0 tolerates a missing `audit_actor_type` (created in step 1) instead of raising — see above.
- The new-table grant guard allows `cis_app` (plan said "no grants"), so a DB where X1 244 applied first still passes.
- Index on the snapshot table is the 4-column one above instead of `(period_start, app_tag)`.

### Tradeoffs

- **Serialization**: every audit insert waits for the previous inserting transaction to commit. Inventory S243 of
  every writer (`write_audit_log(` + raw `INSERT INTO acp_shared.audit_log`, api/ services/ shared/ scripts/):
  - autocommit / pool writes (lock held for one statement): staff_invite_email_job, trip_reallocation, v1_publish,
    v1_integrations, v1_content_writing, v1_tours 668/913, main.py tenant login (try/except), content writing
    `_insert_placeholder_piece` / `_finalize_piece` (no explicit transaction), piece edit (written after commit),
    role_config / catalog (own short transaction, audit last);
  - inside a transaction, audit row last or followed only by short DB statements: admin.py onboard / PATCH tenant
    (several audit rows interleaved with `UPDATE shared.tenants` on the same row) / brand / key rotate / offboard
    (then `DELETE FROM shared.jev_tenant_allowlist`) / restore, admin_decisions jev credit, admin_content_quality
    (sentence edits, regenerate angles — the job is enqueued BEFORE the audit row, place cards), slate subject pick,
    v1_tours rewrite (job enqueued after the transaction), v1_social gate3 (executemany at the end),
    staff_directory (Cognito calls run after the commit — `steps` lambdas), staff_invite.enqueue_invite.
  - No call site makes an HTTP / LLM / Cognito / S3 call after its audit insert inside the same transaction. Deadlock
    is possible only if a transaction holding the chain lock then waits on a row lock held by another transaction
    that is itself waiting for the chain lock; Postgres detects it (deadlock_timeout 1 s) and aborts one. Not seen in
    any of the paths above (each locks its own rows before its audit row). New code must keep the audit row last
    (QRY-4) — said in the migration header.
- **Isolation level**: correct under READ COMMITTED only; under REPEATABLE READ the unique index on `chain_seq`
  turns a stale read into an error, never a silent fork.
- **Tamper resistance is partial until X1**: the owner `aa_cis_admin` (rds_superuser member) can drop/disable the
  triggers or use `session_replication_role`. The chain makes edits detectable, not impossible; stated in the header.
- `coalesce(x, '')` makes NULL and '' hash alike, and `|` inside a field is not escaped. Acceptable: the chain's job
  is to detect a changed or removed row, and UPDATE/DELETE are refused anyway.

## PR C — backend (health, worker SHA, staff audit middleware, Platform routes, cost per app)

### Decisions

- **`/health`** keeps `status` first and `"ok"`; adds `git_sha` (`shared.sentry_init.release()` = `APP_GIT_SHA`, already
  baked by deploy-dev `--build-arg GIT_SHA`). **`/health/ready`** (public, allow-listed in the S241 auth test):
  `SELECT max(version::int) … WHERE version ~ '^[0-9]+$'` — numeric CIS keys only (critic: bk-/tp-/rl- rows) — 200
  when ≥ `REQUIRED_CIS_SCHEMA = 248`, else 503 (`schema_behind`, or `db: error`); 5 s in-process cache incl. failures.
- **Worker SHA** is written once, at registration (`worker_register(..., git_sha)` upsert), not on each heartbeat:
  the SHA never changes for a process. `worker_health()` returns it, so `/admin/job-runner/workers` shows it.
- **Deploy gate helper** `shared/jobs/worker.py deploy_gate_status(pool)` extracted from the route (no copy); the
  CI route and the Apps card call the same function.
- **Middleware position**: registered BEFORE `StaffBearerMiddleware` in main.py, i.e. INSIDE it (plan said "wraps"):
  StaffBearer passes a *copied* scope with `state.staff_identity`, so only an inner middleware can read the verified
  identity and the `route` the router writes into that scope. Consequence: requests StaffBearer itself refuses
  (bad Cognito token 401/403/503) are not audit rows; they stay in the `staff_bearer_refused` log line.
  Rate-limited (429) and policy-denied (403) calls are rows.
- **Actor**: Cognito identity → `admin:<id>` (`auth=cognito`); else `x-admin-user-id` → `admin:<id>`
  (`legacy_unverified`); role header only → `staff:unknown`; no role → `machine` (`machine.request`).
  `tenant_id` left NULL on purpose (the Tenant 360 Audit tab reads by tenant_id and should keep showing domain
  events only). The write is a separate autocommit statement after the response, bounded by 3 s.
- **`write_audit_log`** gained optional `actor_type / http_method / route / status`; without them it runs the
  exact old SQL (no behaviour change for the ~40 existing callers or their SQL-asserting tests).
- **Router** `admin_platform_ops.py` (not `admin_platform.py`, the AA-816 lane's file), no include prefix, POLICY:
  apps → `ops.read`, audit + verify → `audit.read`, cost → `spend.read`. Snapshot regenerated (+5 entries).
- **Verifier** recomputes in Python from DB columns (`details::text` read from the DB); reports the first bad
  `chain_seq` and why (content, link, missing rows, wrong start). Full-chain result cached 60 s; `from_seq` never.
  It also splits rows without `chain_seq` at the chain boundary (248's `schema_versions.applied_at`, else the
  genesis row's `created_at`): older ones are `pre_chain_rows`; newer ones are `unchained_after_genesis` (+ up to
  10 ids) and make `ok` false — such a row can only come from an insert with the trigger skipped.
- **Per-app cost module** (critic finding 5: AA-884 owns it, AA-858 only reads). Signature for AA-858:

  ```python
  from api.services.platform_cost import cost_by_app
  async def cost_by_app(pool, month: str | None = None, *, redis=None, refresh_if_stale: bool = True,
                        now: datetime | None = None) -> dict
  # -> {"month", "period_start", "period_end_exclusive",
  #     "aws": {"account_id", "has_data", "total_usd", "covered_from", "covered_to", "fetched_at", "untagged_usd"},
  #     "apps": [{"app", "kind": app|llm_app|shared_tag|other_tag|untagged, "label", "aws_usd", "aws_bedrock_usd",
  #               "services": [...], "aws_tags", "ai_usd", "ai_in_aws_acc2_usd", "ai_calls", "ai_by_source", "total_usd"}],
  #     "totals": {"aws_usd", "ai_usd", "total_usd"}, "llm_satellites": {"acc1", "acc3", "ce_fetched_at"},
  #     "refresh": {"attempted", "ok", "reason", "stale", ...}, "sources": {...}}
  ```

  Also `collect_apps(pool, redis, refresh=False)` / `collect_app(pool, redis, app_id)` in
  `api/services/platform_apps.py` for health. AA-858 passes its `request.app.state.redis` so the lazy refresh can
  take the lock; with `redis=None` nothing is refreshed.
- **Cost model**: `aws_usd` = CE acc2 by App tag (matches the console, Done-when c); `ai_usd` = gateway estimates by
  `quality_signal->>'app'` from `llm_call_log` (raw days) + `llm_call_daily` (rolled days, never both for a day);
  `total = aws + ai − ai_in_aws_acc2` (acc2 Bedrock — `provider LIKE 'bedrock%' AND coalesce(account,'acc2')='acc2'` —
  is already inside some tag's AWS cost, usually untagged). acc1/acc3 Bedrock CE actuals (SERVICE snapshot) are shown
  next to the estimate, not added.
- **Lazy refresh**: staleness is decided **per day** of the window from `read_app_cost_range()["day_fetched_at"]`
  (newest fetch per day): stale when a day before the last 2 days (`CE_LAG`) has no row — the stored data covers
  only part of the window — or when a day CE may still revise (fetched < 3 days after it ended) was fetched > 24 h
  ago. Redis `SET NX EX 120` lock `platform_cost:refresh_lock:v1`; lock taken / no Redis → stored data,
  `refresh.reason` says why. Every attempt leaves a per-window marker `platform_cost:attempted:v1:<start>:<end>`
  (24 h after a success — rows or none —, 6 h after an AWS error); while it is set no CE call is made and
  `refresh.skipped = "recent_attempt"`. CE: 1 request (~$0.01) per refresh (pages add requests); DAILY × TAG App ×
  SERVICE. `GET /admin/platform/cost` uses it by default (`?refresh_if_stale=false` reads only).
- `POST /admin/cost-explorer/check` also fetches the App tag for the same window (+1 request); a failure lands in
  `errors.acc2_app_tag`, the SERVICE check still succeeds.

### Review fixes (S243 fixer)

- **Major — partial coverage counted as fresh.** `_is_stale()` looked only at the newest `fetched_at`, so after a
  7-day `POST /admin/cost-explorer/check` on the empty table the month showed ~7 days for 24 h. Fixed with the
  per-day rule above (missing days before `CE_LAG` → stale; also catches a gap in the middle and a 7-day check that
  crosses a month boundary). `read_app_cost_range()` gained `day_fetched_at` (additive). Chosen over making the
  check fetch the whole month: the check keeps its own window semantics (External Spend), and the cost page is
  correct whatever wrote the rows. Tests: `test_partial_coverage_is_stale_even_when_freshly_fetched`,
  `test_only_not_final_days_age`, `test_partial_window_after_a_check_triggers_one_full_month_refresh`.
- **Minor — an empty CE answer was re-fetched on every view.** Per-window attempt marker (above). Test:
  `test_empty_refresh_is_remembered_and_not_repeated`; error TTL asserted in `test_failed_refresh_keeps_stored_data`.
  Worst case now: one CE call per viewed window per day (the current month's window end moves daily → ≈ $0.30 per
  month for the current month), at most 4/day per window while CE fails.
- **Minor — unchained rows after 248 counted as pre-chain.** `unchained_rows()` + `ok=false` (above). Boundary is
  248's `applied_at` rather than the genesis `created_at` alone: it exists before the first chained row, and a
  genesis row whose transaction began before 248 could carry an earlier timestamp. Limit (documented in the module):
  whoever bypasses the trigger can also backdate `created_at`; then the row counts as pre-chain. Tests: unit
  `test_verify_cached_flags_unchained_rows_after_the_boundary`, integration `test_unchained_row_after_248_is_flagged`.
