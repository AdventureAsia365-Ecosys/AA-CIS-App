## PR A — migration 248

### Decisions

- **Hash chain in a BEFORE INSERT trigger** (`acp_shared.audit_log_chain()`), serialized by
  `pg_advisory_xact_lock(884, 1)`; `chain_seq` = last + 1 read under the lock, no sequence (a rolled-back insert leaves
  no gap; nothing for X1 to grant). Canonical text = `concat_ws('|', prev_hash, id, chain_seq, tenant_id, actor,
  actor_type, action, resource_type, resource_id, details::text, created_at UTC to µs, http_method, route, status)`,
  NULLs as `''`, sha256 hex. `details::text` is jsonb's normalised text, so the Python verifier reads it from the DB
  (no attempt to re-serialise jsonb in Python).
- **Append-only** = one function raising SQLSTATE 42501 for BEFORE UPDATE / DELETE (row) and BEFORE TRUNCATE
  (statement). Not SECURITY DEFINER, `search_path = pg_catalog, acp_shared`, EXECUTE revoked from PUBLIC (SEC-4, same
  shape as 243's key guard). The chain trigger runs as the inserting role, so that role needs SELECT + INSERT on the
  table (master today; X1 244 gives cis_app SELECT/INSERT/UPDATE/DELETE on all tables — the triggers refuse the last
  two).
- **Enum** gets `staff`, `machine` (ADD VALUE IF NOT EXISTS inside the transaction; neither used in the file).
- **The type / `actor_type` column did not exist in CI**: 021 runs before 030 creates `audit_log`, so the whole 021
  file fails when files replay in number order (conftest swallows it). 248 creates the type (all five values) and the
  column when missing — a no-op on Dev, where both exist. Found by the first local run (the type-owner guard raised).
- **`shared.cost_explorer_app_snapshot`** is a new table, not a column on `shared.cost_explorer_snapshot`: the old
  table's readers and its retention rule key on (account, service, day); adding a tag dimension would change both.
  Index `(period_start, app_tag, service, fetched_at DESC)` serves the "newest fetch per key" read and the future
  superseded-fetch retention rule. `REVOKE ALL … FROM aa_app_user` (SEC-3, 007b default ACL); the guard allows only
  the owner and cis_app (244's default privileges may land first on another DB).
- **Test cleanup**: `tests/integration/_audit_cleanup.py` `delete_audit_rows(db, where_sql, *args)` deletes in one
  transaction with `SET LOCAL session_replication_role = replica` (superuser test DB only). The 7 teardowns the plan
  listed were all the DELETEs on `audit_log` in `tests/` (grep `-B2` for multi-line ones found no more).

### Changed (vs the plan)

- Guard 0 tolerates a missing `audit_actor_type` (created in step 1) instead of raising — see above.
- The new-table grant guard allows `cis_app` (plan said "no grants"), so a DB where X1 244 applied first still passes.
- Index on the snapshot table is the 4-column one above instead of `(period_start, app_tag)`.

### Tradeoffs

- **Serialization**: every audit insert waits for the previous inserting transaction to commit. Inventory S243 of
  every writer (`write_audit_log(` + raw `INSERT INTO acp_shared.audit_log`, api/ services/ shared/ scripts/):
  - autocommit / pool writes (lock held for one statement): staff_invite_email_job, trip_reallocation, v1_publish,
    v1_integrations, v1_content_writing, v1_tours 668/913, main.py tenant login (try/except), content writing
    `_insert_placeholder_piece` / `_finalize_piece` (no explicit transaction), piece edit (written after commit),
    role_config / catalog (own short transaction, audit last);
  - inside a transaction, audit row last or followed only by short DB statements: admin.py onboard / PATCH tenant
    (several audit rows interleaved with `UPDATE shared.tenants` on the same row) / brand / key rotate / offboard
    (then `DELETE FROM shared.jev_tenant_allowlist`) / restore, admin_decisions jev credit, admin_content_quality
    (sentence edits, regenerate angles — the job is enqueued BEFORE the audit row, place cards), slate subject pick,
    v1_tours rewrite (job enqueued after the transaction), v1_social gate3 (executemany at the end),
    staff_directory (Cognito calls run after the commit — `steps` lambdas), staff_invite.enqueue_invite.
  - No call site makes an HTTP / LLM / Cognito / S3 call after its audit insert inside the same transaction. Deadlock
    is possible only if a transaction holding the chain lock then waits on a row lock held by another transaction
    that is itself waiting for the chain lock; Postgres detects it (deadlock_timeout 1 s) and aborts one. Not seen in
    any of the paths above (each locks its own rows before its audit row). New code must keep the audit row last
    (QRY-4) — said in the migration header.
- **Isolation level**: correct under READ COMMITTED only; under REPEATABLE READ the unique index on `chain_seq`
  turns a stale read into an error, never a silent fork.
- **Tamper resistance is partial until X1**: the owner `aa_cis_admin` (rds_superuser member) can drop/disable the
  triggers or use `session_replication_role`. The chain makes edits detectable, not impossible; stated in the header.
- `coalesce(x, '')` makes NULL and '' hash alike, and `|` inside a field is not escaped. Acceptable: the chain's job
  is to detect a changed or removed row, and UPDATE/DELETE are refused anyway.
