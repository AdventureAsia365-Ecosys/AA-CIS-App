# AA-229 — Pin CIS review-queue fetch to master tenant

## Problem
HITL review tours did not appear in the admin UI. `review_queue` rows are enqueued
under the master tenant (`00000000-0000-0000-0000-000000000001`), but the three
review handlers fetched using `tenant_id = tenant.get("sub", <master>)`. When the
admin auth context carried a non-master `sub`, the fetch keyed off the wrong
tenant and returned zero rows.

## Decisions
- **Approach C (pin to master)** chosen over deriving tenant from request or
  re-enqueueing under the caller's tenant. CIS is effectively single-tenant; the
  master tenant is the canonical owner of review rows. Multi-tenant review fetch
  is explicitly deferred to ACP.
- `get_sources` deliberately left untouched (still `tenant.get("sub", ...)`) — it
  is not part of the HITL review path.

## Changed
- `api/routers/v1_pipeline.py`: 3 handlers (`get_review_queue`, `approve_review`,
  `reject_review`) now hardcode `tenant_id = "00000000-0000-0000-0000-000000000001"`
  with an AA-229 comment block. No signature/route changes.

## Tradeoffs
- Hardcoding master is a single-tenant assumption. Acceptable now; flagged in
  comments so ACP multi-tenant work knows to revisit. Avoids over-engineering a
  tenant-resolution layer CIS doesn't need yet.

## Should know
- DB verify (S3-mediated ECS Exec) confirmed all 3 pending rows live under master
  and no other tenant_id has rows — so the fix is purely a fetch-key correction,
  no data migration needed.
- Reviewer: the change is mechanical (3 identical edits). The risk is route order
  / scope, not logic — confirm `get_sources` was not altered.
