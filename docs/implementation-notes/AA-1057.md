# AA-1057 — Segment Subject liveness by any served member (GAP 1), retarget after supersede / rewrite (GAP 2)

Source: S273 system picture (root `docs/audits/2026-11-08-S273-session/system-picture/`, section 3 rows GAP 1 and
GAP 2, section 5 items 6 and 9). After-check metrics of the propagation probe: `d.segment_pick_wrongly_dead.*`,
`d.subjects_on_nonlive_route[state=used,route_current=False,tour_live=True]`, `d.angle_requests_on_inactive_atom`.

## Decisions

- **Subject rule in every gate, plus a re-seed** (both options of the audit): gates 1-9 read the Subject rule at
  once (no data change needed, so a retire never shows a false 409 / flag / mail, even before a recompute runs);
  the re-seed (gate 11) then moves the request's atom / trip onto a served member so T8 / T9 can work from it.
- **One SQL rule** in `shared/tour_liveness.py`: `segment_served_member_sql` (EXISTS), `segment_served_member_tour_sql`
  (the member tour, lowest id), `requests_about_tours_sql` (the derivative rule), `tour_served_sql`. Plain SQL on
  the base tables with the view's member rule (the tenant pool has no grant on `v_active_tour_atoms`, CIS 241), so
  the same fragments run on both pools.
- **A request without a Segment Subject** (Route Subject, atom request, trip request) keeps the representative-tour
  rule unchanged.
- **GAP 2 retarget as a recompute stage** (`retarget`, after `route`, on the tour and the platform pass): every
  rewrite (atomize → tour recompute), supersede (publish → recompute) and retire / restore (platform recompute)
  reaches it, and the new Route / atom ids exist by then. A sweep over all stale rows, not only the event's tour:
  the stale set is small (S273: 7 + 3), the sweep heals rows left by earlier runs, and one code path serves the
  one-off script too.
- **Route Subject rules**: `identity` (current Route of the same tour family with the same day span), else `overlap`
  (most shared Segment ids, one best). Only `picked` / `used` Subjects; a `proposed` one is replaced by the next
  proposal anyway. A target the tenant already holds (same channel; `idx_subject_unique_route`) → `taken`, no change.
- **Request rules**: the AA-990 `atom_repoint` rule first (same place, same tour family; atom id only), then the
  Segment re-seed (`slate._resolve_representative_atom`, exactly what a pick does today: atom, `trip_id`, Blog walk).
  Route requests are included in the atom re-point (their atom id is the anchor; the walk is guarded by route_guard).
- **No re-seed while the old tour is paused** (outcome `paused`): a pause or a supersede waiting for its Master comes
  back on the same tour; a re-seed to another tour would be permanent.
- **No member substitution for a paused representative either** (review fix): `REQUEST_TOURS_SQL` and
  `LIVE_POST_TOUR_STATE_SQL` substitute a served member's tour only when the representative is `retired` (the case the
  retarget stage re-seeds). With `paused` substituted too, the gate passed while the request still sat on an atom
  outside the live view, so T8 / T9 answered `atom_replaced` ("pick this part of the tour again") for something that
  comes back on its own. Now the tenant gets 409 `tour_paused` ("try again once it is out"), the served badge says
  paused, and `requests_about_tours_sql` counts the request in the pause's derivatives (queued T8 / T9 jobs cancelled,
  as before AA-1057). The retire path (bell, fan-out, mail) is unchanged.
- **Mode env `RECOMPUTE_RETARGET_MODE`** = `report` (default for now) | `apply` | `off` (review fix). With `apply`
  as the default, the first recompute after the deploy would have moved the S273 rows before the audited DRY RUN.
  So the stage ships in `report`; the one-off moves the rows (DRY RUN, then an apply pinned to the reviewed ids), and
  a follow-up one-line PR (branch `fix/aa-1057-retarget-apply-default`) makes `apply` the default. Every `apply` run
  puts `restore` (the `restore_rows` list, at most `RESTORE_LOG_CAP` = 200 per kind, `truncated` flag) in its job
  result and log, so automatic changes leave the old ids too.
- **Restore list covers every overwritten column** (review fix): a re-seed also overwrites `trip_id` and
  `route_segment_ids`, so the plan reads both (`old_trip_id`, `old_route_segment_ids`) and `restore_rows` lists them
  for outcome `reseed`. A repoint changes `atom_id` only.
- **One-off script** `scripts/aa1057_retarget_once.py` runs the same plan: DRY RUN by default (counts per outcome +
  a sha256 pin of the ids it would change; no tenant text), `--apply --expect-subjects N --expect-requests M
  --expect-subject-pin P --expect-request-pin Q` in one transaction, refused unless the counts AND the pins still match
  (same size, other ids: refused; review fix), restore list (ids only) printed before the UPDATE and re-count on a
  new connection after. It needs only `cis_app` (CIS tables), so it runs over ECS exec. `scripts/` is gitignored in
  this repo: the file is force-added (`git add -f`), like the other tracked one-offs.

## Tradeoffs

- The derivative rule runs one more EXISTS per request in the fan-out / cancel queries. `angle_gate_request` is small
  (thousands of rows) and every subquery is on an indexed key; the fan-out runs once per lifecycle event.
- A flag written when the last served member left names a tour of the event's key. If later a DIFFERENT member's key
  is restored, that key's restore does not resolve the flag; the move to draft does (gate 8, `subject_alive`), so
  the page is never drafted, but the tenant gets no "back on sale" notice for it.
- The re-seed follows the pick rule, which only considers members on the tenant's own tours (`tenant_tour_versions`);
  the Subject rule counts any served member (the Slate's `segment_dead` rule). A Segment alive only on tours the
  tenant never adopted keeps its gates open but its request stays on the old atom (T8 / T9 answer `atom_replaced`,
  "pick this part of the tour again").

## Should know

- The one-off is run after the CIS deploy (the script imports `services.acp_shared.retarget`). The stage runs in
  `report` mode until the follow-up PR, so the DRY RUN still sees the S273 rows; job results of recomputes in between
  show the same counts and pins (nothing written).
- Pause tradeoff: a paused representative of a Segment request keeps its 409 `tour_paused` even when another member
  is served; the tenant waits for the pause to end (or picks the place again). Re-seeding on a pause would move the
  request off a tour that comes back.
- Probe after-check: `d.subjects_on_nonlive_route` keeps counting Subjects on a superseded Route with no successor
  (`no_match`) and Subjects on a retired tour; `d.angle_requests_on_inactive_atom` keeps requests with no live
  same-place atom and no Segment seed. The plan's outcome counts name each.
