## STEP0 (05/09/2026)

Confirmed the issue's premise is fully correct and still holds on current `main`
(2b7eb13, migration 144 applied live).

**Code read**: `services/export/handler.py::process_export()` has a block (the
"ACP-S1: manifest.json + EventBridge on batch completion" comment, now at
lines ~259-345 — the issue's line numbers ~131-197 are stale, file has grown
since filing) that runs only when `sync_batch_completion()` reports
`just_completed=True`. It calls `services.acp.handler.upload_manifest()` (S3
put_object), then within `async with conn.transaction():` does an
`INSERT ... shared.acp_runs` + `api.services.run_context_db.write_run_context_stage()`

`services.acp.handler.publish_s1_completed()` (EventBridge `put_events`). The
whole thing is wrapped in `try/except Exception as _acp_err: logger.error(...)`
— any failure anywhere in this block is swallowed and logged, never surfaces
to the caller or blocks the real export (which already completed 3 steps
earlier: `PublishedCatalogRepository.insert()` + `raw_tours.pipeline_status =
'published'`).

## Decisions

- **Scope held to exactly the issue's 3 items** (delete ACP-S1 block in
  `services/export/handler.py`; delete `services/acp/handler.py` entirely;
  delete `tests/acp/test_run_context.py` + `tests/acp/test_s1_state_bridge.py`).
  Item 4 (dispose of the empty `aa-cis-dev-acp-events` bus) is explicitly
  "cân nhắc" (consider) in the issue, not a required action, and touches
  Infra (Terraform, separate repo/PR per this repo's IaC convention) — left
  as-is, noted as an open item in the closing comment rather than actioned.
- **Did NOT touch** `services/acp_shared/cost_utils.py`,
  `services/acp_shared/h3_rule_extractor.py`, `services/acp_canary/lambda_handler.py`,
  `api/routers/admin_pipeline.py`'s stuck-run sweep — all of these still
  contain literal SQL referencing the now-dropped `acp_shared.acp_runs`
  table (dead on arrival, same root cause as this issue) but migration 121's
  own header comment explicitly named these as "flagged for a possible
  future round, not silently expanded here" — out of scope for AA-492, which
  names only `services/export/handler.py` + `services/acp/handler.py` +
  the 2 test files. Not silently expanding scope here either; flagging in
  the closing Linear comment instead so it's visible for a future ticket.
- **`services/acp_shared/event_constants.py` (ACPEventSource/ACPEventDetailType)
  kept, untouched** — still imported by `services/acp_shared/hitl_events.py`
  (itself unrelated to this issue, not touched), so it is not orphaned by
  this change even though `services/acp/handler.py` (its other consumer) is
  being deleted.
- `tests/unit/test_s0_eventbridge.py` and `tests/test_eventbridge_contract.py`
  both import from `services.acp.handler` (`publish_s0_completed_with_retry`,
  the module itself) — the issue did not name these 2 files, but they
  directly test code being deleted, so they must go too or CI breaks with an
  ImportError. Deleting them is a direct consequence of item 2, not scope
  creep.
- `tests/unit/test_aa483_batch_completion_race.py` patches
  `services.acp.handler.upload_manifest`/`publish_s1_completed` and
  `api.services.run_context_db.write_run_context_stage` to assert the
  ACP-S1 block runs/doesn't run under a race — since the block itself is
  being deleted, these patch targets and the related assertions in that
  test file need updating (not deleting the whole file — AA-483's own race
  fix on `sync_batch_completion()` is still real and still tested).

## Changed

- `services/export/handler.py`: removed the entire "ACP-S1: manifest.json +
  EventBridge on batch completion" `try/except` block from `process_export()`
  (the `if just_completed:` body). `sync_batch_completion()` call itself and
  everything before/after it (catalog insert, `pipeline_status='published'`,
  A3 atomize background task) is unchanged. Removed the now-unused `json`
  top-level import — no longer used anywhere else in the file — and kept
  `Counter`/`json.loads` local imports gone with the block (they were
  local-scoped inside the deleted branch).
- `services/acp/handler.py`: deleted entirely (0 real callers post-deletion
  of the above block).
- `tests/acp/test_run_context.py`: deleted (tests `api/services/run_context_db.py`
  functions, which still exist as a module but whose only real caller was
  the block just deleted — see below).
- `tests/acp/test_s1_state_bridge.py`: deleted (tests the exact
  transaction-ordering behavior of the deleted block).
- `tests/unit/test_s0_eventbridge.py`: deleted (tests `services/acp/handler.py`
  functions that no longer exist).
- `tests/test_eventbridge_contract.py`: deleted (tests
  `services.acp.handler` module-level constants/shape, module no longer
  exists).
- `tests/unit/test_aa483_batch_completion_race.py`: updated — removed the 2

  `services.acp.handler.upload_manifest`/`publish_s1_completed` and
  `api.services.run_context_db.write_run_context_stage`, since the code

  AA-483's actual subject (the atomic `UPDATE ... WHERE NOT EXISTS` race
  fix in `sync_batch_completion()`) is untouched and still tested.

### `api/services/run_context_db.py` — NOT deleted (scope decision)

The issue's step 2 only names `services/acp/handler.py` for the "delete
whole file if no other real caller" check. `api/services/run_context_db.py`
(`get_run_context_validated`/`write_run_context_stage`) is a **different**
file, not named in the issue, whose only real (non-test) caller was also the
block just deleted in `services/export/handler.py`. Post-deletion it has 0
real callers left (confirmed by grep) and operates on
`acp_shared.acp_run_context`, a table also already dropped (migration 121) —
so it is equally dead. Left in place rather than deleted, strictly for scope
discipline (the issue's own text does not name this file) — flagged clearly
in the closing Linear comment as a same-shape follow-up candidate, not
silently left for someone to rediscover from scratch.

## Tradeoffs

- Deleting whole files (not just the referenced functions) for
  `services/acp/handler.py` — all 5 functions in that file
  (`upload_manifest`, `publish_s1_completed`, `publish_s0_completed`,
  `publish_s0_completed_with_retry`, `_update_run_failed`) are dead per the
  caller-check above; keeping a partially-dead file around serves no purpose.
- Left `api/services/run_context_db.py` in place despite being equally dead
  post-change (see above) — strict scope discipline over a slightly more
  thorough cleanup, since the issue text does not name this file and a
  silent scope expansion is worse practice in this repo than flagging a
  follow-up.
