# AA-978 — tenant.membership.v1 routes and Tenant 360 member routes (CIS)

Slice S2b of AA-978 (CRM-P1): CIS serves `tenant.membership.v1` to the partner CRM and gives staff the Members
routes. Storage (CIS 276) has its own notes: `AA-978-cis-276.md`. This branch is stacked on AA-977's backend branch
(both edit `catalog_http.py` / `m2m_auth.py`, SCHEDULE S250 §2) and carries a cherry-pick of the 276 commit so its
CI replays the migration.

## Decisions

- **`require_m2m(scope, realm, refused, log_prefix)` in `api/core/m2m_auth.py`.** The dependency factory, the Problem
  exception (`M2MProblem`) and its handler moved there from `catalog_http.py`. `catalog_http` keeps
  `CatalogProblem`, `problem_response`, `catalog_problem_handler` and `require_catalog_reader` as aliases (main.py,
  tests and AA-977 import them), with the same log event names (`catalog_http_refused` …) via `log_prefix`, so no log
  filter changes. One handler registration in `main.py` serves both route classes (same class).
- **Scope per route class.** `/tenant/membership/v1` needs `cis.tenant/read`; a `cis.catalog/read`-only token gets 403
  there, and a `cis.tenant/read`-only token gets 403 on `/catalog/v1` (tested both ways).
- **Snapshot = invited + active members.** Removed rows reach the CRM through the feed; the contract does not say
  whether the snapshot lists them, and the CRM treats CIS as a revocation source, so "not in the snapshot" = "not a
  member". Ordered by `created_at, membership_id`.
- **Snapshot ETag hashes the body without `as_of`.** Otherwise every call would have a new tag and 304 would never
  happen. `Cache-Control: private, no-cache` (revalidate every time: the CRM must see a removal at once) and
  `Vary: Authorization`. The lookup and the feed are `no-store`.
- **Feed cursor = `base64url("v1:<txid>:<seq>")`**, order `(txid, seq)` below `pg_snapshot_xmin(pg_current_snapshot())`
  (why: `AA-978-cis-276.md`). `next_cursor` is required by the contract, so an empty page returns the caller's cursor
  (or the start cursor): the consumer can always store it.
- **Reads on the main pool (cis_app)**, one READ ONLY transaction; `UndefinedTableError` (code deployed before 276)
  -> 503 like any storage outage (AA-977 review precedent).
- **Errors.** 400 `invalid` (bad limit / cursor / partial identity), 404 `not_found` (unknown or malformed tenant id),
  401 / 403 / 503 from `require_m2m`. 503 uses `error: unavailable`, which is not in the contract's Problem enum: the
  contract declares no 503 at all (same as the catalog's pre-1.2 state); noted for the root contract owner.
- **Staff routes in `admin_tenant360.py`.** `GET /admin/tenants/{id}/members` (`tenant.read`), `PATCH
  .../members/{membership_id}` and `POST .../members/{membership_id}/remove` (`tenant.write`, admin role only; the
  staff route-policy snapshot is updated). PATCH accepts only `content_studio_role` (`extra="forbid"`: a `crm_role`
  field is a 422). Same role / second remove = no-op, no audit row, no event. A removed membership is 409 on PATCH.
  Audit actions `tenant.member_role_changed` / `tenant.member_removed` (details: role / status before and after, never
  the identity). The staff list shows the identity only as a 12-hex sha256 fingerprint of `iss|sub`.
- **Writes lock the row (`FOR UPDATE`) in one transaction with the audit row**; the CIS 276 trigger writes the feed
  event in that same transaction.

## Tradeoffs

- A removed member's row stays (90 days, DM-7) and keeps its identity, because the `membership.removed` event and the
  CRM's matching need it.
- The feed waits for the oldest open transaction on the instance (cluster-wide horizon). Short transactions keep it
  within seconds; a long one delays it, never loses an event.
- Fingerprint, not the raw sub, in the staff UI/API: support can still match a case by computing the same hash.
