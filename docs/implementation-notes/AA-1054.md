# AA-1054 — pilot fence (S297 slice, lane l9-pilot-fence)

Tech lead decision S295 (sec-Q11): disable the Dev-only E2E identities on the pilot day, not at go-live, and add a
shared `is_pilot` fence for CIS and Booking. This slice builds the fence; it removes no E2E exception, allow-list or
bridge code (the E2E suites still need them until the pilot day).

## Decisions

- **One switch in the CIS settings registry**: `cis.platform.pilot_e2e_fence` (CIS 495; bool, default off, area
  platform, maker-checker, impact high, no env override: an env var must never open the fence again). Edits are
  audited by the registry (proposer, approver, reason, history on Platform › Settings).
- **Booking reads it through a contract view, not a grant**: CIS 496 `catalog.v_pilot_fence_v1` (one row: `fence_on`,
  `version`, `effective_from`), SELECT to `booking` only, catalog recipe. catalog_owner gets two narrow SELECT policies
  for this one key (named without "catalog_owner" so CIS 415's closing check, which lists that pattern, is unaffected).
  A stored non-boolean reads `fence_on` true; no definition row gives no row (Booking then refuses, fail closed).
- **Who is fenced**: any row or token address of the E2E mailbox domain (`e2e_staff.E2E_MAIL_DOMAIN`), any local part.
  This includes A10 (`e2e@`, a plain `content` row that no other E2E rule marks), future E2E addresses and look-alikes.
- **Where**: `staff_identity.resolve_staff` right after the row is loaded, before rules 5b-5f (the bearer middleware
  and `/auth/verify-admin` both go through it). Also `e2e_staff.dev_only_e2e_environment()` answers False while the
  fence is on, so every other E2E exception that asks it closes without touching each call site.
- **Refusal reason**: 403 detail and log reason `e2e_pilot_fence`; the BFF maps it to `/login?error=pilot_fence` with
  an English and Vietnamese message.
- **Fail closed on an unread switch (review fix pass)**: `pilot_fence.state()` answers on / off / unknown. Off only on
  a confirmed false (an approved value, or the compiled default once the reader holds a snapshot read from the
  database). Unknown when the process has a settings pool but no snapshot (a new task before its first refresh, or
  every refresh failed) or the stored value was refused by the definition: E2E identities get 403
  `e2e_pilot_fence_unknown` (the AA-Booking reason) and `dev_only_e2e_environment()` answers False. Before deciding,
  `check()` (now async) asks `shared.settings.ensure_loaded()`, one non-forced read when no snapshot is held, so a
  new task does not refuse the E2E suites only because its background refresh has not run yet. Without a pool (unit
  tests, scripts) or under `ENVIRONMENT=test` the compiled default counts as confirmed. `shared/settings/reader.py`
  is untouched (the byte copy AA-Partner and AA-TripPlanner-Web vendor): the new `installed()` / `loaded()` /
  `ensure_loaded()` live in `shared/settings/__init__.py`.
- **The academy is fenced too (review fix pass)**: `/learn/v1` resolves its learner without `resolve_staff`, so
  `learn.learner_ctx` calls `pilot_fence.check()` before it writes a learner row; A10 (a plain `content` row that
  `is_dev_only_e2e_address` does not mark) would otherwise keep learning as a real learner. The contract's error code
  stays `forbidden` (learn.http.v1 has a closed error enum). Sweep: no other staff token path resolves staff outside
  `resolve_staff` (the tenant-assignment E2E check is an admin action behind an already resolved actor).

## Tradeoffs

- **Unknown key reads off.** The code PR names the key in its own constant (`pilot_fence.PILOT_E2E_FENCE`) so it is
  CI-green without the migration PR; a build without CIS 495's compiled default reads off (logged
  `pilot_fence_switch_unknown`) instead of fencing every E2E suite. Once the migration PR is on main (it merges first)
  the key is always known and the reader falls back to the compiled default (off) or the last snapshot, never to
  "unknown". A unit test checks the two constants match once `api.core.pilot_fence_settings` exists.
- **Unknown refuses the E2E suites, not real staff.** A task whose settings reads keep failing refuses the E2E
  identities (the database is unreachable then anyway); real staff never read the switch. A Dev outage of the settings
  read therefore shows up as `e2e_pilot_fence_unknown` in the E2E runs, which is the intended signal.
- Settings cache 30 s: the switch takes effect within one cache window (plus the BFF verify cache).
