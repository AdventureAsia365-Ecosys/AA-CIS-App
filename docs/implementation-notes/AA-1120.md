## Root cause

### Every DataForSEO call path (S282, origin/main fce7693)

| Path | Paid calls | Cache before AA-1120 |
|---|---|---|
| S1 SEO fetch `seo_intelligence/handler.py::process_seo` | `fetch_all` (keywords, SERP, ideas) per tour | Redis per (seed, market) 7 days (AA-625) + `seo_context` per tour |
| S1 prefetch `s1_prefetch.py::prefetch` | `keywords_for_keywords` batched, one live SERP per tour | `seo_context` reused per tour 180 days, research store read for ideas and PAA (AA-653); **the SERP was bought once per tour, so tours sharing a seed ("trekking in <country>") bought the same SERP again** |
| Segment research phase B (volumes) `segment_research_batch.py` | live `search_volume` task, or a Standard queue task | the volume store (`acp_contract.search_demand`, `FRESH_FOR`) read once per market before chunking, in both modes (AA-1055) |
| Segment research phase C (SERP) | one live SERP per place, or Standard queue SERP tasks | the keyword's SERP row read before buying (`SERP_FRESH_FOR`); **one purchase per place, so places with the same best keyword bought the same SERP twice** |
| Standard queue `dfs_queue.py::StandardQueue` (AA-1055) | `task_post` (paid at post), `tasks_ready` / `task_get` (free) | **none**: it never read or wrote the store, never deduplicated, and kept no record of the task ids it had paid for |
| Admin SERP top-up `question_topup.py::run_topup` | live PAA-deep SERP | its own `search_demand` market, a rerun skips stored places, $3 cap in all (AA-779) |
| Retired per-place loop (`segment_research.py` `_volumes_tool`, `_serp_tool`, `_suggestions_tool`) | live volume / SERP / ideas | volume store read; SERP never cached; refused by `run_segment_research` since AA-1055 |
| AA-1055 queue trial `scripts/aa1055/dfs_queue_trial.py` | one task of each kind, posted by hand through `queue._post` | none, on purpose (adhoc measurement) |

### Why the queue path "bypassed the cache"

Three separate things, two real and one in the ledger:

1. **Paid tasks were lost and bought again.** A queue task is paid when it is posted; its answer is collected later
   with free polls. Nothing recorded which task held which keywords. When the wait did not finish (the job's
   `max_attempts=2` retry, a worker restart or deploy during the up-to-3,600 s wait, the queue timeout), the store got
   nothing for those keywords, so the next attempt or run posted and paid for them again. AA-1055 only avoided
   re-posting within the same run.
2. **The same SERP was bought for several places.** Phase C bought one SERP per place for its best keyword; two
   places with the same best keyword (a town and its pier, a gorge and its trail) paid twice in the same run. The
   S1 prefetch did the same per tour for a shared seed.
3. **The ledger hid the cache hits of the queue path.** Phase B logged its store hits as ONE `cache_hit` row per
   market per run under the **live** label `search_volume_bulk`, even in queue mode; phase C logged its fresh-SERP
   skips not at all; the per-place loop of October logged no hit row although it read the store. So every
   `search_volume_bulk_queue` / `serp_advanced_queue` row is `cache_hit = false` by construction, and "10 cache hits
   in October" counts rows, not keywords (one row stood for up to 1,000 keywords).

### Reading the issue's numbers (to be confirmed by the replay, live step)

- **"216 of 335 live calls repeat an endpoint + keyword + location pair, one pair 64 times"**: a queue post and a bulk
  volume task log `keyword` NULL (one row holds up to 100 SERPs or 1,000 keywords), so every such row of one location
  is the same "pair". On 09/11 alone the 171 queue rows fall into about 7 (endpoint, location) pairs: about 164
  "repeats" by construction. The 64 matches the 65 `serp_advanced_queue` posts, all US, keyword NULL. The replay
  prints the repeat count split by `keyword IS NULL`.
- **"10.04 USD on 09/11 from one segment_research run"**: the S274 session log lists about seven runs that day, each
  approved with its own cap: the first R1 that died on the LLM route after 4.52 USD of DataForSEO (lesson S274), R1
  US 1.62, UK 0.48, AU 0.48, then R2 DE 0.96, FR 0.96 and NL. The replay prints one block per `segment_research` job
  of the day, with what each paid, what reached the store ("paid, not stored" = bought and lost or bought twice) and
  what the AA-1120 planner would buy.

## What was built

- **`services/seo_intelligence/research_cache.py`** — the one research cache: `ResearchCache.volumes` / `serps`
  (fresh reads within the windows), `put_volumes` / `put_serp` / `put_serp_answer` (the only writers of research
  volumes and SERPs; the SERP write resets the Segment caches, AA-630 / AA-631), `log_hits` (a 0 USD `cache_hit` row
  under the endpoint label the run buys through), `pending_tasks` (queue tasks paid for within the recovery window,
  read from the post rows' meta `posted`), `dedupe`, `fresh_windows` / `volume_fresh_for` / `serp_fresh_for` (the
  settings), and `DFS_CALL_SITES` (the guard's registry).
- **`dfs_queue.StandardQueue(client, *, cache=...)`** — `cache` is required (None only for the adhoc trial).
  `volumes` / `serps` deduplicate their asks, read the store, collect free the paid-but-uncollected tasks of earlier
  runs (`task_get`), post only the rest, write every answer back before the caller sees it, and log their hits under
  `search_volume_bulk_queue` / `serp_advanced_queue`. Every post row's meta now holds `posted: [{id, keywords,
  location_code}]`, so the ledger shows which keyword each paid task carried.
- **Phases** — phase B reads through the cache and logs hits under the run's label; the live purchase reads the store
  again just before buying and writes back (`_purchase_volumes`). Phase C buys ONE SERP per distinct best keyword
  (`_serp_targets`, `serp_shared_keyword` in the result), logs fresh skips as hit rows, and in queue mode treats a
  `CachedSerp` answer as fresh. The freshness windows of the plan (`_fresh_tiers`, `_plan`), the coverage guard
  (`research_coverage.measure`) and the admin SEO / tenant 360 pages read the settings (the literal 365 copies in
  `admin_seo._FRESH_DAYS` and `admin_tenant360.FRESH_DAYS` are gone; the settings-lint rest baseline shrinks by two).
- **S1 prefetch** — one SERP per (seed, location): another tour's reusable `seo_context` row with the same
  `cache_key` (younger than `S1_SEO_REUSE_DAYS`), then this run's answers (`seed_serps`, `_tour_serp`,
  `serp_reused` in the summary).
- **Pre-run estimate** — `research_estimate.estimate_deduped` (0 USD store reads): distinct uncached keywords per
  market, one SERP per distinct best keyword not fresh, posts of 100 in queue mode, `calls` (ledger rows) and
  `dfs_usd`. `run_segment_research` returns it as `estimate.deduped` in the preview and the run; `estimate_plan` stays
  the upper bound for the USD cap and the balance check.
- **Guard** — `tests/unit/test_aa1120_dfs_cache_guard.py` (AST): every paid DFS call (client methods on any
  receiver; `volumes` / `serps` / `_post` on a queue) must sit in a function listed in `DFS_CALL_SITES`; a
  `research_cache` site's top-level function must read and write through a cache; no stale entry; every
  `StandardQueue(...)` passes `cache=`; inside the queue the cache read comes before the first post.
- **$0 replay** — `scripts/aa1120/planner_replay.py` (READ ONLY, no app import): per `segment_research` job of a day,
  before (ledger), stored (store rows in the job window, "paid, not stored"), after (the plan rebuilt from the log and
  the keyword maps, minus pairs fresh before the job or planned by an earlier job of the day), totals with the
  reduction %, and the month's repeat pairs split by keyword NULL.

## Decisions

- One module owns the research store reads and writes; the queue gets it at construction instead of each caller
  wrapping the queue. A future caller of the queue cannot skip the store (the guard checks `cache=`).
- Queued-task recovery reads `shared.dfs_call_log` meta (`posted`) instead of a new table: the post row already
  exists for every paid post, it is small (about 3k rows), and no migration or retention row is needed. Recovery is
  bounded by its own setting (7 days by default; DataForSEO keeps a task for 30 days, the setting's maximum).
- The windows are read once per run (`fresh_windows`, `settings.aget`) and passed down (`Windows`), so one run never
  mixes two values; the admin pages read `volume_fresh_for()` per request.
- The deduped estimate is shown beside the upper bound, not instead of it: the USD cap and the balance check keep the
  conservative figure (a store write between preview and run can only lower the real spend).
- Review fix (S282): the volume write-back now runs inside the purchase (`_purchase_volumes`, `StandardQueue.volumes`),
  so it sits inside phase B's error-classifying `try`. A store error there (statement timeout, dropped connection,
  full pool) would have been split like a refused task and the halves bought again. `ResearchCache.put_volumes` now
  raises `PaidNotStored` (a non-fatal `DFSCallError`) on any store error, and `_buy` treats it like
  `QueuedTaskFailed`: the chunk's keywords fail (no log row, the places stay stale), nothing is split or bought again
  in the run. The next run collects the paid queued task (recovery), or on the live endpoint buys the keywords once.
  Tests: `test_live_phase_b_store_error_after_a_paid_volume_task_does_not_buy_again`,
  `test_queue_phase_b_store_error_after_a_paid_post_does_not_post_again` (300-keyword chunk, one paid call).
- S1 seeds are reused from `seo_context` (S1's own cache, keyed by seed and location), not written into the research
  store: a seed such as "trekking in <country>" is not a place keyword and must not land on Segments.

## Changed vs the issue

- The issue says the queue path "never reads or writes the cache". Phase B did read the store before both endpoints;
  what was missing is listed under Root cause. The fix still moves the read and write-back into the queue itself.
- "Next scheduled refresh": research is admin-triggered (AA-646); there is no schedule. Verification = the next
  approved run, plus a free preview now (`estimate.deduped`).
- Added: S1 one-SERP-per-seed, the admin pages reading the volume window setting, the post rows' `posted` meta.

## Tradeoffs

- `stats.volume_tasks` / `keywords_bought` count a chunk handed to the purchase even if a concurrent writer answered
  part of it between the two reads (rare: research runs one at a time).
- The replay's "after" uses the store rows dated in each job's window; a later run that rewrote a row moves it out.
  With 365-day windows first purchases are not rewritten.
- A live purchase whose store write fails is paid once more by the next run (the live endpoint keeps no task to
  collect). Holding the answers in memory for this run instead would log places researched that the store does not
  hold, so the next run would trust rows that are not there.
- A recovered task that is still queued (another live run posted it) is waited for; research runs with
  concurrency 1, so this only happens after a crash.
