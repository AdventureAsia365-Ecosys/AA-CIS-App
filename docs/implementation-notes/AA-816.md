# AA-816 — Staff directory (Cognito Phase 1, ADR 0006)

Plan: `AA-Ecosys/docs/audits/2026-10-18-S242-cognito-phase1/plan.md` (Stage B). Related: AA-854 (Phase 0/1
identity infra).

## Step C1 — migration 247 + NULL password_hash fails closed (S242)

### Decisions
- **Grant table, not a per-app column.** `shared.staff_app_grant (admin_user_id, app, role)`, PK
  `(admin_user_id, app)`, `app IN ('booking')`, `role IN ('admin','sales','contracting','content_creator')`
  (Booking bk-003 `staff_users_role_chk`). S241 decision Q3; the ADR text (per-app role columns) is amended
  in R1. `role` on `admin_users` stays NOT NULL.
- **FK `ON DELETE CASCADE`** on `staff_app_grant.admin_user_id`: a grant means nothing without its person.
  Staff rows are deactivated, not deleted, in practice; the other FKs to `admin_users` stay NO ACTION.
- **Timestamps** `created_at` / `updated_at` on the grant table; no `granted_by` column — the actor goes to
  the audit log (`services/acp_shared/audit_log.py`) in C6, like the rest of the admin writes.
- **Email CHECK is stricter than "ends in @adventure.asia":** the stored value must be lower-cased
  (`email = lower(email)`) and match `^[^@[:space:]]+@adventure[.]asia$` (one `@`, no whitespace, exact
  domain — no sub-domain, no look-alike). ADR 0006 says "lower-cased"; the unique index is still on
  `lower(email)` as the plan asks. Writers (link script C8, directory C6) must lower-case before insert.
- **Cognito pair CHECK** also requires `cognito_iss LIKE 'https://%'` and `length(cognito_sub) BETWEEN 1 AND 128`
  when set. Both columns must be explicitly NOT NULL in the "set" branch: the first draft
  (`iss LIKE … AND length(sub) …`) let `iss` set + `sub` NULL through, because a CHECK that evaluates to
  NULL passes. The integration test caught it.
- **Unique on the pair `(cognito_iss, cognito_sub)`**, not on `sub` alone (ADR 0006 §9): the same sub from a
  rebuilt or production pool is another identity. Test covers it.
- **`is_owner` left false for every row.** No data change in the migration; the owner flag is set by the
  link script (C8, `scripts/link_staff_identity.py`).
- **Grants / RLS:** `shared.admin_users` has no non-owner grant and RLS off on Dev (schema reference
  16/10), so the new table gets none either. X1 244 (`GRANT … ON ALL TABLES` + default privileges) covers it
  whichever lands first. The in-file guard refuses only the dangerous direction: a grant on
  `staff_app_grant` that `admin_users` lacks, or different RLS/FORCE flags. Equality was the first draft; it
  failed in the integration harness, whose conftest grants `app_user` on every `shared` table after
  migrations — a test-only grant, so a strict equality guard was environment-fragile.
- **Constraints added through `DO` blocks keyed on `pg_constraint`** (Postgres has no
  `ADD CONSTRAINT IF NOT EXISTS`), so a re-run is a no-op; the integration fixture applies the file twice.
- **Dummy bcrypt hash is now a real hash.** The old dummy (`"$2b$12$" + "0"*53`) makes bcrypt 5.0 raise
  "Invalid salt" at once, so the "constant timing" comment in `admin_login` was not true (unknown user
  answered in microseconds). `_DUMMY_BCRYPT_HASH` is a cost-12 hash of a random value that was thrown away;
  the unknown-user and NULL-hash paths both run a full compare.

### Changed
- `api/migrations/247_admin_users_identity.sql` (new): six columns, `password_hash DROP NOT NULL`, two CHECKs,
  two unique indexes, `shared.staff_app_grant`, guards 0/1, registration `247`.
- `api/routers/auth.py`: `_verify_password(raw, Optional[str])` — no hash → dummy compare, `False`; also
  catches `AttributeError`. `_DUMMY_BCRYPT_HASH` constant.
- `api/main.py` `admin_login`: passes the stored hash (or None) to `_verify_password`; denies explicitly
  when the hash is NULL; same 401 body as a wrong password.
- Tests: `tests/unit/test_aa816_admin_login_null_hash.py` (new), `tests/integration/test_aa854_admin_users_identity.py`
  (new), `tests/integration/test_aa680_booking_staff_lookup.py` (Cognito-only row case; `add_staff` takes
  a `password_hash`).

### Tradeoffs
- `text` columns + CHECK rather than `varchar(n)`: matches Booking's TEXT + CHECK rule and avoids a later
  type change; length is bounded only for `cognito_sub` (128, like `booking.staff_users.cis_user_id`).
- No index on `last_login_at` / `is_owner` — the table has a handful of rows.
- Guard compares ACLs as a subset, not equality: it cannot catch "the grant table is LESS reachable than the
  directory" (e.g. a runtime role missing SELECT). That case fails loudly at the first C6 request and is
  covered by X1's `test_x1_cis_app_privileges` after 244.

### Should know
- **Apply order:** the Infra byte copy (`db/migrations/cis/247_admin_users_identity.sql`, plan I4) must land
  the same day. The runner only checks "already applied", so 247 may be applied before X1 244–246; tests
  apply in sorted order (247 last), so CI and Dev can see different orders — the guards are written for both.
- **Tell the X1 lane:** 245 (ownership transfer to `cis_owner`) and the 246 probe must cover
  `shared.staff_app_grant` and the new `admin_users` columns.
- Role lint (Infra `run_migration.py --inspect` on a `cis/247_…` path) passes: one BEGIN…COMMIT, no role
  switch, no catalog view DDL.
- The integration test applies 247 as a NOSUPERUSER stand-in of the RDS master when the test user may create
  roles (CI). A local test user without CREATEROLE applies it as itself (still a plain owner). Both paths
  were run in S242 (local PG 16 non-superuser, plus a throwaway superuser PG 16 cluster: 243 + 247 + aa680
  tests, 68 passed).

# AA-816 — CIS staff on Cognito WORKFORCE (ADR 0006 Phase 1)

Plan: `AA-Ecosys/docs/audits/2026-10-18-S242-cognito-phase1/plan.md` (stage B). Also Refs AA-854.

## C2 — multi-issuer staff token verifier (not wired), branch `feat/aa854-staff-token-verifier`

### Decisions
- **Two modules.** `api/core/identity_verifier.py` is app-neutral (stdlib + PyJWT only) so it can be copied
  byte-identical into AA-Booking (ADR 0006 §8 rule 9). `api/core/identity_config.py` is CIS-only: the staff
  surface WORKFORCE x {cis-admin, breakglass}, env overrides, a lazy singleton and the start-up prefetch hook.
- **HTTP: stdlib `urllib` in `asyncio.to_thread`, not httpx.** httpx is a CIS runtime dependency, but Booking
  has it only in `requirements-dev.txt`; using it would break the byte-identical copy. Same approach as
  Booking's `app/auth/tokens.py:http_fetcher` (5 s timeout, 256 KB cap, https only). The fetcher is injectable.
- **Logging: stdlib `logging` in the verifier** (portable), structlog in the CIS config module.
- **Env names**: `COGNITO_WORKFORCE_ISSUER`, `COGNITO_CIS_ADMIN_CLIENT_ID`, `COGNITO_BREAKGLASS_CLIENT_ID`
  (same `COGNITO_` prefix as the BFF's client-secret vars). Blank = default. Nothing needs setting on Dev.
- **One verifier instance = one route class.** `MultiIssuerVerifier` holds `IssuerConfig`s, each with its own
  `client_ids`; this is how "each route class declares the exact (issuer, client_id) pairs" (rule 6) is
  expressed. A tenant-route verifier later is a second instance with the EXTERNAL issuer.
- **Bridge profile supported by config** (`audience_claim="aud"`, `token_use=None`, `groups_claim="cis_role"`)
  so Booking Phase 2 can accept CIS-minted tokens and Cognito tokens side by side (rule 8). For Cognito,
  `aud` is not checked at all (access tokens have none; `verify_aud=False`).
- **Header handling**: `alg` must be exactly `RS256` before any key lookup (rejects none / HS* / RS384 / PS* /
  ES*). `jku`, `x5u`, `jwk`, `x5c` are ignored (never read), per ADR wording "ignore"; tests prove an embedded
  `jwk` or a `jku` URL is never used or fetched.
- **Cache timings**: unknown-kid refetch at most once per 60 s (ADR rule 3; Booking uses 30 s). TTL 1 h for
  routine refresh (Cognito rotates rarely). Extra **cold retry 5 s** while no key set has ever loaded: every
  request is failing with 503 anyway, so a quicker retry after a start-up NAT blip shortens the outage at
  negligible cost. A failed or empty fetch keeps the last good key set.
- **Fast path without the lock**: a fresh key set holding the kid returns immediately; only refreshes take the
  per-issuer `asyncio.Lock`.
- **Leeway** 30 s default, `IssuerConfig` refuses > 60 s.
- **`enforce_minimum_key_length=True`** on decode (RSA < 2048 bits rejected). Requires PyJWT >= 2.10-ish; it
  is ignored by 2.12.1 (the local venv), hence the pin.
- **Principal** = `(iss, sub, client_id, groups, email, username)` per the task. `email_verified` (ADR §8
  rule 7) is not included: the WORKFORCE pre token trigger adds only `email` to the access token
  (`workforce.py:119`), and the trigger already refuses unverified/out-of-domain emails.

### Changed
- `requirements.txt`: `PyJWT[crypto]>=2.8.0` -> `PyJWT[crypto]==2.15.1` (same as Booking). 2.15.1 is the
  latest release, so a freshly built image most likely already had it; the pin makes it explicit.
- `CONTEXT.md`: short paragraph under "Staff roles and permissions".
- No change to `api/main.py`, routes, middleware or task definitions: zero behaviour change on deploy.

### Tradeoffs
- urllib-in-thread vs httpx: one thread per fetch (rare: start-up, hourly, rate-limited unknown kids) vs
  portability. Portability wins.
- Verification serialises behind the lock only during a refresh; a slow JWKS (up to 5 s timeout through the
  NAT) can delay requests for that issuer once per minute at worst while stale. Accepted; matches Booking.
- `verify()` decodes the payload twice (unverified for `iss`, then verified). Negligible cost; keeps the
  issuer selection explicit.

### Should know
- (Superseded by the review round below: the prefetch is now started from the lifespan.)
- `get_cis_staff_verifier()` is built from env at first use; call `reset_cis_staff_verifier()` after changing env
  in tests. Its `asyncio.Lock`s bind to the first event loop that uses them (one loop in production).
- Errors map: `InvalidToken` -> 401, `AuthUnavailable` -> 503 (no key set ever loaded for that issuer).
- The Dev constants must match `terraform output` / the pool's `/.well-known/openid-configuration`
  (identity.tf:907-908). Not re-checked live in this step (no AWS calls).
- Tests run locally against PyJWT 2.15.1 (scratch install); with the venv's 2.12.1 only the small-RSA-key test
  fails because that PyJWT ignores `enforce_minimum_key_length`. CI installs the pin.

### Review round 1 (C2) — applied / rejected

**Applied**
- **Prefetch at start-up (major).** The plan's C2 check ("startup log shows the JWKS was prefetched") needs
  the hook called. `api/main.py` lifespan now calls `start_cis_staff_jwks_prefetch()`: a background task
  (`aa854-identity-jwks-prefetch`) so a slow fetch through the NAT never delays start-up; None when
  `ENVIRONMENT == "test"`; cancelled at shutdown by `stop_cis_staff_jwks_prefetch()`. It wires nothing into
  auth, so behaviour is unchanged. The two existing dev-env lifespan tests (`test_aa751_ops_metrics_sampler`,
  `test_aa859_main_pool_gauge`) patch it to None so they never reach the real Cognito JWKS.
- **`Principal.email_verified: bool | None`** (ADR §8 rule 7), so the byte-identical Booking copy needs no
  module change when EXTERNAL tokens arrive. Accepts a real bool **and the exact strings `"true"` /
  `"false"`**, because the EXTERNAL pre token trigger emits strings (`identity_triggers/external.py:176`);
  anything else is None. WORKFORCE access tokens carry no `email_verified` today -> None.
- **JWKS redirects refused**: the fetcher uses an opener whose redirect handler raises, and also rejects a
  response whose final URL differs from the requested one.
- **Over-long `email` / `username` dropped, not truncated** (> 320 chars -> None), since C3 matches staff rows
  on `lower(email)`.
- **Stale key served without waiting**: when the set is past its TTL but holds the `kid`, and a refresh is
  either in flight or not due (failed < 60 s ago), the stale key is returned without taking the lock. A slow
  or failing JWKS now costs at most one waiting request per 60 s window instead of every request.
  Tests added: single-flight on a cold cache (10 concurrent verifies -> 1 fetch), stale -> refresh succeeds,
  stale key served during an in-flight refresh, failed refresh does not make later requests wait.
- **`test_small_rsa_key_rejected` skips on PyJWT < 2.15** with a reason (the shared CIS venv has 2.12.1;
  CI installs the 2.15.1 pin).

**Rejected / deferred**
- **Rename `Principal.iss` -> `issuer`**: rejected. The approved plan (C2) specifies `(iss, sub, client_id,
  groups, email)`; the ADR naming difference is noted in the `Principal` docstring instead of changing the
  field and every caller.
- **Bad `COGNITO_WORKFORCE_ISSUER` -> 500 once wired (finding 6)**: deferred to C3 as the reviewer suggested.
  C3 must map a verifier construction failure to `AuthUnavailable` / 503 (or fail start-up loudly when an
  override is set but invalid). C2 is unaffected: the prefetch hook swallows it and nothing else calls it.

### Should know (review round 1)
- After deploy, the C2 evidence is the CloudWatch line `identity_jwks_prefetched issuer=https://cognito-idp.
  us-west-1.amazonaws.com/us-west-1_bCcFvbSOS keys>=1` from the API task (not the worker: only `api/main.py`
  starts it). `identity_jwks_prefetch_empty` instead means the issuer constant or NAT path is wrong.
- Any future pre token trigger that adds `email_verified` must emit a JSON boolean or the exact string
  `"true"`/`"false"`; other spellings read as unknown (None) and never count as verified.

## C8 — `scripts/link_staff_identity.py` (link the first staff rows to their email)

### Decisions
- **Self-contained S3-exec script** (python3 + asyncpg + boto3). DSN read straight from Secrets Manager
  `aa-cis/dev/rds` with boto3 (plain DSN), parsed with `urlparse` (user/password `unquote`d), `ssl="require"`.
  It does not import `shared.secrets`, so it also runs when `/app` is not importable.
- **Default is `--dry-run`**: lists every `shared.admin_users` row (never selects `password_hash`) plus the
  plan. `--apply` re-reads the rows `FOR UPDATE` inside one transaction and recomputes the plan under the lock;
  any error aborts with no write.
- **Mapping syntax** `username=email[:Display Name]` (repeatable `--map`); the display name may contain `:`;
  leaving it out keeps the current display name. `--map-b64` takes the same entries base64 UTF-8, one per line,
  because a Vietnamese name with spaces inside the nested quotes of `ecs execute-command` is fragile.
- **Email rule mirrors the DB check** `admin_users_email_chk` (lower-cased, `^[^@\s]+@adventure\.asia$`,
  fullmatch). Duplicate usernames / emails in the mapping, an email already held by another row, and an email
  change on a row that already has `cognito_sub` are errors (a linked row's email changes through the staff
  directory, not this script).
- **`--owner <username>`** sets `is_owner=true` on that one row only (`WHERE id=$1 AND is_owner=FALSE`, must
  touch exactly 1 row). It never clears another owner (break-glass is also an owner, plan C7). Refused on an
  inactive row; warns when the row has no email (cannot sign in with Cognito).
- **Never writes** `cognito_iss`, `cognito_sub`, `password_hash`, `role`, `is_active` (guard test on the SET
  clauses).
- **Audit**: one `acp_shared.audit_log` row per change in the same transaction, through the existing helper
  `services.acp_shared.audit_log.write_audit_log` (importable from `/app`); if it cannot be imported, an inline
  INSERT with the helper's exact columns. Actions `admin_user.email_linked` / `admin_user.owner_granted`,
  `resource_type=admin_user`, `tenant_id` NULL, actor `script:link_staff_identity` (`--actor` to override,
  <= 64 chars); details hold username, before/after and `issue: AA-816`. The report says which writer ran.
- **Report**: JSON on stdout (`usernames`, `rows_before`, `plan`, `errors`, `warnings`, `applied`,
  `rows_after` on apply); `--s3` also `put_object`s it to `s3://aa-cis-bronze-005097885195/scripts/s242_link_report.json`.
  Exit 0 = no errors, 2 = errors (nothing applied).

### Changed
- The plan says "sets email and display_name for Nghiệp's row"; the script takes any usernames on the CLI,
  so the `e2e-claude-code` row (D2) can be linked later with the same script.

### Tradeoffs
- Action constants live in the script, not in `PlatformAuditAction`, to keep this PR script-only; C7 (staff
  directory writes) can promote them to `services/acp_shared/audit_log.py` when it adds the UI path.

### Should know
- `scripts/` is gitignored: the file is force-added (`git ls-files scripts/link_staff_identity.py`).
  CI flake8 does not lint `scripts/`; the only flake8 findings locally are the single-line AWS CLI commands
  in the docstring (E501), the same as `aa856_global_profile_probe.py`.
- Current usernames are not known offline (the schema dump says ~7 rows): run `--dry-run --s3` first and read
  `usernames` in the report before choosing the `--map` entries.
