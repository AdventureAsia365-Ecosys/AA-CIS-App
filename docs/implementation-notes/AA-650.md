# AA-650 — Durable job runner (Postgres queue + worker)

Planned with Nghiệp on 28/09 (S201). Design source: ADR 0001 decision 3 (root docs repo).

## Decisions
- **Worker runs inside the API process for now (option C).** Nghiệp: Dev traffic is low and
  nothing is urgent. The worker loop starts from the FastAPI lifespan behind `JOB_WORKER_IN_API`
  (default on). The same code runs standalone as `python -m shared.jobs.worker`, so moving it to
  its own ECS service later (AA-651, deferred) is Infra-only. Durability comes from the
  `shared.job` table + reaper, not from where the worker runs.
- Entry point is `python -m shared.jobs.worker`, not `python -m worker`: the Dockerfile only copies
  `api/`, `shared/` and `services/`.
- API lives under `/admin/job-runner/*`: `/admin/jobs/{id}` already serves the older
  `shared.pipeline_jobs` table (AA-223, A1 run-tour). AA-652 moves run-tour onto this queue.
- First job kind: `segment_research` (its run state lived in process memory, `_run_state`).
- Claims are serialised with a transaction-level advisory lock, so the per-kind concurrency cap
  holds even when two API tasks overlap during a rolling deploy.
- A graceful shutdown (SIGTERM) releases a running job back to `queued` without counting the
  attempt. A crash is caught by the reaper once the lease expires, and that does count.

## Changed (vs. the Linear issue)
- No separate worker ECS service (AA-651 deferred, see Decisions). The "survives a forced ECS
  redeploy" check is done with the in-API worker: the old task releases the job on SIGTERM (or the
  reaper re-queues it) and the new task's worker picks it up.
- Only `segment_research` moves in this issue. T2 rewrite, T9 write, A3 atomize, A1 run-tour and
  revalidate are AA-652.
- Progress for `segment_research` is coarse (phase + result); the research code has no per-place
  progress hook yet. Redis live snapshots (ADR 0004) stay for T2/T9 and move with AA-652.

## Tradeoffs
- Postgres, not SQS (as the issue argues): transactional with the data, queryable, no new AWS
  service. The claim query takes an advisory lock so the per-kind cap is exact; with one or two
  API tasks the lock is never contended in practice.
- Lease 90 s, heartbeat 20 s, reaper every 30 s. A crashed worker's job waits at most ~2 min before
  being re-queued. Shorter leases would re-queue live jobs during long DB stalls.
- Graceful shutdown gives running jobs 20 s, then cancels and releases them. The ECS stop timeout
  is 90 s and the lifespan also drains AA-223 run-tour tasks (25 s).
- `segment_research` gets max 2 attempts: a re-run is cheap (DFS 7-day cache) but not free.
