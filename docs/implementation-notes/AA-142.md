# AA-142 — Sentry Error Tracking

## Decisions
- Used native FastAPI integration (`FastApiIntegration` + `StarletteIntegration`) instead of `SentryAsgiMiddleware` — native integration auto-scopes per-request and captures exceptions without manual wiring.
- `init_sentry()` called at module-level before `app = FastAPI(...)` so integrations patch FastAPI/Starlette before app initialization.
- Sentry context middleware (`sentry_context_middleware`) added as a second HTTP middleware after `rate_limit_middleware` — sets tenant_id, run_id, route tags per request.
- `_get_dsn()` returns empty string on any exception (boto3 credential error in local dev) → graceful degradation without crash.
- `profiles_sample_rate=0.1` included (requires `sentry-sdk[fastapi]>=1.40.0` which bundles profiling).

## Changed
- DSN secret is a plain string (not JSON) → uses `secret["SecretString"]` directly, unlike `aa-cis/dev/api-keys` which uses `json.loads()`.
- `sentry_context_middleware` wired AFTER `rate_limit_middleware` in stack (i.e., runs BEFORE rate_limit in execution order due to LIFO middleware stacking).

## Tradeoffs
- `traces_sample_rate=0.1`: low sampling to avoid Sentry quota burn in dev. Can raise to 0.5 for staging/prod.
- Calling `init_sentry()` at import time means a boto3 call on every cold start. Acceptable since it fails silently if credentials are absent.
