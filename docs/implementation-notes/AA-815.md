# AA-815 — Facebook connect UI + tenant self-unpublish (S237, portal lane item 2)

## Decisions
- **Facebook connect is a pasted Page ID + Page Access Token, not OAuth.** The Linear scope says
  "OAuth flow via existing endpoints", but the existing backend (`/v1/integrations/facebook*`,
  AA-462) takes a pasted token and stores it in Secrets Manager at `acp/social/{tenant_id}`. A Meta
  OAuth login needs a Meta app with review, redirect URIs and app secrets, so it is out of scope
  here. The form explains where to get a token (Graph API Explorer / Business settings,
  `pages_manage_posts`) and suggests a long-lived token.
- **Token expiry is not shown as a date.** Reading the expiry needs `debug_token` with a Meta app
  token, which CIS does not have. An expired token shows up through the existing classified
  test error ("Invalid or expired Page Access Token") on the status card's "Test connection".
- **Unpublish removes the post on the channel first, then flips the row.** WordPress:
  `DELETE /wp-json/wp/v2/posts/{id}` without `force`, so the post goes to the WordPress trash
  (the site owner can restore it for 30 days). Facebook: Graph `DELETE /{post_id}`. Only a
  confirmed removal flips `publish_log` to `unpublished` (`unpublished_by = 'tenant:<id>'`).
  A missing connection is a 422; unreadable credentials or a channel error is a 502, and the row
  stays `published`. The portal never says a post is gone while it is still live.
- **What counts as confirmed:** WordPress 200 with a post object in `status: "trash"`, or
  WordPress's own JSON errors `410 rest_already_trashed` / `404 rest_post_invalid_id` (the post
  is not public either way, so these return `already_gone`). A host or WAF 404 page without the
  WordPress error code raises. Facebook: only `200 {"success": true}`. Graph code 100 /
  subcode 33 means "does not exist OR missing permission", so it raises too. The tenant deletes
  the post on Facebook, and an admin force-unpublishes the row (A4).
- **No permanent delete.** If a WordPress site has its trash turned off (`501
  rest_trash_not_supported`), we do not retry with `force=true`. The tenant gets a clear message
  and deletes the post in WordPress.
- **Disconnect** (`DELETE /v1/integrations/{wordpress|facebook}`) first overwrites the secret
  with a tombstone (`{"disconnected": true}`) through `PutSecretValue`, then deletes the
  `shared.tenant_integrations` row. It does not call `DeleteSecret`, because the ECS task role
  has only `CreateSecret` / `PutSecretValue` on `acp/cms/*` and `acp/social/*`
  (AA-CIS-Infra `modules/ecs/main.tf`). A reconnect reuses the same secret name. If the
  tombstone fails, the call returns 502 and the row stays. A deleted row never points at live
  credentials. Disconnecting when nothing is connected returns `disconnected: false` (idempotent).
  The action is audited (`integration.disconnected`, best effort). It runs through
  `acquire_scoped_conn` behind its own default-off flag (`aa544:integration_disconnect_pool`), so
  it works under AA-817 RLS once that flag is on.
- **New `GET /v1/publish-log`** lists the tenant's `published` / `unpublished` rows, newest first,
  `limit` 1–200 (default 50). The Unpublish action needs a `publish_id`, and no tenant route
  returned one. The projection is tenant-safe: no `last_error`, idempotency key or actor (tenant
  sees content only). It uses `acquire_scoped_conn` behind the default-off flag
  `aa544:publish_log_list_pool`.
- **Unpublish is audited** as `content_piece.unpublished` (best effort, same as publish).
- UI lives on `/portal/t11-publish`:
  - two connection cards (WordPress, Facebook Page) side by side;
  - the pending list gated per channel;
  - a new "Published" card (kit `DataTable` + `ConfirmModal` + toast) with View and Unpublish.
  After an Unpublish the piece is back in "Ready to Publish" (`reloadSignal`). Disconnect (with a
  confirm step) is on `/portal/t11-publish/connection`, which now manages both channels.

## Changed
- **Bug fix outside the literal scope:** `publish()` looked up `integration_type = channel`
  (`'blog'`), but `v1_integrations.py` stores WordPress as `'wordpress'`. A blog piece could
  therefore never find its connection (422 "Connect WordPress"). The new `_INTEGRATION_TYPE` map
  (`blog → wordpress`, `facebook → facebook`) is used by both publish and unpublish. Without this
  fix the Done-when (publish then unpublish a WordPress post) cannot pass. It is one line in
  `publish()`, outside the AA-819 hunks (trial `git merge-tree` against the AA-819 backend branch
  is clean).
- `PublishPendingList` takes `connected: {blog, facebook}` instead of `wordpressConnected`. The
  button says "Connect WordPress / Facebook to publish" per piece.
- `useWordPressStatus` and the new `useFacebookStatus` use react-query (no setState-in-effect). A
  refresh keeps the page up instead of flashing the loading screen.
- Removed the dead `portal/page.tsx.bak.old` and the stale "static mockup" comment in
  `WordPressConnect.tsx`.

## Tradeoffs
- The list route lives in `v1_publish.py` (same `/v1/publish-log` prefix) rather than a new
  router file. The hunk is self-contained and sits above `/pending`. A separate module would have
  added a `main.py` edit for no real isolation gain.
- Unpublish reads and writes through the admin pool (`pool.acquire`), unchanged from before. Every
  statement is scoped by `tenant_id` in its WHERE clause. Moving it onto the tenant pool is AA-544
  rollout work.
- WordPress trash, not permanent delete: recoverable, and the safest default for a tenant-facing
  button.

## Should know
- **AA-819 interaction (orchestrator):** the daily publish limit (D3) counts `publish_log` rows in
  `('requested','published')` for the UTC day. Once Unpublish works, a tenant can publish, then
  unpublish, then publish again, and the unpublished rows drop out of the count. Each of those
  posts really went live, so the cap is bypassable. Suggested AA-819 follow-up: also count
  `unpublished` rows whose `published_at` falls in the same UTC day. This branch does not change
  AA-819 code.
- **Merge order:** the lane plan says to merge after the cis-backend AA-819 PR (both edit
  `v1_publish.py`). The trial merge is clean.
- **Done-when needs from Nghiệp:** a test Facebook Page plus a Page Access Token
  (`pages_manage_posts`), or acceptance of WordPress-only unpublish evidence. Also confirm that
  the WordPress test user's application password can delete posts (Editor/Author on own posts).
  Without that, unpublish returns the "cannot delete posts" 502 and the row stays published.
- No migration and no infra change. No new env vars.
- Tests: `tests/unit/test_aa815_unpublish_disconnect.py` (adapters, route ordering and failure
  paths, disconnect, publish lookup regression, list projection);
  `tests/integration/test_aa815_publish_log_sql.py` (the new SQL on real Postgres: list,
  unpublish flip, disconnect delete).
- **Review fix (S237 adversarial review):** unpublish now refuses (422, no remote call) a post
  that was published to a different WordPress site or Facebook Page than the one connected now.
  WordPress post IDs are per-site integers, so after "Change credentials" to another site,
  `DELETE /posts/{external_id}` would have trashed an unrelated post on the new site. The check
  compares the host of `publish_log.external_url` with the connected `wp_url` (a leading `www.`
  is ignored), and the Facebook `{page_id}_{post_id}` prefix with the connected Page. A WordPress
  site whose public URL host differs from its REST host (headless setups) is refused too; that
  failure is safe (the row stays published, the tenant removes the post on the site).
- **`aa544:integration_disconnect_pool` must stay off.** `aa_app_user` has only SELECT on
  `shared.tenant_integrations` (007b default privileges) and the table has no RLS policy. With
  the flag on, the DELETE would fail after the secret was already tombstoned. Turning it on needs
  a GRANT DELETE + RLS migration first (AA-817 follow-up).
