# AA-680 (staff half) — S245: live refusal evidence, bridge kept

## Decisions

- Owner decision S245: keep the CIS → Booking bridge (`POST /auth/booking-token`, `GET /auth/.well-known/jwks.json`,
  `api/core/booking_jwt.py`, the signing-key secret). Booking Vercel previews have no Cognito callback, so the
  legacy password form is their only staff sign-in. PR-4 (bridge removal) moves to a follow-up issue.
- Evidence for "a WORKFORCE user with no `booking-*` group is refused by Booking" comes from the existing
  Cognito E2E (`e2e-cognito.yml`, user "E2E Cognito", CIS reviewer, Booking none) rather than a new workflow:
  it is the only automatable WORKFORCE identity with no Booking group, and it already has the mailbox plumbing.
- The Booking step runs **after** the CIS sign-in and **before** CIS sign-out, so the managed-login session on
  `staff-auth.lumiguides.it.com` is shared by the booking-staff client and no extra code mail is normally needed.
  If Cognito asks for the address anyway, the step signs in by code once more (one extra mail, same safeguards).
- The step asserts four things: the URL is `booking.lumiguides.it.com/login?reason=no_booking_role`, the
  "no Booking role" notice is shown, no `bk_access` / `bk_staff_rt` / `bk_cis_session` cookie holds a value, and
  `/` still redirects to `/login`. Cookie checks print names only.

## Changed

- `tests/e2e/cognito/cognito-login.spec.ts`: new step 4b (screenshots `04b-booking-login`,
  `04c-booking-refused-no-role`, `04d-booking-still-signed-out`, and `04b2`/`04b3` only on the fallback path);
  the address → code → submit sequence is now a helper (`signInByEmailCode`) shared by step 2-3 and the fallback;
  test timeout 240 s → 360 s for the optional extra code wait.
- `.github/workflows/e2e-cognito.yml`: header comment only (artifact path unchanged: same screenshot folder).
- `CONTEXT.md`: Cognito E2E paragraph describes the Booking step; "Booking staff token (AA-680)" section records
  that the bridge is kept on purpose.

## Tradeoffs

- One test instead of a separate Booking test: a separate test would need its own sign-in (another code mail and
  ~90 s). The cost is that a Booking outage now fails the CIS sign-in run too; the failure names the step.
- Not removing the bridge leaves `aa-cis/dev/booking-jwt-signing-key` and the bridge code paths alive; accepted
  until a preview sign-in exists.
