# AA-1051 — Quality W5: the $0 code of the paid writer proofs (lane l7, S278)

Source plan: root ADR 0020 (D7, D12; amendment S278 pooled classes), the S271 writing-quality audit
(`docs/audits/2026-11-06-S271-writing-quality-audit/`, `data/design-review.json` `arch.roadmap[5]`,
`arch.quality_targets`, the Writing Lab redesign "golden v2" and critic fix F12), and the S275 decision "code eval part
first" (split DEV / CAL / GATE in its own migration, power check, pre-registration file). This lane builds the code
only: **no paid run**. Each paid proof needs the tech lead's own yes and runs only after W2 R1 and W4.

## Decisions

- **The split is a table of its own (CIS 400, expand), not a column of `shared.eval_golden_item`.** A new column is an
  ALTER of an existing table (contract, MIG-4 and a person's apply); a new table with an FK is expand and is
  auto-applied. It also keeps the existing `split` (tune / holdout / trap: the R2 phases, tied to result rows by the
  CIS 284 trigger) untouched: the DEV / CAL / GATE side is orthogonal to it. Append only (a BEFORE UPDATE trigger,
  like CIS 394: an expand file cannot REVOKE cis_owner's default UPDATE grant), FK ON DELETE CASCADE to the item (the
  tenant erasure reaches it through the item), RLS ENABLE + FORCE with the X1 parity policies, no text.
- **Rule: per sample id, cal 30% / gate 30% / dev 40%** (`aa1051-split-v1`, seed `aa1051-eval`). The audit says
  "splits by hash(sample_id)". The AA-1048 claim split is per tour; per tour here would leave the T9 writers (about 20
  blogs on 3 tours) with 0 or 1 tour on GATE. A sample id is the identity across golden versions (R2 pairs controls on
  it), so a sample keeps its side in every version. The bucket is floored to 6 decimals (the column is numeric(7,6),
  rounding could reach 1.0).
- **Stored rows are the truth.** Readers (R2 `PgStore.items`, the proof runner) read the stored side; nothing
  recomputes it at read time, so a v2 rule can never move an item of an existing set version. The importer writes the
  rows with a new version (and fills missing ones on a re-run); `python -m services.writer_proof.splits` fills an
  existing set (DRY RUN first). Both use `ON CONFLICT DO NOTHING`.
- **R2 honours the split** (`--eval-split`, `--sample-ids`): it plans only the non-trap items of the side (traps stay
  in the probe: the trap defence is deterministic), refuses at $0 when the set has no split rows or a fixed id is not
  an item / not on the side, and decides `judge_counts` on the CAL items only. The labelled planned items of the side
  are judged too and reported (`details.kappa_eval_split`, the "GATE within 0.1 of CAL" target); for release 0 their
  control is the same call, so it costs nothing extra. Without `eval_split` R2 is unchanged.
- **Pre-registration = a JSON file in the image** (`services/writer_proof/prereg/<id>.json`), reviewed in a PR. A
  drafted sample needs the DB (GATE ids), so the four files ship as **drafts** (empty sample, proposed margins and
  judge); `runner draft` fills the sample by a seeded hash of the pre-registration id (no data-driven choice) and a
  person registers it in a PR. Only a `registered` file can start a paid run.
- **The lock is the sha of the canonical JSON** (sorted keys, no whitespace: reformatting changes nothing). Each run
  records it in `prompt_eval_runs.details.prereg`; R2 refuses a pre-registered run, and `runner report` refuses a
  verdict, when an earlier run of the same id that has at least one result recorded another sha. No new table: the run
  rows already hold it.
- **Proofs are R2 runs, not a new runner.** R2 already has the pinned judge, the paired controls, the hard stops, the
  mixed-judge refusal, the hard cap from the ledger and the job (`writing_memory_r2`, worker, deploy-blocking). The
  proof runner only builds the configs (fixed sample, GATE, pinned judge, stage `adhoc_aa1051`, prereg fields), gates
  the spend and queues one job per arm. Every model call is the R2 writers' and judge's own `LLMClient.generate` call,
  logged by the gateway / call sites with `**billed_fields(resp)` and relabelled to `adhoc_aa1051` by
  `call_log.bind_eval_stage`. This lane adds no new call site.
- **`adhoc_aa1051` is an eval log stage** (`cfg.W5_STAGE` in `EVAL_LOG_STAGES`, mirrored in
  `central_budget.EVAL_STAGES`) reserved for pre-registered runs (R2 refuses it otherwise, and a pre-registered run
  must use it), so the spend gate can read the W5 spend from the ledger by stage. It is **not** in `MEMORY_STAGES`: W5
  has its own D12 budget ($33), larger than the learning-loop month cap ($25).
- **Decision rule tightened from the audit sketch.** The sketch reads "non_inferior: mean(B - A) <= max(margin,
  2 SE(A - A'))"; the code uses the one-sided upper bound `mean(d) + z_(1-alpha) SE(d) <= max(margin, k SE_noise)`,
  which is what the power check computes power for. `improve` needs the bound < 0 and an improvement >= the same
  allowance. `invalid` first when a requirement fails (paired < the fixed sample, mixed judges, a hard stop 1, a
  missing noise arm).
- **Power check from R1 votes.** Per claim, the chance a re-judge flags it is the majority probability of its vote
  share; claims are grouped into pseudo-items of `claims_per_item` (hash order); the item's re-judge variance is the
  sum of m(1 - m) (counts) or P(1 - P) (any-claim item verdict). Var(d) = 2 var_j + writer_sd^2; writer_sd null gives
  an upper bound on power. The runner refuses a live run without an adequate check (the R1 report file is required).
- **Spend gate** (`spend.refusals`): `--confirm CONFIRM` typed, a cap > 0 within the pre-registered and D12 caps, the
  workflow's and W5's ledger spend + the cap within D12, and the estimate within the cap; a NaN ledger reading fails
  closed. The workflow cap is shared between the arms in proportion to their estimates (each arm's R2 cap also <= the
  R2 hard cap of $10).
- **Cost per object from the ledger.** R2 works one item at a time and flushes the ledger before it stores the item's
  result, so each ledger row of a run belongs to the first result row stored at or after it. Reported per run: ledger
  total, all-in cost per candidate object, attributed cost / requests / writer requests per object (median, mean,
  max), unattributed rows kept and flagged.

- **Review fix pass (S278): a proof runs once, a null run is null by construction.**
  - *Null run.* The `null` workflow regenerates with today's writers (B) against the control's stored outputs (A);
    that is B == A only when the control was written under the same writer configuration (the audit: "A = stored
    finals at matching config_fp"). `r2.null_config_problems` compares the control run's stored fingerprint with
    the current one strictly (golden set, writer route, taxonomy, every config_fp component; a missing or
    unavailable component is a problem, not "no change"; mode_flags only worker vs worker). A baseline import
    (frozen text, no config_fp) is refused: the null run needs a reverify of the active release on this golden
    version first. R2's DRY RUN reports it (`would_refuse`, so `runner plan` blocks) and `run_r2` re-checks it on
    the worker at the run's start (the config can change while the job waits). The pre-registration refuses a
    `release_id` and the `improve` rule for `null`. Chosen over "candidate = the control re-judged": that only
    measures judge noise, not the writer's run-to-run spread the null run exists to measure.
  - *Once only.* A live run is refused while any job of the same pre-registration is queued or running, and once
    any of its runs has results; R2 itself refuses an arm that already has a run with results (`prereg_refusal`),
    so a job queued by any path cannot rerun a decided arm. Each arm's job carries the idempotency key
    `w5:<id>:<sha16>:<arm>:<attempt>` (attempt = jobs ever queued for that arm + 1), so two starts that read the
    queue at the same moment share one job; a run refused at $0 (no result) can be started again as attempt 2.
    `report` decides on the FIRST run with results of each arm and lists any later one as a rerun, never counted.
  - *Reserved spend.* The spend gate adds the caps of every queued or running W5 job (`spend.read_jobs`, payload
    `cap_usd`; unreadable = the R2 hard cap) to the ledger spend, per workflow and in total.
  - *Arm caps.* `plan` compares each arm's estimate with its own run cap, min(its share of `--cap-usd`, the R2 run
    cap $10), and blocks when the estimate is above it (R2's own "estimated > cap" refusal compares with a
    placeholder cap and stays filtered).
  - *Power of `improve`.* `power.check` branches on the rule: `improve` is powered at the pre-registered true
    improvement `power.effect_abs` (required for that rule, > margin), power = Phi((delta - max(z SE, margin)) / SE);
    `n_needed` is None when delta <= margin (the rule then passes at most half the time). The w5-t9 draft proposes
    effect_abs 0.3 on item_fail_rate (margin 0.1).

## Tradeoffs

- **R2 judge, not yet the shared claim engine.** The S275 decision lists "R2 on the shared judge" in the code part;
  this lane did not rewire R2's judge (`eval_judge`) onto the R1 claim instrument (`ground_truth/r1.py` extraction):
  it is a judge change with its own calibration, and W4's promotion decides the pinned instrument first. The proofs
  pin whatever judge the pre-registration names (D7). The power check reads R1 votes, so it is a proxy for the R2
  judge until both share the engine (follow-up).
- **R2's T9 writer is the first draft only.** First-pass yield is exactly what it measures; requests and cost per
  object of the full T9 loop are first-draft numbers here (stated in the w5-t9 draft). The full-loop numbers come from
  the W3 graph's live pieces.
- **S1's 25 stratified tours** (Japan, Rajasthan, contradictions, Optional-heavy) are not golden items; a proof can
  only pre-register golden samples, so they must be frozen into the golden set first.
- **A per-sample split** lets objects of one tour sit on two sides (shared source, not shared text); per tour would
  starve GATE for the T9 writers.
- **A binary item verdict saturates** when an item has many claims: with 60 claims and a few flaky ones the item is
  almost always "fail", so its re-judge variance is near 0 and the power check looks generous. The count metric
  (`fail_claims_per_item`) is the honest one where claims are dense; the tech lead chooses the primary metric when
  registering.

- **Reserved spend over-counts a running job** (its ledger rows so far plus its whole cap): fail closed, and only
  another pre-registration's start is affected (the same one is refused outright while its job is active).
- **No D12 re-check at the job's start.** The only path that queues a W5 job is the runner (R2 refuses stage
  `adhoc_aa1051` without a pre-registration, and its CLI has no prereg flags); the queue reservation, the once-only
  rule in R2 and the idempotency key close the double-spend. A start-time ledger check would also refuse the A'
  arm whenever B's last item overshoots its share slightly.

## Should know

- **Order (MIG-4 chain):** migration-only PR (400) → Infra copy → Migration Apply (expand, auto) → the code PR. The
  code reads the table only when it exists (`splits.table_exists`), so a deploy before the apply degrades to "no split
  rows" refusals, never errors.
- **Renumbered 399 → 400** in the second fix pass: another lane of this wave took 399 on main first (the t9_write v6
  prompt version). Every reference (file names, schema_versions row, test names, readers' messages, the root DM-7.1
  row) now says 400.
- **After the code PR is live:** run the split backfill DRY RUN then `--apply` for the active golden set, then
  `runner draft` per workflow. GATE has about 30% of each writer's items: the null run needs >= 12 t9_blog items on
  GATE, so the golden set needs >= about 40 t9_blog items (the audit's own size); the DRY RUN shows the count.
- **The null run needs a reverify first** while the t9_blog control is release 0's baseline import (frozen text, no
  config_fp): `runner plan` says so. Run the null run before W3 changes the T9 writer, or after a fresh reverify:
  once the writer config moves, the old control no longer makes B == A.
- **No paid call in this lane.** Every live path is behind `--live --confirm CONFIRM --cap-usd` and a registered,
  powered pre-registration; the shipped files are drafts, so a live run is refused today by design.
- **The judges and margins in the drafts are proposals** (judge = the R1 default candidate); the tech lead sets both
  when registering (D7: the instrument R1 pins).
- `tests/unit/test_aa1058_cost_attribution.py::test_every_ruled_ledger_write_carries_its_key` fails on `origin/main`
  too when run after some `billed_fields` tests in one session (order dependent, not this change); alone it passes.
