# AA-988 — Segments follow a Master publish: dead members, orphan segments (S252)

Design input: root `.tmp-session/s252/aa988/design.md` (S252, read-only mapping of CIS `520199cd`). The orchestrator
accepted all four §7 decisions as proposed. This branch builds the AA-988 part in existing jobs only (no new job kind,
no migration). AA-989 (places, card links, embeddings) is in `AA-989.md`; both ship on one branch.

## Decisions

- **S1, member rows of inactive atoms.** `run_segment_matching` (segment stage, one tour) now deletes, in its write
  transaction, the `atom_segment_member` rows of THIS tour's atoms that are soft-deleted or empty-day markers
  (`tour_atoms.deleted OR is_empty_marker`). "Inactive" deliberately does not use `v_active_tour_atoms`: an atom of a
  paused / trashed tour is not deleted, and the restore path does not re-run the segment stage for every tour, so its
  membership stays. The cleanup also runs when the tour has no atom left with place + action (the early return).
- **One lock between segment writers and the GC.** Key `acp:segment_write` (`segment_gc.SEGMENT_WRITE_LOCK_KEY`).
  A segment run holds it SHARED (session level, on one pool connection) from its candidate read to the end of its write
  transaction; `segment_gc` takes it EXCLUSIVE inside its transaction (`pg_advisory_xact_lock`). Shared, not exclusive,
  for the segment runs: they already coordinate with each other through row locks (sorted upserts, AA-857), and an
  a3_atomize segment stage and a `recompute scope=tour` may run at once. Held from the READ, not only around the write:
  the run's candidate pool (pseudo atoms of existing segments) is read before the write transaction, and a GC delete
  in between would make the alias insert (`segment_id_old` FK) or the member re-point fail.
  The GC sets `lock_timeout` (30 s) and reports `skipped: lock_busy` instead of failing the recompute.
- **S2, `segment_gc` stage.** Appended to `PLATFORM_STAGES` (landing → score → route → segment_gc), so it runs in the
  existing debounced platform `recompute` job after ranking and routes are current. Mode from env `SEGMENT_GC_MODE`:
  `report` (default: counts + samples in the job result, writes nothing), `apply`, `off`. Not in `TOUR_STAGES` (a
  tour-scoped recompute already queues nothing platform-wide; the next platform pass collects).
- **What the GC deletes (decision 2: zero-reference orphans only).** A segment is deleted when it has
  - no member row on a live atom (members only on deleted / marker atoms, or none),
  - no `atom_ranking` row (superseded rankings are already deleted by the score stage, so "any" = current),
  - no `atom_segment_alias` row naming it (old or canonical; both are FKs),
  - no `acp_shared.subject` row (FK), no `acp_shared.debate_brand_fit_cache` row,
  - is not in the `ordered_segment_ids` of a current route, nor of any route a subject names (superseded routes are
    kept for `subject.route_id`), nor in any `angle_gate_request.route_segment_ids`.
  In `apply` it first deletes the member rows of deleted / marker atoms of those segments (S1, platform-wide for the
  delete set only), then the segments, in one transaction. Referenced orphans are kept and counted per reference class.
- **No migration.** The optional `tour_atoms.segment_excluded_reason` (design S3) is not built: see Tradeoffs.
- **The delete rule does not depend on RLS of `published_tours`.** "Active member" (probe rule, via
  `v_active_tour_atoms`) only decides what is an orphan; what is deleted needs no member on a non-deleted,
  non-marker `tour_atoms` row. A login that cannot see `published_tours` would see more "orphans" but delete
  nothing more. `subject` and `angle_gate_request` are read as `cis_app` (both have a `<t>_cis_app_all` policy);
  `subject.segment_id` is also an FK, so a hidden Subject row would make the delete fail, not lose data.

## Changed

- `services/acp_contract/segment_gc.py` (new): lock helpers, `plan()` (counts, report mode), `run_segment_gc()`.
- `services/acp_contract/segment_matching.py`: shared lock around the run; inactive-member delete.
- `services/recompute/stages.py`: stage `segment_gc`, `PLATFORM_STAGES` += `segment_gc`.
- `services/export/handler.py`: `recompute_rankings_and_routes` returns `segment_gc` next to ranking/route; the
  atomize path reads the tour's Segments before AND after its segment stage (the stage now drops the dead atoms'
  member rows, and the Segments they left still need the brand-fit cache clear and a re-landing).
- `run_segment_gc(..., scope_ids=[...])`: limits a pass to given Segment ids (tests; a trial batch of the backfill
  through an ECS-exec script). The stage always passes None (every Segment).
- Tests: `tests/unit/test_aa988_989_follow.py`, `tests/integration/test_aa988_segment_gc.py` (also run locally on
  Postgres 16 against the partial local test DB through a scratch conftest: 5/5), updated
  `test_aa735_stage_registry.py`, `test_aa526_a3_atomize_trigger.py`, `test_aa743_scoped_recompute.py`.

## Tradeoffs

- **No exclusion-reason column (design S3).** It needs CIS migration 285 + Infra copy + dump PR + ERD page; the task
  asked to prefer no migration. Without it the probe cannot tell an excluded place atom (transit / unnamed) from a
  missed one. Kept as a follow-up; the segment stage result already carries `excluded_atoms` per run.
- **Session-level shared lock holds one pool connection for the length of a segment run.** The job pool has 5; Jev
  `decide()` calls of `_apart_pairs` share the other 4 (they already wait on the pool). Accepted for a race-free GC.
- **GC in report mode first.** One code path for the backfill and the steady state; flip to `apply` after the report
  count is compared with the DRY RUN (runbook).

## Should know

- `SEGMENT_GC_MODE` is unset on Dev, so the first deploy only reports (`recompute` job result key `segment_gc`).
  Setting it to `apply` is an Infra (task definition env) change.
- Concurrency proof: `tests/integration/test_aa988_segment_gc.py` (real Postgres): GC waits while a segment run holds
  the shared lock and deletes nothing that run claims.

# AA-988 follow-up (S253) — derived Segment ids must be unique

Live finding (Dev, S253): 227 active forming atoms in 157 tours had no `atom_segment_member` row. Replay of tour
`031145c9` (atom "Hutong / walk through to see the local lifestyle of old Beijing", China): `derive_segments` made two
Segments with the same id — the atom's own new Segment and the pseudo (existing) Segment "the Hutong / stroll through".
They are not one moment (`_about_the_same_thing` is false: "walk" vs "stroll", and the objects share no word), but
`_mint` hashes only `place|verb|country`, which is coarser than the join rule. `reconcile_ids` then built
`{segment.id: segment}` and kept only the last one, so the atom's Segment vanished without an error. Reverse order
(atom id sorting after the `__existing_segment__` prefix, e.g. `e...`): the atom's Segment survived instead, under the
existing id, so the atom was glued into an unrelated existing Segment and the run relabelled it (it claimed the id).

## Decisions

- **Re-mint only collision groups, after the derive.** `derive_segments` first mints as before; any id held by more
  than one derived Segment is a collision group. Non-colliding ids are byte-identical to before (ADR 0002: existing ids
  never churn; golden ids pinned in a test).
- **The pseudo keeps its id.** In a collision group, the Segment that contains the pseudo atom of that very id
  (`__existing_segment__<id>`, i.e. the existing Segment the id belongs to) keeps it; every other member is re-minted.
  Without such an owner (pure calls, or an existing Segment whose stored id is an old-formula / AA-857 re-mint) every
  member is re-minted, and a pseudo gets its stored id back through the normal `_claims` path (its pseudo atom is
  assigned to it), so an existing Segment's id is never taken or changed.
- **A pool pseudo's stored id is contested even with one holder (review S253).** The pseudo's own Segment can mint a
  different id (it joined a new atom with a shorter canonical key), and a lone new Segment that is not that moment can
  then mint the stored id. Before, `_unique_ids` saw no shared id and did nothing; `reconcile_ids` aliased the stored id
  to the joined Segment and `_plan_writes` wrote the lone atom into the stored id and relabelled it (the reverse-case
  glue again). Now every stored id of a pseudo in the pool counts as owned: a Segment that mints it without containing
  that pseudo is re-minted, even as the only holder, and the pseudo's Segment reclaims it through `_claims` (no alias).
  A re-mint that lands on another pseudo's stored id (a stored id may itself be an earlier `_mint_specific`) bumps `n`.
- **Re-mint formula:** `sha256(place|verb|country|said|sorted(about)|n)[:16]`, `n` = index among the re-minted members
  of the group with an identical full key (canonical Key + country), ordered by `atom_ids`. Place and verb tokens are
  `[a-z0-9]` only, so the input can never equal a `_mint` input (3 parts vs 6).
- **Guard in `reconcile_ids`:** duplicate ids in `derived` raise `DuplicateSegmentIdError` (a `ValueError`). A dropped
  Segment is never silent again.
- **Invariant in `run_segment_matching`:** after `_plan_writes`, inside the write transaction, every forming atom of
  the tour must be in exactly one `to_write` Segment (`assert_each_atom_in_one_segment`, `SegmentCoverageError`);
  otherwise the run raises before writing and the transaction rolls back.

## Changed

- `services/acp_contract/segment_matching.py`: `derive_segments` passes its minted Segments through `_unique_ids`;
  new `_mint_specific`, `DuplicateSegmentIdError` (guard at the top of `reconcile_ids`), `SegmentCoverageError` +
  `assert_each_atom_in_one_segment` (called in `run_segment_matching` right after `_plan_writes`, inside the write
  transaction, before any write). `_PSEUDO_PREFIX` moved up into the pure section (the re-mint needs it; same value,
  same import path). Module docstring: AA-988 (S253) paragraph.
- `tests/unit/test_aa988_segment_id_unique.py` (new): Hutong case (target + pseudo, two ids, both kept, target in
  `to_write`, the existing row not upserted), same-tour "Hanoi / have dinner" + "Hanoi / eat breakfast" (two Segments,
  stable on the rerun), reverse order (`e...` atom not given the existing id, existing label unchanged), pseudo with an
  old-formula id, empty-action atoms, golden ids of non-colliding pools (computed on main before this change), the
  `reconcile_ids` guard, the coverage invariant over fixture pools, and `run_segment_matching` on a fake DB (both atom
  orders write a new id; a lost atom raises and rolls back).
  Review S253: two 3-atom pools (pseudo + shorter-key new atom + lone atom minting the pseudo's stored id) assert the
  lone atom gets its own id and no alias row is written; one pool asserts a re-mint skips another pseudo's stored id.
- Ops script (root, not in this repo): `.tmp-session/S253/aa988_repair.py` — `MODE=dry|apply|reverse_audit`.

## Tradeoffs

- **Re-mint inside the pure derive, not in `reconcile_ids`.** The collision is a property of the derive (two
  components, one mint), and the pseudo-owner rule needs only the pool, not `assigned`. Keeping `reconcile_ids` a
  strict consumer (guard, no repair) keeps its tie-break rules unchanged.
- **`n` depends on the run's pool.** A re-minted id of a NEW Segment could differ between two runs with different
  pools, but only before it is first written; afterwards its atoms are assigned to it and `_claims` holds it (same as
  every fresh mint).
- **No clean-up of glued Segments here.** Segments that already took a foreign atom under the reverse case (label
  replaced by the atom's) stay as they are: the relabelled pseudo now matches the glued atom, so a rerun keeps it. The
  ops script's `MODE=reverse_audit` sizes it; repairing them is a separate decision.
- **An atom that moves Segment keeps its old member row.** Pre-existing behaviour (the write path inserts, it never
  deletes a member row of a live forming atom). With unique ids this only happens when `_claims` gives an atom's prior
  id to another Segment; not changed here.

## Should know

- Uncontested ids are unchanged (golden test), so the deploy alone re-mints nothing; only runs that hit a contested
  id (minted twice, or a pool pseudo's stored id minted by a Segment without that pseudo) get new ids, for the NEW
  Segment, never for the existing one.
- After the deploy, the 227 atoms are repaired by `aa988_repair.py MODE=apply` (segment stage per tour, sequential,
  no tour-scope recompute). The new Segments get Score/Route/landing from the next platform `recompute` (optionally
  enqueued by the script with `ENQUEUE_PLATFORM=1`, scoped to the touched Segments).
- No migration.
