# AA-388 — Gate B approval UI (Quarter Plan)

## STEP 0 findings (2026-08-12)

Read AA-320 (`services/acp_planning/quarter.py`, migration `092_acp_quarter_plan.sql`,
`api/routers/admin.py:1607-1735`) before writing any code.

- Real endpoints already exist, not just planned:
  - `POST /admin/quarter-plan` — compute + persist a new pending version.
    Body: `{tenant_id, year, quarter, markets[], capacity_posts_per_week, specials[]}`.
    Returns `{version_id, approval_status:"pending", plan}`.
  - `GET /admin/quarter-plan/{tenant_id}/{year}/{quarter}` — latest version (any
    status) for one tenant/year/quarter. Returns full version row + `plan` payload.
  - `POST /admin/quarter-plan/{version_id}/approve` — body `{approved_by}`. Row-locks
    (`FOR UPDATE`), 404 if version not found, **409 if not `pending`** (never a silent
    no-op — re-approve is rejected). On success: `approval_status='approved'`,
    `approved_by`/`approved_at` set, `quarter_plan.current_version_id` moved.
  - **No reject endpoint anywhere** (verified via grep) — out of scope per issue,
    Approve-only UI.
  - **No list-pending endpoint** — only per-`(tenant_id, year, quarter)` lookup
    existed. Gap flagged to Nghiep before building; confirmed via AskUserQuestion to
    add `GET /admin/quarter-plan/pending`.

- Live schema verified via `information_schema` against real RDS (S3-mediated ECS
  exec, account [acc2 id], task already running — no cis-start needed), not just
  the migration file:
  - `acp_shared.quarter_plan`: `plan_id, tenant_id, year, quarter,
    current_version_id (nullable), created_at`.
  - `acp_shared.quarter_plan_version`: `version_id, plan_id, version_no,
    payload(jsonb), source, approval_status(varchar, default 'pending'), approved_by,
    approved_at, created_at`.
  - Confirmed `current_version_id` lives on `quarter_plan`, not on the version table.
  - Confirmed `approval_status` is per-version, not per-plan.
  - Live data at STEP 0 time: 3 versions total, all `approved`, **0 pending** — no
    real pending plan existed to test approve against; a TEST_MODE_SCRIPT plan was
    created for the verify step (see below).

- Route decision: new top-level `/admin/quarter-plan` page (mirrors the API
  namespace, same convention AA-384 used for `/admin/marketplace`), admin-only nav
  group. Not nested under `/admin/curation` (that page is
  content-team-facing — `roles: ["admin","reviewer","content"]` — a different
  audience than Gate B). Learned from AA-384: must add to `middleware.ts`
  `PROTECTED_ROUTES` or the page silently redirects to `/login` even with a valid
  admin session — tsc/build won't catch this.

## Decisions

- Added `GET /admin/quarter-plan/pending` (new, confirmed with Nghiep) — lists all
  `quarter_plan_version` rows with `approval_status='pending'`, joined to
  `shared.tenants` for tenant name.
- No Reject button — API has no reject endpoint; adding one was explicitly out of
  scope for this issue.
- No auto-approve, no default value, no bypass of the human-approval step anywhere
  in the new code — Gate B stays REQUIRED/NEVER-auto per D6.

## Changed

- `api/routers/admin.py`: added `GET /admin/quarter-plan/pending` (new — not part of
  AA-320's original shipped surface). Lists all `quarter_plan_version` rows with
  `approval_status='pending'`, newest first, joined to `shared.tenants` for a
  display name.
- `frontend/app/admin/quarter-plan/page.tsx` (new): list of pending plans → detail
  view (trip count/ids, destination content-share bars, big rocks with atom counts,
  capacity/thin-trip notes) → Approve button. `approved_by` is read from the
  `cis_user` cookie (same convention `AdminSidebar.tsx` already uses to display the
  logged-in admin's name) — no free-text input, no default.
- `frontend/middleware.ts`: added `{ prefix: "/admin/quarter-plan", roles: ["admin"] }`
  to `PROTECTED_ROUTES`.
- `frontend/app/admin/_components/AdminSidebar.tsx`: added "Quarter Plan (Gate B)"
  nav item to the admin-only group, next to Marketplace.

## Tradeoffs

- No Reject button/endpoint — confirmed in STEP 0 that the backend has none;
  building one was explicitly out of scope for this issue.
- Detail view shows `trip_ids` as a raw UUID list (no trip-name resolution) — the
  `QuarterPlan` payload itself doesn't carry trip names, only `destination_shares`
  (keyed by destination string) and `big_rocks` titles do. Adding a join to resolve
  trip names would mean new backend surface beyond what was scoped; the issue said
  "không cần đẹp, chỉ cần đủ để ra quyết định" and destination shares + big rocks
  already carry the human-readable signal needed to decide.
- `approved_by` comes from the `cis_user` cookie rather than a text field — matches
  how the rest of the admin UI identifies the acting admin, and avoids letting a
  reviewer type an arbitrary name into a REQUIRED/NEVER-auto approval record.
