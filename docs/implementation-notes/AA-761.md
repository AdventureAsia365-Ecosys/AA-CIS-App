# AA-761 — Portal Account pages with real data (CIS API part)

The portal itself lives in AA-Partner `portal/` since AA-979 P2a; its notes are AA-Partner
`docs/implementation-notes/AA-761.md`. This repo adds the read endpoints the pages need. No migration (CIS 281
belongs to another lane in S251).

## Decisions

- **Three new tenant routes, `/v1/account/*`** (`api/routers/v1_account.py`, logic in
  `api/services/tenant_account.py`): `GET /activity`, `GET /activity/export` (CSV), `GET /api-key`.
  Billing needed no new route: plan, usage, overage and the plan list come from `GET /v1/billing`, the reset date
  from `GET /v1/quota` (`resets_at`).
- **Main pool with the JWT tenant id bound, not the tenant pool.** `acp_shared.audit_log` has no RLS and no grant to
  `aa_app_user` (schema reference 25/10/2026), so `acquire_scoped_conn` cannot read it, and adding RLS + a grant is a
  migration this lane may not write. Same pattern as `/v1/billing` (AA-496): `get_tenant` (tenant JWT only, a staff
  token is 403), the id normalised to the canonical UUID text the writers store, bound in every query; no route takes
  a tenant id from the query string. The routes emit no `used_tenant_pool` field, so the Infra tenant-pool alarm is
  not affected.
- **Allowlist, not "all my rows".** `audit_log` holds rows tenants must never read even when they carry the
  tenant's id: the AA admin silent corrections (`content_piece.admin_sentence_*`,
  `tenant_tour_version.admin_sentence_*`, `AdminAuditAction` says "tenants never read audit_log"), the staff request
  trail (`staff.request`, AA-884), staff brand / config / membership edits, the plan-id backfill and the erasure
  record. `TENANT_VISIBLE_ACTIONS` lists what is shown: every `TenantAuditAction` plus the account facts AA changes
  that the tenant is told anyway (onboard, restore, plan, rate limit, daily publish limit, status, key rotation).
  A unit test fails if a `TenantAuditAction` is missing or a staff-only action is listed.
- **`details` never leaves raw.** It holds staff before/after values, job ids, publish ids and internal plan ids.
  `detail_text()` builds a short text from a per-action whitelist (channel, format, version number, retry, the plan
  tier names, the new RPM / daily limit, the new status). Actor → `you` / `adventure_asia` / `system`; staff ids are
  never returned.
- **Paging: offset with a total** (`page`, `page_size` ≤ 100), the `my-versions` shape the kit DataTable's
  `serverPagination` already uses. The `(tenant_id, created_at DESC)` index serves both queries. The count query
  runs first; an empty set skips the page query.
- **Dates are UTC days, both inclusive** (`until` is sent as `< until + 1 day`).
- **CSV export is server-side** (every page of the filtered set, not the current page): `text/csv`, the same
  allowlist, formula-looking cells prefixed with `'` (CSV injection), at most 50 000 rows (newest first; a cut file
  ends with a line saying so). The bound keeps one request from loading an unbounded result into an api task; the
  whole table holds ~1.7k rows on Dev.
- **API key facts.** Only the sha256 of a key is stored, so the masked view is the fixed `cis_` prefix and a mask
  (no key character is recoverable, nothing derived from the hash is returned). `issued_at` = newest
  `agency.onboard` / `tenant.key_rotated` / `tenant.restored` row (null when none is recorded, e.g. a tenant seeded
  before AA-797); `last_sign_in_at` = newest `tenant.login` (portal or `/auth/tenant-login`); `last_api_call_at` =
  newest metered call in `shared.tenant_api_usage` (portal sessions are not metered, AA-760); `last_used_at` = the
  newer of the two. A `REVOKED_…` hash (offboarded) reads as `has_key: false`. Rotation stays "contact AA".
- **Invoices: none stored in CIS.** No table holds AA-issued invoices (schema reference), and the billing provider
  decision is open, so there is no invoices endpoint; the portal shows the empty state.
- **Response models** (`api/schemas/public_api.py`, AA-899 rule: a new public route declares its model):
  `AccountActivityPage`, `AccountApiKey`; the export declares `text/csv`. `docs/api/openapi.json` regenerated with
  the pinned fastapi 0.161.1 / pydantic 2.14.1 (additions only).

## Tradeoffs

- Main pool instead of RLS: the boundary is the bound id plus the allowlist, both tested (unit: every query's
  first argument is the token's tenant, a `?tenant_id=` is ignored, a staff token is 403; integration: tenant A
  never sees tenant B's rows or its own staff-only rows). Moving the read to the tenant pool needs a migration
  (RLS on `audit_log` + `aa_app_user` SELECT with a policy) — a follow-up only if the reviewer asks for it.
- Offset paging over keyset: the DataTable pager needs page numbers and a total; a tenant's trail is small.
- No new audit row for an export (the export is a read of rows the tenant already sees).

## S251 independent review: findings and answers

- **Fixed (should-fix): far dates gave a 500.** `build_where()` adds one day to `until`, so
  `?until=9999-12-31` raised OverflowError on `/activity` and `/activity/export`. `validate_filters()` now
  refuses `since`/`until` outside `DATE_FILTER_MIN` (2000-01-01) .. `DATE_FILTER_MAX` (2100-12-31) with a
  ValueError, which the route turns into a 400. No audit row is outside that window, so it drops nothing real.
  The portal mirrors the window (`ACTIVITY_DATE_MIN/MAX` in AA-Partner `portal/lib/account.ts`, plus min/max on
  the date inputs), so a year still being typed (0002-…) never reaches the API. Tests: four new cases in
  `test_invalid_filters_are_refused`, route checks (`until=9999-12-31` on both routes and `since=0001-01-01`
  answer 400), and `test_bounds_of_the_date_window_are_accepted` (the edges pass and 2100-12-31 + 1 day
  binds 2101-01-01).
- **Accepted for this PR (should-fix): main pool instead of RLS / `tenant_tx`.** The finding is right that there
  is no database-level defence in depth: `acp_shared.audit_log` has no RLS and no `aa_app_user` grant, and this
  lane may not add a migration (281 belongs to another lane). Isolation holds today through the token-only tenant
  id bound as `$1` in every query, the action allowlist and the per-action detail whitelist, covered by the unit
  and integration cross-tenant tests. Follow-up for the migration lane (backlog row, no new issue): enable RLS on
  `acp_shared.audit_log` with an `aa_app_user` SELECT policy on `tenant_id = current_setting('app.tenant_id')`,
  keep the writers' path working (writers use the main pool and `BYPASSRLS`/owner rules must be checked), then
  move the three reads to `acquire_scoped_conn`. The independent risky-PR review still runs before merge.
- Tests re-run after the fix (S251): `pytest tests/unit/test_aa761_tenant_account.py` 45 passed; with the pinned
  fastapi 0.161.1 / pydantic 2.14.1 overlay, `test_aa899_openapi_export.py` + `test_aa761_tenant_account.py` +
  `test_aa725_route_sanity.py` + `test_aa577_swagger_docs_gate.py` 65 passed (the OpenAPI document did not
  change: no route signature changed); integration `test_aa761_tenant_account_sql.py` + `test_aa884_audit_rows.py`
  14 passed on a throwaway PostgreSQL 16 cluster (stopped and deleted afterwards); flake8 clean.

## S251 re-review: last API call after the 90-day raw window

- **Fixed (should-fix): "Last API call: None yet" for a tenant whose calls aged out.** `last_api_call_at` read only
  raw `shared.tenant_api_usage`, which the retention job keeps 90 days and then rolls up per month into
  `shared.tenant_api_usage_monthly` (AA-825). `API_KEY_FACTS_SQL` now also reads the newest rolled-up month for the
  tenant (`actor_type = 'tenant'`, `calls > 0`; served by the `(tenant_id, month)` index).
- **Decision: a fallback, not a merge.** The month is used only when the raw max is NULL; a raw call is always the
  newer, exact fact (the rollup holds closed months older than the raw window). It is returned at month precision
  in a separate field, `last_api_call_month` (`YYYY-MM`), so `last_api_call_at` stays an exact timestamp or null.
- **Decision: `last_used_month`.** When that month is newer than every exact use (the latest sign-in is before the
  month's first day), `last_used_month` carries it and `last_used_at` is null, so neither field names an older use
  as the latest. An exact use inside or after that month keeps `last_used_at` (the better fact). At most one of
  the two is set.
- Changed: `api/services/tenant_account.py` (`api_key_facts`, SQL), `AccountApiKey` (+2 required nullable fields),
  `docs/api/openapi.json` regenerated with the pinned fastapi 0.161.1 / pydantic 2.14.1 (only the two fields).
  The portal `ApiKeyCard` shows the month (AA-Partner PR, same issue).
- Tests: unit +4 (raw empty → month; month newer than an old sign-in; a newer exact use wins; raw present ignores
  the rollup), integration +1 (`test_api_key_facts_fall_back_to_the_monthly_rollup`: zero-call month, staff
  `actor_type` month and another tenant's month are ignored; tenant A with a raw call gets no month).
- Tests run (S251): full `pytest tests/unit` 13 647 passed, 2 skipped (pinned fastapi/pydantic overlay);
  integration `test_aa761_tenant_account_sql.py` + `test_aa884_audit_rows.py` 15 passed on a throwaway PostgreSQL
  16 cluster (full migration replay); flake8 clean on the touched files.
