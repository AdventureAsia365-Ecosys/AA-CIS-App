# AA-665 — Cost Operations (C1 + C2 + C3)

Slices from the S255 FinOps audit (root repo `docs/audits/2026-10-28-S255-finops-security/README.md` §8): C1 rename
External Spend to Cost Operations, C2 DataForSEO spend by job, C3 month-end forecast vs budget. C4 (balance history
charts) and C5 (read AWS Budgets live) are not in this change.

## Decisions

- **Two PRs, stacked.** The migration PR carries only `api/migrations/293_dfs_call_log_job_id.sql` and its integration
  test. The code PR is branched on top of it (its CI needs the column); after the migration PR is squash-merged the
  code branch is rebased on `main` and the migration commit drops out as already applied.
- **Partial index** `idx_dfs_call_log_job (job_id) WHERE job_id IS NOT NULL`, same shape as 177's
  `llm_call_log_job_idx`: old rows and calls outside a job stay out of the index. No FK, as in 177 (fire-and-forget log,
  job retention deletes succeeded jobs after 30 days).
- **Job id source.** `shared/dfs_client/call_log.py` reads `shared.llm_client.call_log.current_job_id()` (the contextvar
  the worker binds around every handler) at call time; the sync wrapper reads it before scheduling the write, so the
  caller's context is used even when the write runs later. An explicit `job_id=` wins (including `None`). A value that
  does not parse as a UUID is dropped with a warning and the row is kept (S254 lesson: a slug bound as job id cost every
  llm_call_log row of two S1 jobs). No call site had to change: `dataforseo_client.py`, `handler.py` and
  `segment_research_batch.py` all go through the three writer functions.
- **`GET /admin/dfs-usage/runs`** groups the window's DFS rows by job and joins `shared.job` (kind, created_by, status,
  error cut to 300 chars, `cost_usd` the handler reported, attempt, parent) plus the job's LLM cost from
  `llm_call_log.job_id`. The payload is shown as a short "scope" (scalars cut to 80 chars, lists/objects as their size,
  8 keys max) — the page is admin-only (`spend.read`) but a payload can be large.
- **Rows without a job (before 293).** `infer_unlinked=true` matches them to the jobs whose run window
  `[started_at, coalesce(finished_at, updated_at)]` contains the call: one candidate = `window`, several = `ambiguous`
  (candidate kinds listed), none = `none`. This is the "explain the 25/09 incident" path of the audit, done as an
  endpoint option instead of a one-off script so it is reproducible. Capped at 31-day windows (nested-loop join).
- **Forecast method (C3).** Per series: month to date over complete days + mean of the last 7 complete days x days
  left (today included). For log sources a missing day is 0 (divide by 7); for Cost Explorer a missing day is unknown
  (divide by the days present) and the projection starts after the last stored day (CE lags ~1-2 days). A closed month's
  forecast is its total. The forecast is never below month to date.
- **Providers** = provider families of `platform_cost.provider_family` (bedrock with the acc3/acc1/acc2 split, openai,
  jev = `typesafe`, other) from the same rolled/raw split as `platform_cost.AI_SPEND_SQL`, plus DataForSEO. Jev spend is
  read from `llm_call_log` (provider `typesafe`), not from `decision_log.cost_usd`, so it matches Cost per app and the
  Jev credit estimate.
- **AWS rows** read the stored snapshots only: `shared.cost_explorer_snapshot` per account and, for acc2, also
  `shared.cost_explorer_app_snapshot` (refreshed lazily by Cost per app); per day the newer fetch wins.
- **Budgets.** AI providers: `shared.spend_budget` `global` daily cap x days in month (the Budgets tab has no monthly
  field). AWS: a code constant mirroring the AWS Budgets in AA-CIS-Infra (acc2 250, acc3 250), overridable per account
  with env `COST_OPS_AWS_BUDGETS_USD` (`acc2=300,acc3=250`) until C5 reads AWS Budgets. Status: over / warn (alert % of
  the budget row, 80 for AWS) / ok / no_budget / no_data.
- **`REQUIRED_CIS_SCHEMA` 287 -> 293**: without the column every DFS cost row is lost (the write is fire-and-forget), so
  `/health/ready` must report a missing apply.

## Tradeoffs

- The AWS budget is a constant, not read from AWS: C5 needs an Infra PR first (`budgets:ViewBudget`). If D1 of the audit
  (acc2 250 -> 300) is applied, the env override or the constant must follow.
- The `infer_unlinked` match is a hint: `started_at` is the last attempt's start, overlapping jobs are common during a
  wave, and succeeded jobs are deleted after 30 days (failed ones after 90), so the 25/09 rows can only match failed or
  still-kept jobs.
- The forecast excludes the geocoder and the CRM's own gateway (`crm.llm_call`): neither is in the tables this endpoint
  reads; the CRM spend is visible in Cost per app.

## Review fixes (independent review, S255)

- **AWS run rate left out today's partial day.** A Cost Explorer fetch made today stores today's (partial) figure, and
  the projection used it in the 7-day mean, pulling the rate and the forecast down. The rate window now ends at the
  same day as the complete days (`min(covered_to + 1, today)`); today's partial figure still counts in month to date.
  Unit test `test_cost_forecast_aws_partial_today_counts_in_mtd_not_in_the_rate`.
- **"Match calls without a job" is disabled for windows over 31 days.** With the 90-day preset (or a long custom
  window) the backend answers 422 and the whole Runs panel turned into an error; the page now passes the window's span
  and the button is disabled with a hint.

## Close-out: the 25/09/2026 incident on the page (S256)

The Done-when asks that the 25/09 incident be explainable from Cost Operations alone. After C2 the DataForSEO tab
still showed its 1,169 live calls / $49.02 as "No job" and the time match as "No job running": the sweep ran as an
`asyncio` background task of the tenant rewrite request (`api/routers/v1_tours.py::_run_research_only`, removed on
28/09), before `shared.job` existed, and segment research logged neither a job nor a tenant on its DataForSEO or
`a3_search_demand` rows. No log query can recover the trigger from those rows.

### Decisions

- **Recorded cost incidents as code** (`api/services/cost_incidents.py`): one frozen record per investigated incident
  (trigger, scope, failure point, cause, what changed since, how it was investigated, the LLM stages of the same run).
  Not a table: incidents are rare, each is reviewed like a post-mortem anyway, and a code record needs no migration
  and no edit screen.
- **Numbers are never typed in.** `incident_view` reads calls, live calls, cost and keywords per endpoint, first and
  last paid call and the named LLM stages live from `dfs_call_log` / `llm_call_log` over the incident window, so the
  card and the logs cannot disagree. After the 180-day raw retention the LLM part reads `llm_call_daily` for the
  window's days and says so (`source = "daily"`, whole days).
- **Attribution order in `infer_unlinked`:** one job running = "window", several = "ambiguous", no job but inside a
  recorded incident = "incident", else "none". A job match stays first because it is the more specific signal; on
  25/09 no job table existed, so every call of the window goes to the incident.
- **Window 05:00–11:00 UTC 25/09** (first research call 05:04:56, last paid call 08:51:02, failed lookups until
  10:59). The text comes from the S199 investigation (28/09) and is re-checked against the read-only query of S256
  (root `.tmp-session/S256/aa665/spike_0925.py`); adjust the record if that run disagrees.
- **User-facing text**: English, no issue IDs, roles not personal names (unit test). The test tenant's name is kept:
  admin pages show tenant names, and it is how an admin finds the tenant.

### Changed

- `api/services/cost_incidents.py` (new), `api/services/cost_ops.py` (`dfs_runs` returns `incidents`;
  `DFS_INFER_SQL` takes the incident windows as arrays `$3..$5` and returns `incident_id`).
- Frontend: `frontend/app/admin/cost-ops/IncidentCard.tsx` (new) above the DataForSEO runs; the time-match table

- Tests: `tests/unit/test_aa665_cost_incidents.py` (new), fixture rows of `test_aa665_cost_ops.py`, one integration
  test in `tests/integration/test_aa665_cost_ops_sql.py` (job wins over incident, incident over none, live numbers).

### Tradeoffs

- A heuristic "nearest tenant rewrite before the burst" would have attributed the rows without a record, but it
  guesses (test rewrites ran all day), cannot state the scope or the failure point, and would silently mislabel any
  later burst. The record is explicit and reviewed; its cost is one PR per incident.

### Should know

- No migration, no new route: the existing `GET /admin/dfs-usage/runs` gains `incidents` (always) and

  → one incident with `dfs.calls` ≈ 1,169 and `dfs.cost_usd` ≈ 49.02, and an `inferred` row with
  `attribution = "incident"`.
- Integration tests were not run locally (the local Postgres lacks the CI roles and pgvector, so the conftest replay
  fails before any test); the new SQL was checked against stand-in tables on local Postgres 16. CI runs them.
