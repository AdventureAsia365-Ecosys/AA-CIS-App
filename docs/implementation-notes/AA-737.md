# AA-737 — s1_rewrite / worker throughput for waves

## Decisions

- **Measured first (S218, `shared.job` for 07/10).** The S217 Nepal wave (13:54→16:02, ~83 tours)
  had two phases: s1_rewrite at its cap of 4 for ~75 min (queue up to 68, p50 run 192 s), then
  a ~55 min tail where a3_atomize ran alone. During the s1 phase a3_atomize had **up to 60 jobs
  queued and 0 running** (median wait ~59 min): the worker's `max_parallel=4` is one budget for
  every kind, and s1_rewrite held all 4 slots. Claims are FIFO across kinds (`queue.claim`, ORDER
  BY run_after, created_at), so a free slot is all atomize needs.
- **Main lever = more worker slots, not more atomize.** `JOB_WORKER_MAX_PARALLEL` (default 8) for
  the standalone worker service. a3_atomize stays at cap 1 (issue's explicit out-of-scope).
- **s1_rewrite cap 4 → 6.** Bedrock showed no s1_generate fallbacks at 4 (acc3 satellite; 3/251
  fallbacks on s1_flag_fix only). 6 is a modest step. Beyond ~6 the serial atomize (~45 s/tour)
  becomes the floor anyway, so a bigger s1 cap would not shorten a wave.
- **Thread executor + DB pool sized with the slots.** LangGraph `astream` runs sync nodes (every
  LLM call) on the loop's default executor, sized min(32, cpu+4) = 6 on the 0.5 vCPU task, i.e.
  fewer than 8 slots. Set it to 2×slots. asyncpg pool max 5 → slots+2.

## Changed

- `shared/jobs/worker.py`: `worker_max_parallel()` + `WORKER_MAX_PARALLEL_DEFAULT=8`, used only by
  the standalone entrypoint `_main`; explicit default executor; pool size; `job_worker_config` log.
  `Worker.__init__` default stays 4 (in-API/test worker unchanged).
- `services/jobs/s1_rewrite_job.py`: concurrency 6.
- `CONTEXT.md`: job runner section was stale (still said "worker inside the API process, AA-651
  deferred"); now describes the worker service + slot budget rule.
- Tests: `tests/unit/test_aa737_worker_throughput.py` (env parse, invariant s1 cap + a3 cap <
  slots, constructor default), AA-723 cap test 4 → 6.

## Tradeoffs

- No infra change (task stays 0.5 vCPU / 1 GB). The wave ran at ~20% CPU avg, peak ~79% with 4
  rewrites. 6 rewrites + atomize may peak near 100% for short bursts. Re-measure on the Sri Lanka
  pilot; if CPU saturates, the next step is 1 vCPU in AA-CIS-Infra, not a lower cap.
- Jev grounding is ~80 calls per tour; its rate limit is unknown. Watch for errors on the pilot.
