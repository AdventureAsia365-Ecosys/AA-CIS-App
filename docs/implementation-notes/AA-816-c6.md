# AA-816 C6 — staff directory writes via Cognito

Plan: root `docs/audits/2026-10-18-S242-cognito-phase1/plan.md` step C6; ADR root `docs/adr/0006-ecosystem-identity.md`
§3 (directory is the only writer, DB first then Cognito) and §7 (offboarding = AdminDisableUser, then
AdminUserGlobalSignOut). Branch `feat/aa816-staff-directory-writes`. Own notes file (not AA-816.md) so the
parallel C7 PR does not conflict on it.

## Decisions

- **Routes** (all in `api/routers/admin_platform.py`, all `staff.write`):
  `POST /admin/platform/staff`, `PATCH /admin/platform/staff/{id}/roles`, `POST …/{id}/disable`, `POST …/{id}/enable`,
  `POST …/{id}/sign-out` ("reset"), `POST …/{id}/sync` (the retry). Both retry styles exist: `/sync` for any row, and a
  re-POST of the same create (same address + same roles) is treated as a retry (200, no new row); same address with
  other roles = 409.
- **Policy**: `staff.write` = known staff role that holds `staff.read` (i.e. admin) AND `auth="cognito"` (identity set by
  the C3 staff bearer middleware, read from `scope["state"]["staff_identity"]`, fallback the `current_staff` contextvar)
  AND `is_owner`. The admin requirement keeps the existing "Role 'x' lacks the 'staff.write' permission" refusal for
  reviewer/content and matches the last-owner definition. `is_owner` was added to `StaffRow` / `StaffIdentity`
  (`api/core/staff_identity.py`, one more selected column) so the policy can decide without a DB call.
- **Fresh owner check**: every write locks all owner rows (`SELECT … WHERE is_owner ORDER BY id FOR UPDATE`) and then
  re-reads the actor (active + `is_owner`) inside its transaction, closing the 60 s identity-cache window. Locking the
  owner rows first, always, also prevents a deadlock between two guarded writes and two owners removing each other.
- **Last active owner** = `is_owner AND is_active AND role = 'admin'` (an owner without the admin role cannot open the
  page). Refused (409) when demoting from admin or disabling that row.
- **Self**: cannot demote (CIS role other than admin) or disable yourself (400). Changing your own Booking role and
  signing yourself out are allowed (the UI warns on self sign-out).
- **Break-glass row** = username `admin` OR email in {`admin@adventure.asia`, `breakglass@adventure.asia`} (D1 may move
  the address to `breakglass@`; both are covered). Every write refuses it with 403; create refuses those addresses.
- **Cognito steps** (sync boto3 via `asyncio.to_thread`, client built lazily once on its own Session, region = pool id
  prefix, timeouts 3 s connect / 8 s read, 2 attempts): create = AdminCreateUser (SUPPRESS, email, email_verified=true;
  UsernameExistsException = created) → add `cis-<role>` → add `booking-<role>`; roles = add new → remove old (per app);
  disable = AdminDisableUser → AdminUserGlobalSignOut; enable = AdminEnableUser; reset = AdminUserGlobalSignOut →
  AdminEnableUser (always: we may not read the pool state, AdminGetUser is denied and counts as MAU; enabling an
  enabled user is a no-op) plus `is_active = true` when the row was disabled; sync (active) = create → enable → add the
  wanted groups → remove every other `cis-*` / `booking-*` group; sync (inactive) = disable → sign-out (never creates).
  UserNotFoundException is ignored on disable / sign-out / group removal (nothing to undo) and fails the step elsewhere.
- **Allow-list enforced in code**: `CognitoDirectory._call` refuses any operation outside the six writer operations
  (`COGNITO_OPERATIONS`); a test checks AdminGetUser / AdminSetUserPassword / AdminDeleteUser / ListUsers are refused.
- **Pool id**: `identity_config.workforce_pool_id()` = env `COGNITO_WORKFORCE_POOL_ID`, else the last path segment of
  the WORKFORCE issuer (`DEV_WORKFORCE_POOL_ID = us-west-1_bCcFvbSOS`), so an issuer override moves the writer with it.
- **Username**: local part of the address, characters outside `a-z0-9._-` become `-`, trimmed to 96, then `-2`, `-3`, …
  until free; `admin` is never chosen. `password_hash` NULL, `is_owner` false (the owner flag is never writable here:
  the create body forbids extra fields).
- **Audit** (`acp_shared.audit_log`, actor `admin:<id>`, tenant NULL, resource_type `admin_user`): `staff.created`,
  `staff.roles_changed` (before/after; only when something changed), `staff.disabled`, `staff.enabled`,
  `staff.signed_out` (`reenabled`), written in the same transaction as the change; after Cognito, best effort,
  `staff.cognito_pending` (failed step + error code) or, for sync, `staff.cognito_synced`.
- **Rows without email** (legacy, unlinked): roles / disable / enable / sign-out change the DB only and report
  `cognito: "not_applicable"`; sync refuses them (400).
- **UI gating**: the list response gained `viewer {auth, is_owner, can_write, admin_id}` computed from the verified
  identity (not from cookies, which carry neither the owner flag nor the session kind); `lib/rbac.ts canWriteStaff()`
  reads it. The BFF write rule `platform/` (admin) was added to `API_WRITE_RULES`.

## Changed

- `GET /admin/platform/staff[/{id}]` rows now also return `email, display_name, is_owner, last_login_at, linked
  (cognito_sub IS NOT NULL), booking_role (LEFT JOIN staff_app_grant), breakglass`; the list adds `viewer`. The
  Cognito identity values themselves are still never selected.
- `StaffPrincipal` gained `auth` and `is_owner`; `principal_from_role(role, identity=None)`.
- Staff page: Name / email column with Owner / Break-glass badges, Booking role and Last sign-in columns, "Add staff"
  dialog, a "Manage access" panel in the drawer (role selects, Disable / Enable with confirm, Sign out everywhere with
  confirm, Retry Cognito sync), and ok / pending (with "Retry Cognito") / error banners. The drawer's old "Booking role:
  managed in Booking admin" line is replaced by the grant value.

## Tradeoffs

- Pending is HTTP 502 with a JSON body (`status`, `detail`, `failed_step`, `error_code`, `retry`, `staff`) rather than a
  2xx with a flag: a client that ignores the body still sees a failure. The BFF passes the body through unchanged.
- No AdminListGroupsForUser (not in the allow-list), so sync removes every non-wanted staff group blindly (up to 6 calls).
- Role change runs Cognito "add new" before "remove old": a failure in between leaves MORE access briefly, never none.
- The audit row is committed before Cognito runs; a failed Cognito step adds a second `staff.cognito_pending` row
  instead of rewriting the first.
