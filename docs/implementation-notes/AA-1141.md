# AA-1141 — Ecosystem status P1 (S291)

The eight P1 features the S285 review picked for the Ecosystem status page (`/admin/overview`, AA-1140), each 0 USD.
Migrations CIS 482 (expand: the ack and saved view tables) and CIS 483 (contract: eleven settings) ship first as one
migration-only PR; this code PR follows. Backend: `api/services/ops_status/` (new modules `changes`, `acks`,
`forecast`, `anomaly`, `pipelines`, `views`, `digest`); page: `frontend/app/admin/overview/` (new `_status/Ack.tsx`,
`Capacity.tsx`, `Changes.tsx`, `Views.tsx`).

## Decisions

- **1. Change annotations + What changed: read where each change is already recorded, no new writer.** Deploys from
  `acp_shared.ops_event` (the sampler, CIS 475), setting changes from approved `shared.setting_value` rows (at
  `effective_from`, every app), migrations from `shared.schema_versions` (every owner; the app from the key prefix),
  waves from `shared.rerun_wave` (opened, paused, closed) and route control versions from
  `shared.llm_route_config_version`. The `ops_event` kind CHECK stays as it is (no contract migration to widen it).
  Links: a deploy opens its commit in the app's public repo (the commit page names the PR), a setting opens Platform ›
  Settings on that key (its history), a migration the Data model page, a wave Jobs, a route change AI gateway ›
  Routing. Every chart draws them as vertical lines; a type is told by a letter on top (D, S, M, W, R) and its own
  line pattern, plus a colour; tick boxes hide a type (URL key `ann`); the panel filters by app and type (`chg`).
  The A0 assistant keeps its own short "what changed" evidence of one item; `changes.py` is the page's range-wide
  list (no duplicate of the assistant's collector).
- **2. Ack / snooze / mute.** Item ids are the status page's own ids. Ack lasts `cis.ops.status_ack_hours` (24) and
  then counts as open again if still there; snooze for one of the lengths of `cis.ops.status_snooze_choices_hours`
  (default [1, 4]; each one of 1, 2, 3, 4, 6, 8, 12, 24, 48, 72) or until `cis.ops.status_snooze_tomorrow_hour` (8)
  the next day on the viewer's clock. A length goes to the API as `snooze_hours` (refused unless the setting offers
  it; the API adds it to its own clock, so a skewed browser clock does not matter); "until tomorrow" goes as `until`,
  checked to be at most 48 h ahead and on a UTC quarter hour (the next morning on any clock); mute until a picked time, at most `cis.ops.status_mute_max_days` (7) ahead; reason at least
  `cis.ops.status_ack_reason_min_chars` (20). One row in force per item (a new ack clears the old one in the same
  transaction); "Back to open" clears it now. Audit rows `ops_alert_ack` / `ops_alert_ack_cleared` in
  `acp_shared.audit_log`. Who: route policy `ops.write` (role matrix: admin); the route also refuses the business
  owner (`shared.admin_users.is_business_owner`) and fails closed (503) when that flag cannot be read; the status
  answer carries `viewer.can_ack` (the ack route's own policy check for this principal, so read-only roles, view-as
  sessions and the read-only E2E identity see no buttons). An item set aside stays listed (status acked / snoozed /
  muted, "Acked by <name> at <time>, until <time>: <reason>"), sorts after the open ones and leaves the open count.
  An ack covers the severity it was given at (stored with the row) and milder: when the same item id gets worse
  (health "not ready" SEV2 to "fails" SEV1, warn to crit, a queue with no live worker) the item is open again and
  says "Worse since it was acknowledged at SEV2 by <name> at <time>: open again" (`escalated` block).
- **3. Freshness.** Every card's "as of" chip turns grey with the word "stale" after `cis.ops.status_stale_factor`
  (CIS 475, reused) x the section's refresh time, computed against the answer's `generated_at`. Footer "Background
  producers": the 5-minute sampler (newest `ops_sample`), the OPS-12 digest (newest finished `report_run`), the nightly
  probes (newest `kpi_daily` result), the delivery summary (`generated_at`) and the schema dump ("not measured yet":
  it runs on GitHub and in an ECS task without a verdict line CIS can read).
- **4. Capacity forecast.** RDS free storage: a least-squares line through the 6-hourly minimum of
  `FreeStorageSpace` over `cis.ops.status_forecast_window_days` (7). One GetMetricData metric, cached 6 h in Redis and
  never read without Redis: at most 4 reads a day, about 0.001 USD a month (GetMetricData has no free tier; this is the
  only AWS read added). With storage autoscaling the limit is the autoscaling ceiling (MaxAllocatedStorage from the
  sampler's database row); without it, the free storage warn limit (the CIS 477 share). AI caps: every LLM connection
  with a monthly budget (AI gateway › Budgets, `ai_gateway.read_connection_budgets`, the CIS share the gateway
  enforces), month to date as a straight line. That read is one month-to-date ledger scan (the reader used to scan
  twice: `cost_guard.connection_budgets` now takes the spend the caller already read) and is cached 15 minutes (the
  section's refresh time) in Redis, single flight with the last good value, so the 60 s refresh of every open tab, an
  ack POST and the digest reuse it; without Redis it is read directly; "not this month" when it would only reach the cap after the month
  ends. GitHub Actions cache: no source in the database, so the row says "not measured yet" with that reason. Levels:
  `cis.ops.status_forecast_warn_days` (30) / `_crit_days` (7); a critical row is a SEV3 Needs-attention item.
- **5. Cost anomaly.** Source `shared.ai_usage_hourly` (the quarter-hour rollup, live traffic only), never a second
  ledger scan: one read of baseline days x 24 hours plus the two hours checked, cached 5 minutes per hour and settings.
  Group app x provider family x route (`sections.connection_key`: `anthropic`, `openai`, `bedrock:<account>`), so the
  grouping holds when a route moves to Bedrock (tech lead G6). An hour (the previous complete one, or the current one
  so far) is abnormal above `max(N x median hour, floor)`: N `cis.ops.status_cost_anomaly_factor` (3), baseline
  `_baseline_days` (7, hours with no spend count as 0), floor `_floor_usd_h` (0.10 USD). Red banner above the verdict
  plus one SEV3 item per group (so it can be acked).
- **6. Daily digest.** The existing OPS-12 digest (job kind `report_generate` on `shared.job`, stored in
  `shared.report_run`, e-mailed to its opt-in list) gains an "Ecosystem status" section built by the SAME
  `build_status` / `verdict.decide` (range 24 h) on the job's pool and Redis before a connection is held, with links to
  the page filtered on the item's app and severity (and a link to the SEV1 / SEV2 view). It never fails the digest.
- **7. Saved views + pause.** Named views per staff member in `acp_shared.ops_saved_view` (only the page's URL keys,
  each a short plain value; a name that exists is replaced). Auto refresh pauses on a custom range (a drag across any
  chart zooms: it becomes a custom range), while the tab is hidden (`visibilitychange`), or by hand (Pause / Resume
  chip).
- **8. WCAG 2.2 AA.** Levels next to coloured values carry a glyph with the level in words (`LevelGlyph`); the
  uptime strip is an image with its counts in words; the verdict headline is `role="status" aria-live="polite"`;
  every chart has a table view (signals: per step; resource sparklines: latest / worst / limits; the uptime strip and
  the event lanes already sit next to tables with the same numbers); controls are kit buttons, inputs and tick boxes
  (keyboard focus from the kit); the change types are told by letter and line pattern, not colour.

## Changed (against the issue)

- Cost Explorer read once a day (item 5, optional, about 0.30 USD a month): **not done**, it needs an explicit yes.
- Push for SEV1 / SEV2 not acknowledged after N minutes (item 6): **P2, not built** (the issue allows it); the SNS
  alarms still page in real time.
- Actions cache forecast (item 4): no source in the database; shown as "not measured yet".
- Saved views are server-side per staff member (work across devices), not the kit's localStorage DataTable views.
- The anomaly breaker's cached median (`anomaly_breaker.cached_median`) is a whole UTC day of one app; this banner
  judges one hour of one app x provider x route, so the two are not the same quantity and the breaker cache is not
  reused (see `anomaly.py`).
- Tables in `acp_shared` (DM-1.5: CIS-private), like CIS 475.

## Tradeoffs

- The ack route builds the status page once to find the item (so an ack names an item that exists now, with its
  title, app and severity as seen); the CloudWatch part is the page's own 5-minute cache.
- An all-acked page reads "All systems normal · N set aside": the items stay listed and counted next to the headline.
- The digest part costs one status build per day on the worker (DB reads; the CloudWatch signals come from the cache
  when the page was opened in the last 5 minutes, else one read, about 0.00025 USD).
- The forecast's storage line uses the 6-hourly minimum, which follows autoscaling steps as a jump; the ceiling answer
  is the one that matters while autoscaling is on.

## Review fixes (S291, independent reviewers)

- Forecast budgets: cached and scanned once (see decision 4). The Budgets tab of the AI gateway gets the single scan
  too (same reader).
- Escalation: an ack, snooze or mute no longer hides an item that got worse (see decision 2). An acked SEV1 that stays
  SEV1 still leaves the open count (the person on duty took it, with a reason, for at most the ack hours); this was
  weighed and kept, the item stays listed next to the headline.
- Snooze lengths: a setting (`cis.ops.status_snooze_choices_hours`, folded into CIS 483 before it is applied) instead
  of the page's fixed 1 h / 4 h; the API checks every snooze against it. The unused `SNOOZE_HOURS` constant is gone.

## S292 — two noisy Needs-attention items (lane h-status-noise)

The tech lead confirmed both as noise and asked to fix the checks, not their thresholds.

### Decisions
- **Role connections (`rds_role_connections`)**: "crm_app 5/6" fired only while the partner CRM rolled out. Its
  CONNECTION LIMIT 6 is pool max_size 3 x 2 tasks, sized for the few minutes the old and the new task overlap. The
  check now alerts only when a role stays above `cis.ops.role_connections_pct` on `cis.ops.role_connections_samples`
  (CIS 488, default 3, 1-12, maker-checker, EN + VI guide) api sampler ticks in a row (5 minutes apart). The run is
  counted per process in a plain dict the sampler loop holds and passes through `sample_once(role_runs=...)` into
  `state_findings(tick, role_runs)` (`shared/ops_checks.observe_role_runs`). The tick logs `roles_above_samples`.
  A dict, not a class, kept `api/core/ops_metrics_sampler.py` within the 800-line code-health limit.
- Why samples in a row and not "skip a role while its ECS service has a rollout in progress": the ECS state is read
  by another job (the status sampler on the worker), up to 5 minutes apart from the api's role read, so a deploy that
  starts between the two reads would still alert; it would also need a DB role -> ECS service map that no other code
  keeps (the TripPlanner role is Lambdas, db_migrator runs one-off tasks). Samples in a row need neither, work for
  every app's rolling deploy (CIS's own included) and still alert on a lasting peak.
- **Route digest**: only routed stages are judged (`route_watch.routed_stage`: a `shared.llm_role_config` row or a
  code route in `role_config.SAFE_DEFAULTS`, and never an `adhoc_` name). The connection probe `adhoc_conn_test`
  calls every model of every connection, the ones an account refuses included, so its "requests with no answer" are
  its expected result, not a route problem. Unrouted stages are named in the digest's `unrouted` list (job result) and
  left out of its totals and its bell.

### Changed
- A tick whose role read failed (no `roles` field) neither adds to nor resets a run.
- `state_findings(tick)` without a tracker keeps the old one-sample rule (callers and tests that hold no history).
- The watch alerts (`route_fb`, `route_last`, `route_cost`, `route_back`) are unchanged: `route_last` already needs a
  route of two models; the others had not fired on the probe.

### Tradeoffs
- An api restart (every CIS deploy) starts every run again: a real lasting peak across a CIS deploy alerts up to
  N ticks later. Accepted: no state table, and the bell dedupe already spans two api tasks.
- A deploy whose overlap lasts N ticks or more (a stuck rollout) alerts; that is wanted, and the failed rollout is its
  own SEV2 item.

  488. Its branch needs origin/main with the migration PR merged before its tests pass.
