# AA-840 — Slate proposes for every enabled Channel (Facebook no longer starved)

Branch `fix/aa-840-slate-per-channel` (S238, lane F). Linear: AA-840. Related: AA-831 item 3, AA-632, AA-511 Gap B.

## Decisions

1. **Source of "enabled channels" = `acp_shared.tenant_config.channels`.** It is the only per-tenant
   channel setting (admin Tenant 360 > Planning config, migration 101). `shared.tenant_integrations`
   (WordPress / Facebook connections) was considered and rejected: planning must not depend on a
   publish connection (email, LinkedIn, Instagram, TikTok, landing page and ads have no publish step
   at all), and a tenant should see Facebook ideas before they connect a Page.
2. **No `tenant_config` row = every Channel** (today's behaviour). Read by
   `slate._tenant_enabled_channels()`; values the Slate does not know are ignored; the result is in
   `CHANNEL_BARS` order so the round-robin is deterministic.
3. **Place rule (documented in `_choose_slate()` and CONTEXT.md, Slate step 3):**
   - a place (Segment `canonical_place`) appears at most once per Channel (origin `choose()` rule,
     strongest Segment keeps it);
   - a place appears on at most `MAX_CHANNELS_PER_PLACE = 3` Channels of one Slate;
   - Channels take turns: each round, every enabled Channel in `CHANNEL_BARS` order takes its
     strongest candidate still allowed (Bar cleared, place rule, `most_per_hub`), until none can.
   - Routes (Blog) carry no place and are never counted.
   Round-robin is what actually fixes the starvation. A per-Channel place set alone (no cap) would
   put every place on all 7 Segment Channels; a cap without turns would still let the first 3
   Channels (LinkedIn, Facebook, Instagram) take every seat and starve TikTok and the on-demand
   Channels.
4. **Why 3:** with N bar-clearing places a Slate has 3·N Segment seats. A live-shaped simulation
   (17 places clearing the social Bar + 8 that only clear the open on-demand Bar, all 8 Channels)
   gives linkedin 8, facebook 8, instagram 7, tiktok 7, email/landing_page/ads 15 each. Before:
   linkedin 17, facebook/instagram/tiktok 0, email ~8 (matches the live Dev counts below).
5. **`compute_slot_grid()` is deleted, not wired** (separate commit). It is the N6 monthly
   calendar allocator: it needs an approved `QuarterPlan`, a `RunwayMap`, `Trip` and `AtomRecord`
   rows and produces trip/atom `Slot`s — the deprecated Slot concept (CONTEXT.md: "_Avoid_: slot").
   The Slate works on Segment/Route × Channel Subjects and has no quota; making the allocator its
   quota source would mean building a quarter plan for every tenant on every proposal. The one
   thing the Slate needed from that path — the tenant's channel list — is now read directly.
   Removed with it: `Slot`/`SlotGrid` (models), `FRAMEWORK_TABLE`/`SLOT_MIX` (constants), and the
   tests that only exercised the allocator (`test_aa301_allocator.py`, the allocator half of
   `test_aa449_channel_extension.py`, `TestSlotGridIsolation` in `test_aa301_multitenant.py`).
6. **Fetch / Debate only the grains an enabled Channel uses.** Blog-only tenant: no Segment fetch,
   no Segment Debate (Debate's brand-fit cut is a paid call on a cache miss). `apply_debate()` is
   still called with `[]` (returns at once), so the call shape is unchanged.

## Changed

- `services/acp_shared/slate.py`: `_tenant_enabled_channels()`, `_hub_key()`, `_choose_slate()`
  (round-robin + place rule), `_choose()` is now a one-Channel wrapper (the `seen_places` parameter
  is gone), `propose_slate()` proposes only for enabled Channels, still runs the stale-`proposed`
  DELETE for every Channel (switching a Channel off clears its proposals; picked/used/cut stay), and
  returns `channels` + `proposed_per_channel` in the `t7_slate` job result. `fetch_slate()` adds
  `enabled` per Channel and hides `proposed` rows of a disabled Channel at once (still read-only:
  one extra SELECT, no LLM — AA-764 holds).
- `services/acp_planning/tenant_config.py`: the channels fallback for a tenant with no row is every
  Slate Channel (was `["blog"]`). Only the admin GET/PUT `/admin/tenants/{id}/config` reads it
  (trip reallocation reads only markets). Before, the admin form showed `blog` for every tenant
  while the Slate used all Channels, and saving the form unchanged would have narrowed the Slate to
  blog.
- `api/migrations/236_tenant_config_all_channels.sql`: widens the `tenant_config_channels_valid`
  CHECK from blog/facebook/tiktok/email (migration 101) to the 8 Channels. The API already accepted
  8 (`_VALID_CHANNELS`, AA-449); saving linkedin/instagram/landing_page/ads failed in the DB.
- `CONTEXT.md` Slate step 3 rewritten.
- Tests: `tests/unit/test_aa840_slate_channels.py` (new, 24 tests: the 5-segment repro, place
  rule, determinism, enabled-channel source, `propose_slate()`/`fetch_slate()` on a fake pool);
  `test_aa511_slate.py`: the two AA-632 shared-`seen_places` tests replaced by the new rule;
  `tests/integration/test_aa840_tenant_config_channels.py` (migration 236 on real Postgres: 8
  Channels save, unknown still rejected, the Slate reads the row). Checked red without 236 (3 of 4
  fail on a fresh DB) and green with it, on a private PG16.

## Tradeoffs

- LinkedIn now gets about half the proposals it had (17 → ~8 on Dev tenants). Tenants post 3/week,
  so 7–8 per Channel is still more than a week's need; the cap is one constant to tune.
- The round-robin favours Channels earlier in `CHANNEL_BARS` by at most one pick per round (they
  pick first in each round). Kept, because it is deterministic and the gap is small.
- On-demand Channels (open Bar) compete with social Channels for the same strong places. They pick
  last in each round, so the social Channels get first choice of the places only they can use.
- A tenant whose `tenant_config` row predates AA-840 is now filtered by it. On Dev only
  `exploreasia-co` (inactive) has a row (`{blog}`) → it will get a Blog-only Slate.
- `pick_subject()` does not re-check the enabled list: a stale `proposed` row of a just-disabled
  Channel is hidden by `fetch_slate()` and removed by the next proposal, but a direct POST with its
  id would still pick it. Not worth a guard now.
