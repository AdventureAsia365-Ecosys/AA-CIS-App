## AA-103: E2E UI Build (CIS + ACP full stage pages)

### Decisions

**CIS frontend uses inline styles (not Tailwind)**
Decision: Matched the existing CIS dashboard/tenants pattern which uses inline styles + adminUi.tsx design system. ACP uses Tailwind — kept them separate.

**POST /v1/pipeline/run for S0 upload (not presigned S3 flow)**
Decision: Used existing `/v1/pipeline/run` (file upload → sync pipeline) for the CIS S0 upload page. This runs S0+S1 together, not just S0. The "run-batch" endpoint from the task spec doesn't exist.
Why: The presigned URL flow (`/v1/pipeline/upload-url` + `POST /v1/pipeline/ingest-s3`) is more complex and the output structure is less clear. `/v1/pipeline/run` works immediately.
TODO: If S0 needs to show raw_tours without running S1, a new `/v1/pipeline/ingest-only` endpoint is needed.

**ACP S1 uses `/acp/s1/` endpoints (not pipeline/run)**
Decision: CIS /pipeline/s1 and ACP /pipeline/s1 both use the `/acp/s1/` router which has proper batch management, SSE, and version comparison.

**Gate 1 uses `/v1/acp/gate/gate1/` endpoints**
Actual backend path for Gate 1 approve/reject: `POST /v1/acp/gate/gate1/approve` and `POST /v1/acp/gate/gate1/reject`.
Gate 2 uses the older pattern: `POST /v1/hitl/gate2/{run_id}/approve`.
Gate 3 uses the new pattern: `POST /v1/acp/gate/gate3/approve`.

**ACP CI triggers only on PRs to main**
The ACP `.github/workflows/ci.yml` trigger is `pull_request: branches: [main]`, not `[develop]`. Created draft PR targeting develop for code review but can't trigger CI from feature branch. Verified locally with `npm run lint` (next lint) and `tsc --noEmit` — both clean.

**CIS AdminSidebar `active` check uses `startsWith`**
The existing sidebar checked exact match `pathname === n.href`. Changed to `pathname.startsWith(n.href + "/")` for nested routes like `/pipeline/s1`.
Risk: `/workspace/pipeline` would match `/workspace/pipeline/s0` — mitigated by exact-match taking priority.

### Changed

- `/upload` page: Shows pipeline results (after S0+S1), not pure raw_tours. The API combines ingestion and rewrite in one step.
- ACP workspace nav: Added S0–S4 stage pages to existing nav. Removed `/workspace/s1/run` and `/workspace/s3/review` shortcuts to reduce duplication — kept them accessible from nav.

### Tradeoffs

- **Inline styles vs Tailwind for CIS**: Matched existing code. Slightly more verbose but consistent with dashboard/tenants pages.
- **Synchronous pipeline in S0**: `/v1/pipeline/run` blocks until all tours are processed (up to 20 × ~30s). UI shows "Processing…" indefinitely. Better UX would be async with SSE, but that requires a new endpoint.
- **ACP pages use `run_id` query param**: All S2/S3/S4 pages accept `?run_id=...` to navigate between runs. Simpler than storing in localStorage.

### Should Know

- CIS S1 page shows all tours (not filtered by batch). The `GET /acp/s1/tours` endpoint lists all approved raw_tours.
- ACP S3 content calendar parsing: The calendar markdown is extracted with a rough regex on `|`-separated table rows. Works for standard markdown tables but may break on nested pipes.
- ACP S4 social posts: The `social` field path in BlogDraft is inferred (`draft.social`). The actual API response structure may differ — check `v1_s4_social.py` if this is empty.
- Gate history is not yet shown — just current status. If review history matters, the HITL endpoints need a history endpoint.
