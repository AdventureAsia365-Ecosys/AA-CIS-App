# AA-796 — T2 tenant projection (AA-770 compliance for tenant APIs)

## Decisions
- Projection-only (S235 synthesis correction, wins over the original B plan): the stored
  `tenant_tour_versions.status` is not changed and `services/jobs/t2_rewrite_job.py` is not touched.
  `needs_review` (score < 7.0) stays the admin signal; tenant reads map it to `ai_generated`
  ("Ready to review") at read time. No data UPDATE of the existing rows.
- One shared module `api/routers/_tenant_projection.py` owns the tenant rule (status mapping,
  hidden fields per table, forbidden-key regex, key-walk helper). `v1_tours.py` and
  `v1_marketplace.py` both import it; `v1_marketplace.tenant_version_state` is re-exported.
- Every tenant projection also drops any column whose name matches the forbidden-key regex
  (`needs_review|quality|score|qa_|judge|llm_cost|jev_cost`), on top of the named hidden fields.
  Several reads are `SELECT pt.*` / `ttv.*`, so a column added later cannot leak by default.
- `/v1/tours/{id}/full` tenant-JWT branch returns only `published` (no `quality_score` /
  `quality_score_id`), `raw` (minus the admin A1 review state: `review_status`, `reviewed_by`,
  `reviewed_at`, `review_notes`) and `seo`. `generated` and `quality` are not even queried for a
  tenant. The admin (`X-Admin-Secret`) branch is unchanged — `frontend/app/api/tour-full/[id]` uses it.
- Gate-1 (Nghiệp, 14/10/2026): the A1 quality score is removed from the tenant pool (column,
  `min_quality` filter, `sort=quality`); the pool is always newest first. Old clients sending
  `min_quality` / `sort=quality` get a 200 with the newest-first list (FastAPI ignores the unknown
  param; `sort` is still accepted but ignored).
- Gate-1 (Nghiệp, 14/10/2026): `/v1/billing` no longer returns `llm_cost_usd` (nor `jev_cost_usd`,
  which it never selected but is now explicitly stripped). This deliberately REVERSES AA-636, which
  kept `llm_cost_usd` in the response while hiding it in the UI. Reason: LLM/Jev spend is AA's
  cost, not part of the tenant's bill, and migration 223 (AA-798) may only drop/recreate the view
  once no tenant API reads that column.
- `/my-versions?status=ai_generated` (or `needs_review`) matches both stored values
  (`ttv.status = ANY($n::text[])`) so a low-score version is never hidden from the tenant's list.

## Changed
- New `api/routers/_tenant_projection.py`: `tenant_version_status`, `tenant_status_filter`,
  `tenant_version_state` (moved from v1_marketplace), `project_version/tour/raw/billing`,
  `TENANT_FORBIDDEN_KEY_RE`, `forbidden_keys` (key-walk helper used by the test).
- `api/routers/v1_tours.py`: pool (no score column/filter/sort, rows projected), billing (no cost
  column, activity status mapped), my-versions (rows projected, filter widened), `/{id}/full`
  tenant branch, `GET /{id}`, `/versions/{id}` + `version_history`.
- `api/routers/v1_marketplace.py`: imports the shared state function; rows go through
  `project_version` before the coarse state mapping.
- Portal: `ui.tsx` — `needs_review` reads "Ready to review" with the default badge (defence in
  depth); unused `ScoreBadge` removed. `PoolFilters.tsx` — sort select removed (only one option
  was left). `PoolTab.tsx` — `quality_score` type + `sort` param removed. `DashboardTab.tsx` —
  `llm_cost_usd` type removed. `PlaceholderTabs.tsx` needed no edit (it renders through
  `statusLabel`).
- NOT changed (per S235 correction): `services/jobs/t2_rewrite_job.py`, the admin routers, any
  stored data, migrations, CONTEXT.md (text handed to the orchestrator).

## Tradeoffs
- Read-time mapping vs changing the job: the job change would make stored data honest for the
  tenant but would lose the admin's simplest signal and collide with Lane A's T2 rerun. Mapping at
  read time is reversible and keeps history as written.
- Regex safety net can, in theory, drop a legitimate content column whose name contains `score`
  etc. None of the projected tables has one today (checked against db-schema-reference.md).
- Removed the sort control instead of leaving a one-option select.

  reader found).
- The 3 existing `needs_review` rows stay `needs_review` in the DB; admin views keep showing them.
