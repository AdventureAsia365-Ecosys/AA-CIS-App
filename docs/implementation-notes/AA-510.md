## route_id generation — reported before deciding (per build prompt's own gate)

Read `src/aa_social/routes.py` fresh (not re-derived from STEP0 alone) — `derive_routes()`,
line 107:
```python
route_id=f"{trip_code}:{first}-{last}"
```
**Answer: neither hash nor uuid4() — deterministic string concatenation** (`chuỗi ghép`) of the
trip identifier and the day span. The build prompt's fallback ("nếu repo gốc không cho câu trả
lời rõ ràng, mặc định dùng uuid4()") does not trigger — the origin answer is unambiguous.

**Adapted for AA-CIS, not ported verbatim**: the origin is single-tenant (1 SQLite file per
brand, no `tenant_id` concept at all). AA-CIS is multi-tenant with a shared `route` table — two
different tenants can both rewrite (own an `owner_scope`) the same underlying
`raw_tours.tour_id` (AA-445-02's shared-pool rewrite pattern), so `tour_id:first-last` alone
would collide across tenants. Decision: **`route_id = f"{tenant_id}:{tour_id}:{first_day}-
{last_day}"`** — same deterministic-concatenation family the origin uses, extended with the one
dimension (`tenant_id`) the origin never had to handle. Documented here rather than silently
changed.

## derive_routes() / families() — reported before deciding

Both are pure functions, ported near-verbatim (confirmed via STEP0 + this session's own re-read):

- **`derive_routes(moments)`**: group by trip key → cut into consecutive-day runs (`_runs`, a
  gap of >1 day breaks the run — usually the transfer day) → cut runs into ≤`MOST_DAYS=5`-day
  spans (`_spans`) → drop spans with `<LEAST_DAYS=2` days or `<LEAST_PLACES=2` distinct places.
  Not a sorting algorithm — order is itinerary day order, full stop.
- **`families(trips, share=SHARED_ENOUGH=0.3)`**: union-find. Two trip keys merge when
  `|shared segment_ids| / min(|A|, |B|) >= share` (ratio over the SMALLER set, deliberately, per
  the origin's own comment — a big trip sharing a little with a small one still counts). Family
  name = alphabetically-smallest member. Threshold `0.3` is a constant measured on the origin's
  own Japan catalog, not a law of nature — kept as AA-CIS's starting point (module constant,
  never inlined) since this repo has no equivalent catalog to re-measure against yet.

## Decisions

1. **`route_id` — see above.** Deterministic composite key, not uuid4().
2. **Schema correction vs. the build prompt's literal SQL — `route.tour_id` is `UUID`, not
   `TEXT`.** `silver_aa_internal.raw_tours.tour_id` is `UUID PRIMARY KEY` (confirmed,
   `002_schema_v2.sql`/`003_schema_v3.sql`) — a `TEXT` FK column cannot reference a `UUID` PK in
   Postgres; the literal migration in the build prompt would fail to apply. Fixed to `UUID`,
   matching every other FK into `raw_tours(tour_id)` in this codebase (`tour_atoms.tour_id`,
   `atom_ranking.tour_id`).
3. **Schema addition vs. the build prompt's literal SQL — `route` gains `first_day SMALLINT`,
   `last_day SMALLINT`, `score INT` columns**, none of which the prompt's literal `CREATE TABLE`
   lists. The origin's own reference schema (`workspace.py:318`) has all three
   (`first_day INTEGER, last_day INTEGER, score INTEGER`) and the live-verify requirement itself
   ("Route đúng thứ tự total_rank") is not checkable from a table that only stores
   `ordered_segment_ids` — there would be nothing to `ORDER BY` without re-deriving it from
   `atom_ranking` on every read. Added as the minimal fix, not a redesign.
4. **`atom_ranking` grain is per-Segment, not per-Atom (AA-515 Decision 3)** — so `Moment` here
   is keyed on `segment_id`, not `atom_id` (the origin's own grain), and `route.ordered_segment_ids`
   stores segment ids, matching the column name the build prompt itself chose. `day`/`place` for
   a (tour, segment) pair come from `MIN(tour_atoms.itinerary_day)` / `atom_segment.canonical_place`
   — a segment normally lands on one day per tour; `MIN` is the defined tie-break for the rare
   case it doesn't (e.g. a re-visited place two different days), not a silent bug.
5. **Only non-excluded (`excluded_reason IS NULL`) `atom_ranking` rows feed `derive_routes()`**
   — matches the origin (`score` stage) reading only `atom_scores`-ranked atoms, and ADR 0019/
   0020's transit/unnamed-place exclusion, already enforced one layer down at ranking time
   (AA-515), is not re-implemented here.
6. **Hub matching threshold reuses `SHARED_ENOUGH` (0.3)`** for both family-forming (route→route
   grouping by tour) AND hub-reuse matching (new family's tour-id set vs. an existing hub's
   tour-id set) — one named constant, not two unvalidated magic numbers. Prompt only specified
   the family-forming case; extending the same constant to hub-reuse was the smaller, disclosed
   choice over inventing a second unmeasured threshold.
7. **Hub matching signal is tour_id-set Jaccard first, hub_name equality as a tie-break** — "match
   Hub cũ qua tour_id set/hub_name" (prompt) read as: the primary evidence is which real tours a
   hub covers (durable across a Segment-level reshuffle), name equality is a secondary check for
   the (rare) case a freshly-computed name coincides with an old hub's name despite low tour
   overlap. Implemented as tour-set match primary, since it is the evidence that actually survives
   Route's own rebuild-whole churn.
8. **`hub.hub_name` is never overwritten on reuse** — only set at creation. A rebuild that matches
   an existing hub bumps `updated_at` only. This preserves any future marketer rename (no rename
   UI exists yet, but the column is a real "chosen name" per CONTEXT.md's Hub definition — "named
   as a traveller would say it" — not a value this pipeline should keep clobbering).
9. **Hub name generation (no marketer UI exists yet)**: deterministic placeholder —
   `" → ".join(places)` from the alphabetically-first tour in the family (mirrors the origin's
   own "family named after first trip_code" rule, applied to name generation since AA-CIS has no
   equivalent to a human-authored family name yet). Disclosed placeholder, not a claim this is
   marketer-quality copy — CONTEXT.md's own Hub definition (human-chosen name) implies a future
   naming/rename step is separate scope, matching STEP0's suggestion that Hub's "human pick" layer
   is properly AA-511+.
10. **Hub rows are never deleted.** Route is rebuilt whole (DELETE+INSERT) every run, matching
    the STEP0-confirmed origin behavior (`_store_routes()`, "derived, never accumulated"); Hub is
    NOT — an unreferenced-this-run hub is left in place. This is what makes
    `subject.route_snapshot`'s immutability (ADR 0024) actually meaningful: a Subject that named a
    Hub can still show that name even if this tenant's next rebuild no longer regroups any route
    into it.
11. **Route detection has no `channel` column/filter.** The build prompt's "chỉ Channel=Blog" is
    read as scope framing, not a per-row filter to implement — Route/Hub have no channel concept
    of their own (confirmed: neither the prompt's schema nor `atom_ranking`/`atom_segment` carry
    one); the Blog-only constraint is enforced entirely by only Blog-track consumers (future
    AA-511 slate/subject-pick UI) ever reading Route/Hub at all. `channels.toml`'s
    `takes_route=true` (STEP0 Q2) is exactly this — a downstream-consumer flag, not a filter this
    stage applies to itself.

## Changed (existing files)

- `api/routers/v1_tours.py::_run_ranking_pipeline()`: after `run_atom_ranking()` succeeds, calls
  `run_route_detection()` in the SAME background task (not a second `create_task()` — Route is
  built entirely from what ranking just wrote, so this is the natural next step of one pipeline
  run, not an independent trigger). Its own failure is caught separately and does not undo a
  successful ranking result already committed.

## Tradeoffs

- `journey_name()`/Hub naming is a disclosed placeholder (Decision 9), not marketer copy — a
  real naming/rename UI is out of this build's scope (STEP0's own suggestion: that's the
  "human pick" layer, closer to AA-511+).
- Hub-reuse matching reuses `SHARED_ENOUGH` rather than a separately-measured threshold
  (Decision 6) — disclosed, not silently assumed equivalent.
- `MIN(tour_atoms.itinerary_day)` as the tie-break for a Segment landing on >1 day within one
  tour is untested against real data (no real tour in this catalog is known to do this) — a
  reasonable default, not a measured one.
