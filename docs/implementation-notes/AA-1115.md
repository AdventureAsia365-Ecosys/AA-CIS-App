# AA-1115: the planner addresses for the launcher snippet (CIS half)

The CIS half of AA-1115. AA-Partner shows the Trip planner launcher snippet on the Content studio's Add-ons page
(`web/lib/plannerLauncher.ts`), and AA-TripPlanner-Web serves the agency-branded planner. The snippet needs data
only CIS has: the tenant slug, its active custom planner hosts, and the `tp.launcher` entitlement.

## Decisions

- **Field on the studio list only.** `GET /v1/account/add-ons` now answers `StudioAddOnList`: each entry may carry
  `planner` {url, domains, launcher}. The value is set only on the tripplanner entry while it is `active`, and is
  null everywhere else. The CRM relay (`tenant.addons.v1`, `api/routers/tenant_addons.py`) keeps its frozen
  contract: `AddOnState` is unchanged, and a test checks this.
- **No URL when the planner would be a 404.** `url` is set only when the tenant is in service, `tp.hosted`
  resolves, and the slug has the TripPlanner slug shape. This is the same rule as `served` in
  `catalog.v_tenant_tripplanner_v1`. Otherwise `planner` is null and the page shows no snippet.
- **Origin from the existing TripPlanner host setting.** The origin is the scheme and host of
  `TRIPPLANNER_REVALIDATE_URL`, which AA-CIS-Infra already sets for the catalogue purge job. When that is not set,
  the origin is the Dev host. Only https is accepted. This is an address, not a threshold, so it needs no admin
  setting.
- **Domains:** only rows of `shared.tenant_tripplanner_domain` with status `active`, sorted. A host that is still
  being validated is not offered.

## Changed

- `services/tenant_account/planner_site.py` (new): one query on the main pool (`cis_app` reads `shared.tenants`,
  `shared.v_tenant_entitlement_resolved` and `shared.tenant_tripplanner_domain`).
- `api/routers/v1_account_addons.py`: `PlannerSite`, `StudioAddOnState`, `StudioAddOnList`, and `_with_planner`.
- `docs/api/openapi.json` (regenerated with the pinned fastapi/pydantic) and `CONTEXT.md`.
- Tests: `tests/unit/test_aa1115_planner_site.py` and `tests/integration/test_aa1115_planner_site_pg.py`.

## Tradeoffs

- One extra query per list read, run only when the tripplanner add-on is active. The list is read by hand on the
  Add-ons page, so the cost does not matter.
- "View as tenant" sessions see the addresses too. They are public URLs.

## Should know

- No migration. The Partner page already reads `planner` and stays hidden until this ships.
