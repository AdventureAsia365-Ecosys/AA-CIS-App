# AA-116 — Gate 3 Retry Context

## Decisions

**gate3_context lives on blog_drafts, not acp_hitl_requests.**
The task spec references `acp_hitl_requests`, but Gate 3 HITL is implemented entirely on `acp_silver_s4.blog_drafts` (via `hitl_gate3_status` / `PATCH /drafts/{draft_id}/hitl`). Gates 1 and 2 use `acp_hitl_requests`; Gate 3 does not. Adding `gate3_context` to `blog_drafts` keeps the data co-located with the HITL decision.

**`_build_gate3_context` is a pure function** exposed at module level so unit tests call it directly without mocking the full graph.

**gate3_context = None when first attempt passes** (single entry with score ≥ threshold). The condition `len(history) == 1 and score >= threshold` is the only null case; a single failed attempt (circuit breaker with MAX_REWRITE=1) still produces a context.

**score_history uses len(history)+1 for attempt numbering**, not `rewrite_count+1`. `rewrite_count` is shared between post_process violations and evaluator failures, so it could over-count. `len(score_history)+1` is exact per evaluate_node call.

**issues capped at 5** per entry (`issues[:5]`) to keep JSONB payload bounded.

## Changed

- `S4BlogState` gains two new fields: `score_history: list` and `gate3_context: Optional[dict]`.
- `evaluate_node` appends `{attempt, score, issues}` to `score_history` on every call (pass or fail).
- `save_node` calls `_build_gate3_context()` and includes `gate3_context` in the INSERT.
- Migration 062 adds `gate3_context JSONB` (nullable) to `acp_silver_s4.blog_drafts`.
- `GET /v1/acp/s4/blog/drafts/{draft_id}` now selects and returns `gate3_context`.
- `_run_pipeline` initialises `score_history=[]` and `gate3_context=None` in state.

## Tradeoffs

- Could have built gate3_context inline inside save_node rather than extracting to a helper, but the helper is testable without any async mocks.
- Did NOT add gate3_context to `acp_hitl_requests` because that table is unused for Gate 3.

## Should know

- Reviewer: the `gate3_context` field is read-only from the API — Trang cannot edit it.
- The acknowledgment checkbox (frontend) must gate the Approve button when `best_score < 7.0`. This is a frontend concern in AA-ACP-App; the backend just persists and surfaces the data.
- `score_history` tracks evaluator-only scores. Post-process rule violations don't appear here.
