# AA-998 — Remove acc1 from the CIS LLM gateway and cost reads

S255 (28/10/2026). acc1, the personal AWS account that was the cross-account LLM fallback (AA-397) and
the third Cost Explorer account (AA-623), leaves the ecosystem. LLM runs on acc3 only; acc2 native stays
as it is (embed, and the legacy T1/T2 tiers behind `LLM_LEGACY_ACC2_NATIVE`). Nghiệp accepts losing the
cross-account fallback: an acc3 failure now falls to a same-account model (legacy chain Sonnet → Haiku on
acc3, or the stage route's next model) or to the job retry.

## Decisions
- `bedrock_satellite`: only `acc3` in `_SATELLITE_ACCOUNTS` / `_INFERENCE_PROFILES`; the defaults of
  `_get_satellite_session`, `get_satellite_client`, `invoke_claude` and `LLMClient._call_bedrock_satellite`
  are `DEFAULT_SATELLITE_ACCOUNT = "acc3"`. An unknown account (incl. "acc1") raises `ValueError` before any
  AWS call. `INFERENCE_PROFILE_SONNET/HAIKU` kept as names, now built on acc3.
- Legacy chain: tiers T1.5b / T2.5b and the `fallback_acct` parameter removed from every `LLMClient` method
  (`_call_key`, `_call_key_logged`, `_call_route`, `_legacy_*`, `_start_shadow`, `_run_shadow*`). Event names
  that named the removed tier now name the next tier (`t1_5a_satellite_failed_trying_t2`,
  `t2_5a_satellite_failed_trying_t3`); no metric filter in AA-CIS-Infra uses them.
- `CatalogModel.account_for` only considers `SERVING_ACCOUNTS = ("acc3", "acc2")`; a stale "acc1" profile
  (before migration 295 applies) or `account_route = 'acc1'` is never chosen.
- Settings › Models: `_ACCOUNT_ROUTE_OPTIONS` = acc3 only; `PATCH /admin/llm-config/{stage}` answers 422 for
  any other `account_route` (before the DB CHECK would). `S1BatchSubmitRequest.account` is `Literal["acc3"]`.
- Cost Explorer: fetches `FETCH_ACCOUNTS = ("acc2", "acc3")`; "all failed" = both. Historical
  `shared.cost_explorer_snapshot` rows of acc1 stay and are read with `account_key = "retired"`
  (`RETIRED_ACCOUNT_KEY`): any stored account that is neither acc2 nor acc3 (the code holds no acc1 ID any more).
- Cost per app (`platform_cost.llm_satellites`): `acc3` always; a `retired` entry (account_id null) only when the
  month holds CE history or llm_call_log Bedrock rows of another account. Cost Operations forecast: Bedrock split
  and AWS rows acc2/acc3, plus one `retired` row only when the month has its data. Frontend maps any llm_call_log
  account other than acc2/acc3 to "retired" and never shows that account's ID.
- Guard test `tests/unit/test_aa998_no_acc1_runtime.py`: fails if `acc1`, the acc1 account ID, the three acc1 IAM
  roles, the fallback-account env var or the acc1 CLI profile appears in runtime code (api/ except migrations,
  services/, shared/, worker/, scripts/, frontend/app, frontend/lib, frontend/components, portal/). README /
  CONTEXT may say "acc1" (retired) but name none of its resources. Comments included, so runtime code says "the retired
  fallback account" instead of the name. The account ID is matched by its sha256 only (review fix): an ID split
  into string parts is still the ID in a public repo (AA-902, DM-6.10), so the test hashes every 12-digit run of a
  line and compares it with the stored digest; `.github/scripts/check_resource_ids.py` already refuses any
  12-digit account ID.

## Changed
- Migration 295 (own commit): `bedrock_profile_ids - 'acc1'` on every row that has it (refuses a row whose only
  profile is acc1), and `llm_role_config_account_route_check` → `account_route IS NULL OR = 'acc3'` (refuses while
  a stage routes to acc1). The `generated_content.satellite_account` CHECK (100) is kept: historical rows hold
  'acc1'. Old migrations untouched.
- Tests rewritten acc3-only; conftests and `scripts/export_openapi.py` drop the fallback-account env stub;
  `scripts/aa856_global_profile_probe.py` drops `--account acc1`; `setup_run_health_alarms.py` docstring uses
  `aa365-admin`. New: `tests/unit/test_aa998_acc3_only.py` (defaults, refusals, PATCH 422, batch Literal),
  `tests/unit/test_aa998_no_acc1_runtime.py` (guard), `tests/integration/test_aa998_migration_295.py`.
- `docs/api/openapi.json` regenerated (FastAPI 0.161.1 / Pydantic 2.14.1, the pinned versions): the only change is
  `"const": "acc3"` on `S1BatchSubmitRequest.account`.
- `tests/integration/test_aa803_migration_259.py`: re-running 259 on the post-295 state hits 259's own guard (its
  rows no longer carry acc1), so the tests that re-run it undo first, and the teardown re-applies 295.
- An `account_route` other than acc3 left in the DB (only before 295) is ignored by `LLMClient._generate` with a
  `llm_account_route_ignored` warning, never called.

## Tradeoffs
- `account_key` labels every unknown stored account "retired" rather than matching the acc1 ID: the code may not
  carry that ID, and only acc1/acc2/acc3 were ever fetched. If acc2 cannot be resolved (STS down) the key stays
  None, as before.
- Kept `account_route` as a column (acc3 or NULL) instead of dropping it: dropping would touch TripPlanner's
  reader and the admin UI for no gain now.
