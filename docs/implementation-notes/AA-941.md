# AA-941 (CRM-13a) — CIS admin S-01: the partner CRM's AA L1 console

Card CRM-13a "AA admin L1 console" (root `docs/audits/2026-10-21-S246-crm-design-v3/design-v3.md`, A1 L1, T9, Q1 6.3,
Q2 3.12). This repo holds the CIS half: the page Platform › Tenants › **Agencies (CRM)** (`/admin/platform/agencies`)
and a thin relay to the CRM's `crm.ops.v1`. The CRM half (the L1 routes, the ops serializer allow-list, crm-011) is
AA-Partner branch `feat/aa-941-*`.

## Decisions

- **Relay, not a second implementation.** `api/routers/admin_crm_console.py` (prefix `/admin/platform/crm`, 19 routes)
  mirrors one `crm.ops.v1` route each and `api/services/crm_console.py` sends it with the signed-in staff member's own
  WORKFORCE access token. No new secret, no M2M client, no read of schema `crm`. The CRM decides who may write
  (crm-platform-admin) and what an L1 answer may contain; CIS does not re-filter keys (the CRM serializer and the root
  contract CI are the enforcement points).
- **Path allow-list before any call.** `crm_console.ALLOWED` lists the L1 routes (method + full-match regex, UUID
  ids). Anything else answers 404 `crm_path_not_allowed` without a network call, so the relay cannot be pointed at
  other CRM paths (the router builds the paths, and FastAPI already validates the UUID path params; the list is the
  second fence).
- **Pass-through bodies.** Request bodies are JSON objects without a CIS model (the CRM validates with
  `extra="forbid"`); its status code and `{detail, message, ...}` come back unchanged, so `has_travellers`,
  `owner_exists`, `missing_group` reach the page as they are. Relay errors: 401 `cognito_session_required` (legacy
  password session), 503 `crm_unavailable` (network / timeout), 502 `crm_bad_response` (not a JSON object).
- **Policy**: GETs `tenant.read`, writes `tenant.write` (admin role; the viewer is refused on every write by
  `READ_ONLY_ROLES`). The BFF already limits `platform/` to admins for reads and writes (lib/rbac.ts).
- **`GET /console` adds CIS's `environment`** to the CRM's `{can_write}`: the create dialog forces "synthetic"
  outside prod (the CRM answers 422 `synthetic_required` otherwise) and the frontend has no environment flag.
- **Ticket reference on every write** (WriteModal, pattern `^[A-Za-z][A-Za-z0-9]{0,15}-[0-9]{1,10}$`, the CRM's own
  pattern) — also sent on `complete` and `deactivate`, where the spec marks it optional. The insights opt-out sends
  it as `owner_request_ref` (Q2 3.12: the owner's written request).
- **No polling** (S240): everything loads when the page / drawer opens and on Refresh.
- **UI**: kit only (PageHeader, DataTable for the list and the member table, Drawer, Modal, Toast, Badge, Button,
  ErrorState, SkeletonBar). English only; strings are plain so they can move to an i18n file.

## Changed

- **Bug fix for AA-936 (#975)**: `StaffBearerMiddleware` drops the `Authorization` header after it verifies a Cognito
  token, so `request.headers.get("authorization")` in `GET /admin/platform/apps/crm/jobs` and `GET /admin/platform/cost`
  was always empty on a Cognito session and the CRM jobs card / CRM AI spend always said `cognito_session_required`.
  The middleware now keeps the verified token in `scope["state"]["staff_access_token"]` (never logged) and
  `platform_apps.relay_authorization(request)` reads it (falling back to the header); both AA-936 routes and the new
  relay use it. Covered by `test_verified_workforce_token_reaches_the_aa936_jobs_relay` (real middleware, real app).
- Timeouts: reads 2 s, **the agency list 5 s** (the spec said 2 s for all reads; the CRM opens one transaction per
  agency listed), writes 10 s (owner invite mails inside the CRM transaction).
- The members table has a per-row **Disable** action (the spec lists the deactivate route but not a button).
- `tests/e2e/smoke/ui-smoke.spec.ts` gains the page (viewer refused).

## Tradeoffs

- No CIS request models: one place validates (the CRM) and the page shows its 422s; the OpenAPI document shows the
  bodies as free objects (admin routes are outside the AA-899 typed-response rule).
- List/array answers (`data-requests`, `jobs`) are read tolerantly (`listOf`: `items`, a named key, or a bare array)
  because the CRM half is built in parallel; the TenantPage shape (`items`, `next_cursor`) is the spec's.
- "Has travellers" disables the first-owner button in the UI from the list flag; the CRM re-checks (409).

## Should know

- **Bodies are never logged.** The relay logs method, path pattern (UUIDs replaced), status and duration only
  (`crm_console_call`); Sentry drops request bodies (`shared/sentry_init.py`: `max_request_body_size="never"`,
  `before_send` pops `request.data`); the staff audit middleware stores no body. The owner's e-mail lives only in the
  WriteModal input and is cleared on close.
- Auth chain: browser → BFF `/api/admin/platform/crm/...` (requireAdmin, Cognito Bearer forwarded) → CIS API
  (StaffBearerMiddleware verifies, staff_policy) → CRM `/crm/ops/v1/...` with the same token (route class OPS:
  issuer + client, then the group).
- Depends on the CRM's L1 routes (AA-Partner, crm-011). Until they are deployed, the page's console call answers the
  CRM's 404 and the page shows that error; nothing else breaks.
- Regenerated: `tests/unit/snapshots/aa882_staff_route_policy.json`, `docs/api/openapi.json` (fastapi 0.161.1,
  pydantic 2.14.1 like CI).
- Tests: `tests/unit/test_aa941_crm_console.py` (relay, allow-list, pass-through, error mapping, no body in logs,
  timeouts, policy for every route, viewer/content refused, real-middleware token relay).
- UI verify (skill aa-ui-verify) on the Vercel preview with a crm-platform-admin Cognito account is still to do.
