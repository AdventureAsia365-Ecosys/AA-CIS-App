# AA-376 — repair_fn wiring (8 F-gate only)

`run_piece_through_produce_gates()` (pipeline.py) hardcoded `max_repairs=0` since AA-364 —
`_repair_not_available()` existed only to fail loudly if that ever changed by accident. AA-367's
live verify (6 attempts, 5 fully run, to get 1 real passed piece) quantified the real cost of no
repair path. This issue wires a real `repair_fn`.

## STEP 0 findings (summarized — full raw dump in chat)

- `repair_fn` already existed as an unused parameter shape (`run_gates()`'s signature,
  `Callable[[str, list[str]], str]`) — never a real implementation.
- Real prior art already in-repo: the ported prototype (`docs/AI-gent-for automation works/
  aa-marketing-v2/aamc/generation.py::repair()`, its own "E5") — one LLM call, "fix ONLY listed
  violations, preserve structure/voice/length", full-body rewrite, no per-gate split.
- `REPAIR_TOTAL_MAX = 3` already decided (ADR-2026-029, `models.py:28`) — not a fresh number to
  pick.
- Real live-verify gate-failure data (AA-367 + AA-375): F3 (blog structural variance) fails most
  often historically; AA-375's newer live run also found F1 (grounding) and F9 (brand/SEO,
  facebook) failing — facebook held on F9 ONLY in that run, passing all 8 other gates (highest
  ROI case for repair).
- F6 (`route_to_sellable`) mixes 2 non-content-fixable sub-violations ("no cta_target" —
  `Brief.cta_target` missing; "url_alive not True" — no confirming `acp_deliver.tenant_tour_pages`
  row) with 1 content-fixable one ("CTA {target} not present in body" — literal-string insertion).
  Calling repair on the first two would always waste a round + a Sonnet call — decided (with
  Nghiep) to filter these out before ever calling `repair_fn`.
- Separately confirmed (own thread, not re-litigated here): the "F5 gap" in `gates.py`'s numbering
  is not a botched renumbering — `packets.py::ALLOWED_PUBLISH_MODES_UNTIL_F6` locked "F6" to
  route-to-sellable a day before AA-372 wrote the actual gate functions, so F6/F7 kept their
  prototype numbers while F2-F4 shifted down. Unrelated to this issue's scope, not touched here.

## Decisions

- **One shared `repair_fn`, not per-gate.** Matches the prototype's own E5 exactly — a single
  Sonnet call given `(body_tagged, violations)`, asked to fix only the listed violations. No
  gate-specific repair logic anywhere.
- **New module `services/acp_produce/repair.py` (E5)**, not folded into `generation.py`. Follows
  the established one-file-per-E-step convention (`generation.py`=E1/E2, `adapt.py`=E3,
  `faq.py`=E4) rather than `generation.py`'s own narrower "N7 E1 (Outline) + E2 (Draft)" scope.
- **F6 filter implemented as an `is_repairable` predicate parameter on `run_gates()`** (default
  `lambda result: True`, fully backward-compatible), not hardcoded gate-name logic inside
  `run_gates()` itself. Matches the existing separation of concerns where gate-specific routing
  (F8's rubric, F9's blog/social split) lives in `pipeline.py`'s closures, not in `gates.py`'s
  generic orchestrator. `pipeline.py::_is_f6_content_fixable()` inspects individual violation
  strings (not just `result.gate`), since a real F6 failure can carry the repairable
  "CTA not present" violation alongside a non-repairable one in the same round.
- **`run_gates()` now catches any exception from `repair_fn` and holds immediately** (not just the
  F6 filter case) — not explicitly requested, but a direct consequence of wiring a real Sonnet
  call into a path that previously could never fail (repair was never reached). Without this, a
  real `RepairFailed` (Sonnet exhausted retries) would propagate uncaught through
  `run_piece_through_produce_gates()` and crash the calling `slot_runner.py`'s entire
  `run_slot_production()` — losing all pieces for that slot, not just the one that failed repair.
  Mirrors the prototype's own `except llm.LLMError: return _hold(...)` around its `repair()` call.
  `piece.repair_count` is only incremented on a `repair_fn` call that actually returns, matching
  the prototype's own counter placement.
- **`output_rules` gap is out of scope** (AA-381) — `pipeline.py:164-170`'s pre-`run_gates()`
  short-circuit is untouched. A piece failing `output_rules` still holds with zero repair
  opportunity, unchanged from before this issue.

## Changed

- New `services/acp_produce/repair.py`: `repair_piece(body_tagged, violations) -> str`,
  `RepairFailed` exception. Real Bedrock satellite Sonnet call (`invoke_claude(..., model=
  "sonnet")`), same retry/backoff policy as E2/E3 (3 attempts, 2s/4s backoff), `max_tokens=4096`
  (project-wide ceiling, not E2's dynamic per-batch sizing — repair returns the FULL body, not a
  batch).
- `services/acp_produce/gates.py::run_gates()`: added `is_repairable` parameter (default
  always-True), wrapped the `repair_fn` call in `try/except Exception` → hold on failure without
  incrementing `repair_count`. Added `structlog` logger for the new `gate_repair_fn_failed`
  warning log.
- `services/acp_produce/pipeline.py`: removed `_repair_not_available()`; added
  `_is_f6_content_fixable()` predicate + `_F6_NON_CONTENT_FIXABLE_MARKERS`; wired
  `repair_fn=repair_piece`, `max_repairs=REPAIR_TOTAL_MAX` (imported from `models.py`, not
  re-hardcoded), `is_repairable=_is_f6_content_fixable` into the real `run_gates()` call. Updated
  the "No repair loop" module-docstring paragraph and `run_piece_through_produce_gates()`'s own
  docstring to describe the real wiring; left the AA-364-dated historical scope-boundary
  paragraph (lines 6-13, "C3 and E1-E5 do not exist yet") untouched as a dated historical record,
  consistent with how the rest of this repo preserves dated scope notes.
- New `tests/unit/test_aa376_repair.py` (5 tests): `repair_piece()` happy path, prompt carries
  every violation, retry-then-succeed, `RepairFailed` after max retries, response whitespace
  stripped. No live Bedrock calls (`invoke_claude` mocked throughout, same convention as
  `test_aa370_generation.py`).
- `tests/unit/test_aa298_gates.py`: 3 new `run_gates()` tests — `is_repairable=False` holds
  without calling `repair_fn`; a predicate that only vetoes one gate still allows normal repair
  for others; a raising `repair_fn` holds without incrementing `repair_count`.
- `tests/unit/test_aa364_pipeline.py`: fixed 2 pre-existing tests
  (`test_piece_failing_f1_grounding_holds_with_grounding_reason`,
  `test_brand_seo_audit_persisted_in_its_own_column_when_f9_flags`) that started making real
  (failing) Bedrock/STS network calls once `max_repairs` went from 0 to 3 — each was silently
  burning ~6s in real retry/backoff before this fix (see Tradeoffs). Added 4 new tests: F9-only
  facebook piece reaches `passed` after exactly 1 repair round (closest unit-level proxy to the
  real AA-375 finding); F6 "no cta_target" and "url_alive not True" both hold immediately with
  `repair_piece` never called; a `repair_fn` that never actually fixes the violation holds after
  exactly `REPAIR_TOTAL_MAX` rounds.

## Tradeoffs

- **Found and fixed a real test-suite risk, not just a wiring gap.** Before the fix, 2 tests in
  `test_aa364_pipeline.py` passed but each took ~6s (18.05s total suite runtime vs. 5.06s
  baseline) because `max_repairs=0 → REPAIR_TOTAL_MAX` made them attempt a REAL `repair_piece()`
  call with no mock — `invoke_claude()` wraps every underlying failure (including STS AssumeRole
  with no real credentials) into `BedrockUnavailable`, so `repair_piece()` correctly retried 3x
  with real `time.sleep()` backoff before `run_gates()`'s new exception safety net caught the
  eventual failure and held. The tests happened to still pass (repair_count stayed 0, matching
  the old assertion) — but only by accident of the safety net, and only slowly. In an environment
  with real AWS credentials reachable from the test runner, this could have made a real Sonnet
  call from a unit test instead of failing at the AssumeRole step. Fixed by mocking
  `services.acp_produce.pipeline.repair_piece` explicitly in both.
- **Broad `except Exception` in `run_gates()`**, not a narrow `except RepairFailed` importing from
  `repair.py`. Chosen to keep `gates.py` decoupled from any specific `repair_fn` implementation's
  exception type (the function stays a generic `Callable[[str, list[str]], str]` contract) —
  logged via `structlog` so the catch is visible, not silent.
- **`_MAX_TOKENS = 4096` (repair.py) is a fixed ceiling**, not E2's dynamic per-batch sizing —
  repair returns the full piece body in one call, so it needs at least as many tokens as the
  original body; 4096 matches the project-wide "max_tokens = 4096, NOT 2000" rule already in
  place elsewhere in this repo.

## Should know

- `RepairFailed`/`AdaptChannelFailed`/`DraftGenerationFailed`/`FAQAnswerFailed` now form a
  consistent per-E-step exception family — each caught by its own immediate caller, never left to
  propagate raw into `slot_runner.py`.

## Live verify — real Bedrock/Nova Pro/Postgres, zero mocking of the AA-376 code paths

`tests/verify_scripts/aa376_repair_verify.py`, run via S3-mediated ECS exec (`aa-cis-dev-cluster`/
`aa-cis-dev-api`, 07/08/2026 — ECS/RDS were already running from an earlier session in the same
day, not started fresh for this). Calls `run_piece_through_produce_gates()` directly (not the full
`slot_runner.py` chain) with hand-constructed `Piece`s + synthetic `valid_ids`/`text_by_id` — same
"test constructs the input, production code does the work" convention `test_aa364_pipeline.py`
already established for this exact function; repair operates on an already-drafted `body_tagged`,
so C1-E4 generation is out of scope for this issue and would only add cost/non-determinism.

**Harness note**: `aws ecs execute-command --interactive` sessions in this environment do not
reliably survive a multi-call, tens-of-seconds script (matches a known prior finding — ECS exec +
long synchronous work needs a double-fork daemonize + poll-a-log-file pattern, not a blocking
interactive session). Worked around by daemonizing the verify script (Python double-fork,
redirect stdout/stderr to `/tmp/aa376_out.log`), polling for a completion marker via short
`execute-command` calls, then having the container `boto3.upload_file()` its own log to S3 for a
clean download — plain `tail`/`cat` on a large file also truncated mid-stream through the
interactive session.

**Scenario B (F6 filter) — 4/4 real runs, 100% consistent**: a blog piece with no
`tenant_tour_pages` row (`url_alive=None`) held immediately every time — `repair_piece` wrapped to
raise `AssertionError` if ever called; it never was. `repair_count` stayed 0, total time ~2.4-2.8s
(just the mandatory F8+F9 Nova Pro calls the "run every gate every round" design already makes
regardless of `is_repairable` — unrelated to this issue, not changed here). Confirms the filter
works exactly as designed against real infra, zero wasted Sonnet calls.

**Scenario C (max_repairs=3 exhaustion) — 4/4 real runs, 100% consistent**: an F1 grounding
violation (fabricated atom id) with `repair_piece` stubbed to return the body unchanged (see
script docstring for why this one sub-scenario controls the repair OUTPUT — proving the loop
mechanism live, not gambling on an LLM permanently failing 3x) held after exactly 3 rounds every
time, `repair_count=3`, no infinite loop, ~9-12s total (6 real Nova Pro calls, 2/round).

**Scenario A (repair on a real LLM-judged failure) — 4 real attempts, did NOT reproduce AA-375's
exact "facebook, F9-only" case, but produced richer real evidence than planned:**
- Attempts 1-3 (facebook, `hook_story_cta` framework): all 3 real, differently-worded hand-crafted
  bodies failed BOTH F8 ("ends with CTA" criterion) AND F9 on round 1 — never F9-alone. `repair_fn`
  targeted F8's violation each time (first in gate order) with a real Sonnet call every round, but
  the real Nova Pro judge kept scoring "ends with CTA" as unmet across all 3 rounds in every
  attempt, including one attempt with no trailing `HASHTAGS:` line (ruling out "hashtags is the
  literal last line" as the cause) and one where Sonnet's round-2 rewrite was substantial (not
  just appending a CTA). Held after 3 rounds every time. This reproduces and reinforces AA-367.md's
  own already-documented finding ("facebook: 5/6 held ... F8 ('ends with CTA')") — not a new bug,
  and not something a differently-phrased hand-written CTA line could clear in these attempts.
- Attempt 4 (switched to blog, `hub` framework — no CTA-ending requirement in that rubric):
  F8 passed cleanly. Round 1 first_failure was F9 (7 real flagged codes: SUMMARY_OFF_BRAND,
  HIGHLIGHTS_TOO_GENERIC, SEO_TITLE_WEAK, META_INCOMPLETE_SENTENCE, GENERIC_AI_WORDING) — `repair_fn`
  called with F9's violations, real Sonnet rewrite. Round 2's re-check found F9 *still* flagged
  (now 9 codes — repair's rewrite fixed some brand-voice issues but genuinely introduced new SEO/
  structure ones: PRODUCT_TRUTH_RISK, ITINERARY_STRUCTURE_WEAK, DFS_INTENT_UNDERUSED,
  KEYWORD_STUFFING_RISK) — `repair_fn` called again with the new violation set. Round 3's re-check
  caught a genuine regression from round 2's rewrite: F6 now failed ("CTA ... not present in
  body" — round 2's rewrite had dropped the literal CTA string) — **this is `run_gates()`'s own
  P0-3 full-restack fix catching a real repair-introduced regression on live infra**, not a
  synthetic unit-test scenario. Round 3's repair re-inserted the CTA (F6 passed on the final
  check) but F9's content-quality flags were never fully resolved within the 3-round budget — held
  on F9 after exactly 3 rounds.

**What this proves, honestly**: the wiring is real and functional end-to-end (real Sonnet calls
every round, real Nova Pro re-judge every round, real DB persistence, `_is_f6_content_fixable`
filter and `REPAIR_TOTAL_MAX` termination both 100% correct across 4/4 runs each) — including an
unplanned but valuable live demonstration of the P0-3 regression-catching mechanism actually
catching a real repair-induced regression. DET gates (F1-F7) passed cleanly on round 1 in *every*
one of the 4 attempts — repair was never needed for these, consistent with STEP 0's
deterministic-vs-LLM-judged classification. What it does NOT prove is the specific "single LLM-
judged gate fails, one repair round, clean pass" happy path from AA-375's own facebook finding —
4 real attempts instead reproduced AA-367's known F8 gap and surfaced a new, real finding: **a
single generic "fix ONLY these violations" repair call struggles with F9's multi-dimensional
brand/SEO rubric** (5-10 simultaneous flagged codes spanning brand voice, SEO, and structure) —
fixing some flagged dimensions can genuinely introduce regressions in others, since `repair_piece()`'s
prompt gives it the violation list but not the full rubric or worked examples. Worth a real
follow-up ticket (not fixed here, out of AA-376's own "wiring" scope): repair's prompt for
LLM-judged gates (F8/F9) may need more structure than DET gates' repair, which had no observed
issues in any attempt.

**Cost/round data (real, all 4 runs)**: every attempt's DET gates (F1-F7) passed on round 1
without ever invoking repair — repair rounds were spent exclusively on LLM-judged gates (F8/F9).
Real Sonnet repair-call latency: 1.6-3.4s/call (~1150-1330 input tokens, ~45-149 output tokens per
call — small relative to E2's full-draft ~1800/880 tokens, confirming repair calls are cheaper
than full regeneration per-call even when they don't succeed). Total per-scenario wall time:
Scenario A 15.8-19.0s (3 rounds, 2 Nova + up to 1 Sonnet call/round), Scenario B 2.4-2.8s (1 round,
no Sonnet), Scenario C 9.1-11.9s (3 rounds, 2 Nova/round, no real Sonnet — stubbed). Compare
against AA-367's baseline: 6 full slot-production attempts (5 fully run), each a fresh
C1-C3+E1-E4 regeneration (research + outline + draft + adapt + FAQ, ~$0.05+/attempt by AA-370/371's
own real cost figures) — AA-376's repair rounds reuse the existing draft and only pay for a
~1-3s targeted Sonnet call (+ the already-mandatory F8/F9 re-judge), several times cheaper per
round than AA-367's discard-and-regenerate-everything approach, even in the runs here that still
ended `held` rather than `passed`.
