# AA-1178 — Monitoring jobs never wait behind a long background job

Session S292, lane i-monitor-lane. Two CIS PRs (MIG-4): the migration-only PR (CIS 489: two `shared.setting_definition`
rows, `compiled_defaults.json`, `shared/jobs/lanes.py`, its integration test) and this code PR (branch from
`origin/main`, without the migration; chain: cis/489 applied before it). `shared/jobs/lanes.py` is byte-identical in
both PRs (the settings-lint reader check needs a module naming the keys in the migration PR; the code PR needs it to
run on its own), so the merge of main into this branch adds nothing for it.

## Decisions

- **The monitoring lane has slots of its own, on top of `max_parallel`.** The issue asked for "their own small cap so
  they cannot take a wave's slots". Sharing the main slots under a separate group cap would still let two monitors take
  main slots before a wave arrives (s1_rewrite 5 instead of 6, atomize waiting for a monitor to end), and the business
  owner session constraint was that wave and content claiming must not change. With their own slots the main slots,
  the reserve and the background group cap work exactly as before for every non-monitor kind, and the monitors also
  keep running while a wave fills the main slots (before, they waited for the whole wave).
- **`monitor=True` requires `background=True` and not `deploy_blocking`** (`job_kind` raises). Every existing check
  that reads `k.background` (Jobs page, tests, the deploy gate exemptions) keeps its meaning; `background_kinds()` still
  includes the monitors, `monitor_kinds()` is the subset.
- **Tagged kinds**: every background kind that is `deploy_gate_exempt` today, i.e. the periodic $0 watchers:
  `ops_status_sample` (60 s), `llm_route_watch` (60 s), `quality_funnel_watch` (60 s), `compliance_db_checks` (120 s),
  `llm_model_lifecycle_sync` (120 s), `ai_usage_rollup` (1,200 s expected; the issue names it), `llm_connection_probe`
  (600 s; the connection circuit health probe, a few tiny calls). Not tagged: report, retention, writing-memory,
  place pipeline, erasure, supply, Cost Explorer (a paid read) kinds.
- **Both caps are settings** (tech lead S279): `cis.ops.jobs_background_max_running` (int 1–4, default 1, the AA-712
  value) and `cis.ops.jobs_monitor_max_running` (int 1–4, default 2), area `ops`, maker-checker, EN + VI guides.
  The `BACKGROUND_MAX_RUNNING = 1` constant is gone (removed from the settings-lint baseline).
- **Reading the caps never stops the claim loop**: `lanes._read` returns the seeded default when the reader raises
  (a key not compiled yet, a broken definition) and warns once (`job_lane_cap_unreadable`). The reader itself already
  serves the compiled default when the DB cannot be read.
- **Pool and executor are sized for the setting's upper bound** (`lanes.monitor_slots_bound()`, the definition's
  `max_value`, 4): both grow lazily, so an unused slot costs nothing and raising the cap needs no restart (lesson
  "raise slots, raise the thread executor and DB pool too", AA-737).
- **No readiness raise**: the reader serves the compiled defaults while the CIS 489 rows are missing.

## Changed

- `shared/jobs/registry.py`: `JobKind.monitor`, `job_kind(monitor=...)` with the guard.
- `shared/jobs/worker.py`: `monitor_kinds()`, `claim_caps_for(..., running_monitor=, monitor=, background_max=,
  monitor_max=)` (main slots: old rule over non-monitor kinds, nothing when no main slot is free; monitor lane: the
  monitor kinds while fewer than the cap run), `Worker.running_monitor()`, `Worker.free_main_slots()`, `_fill_slots`
  loops until the caps of both lanes are empty or claim returns nothing; `_main` sizes executor and pool for
  `max_parallel + monitor_slots_bound()` and logs `monitor_slots`.
- `shared/jobs/backlog.py`: the sampler counts main and monitor running rows per worker and calls the same
  `claim_caps_for` with the caps read once per sample.
- Seven job modules: `monitor=True`.
- `GET /admin/job-runner/summary`: each kind carries `lane` (`main` | `background` | `monitor`). The response is an
  untyped dict, so `openapi.json` does not change.
- Tests: `tests/unit/test_aa1178_monitor_lane.py` (the Done-when cases, the S292 queue, the wave shape, the settings,
  the fallback, `_fill_slots`, sampler = worker); `test_aa737`, `test_aa712`, `test_aa751` now say "long background"
  where they meant it.

## Tradeoffs

- Up to `cis.ops.jobs_monitor_max_running` more jobs run at once on a worker than `max_parallel` (8 + 2 on Dev). The
  monitors are DB reads and control-plane calls; the 0.5 vCPU worker has headroom for two of them. A wave is not slowed
  by them through slots; it shares CPU with them for a minute every 5 minutes, as it did before for the background one.
- A slow monitor (an `ai_usage_rollup` backfill, a probe run) plus a second one fill the lane, so the 5-minute status
  sample can wait for one of them. Raising the setting is the lever; splitting the lane per kind was not worth it.
- The `max_parallel` written to `shared.job_worker` stays the main slots; the Jobs page shows the extra lane through
  the running rows only.
