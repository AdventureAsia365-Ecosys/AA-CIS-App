## Decisions

- ~~Do not widen `ALLOWED_PUBLISH_MODES_UNTIL_F6`~~ — **superseded same-day**, see "Follow-up
  decision" above. Original reasoning kept for the record: even though F6 was technically
  wired into `run_gates()`, the STEP 0 session alone had only confirmed the Trang-scoping
  question, not this guard — so the first round left `confirm_to_publish`/`veto_window_auto`
  blocked with `PublishModeBlockedError`, exactly as AA-364/AA-367 had left them, until Nghiep
  gave the explicit call recorded above. `suggest_ramp_transition()` still only computes what
  the ramp *would* suggest (pure function, no DB, no side effect) — confirming remains a
  separate call, matching the prototype's "agency-confirmed, never silently switched" framing;
  what changed is that confirming can now actually succeed.
- **BOFU hard-block checked before, and independently of, the F6 guard** — so it still holds
  even after the F6 guard's widening above. Implemented as a real DB join
  (`packet_has_bofu_piece()`), not a comment/convention. This is the one constraint the
  follow-up decision explicitly did NOT touch — verified by a dedicated post-unlock test.
- **Decision log reuses `acp_shared.audit_log`** (migration 030) rather than inventing a new
  table — same table every other real ACP gate/approval action in this repo already writes to.
  `action='publish_mode_transition'`, `resource_type='packet'`, `details` jsonb carries
  `from`/`to`/`blocked`/`block_reason`. Every `confirm_ramp_transition()` call writes exactly
  one entry, whether it succeeds or is blocked — a blocked escalation attempt must stay visible
  in the log, never silently dropped.
- **No new UI for Trang's veto action.** Per the issue's own instruction: the admin surface
  cannot scope an action to a specific reviewer identity in any way that's actually wired end
  to end today (see STEP 0 admin_users finding) — building UI on top of that would be cosmetic.
  Reported as a real product-decision gap instead (see AFTER DONE).
- **No new migration.** `packets.publish_mode` (094) is the ramp state; `acp_shared.audit_log`
  (030) is the Decision log; the BOFU join uses existing columns (`pieces.slot_id`,
  `acp_v2_slots.payload`, both already live). Nothing to add at the schema level.

  reviewers should not expect a new column in the diff.
- `confirm_ramp_transition()` is the only new call site for `packets.set_publish_mode()`

  return `False` for it (no match, not a false positive) — but also can't be proven BOFU either
  way. Fine for current dev state (096 re-pointed the only live FK), flagged in case older data
  ever resurfaces.
