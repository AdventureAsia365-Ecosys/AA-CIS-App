# AA-860 — X1 S16 (CIS 244: cis_app runtime grants, default privileges, parity policies)

Branch `feat/x1-s16-migration-244`, migration-only PR (plus its tests and the conftest support). Plan: root
`docs/audits/2026-10-17-S241-x1/x1-plan.md` S16, the S242 amendments block and the S243 amendments block (same
session). Accepts critic finding 7 (FORCE-RLS parity policies in 244).

## Decisions
- **Parity policies on all 16 RLS tables, not only the 8 ENABLE-only ones (S243 correction).** The plan said
  FORCE RLS filters the master, so a non-owner `cis_app` would need no policy on the FORCE tables. The live
  AA-817 probe v2 (`docs/audits/2026-10-16-S239-in-progress-audit/aa817-done-evidence/probe_v2_after_239.json`)
  shows `foreign_guc == total` for `aa_cis_admin` on every FORCE table (it is in `rds_superuser`), and ~69 CIS
  files read them without a GUC. Without the policies `cis_app` would read 0 rows and be refused writes on
  raw_tours / published_tours / generated_content / … after S18. `USING (true) WITH CHECK (true)` reproduces
  today's runtime behaviour exactly; tenant isolation stays on the tenant pool (`aa_app_user`).
- **The master's counts are measured before the policies exist (3b).** The master is a member of `cis_app`
  (rl-001) and a policy `TO cis_app` applies to members, so after `CREATE POLICY` the master always matches it;
  a parity check measured afterwards would be a tautology. 3b counts each FORCE table and `tenant_tour_versions`
  without a GUC and under a forged foreign GUC, keeps the numbers in transaction-local settings `x1_244.*`, and
  the last block compares `cis_app`'s counts with them. Test `test_guard_parity_refuses_a_filtered_master`
  proves the guard fires when the master *is* filtered (the plan's original premise).
- **Trigger functions get no EXECUTE.** `GRANT EXECUTE ON ALL FUNCTIONS` is followed by a loop that revokes it
  on every trigger function in the 11 schemas (243's key guard, `shared.job_set_updated_at`, AA-884 248's audit
  triggers when 248 lands first). Matches owners.yaml ("functions other than trigger functions") and SEC-4.
  Default privileges still grant EXECUTE on future functions (owners.yaml `default_acl`); harmless for
  trigger functions, which cannot be called directly.
- **Guards are exact.** The RLS table set of the 11 schemas must be exactly the 8 + 8 names; each must carry the
  `<t>_cis_app_all` shape; `cis_app` must be a member of nothing with no special attribute; grants on every
  existing relation / sequence / non-trigger function; registry read-only; the 33 default-ACL rows; behaviour as
  `cis_app` (parity, `shared.job` UPDATE, registry INSERT/DELETE refused, `booking.customers` /
  `tripplanner.sessions` refused). The cross-app tables are found through `pg_class`, not `to_regclass()`:
  name resolution needs USAGE on the other schema, which the CI stand-in master lacked (and would hide the
  check on a master without it).
- `ALTER DEFAULT PRIVILEGES FOR ROLE aa_cis_admin` names the master explicitly (owners.yaml and the probe key
  on it). CI gets a NOLOGIN role of that name (conftest) so the statement resolves.

## Changed (vs the plan text)
- Plan S16 item 3 ("no policy on FORCE tables") and the guard "published_tours without GUC = 0" are inverted
  (see Decisions). The S243 amendments block in x1-plan.md records it.
- **The conftest replay skips 244** (like 001/002/007b/008). Reason: its policies `TO cis_app` make the
  exact-policy guards of 229 / 237 / 239 / 241 refuse, and their tests re-apply those files (130 errors when
  244 was replayed). On Dev those files never re-run, and 244 is applied after 247–249 anyway, so the X1
  tests apply 244 themselves in the Dev order and remove it at teardown (`conftest.x1_244_undo`).
- The CI DB is not Dev-shaped where 244 looks: 008 is skipped (no FORCE on content_exports /
  webhook_deliveries), `tenant_tour_versions` and `acp_output_rules` do not exist, the four empty CIS schemas
  are missing, six legacy tables dropped on Dev keep RLS. `conftest.x1_244_ci_shape` fixes that around the
  X1 tests (permanent: the empty schemas, FORCE per 008; temporary: RLS off on the explicit legacy list,
  two stand-ins), `x1_244_ci_unshape` restores. The legacy list is explicit so a future RLS table is never
  silently switched off.
- Plan S15's "standing ENABLE-only check" lives in `test_x1_cis_app_privileges.py` and covers FORCE tables too.

## Tradeoffs
- `test_x1_cis_app_privileges` runs 244 up to its registration (grants, default privileges, policies), not its
  guards: the exact RLS-set guard is a one-time apply check (tested in `test_aa860_migration_244`) and would
  refuse any later, correctly-policied RLS table in this standing test.
- 244 does not revoke UPDATE / DELETE on `acp_shared.audit_log` from `cis_app` (AA-884 248's comment invites
  it as defence in depth). Kept out to stay in scope; 248's triggers refuse both anyway. Candidate for 245.
- No GUC-aware policy: AA-860 Done-when (1) as worded ("forged foreign GUC on the main pool → 0 rows") is not
  met by design; it needs Nghiệp's amendment (lane plan blockers).

## Should know
- **Dev order:** 244 is applied on Dev after 247 (identity), 248 (AA-884) and 249 (AA-878). `GRANT … ON ALL`
  covers every object that exists at apply time (incl. `shared.staff_app_grant` and 248's
  `shared.cost_explorer_app_snapshot`, which 248's guard allows for `cis_app`), the trigger-function revoke
  covers 248's audit functions, and the default privileges cover what the master creates later. Tested in
  `test_aa860_migration_244`: objects created before 244 (table + identity sequence, standalone sequence,
  function, trigger function), objects the master creates after it (default privileges), and an object a
  superuser creates after it (no grant: why the CI replay order differs).
- **Any later migration that adds an RLS table in the 11 schemas** must add a permissive policy `TO cis_app`
  in the same file (CI standing check), and a later migration that asserts an exact policy set on these 16
  tables must allow `<t>_cis_app_all` (229/237/239/241 style guards).
- The master stays a member of `cis_app`, so it also matches these policies (no change: it reads these tables
  unfiltered already). From S20 `db_migrator` is a member of `cis_app` too, but DB Migrate runs CIS files as
  `cis_owner` (not a member): 245 must give `cis_owner` its own policies or `NO FORCE` on the FORCE tables
  (owner-rights views v_active_tour_atoms, v_trip_registry, v_tour_photos, v_destination_photos).
- The 7 views in the 11 schemas read CIS tables only (checked in the schema reference), so SELECT on them does
  not open a path to booking / tripplanner.
- Locks: `CREATE POLICY` on published_tours / raw_tours / … takes ACCESS EXCLUSIVE for milliseconds; apply with
  the job tables idle (DB Migrate's idle check), lock_timeout 5s.
- Checks run locally (PG 16, scram auth, scratch cluster): full integration suite 611 passed / 1 skipped
  (baseline main 573); Infra `run_migration.py --inspect` on a `db/migrations/cis/` copy → no errors; mutation
  checks: without the raw_tours parity policy every X1 test fails (guard + standing check); a later migration
  adding an RLS table without the policy fails the standing check, with it passes.
