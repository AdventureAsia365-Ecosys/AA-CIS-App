# AA-1045 — AI gateway usage analytics explorer

Lane `aa1045-explorer`, session S268 (Claude Code). Branch `feat/aa1045-usage-explorer`.

## Decisions

- **Rollup table, not a materialised view.** `shared.ai_usage_hourly` (CIS 372, contract) is rebuilt per hour range by a
  job kind on `shared.job` (`ai_usage_rollup`, ADR 0003a template): DELETE the range, INSERT ... SELECT from the four
  CIS ledgers, one transaction per 24 hours. Idempotent per hour; a REFRESH of a materialised view would rewrite all
  history every time and could not keep hours past the raw retention window.
- **Schedule.** The api's ops sampler queues a run every quarter hour (idempotency key per quarter hour) that re-rolls
  the last 6 UTC hours (the current one included), so late rows are counted; and once a backfill of the raw window
  (key `ai_usage_rollup:backfill:v1`). Nothing is queued before 372 is applied (`to_regclass`), and
  `AI_USAGE_ROLLUP=off` stops both. The kind is background, concurrency 1 and deploy-gate exempt (always queued).
- **Never re-roll past the raw window** (175 days, `usage_rollup.RAW_WINDOW`): once the retention job deletes raw
  rows, a re-roll would replace an hour's history by nothing. Every mode clamps to it.
- **Sources.** llm (`shared.llm_call_log` without Jev's `typesafe` rows, as the Calls tab), jev (`decision_log`), dfs
  (`dfs_call_log`), geocoder (`geo.geocode_call`; one row is a batch, `requests` sums its requests). The CRM ledger
  (`crm.llm_call`) is not readable from CIS: the explorer merges the CRM's daily totals (crm.ops.v1 GET /llm/usage,
  with the staff member's own token, chunked by 92 days) at read time when the granularity is a day or longer and no
  filter needs a value the CRM does not send. TripPlanner writes into `shared.llm_call_log` (app `tripplanner`), so
  it is in the llm source. Booking has no LLM ledger of its own.
- **One dimension definition per ledger** (`api/services/usage_dims.py`), used by the rollup builder, the raw per-unit
  query and the Calls tab's new drill-down filters, so a cell and its Calls list count the same rows (integration
  test `test_explore_groups_filters_series_crm_and_drill_down`).
  - provider = the spend-budget provider (`bedrock*` -> bedrock), the same values as the Calls provider filter;
  - account = `coalesce(connection_key, account)` (llm), `typesafe`, `dataforseo`, the geocoder's provider;
  - model = the model (llm, Jev) or the endpoint (DataForSEO, geocoder);
  - family = the catalog family of the model (`model_key` first, then `wire_model`), joined at read time;
  - product = `llm_route_chains.product_of(stage)` as a SQL CASE (crm for `crm_*`, other otherwise), at read time;
  - traffic = experiment | shadow | live.
- **Fallback rule.** `shared/llm_client/route_watch.py` (AA-1042) is not on main yet, so the rule is written in
  `usage_dims.FALLBACK_SQL` as the same rung rule: an answered row with `fallback_used`, `attempt_no > 1` or a route
  position > 0. Fallback rate = fallback answers / answered LLM requests.
- **p95 latency** from a fixed 20-bucket histogram per rollup row (`LATENCY_BOUNDS_MS`), linear inside the bucket:
  approximate, documented on the page as p95.
- **Cost per tour / per piece** needs distinct counts, which do not add up across hours, so it is read from the raw
  LLM ledger on request (`per_unit=1`), only inside the raw window.
- **Times.** ICT presets and buckets (`date_trunc(..., 'Asia/Ho_Chi_Minh')`; ICT is UTC+7 whole hours, so every ICT
  bucket is whole rollup hours); answers carry ISO strings with their offset; the data stays UTC. The invoice card uses
  UTC months (provider invoices are UTC).
- **Edge buckets are clipped** (fix pass): a day / week / month bucket the range cuts (the first and last day of 7d,
  24h or 30d, any range at week or month) answers `start` / `end` clipped to the range, `partial: true` and a label of
  the clipped span (`2026-10-28 15:00–2026-10-29`), in `rows[].bucket` and `series[]` (`usage_explorer.bucket_span`).
  The page's drill-down clips again (`drillHref`), so the Calls list holds the rows the cell counted.
- **Access.** New prefix `/admin/usage-explorer/*`, spend.read (admin, finance, ai_ops; never customer_success,
  support or tenants). Saved views are the caller's own (`staff_id_of`: the verified Cognito staff id), their writes
  need spend.read like the bell's own state; the viewer role is refused on writes anyway. A re-roll
  (`POST .../rollup/run`) is ops.write (admin), audited `usage_rollup.run_requested`.
- **Frontend.** Its own page `/admin/usage` (AI & spend › Usage explorer), so the AI gateway page the AA-1042 lanes
  change is touched only in the Calls tab (a drill-down line) and `lib/aiGateway.ts` (eight new Calls filter keys).
  Multi-select filters are kit ChipButtons in a kit Drawer (no multi-select in the kit); the table sorts on the server
  (`manualSorting`, sort/dir in the address).

## Changed

- Calls API (`GET /admin/ai-gateway/calls`) gains `since` / `until` (a custom half-open range replacing the window, at
  most 400 days) and `tenant`, `model`, `account`, `role`, `error_class`, `product` (each `(none)` = no value). A
  filter a ledger cannot answer leaves it out, as before.
- Invoice view: there is no table of provider invoices anywhere, so the card shows the ledger month total and the
  provider's own figure where the nightly reconciliation stored one (`shared.llm_cost_reconcile.provider_usd`); the
  invoice column is empty and the card says what is missing (an invoice store, AA-1026 reconciliation).

## Tradeoffs

- Grouping by a dimension the CRM does not send (provider, tenant, …) still merges the CRM rows with an empty value
  there, so the totals stay whole; filtering on such a dimension leaves the CRM out (it could not be narrowed).
- At most 2000 groups are returned after sorting (`truncated` says so); the CSV is built in the browser from them.
- The quarter-hourly run costs one small aggregate over 6 hours of ledger rows; the backfill reads 175 days once, one
  day per transaction.
