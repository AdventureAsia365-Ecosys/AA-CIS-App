# AA-1061: the RLS allowlist entry of the Booking inquiry inbox view leaves with bk-076 (S294)

Booking bk-076 (`migrations/076_aa1037_retire_b2c.sql`, destructive) drops `booking.v_ops_inquiry_inbox` (bk-035) and
with it the `cis_app` SELECT grant on it. The X2 RLS catalogue allowlist still names that grant
(`booking.v_ops_inquiry_inbox:cis_app`, rule g). Once the view is gone the entry matches nothing on Dev, and the
nightly stale check of AA-CIS-Infra (Migration Copy Guard, step "RLS allowlist has no stale entry", AA-1112) fails on
it. This PR removes the entry from both byte copies here; the Infra copy `db/rls_catalogue_rules.py` follows.

## Decisions

- **Removed, with a one-line history comment** in the place of the entry, like the AA-1046 note on the TripPlanner
  grants that tp-027 revoked: a grant back on a view of that name is a violation again.
- **Both copies in one commit** (`tests/integration/rls_catalogue_rules.py`, canonical, and
  `shared/compliance/rls_catalogue_rules.py`): `tests/unit/test_aa1173_compliance_db_checks.py` keeps them
  byte-equal.
- **Merge window: after the bk-076 apply.** Until the apply the entry still matches the live grant, so the PR stays a
  draft until the DB Migrate apply of bk-076 has succeeded, then merges here first and in Infra second (Infra's Copy
  Guard compares its copy with this repo's `main`), both before the next 02:17 UTC Copy Guard run. Merging before the
  apply would also be safe for CI (the removed entry is simply not checked), but the nightly Dev reference would show
  the still-live grant as a rule-g violation for every day the destructive apply waits for its DRY RUN pins.

## Changed

- Only the allowlist. `services/reports/reliability.py` (the K-REC-INBOX text "not read"),
  `tests/integration/test_aa1003_r4_reports.py` and the cross-app denial probes on `booking.customers` are history or
  already guard on the table's existence (AA-1046 notes); they are left as they are.

## Tradeoffs

- One extra pair of small PRs after the apply instead of folding the change into the Booking drop PR: the rules file
  lives in CIS and Infra only, and Booking cannot change them.

## Should know

- The CIS CI replay has no `booking` schema: the entry is not `cis_side()`, so this repo's
  `test_rls_catalogue_guard.py` neither needed it nor checks its absence. Only the Dev dump sees it.
- If the apply slips past a night with this PR still unmerged, nothing turns red: the entry only goes stale after the
  drop.
