# AA-978 — CIS 276: membership directory and event feed (storage slice)

Slice S2a of AA-978 (CRM-P1): the storage behind contract `tenant.membership.v1`. The routes
(`/tenant/membership/v1`, Tenant 360 member routes) come in the AA-978 code PR, notes in `AA-978.md`. Separate
file so the two PRs never edit one notes file (lesson S242).

## Decisions

- **Key 276, not 275.** SCHEDULE S250 §1 gives 275 to AA-977. The two files are independent; 276 is applied after
  275 (DB Migrate applies in key order, never with a hole).
- **Feed order is `(txid, seq)`, not `seq`.** The plan said "cursor of seq, serve rows with txid < horizon". That
  skips events: transaction A takes its xid, B takes a later xid and a lower seq and commits, then A writes its event
  (higher seq) — once A's txid is below the horizon and the cursor has passed B's seq, A's event is never served.
  Ordering by `(txid, seq)` below `pg_snapshot_xmin(pg_current_snapshot())` is safe: every transaction that can
  still commit has txid >= the horizon, so it always sorts after the cursor. The integration test
  `test_an_open_transaction_holds_back_every_later_event_and_is_never_skipped` builds exactly that case.
- **Trigger privileges (SCHEDULE §5): invoker triggers plus a guard, not SECURITY DEFINER.** Data standards MIG-6
  forbids SECURITY DEFINER in migrations. Proof instead: on Dev only cis_app (and the owner, and the master as a
  member of cis_app) may write `shared.tenants` (schema reference 24/10: grant cis_app only), and cis_app gets
  INSERT on the event table. Guard 2 of the file refuses any role with INSERT/UPDATE on `shared.tenants` (table or
  `is_active` / `cancelled_at` column level) that could not insert an event; a standing integration test repeats
  the check, so a future writer must come with the event grant.
- **Events come only from the triggers.** The event guard refuses an INSERT at `pg_trigger_depth() < 2`, so cis_app
  holding INSERT cannot forge a `membership.removed`. UPDATE and TRUNCATE are always refused.
- **Explicit REVOKE / GRANT (SCHEDULE §5 point 3).** REVOKE ALL from PUBLIC, cis_app, aa_app_user, catalog_owner on
  both tables and the identity sequence (the Dev default ACL of cis_owner would hand cis_app DML and sequence
  rights), then cis_app: members SELECT/INSERT/UPDATE/DELETE, event SELECT/INSERT/DELETE. An identity column's
  nextval does not check sequence privileges, so cis_app has none on the sequence (tested as cis_app).
- **DELETE is limited by the guards, not refused.** The DM-7 rows (root R2) say both tables go 90 days after
  removal / occurrence and with the tenant in the AA-839 erasure. So DELETE passes only for a removed member 90 days
  after `removed_at`, an event 90 days after `occurred_at`, or any row of an offboarded (or deleted) tenant. A silent
  DELETE of a live member is refused: it would revoke nobody in the CRM.
- **The Membership JSON is built inside the emit trigger.** A helper SQL function called from the trigger body needs
  EXECUTE for the writing role (the trigger itself does not); inlining keeps EXECUTE revoked from PUBLIC on all four
  functions.
- **Membership status rules.** invited -> active -> removed; removed is final (a re-added person is a new row; the
  partial unique index covers only non-removed rows); the identity binds once (NULL while invited, set at
  activation) and never changes; `invitation_id` is required while invited. Insert as `removed` is refused.
- **Agency state mapping** (plan note): deleted = `cancelled_at` set; locked = `is_active` false; active otherwise.
  A restore of an offboarded tenant emits `tenant.unlocked`. A tenant inserted locked or offboarded emits
  `tenant.created` then `tenant.locked` / `tenant.deleted`.
- **No FK from the event table to `shared.tenants`.** Many integration tests hard-delete their tenants, and an event
  outlives the row it describes. `tenant_members.tenant_id` has the FK (NO ACTION): a hard delete of a tenant with
  members fails, as it should.

## Changed (vs. the plan)

- Columns: added `removed_by` (who removed, a label) next to `removed_at`.
- `tests/integration/rls_catalogue_rules.py`: rule a allowlist entries for both tables (tenant_id without RLS, cis_app
  only, like `shared.tenants`). The Infra byte copy `db/rls_catalogue_rules.py` ships in the 276 copy PR.
- `services/erasure/inventory.py`: both tables registered as `delete` (the AA-839 CI test fails on an unregistered
  tenant table).
- `tests/integration/test_aa839_erasure_job.py::test_a_restore_after_the_first_checks_stops_the_apply_inside_the_
  transaction`: a restore now writes a `tenant.unlocked` event, which changes the erasure counts by itself; the test
  turns the feed trigger off for its one restore statement so it still reaches the locked re-check it is about.
  (In production both checks stop the apply.)

## Tradeoffs

- The horizon is cluster-wide: a long open transaction anywhere on the RDS (another app's job) holds the feed back
  until it ends. Dev transactions are short; the 60 s budget of the contract holds unless something keeps a
  transaction open for minutes. The CRM consumer can report feed lag.
- Every tenant create / lock / unlock / offboard / restore writes one row. A handful a month; no index beyond
  `(txid, seq)`.
- The probe in guard 3 inserts a synthetic tenant inside an always-rolled-back sub-block. On Dev that briefly takes a
  row lock on nothing else; DB Migrate applies with the job tables idle anyway.
