# AA-230b — Admin alias for review-queue approve/reject

## Decisions
- Exposed `/admin/review-queue/{id}/approve` and `/admin/review-queue/{id}/reject` in
  `admin_pipeline.py` as thin aliases that reuse the v1 logic verbatim
  (`api.routers.v1_pipeline.approve_review` / `reject_review`) — no logic duplication.
- Pass `tenant=None` into the reused functions: they hardcode the master tenant
  (`00000000-0000-0000-0000-000000000001`) internally (AA-229), so the `tenant` param is
  unused on the approve/reject path. Safe to pass None.
- Used Edit tool instead of the indent-sensitive `/tmp/patch_admin_alias.py` heredoc to
  avoid the indent-corruption risk the prompt flagged.

## Changed
- Frontend `frontend/app/admin/review/page.tsx`: 3 fetch calls re-routed from
  `/api/pipeline/review-queue*` → `/api/admin/review-queue*` so the BFF sends them through the
  same-origin admin proxy (X-Admin-Secret), bypassing the API Gateway Lambda authorizer.

## Tradeoffs
- Why alias instead of fixing the gateway authorizer: `/v1/pipeline/*` sits behind the Lambda
  authorizer (requires Bearer JWT). The admin BFF sends X-Admin-Secret only → 401 at gateway.
  `/admin/*` is exempt from the authorizer, so re-exposing there is the minimal-risk fix.

- GET `/admin/review-queue` already existed (AA-230/AA-229 work); this adds only the
  approve/reject POST aliases to complete the set.

  reload `/admin/review` → queue shows tours, Console has no 401.
