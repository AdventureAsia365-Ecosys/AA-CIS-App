# AA-742 — decision_log: no full row per cache hit

## Decisions
- **Rollup keeps mode + zone** (`shared.decision_cache_hits_daily`, PK day/stage/question_key/mode/zone).
  The issue only asked for a hit count; with zone + mode the summary page keeps the same
  verdict / zone / acted numbers it showed when hits were ledger rows.
- **Hits are buffered in-process and flushed in batches** (≥ 500 pending or ≥ 60 s since the last
  flush, on the next ledger write). One upsert per decide() would turn every A3 recompute into
  hot-row contention on the same (day, stage, question) rows. A crash loses at most the unflushed
  counts; verdicts are never lost (they are in the ledger as the original non-cached row).
- **Scope 3 (A3 asks every segment) is solved with an in-process memo in decide()**, not in
  `atom_ranking.py`. The memo is keyed by (subject_key, tenant, question_key, wording hash), LRU
  50k entries, TTL 6 h. A repeat ask during a wave costs no DB lookup and no ledger row. Changing
  which segments A3 iterates is AA-743's job (scoped recompute) and is left there.
- **Expiry**: `_CACHE_SQL` now filters `NOT l.cached`, so the 180-day age runs on the verdict Jev
  actually gave. Old re-logged hit rows (cached=true) are ignored by the lookup.

## Changed
- `api/migrations/206_decision_cache_hits_daily.sql` — new table.
- `shared/llm_client/decide.py` — memo, hit buffer + flush, `NOT l.cached`, `_write_logs` writes no
  row for cached verdicts.
- `api/routers/admin_decisions.py` — `/summary` reads the rollup (7th parallel read) and folds hits
  into questions / stages / daily.
- `tests/unit/conftest.py` — autouse fixture clears the memo between tests.

## Tradeoffs
- Memo TTL 6 h can serve a verdict up to 6 h past `CACHE_MAX_AGE_DAYS` (180 d). Negligible.
- The memo is per process (api and worker each have one). A cold process falls back to the DB cache.
- `/admin/decisions/log` no longer lists cache hits (there are no rows). The summary still counts them.

## Should know
- Apply migration 206 **before** the deploy. If the table is missing, the flush fails, is logged
  (`decision_log_write_failed`) and the counts are kept for the next try — no stage breaks.
- Scope 4 (retention cleanup of existing `cached=true` rows, ~600k+) is a separate destructive step:
  DRY RUN count → S3 export → Nghiệp approval → delete. Not in this PR.
- S218 audit scripts read zones per subject from the ledger; the original (non-cached) row is still
  there, so Jev coverage per subject is unchanged.
