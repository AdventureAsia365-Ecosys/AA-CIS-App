# AA-844: photos CDN redirect and the daily photo_sync schedule (AA-CIS-App part)

The CloudFront distribution, its certificate, the bucket-policy grant and the ops-probe schedule
are in AA-CIS-Infra (`accounts/aa365/photos_cdn.tf`, `dfs_balance.tf`; notes `AA-844.md` and
`AA-844-grant.md` there). This repo changes where `/content/photos/{id}` redirects, adds the
schedule endpoint the Lambda calls, and shows the scheduled runs on `/admin/photos`.

## Decisions

- **Host resolved in the app layer, not in the catalog views.** Every consumer (catalog photo
  views, TripPlanner covers and `og:image`, Booking `CisPhoto.tsx`, `shared.destinations.cover_image_url`)
  keeps the `/content/photos/{id}` path; only the 302 target changes. No view or migration change,
  no consumer change. The API stays in the image path: one API Gateway, ALB, ECS hop and one row
  read per image view; CloudFront serves the bytes.
- **`PHOTO_CDN_BASE`** is a code default (`https://img.lumiguides.it.com`), like `public_base()`, so
  no deployed config changes. `off` (or an empty value) switches back to presigned S3 URLs. It is
  the rollback lever without a revert.
- **`cdn_url(key, sha256)`** strips the `photos/` prefix (the distribution's `origin_path` is
  `/photos`) and appends `?v=<sha256[:12]>`. A Drive edit overwrites the same S3 key and changes
  `sha256`, so the edge cache key changes with it and no invalidation is needed. A key outside
  `photos/` gives `None` (presign), so the CDN can never be asked for another prefix.
- **Redirect cache: 1 day (`max-age=86400`) for the CDN target**, 50 minutes kept for the presign
  fallback (below its 1-hour expiry). The CDN URL never expires, so a long redirect TTL saves API
  hops; the cost is that a reject takes up to a day to stop the redirect in browsers that already
  cached it.
- **One job per country** for the schedule (not one job for all seven folders): a Drive quota stop
  (`DriveQuotaStop`) or a failure in one country does not hide the others, and the admin card and
  the Done-when check read per country.
- **Idempotency**: key `photo_sync:schedule:<country slug>:<UTC day>`; check and inserts run in one
  transaction under `pg_advisory_xact_lock(hashtext('photo_sync:schedule'))`. Skipped while any
  `photo_sync` job is queued or running (a manual run, or the previous schedule still going), so a
  manual run and the schedule never overlap (the kind has concurrency 1 anyway).
- **No rerun-wave check** (retention's `schedule_all` has one): photo_sync does no LLM work, only
  Drive and S3 I/O. Deliberately not copied.
- **Capability `photos.write`** for the route (admin only), plus a `MACHINE_ROUTES` entry for the
  ops-probe Lambda (secret, no role). Same pattern as the retention and staff-reconcile schedules.
- **`match_destinations: False`** on scheduled jobs: place matching stays a manual, per-country
  choice (S207 decision), the schedule only keeps the photos in step with Drive.
- **`last_scheduled`** on `/admin/photos/summary`: latest scheduled job per country over 8 days,
  shown for the latest UTC day. `all_ok` only when every CON country has a job that day that
  succeeded with `result.totals.errors = 0`. A failed job has no result (`set_result` is never
  reached), so its errors are NULL and it is not ok. A country whose latest scheduled job is from an
  earlier day is listed as "not run".

## Tradeoffs

- **302 through the API vs CDN URLs in the views**: keeps the read contract and every consumer
  unchanged, at one API hop per image view (softened by the 1-day redirect cache). Writing CDN URLs
  into the views would need a CIS migration plus a contract change for TripPlanner and Booking.
- **Not done: skipping known error files (plan change 7).** Today every run retries the rows in
  `status='error'` (their `drive_modified_at` is not advanced on error), so `errors` stays above 0
  while a file keeps failing, and the "0 errors" Done-when line depends on the data. Skipping them
  is a behaviour change (a fixed file would not be retried until Drive marks it modified) and needs
  Nghiệp's agreement first; not built here.

## Should know

- **Deploy order**: merge and deploy only after the Infra distribution is applied and its curl
  checks pass. The code defaults to the CDN host, so deploying first would redirect every image to a
  host that does not answer yet.
- **A rejected photo stays reachable at a CDN URL handed out before the reject.** The route returns
  404 for it, but the object stays in S3 and CloudFront caches it for up to a year; before AA-844 a
  presigned URL died within an hour. Reject is reversible, so objects are not deleted on reject.
  Options if this matters: delete or move rejected objects plus an invalidation, or a shorter edge
  TTL. Raised with Nghiệp, not decided here.
- **Deploy gate**: the seven serial jobs (concurrency 1) run for a while after 04:00 ICT, and the
  Deploy Dev guard blocks a deploy while they are queued or running.
- **Rollback without a revert**: set `PHOTO_CDN_BASE=off` on the api task definition (an underscore
  env var: edit it by hand, never through generated scripts).
- **Time-gated evidence**: the Done-when line "2 consecutive scheduler days, succeeded, 0 errors" is
  read from the `shared.job` rows with `created_by='scheduler:aa-844'`, `last_scheduled.all_ok`, and
  the Lambda log line `ops_probe ok path=/admin/photos/sync/schedule` (the Lambda never raises, so a
  403/404/500 there only shows in its log).
- Local runs: the new unit file (17 tests), the new integration file on local Postgres (6 tests),
  `test_aa708_photo_sync.py`, `test_aa882_route_policy.py`, `test_aa882_staff_authz.py`; `tsc --noEmit`
  clean, eslint on `page.tsx` shows only the three warnings that were there before.
