# AA-969 part 2 (lane l1-aa969-d16): CIS clean-up skips the pilot tenant

Item (3) of the S265 re-scope comment on AA-969 (root ADR 0019 d16): every clean-up, E2E and wave job skips the pilot
tenant. This note covers the `shared.job` kinds and the E2E identity of AA-CIS-App. The marker is the R1 one
(`shared.tenants.is_pilot`, CIS 354, at most one tenant, `kind = 'agency'`).

## Decisions

- **Inventory of `shared.job` kinds that delete, reset, seed or bulk-rewrite data, and what each does now:**
  - `retention_llm_call_log`, `retention_tenant_api_usage` (tenant rows): **skip the pilot** (`NOT_PILOT` on every
    part). The rollups (`llm_call_daily`, `tenant_api_usage_monthly`) are written first as before, so the pilot's
    numbers stay answerable; only its raw rows are kept. The windows (180 / 90 days) are longer than the pilot
    (8 weeks), so in practice this matters for the `manual_override` proof run (21-day cutoff) and for rows that
    predate the pilot marking.
  - `retention_job`, `retention_decision_log`, `retention_cost_explorer_snapshot`: unchanged (platform rows: job queue,
    Jev verdict cache, AWS cost snapshots; no tenant data).
  - Waves (`shared.rerun_wave`, `s1_rewrite` / `a3_atomize` / `recompute` / places / photos): unchanged. They rewrite
    AA's own catalogue (tenant `aa_internal`), never a tenant's rows.
  - `t2_rewrite`, `t7_slate`, `t8_angles`, `t9_write`: unchanged. Queued by the tenant's own requests (no fan-out over
    tenants exists); skipping them would stop the pilot's product.
  - `tour_retirement_fanout` / `retired_page_draft` / `tour_notice_email`: unchanged (ADR 0015: the pilot must learn
    that a tour left the catalogue).
  - `data_erasure`: unchanged. DRY RUN + approved fingerprint + snapshot, tenant mode only after offboarding.
  - `writing_memory_*`, `supply_media_purge`, `tripplanner_purge`, `tenant_provision`, `tenant_account_tick`: not
    clean-up of tenant data (AA-side learning artefacts with rollback, Booking supply photos, CDN cache drops, the
    tenant creation saga, the time-based lifecycle moves).
- **E2E:** the A10b E2E staff identity may write only to a synthetic tenant (`is_synthetic_tenant`). The check now
  also requires `is_pilot IS NOT TRUE`, so a pilot tenant marked canary by mistake is still read-only to E2E (Tenant
  360 invites, view-as).

## Changed

- `services/retention/policy.py`: `NOT_PILOT`, set as `where` of the two tenant-row specs.
- `api/core/e2e_staff.py`: `SYNTHETIC_TENANT_SQL` excludes the pilot.
- Tests: `tests/unit/test_aa969_pilot_skip.py`, `tests/integration/test_aa969_pilot_skip.py`; the A10b unit test pins
  the new SQL.

## Tradeoffs

- The retention admin page counts candidates with the same specs, so it already shows the pilot's rows as not due.
- Rows of the pilot that are already past the window stay until the marker is cleared; then the next run takes them.

## Should know

- No migration. Live check after deploy: a manual DRY RUN of `retention_tenant_api_usage` succeeds
  (`POST /admin/job-runner/retention/run`), and `/health` is 200.
