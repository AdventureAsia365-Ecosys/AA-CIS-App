# AA-987 — CIS half: a tour lifecycle event triggers a TripPlanner cache purge

Problem (AA-986 E2E, S248): the backend refused a retired tour at once, but the public TripPlanner site kept it for
up to 30 min (browse list on the Vercel CDN `max-age=1800`, ISR pages 30 min, the proxy's retired list refreshed every
30 min). Done-when: on Dev a retired synthetic tour answers 410 and leaves the browse list within 2 minutes; a restore
brings it back within 2 minutes. TripPlanner half: AA-TripPlanner-Web `docs/implementation-notes/AA-987.md`.

## Decisions

- **Push from CIS, driven by the outbox, not a TripPlanner poller.** The issue offered a signed webhook or a
  TripPlanner poll of `catalog.v_tour_lifecycle_outbox` every minute. TripPlanner has nothing that runs every minute:
  Vercel Hobby crons run once a day, and a new EventBridge schedule + Lambda would be new AWS cost and infra for one
  check. CIS already has a durable job runner and an always-on worker. ADR 0015 rejected *bare* push webhooks in
  favour of outbox → pull → inbox; this design keeps the outbox and the inbox semantics on the CIS side: one job per
  outbox row, keyed on the row's `idempotency_key` (the anti-join of contracts rule 4), so delivery is at-least-once,
  idempotent and visible, and the HTTP call only says "drop your caches".
- **Job kind `tripplanner_purge`** (`services/jobs/tripplanner_purge_job.py`, plain name: CIS kinds have no prefix and
  `job_kind_chk` refuses `tp_`). Idempotency key `tripplanner_purge:<tour_lifecycle_event.idempotency_key>`. Payload
  `{"event_key", "trigger"}`; the handler re-reads the row from `gold_aa_internal.tour_lifecycle_event` (the base table
  of the contract view: `cis_app` has SELECT on it, not on `catalog.v_tour_lifecycle_outbox`) and sends exactly the
  view's columns.
- **Three enqueue points**: `services/tour_lifecycle/effects.run_after_commit` (every admin lifecycle route and the
  staging / set-active / trash routes of `admin_pipeline.py`), the publish of `services/export/handler.process_export`
  (it calls the service's `publish` without `run_after_commit`; a publish that closes a paused key writes `restored`),
  and a **sweep** in the api ops sampler (every 300 s): one `INSERT ... SELECT ... WHERE NOT EXISTS` for every event of
  the last 2 h without a job, 30 s lag so the after-commit enqueue goes first. The sweep is the safety net for a crash
  between commit and enqueue and for any future writer that forgets the hook.
- **The purge runs first in `run_after_commit`**, before the recompute: it is the one effect the public site waits on,
  and it never raises.
- **HMAC-SHA256** over `f"{t}.{body}"`, header `X-AA-Signature: t=<unix s>,v1=<hex>` (Stripe-style; TripPlanner
  refuses a timestamp more than 300 s away). Body: `{"contract": "catalog.tour.lifecycle.v1", "events": [row]}`,
  compact JSON with sorted keys (ASCII), so both sides hash the same bytes. A fixed vector is pinned in both repos'
  tests.
- **Secret** `aa-cis/<ENVIRONMENT>/tripplanner-revalidate-hmac` (plain string or `{"secret": "..."}`), read by name at
  run time with a 10-min TTL cache (60 s after a failure), like the other CIS secrets. Not under `tripplanner/*`: the
  CIS task role has an explicit Deny there (X1 S19). The task role's GetSecretValue grant on `*` already covers it, so
  no IAM or task-definition change. Local override: env `TRIPPLANNER_REVALIDATE_SECRET`.
- **URL** `TRIPPLANNER_REVALIDATE_URL`, default `https://aa-tripplanner.vercel.app/api/revalidate/catalog` (the
  TripPlanner Dev production alias; public anyway). An empty value switches delivery off.
- **Not configured = success with `skipped: not_configured`**, one warning line. Before the secret exists every event
  gets one quick skipped job, never a failed one (no alarm noise, no deploy-gate rows).
- **Retries**: `max_attempts` 4 (backoff 30 / 60 / 120 s). 2xx = delivered; 408 / 425 / 429 / 5xx / network = retry
  (503 is TripPlanner's "secret not set yet"); any other 4xx = `NonRetryable` (bad signature or payload: waiting does
  not fix it). After the last attempt the time-based TTLs on TripPlanner (30 min) still bound the lag, as before.
- **Not `deploy_gate_exempt`**: the unit suite pins "no exempt kinds" (AA-751), and a queued purge retry at most delays
  a CIS deploy by ~3.5 min. Not `background`: a purge is a ~1 s HTTP call and must not wait behind place jobs.

## Changed

- `services/tour_lifecycle/service.py`: each `Outcome.events` entry also carries its `idempotency_key` (the column
  value written by `_write_event`). No SQL change.
- `services/tour_lifecycle/effects.py`: `notify_tripplanner(db, events, trigger=...)`, called first by
  `run_after_commit`.
- `services/export/handler.py`: `notify_tripplanner(conn, published.events, trigger="publish")` after the publish.
- `api/core/ops_metrics_sampler.py`: a fifth part `_tripplanner_purge_part` (fields `tripplanner_purge_swept` /
  `tripplanner_purge_error`); `PART_TIMEOUT_S` 60 → 50 s so five parts still fit the 300 s interval.
- `services/jobs/__init__.py` registers the kind. CONTEXT.md: one paragraph under the tour liveness entry.
- No migration, no new table: `shared.job` is the delivery record.

## Tradeoffs

- One job per event vs one batched job: a bulk retire of N tours sends N notices and N purges. Each purge drops the
  same roll-up tag on TripPlanner, so they are equal and cheap; batching would need a debounce key and a cursor. Dev
  lifecycle events are a few per day.
- Push vs pull: push couples CIS to a TripPlanner URL. Accepted: the URL is one env var, the payload is the outbox
  row (no CIS internals), and a pull consumer can replace it later without a contract change.
- The sweep runs in the api, not the worker: the ops sampler is the existing periodic loop (it already sweeps retired
  kinds). Its 300 s interval means a lost after-commit enqueue is delivered in ≤ ~5.5 min, not 2; the normal path is
  seconds (worker poll 5 s + one HTTP call).

## Should know

- Orchestrator steps: create the secret `aa-cis/dev/tripplanner-revalidate-hmac` (random 32+ bytes) and set the
  same value as the TripPlanner Vercel env `CATALOG_REVALIDATE_SECRET` (Production + Preview); deploy TripPlanner
  first (the route must exist), then CIS. Cost: one Secrets Manager secret ($0.40 / month); no other AWS resource.
- Verify on Dev: trash a synthetic tour's Master in admin → Jobs page shows one `tripplanner_purge` job `succeeded`
  with `result.status` 200 within seconds; `curl -I https://aa-tripplanner.vercel.app/tours/<slug>` → 410 within 2 min;
  `/api/browse?resource=catalog-tours&country=<c>` no longer lists it. Restore + activate → back within 2 min.
- Logs: `tripplanner_purge_delivered` / `_failed` / `_not_configured` / `_secret_unavailable` / `_enqueue_failed`
  (CloudWatch `/ecs/aa-cis-dev`), never the secret or the body.
- Tests: unit `tests/unit/test_aa987_tripplanner_purge.py` (vector, delivery answers, skip, enqueue + replay, sweep,
  wiring), `tests/unit/test_aa751_ops_metrics_sampler.py` (the sweep part); integration
  `tests/integration/test_aa987_tripplanner_purge.py` (real event rows → one job per event, replay adds none, sweep
  once, handler signs the outbox row, `cis_app` grants). The integration file needs the CI Postgres (superuser
  bootstrap of the roles); it does not run on a local non-superuser DB, like the AA-986 L2 suite.
- During development one unit-test run reached the real TripPlanner URL once (404, the route did not exist yet,
  signed with the test secret) before `deliver` looked `_post` up per call; fixed, the tests no longer touch the network.
