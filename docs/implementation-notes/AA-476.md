### Phần C.1 — pipeline_runs.status stuck at 'ingesting' (bug #1, folds in Phần A's gap #3)
Root cause (found going deeper than Phần A's initial framing): `sync_batch_completion()`
(new name, extracted from `process_export()`'s inline logic — `services/export/handler.py`) is
the ONLY place `pipeline_runs.status` ever advances past `'ingesting'` anywhere in the codebase.
It only ever recognized `raw_tours.pipeline_status = 'published'` as "this tour is done" — but
`reject_review()` (api/routers/v1_pipeline.py) NEVER touched `raw_tours.pipeline_status` at all
(only `review_queue.review_status` + `generated_content.status`), so a rejected tour stayed
`'ingested'` forever and the completion check's `pending` count never reached 0.
- `sync_batch_completion(conn, batch_id, silver=...)`: same tours_passed/pending/status-flip
  logic as before, but the pending query now excludes `'hitl_rejected'` and `'failed'` too
  (`_TERMINAL_TOUR_STATUSES`), not just `'published'`.
- New `mark_tour_rejected(conn, tour_id)`: sets `raw_tours.pipeline_status = 'hitl_rejected'`
  then calls `sync_batch_completion`. Wired into `reject_review()` right after its existing
  `generated_content.status = 'rejected'` UPDATE.
- This is the single shared fix point — Phần A's gap #3 and the original bug #1 are the same
  defect (per Nghiep's instruction not to patch them separately); no second code path added.
- Tests: `tests/unit/test_aa476_batch_completion.py` (new, 5 tests, drives the real functions)
  + updated `tests/unit/test_aa211_212_gate_hitl.py`'s 2 reject tests (extra fetchrow in the
  mocked sequence for the new tour_id lookup, `mark_tour_rejected` patched).
- **Known follow-up, NOT done here** (would require touching real data, blocked by "no apply"):
  any batch ALREADY stuck at `'ingesting'` in the live DB from before this fix ships stays stuck
  — this only fixes the code path going forward. A one-time backfill (re-run
  `sync_batch_completion` for every existing `batch_id`) would be needed to fix historical rows,
  not attempted in this task.

### Phần C.4 — file_hash unique index migration
New `api/migrations/123_raw_sources_file_hash_unique_index.sql`. Definition copied verbatim from
a **read-only** query against the live dev DB (`pg_indexes`, via the standard S3-mediated ECS
exec pattern — no data touched, script deleted from S3 after):
```sql
CREATE UNIQUE INDEX idx_raw_sources_file_hash ON silver_aa_internal.raw_sources
    USING btree (file_hash) WHERE (file_hash IS NOT NULL)
```
It's a PARTIAL unique index (guards only non-NULL file_hash), not a plain UNIQUE constraint —
migration reproduces that exactly. Uses `CREATE UNIQUE INDEX IF NOT EXISTS` so it's a safe no-op
on the current DB. **NOT run against the real DB** — per "no apply" instruction, only verified by
comparing the migration's SQL text against the live `pg_indexes` output, not by executing it.

## Tradeoffs
- **Bug #11**: chose "relabel honestly" over "add instrumentation for a real count." STEP0 found
  `brand_audit_status` (the most promising existing signal) is NOT a reliable "call happened"
  proxy — `brand_audit_node` sets it to `'pass'` on 3 separate no-LLM-call skip branches (missing
  `generated`, AA-206 judge-result reuse, missing `OPENAI_API_KEY` — the last is ~100% of rows
  right now per the AA-351 zero-credit finding). Building a "more accurate" count from existing
  columns risked shipping a confidently-wrong number, worse than an honestly-labeled undercount.
  A real fix needs a persisted per-node call counter (`generated_content.metadata.llm_call_count`
  or similar), which is a write-logic change explicitly out of scope for this batch.
