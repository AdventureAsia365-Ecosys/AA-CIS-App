# AA-921 — Pinned example sets and tenant preference summaries (WM-27, WM-28, WM-29)

Session S260 (Claude Code, lane L5). Design: root `docs/audits/2026-10-20-S245-writing-learning-loop/` (README,
cost-cuts, `issues/README.md` Group 7); app ADR 0010. Built on AA-919 (releases, golden set, R2, shadow) and AA-920
(insertion builder, post-activation check).

## Decisions

- **Two new tables, no change to the release table (CIS 313, expand).** Pinning exemplars inside
  `shared.writing_memory_release` (a new `exemplar_ids` column plus a new CHECK / trigger on the release) would be a
  contract file (ADR 0017: a new constraint or trigger on an existing table) and need the two-PR order. A link table
  `shared.writing_memory_release_exemplar` with an FK to the release is expand (an FK *from* a new table is allowed), so
  the migration, code and readiness bump ship in one PR.
- **Exemplars ride on a `rules` release only.** CIS 287's CHECK ties `empty` to "no rule"; an exemplar-only release
  would need a new content class and a rewrite of the 287 guard (contract). A `rules` release already needs an R2 pass
  and a shadow pass at activation (CIS 287 CHECK + trigger), which is the evidence the design asks for exemplars. A
  tenant's first release with examples therefore carries at least one rule (in practice its preference summary).
  `lexicon_only` / `repair_hint_only` releases pin nothing (the link trigger refuses them).
- **The examples are part of the release fingerprint.** `exemplars.release_sha256` hashes the rules and the pinned
  `(exemplar_id, channel, position, masked_text)`; with no example it is exactly the old `items_sha256`, so every
  release drafted before CIS 313 keeps its hash and renders as before. `insertion.attach_items` loads both and checks
  the hash: an edited or erased example makes the whole part render nothing (fail closed), and the post-activation
  check then reports the writes as not carrying the release.
- **Links are written only in the draft's own transaction** (trigger: release `created_at = now()` and status
  `draft`), never updated. This is the DB half of "the release sees exactly what will run" — the items hash is fixed at
  draft time by CIS 287.
- **Selection = pinned first (newest pin), then the newest candidates, 2 per channel** (`exemplars.pick`), the same
  function for the draft, the Exemplars tab's "Next draft" preview and the `in_next_draft` flag. No ranking by a
  model, no embeddings.
- **Candidate text**: an approved T9 piece's `content_text`, or the edited field of the T2 version's
  `rewritten_content` (else the whole version), masked by `masking.mask`, whole sentences up to 120 words, at least 20
  words. The channel comes from the signal (the CI schema has no `content_piece.channel`; Dev has it, the signal holds
  the same value).
- **Where examples render**: after the tenant rules — T9 in the user prompt (`t9_tenant_lines`), T2 at the end of the
  system-prompt block (`t2_block`). Never in the T9 platform slot, which is appended to the cached `SYSTEM_PROMPT`
  shared across tenants. Tenant examples first, platform examples as fill up to 2, never another tenant's.
- **Carry-over check** (the n-gram half of the WM-27 Done-when): `eval_checks.exemplar_copies` — the output is masked
  the same way and any 6-word run with >= 3 content words shared with an example is a QA trace `exemplar:<id>`; wired
  into R2 (`checks`), the shadow and the post-activation check, so a release whose writer copies its examples fails
  its evidence and an active one rolls back.
- **Preference summaries reuse the rule store** (`kind = preference_summary`, CIS 280 already has the kind, its CHECKs
  and the 250-token tenant cap). Drafting runs inside the existing `writing_memory_mine` job with
  `payload.mode = preference_summary` (no new job kind), on the same stage / judge route and caps; those runs are
  excluded from the miner's monthly run count (`mining._RUNS_SQL`).
- **Quarantine = stored `rejected` by the lint with `lint.quarantine = true`** and the failed `unsourced_claim` check
  (promise words of the fact filter, any digit or mask token, any add-verb per `lint.constraint_only`). Same shape the
  miner uses for a lint-rejected draft, so the Candidates tab shows it with its reason.
- **The LLM path is off by default**: `WRITING_MEMORY_PREF_SUMMARY` unset → `run_preference` makes no call and returns
  `state: needs_llm_path`; `POST /admin/writing-memory/run {kind: preference_summary}` answers 409 `needs_llm_path`;
  the Tenant 360 card shows "drafting needs the LLM path (off)".
- **Tenant 360 "Voice memory" card** lives on the Quality tab (below the gate tables), from one admin route
  `GET /admin/writing-memory/tenants/{id}/voice` (explicit tenant filter on every query).

## Changed (vs. the issue text)

- The issue text says masks like `[PLACE]`; the code uses the existing masking vocabulary (`[NAME]`, `[N]`, `[PRICE]`,
  `[TIME]`, `[URL]`), the same one the rule drafter sees. CONTEXT.md updated.
- No platform-exemplar source is built: platform examples can exist in the table and are used as fill, but nothing
  creates them yet (the "use as example" chip exists only on tenant T2 / T9 edits). A curated AA voice pool is a
  follow-up if wanted.
- WM-29 "source link": the Content quality page has no deep link by id, so the drawer shows the source table and the
  short id (like the rule provenance), not a link.

## Tradeoffs

- Link table vs. array column: one more table and a join on every resolve of a release with content (one indexed query
  per part), in exchange for an expand-only migration and FK cascades on erasure.
- A `never` set after the draft does not change the release text (fixed by hash); the API refuses the first
  activation (`exemplar_never`, `releases.check`) but the DB does not (that would be a trigger on the release table,
  contract). The DB still refuses linking a `never` example at draft time.
- Readiness goes to 313, which also requires 311 / 312 (open gateway PRs) to be registered — renumber at merge.
