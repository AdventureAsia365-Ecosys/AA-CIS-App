# AA-688 — Batch Cohere embeddings in PAA question landing

## Baseline (Dev, 29/09/2026 02:44 UTC, job 547d955b, tour 05cb2c55)
- Job `a3_atomize` started 00:24:38 UTC, still `running` at 02:44 (released once by the S201 deploy,
  re-run from 02:21).
- Since the re-run: 382 `f10_embed` calls in 22.7 min, 1 text each, $0.000394 total.
- Scope is much wider than "this tour": 3,386 of 3,463 segments have `questions_count IS NULL`,
  and a NULL segment is always recomputed (migration 163 semantic). So the first run after the
  reset recomputes almost the whole platform.
- Work left for that run: only 977 of 9,115 segment atoms have both view embeddings
  (~16,000 atom-view texts), plus the candidate questions (723 already cached). At one paced
  call per text (3.5 s) that is roughly 16 hours.

## Decisions
- **Pre-pass in `precompute_question_landings()`**, not only per segment: collect every in-scope
  segment's atoms and capped candidate questions, embed all missing atom views and questions in
  batches of 96, then land. Per-segment batching alone would still pay one paced call per
  segment (~3,400 calls, ~3.3 h).
- `compute_embeddings(texts)` added next to `compute_embedding()`; the single-text function now
  delegates to it, so there is one code path to the gateway and one log-row shape
  (`quality_signal.texts` = batch size).
- Batch helpers call `compute_embeddings` through `asyncio.to_thread()`. The old helpers called
  the blocking function straight from async code (the S201 incident cause); the new path does not
  block an event loop even if called outside the A3 job thread (e.g. the admin atom PATCH).
- Each batch is written to the cache as soon as it returns, so a killed/released job keeps what
  it already paid for and the retry only embeds the rest.
- A question whose batch failed is not retried one-by-one inside the landing loop; it goes
  straight to claim-by-name (same soft-fail as before, without re-paying pacing per question).
- Progress: an optional sync `progress(fields)` callback is threaded from the job down to the
  pre-pass. The A3 chain runs in its own thread/loop (S201 hotfix), so the job wraps
  `ctx.progress()` with `asyncio.run_coroutine_threadsafe` onto the worker's loop
  (fire-and-forget; a failed progress write never fails the job).

## Changed
- `services/acp_shared/content_embedding.py`: `compute_embeddings()`, `MAX_TEXTS_PER_CALL = 96`.
- `services/acp_contract/atom_matching.py`: `embed_questions_cached()`,
  `ensure_atom_embeddings_batch()`, `land_question_on_atom(..., vector=None)`.
- `services/acp_contract/atom_ranking.py`: pre-pass + progress in
  `precompute_question_landings()`; `land_questions_for_segment()` uses the batch helpers.
- `services/export/handler.py`, `services/jobs/a3_atomize_job.py`: progress plumbing.

## Tradeoffs
- Batch of 96 short texts is still one request against the 20 req/min quota, so pacing stays
  3.5 s per call. Token-per-minute quota was not an issue for these short texts (atom views are a
  few words, questions ~10 words).
- Kept the single-item functions (`ensure_atom_embeddings`, `_embed_question_cached`) for
  existing callers/tests rather than deleting them.

## Should know
- `questions_count` semantics are unchanged: same capped candidate set, same k=1 nearest atom,
  same claim-by-name fallback. Only how/when embeddings are fetched changes.
