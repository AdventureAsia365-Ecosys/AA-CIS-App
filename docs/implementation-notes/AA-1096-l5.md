# AA-1096 lane L5 — TripPlanner settings on the registry (CIS side)

S279 thresholds audit (root `docs/audits/2026-11-13-S279-session/thresholds-audit/`, section 3.1 TripPlanner rows and
lane L5). TripPlanner has no staff surface, so its settings are CIS rows (`shared.setting_definition` with
`app = 'tripplanner'`, CIS 407) that TripPlanner reads through a catalog contract view. The TripPlanner reader is in
AA-TripPlanner-Web (`backend/shared/settings.py`, notes `docs/implementation-notes/AA-1096-l5.md` there).

PRs, in order (MIG-4):

1. **Migration-only** (CIS 414-415, both contract, one batch; 413 was the main max once the quality settings landed):
   - 414: 17 TripPlanner definitions (rate limits, planning chat monthly caps, lead cap per tenant, lead hold, narration
     cache TTL and max_tokens, planning chat steps and max_tokens, the two hand-off switches) and the TripPlanner app
     profile's `default_daily_budget_usd = 5.0` (only when still NULL);
   - 415: `catalog.v_app_settings_v1` (app, key, value, version, tenant_id, effective_from), SELECT to tripplanner,
     catalog_owner column grants and two FOR SELECT policies (TripPlanner rows only);
   - with them: the regenerated compiled defaults, the CIS binding reading every key of `shared.setting_value`
     (`KEY_PREFIX = ""`), settings-lint's dead-key check limited to `app = 'cis'`, conftest skipping 415, the seed test
     and the two integration tests. These ride with the migrations because that PR's CI fails without them.
2. **Code** (this branch, no migration file, works before and after 414): the CIS mirror `TP_DEFAULT_DAILY_CAP_USD`
   is gone; the Apps board TripPlanner card and the TP-01 weekly report read the cap from the app profile row.

## Decisions

- **The daily cap has one source: the app profile row**, not a registry key. `shared.llm_app_profile`
  `default_daily_budget_usd` already wins over the env cap in TripPlanner (`llm_gateway.budget_status`), is edited on
  AI gateway › App profiles (audited, tighten-only for delegated roles since L1) and is read by the CIS ops check
  `llm_spend_alert`. A registry key for the same number would be a second source. 414 seeds 5.0 (today's Terraform and
  code value) only when the row is NULL.
- **Seeds = today's effective values.** Terraform sets none of the 17 env vars except
  `REQUIRE_REGISTRATION_BEFORE_HANDOFF=true`, equal to the code default, so every seed is the TripPlanner code default.
- **`env_override` is NULL for the TripPlanner keys.** The CIS reader honours an env override first; for TripPlanner
  that would read a CIS env var that never exists, and the TripPlanner reader serves the view first anyway (its env
  var is only the fallback while the view cannot be read, one release). The description of each key names its env var.
- **Per-tenant overrides** only where the audit (Q4) allows them: the lead cap and the planning chat tenant cap
  (`scope_kind platform+tenant`). The API already accepts `tenant_id` on a proposal; the page lists platform values.
- **The view resolves the value in force** (approved, `effective_from <= now()`, latest by effective_from then
  version) and serves the default as version 0, so TripPlanner never needs `status` or the proposal columns, and a
  missing key in the view means "not migrated yet" to it.
- **Isolation, twice.** The view's rows are `app = 'tripplanner'` AND `pg_has_role(current_user, 'tripplanner',
  'USAGE')`, so a role granted the view by mistake sees nothing; catalog_owner's RLS policies on both tables show it the
  TripPlanner rows only, whatever a later view says.
- **Numbers 414-415**: 412-413 are the quality settings registry of the same wave (merged first).

## Changed (vs. the lane brief)

- No `tripplanner.*` daily-cap key: the brief's "single source" is the app profile (above).
- The CIS Apps board card shows "no app-profile cap" when the row is NULL instead of a mirrored 5 USD.
- `cis_app` sees TripPlanner rows on Platform › Settings through the CIS binding (prefix widened), no page change: the
  page already lists any app of `settings_registry.APPS` generically.

## Tradeoffs

- Enforced is seeded `true` although TripPlanner reads the keys only once its PR is deployed (minutes later in the same
  wave); the alternative (411's `enforced = false` + a follow-up migration) costs one more migration for a gap of one
  deploy.
- The Apps board still sums the online stages only, while the profile cap counts every `tp_*` stage; TripPlanner has
  no offline stage today, so the numbers are the same.

## Should know

- Platform › Settings shows "overridden by env" only for a CIS env var; the TripPlanner Lambda env is not visible from
  CIS. The TripPlanner jobs Lambda op `settings` reports what TripPlanner actually serves and from where.
- Infra lane L6 removes the TripPlanner env vars (and the Terraform daily-cap variable) after one release.
