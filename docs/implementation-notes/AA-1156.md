# AA-1156 — My work: one queue page for content roles

## Decisions

1. **One endpoint, tiles by capability.** `GET /admin/my-work/summary` (api/routers/admin_my_work.py) needs any of
   `review.act`, `content.write`, `quality.write` (POLICY). Each tile is in the answer only for a role holding its
   capability: Review Queue waiting (`review.act`); supply drafts to review, hotels and services with no description,
   AA content drafts (`content.write`); place cards to review, compliance holds (`quality.write`). Result today:
   admin and content_lead get all six, content the first four, tenant_qa the last two; viewer, ai_ops, finance,
   support and customer_success get 403 (no tile). Nothing names a person.
2. **Same filter as the target page, by construction.** Every count runs next to the page's own list query and shares
   its WHERE text:
   - Review Queue: `_review_queue_where` extracted from `admin_review_queue` (the page and `review_queue_summary` both
     call it); the page's default view is `status=pending`, so the link is `/admin/review` with no query.
   - Supply copy: `LIST_FILTER_SQL` shared by `list_entities` and `status_summary`. Drafts to review =
     `has_draft=1` (an open `shared.supply_content_version` with status `draft`, `OPEN_DRAFT_SQL`); no description =
     `status=draft` ("No content yet"). See decision 7.
   - AA content: `SUMMARY_SQL` built on the list's `_LIST_FROM` (`status=draft`).
   - Place cards: the filter moved to `services/acp_shared/place_card_list.py` (`list_filter`), used by the page route
     and by `summary` (`status=auto_checked`, the cards no person verified yet).
   - Compliance: `FILTER_SQL` shared by `LIST_SQL`, `COUNT_SQL` and `SUMMARY_SQL` (page default `state=open`).
3. **The backend sends the filter, the frontend keeps the path.** Each tile carries `filter` (e.g.
   `{"status": "in_review"}`); `frontend/lib/myWork.ts` maps the key to the page path and adds the filter as the query.
   Supply copy and AA content now read `?status=` from the URL (read once hydrated, the Place cards pattern, so the
   server render matches); Place cards already did.
4. **Oldest item age:** Review Queue `min(created_at)`, supply drafts the oldest open draft's `created_at` (a redraft
   does not move the entity row), supply no-description `min(updated_at)` of the entity (moves when the content
   status changes), AA content the newest version's `created_at` (for a draft row that is the waiting draft), place
   cards and compliance flags `min(created_at)`. The page shows it relative to the summary's `generated_at`.
5. **Landing:** `landingPage()` sends content, content_lead and tenant_qa to `/admin/my-work`; admin keeps
   `/admin/overview` and finds My work in the Home group (first after Overview); the viewer (UI-smoke account) keeps the
   Review Queue. The phone bottom nav shows My work in Overview's place for a role that cannot open Overview.
6. **"Booking: My work"** opens the Booking staff dashboard through `appPageUrl("booking", "/")`, shown to roles with
   `content.write` until the session carries the Booking grant (the later Booking-roles slice refines it). Booking checks
   its own grant.

7. **Supply drafts are counted by open draft version, not by entity status** (review fix pass). `in_review` is set
   only when the entity was `draft` (`_insert_version`); after Booking changes the facts of published content the
   entity turns `stale` and its redraft leaves it `stale`, and a human edit of published content leaves it
   `published`. Counting `content_status = 'in_review'` would miss every redraft after the first publish. The new
   optional list filter `has_draft` (true / false / any) on `GET /admin/supply-content`, read by the page from
   `?has_draft=` (and offered as an "Open draft" select), is the tile's filter, so the tile and the page still share
   one WHERE. The "no description" tile keeps `status=draft` (a `draft` entity never has an open draft: the first
   draft moves it to `in_review`, a reject of the last draft moves it back). A `stale` entity with no redraft yet also
   shows no CIS text in Booking but is left out of that tile on purpose: the pull already queued its redraft job (the
   page's feed board shows that job's failures), so it is not a person's work until the draft exists; the tile's info
   text says so.

## Changed

- No migration, no new table, no new setting (no threshold was added: counts and ages only).
- `GET /admin/supply-content` gained the optional `has_draft` query (openapi.json regenerated with the pinned
  fastapi 0.161.1 / pydantic 2.14.1); `list_entities` now binds limit / offset as `$4` / `$5`.
- `api/routers/admin_content_quality.py` shrank by 8 lines (the place-card filter moved to a service module); it is a
  code-health baseline file and may not grow.
- `api/core/staff_authz.py` gained one POLICY line and is now exactly at its code-health baseline (1115 lines): any
  further line there must remove one.

## Tradeoffs

- Tiles are computed on request (6 small COUNT/MIN queries, indexed columns), no cache: the page has a Refresh button
  and no polling, so freshness beats a cache here.
- A tile whose table is missing (a migration not applied on some environment) answers `available: false` instead of
  failing the whole page.
- Compliance is a cross-tenant view (every agency's held content). It stays with `quality.write` holders, the same
  roles the page rule (TENANT_QA) already lets in.
