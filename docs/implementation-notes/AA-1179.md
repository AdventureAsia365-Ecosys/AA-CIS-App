# AA-1179 — Faster tenant served-badge lookup and a sargable anomaly-breaker baseline (C4.3 W48 findings 1 and 3)

Lane c-tenant-read-sql, S293. Source: root `docs/audits/2026-11-24-S290-session/c43-w48/README.md` (findings 1 and 3).

## Starting point (what S291 already shipped)

The W48 probe ran 24/11 05:35Z. Later the same day S291 merged two PRs that cover most of finding 1 and part of
finding 3 (`docs/implementation-notes/S291-cis-followups.md`):

- CIS migration 480: btree `raw_tours_key_expr_idx` on `((COALESCE(source_group_id, tour_id))::text)`.
- `REQUEST_TOURS_SQL` (`shared/tour_liveness.py`): the representative tour is computed once per request row
  (`CROSS JOIN LATERAL ... rep`), the key's state is a one-key `LEFT JOIN LATERAL` lookup of `v_tour_liveness` (with an
  `OFFSET 0` fence, so the key filter is pushed into the view's GROUP BY and becomes an Index Cond on 480), and the
  Subject rule subquery runs only inside the `CASE` branch of a retired representative.
- The anomaly breaker reads its baseline median once per process, app and UTC day (`cached_median`), and its rolled-day
  test runs per grouped day.

S291's live check (ECS exec, root `docs/audits/2026-11-24-S291-session/evidence/aa838-explain-old-vs-new.txt`) measured
the lookup at 25.5 → 4.0 ms and 4,385 → 149 buffers for one tenant's 8 newest requests, and 15/15 result pairs equal.
So deliverable (1) of this issue is already live; this lane adds the proof the issue asks for (every tenant and
request, the tenant role, p95) and finishes finding 3.

## Decisions

- **`REQUEST_TOURS_SQL` is not changed again.** The S291 statement already has every element the issue lists (LATERAL
  representative, Subject rule only when retired, the expression join replaced by an indexed one-key lookup). Another
  rewrite would add risk to the Thursday 26/11 demo flows (publish / write / angle-gate 409s) for no measured gain. This
  lane adds integration tests for the Subject rule branches the S291 test did not reach and the live equivalence run.
- **Baseline: one sum per day on a raw `created_at` range (LATERAL), not one grouped scan of the window.** The S291
  statement grouped every ledger row of the window by `(created_at AT TIME ZONE 'UTC')::date`; on Dev (PG 15) the
  planner sorts the rows for that GroupAggregate, and for 28 days (~52,000 rows) the sort spilled (`temp_w` 176 blocks
  in the S291 evidence; the pre-S291 statement 292). The new statement joins each day to
  `SELECT sum(cost_usd) FROM llm_call_log WHERE created_at >= day 00:00 UTC AND created_at < next day 00:00 UTC AND
  <app> = $3 AND NOT EXISTS (rolled day)`: no expression on the column, an index range on
  `llm_call_log_created_id_idx` per day, no sort at all, and the rolled test is a one-time filter (a rolled day skips
  its ledger read). Local check on a 400,000-row synthetic ledger (work_mem 4 MB, jit off like Dev): 28 days read
  ~16,000 buffers instead of ~86,000 (the grouped form seq-scans the table) and take ~35 ms instead of 50–180 ms.
- **The app filter stays the coalesce Filter.** `coalesce(app, quality_signal ->> 'app', 'cis') = $3` is applied to rows
  the created_at range already selected; making it an index condition needs an index on the app (or the expression)
  of a ~300 MB ledger, which needs `CREATE INDEX CONCURRENTLY` in a no-transaction file (S291: the CIS integration
  replay cannot run one yet). The plan does not need it: the per-day range is the selective part. Same reasoning as
  the S291 review (an app-split UNION would scan the window twice).
- **Live proof without EXPLAIN.** The run-script PII guard (AA-969) plans every statement with
  `EXPLAIN (VERBOSE, FORMAT JSON) <statement>` first and refuses what it cannot plan, so an `EXPLAIN ANALYZE` statement
  is refused (S291 hit this and fell back to ECS exec). The AA-CIS-Infra scripts of this lane therefore measure each
  statement through `pg_stat_statements` deltas (calls, execution time, shared hit / read, temp written per call; each
  statement is wrapped so its query id is the script's own, never shared with app calls) plus client timings (p50 /
  p95) and per-relation scan counts from `pg_stat_xact_user_tables` (sequential and index scans per table: whether
  `raw_tours_key_expr_idx` and `llm_call_log_created_id_idx` were used and which tables were seq-scanned). Plans
  are not printed; the counts answer the Done-when (buffers, p95, temp).

## Changed (against the issue)

- No change to `REQUEST_TOURS_SQL` (see above); the old-vs-new comparison is pre-S291 (the W48 statement) vs today's.
- No new index (the per-day plan does not need one).
- The issue's "EXPLAIN (ANALYZE, BUFFERS) through run-script" became pg_stat_statements / pg_stat_xact counters
  through run-script, for the guard reason above.

## Tradeoffs

- The per-day LATERAL runs `baseline_days` small index scans instead of one scan; with a generic plan the planner
  estimates 1,000 days (generate_series), which only matters for JIT costing (Dev runs with `jit = off`, S257 probe).
- With the median cached per process and UTC day (S291), the baseline runs a few times a day; the change matters for
  the temp spill and the admin status page's first read, not for call volume.
