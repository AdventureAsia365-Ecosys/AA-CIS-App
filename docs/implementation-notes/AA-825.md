# AA-825 — Retention + rollups for log tables (S237, decision E3, data standards DM-7 / C5.4)

Two branches, per S237 D8 (migration file first, code after the apply):

- `feat/aa-825-mig-233` — `api/migrations/233_retention_rollups_sargable_usage.sql` + its test.
- `feat/aa-825-retention-rollups` (stacked on the first) — TTL job kinds, rollup writers,
  admin visibility, tenant usage reader on the rollup.

## Decisions

- **Migration number 233.** 229 (AA-817), 230 (AA-819), 231 (AA-791) are taken, 232 is reserved
  (AA-679, now unused, D1/D4). 233 is the next free number.
- **Plain `CREATE INDEX`, not `CONCURRENTLY`.** AA-CIS-Infra `db/run_migration.py` sends the whole
  file as one simple-protocol `conn.execute()`; Postgres runs a multi-statement simple query as an
  implicit transaction block and `CREATE INDEX CONCURRENTLY` refuses to run in one (205 was applied
  by hand for that reason). `SET LOCAL lock_timeout = '5s'` makes the file fail cleanly instead of
  queueing behind a long transaction. Builds take a SHARE lock (reads continue, INSERTs into that
  table wait ~1-3 s at today's sizes).
- **View rebuild guarded by `to_regclass('gold_aa_internal.tenant_tour_versions')`.** The CI test DB
  has no such table (no repo migration creates it), so 223 never applied in CI. Without the guard,
  233 would also roll back entirely in CI and the rollup tables would not exist for the retention
  tests or for `test_aa797` (which now reads the monthly rollup). The guard only skips the view;
  on Dev the table exists, so the view is always rebuilt (verify with `pg_get_viewdef` after apply).
- **Same numbers.** Each `date_trunc('month', col) = date_trunc('month', now())` became
  `col >= date_trunc('month', now()) AND col < date_trunc('month', now()) + interval '1 month'`.
  Same rows in the session time zone; NULL timestamps match neither form. Test compares the 223 and
  233 definitions on the same seeded rows, including the month boundary instants.
- **Archive format = JSONL.gz, not Parquet.** `pyarrow` is not in `requirements.txt` (pandas 2.2 does
  not pull it in; checked in the repo venv). Adding a ~40 MB wheel to the image for this was not
  worth it; the archive is `to_jsonb(row)` per line, gzipped. Converting to Parquet later is a
  mechanical Athena/Glue CTAS step (L6). DM-7.3 / C5.4a say Parquet: this is a deliberate deviation,
  flagged in the PR.
- **decision_log window = 180 days, labelled rows kept.** Confirmed in code:
  `shared/llm_client/decide.py` `CACHE_MAX_AGE_DAYS = 180` (`_CACHE_SQL`: `created_at > now() -
  make_interval(days => 180)`, `NOT cached`), in-process memo 6 h. A verdict older than 180 days is
  never served from the cache, so 180 days is the floor. Rows with `outcome IS NOT NULL` (human truth
  labels, AA-756 calibration, read up to 365 days by `/admin/decisions/outcomes/summary`) are never
  deleted. The window is imported from `decide.CACHE_MAX_AGE_DAYS` so it cannot drop below the cache.
  The data-standards table still lists decision_log as "decided in N4": the first live run is
  Nghiệp's approval (DRY RUN first, DM-7.2/7.5).
- **One job kind per table** (`retention_llm_call_log`, `retention_tenant_api_usage`,
  `retention_job`, `retention_decision_log`, `retention_cost_explorer_snapshot`), all
  `concurrency=1, background=True, max_attempts=2` (C5.4d). Separate kinds give separate history on
  the Jobs page and a per-table "last live run" for the 2x rule.
- **Mode decision (DM-7.2)**, `retention_job.decide_mode`:
  - manual run: DRY RUN unless `dry_run=false`; a live manual run needs `max_rows` (the count
    Nghiệp approved from the DRY RUN) and deletes at most that many, oldest first;
  - scheduled run: DRY RUN until a live run of the kind with the same windows has succeeded; then
    live, but HELD (nothing written, bell `platform.retention.held`) when candidates exceed
    `2 x` the last live run's deletions, with a floor of one batch (5,000) so a quiet previous day
    (0 rows) does not hold every run;
  - every run is capped at 200,000 deletions (40 batches); the rest waits for the next run.
- **Batches (C5.4c)**: <= 5,000 rows per transaction (the spec's limit; C5.4c allows 10,000),
  keyset on `(retention column, id)` (indexes added in 233), `FOR UPDATE OF t`, `statement_timeout`
  30 s, pause 200 ms, cursor stored in the job's progress and resumed on a retry.
- **Archive-then-delete in one transaction**: lock the batch, put the S3 object, DELETE by id, and
  roll back if the DELETE count differs from the archived count. An archive object never mixes two
  UTC months (exact `yyyy/mm` partition). The key carries the attempt's start time, so a retry of
  the same job never overwrites an object whose rows are already gone.
- **Rows referenced by a foreign key are never candidates**: the runner reads single-column FKs
  pointing at the table from `pg_constraint` and adds a `NOT EXISTS` for each. For `shared.job`:
  `acp_shared.content_piece.job_id`, `gold_aa_internal.tenant_tour_versions.job_id`,
  `shared.job.parent_job_id` (all `NO ACTION`; a plain DELETE would fail). Discovered at run time so
  the CI DB (no tenant_tour_versions) and future FKs work without code changes.
- **Rollups once per day / month, from complete raw rows**: cutoffs are UTC midnights; a day/month
  already present in the rollup is skipped (its raw rows may be partly deleted). Monthly rollup
  covers whole months up to the end of the cutoff's month (closed, 90 d > 31 d).
- **cost_explorer_snapshot**: rows with a strictly newer fetch of the same
  `(account_id, service, period_start)` — exactly what `cost_explorer._RANGE_ROWS_SQL` never reads.
  Rows fetched in the last day are left alone. No archive (DM-7 table).
- **Scheduling**: the existing ops-probe pattern (EventBridge Scheduler -> Lambda
  `aa-cis-dev-dfs-balance-check` -> secret-gated admin POST). New path
  `POST /admin/job-runner/retention/schedule` enqueues one `trigger=schedule` job per kind,
  idempotent per UTC day, nothing while a rerun wave is open. The Lambda's `_PATHS` needs the new
  path (AA-CIS-Infra, one line) — not in this repo.

## Tradeoffs

- JSONL.gz instead of Parquet (no pyarrow in the image) — readable with any tool, convertible later.
- Plain CREATE INDEX (short write lock) instead of CONCURRENTLY (would need a no-transaction mode
  in the Infra runner, N5/AA-807).
- 5,000-row batches with a 200 ms pause: the first backlog run of a table is slow-ish (~1 min per
  200k rows) but never holds a lock for long on the shared instance.
- Rollup NOT EXISTS per day/month instead of an upsert: a rollup is never "corrected" later; if a
  rollup row were wrong, fix it by hand from the S3 archive.
- The 2x rule compares with the last *live* run's deletions; a floor of one batch avoids holding
  every run after a zero day, at the cost of letting a jump from 0 to 5,000 through.

## Should know

- **decision_log cache TTL confirmed**: `shared/llm_client/decide.py:280` `CACHE_MAX_AGE_DAYS = 180`
  (DB cache, `NOT cached` rows only), memo `_MEMO_TTL_S = 6 h`. The window is tied to that constant.
- **llm_call_log readers with windows > 180 days** (`admin_llm_ops` spend pages, `days` up to 365)
  still read raw rows only. Once live deletion starts they show at most 180 days of raw history.
  Follow-up: read `shared.llm_call_daily` beyond the raw window (DM-7.4). The first live run of
  that kind is Nghiệp's call, so this can be sequenced.
- The view rebuild is skipped only when `gold_aa_internal.tenant_tour_versions` is absent (CI);
  after the Dev apply check `pg_get_viewdef('shared.v_tenant_monthly_usage')` contains
  `called_at >= date_trunc`.
- `idx_tenant_api_usage_tenant_id` (tenant only) is now a prefix of the new composite index;
  dropping it is a later cleanup after EXPLAIN on Dev confirms the planner uses the composite.
- The retention jobs, while queued/running, count for the Deploy Dev guard (a few minutes a day
  right after the 06:15 UTC ops probe). They are background kinds, so they also queue behind a
  place-pipeline backlog (BACKGROUND_MAX_RUNNING = 1).
- `s3://aa-cis-bronze-{acc2-id}/archive/` has no lifecycle rule yet (Infra; DM-7 proposes IA
  after 90 days). Bucket default encryption AES256 and versioning are on; objects are put with
  `ServerSideEncryption=AES256`. The ECS task role already has `s3:PutObject` on `*`.
- First runs (DM-7.2): for each kind, `POST /admin/job-runner/retention/run {"kind": ...}` (DRY RUN),
  read `candidates_total` in the job result, Nghiệp approves, then
  `{"kind": ..., "dry_run": false, "max_rows": <approved>}`. Only after that do the scheduled runs
  go live.
- **Review fixes (adversarial review, S237)**:
  - A retry of a *scheduled* run used to subtract the first attempt's deletions twice (its limit is
    this attempt's candidate count, already net of them), so it stopped short. `rows_left()` now
    treats a manual limit as the job total and a scheduled limit as this attempt's own, both under
    `RUN_MAX_ROWS` for the whole job (unit-tested).
  - `fk_refs()` now refuses (UnsupportedForeignKey) any FK onto the table that is multi-column or
    points at a column other than `id`: the NOT EXISTS guard only expresses `ref_col = t.id`, and an
    unguarded FK would make a DELETE fail half-way or, with ON DELETE CASCADE, delete child rows.
- **`shared.job` TTL bounds idempotency keys.** `queue.enqueue` dedupes on `idempotency_key` forever
  while the row exists. Deleting succeeded jobs after 30 d (failed 90 d) frees their keys, so the
  same key enqueued again later runs again instead of returning the old job: `a3_atomize:{version}`
  (re-publishing the same version > 30 d later atomizes again), `s1_rewrite:{tour}:{tier}:{batch}`,
  `s1_batch_ingest:{arn}`, `place_extract:...`. T2/T9 jobs that produced a version / piece are kept
  by the FK guard. Acceptable for the E3 windows, but it is a behaviour change to know about.
- **Old wave reports.** `services/waves/report.py` derives tour state from `shared.job` rows created
  in the wave window. For a wave older than 30 days the succeeded jobs are gone, so a recomputed
  report of that wave is no longer faithful (the stored `last_check` stays). Waves are closed within
  days, so only history pages are affected.
- **decision_log list page** (`GET /admin/decisions`, `days` up to 365) shows at most 180 days of
  unlabelled rows after the first live run (labelled rows are kept).

## S239 (16/10/2026) — manual override: prove rollup + archive on Dev now

Branch `aa-825-retention-manual-override`. Why: the S239 DRY RUN (root repo
`docs/audits/2026-10-16-S239-in-progress-audit/aa825-dryrun/`) found 0 rows older than the windows
in `llm_call_log` / `tenant_api_usage` / `decision_log` / `job`, so the rollup and archive paths
were never exercised on real data. Nghiệp's Dev rule: no waiting for data to age.

### Decisions

- **Override = an explicit cutoff, not a shorter window.** `POST /admin/job-runner/retention/run`
  with `older_than: "YYYY-MM-DD"` enqueues `{"trigger": "manual_override", "older_than", "dry_run",
  "max_rows"}`. The job uses UTC midnight of that date as the cutoff of every part instead of
  `now - window`. The policy windows (`policy.py`) are unchanged, so it is not a DM-7.5 window change.
- **Only the two rolled-up kinds** (`OVERRIDE_KINDS` = llm_call_log, tenant_api_usage: rows are
  summarised before they go). Refused for `retention_job` (deleting young succeeded jobs frees
  idempotency keys), `retention_decision_log` (the Jev verdict cache reads 180 days; deleting
  younger rows turns cache hits into paid calls) and `retention_cost_explorer_snapshot` (it already
  has real candidates under its own policy).
- **Cutoff at least 21 days old** (`OVERRIDE_MIN_AGE_DAYS`; 31 at first, lowered S239 so Dev can
  prove the path today: the oldest `llm_call_log` row is 2026-09-17, so 31 days meant waiting until
  19/10, and Nghiệp's rule is no waiting on Dev). Raw-only `llm_call_log` readers default to 7 or 30
  days or the current month (External Spend tree / daily / calls, Overview, Tenant 360, tenant
  list/billing view, cost guard): the 7-day windows never see deleted rows; a 30-day window may lose
  the deleted rows' raw figures (Dev only, ≤ 200 internal rows, about $1.10 on 17/09), which the
  daily rollup keeps. `tenant_api_usage` overrides also need a closed month (cutoff ≤ the 1st of the
  current month), checked in `override_cutoff`, because the monthly rollup only writes ended months.
- **Small, explicit live runs.** DRY RUN unless `dry_run=false`; a live override needs
  `1 <= max_rows <= 1000` and is refused above it (not capped), so a typo cannot become a big delete.
- **Refused for scheduled triggers.** `older_than` with any trigger other than `manual_override` is a
  NonRetryable error, the scheduler (`schedule_all`) only ever enqueues `{"trigger": "schedule"}`,
  and the API checks the same rules as 422s before enqueueing (the job re-checks with the DB clock).
- **Dev / test only.** Refused unless `ENVIRONMENT` is `dev` or `test` (unset = dev, the sentry.py
  convention; Terraform sets `dev` on the one ECS deployment, CI sets `test`). A future prod on acc2
  with another value refuses it. No env var change is needed.
- **Never "the last live run".** `_LAST_LIVE_SQL` skips `trigger = manual_override`, so an override
  neither unlocks scheduled live runs nor sets the base of the 2x growth rule. `GET /retention`
  shows it under `last.override` and `scheduled_mode` stays `dry_run`.
- **Logged** in the job result: `trigger: manual_override`, `override: {older_than, cutoff,
  policy_cutoffs, min_age_days, max_rows_cap}`, plus the usual candidates / rollup_rows /
  deleted_total / archived_total / per-part object_keys. Job `created_by = admin:<x-admin-user-id>`.

### Changed (applies to every live run, not only overrides)

- **Rollup coverage guard.** After `rollups.write`, `rollups.pending(cutoff)` must be 0 (every
  day / month older than the cutoff that has raw rows is in the rollup), else `RollupIncomplete`
  (NonRetryable) stops the run before the first DELETE. Catches an open month (the monthly INSERT
  skips months whose end is after now()) and any missed day.
- **Archive verified before DELETE.** `S3Archiver.put` sends `Content-MD5` (S3 rejects a damaged
  body) and then `HEAD`s the key: exact byte length and `rows` metadata must match, else
  `ArchiveNotVerified` inside the batch transaction, which rolls back (nothing of that batch is
  deleted). The ECS task role already has `s3:GetObject` (HEAD) on `*` (AA-CIS-Infra
  `modules/ecs/main.tf`), so no Infra change.
- Integration test for the admin usage reader pins its read connection to UTC (Dev RDS runs UTC; a
  local Postgres in Asia/Bangkok bucketed the raw month differently and failed the comparison).

### Tradeoffs

- **Raw-only llm_call_log readers DO change for windows that cover the deleted rows.** No admin page
  reads `shared.llm_call_daily` yet (DM-7.4 follow-up above). So a live override of
  `retention_llm_call_log` lowers, by exactly the deleted rows' cost / calls: External Spend for a
  custom window covering the deleted day(s), the all-time "total LLM cost" on the tenant detail page
  (`/admin/tenants/{id}/details`, `total_llm_cost_usd`), per-piece cost on the content-quality pages
  for pieces whose job ran that day, wave reports of waves on that day, and the Jev credit estimate
  only if deleted rows are `provider='typesafe'` on or after the first top-up date. Default windows
  (7 / 30 days, current month) do not change. The rollup keeps the exact totals of those days
  (verified by the run plan's SQL). `tenant_api_usage` has no such gap: its only multi-month reader
  (`/admin/tenants/{id}/usage`) already reads rolled-up months from the rollup; the other readers are
  the current month or the last hour.
- The override rolls up every not-yet-rolled day / month older than its cutoff (the normal invariant);
  with `older_than = oldest day + 1` that is exactly one day / one month.
- A day can end up partly in raw and fully in the rollup (max_rows smaller than the day). Correct
  for the retention invariant (that day is never rolled again, its raw rest goes at 180 days), but
  the future rollup-aware readers must take a day from the rollup whenever the rollup has it, not
  by "older than the window".

### Should know

- Archive format is still gzipped JSONL, not Parquet (see the first section).
- A late backfill into an already rolled-up day (like `reconcile_s224`) would not be rolled up again.
  The override makes this a bit more likely because it rolls up younger days (31+ instead of 180+).
- Run plan for the orchestrator: scripts in `.tmp-session/s239/aa825proof/` of the workspace
  (`aa825_override_ctx.py` read-only DB context via S3 + ECS exec, `aa825_override_run.py` admin API
  DRY RUN / live + page before/after); evidence goes to the root repo
  `docs/audits/2026-10-16-S239-in-progress-audit/aa825-override/`.
