## AA-330 Phần B: BUILD — runway_months() + parse_price() + finalize endpoint (08/08/2026)

Built exactly the 4 commercial decisions Nghiep confirmed (see STEP 0 section below for the

### New module: services/acp_shared/marketplace_estimates.py
- `runway_months(atom_count, posts_per_week)` — `floor(atom_count / (posts_per_week * 4))`, pure
  function. `WEEKS_PER_MONTH=4` from `allocator.py`'s own `weeks=[1,2,3,4]`. Unit-tested against all
  4 rows of the issue's example table (all match; the 5-tour/35-atom row only matches at the upper
  end of its "1-2 posts/week" range).
- `parse_price(price_raw) -> Optional[float]` (USD). FX table hardcoded, looked up 2026-08-08 from
  exchange-rates.org (page timestamped 2026-08-08 03:00 UTC), cross-checked against the Federal
  Reserve H.10 release (2026-08-03, week-ending 2026-07-31 close) — both agreed within ~2% on all 8
  currencies. **No live-rate mechanism exists — this table will silently drift stale. Flagged, not
  built.** Currency detection: explicit code/word (USD/GBP/EUR/INR/JPY/KRW/THB/TWD, "yen"/"baht") beats
  a bare symbol ($/£/€/¥/₩) — resolves real supplier noise like `"$23,300 TWD"` to TWD, not USD.
- Tiered-by-group-size (`"N-M Traveller : $X"` lines) takes the lowest **genuine tier**, deliberately
  excluding non-tier lines in the same field (`"Single Occupation: $X"`, `"Single Supplement: $X"`) —
  a real sample had a Single Occupation charge ($54) LOWER than every real tier ($492/$292/$244); took
  the lowest tier ($244), not the supplement. Adult/Child pattern takes the lower of the two (both are
  genuine bookable totals, unlike the supplement case).
- Two real regex bugs found and fixed during manual verification against live samples (not caught by
  the STEP 0 manual read, only surfaced once actual code ran against actual data): (1) an hourly-rate
  sample (`"1,000 yen/hour; 2,000 yen/3 hours; ..."`) was parsing as if 1,000 yen were the tour price —
  fixed by detecting a `/hour`/`/hr`/"per hour" suffix immediately after a match and rejecting it, since
  that's a per-unit-time rate, not a comparable tour price; (2) an unbounded `\s*` gap between currency
  marker and number let a stray `$` several lines away from any real price reach across a newline and
  grab an unrelated row-index number (`"1"`) from a different table row — fixed by restricting the gap
  to same-line whitespace only (`[ \t]{0,3}`, no `\n`). Both are regression-tested.

### Wired into api/routers/admin_marketplace.py
- `GET /catalog` now returns `price_usd` (nullable) + `price_available` (bool) per tour, plus
  `min_price`/`max_price` query filters — applied ONLY to `price_available=true` tours; a tour with no
  reliable price ALWAYS appears regardless of the filter (D2), never hidden.
- `POST /portfolios` accepts an optional `posts_per_week`; when given, `atom_snapshot.runway_months`
  is computed from the real re-counted `total_atoms` via `runway_months()`. Omitted -> stays `null`,
  never guessed.
- New `PATCH /portfolios/{portfolio_id}/finalize` — `draft` -> `finalized`, sets `finalized_at`.
  Rejects (409) an already-finalized portfolio rather than silently re-stamping it — protects the
  audit trail of when the commercial commitment was actually made.

## AA-330 Phần B: STEP 0 — price_raw survey + runway_months() proposal (NOT built, investigation only)

Full findings posted as a Linear comment (08/08/2026) — this section is a pointer, not a duplicate.
No code was written for Phần B in this pass (explicit task constraint) — only investigation.

### Key finding — atom depletion semantics (allocator.py, full read, not just line 184)
Atoms are **not** consumed/marked-used permanently. `_eligible_atoms()` only excludes `deleted=true`
(manual curation) or same-month/same-trip/same-channel reuse (`used_this_month`, a local `set()` reset
on every `compute_slot_grid()` call — never persisted, never carries across months). `cooldown_until` is
read (line 101) but has **zero write sites anywhere in the repo** (confirmed by grep) — always `{}` in
practice. `constants.py`'s `ATOM_COOLDOWN_WEEKS = 6` is defined but **never imported/used anywhere** —
a designed-but-never-wired 6-week rotation intent. `usage_log` is written (AA-361) but only read by
`quarter.py`'s big-rock TOFU-anchor selection, not the main per-slot allocator. Also: `n_atoms` per slot
is not fixed at 1 — blog slots can consume up to 4 atoms (`allocator.py:176`), facebook/tiktok exactly 1.

### Proposed runway_months() formula
`floor(atom_count / (posts_per_week × 4))`, `WEEKS_PER_MONTH=4` taken from allocator.py's own
`weeks=[1,2,3,4]` slot-grid convention (not invented). Reproduces 3 of 4 rows in the issue's own example
table exactly (7.25→7, 9.0→9, 12.857→12+); the 4th row only matches using the upper end of its stated
range (2 posts/week, not 1). This model assumes one-time-use, non-repeating atoms — a deliberate
conservative/worst-case choice for a customer-facing number, explicitly **not** what allocator.py
actually enforces (atoms are reusable). Flagged to Nghiep for confirmation before building.

### Proposed price_raw survey result
Only real tour-price column in the whole DB: `silver_aa_internal.raw_tours.price_raw` (TEXT), exposed via
`v_trip_registry.price_raw`. 534/793 (67%) non-null, 462 distinct values (mostly near-unique free text,
unlike duration_raw's ~6 recurring shapes). 8 currencies observed (USD/GBP/EUR/INR/JPY/KRW/THB/TWD),
plus tiered-by-group-size, adult/child, seasonal date-range tables, bare unlabeled numbers, and literal
non-numeric placeholders ("From $" with nothing after it, "On request"). Rough manual estimate (160
samples read, no parser coded/tested): ~50-55% of the full catalog could get one reliable filterable
price at v1; the rest returns `None`, never fabricated. Currency-conversion strategy (recommended: no
conversion, currency-scoped filter, to avoid a stale hardcoded FX rate) needs Nghiep's confirmation.

### Decisions
- STEP 0 already done + documented in the Linear comment (07/08/2026, S136) — not re-run. Only did the
  Phần A supplement STEP 0 (re-read `admin_atoms.py` + `(admin)/workspace/catalog/page.tsx` live) since

- Migration number: 097 (096 confirmed as latest via `ls api/migrations/`).
- New table `acp_shared.marketplace_portfolios` has **no `tenant_id` column and no FK to
  `shared.tenants`** — per STEP 0, a portfolio is chosen before a tenant exists (D4 Mode A / SSP:
  tenant licenses AA's platform-scoped catalog). N1 (AA-309) will read `portfolio_id` → `tour_ids` to
  seed `tenant_atom_state` after the real tenant is created — that's the only linkage, and it points
  the other direction.
- No RLS on the new table (unlike `acp_v2_runs`/`acp_v2_slots`, migration 096) — there is no
  `tenant_id` to scope a `tenant_isolation` policy on. Access control is the same `x-admin-secret`
  gate as every other admin router.
- `duration_min`/`duration_max`/`period_month` filters reuse `services/acp_planning/runway.py`'s
  `parse_duration_days`/`parse_period` as-is (already survey-built from a live 749-row scan of
  `duration_raw`) rather than writing a second parser — applied in Python after the SQL fetch since
  they're regex-based, not SQL-expressible. `destination` and `min_atoms` (atom-richness) are filtered
  in SQL. No `price` filter — Phần B, `price_raw` has never been surveyed the way duration/period were.
- `has_image` has no dedicated column anywhere in `raw_tours`/`published_tours`/`v_trip_registry`
  (checked) — derived from `bool_or(tour_atoms.media->>'has_photo')` per tour, the same live source
  `admin_atoms.py` already reads for atom-level photo presence. Real data, not fabricated.
- `atom_snapshot.total_atoms` on `POST /portfolios` is a fresh `COUNT(*)` against
  `acp_contract.tour_atoms` for exactly the submitted `tour_ids` at save time — never copied from the
  catalog list response, so a stale client-side number can't be persisted. `runway_months` and
  `posts_per_week` are always `null` — no formula exists yet (STEP 0 grep: zero hits for
  `runway_months`/`estimate_runway`/`months_of` anywhere in the repo).
- UI copies `(admin)/workspace/catalog/page.tsx`'s structure (`adminHeaders()` + fetch + filter bar +
  table), not its API or fields — that page serves a different purpose (S1 content-version history for
  already-onboarded tenants), confirmed 0 hits for "portfolio"/"prospect" in `AA-ACP-App/src`.

- SQL-filter (`destination`, `min_atoms`) + Python-filter (`duration_min/max`, `period_month`) split,
  rather than pushing everything into SQL or everything into Python: SQL for what SQL does natively

  parser and would otherwise mean duplicating regex logic in SQL. Dataset is catalog-sized (~793 rows
  max, `aa_internal` only), so a single unpaginated SQL fetch + in-memory pagination has no real cost.
- No finalize-portfolio endpoint — explicit task constraint (Phần B). Only `status='draft'` rows can
  ever exist from this code path today.
