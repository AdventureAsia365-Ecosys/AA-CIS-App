# AA-509 — Segment: schema + matching + T5 decompose upgrade (place/action split)

Sub-issue of AA-507. STEP0 evidence: `docs/claude_audit/AA-509-step0-schema-matching-investigation.md`
(read first — full schema/algorithm/JOIN evidence, not re-derived here). Build prompt chose
Hướng A (add `place`/`action` fields to T5 decompose) + the literal migration SQL from Linear.

## Decisions

1. **`tour_atoms.text` is kept, not dropped, and now derived** (`derive_atom_text()`, `services/
   acp_shared/atom_extraction.py`) as `f"{place} — {action}"`. Grep before touching anything
   (per house convention — see memory) confirmed `text` is read directly by
   `score_distinctiveness()`, T9's `content_seed` (`acp_angle_gate/service.py`,
   `acp_content_writing/service.py`), N7 research H2 titles (`acp_produce/research.py`),
   `slot_runner.py`'s citation map. Rewriting every one of those to read place+action separately
   was real, unrequested blast radius — the build prompt only asked T5's decompose OUTPUT to
   split place/action, not every downstream consumer's input shape. Real, disclosed trade-off:
   `text` used to be an LLM-written 1-2 sentence narrative; it is now a terser
   `"{place} — {action}"` join, which may read less naturally to a human reviewer or in
   generated content that quotes it verbatim — not measured here, flagged for a future pass if
   it turns out to matter.
2. **`content_hash_atom_id()` signature/argument order changed** to the build prompt's literal
   formula: `(owner_scope, tour_id, day, place, action)` — was `(tour_id, owner_scope, day,
   text)` under AA-508. Every call site (both the per-day and legacy whole-tour paths in
   `tenant_pipeline.py`) updated to match; the empty-day marker now hashes
   `("__empty__", "__empty__")` for (place, action) instead of a single `"__empty__"` text.
3. **`atom_segment` rows are UPSERT-only, never deleted** by `segment_matching.py` — required by
   `atom_segment_alias.segment_id_old`'s own FK to `atom_segment(segment_id)`: when two Segments
   merge, the id that gives way is recorded as an alias and has to keep existing as a row for
   that FK to hold (matches ADR 0002's own framing — "the id that gave way ... still resolves",
   not that it disappears). `atom_segment_member` (pure derived membership) IS fully
   DELETE+re-INSERTed per tenant every run — safe because every segment_id touched was just
   UPSERTed into `atom_segment` first. Diverges from the SQLite reference repo's own
   DELETE-then-reinsert of its `segments` table, which has no such FK to violate. Consequence
   (disclosed, not hidden): a segment_id that stops being derived at all (every one of its atoms
   soft-deleted, or re-atomized into different place/action) lingers forever as a zero-member row
   in `atom_segment` — small, permanent residue, same class of "old rows linger" gap AA-508 (and
   this repo generally) already accepts elsewhere for exactly this reason.
4. **`_mint()` (segment_id derivation) folds `tenant_id` into its hash input** — the reference
   repo's own formula is `sha256(place|verb)` alone (no tenant concept, one SQLite file per
   brand). Without this, two tenants both describing "walk the Nakasendo trail" would derive the
   IDENTICAL segment_id and collide on one `atom_segment` PK row — the exact collision class
   AA-508 already found and fixed for `tour_atoms.atom_id` (that task's Decision 2). Found and
   fixed during this build, not flagged by STEP0 (STEP0 covered the tour_atoms.owner_scope JOIN
   question but not this second, separate collision surface in the NEW `atom_segment` table) —
   confirmed real via `test_cross_tenant_same_content_does_not_collide_segment_id` and live
   Bedrock/DB verify.
5. **`is_alias` on `atom_segment_member`** kept as an unused reserved column, per the build
   prompt's literal schema — not populated by `segment_matching.py`. STEP0 flagged its semantics
   as unclear (segment-level vs. atom-level alias); the build prompt reverted to the literal
   Linear schema without resolving that question, so it's left exactly as specified and unused,
   not guessed at.
6. **STEP0's "Hướng A vs B" question is now settled by the build prompt** (Hướng A — real
   place/action fields). STEP0's "is_alias semantics" and "trigger-point cost" open questions
   were NOT re-litigated here — build prompt gave an exact schema and an exact trigger point
   ("chạy tự động ngay sau T5 hoàn tất"), so those are followed literally rather than re-decided.

## Changed

- `services/acp_shared/atom_extraction.py`: `SYSTEM_PROMPT` now asks for `place`/`action`
  (adapted from Ms. Thư's `src/aa_social/stages/atoms.py` extraction rules) instead of a
  combined `text`. New `derive_atom_text()`. `content_hash_atom_id()` signature/formula changed
  (Decision 2).
- `services/acp_produce/tenant_pipeline.py`: both `_atomize_per_day()` and
  `_atomize_whole_tour_legacy()` read `place`/`action` from the LLM response, derive `text`, and
  write both new columns; `_content_hash_atom_id()` call sites updated to the new argument order.
- `api/migrations/129_atom_segment.sql`: `tour_atoms.place`/`action` (nullable, no backfill —
  same precedent as migration 093's `itinerary_day`) + `acp_contract.atom_segment`/
  `atom_segment_member`/`atom_segment_alias`. Applied live (see below).
- `services/acp_contract/segment_matching.py` (new package): pure port of `derive_segments()`/
  `reconcile_ids()`/everything they call from `src/aa_social/segments.py`, adapted per Decisions
  3-4; DB-facing `run_segment_matching(tenant_id, pool)` wrapper.
- `api/routers/v1_tours.py::atomize_version()`: calls `run_segment_matching()` right after
  `run_t5_atomize()`, whenever `result["status"] != "skipped"` — best-effort (try/except +
  `logger.warning`, same pattern as the existing `escalate_t5_atomize_failure()` call just below
  it), placed BEFORE the `status == "failed"` 502 raise so a partial-day-failure run's
  successfully-committed atoms still get grouped.
- `api/routers/admin_atoms.py::list_atoms`: `LEFT JOIN` onto `atom_segment_member`/`atom_segment`,
  returns `segment_id`/`canonical_place`/`canonical_action` per atom (NULL when ungrouped).
- `frontend/app/(tenant)/portal/_components/AtomsTab.tsx`: group-by-Segment render layer
  (`groupBySegment()`, `SegmentGroup` collapsible header, extracted `AtomCard`) — pure
  client-side transform over the already-loaded/filtered atom page; star/delete/filter behavior
  unchanged, per-atom. Known limitation: a Segment whose members straddle two paginated pages
  renders as separate singleton rows on each page (not solved — out of scope, small volumes).
- Tests: `tests/unit/test_aa509_segment_matching.py` (new — 8 pure-function tests: no-merge,
  synonym-merge, place-mismatch, cross-tenant non-collision, reconcile stability, bridging-alias,
  empty-verb non-merge). `tests/unit/test_aa508_atom_content_hash.py` and
  `tests/unit/test_aa445_t5_distinctiveness.py` updated to the new place/action JSON contract and
  `content_hash_atom_id()` signature (their JSON mocks previously used `"text"` directly — this
  task's own SYSTEM_PROMPT change makes that contract stale, updating it is in-scope, not a
  deviation from any "don't touch this test" constraint).

## Tradeoffs

- `text`'s narrative quality (Decision 1) — not measured, flagged for later if it matters.
- `atom_segment` never-deleted rows (Decision 3) — small permanent residue over time, matches an
  existing accepted pattern in this codebase.
- STEP0 mục 7's O(n²)-per-tenant cost of `derive_segments()` recomputing over the tenant's WHOLE
  atom set on every T5 completion — not solved here, per the build prompt's own "known trade-off,
  không cần giải ở bước này" instruction.
- T6 grouping's pagination-boundary limitation (see Changed, AtomsTab.tsx) — not solved, small
  volumes make it low-impact today.

## Should know

- Migration 129 is **NOT** wrapped `CREATE TABLE IF NOT EXISTS` (unlike migration 128) — it only
  ever runs once; the live-verify script's own migration-apply step checks
  `shared.schema_versions` for `'129'` first and no-ops if already applied, same idempotency
  guarantee the `ON CONFLICT DO NOTHING` on the `shared.schema_versions` INSERT itself gives.
- `run_segment_matching()` scopes every read/write to one `tenant_id` — never touches another
  tenant's `atom_segment`/`atom_segment_member` rows. Verified live (STEPD below) that an atom
  with `owner_scope='platform'` is excluded outright (never appears in any `atom_segment_member`
  row), not merely deprioritized.
- The router wiring (`atomize_version()` calling `run_segment_matching()`) is exercised by the
  existing `test_aa469_viec1_t4_t5_split.py` suite (no new assertion failures — those tests don't
  assert on segment_matching's own behavior, they just don't break), not by a dedicated new
  router-level test; the DB-facing logic itself is proven by the live-verify below and the pure
  logic by `test_aa509_segment_matching.py`. A harmless `RuntimeWarning: coroutine ... was never
  awaited` appears in that existing test suite's output — an artifact of those tests' `pool`
  mocks not being shaped for a second, unrelated `pool.acquire()`/`conn.transaction()` call my
  best-effort try/except swallows; no test assertion fails, and real asyncpg's `transaction()` is
  a proper async context manager (confirmed by the live-verify itself completing cleanly).

## T6 UI (group-by-Segment) — confirmation + live-verify (2026-09-02, in response to the reopened
## comment)

The reopened comment's first ask was: confirm whether `t6-atoms/page.tsx` already has real
group-by-Segment, since it may have been built and simply not reported. **It was already built** —
in this same PR #268 (`5f6a740`), see "Changed" above (`AtomsTab.tsx`: `groupBySegment()`,
`SegmentGroup`, extracted `AtomCard`). What was genuinely missing was disclosure: the "Live Verify"
/ "Post-merge" sections above only ever exercised `run_segment_matching()` at the function/DB
level — the T6 render layer itself was never separately live-verified or documented with UI
states. This section closes that gap. **No new code was written for this section** — confirmed via
`git show origin/main:frontend/app/(tenant)/portal/_components/AtomsTab.tsx`, current as of this
check, unchanged since #268.

### UI states (documented against the actual shipped code, `AtomsTab.tsx`)

- **Loading**: `<LoadingScreen message="Loading your atoms…" />` — unchanged by AA-509, shown
  before the first `GET /admin/atoms` response.
- **Empty (0 atoms)**: `<EmptyState icon="🧩" title="No atoms yet" .../>` — unchanged by AA-509;
  Segment grouping only ever applies to a non-empty atom list, so an empty tenant sees the exact
  same empty state as before this feature existed.
- **Empty (0 Segments, atoms present)**: not a distinct UI state — `groupBySegment()` degrades to
  the pre-AA-509 flat list automatically (every atom has `segment_id: null`, so every row is
  `{kind: "atom"}`). No separate "no segments" banner; this was a deliberate render-layer decision
  (comment in the file, lines 18-23) rather than an oversight — confirmed correct behavior, not a
  gap.
- **Success, mixed Segments + ungrouped atoms**: a Segment renders as a collapsible card — gold
  header (`T.goldTint` background) showing `{place} — {action}` + a `"N atoms, same moment"` count
  badge + a `Layers` icon + a chevron toggle; expanded by default (`collapsedSegments` starts as an
  empty `Set`, i.e. "nothing hidden"); an atom with no Segment (`segment_id: null` — includes any
  `owner_scope='platform'` atom, since `run_segment_matching()` never touches platform atoms per
  STEP D above) OR a Segment with only 1 member on the current page renders as a plain `AtomCard`
  in its original list position, with no header — visually identical to how every atom rendered
  before AA-509.
- **Error**: unchanged — a failed `fetch` on `/admin/atoms` leaves `atoms` at its previous value
  (`.then(r => r.ok ? r.json() : null)` short-circuits on non-OK, `setLoading(false)` still runs in
  `.finally`) — no dedicated error banner, matches this component's pre-existing (pre-AA-509)
  error handling exactly; not something this section's scope changed.
- **Per-atom curation action (star/delete)**: identical code path (`toggleStar`/`deleteAtom`)
  whether an atom renders standalone or inside a `SegmentGroup` — `SegmentGroup` is a pure wrapper
  that maps its `atoms` prop to the same `AtomCard` component with the same `onStar`/`onDelete`
  callbacks. Grouping is display-only; curation state and the `distinctiveness` (HIGH/MED/LOW)
  badge stay attached to the individual atom object, never lifted to the Segment.
