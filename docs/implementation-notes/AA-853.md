# AA-853: migration 282, Dev's hand-made schema state in git

Issue: the nightly schema drift report (AA-CIS-Infra DB Schema Dump) must show 0 unmanaged objects. The replay side
(baseline for the lost AA-ACP-App lineage, order fixes, owner decisions) is in AA-CIS-Infra
`docs/implementation-notes/AA-853-schema-drift.md`. This file covers CIS migration 282 (S251 decision D2: Dev is the
truth; codify it).

## Decisions

- **One migration that is a no-op on Dev.** Every step reads the catalog first and acts only where the shape differs
  from Dev's; on Dev nothing is altered, rewritten or locked beyond catalog reads (proved on a Dev-shaped copy: a
  second apply holds no AccessExclusive / Share lock). On a database built from the files alone (CI, a fresh install,
  the drift replay) it converges to Dev.
- **What is codified (all found by the replay, each with its evidence in the file header):** hand-added columns
  (`pipeline_runs.llm_model / llm_provider / step_name`, `tenant_brand_rules.created_at` and its 104 copy,
  `raw_sources.file_hash`); nullability (`tenants.is_canary / skip_hitl` nullable, `tenant_brand_rules.brand_name`
  NOT NULL); index names and shapes Dev has (044's constraint as `uq_tenant_brand_name_version`, 048's index as
  `idx_generated_content_metadata_gin` with `jsonb_path_ops`, 123's partial unique index); the tables AA-598 G3 and
  AA-603 dropped by hand (archived scripts in the root repo); the v1 schemas `bronze/gold/ops/silver`; `raw_tours`
  text columns (varchar in 003) and `membership_plans.overage_*` `numeric(8,4)` (223 captured `numeric(10,4)`), with
  every view on them; the two `raw_tours` CHECKs in Dev's deparsed form.
- **Views on a changed column are saved, dropped and recreated generically**, not by copying their definitions into
  the file: definition (`pg_get_viewdef`), reloptions, owner, privileges, comments, in dependency order (depth =
  longest path). Copying 19 view definitions would freeze them in a file that may run after a later view change.
  Catalog views go through the X1 S22 recipe (GRANT CREATE … ; SET LOCAL ROLE catalog_owner; … ; SET LOCAL ROLE
  cis_owner; REVOKE): the role switches are literal (the DB Migrate lint refuses dynamic ones), the per-view DDL is
  dynamic inside DO blocks, and the state travels between blocks in the transaction-local setting `aa282.state`.
  Anything it cannot recreate faithfully (a materialized view, a view of another owner, rules / triggers / column
  grants on a view, a policy on a changed column, a cis_owner view on a catalog view of the set) is refused.
- **Hand drops refuse data.** A table Dev dropped is dropped only when empty (Dev dropped them at 0 rows); a v1 schema
  only when its tables are empty, the running role may drop it, and nothing outside the v1 schemas depends on anything
  in them (pg_depend: a view, a foreign key, a column of one of their enum types; refused otherwise). No CASCADE: the
  tables (together, for their foreign keys between v1 schemas), then their enum / domain types, then the schemas are
  dropped RESTRICT, so any other object in them (a function, a view) fails the file instead of vanishing (S251 review
  S3). Under DB Migrate those schemas are the RDS master's
  (001), 245 did not move them, so 282 (as cis_owner) leaves them with a NOTICE; recorded as an owner decision in
  AA-CIS-Infra `db/schema_drift_decisions.json`.
- **`public.checkpoint_migrations` is not touched**: LangGraph's bookkeeping, kept on purpose by 122; recorded as an
  exemption in the Infra decisions file instead.
- **No defaults on the added columns**: the live dump has no column defaults and no code reads these columns.

## Tradeoffs

- Generic view recreation is more code than a literal file, but it is exact (same definition text the database
  holds) and safe to run whenever; its post-check compares owner, options, columns and privileges with the saved
  state and RAISEs on any difference.
- The `membership_plans` narrowing rewrites a 4-row table on an old-shape database; values above 9999.9999 would
  fail (none exist: the plans are 4.0 / 3.0 / 2.0 / 0.0).
- The v1 schemas stay in a DB Migrate-built database (the master's); dropping them would need a master-run Infra
  `roles/` file for an empty, unused layer.
