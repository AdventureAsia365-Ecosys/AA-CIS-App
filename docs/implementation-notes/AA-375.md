# AA-375 — Real slot-runner glue (C1-F9), dev+verify scope only

STEP 0 (offline, prior to this session) + F6 cross-check already done, per issue instructions.
This issue's own scope: write the real glue function chaining C1-C3 -> E1 -> E2 -> E3 -> E4 ->
F1-F9 against a real `Slot`, and verify it end-to-end against real dev data. Explicitly NOT this
issue: router (HTTP), cron/EventBridge trigger — both deferred until AA-377 (Slot persistence)
and AA-378 (`acp_runs` table decision) land, because wiring an automatic trigger now would hand
`allocate_month()` a fresh non-stable `slot_id` on every re-run and produce duplicate content.

## Decisions

- **New file**: `services/acp_produce/slot_runner.py` — every existing module in this package
  (`adapt.py`, `generation.py`, `research.py`) already refers to "the not-yet-built slot-runner"
  by that exact term in its own docstring, so the name isn't a new choice, it's the name the
  codebase already uses for this gap.
- **`market` parameter (STEP 2 of the issue's own instructions)**: the issue text assumed
  `Trip.market` exists to resolve from. It does not. Confirmed by reading
  `services/acp_planning/models.py::Trip` (backs `acp_contract.v_trip_registry`, migration 078) —
  no `market` field — and by grepping `services/acp_planning/*.py`: `market`/`primary_market` is
  a caller-supplied parameter throughout N4-N6 (`runway_map(markets=...)`,
  `plan_quarter(markets=...)`, `allocate_month(primary_market=...)`), and `runway.py` states
  directly "no tenant market-config table in this schema yet". Not hardcoded, not invented:
  `run_slot_production()` takes `market: str` as a required caller-supplied parameter, same
  convention `run_slot_research()` and `allocate_month()` already use. Whoever builds the
  AA-377/378 trigger resolves it the same way `allocate_month()`'s caller already has to.
- **E2/E4 failure handling**: `generate_draft()`'s and `apply_faq()`'s own docstrings both
  explicitly name "the not-yet-built slot runner" as the intended catcher of
  `DraftGenerationFailed`/`FAQAnswerFailed`, instructing it to log to `unknown_ledger` and skip
  the slot. Implemented literally: both are caught here, logged via
  `research.log_unknown(..., kind="other")` (neither failure fits the four existing kinds), and
  the function returns `[]` rather than propagating or fabricating a partial Piece.
- **`compile_brief()` TOPIC REJECTED (`brief is None`)**: no extra logging added here —
  `compile_brief()` already writes the reason to `unknown_ledger` itself; `run_slot_production()`
  just returns `[]`.
- **Return shape**: `list[Piece]` — every Piece the slot produced (blog + up to 2 adapted channel
  pieces), each already run through `run_piece_through_produce_gates()` (status "passed" or
  "held", never "in_progress"). Packet assembly (`packets.py`, AA-367) is NOT called from here —
  stays the caller's own separate step, unchanged from AA-367.

## Changed

- New `services/acp_produce/slot_runner.py`: `run_slot_production(db, pool, tenant_id, slot,
  run_id, market, dfs_client=None) -> list[Piece]`.
- New `tests/unit/test_aa375_slot_runner.py`: 5 unit tests mocking every chained function —
  exercises only this module's own orchestration (TOPIC REJECTED short-circuit, E2/E4 failure ->
  `unknown_ledger` + `[]`, Piece fan-out into gates, `tour_id` resolution from `slot.trip_id`).
  Every chained function already has its own real-logic test file; these don't re-test them.
- No migration (no new DB shape — reuses `acp_deliver.pieces`/`acp_shared.unknown_ledger` exactly
  as the functions it calls already do).

## Tradeoffs

- **`pool` parameter is unused.** The issue's own function signature spec included it
  (`run_slot_production(db, pool, tenant_id, slot, run_id, market, dfs_client=None)`), but
  nothing in the real chain (`run_slot_research`/`build_outline`/`generate_draft`/
  `adapt_channels`/`apply_faq`/`run_piece_through_produce_gates`) takes a `pool` — every one
  takes only `db: asyncpg.Connection`. Kept in the signature per the spec rather than silently
  dropped (the caller may want the same `(db, pool, ...)` shape `packets.deliver_packet()`
  already uses), but genuinely not consumed today — flagged here rather than inventing a use for
  it. Worth confirming with whoever wires AA-377/378 whether this function should eventually call
  packet assembly itself.
- **No repair loop** — `run_piece_through_produce_gates()` is still called with the hardcoded
  `max_repairs=0` path (`pipeline.py`'s own current limitation, AA-367.md gap #4, not touched by
  this issue). A real piece failing any gate holds outright; this glue function does not retry.

## Should know

- This is glue only, not "real automation" — no router, no cron/EventBridge trigger (deferred to
  AA-377/378, per issue instructions). AA-375 stays open for that half; only the glue-function
  part is done here.
- `tests/verify_scripts/aa367_real_piece_chain.py` (AA-367's own test-only glue) is NOT changed
  and does NOT import this new module — it predates `slot_runner.py` and inlined the same chain
  by hand because this module didn't exist yet. Left as-is (still test-only, not run by
  pytest/CI).
### Live verify — 3 real attempts, real DataForSEO/Bedrock/Postgres, zero mocking

`tests/verify_scripts/aa375_slot_production_verify.py`, run via S3-mediated ECS exec
(`aa-cis-dev-cluster`/`aa-cis-dev-api`, 07/08/2026). Unlike AA-367's script, this one pulls a
real, non-hand-constructed `Slot` from `allocate_month()`, per this issue's own instructions.

- **Attempt 1** (script bug, not a production finding): hardcoded a single known-rich `TOUR_ID`
  from AA-367's own recon to seed `tenant_tour_pages` before calling `allocate_month()`. That
  tour did not make this run's real top-N `plan_quarter()` cut — `RuntimeError`, no chain call
  made. Fixed by seeding `tenant_tour_pages` for whichever trips `plan_quarter()` actually chose
  (`quarter_plan.trip_ids`), computed BEFORE the seed rather than assumed.
- **Attempt 2** (real, correct reject path): with the seed-order fix, `allocate_month()` produced
  a real evergreen blog `Slot` with real `atom_ids` + real `cta_target`. `run_slot_production()`
  called the real chain, correctly returned `[]`, and exited cleanly (no crash, no fabricated
  Piece). Root cause, confirmed by querying `acp_shared.unknown_ledger` directly:
  `kind=no_demand_evidence`, keyword = `"Walk alongside Cheonggyecheon Stream, an 8.4 kilometre
  water"` — **`allocate_month()`'s own `keyword_seed = chosen[0].text[:60]` (allocator.py, B6) is
  a truncated ATOM SENTENCE FRAGMENT, not a real search-intent phrase.** DataForSEO legitimately
  finds no search volume for it, so `compile_brief()`'s demand law (research.py, correctly, by its
  own rules) rejects the topic. This is systemic, not flaky: every real "evergreen"/"reactive_hold"
  `Slot` `allocate_month()` produces today carries this same kind of `keyword_seed`, so it hits
  this same reject deterministically, independent of anything in `slot_runner.py`. `kind=
  "campaign"` is the only real bypass `compile_brief()` offers today (`demand_reason = "slot
  kind=campaign"`, no volume required) — worth a real follow-up ticket on `allocator.py`'s
  `keyword_seed` construction (out of this issue's scope, not touched here).
- **Attempt 3** (real happy path, forcing a `kind="campaign"` Slot via a real matched trip name in
  `plan_quarter(specials=["Essential Korea"])` — not a fabricated Slot, a real trip that scored
  into `quarter_plan.forced_specials`): the full chain ran for real — `dfs_keywords_fetched`,
  `compile_brief()` real Brief, E1 outline, E2 `generate_draft()` (real Sonnet, `sonnet-4-6`,
  ~6.9s), E3 `adapt_channels()` (real Sonnet, facebook + tiktok, ~5.3s/~6.8s), `output_rules_
  applied`, real Nova Pro judge calls (F8/F9). `run_slot_production()` returned 3 real `Piece`s
  (blog, facebook, tiktok) — **confirmed independently persisted**: a separate read of
  `acp_deliver.pieces WHERE run_id = ...` returned exactly the same 3 `piece_id`s the function
  returned, proving `_persist_piece()` (pipeline.py) really writes through this new glue path.
  None reached `status="passed"` this attempt:
  - blog: held on `F1_grounding` (+ F3/F4/F8/F9) — model stated `1,000`/`18` not verifiably
    present in its cited atom's text.
  - facebook: held ONLY on `F9_brand_seo_audit_social` (`SUMMARY_OFF_BRAND`, `GENERIC_AI_WORDING`)
    — passed all 8 other gates (output_rules, F1, F2, F3, F6, F7, F8).
  - tiktok: held (gate detail not re-fetched — persistence + return-value match already
    confirmed for all 3).
  This matches AA-367.md's own already-documented finding (gap #4: no repair loop wired —
  `max_repairs=0` still hardcoded in `pipeline.py`) rather than indicating anything wrong with
  `run_slot_production()` itself — the glue correctly chained, gated, and persisted all 3 real

  AA-367 already needed up to 6 attempts to clear. Not re-chased further here — burning more
  live Sonnet/Nova/DFS calls to re-confirm an already-documented gap was judged not worth the

  All test-only rows (`tenant_tour_pages` x4, `acp_runs` x1, `pieces` x3) cleaned up after —
