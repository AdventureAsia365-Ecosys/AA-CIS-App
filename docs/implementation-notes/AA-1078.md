# AA-1078 — Make hidden failures visible (failed piece code, job cost from the ledger, flag_fix output limit)

Source: root audit `docs/audits/2026-11-10-S276-aa741-phase3/` §4.5.8, §4.7, §7.1, §9.7, roadmap items 3-5.

## Decisions

### (3) `shared.job.cost_usd` filled from the ledger
- **The column now holds the job's whole cost**: the handler's own spend (`ctx.add_cost`, e.g. DataForSEO) plus the
  sum of its `shared.llm_call_log` rows (linked by `llm_call_log.job_id`, which the worker binds around every handler,
  `call_log.bind_job`). Every write that saves a handler cost (`_finish`: succeeded / failed / stopped_budget /
  cancelled, `fail` to queued, `release`, the reaper's fail) stamps it in the same UPDATE.
- **No schema change.** The LLM part of the stamp is kept in `progress.cost_stamp.llm_usd` so that
  `handler cost = cost_usd - stamp` stays exact. `progress` and not `result`: a manual Retry and the retirement
  re-queue set `result = NULL` but keep `progress`. A column would have touched the shared job template (Booking and
  CRM job tables) and the hot `RETURNING *` claim (the AA-993 G1 note in `queue.py`).
- **No double count anywhere.** `JobContext.cost_usd` starts from the handler part (`queue.handler_cost`), so a retry
  or a release does not add the stamped part again; `set_progress` (hot path, no ledger read) keeps the stamp. The
  read side becomes `queue.JOB_COST_SQL` = handler part + the live ledger sum (list, sort, `/admin/job-runner/summary`),
  so a fire-and-forget ledger row written after the job ended still shows; `cost_ops` reads the handler part
  (`job_reported_cost_usd` keeps its meaning). A row written before this change has no stamp and reads as before.

### (1) A failed T9 piece fails its job, with a typed code
- **The job fails, at once.** When `run_write_background` stores the piece as `failed` (it catches its own exception
  and returns), `t9_write_job.run` raises `OutputFailed("t9_piece_failed", "<exception class>: <reason>")`, a
  `NonRetryable` subclass in `shared/jobs/registry.py`. `worker.failure_outcome` writes it as its code (no
  `NonRetryable:` prefix), so `shared.job.error` starts with `t9_piece_failed` (the list's `reason` filter and the
  failed counts per kind read it) and `job.result` = `{piece_id, piece_status: failed, failure_code, error_class}`.
- **No retry.** The piece is no longer `processing`, so a second attempt would only skip it; a re-run would also pay
  for a new write. The tenant's Retry (portal) is the retry. A re-run over an already failed piece (an admin Retry of
  the job) fails the same way instead of a green "skipped".
- **The piece status in the job views.** `progress.piece_status` is set at the end of every t9_write job and the Jobs
  list shows it next to the phase ("done · piece held"); a failed job shows its typed error; the drawer already lists
  the piece with its status ("Wrote").
- The exception class of e16fbbfb itself is in its `held_reason` (read-only query in the PR body).

### (2) flag_fix: an output ceiling, a lost fix is never a pass, the task in the ledger
- **Ceiling + effort as config rows** (CIS migration 396, its own migration-only PR, class contract): `t2_flag_fix` and
  `s1_flag_fix` on `haiku-5-5` get `max_tokens 16000` and `effort low`. 16000 = the S1 writer v2's ceiling for the
  whole page (a field is never longer than its page). The field rewrite and the meta re-repair set no max_tokens, so
  the row applies; the grounding sentence repair keeps its explicit 4096 (call site wins) and gets the effort only.
  The code does not need the rows (the gateway reads `stage_model_params` since 320): either merge order is safe.
- **A cut reply is not applied.** `flag_fix_node`: when the gateway hands back a reply stopped on its ceiling
  (`token_floor.is_cut_reply`, after its one truncation retry) nothing of it is applied (a json_repair salvage of a
  cut reply could store a field cut short). The node returns like a failed call (`fix_pass_applied` false: an A1
  flagged draft stays unpublishable, as `_is_publishable` already rules) and records
  `fix_not_applied = {reason: reply_cut | error, stage, fields, stop_reason}`; the exception path records it too
  (`reason` = `reply_cut` when the route ended on cuts, `token_floor.is_cut_failure` / `route_ended_on_cut`).
  `fix_not_applied` is a `ContentState` key (AA-209 gotcha) and `_rewrite_tour` returns it.
- **T2 does not report passed over a lost fix.** `t2_rewrite_job._rewrite_and_save`: a kept draft with
  `fix_not_applied` saves `qa_status = escalated`, `qa_auto_passed = true` and puts the record in `job.result`
  (`fix_not_applied`). The version status rule (score-based) is unchanged; no review-queue row (no QA issue to list).
- **The task in the quality signal.** `call_log.bind_task(task)` (a ContextVar like `bind_job`): every ledger row
  written while bound gets `quality_signal.task` unless it names one, including the gateway's own cut / attempt /
  billed-unusable rows (the `task=unknown` rows of the audit). Tasks: `field_fix` (flag_fix_node), `meta_rerepair`
  (`_rerepair_meta`, also on the T2 linear path), `sentence_repair` (`grounding.repair`, also T3's repair). The
  caller rows also state the task explicitly.

## Tradeoffs
- The column is exact at the moment of the stamp; a ledger row written later (fire-and-forget) or a re-priced row is
  in the read side only. The live check compares the column with the ledger for jobs of the last 24 h.
