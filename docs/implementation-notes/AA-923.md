# AA-923 — Writing memory: labels for T2/A1, offboarding deletion, retire the old lesson paths

Covers WM-32 (labels on T2 versions and A1 content), WM-33 (offboarding deletion of learned tenant data) and WM-34
(retirement of `shared.pipeline_lessons`, `acp_shared.acp_output_rules`, `/v1/rules` and the dead rule adapter code).
Spec: root `docs/audits/2026-10-20-S245-writing-learning-loop/issues/README.md` Group 9.

## Decisions

- **WM-34 is two PRs, code first.** The code PR removes every reader and writer (the `/v1/rules` router, the
  AA-132 lessons loader and write-back, `api/services/acp_post_processor.py`, `services/acp_produce/rule_adapter.py`
  and their tests). A separate migration-only contract PR then quarantines both tables in `retired` (DM-3.9: candidate
  → quarantine → drop after >= 14 days), so the deployed code never reads a table that is gone. The drop itself is
  a later migration (after the 14 days and a second DRY RUN), not part of this issue's code.
- **Quarantine, not DROP, in this issue.** The spec says "drop tables"; the data standards (DM-3.9) and the
  AA-850 precedent (CIS 294 → 296) require the reversible quarantine step first. "Schema reference PR shows the
  tables gone" is met for their source schemas the night after the quarantine apply.
- **`api/core/staff_secret.py` stays.** Its only router was `/v1/rules`, but it is a staff/machine auth guard, not
  a lesson path, and AA-923 does not name it. Deleting an auth module is a separate, reviewed auth change. The S241
  route-auth tests keep exercising it on a probe router with the old `/v1/rules` shape.
- **The `/v1/rules` prefix stays in `STAFF_PATH_PREFIXES`** (and in the BFF mirror `STAFF_API_PREFIXES`), like
  `/v1/social` after AA-850: the prefix is fail-closed staff-only, so a route added there by mistake later still
  goes through the staff middleware and POLICY. Only the POLICY entry of the removed PATCH route goes. After deploy
  `/v1/rules` answers 404 (no route); a unit test checks the real app.
- **`flag_fix_node._write_lessons_safe` stays as a logging no-op** (the AA-729 harness and unit tests patch it by
  name); `write_lessons_log` and the frozen flag are gone.
- **`scripts/aa729/select_samples.py` keeps its `lessons_text` parameter** fixed to `""` so the frozen golden-set
  samples stay byte-reproducible.

- **WM-32: a sibling table, not a widened key.** `acp_shared.content_label` (CIS 315, expand) holds T2 version and
  A1 rewrite labels with the same CHECKs as `content_piece_label`. Changing 231's primary key to a subject type would
  be a contract change on a live table and touch every T9 reader (KPIs, disagreements, the list filter); the spec
  allows "a sibling table with the same CHECKs", and "existing T9 labels unchanged" is then true by construction.
- **No FK on `subject_id`.** `gold_aa_internal.tenant_tour_versions` is live-only (the CI replay lacks it), so an
  FK would not replay. The row carries the subject's `tenant_id` instead: the AA-839 erasure deletes it with the
  tenant (inventory entry), and rule a of the RLS catalogue gets its `tenant_isolation` policy.
- **A1 = one `silver_aa_internal.generated_content` row** (the S1 output the Rewrite tab shows), labelled in any
  status; a T2 version is labellable unless `pending` / `failed` (no finished text). The text hash: T2
  `rewritten_content::text`, A1 the rewrite fields joined with newlines.
- **One label form for all three subjects.** `PieceLabel.tsx` now has `SubjectLabelSection` next to
  `PieceLabelSection`; both use the same form, list and load states. Admin role only (backend, BFF write rule
  `content-quality/a1-content/`, the page); T2 writes already sit under `content-quality/tour-versions/`.
- **WM-33 needs no new deletion code.** The AA-839 `data_erasure` job is the one offboarding function: every
  learned-writing store (signals, tenant rules incl. preference summaries, exemplars and their release links,
  releases, shadow outputs, keeps, disagreement items, and now the T2 labels) is in `services/erasure/inventory.py`,
  and its completeness test fails CI on a tenant-keyed table without an entry. What WM-33 adds is the proof: an
  integration test seeding one row per store for two synthetic tenants (DRY RUN counts and writes nothing; the apply
  deletes all of them; the other tenant keeps every row), and the live DRY RUN + apply on Dev by the orchestrator.
- **AI Use Register.** It does not exist yet (AA-804). The stores and the D16 exception (legacy before/after text in
  the append-only `acp_shared.audit_log` stays) go into the compliance register (root `docs/legal/register.md`,
  a RoPA row) in a root docs PR; AA-804 moves it into the AI Use Register when that is built.

## Changed

- Removed: `api/routers/v1_rules.py`, `api/services/acp_post_processor.py`, `services/acp_produce/rule_adapter.py`,
  `services/content_generation/pipeline_lessons.py`, their tests (`test_aa363_rule_adapter.py`,
  `test_acp_post_processor.py`, `test_output_rules.py`, `test_aa915_pipeline_lessons_frozen.py`).
- `api/main.py`: the `/v1/rules` router is no longer included. `api/core/staff_authz.py`: the PATCH POLICY entry
  removed; prefix comment updated. Route-policy snapshot regenerated (two `/v1/rules` rows gone).
- The three S1 prompt builders (`admin_pipeline._execute_run_tour`, `s1_batch._load_prompt_state`, the AA-645
  shadow script) no longer call the lessons loader (it returned "" since AA-915: prompts are unchanged).
- New guard `tests/unit/test_aa923_retired_lesson_paths.py`: no runtime file queries either table, the four modules
  stay gone, the lessons hook sends no SQL.
- `CONTEXT.md`: the "frozen predecessor" paragraph is now "retired predecessor".

- WM-32: migration `315_content_label.sql` (expand); four routes in `api/routers/admin_content_quality.py`
  (`GET/POST /tour-versions/{id}/label`, `GET/POST /a1-content/{id}/label`); POLICY entries (GET tenant.read, POST
  quality.write); readiness `REQUIRED_CIS_SCHEMA = 315`; erasure inventory entry; frontend `SubjectLabelSection` in
  the T2 version drawer and the tour panel's Rewrite tab; BFF write rule; EN + VI messages.
- WM-33: `tests/integration/test_aa839_erasure_job.py::test_offboarding_erases_every_learned_writing_store_and_no_other_tenant`.
- Tests: `tests/unit/test_aa923_subject_labels.py`, `tests/integration/test_aa923_migration_315.py`.

- WM-34 quarantine PR (contract, MIG-4): `api/migrations/316_aa923_quarantine_lesson_tables.sql` moves both tables
  to `retired` (the CIS 294 shape: guard, move, comment with the way back, revoke every grant, post-check). Its guard
  accepts a table that is absent (the CI replay has no `acp_output_rules`) and refuses a view, an inbound FK or an
  output rule of a non-platform tenant. `tests/integration/test_aa923_migration_316.py`; the 296 test ignores the
  later quarantine; `rls_catalogue_rules.py` allowlists `retired.acp_output_rules` next to the old key (AA-CIS-Infra
  byte copy `db/rls_catalogue_rules.py` in its own PR, after this one merges).
- The erasure inventory keeps its `acp_output_rules` entry until the drop migration: after the quarantine the
  planner reports it as missing (harmless), and removing it earlier would make the Dev erasure see an
  unregistered tenant-keyed table between the code deploy and the 316 apply.

## Tradeoffs

- Keeping `staff_secret.py` leaves a guard with no router; the alternative (delete it now) widens a lesson-retirement
  PR into an auth change. Follow-up noted for the orchestrator.

- The light-edit share / minutes-to-fix KPIs (AA-922) still read T9 labels only; adding T2 / A1 labels to them is a
  KPI change for a later release train, not part of "labels exist".
- No FK means a label can outlive a deleted T2 version (only the erasure deletes versions today, and it deletes the
  labels with the tenant).
