# AA-1154 — CIS admin assistant (ops assist)

Tech lead decisions AI1-AI12 (S285 advisory, root `docs/audits/2026-11-19-S285-session/advisory-ai-assistants.md`,
sections 3-8). One assistant inside the CIS admin: evidence, rule-based action cards, a plain-words Summary. Phases:
A0 (this note) evidence + action catalogue + playbooks, no LLM; A1 LLM ranking and explanation + buttons; A2 predicted
against actual outcomes and the digest paragraph.

## A0 — evidence, action catalogue, playbooks (no LLM, 0 USD)

### Decisions

- **No table in A0.** The cards are computed on read from existing sources; nothing is stored. The advisory's
  `ops_incident` / `ops_assist_run` tables belong to A1/A2 (a card that was executed, its predicted and actual
  outcome). The only migration is CIS 481: twelve settings.
- **The action catalogue is a code registry, served read-only** (`api/services/ops_assist/catalog.py`,
  `GET /admin/ops-assist/catalog`), deny by default like the route authz: each row names the API it calls by its
  `POLICY` key, and the unit test checks the key exists with the capability the row lists (and the dry run and way
  back routes). It holds no threshold.
- **Every limit is a setting** (CIS 481, area `ops`, maker-checker, EN + VI guides; `shared/ops_assist_settings.py`):
  evidence window 30 min, changes window 120 min, refused calls that open a signal 3, throttled calls that open a
  signal 3, spend spike factor 3x, days of the usual-spend median 7, smallest spend per hour that can be a spike
  0.10 USD, stages that make an action wide 5, the most an R1 action may cost 0.10 USD, outcomes before a track
  record 5, card lifetime 30 min, shortest R3 reason 20 characters (AI7). The throttle trigger, the spike floor and
  the baseline days were split out in review: the throttle signal first reused the refusal trigger and the spike
  floor the R1 money cap (an admin tuning one would silently move the other), and the baseline was a 7-day constant
  also written into card copy. The copy now names the snapshot's own number (`evidence.baseline_label`).
- **Risk by rule** (`risk.py`): the highest of direction (read R0, simulate R1, tighten R2, reroute / rerun / loosen
  R3; a limit change decides tighten or loosen with `settings_registry.loosened()`), scope (app R2; all, or a
  connection / route serving at least the wide-scope setting of stages, R3; a read or a simulation is never raised by
  scope), money (cents up to the small-money setting R1; paid above it or with no estimate yet R3) and reversible (no
  R3). Copy-only actions (ECS rollback, the worker's desired count, an AWS Support case) are R4.
- **Confidence has four sources and names its basis**: `code` (a fixed consequence of the API), `measured` (the ledger
  of the window, a DRY RUN estimate, a preview), `history` (right k of n, shown only from the history setting; A2
  records outcomes, so A0 always shows `not_enough_data` for the track record), `not_enough_data`. Never a percentage.
- **Signals beyond the Needs-attention list.** The status page does not list an AI connection refusal (the breaker's
  `llm_circuit_open` bell is not a `platform.ops_check.*` bell). The assistant raises its own signals from the breaker
  and the ledger (`llm-conn-<key>`, `llm-throttle-<key>`, `llm-spend-<key>`, `GET /admin/ops-assist/signals`) and the
  page shows them under the attention list ("The assistant also sees") with the same Actions button. A model the
  connection is known to be refused for (AA-900 expected refusal, acc3's GPT models) never opens a signal.
- **Evidence = the page's own build.** The cards endpoint calls `ops_status.build_status` with the page's range, so the
  item ids, numbers and the CloudWatch Redis cache are the page's (no new AWS cost). Each other source (breaker rows,
  `shared.llm_call_log` of the window and its hourly median over the baseline-days setting, the route config and the versions of the changes
  window, failed `llm_access_denied` jobs, oldest due queued jobs, open waves, the newest probe job, `acp_shared.ops_event`
  of the changes window) is read on its own; a failure is listed under `unavailable`, never read as healthy.
- **Business owner** (`shared.admin_users.is_business_owner`, CIS 462; the role is admin): the API answers
  `audience: "summary"` with the Summary only, no cards, no evidence (AI10).
- **Playbooks**: `llm_access_denied` (account level first: the probe card ranks first, the 29/10 lesson), `llm_throttled`,
  `llm_cost_spike`, `queue_stuck`, `server_errors`, `generic`. Unmet preconditions rank after met ones, copy-only last;
  a card without an evidence link is dropped; "deliberately not proposed" lists the advisory's three (switch the
  refused connection off by hand, reset the anomaly breaker, retry every failed job).

### Changed (against the issue / advisory)

- The advisory named `shared.ops_event`; AA-1140 shipped it as `acp_shared.ops_event` (DM-1.5). A0 reads that.
- The advisory's A0 also listed `ops_incident` / `ops_assist_run` and the queue-stuck live drill; tables moved to A1/A2
  (nothing to store without execution). The queue-stuck playbook (an unregistered kind gets a cancel card) is in A0.
- `cognito-login` playbook: no signal source on the status page yet; not in A0.
- The panel is read-only: the "Preview / Execute" buttons, `X-Suggested-By` and the R3 reason box are A1.

### Tradeoffs

- The cards endpoint rebuilds the status page (about 15 small DB reads + the cached CloudWatch part) on each open; a
  drawer opens rarely and caches its answer 60 s in the page.
- The usual-spend median (7 days by default) reads `shared.llm_call_log` grouped by connection and hour (a range scan on the created_at index,
  a few thousand rows a day on Dev).
- The replay snapshot is a hand-written JSON of the 29/10 facts on today's routes (connection, model and stage keys from
  the repo, counts invented to the incident's scale); it is not a DB dump.

## A1 — the model ranks and explains, Analyse, auto-analysis, the look-up panel (S292)

### Decisions

- **One stage, one cap, one kill switch.** CIS 487 (migration-only PR, contract) seeds `shared.llm_role_config` stage
  `ops_assist` (role writer, haiku-5-5, no fallback, no shadow, scopes `aws_only` + `vendor_direct`, deadline 25 s,
  degrade `basic_narration`, pii_class content, free_text true) and `shared.spend_budget` `llm / stage:ops_assist`
  10 USD a month, hard stop, alert 80 % (AI3). "Deep analysis" is the same stage with `model_tier` = the setting
  `cis.ops.assist_deep_model` (default sonnet-5-5), so the kill switch, the data scope, the month cap and the provider
  order apply to it too and its ledger rows carry the same stage.
- **Four A1 choices are settings (review, S292 fix pass)**, seeded by CIS 487 (maker-checker, EN + VI guides,
  `shared/ops_assist_settings.py`): `cis.ops.assist_auto_severities` (list of sev1 / sev2 / sev3, default
  [sev1, sev2], empty = no automatic analysis), `cis.ops.assist_auto_incident_gap_min` (240), `cis.ops.assist_deep_model`
  (enum haiku-5-5 / sonnet-5-5 / opus-5-5, default sonnet-5-5) and `cis.ops.assist_lookup_windows_min` (list of 15, 30,
  60, 120, 180, 360, 720, 1440; default [15, 60, 360, 1440]). The enum's allowed values are static in the seed (the
  compiled-defaults parity check reads the seed JSON, so it cannot query the catalog at seed time); the preflight
  checks the chosen key is still an enabled catalog chat model before each Deep call and uses the stage route when
  it is not (`llm.deep_fallback`, a line in the drawer).
- **No personal data or secrets in the prompt.** The item detail (job last error, alarm description, ECS rollout
  reason) is free text. Every text of the bundle and of the look-up rows goes through `explain.scrub`: connection
  string credentials and AWS key ids, then the gateway's `free_text_scrub.scrub_text` (e-mails, phones, tokens, key
  parameters, cards, ids). The stage row also says `free_text`, so the gateway scrubs the whole prompt again before any
  attempt and refuses the call when the scrub fails (fail closed).
- **A read-only session asks no AI.** The E2E identity, a viewer and view-as get 403 on every POST, so the status page
  waits for `GET /admin/session` (`useSessionAccess().settled`, new) and sends no analyse / auto / phrase POST for a
  read-only session (`_status/useMayAsk.ts`); Deep / Again / Phrase sit behind `<WriteOnly>`; the rule-made cards
  still show. The UI smoke asserts it on `/admin/overview` for a read-only admin run.
- **Role `writer`, not `decide`.** The row CHECK of `llm_role_config.role` allows writer / judge / validate / embed;
  `decide` is the Jev seam (ADR 0009 D3). The call writes a ranking and short texts: the generate seam.
- **Preflight before every call** (`explain.PREFLIGHT_SQL`): no call while the stage row is missing or switched off or
  the stage has no hard-stop month cap. This replaces a readiness raise for 487: with 487 not applied the page simply
  shows the rule-made cards with "not set up yet", never a call on gateway defaults without a cap.
- **The model can only reorder and add words.** One fenced JSON bundle (`services/ai_safety/prompt_fence.fence`,
  always on for this new prompt), a JSON schema answer, `validate()` keeps known card ids and evidence ids only, the
  ranking moves cards inside the rule's groups (met preconditions, unmet, copy-only last), an explanation without a
  known evidence id is dropped, a sentence with a probability is removed. Unknown ids are recorded in
  `llm.dropped_ids`. Card risk, calls, way back and approval are never touched.
- **Cache = card lifetime** (`cis.ops.assist_card_ttl_min`, Redis): the same item, range and depth reuse the model's
  part for that long (cards keep ids, so explanations follow their card). "Analyse again" (`fresh`) asks again.
- **Auto-analysis once per incident (AI6)**: `POST /admin/ops-assist/auto`, called by the status page every 5 minutes
  while open; the server picks open Needs-attention items and assistant signals of the automatic severities and sets
  a Redis marker per item id with NX (first caller wins, nobody pays twice). The marker is keyed on the item id alone:
  for the health-* and svc-* items `since` is the newest sample's time (it moves every sampler tick), so the first
  build keyed on it paid once per item every card lifetime (review finding). The marker lives
  `cis.ops.assist_auto_incident_gap_min` (never below the card lifetime) and is renewed while the item stays open.
  Without Redis nothing runs automatically. Keying on AA-1142's `ops_incident` id is a follow-up once that table ships.
- **Look-up panel** "what changed in the last …" over the windows of `cis.ops.assist_lookup_windows_min` (minutes; the
  API refuses another window with 422 `window_not_offered` and lists the offered ones in `windows`; the page builds its
  choices from that answer and has no window list of its own): the status page's own change list
  (`ops_status.changes.collect`) plus alarms and service drops from `acp_shared.ops_event`; a rule-made headline and
  lines, $0. "Phrase with AI" sends the same rows (never who made a change) and keeps the answer only when it cites a
  row. Nothing changed = no call.
- **Every limit stays a setting or a technical constant**: display lengths and the output ceiling (8192, the S271
  effort floor) are `technical-constant`; `lookup.DEFAULT_WINDOW_MIN` (60) only picks which offered window opens
  first ("the last hour", the panel's question) and falls back to the shortest offered one.

### Changed (against the issue / advisory)

- The "Preview / Execute" buttons with `X-Suggested-By` (advisory A1) are not in this slice: the orchestrated scope
  for S292 was ranking, explanation, Analyse, auto-analysis and the look-up panel, with no execution. Follow-up.
- The row button reads "Analyse" (was "Actions") and opens the same drawer: the rule cards at once, the AI's ranking
  when it answers.
- No `ops_incident` / `ops_assist_run` table in A1: the cache and the auto marker live in Redis; the ledger row is the
  durable record of each call. The outcome table belongs to A2.
- The prompt is not in the prompt register yet (`prompt_versions.json` + `shared.prompt_version`): the ledger rows
  carry `quality_signal.prompt_version = ops_assist.v1`. Follow-up.

### Tradeoffs

- The deep model is a setting on the same stage, not a second stage row: one stage keeps one month cap, one kill
  switch and one ledger stage as AI3 asks.
- The code PR is stacked on the migration branch (unlike the usual MIG-4 split): it reads the CIS 487 settings, and
  the settings lint (every read key compiled) and the seed parity check (compiled defaults = the migrations) need the
  migration, `compiled_defaults.json` and `shared/ops_assist_settings.py` on the same branch. After the CIS migration
  batch merges, the wave tool merges main into it (it carries a migration main already has) and gates the new head.
- The automatic analysis runs from the open status page, not from the worker: building the status page needs the
  API's Redis cache and the caller's token for the other apps' health. An incident nobody looks at is analysed the
  first time someone opens the page.
- Each Analyse rebuilds the status page twice (the GET cards and the POST analyse), cached CloudWatch part.
