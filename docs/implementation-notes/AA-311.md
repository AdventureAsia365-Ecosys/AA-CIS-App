# AA-311 — Retire `_start_pipeline()` call in `process_file()`

## Decisions

- **Delete the call outright, don't wrap in try/except.** `_start_pipeline()` has exactly one
  side effect (`_sfn().start_execution(...)`) and no other purpose — per the no-dead-code rule,
  a bare removal beats a caught-and-logged call that still does nothing useful.
- **Keep the `_start_pipeline()` function definition.** It's the only call site (verified via
  repo-wide grep), so nothing else breaks by leaving it, and it documents the Step Functions
  input shape (`$.tours` Map state contract) if AA-182 is ever revisited. Marked with a
  `# UNUSED as of AA-311` comment pointing back at the AA-182 decision so nobody re-wires it
  without re-reading that context.
- **Drop `sfn_triggered` from the response dict**, not just the call. It was derived from
  `bool(sfn_arn)` (env var presence), which is now meaningless — no trigger ever fires,
  configured or not. Leaving the field in would silently lie to API consumers.

## Changed

- `services/ingestion/handler.py`: `process_file()` no longer checks `STEP_FUNCTIONS_ARN` or
  calls `_start_pipeline()` after the `raw_tours` INSERT succeeds. `_start_pipeline()` itself is
  untouched (just annotated as unused).

## Tradeoffs

- Not migrating to a working Step Functions trigger, per AA-182 (state machine
  "aa-cis-dev-pipeline" is deployed but bypassed by design — CIS rewrite runs directly via
  `_rewrite_tour()`, no SM involved). AA-311 is scoped to removing the erroneous call, not
  re-architecting the trigger path.
- `_sfn()` / `_sfn_client` boto3 helpers are left in place even though nothing calls them at
  runtime now — they're only reachable via the unused `_start_pipeline()`. Removing them would
  mean deleting `_start_pipeline()` entirely, which goes beyond what was asked.

## Should know

- Root cause (verified via real CloudWatch log, stream
  `api/api/4b84257deeff48b9b228c974a1480f88`, ~04:59:25 UTC 2026-07-20): ECS task role lacks
  `states:StartExecution`, so the post-INSERT trigger call raised `AccessDeniedException`, which
  propagated out of `process_file()`'s `try` block and turned a successful DB write into a 500.
- New regression test: `tests/unit/test_aa311_no_step_functions_call.py` — sets
  `STEP_FUNCTIONS_ARN` to a real-looking ARN (the condition that used to be enough to trigger the
  bug) and asserts neither `_start_pipeline()` nor the boto3 `start_execution` call ever fires,
  and that the success response no longer carries `sfn_triggered`.
- AA-182 stays open in Backlog — this issue only retires the dead call, it doesn't resolve the
  broader "SM deployed but bypassed" tech debt.
