# AA-917 — Writing memory: rule store and the mining job (WM-09..WM-14)

Writing memory, Group 3 (root `docs/audits/2026-10-20-S245-writing-learning-loop/issues/README.md`), under app ADR 0010.
Delivered in slices: the CIS 280 storage PR (WM-09, this branch), its Infra byte copy, then the code PR (WM-10 backfill,
WM-11 fact filter, WM-12 miner, WM-14 admin API), stacked on the AA-916 capture branch.

## Decisions

- **Migration key 280** (S250 schedule: 279 is reserved for AA-851). Apply after 279 so the readiness check
  (max(version)) never reports 280 while 279 is missing.
- **Same shape as 277** (ADR 0010 decision 10): scope / tenant_id CHECK, RLS ENABLE + FORCE, `writing_rule_cis_app_all`
  and `writing_rule_cis_owner_all` (X1 parity, rule t exempt), `tenant_isolation` TO `aa_app_user` — but **no
  tenant-pool privilege at all**: tenants never see rules (ADR 0010, D7). The policy is there for rls_catalogue rule a
  (a `tenant_id` table needs an `app.tenant_id` policy) and as the floor if a grant ever appears.
- **Token caps in the DB, as an AFTER row trigger** (`shared.writing_rule_token_cap`), not only in code: the plan says
  "enforced at write". An AFTER trigger sees the generated `token_estimate` of the new row (a BEFORE trigger would not)
  and the other rows of the same statement. It takes a transaction advisory lock per (writer, scope, tenant) first, so
  two concurrent approvals cannot both slip under the cap (READ COMMITTED: the sum after the lock sees the other
  commit). Only `approved` + `active` count: candidates are unlimited.
- **Token estimate = ceil(chars / 4)** of `rule_text` + `replacement` (generated column). Deterministic and cheap; no
  tokenizer in Postgres. Close enough for a 400 / 250 budget.
- **Per-row caps as CHECKs**: ≤ 25 words for a rule; a `preference_summary` ≤ 5 sentences and ≤ 125 words (the plan
  says ≤ 5 sentences; 25 words could not hold one) and tenant scope only.
- **Nothing auto-activates at the row level too**: `approved` / `active` need `approved_by` + `approved_at` (CHECK).
- **D9 in the DB**: a platform rule with tenant evidence needs `support_tenants >= 3`; a tenant rule `<= 1`.
- **Gate rename key = `reason_code` + `gate_class`** (the qtax-v1 taxonomy class of the gate,
  `services/quality/registry.gate_classes`). The taxonomy maps old and new gate names to the same class, so a rule
  survives the AA-787 rename. No separate alias table.
- **`match_phrases`** (≤ 5, entity-masked): what the rule targets. The PREDICT check (WM-12) counts held-out edits that
  remove one; the R0 replay (AA-918) counts how often one appears. Added now so 918 needs no migration.
- **One open rule per cluster** (partial unique index on candidate / approved / active): re-mining a cluster is
  idempotent; a rejected rule does not block a new candidate next month.
- **Stage `writing_memory_mine` seeded in 280** with the judge route of 224 (gpt-5.6-luna → gpt-6-luna →
  gpt-6-luna-openai last, no shadow), role `judge`, plus the spend budget `bedrock / job:writing_memory_mine` ($1 a
  run, $2 a day, hard stop). The $25 calendar-month cap (E4) is a code check over the writing-memory stages of
  `llm_call_log`, since `spend_budget` has no monthly axis.

## Tradeoffs

- FORCE + owner parity policy behaves like no FORCE for the owner; kept for the ADR invariant and the X1 convention
  (same as 277).
- No FK from `signal_ids` to `writing_signal` (array, polymorphic erasure order); a platform rule may keep ids of a
  tenant's erased signals — ids only, never text.
- The cap trigger serialises approvals of one writer / tenant (advisory lock); approvals are rare human clicks.
