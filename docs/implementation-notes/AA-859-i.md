# AA-859 PR-I — W9 integration status / connect / test on the tenant pool

Flag: `INTEGRATION_CONNECT_FLAG` = `aa859:integration_connect_pool` (declared in PR-S, not added here).
Routes: GET / POST `/v1/integrations/{wordpress,facebook}`, POST `/v1/integrations/{wordpress,facebook}/test`.
Depends on migration 241 (column INSERT / UPDATE on `shared.tenant_integrations`), applied on Dev.

## Decisions
- One helper per DB step, shared by WordPress and Facebook (`_fetch_status_row`, `_upsert_integration`,
  `_fetch_test_row`, `_record_test_result`), each one `acquire_scoped_conn(..., INTEGRATION_CONNECT_FLAG,
  fail_closed=True)`. No helper nests another, so one request = 1 acquire (status, connect) or 2 sequential
  acquires (test).
- SQL in module constants (`_STATUS_SQL`, `_CONNECT_UPSERT_SQL`, `_TEST_SELECT_SQL`, `_VERIFY_OK_SQL`,
  `_VERIFY_FAILED_SQL`); `integration_type` became parameter `$2` instead of a literal per type. Same
  statements otherwise, character for character in the SET / INSERT / RETURNING lists.
- One log event per request with `used_tenant_pool=`: `aa859_integration_status`, `aa859_integration_connect`,
  `aa859_integration_test` (logged in the first block, so it is there on every exit path after the acquire).
- Flag off: no transaction wrapper (one statement per acquire, autocommit), exactly as before. Flag on:
  acquire_scoped_conn's own transaction with `app.tenant_id` LOCAL.
- Connect order stays as the plan says: Secrets Manager put first (`asyncio.to_thread`, no connection), then
  the UPSERT block. A secret write failure (502) takes no connection at all.
- No MAIN exception in these routes: connect / test write no audit_log row today, and nothing is enqueued.

## Changed (vs. plan / old behaviour)
- Test-connection, block 2: when the verify UPDATE returns no row (a disconnect between the two blocks),
  the route answers 404 "<name> is not connected yet" and logs `aa859_integration_test_row_gone`. Before,
  `_row_to_status(None)` raised TypeError (a 500). This is the only flag-off behaviour change, and it only
  happens on that race.
- Existing unit tests (`test_aa457_integrations.py`, `test_aa462_integrations_facebook.py`) updated for the
  extra `$2` argument of the connect UPSERT.
- The fail-closed matrix runs from a new file (`tests/unit/test_aa859_integration_connect_pool.py`) that
  calls `test_aa817_fail_closed_routes.py`'s check functions with these routes, instead of editing that
  file's `ROUTES` (parallel PRs). Reentrancy entries are in `tests/unit/test_aa859_reentrancy_i.py`.

## Tradeoffs
- Secret first, then DB: if the tenant pool then refuses (503: no tenant connection, Redis on + pool down)
  the secret already holds the new credentials while the row keeps the old `config` (site_url / page_id) or
  does not exist yet. Same as the old code when the DB write failed after the put; a retry of connect heals
  it. The reverse order would leave a row pointing at credentials that were never written.
- The verify UPDATE is not pinned to the row block 1 read (no `updated_at` match, unlike disconnect): a
  reconnect between the blocks gets the old credentials' test result recorded on the new row. Old
  behaviour, rare (two tenant clicks within ~8 s), and the next test fixes it; pinning it would change the
  route's answers.
- Kept `_put_secret` / `_get_secret` with botocore's default client config (not the bounded disconnect
  config): no connection is held during them, so a slow call costs only that request.

## Should know
- The UPSERT writes only 241's grants: INSERT (tenant_id, integration_type, config, secret_key,
  connected_at), DO UPDATE SET (config, secret_key, updated_at). A unit test parses both lists from
  migration 241 and from the SQL constants; an integration test shows a SET of `connected_at`,
  `integration_type`, `tenant_id` or `created_at` is 42501 on the tenant pool (and fine for the owner).
- Postgres checks INSERT WITH CHECK before conflict arbitration, so an UPSERT carrying another tenant's id
  is refused (row-level security) on both the insert and the conflict path; tested on both.
- The flag shares nothing with `INTEGRATION_DISCONNECT_FLAG`; either can be on alone (tested).
- Rollback of the route: `DEL aa859:integration_connect_pool`. A 241 rollback must DEL this flag first.
- Review fix (no-connection-held check): the /test routes catch every Exception around the remote GET, so a
  check that raises there is swallowed into a failed verify. `_no_connection_held` now records the holders
  at each Secrets Manager / HTTP call into `pool.held_seen`; the reentrancy test asserts every record is
  empty, that every stand-in was reached, and that `/test` returns `success is True`. A route-level
  mutation test (a tenant block held across the GET) shows the record catches it.
- Review fix (block-1 forgotten WHERE): the 404 alone could not tell RLS hiding A's row from a leak that
  block 2 then 404s; the integration test now asserts `_get_secret` is never called on the tenant pool and,
  on the admin pool with the same mutation, is called with A's key.
