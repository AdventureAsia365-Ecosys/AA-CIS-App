# AA-832 — per-role RDS connection metric (CIS app side)

AA-832 adds the missing RDS alarms (latency, disk queue, XID, connections retuned) plus a per-role
connection alarm against each LOGIN role's `CONNECTION LIMIT`. RDS has no per-role metric, so the
CIS worker samples `pg_stat_activity` every 5 minutes and publishes it to CloudWatch. This file
covers the CIS half; the Terraform half (schedule, IAM, alarms) is the AA-CIS-Infra branch of the
same issue.

## Decisions
- **New job kind `ops_rds_role_connections`** (`services/jobs/ops_rds_role_connections_job.py`):
  one query (`pg_roles` LEFT JOIN `pg_stat_activity`, LOGIN roles with `rolconnlimit > 0`), then one
  `PutMetricData` to namespace `AA/RDS`, dimension `Role=<rolname>`, two metrics per role:
  `RoleConnections` (Count) and `RoleConnectionLimitPct` (Percent, `100 * connections / limit`).
  Roles are discovered on every run, nothing is hard-coded. Region: `AWS_REGION` /
  `AWS_DEFAULT_REGION` / `us-west-1` (same order as `ses_mailer`).
- **Trigger = the ops-probe Lambda every 5 minutes** (EventBridge Scheduler, Infra side) →
  `POST /admin/job-runner/rds-role-connections/schedule`, admin-secret gated like
  `/retention/schedule`, always 200. Idempotent by state, not by key: when a queued or running job
  of the kind exists it returns `{"enqueued": false, "reason": "already_pending", "job_id": …}`, so
  a dead worker never piles up rows (one row waits, the next calls say `already_pending`).
- **`background=False` (deviation from the session contract, which said `background=True`).**
  A background kind is not claimed while ANY other background job runs on the worker
  (`Worker.claim_caps`, `BACKGROUND_MAX_RUNNING = 1`) and claim is FIFO, so behind a place-pipeline
  batch or a 30-min retention run the sample would wait for hours. Missing datapoints +
  `treat_missing_data = notBreaching` = a silent alarm exactly while the worker is busiest. A
  normal kind takes one slot for well under a second. It is not a guarantee during a wave: the
  8-slot worker runs `s1_rewrite` 6 + `a3_atomize` 1 + background 1, and claim is FIFO, so an older
  `s1_rewrite` backlog can win each freed slot and a sample can wait tens of minutes. The Infra half
  covers that gap with a "sampling stopped" alarm (no `RoleConnections` sample for 45 minutes,
  missing data = breaching), so a silent gap becomes an email instead of a quiet OK. Precedent: `ops_alert_email`, the other short ops kind,
  is not background either. Guarded by `test_kind_registered` (`k.background is False`).
  **The Linear AA-832 Scope line still says `background=True`**: the PR body and a Linear comment
  must state this deviation (text below) so the Done-when check does not read it as a miss.

  > Deviation from AA-832 Scope: `ops_rds_role_connections` is registered with background=False,
  > not background=True. Background kinds are not claimed while another background job runs
  > (`Worker.claim_caps`, BACKGROUND_MAX_RUNNING=1, FIFO claim), so during a place-pipeline batch or
  > a retention run the 5-minute samples would stop while the per-role alarms
  > (`treat_missing_data = notBreaching`) stay silent. The job is a single catalog query + one
  > PutMetricData (sub-second), same as `ops_alert_email`, which is also not background.
- **`max_attempts=2`**: one retry (30 s backoff) for a throttled/transient `PutMetricData`; a
  second failure leaves the job `failed` on the Jobs page. Errors are logged
  (`ops_rds_role_connections_put_failed`) and re-raised, never swallowed.
- **Deploy guard exemption = per-kind opt-in flag** `@job_kind(..., deploy_gate_exempt=True)`.
  There was no exclusion mechanism: `GET /admin/job-runner/deploy-gate` counted every queued/running
  row. The flag is set on this kind only; `deploy_gate` passes the flagged kinds to
  `queue.active_count(pool, exempt_kinds=…)` and returns them as `exempt_kinds` so the CI log says
  why a visible row did not block.

## Changed (vs. the request)
- `shared/jobs/registry.py`: new `JobKind.deploy_gate_exempt` (default False).
- `shared/jobs/queue.py::active_count` takes `exempt_kinds` (default none = old behaviour).
- `api/routers/admin_job_runner.py::deploy_gate` response gains `exempt_kinds`.
- No migration (no CHECK constraint lists kinds; `shared.job.kind` is free text), no frontend change
  (the Jobs page reads kinds from `/admin/job-runner/summary`).

## Tradeoffs
- No idempotency key per 5-minute slot: a duplicate Scheduler delivery racing the pending check
  could enqueue two jobs; both run (concurrency 1) and publish two datapoints a few seconds apart,
  which the `Maximum` alarm statistic absorbs. A slot key would also have blocked a manual re-run
  in the same 5 minutes.
- 288 rows/day in `shared.job` (~8.6k succeeded rows kept by `retention_job`'s 30-day window).
- A deploy that interrupts a running sample costs one datapoint at most; the worker's grace period
  normally lets a sub-second job finish.

## Should know
- The job needs `cloudwatch:PutMetricData` (condition `cloudwatch:namespace = AA/RDS`) on the role
  the WORKER task runs as — Infra half. Until it is applied every run fails with AccessDenied
  (visible on the Jobs page), which is expected.
- `pg_stat_activity` rows of other roles are visible to `aa_cis_admin` (verified live 16/10), so
  the counts are complete; `usename` is the session user, which is what `CONNECTION LIMIT` counts.
- Deploy guard before this change: `deploy-dev.yml` job `preflight` curls `/deploy-gate`, which was
  `queue.active_count` = every `shared.job` row in queued/running, no per-kind or background
  exclusion. The manual check in `skill/aa-ship/SKILL.md` (`SELECT kind, status, count(*) … IN
  ('queued','running')`) will show this kind's row now and then; it is safe to ignore.
- DB Migrate (AA-CIS-Infra `db-migrate.yml` + `db/run_migration.py`) has no `shared.job` idle check;
  it relies on `lock_timeout 5s`. This job reads only catalog views, so it cannot hold a lock an
  app-table ALTER waits on.
- Retention: succeeded rows go after 30 days, failed/cancelled after 90 days (archived) via
  `retention_job` (`services/retention/policy.py`). 288 rows/day stays far below the 2x-growth
  floor of 5,000 candidates, so the daily scheduled run is never HELD by this kind. Steady state
  ~8.6k–8.9k extra rows (today the table has ~2.5k).
- The Jobs page list will be dominated by this kind (288/day); filter by kind to hide it.
- Integration test `tests/integration/test_aa832_rds_role_connections.py` creates roles, so it skips
  on a local DB whose user lacks CREATEROLE; it runs in CI (cistest is SUPERUSER there).
- Monthly cost (with the Infra half, list prices, before free tier): 7 new alarms × $0.10 = $0.70;
  6 custom metrics (2 × 3 roles) × $0.30 = $1.80; 8,640 PutMetricData × $0.01/1k = $0.09;
  8,640 Scheduler invocations ≈ $0.01, Lambda requests + ~0.5 s at 128 MB ≈ $0.01,
  API Gateway 8,640 × $3.50/M ≈ $0.03, logs ≈ $0.01 → about **$2.65/month**.
