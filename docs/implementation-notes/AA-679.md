# AA-679 — CIS catalog views (read model) + `catalog.tour.v1` contract

Branch `feat/aa-679-catalog-views` (CIS) and `docs/aa-679-catalog-contract` (root repo, contract file).
Scope of this slice: CIS migration 225 (schema `catalog`, views, grants), the JSON Schema contract,
an integration test. Outbox events are the next slice.

## Decisions

- **Schema name `catalog`.** ADR 0001 decision 1 calls it the "Catalog & Tour Graph read model" and
  names the contract `catalog.tour.*`; the ownership doc prescribes no other name. Owner: AA-CIS-App
  (row added to `docs/database/schema-ownership.md` in the root PR).
- **Identity = `(source_system, source_id)`** as the contracts README rule 3 says. `source_id` is
  `raw_tours.source_group_id` (stable across re-uploads: a re-upload creates a new `tour_id` with
  `source_version + 1` in the same group, ADR-018 / migration 052), falling back to `tour_id` for a
  row with no group (none expected — ingestion always sets it). `tour_id` (current CIS version) is
  exposed too, for joins with the photo views, but consumers must key on `source_id`.
- **Filter = what is live in Master Content**: `published_tours.master_status = 'active' AND
  deleted_at IS NULL` (same rule as `acp_contract.v_active_tour_atoms`, migration 203), the raw source
  `source_status = 'active' AND deleted_at IS NULL` (same rule as `v_trip_registry`, migration 195),
  and the AA master tenant `00000000-0000-0000-0000-000000000001` only (see Should know: RLS).
- **Days are parsed in SQL from the canonical itinerary string** `Day N — Title\nBody`
  (`graph.py::_process_itineraries`, AA-353; Python twin
  `services/content_generation/itinerary_utils.parse_canonical_itinerary_days`). Same semantics:
  a header is a line starting `Day <n> —`; the body runs to the next header; a repeated day number
  keeps the last block (Python dict semantics). A tour whose text is not in that format has no
  `v_tour_day` rows; `v_tour.itinerary_text` still carries the whole text.
- **Places come from active atoms** (`acp_contract.tour_atoms` with the `v_active_tour_atoms` rule —
  `NOT deleted AND NOT is_empty_marker`, joined to a live `v_tour` row; see S236 below for why not the
  view itself — `place` + `itinerary_day`), one row per
  (tour, day, case-insensitive place), enriched with the AA-772 place card when the atom is linked to a
  non-rejected card, and with lat/lng from `shared.destinations` when a destination has the same name
  (case-insensitive; the table is unique on `lower(name)`) **and** the same country (card country,
  else tour country). A wrong pin on a map is worse than a missing one, so no fuzzy matching.
- **Place order = itinerary order** (review fix). Within a day, `position` follows the first
  case-insensitive mention of the place in that day's title + body; places the text does not name
  come after, ordered by `created_at` then the lower-cased place (C collation). Atom ids
  (`atom_<uuid hex>`, one a3_atomize run per tour) carry no order and are never a tie-break.
  `place_name` spelling: the one written verbatim in the day text, else the most frequent, else the
  first in C collation — deterministic for the same data.
- **Internal helper view `catalog._tour_day_text`** (day title + body parsed once) feeds both
  `v_tour_day` and `v_tour_place` (the place order needs the day text, and `v_tour_day.places` needs
  the places, so the parse moved out of `v_tour_day`). Not granted, not in the contract.
- ~~Runner assertion: BYPASSRLS or superuser~~ — **replaced in S236** (it is what failed the Dev
  apply: RDS has neither). See "S236 redesign" below.
- **S236 redesign — least-privilege owner, no BYPASSRLS anywhere.** Facts (Dev, S236): runner and
  table owner `aa_cis_admin` is `rolsuper=false, rolbypassrls=false`; `published_tours` / `raw_tours`
  have RLS ENABLED + FORCED with one policy `tenant_isolation TO public USING (tenant_id =
  current_setting('app.tenant_id', true)::uuid)`; `tour_atoms`, `place_card`, `atom_place_card`,
  `destinations`, `place_photo` have no RLS. A view owned by `aa_cis_admin` would therefore return
  nothing unless the reader set `app.tenant_id`. Design:
  1. Role `catalog_owner` NOLOGIN NOSUPERUSER NOBYPASSRLS NOCREATEROLE (idempotent DO block).
  2. `catalog_owner` gets `USAGE` on schemas `catalog`, `gold_aa_internal`, `silver_aa_internal`,
     `acp_contract`, `acp_shared`, `shared` and `SELECT` on exactly `published_tours`, `raw_tours`,
     `tour_atoms`, `place_card`, `atom_place_card`, `shared.destinations`, `shared.v_tour_photos`,
     `shared.v_destination_photos`. Nothing else, no write.
  3. RLS policy `catalog_owner_aa_master_read` on `published_tours` and `raw_tours`: `FOR SELECT TO
     catalog_owner USING (tenant_id = '00000000-0000-0000-0000-000000000001'::uuid)` (AA master tenant =
     TripPlanner's `MASTER_CONTENT_TENANT_ID`, the `aa_internal` tenant of 004/005). Guarded by a
     `pg_policies` check (CREATE POLICY has no IF NOT EXISTS).
  4. All 7 views (incl. `_tour_day_text`) keep `security_barrier = true` and their filters, and are
     `ALTER VIEW … OWNER TO catalog_owner`. Grants to `aa_app_user` / `tripplanner` / `booking` unchanged.
  5. Runner check: `GRANT catalog_owner TO CURRENT_USER`, assert `pg_has_role(.., 'MEMBER')` and
     actually `SET LOCAL ROLE catalog_owner` / `RESET ROLE` (PG16 also needs the SET option).
     Sanity check before COMMIT: as `catalog_owner`, with `app.tenant_id` pinned to the nil uuid (so
     `tenant_isolation` admits nothing and only the new policy can), `count(*) FROM catalog.v_tour`;
     the runner then counts live AA master tours with `app.tenant_id` = master. Raises only if that
     count is > 0 and the view's is 0 — so an empty CI DB passes, Dev must see rows.
- **Atoms from the base table, not `v_active_tour_atoms`.** That view is owned by `aa_cis_admin` and
  joins `published_tours`; reading it from a catalog view runs its RLS check as `aa_cis_admin`
  (FORCE RLS, no `app.tenant_id`) → zero atoms. `v_tour_place` reads `tour_atoms` with the same rule
  (`NOT deleted AND NOT is_empty_marker`); the `published_tours` side of the rule is already enforced
  because every atom is joined to a live `v_tour` row. The shared photo views read only
  `shared.place_photo` (no RLS) and are reused as they are.
- **The runner is not left a member of `catalog_owner`** (deviation from the brief, which said
  `GRANT catalog_owner TO aa_cis_admin`). Policies apply to every role that *inherits* the policy's
  role, and `aa_cis_admin` is also the CIS API's runtime role (DB Migrate uses the api task's
  `DATABASE_URL`). A lasting membership would make `catalog_owner_aa_master_read` apply to every CIS
  API session, so a tenant-scoped session (app.tenant_id = tenant X) would also see AA master rows.
  225 therefore grants the membership at the top, does the `ALTER … OWNER`, the sanity check, and
  `REVOKE catalog_owner FROM CURRENT_USER` before COMMIT. Same for `CREATE` on schema `catalog`
  (needed by `catalog_owner` only at `ALTER … OWNER` time). A later migration that edits a catalog
  view repeats the dance (GRANT at top, REVOKE at the end). On PG16+ the creating CREATEROLE runner keeps
  an ADMIN-only grant (no INHERIT, no SET) — harmless, and it is what lets it re-grant later.
- **`updated_at` is not a change cursor.** `published_tours` has no `updated_at`; an in-place Master
  Content edit moves `content_hash` but not `updated_at`. Stated in the view comment, the contract
  and the contracts README: consumers diff `content_hash`.
- **`duration_days`** = first `N day(s)` in `raw_tours.duration`, else the highest day number in the
  canonical itinerary. No new number invented.
- **No price in the catalog.** Prices belong to AA-Booking (ADR 0005 decision 1); `price_raw` is not
  exposed.
- **No intensity.** CIS has no intensity field (TripPlanner derives one in its Tour Graph). The
  view exposes the source `activities` jsonb and per-place `activity_types` instead.
- **`content_hash`** = md5 of a JSON array of every content field the view exposes (incl. cover
  photo path). Consumers compare it to decide whether to re-sync; `source_version` is also exposed.
- **`slug`** = ascii-folded-by-replacement `name-country` (max 80) + `-` + first 8 hex of
  `source_id`, so it is unique and stable while the title stays the same. It is a URL hint, not an
  identity.
- **Grants**: `USAGE` on schema `catalog` + `SELECT` on every view to `aa_app_user`, `tripplanner`,
  `booking`. Unguarded (ownership rule 5 / ADR 0004 decision 6).

## Changed

- (vs task text) Added two thin photo views `catalog.v_tour_photo` / `catalog.v_destination_photo`
  so consumers read only schema `catalog` (no `shared` grant needed for Booking).
- `catalog.v_tour` also carries `itinerary_text`, `lifecycle_stage`, `best_time_to_go`,
  `group_size` (source facts, useful to Booking quotes), and `sku`.

## Tradeoffs

- Views, not materialized views: always current, no refresh job. `v_tour_place` aggregates ~32k
  atoms; fine for a sync job, not for a per-request hot path (TripPlanner keeps its own read models).
- SQL regex parsing duplicates `parse_canonical_itinerary_days`. Accepted so the read model is pure
  SQL (no CIS code in the consumer path); the integration test pins the same cases.

## Should know

- **RLS (S236).** The first version assumed the owner `aa_cis_admin` was BYPASSRLS (007b's comment
  says so — stale: on RDS it is not, and there is no superuser). CI hid it because conftest applies
  migrations as a superuser, which bypasses RLS even with FORCE. Now the owner is `catalog_owner` and
  RLS limits it to the AA master tenant (above). Consumers do **not** set `app.tenant_id`.
- **`app.tenant_id = ''` fixed in 225 (S236, coordinator call for AA-812).** `tenant_isolation` is `TO
  public`, so it is OR-ed with the catalog policy for `catalog_owner`. A pooled connection holds
  `app.tenant_id = ''` after any transaction that ran `set_config('app.tenant_id', …, true)`
  (TripPlanner `extraction/tour_days.py`, `assembly/master_content.py`; CIS `aa544_tenant_pool.py`,
  `raw_tour_repository.py`), and `''::uuid` then raised `invalid input syntax for type uuid` as soon as
  a catalog read scanned a non-master row. 225 now runs `ALTER POLICY tenant_isolation … USING
  (tenant_id = NULLIF(current_setting('app.tenant_id', true), '')::uuid)` on `published_tours` and
  `raw_tours` only. Name, `TO public`, `FOR ALL`, PERMISSIVE unchanged; neither policy has a WITH
  CHECK (004/008 define USING only, so USING also checks writes) — the DO block would give a WITH
  CHECK the same expression if one existed. Guard: altered only while the qual has no `NULLIF`, so a
  re-run is a no-op (verified). Impact check before changing: grep of CIS code, tests and migrations
  for `tenant_isolation` / `app.tenant_id` — no caller relies on `''` raising; the existing tests
  already treat "no tenant" as 0 rows (`test_tenant_rls.py::test_no_context_returns_no_rows`,
  `test_007::test_rls_no_context_sees_no_rows` on `pipeline_runs`, untouched). Behaviour change: a
  CIS session with `''` now reads 0 rows instead of an exception, and a write is refused by RLS
  (still an error). The other `tenant_isolation` policies (seo_context, generated_content,
  quality_scores, pipeline_runs, gold exports/webhooks) keep the old cast — out of scope.
- **Test emulates RDS (S236).** Module fixture `rds_like_225` in `test_aa679_catalog_views.py`: undoes
  the superuser-applied 225 (drops schema `catalog`, the policies, role `catalog_owner`, the version
  row), creates `zz679_rds_runner` (LOGIN NOSUPERUSER NOBYPASSRLS CREATEROLE), hands it the schemas,
  tables (FORCE RLS stays on) and views 225 reads, plus `CREATE` on the database, and runs 225 as that
  role with errors **not** swallowed. Teardown: `REASSIGN OWNED BY` runner to the test superuser,
  drop it. Tests then read as `SET ROLE booking` / `tripplanner` / `catalog_owner`. Locally (PG16
  throwaway cluster) the sanity check was also run red/green on a DB with a committed live AA tour:
  full 225 → OK (`catalog_owner = 1 rows, live = 1`); 225 without the policy block → raises; in-place
  re-run (version row deleted, views already owned by `catalog_owner`) → OK. The fixture also puts
  `tenant_isolation` back to its 008 shape first, so every run exercises the ALTER POLICY. Tests for
  it: `test_tenant_isolation_treats_empty_tenant_as_none` (policy shape), `test_catalog_read_on_a_
  pooled_connection_with_empty_tenant` (booking/tripplanner on a connection left at '' by an
  earlier local set_config, with an other-tenant row in the scan), `test_cis_roles_with_empty_tenant_
  see_no_rows` (app_user and the table-owner runner: 0 rows, no exception),
  `test_tenant_scoped_reads_unchanged` (master/other scoping and cross-tenant write refusal). The
  first three fail without the ALTER POLICY block (invalid input syntax for type uuid), pass with it. RDS is PG15 (no per-grant
  INHERIT/SET options; CREATEROLE may grant any non-superuser role) — the file uses only syntax valid
  on both.
- **Flaky test fixed** (review): the old place test depended on the random uuid part of atom ids
  (all atoms share `now()` in one transaction). The test now names places in the day text and
  pins the order and spelling rules; a second test pins the no-text-match spelling tie-break.
- The contract sample is validated against the schema with `jsonschema` (Draft 2020-12) by hand;
  the schema file lives in the root repo, so no CIS CI test validates it yet (README rule 7 gap).
- **Next step (out of scope):** outbox events `catalog.tour.published|updated|trashed` (a
  `catalog.outbox` table written by CIS when master status / content changes, `v_tour_outbox` view,
  Booking `bk_catalog_pull` job). Until then consumers poll `v_tour` and compare `content_hash`.
- **security_barrier (review blocker).** Every view in schema `catalog` (`v_tour`, `v_tour_day`,
  `v_tour_place`, `v_tour_photo`, `v_destination`, `v_destination_photo`, internal `_tour_day_text`)
  is created `WITH (security_barrier = true)`. Reason: inside the AA master tenant (all the RLS
  policy limits) the views' own WHERE filters (live status; and master tenant when a reader sets
  `app.tenant_id`) are the only row limit; without the barrier the planner
  may push a consumer's leaky function / qual below those filters and leak hidden rows (reviewer
  reproduced on PG16 as role `booking`). Tradeoff: consumer quals using non-leakproof functions are
  no longer pushed into the view, so some filtered reads may plan a bit worse; correctness wins.
  Guard: `test_every_catalog_view_is_security_barrier` checks `pg_class.reloptions` for every view
  in `catalog` (new views are caught automatically). Verified red on the old 225 (all 7 views
  listed), green after.
