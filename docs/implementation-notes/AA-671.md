# AA-671 — pool facets for the portal Marketplace (activities, intensity, cover photo)

The Marketplace redesign shipped in AA-Partner #109 without the activity / intensity filters and the card cover image,
because `GET /v1/tours/pool` had no fields for them. This change adds them to the pool API, from CIS data the catalog
already serves. No migration.

## Decisions

- **Where the facets come from.** Activities and intensity are the tour's **graph components**: the distinct
  `activity` codes of its places, and the **highest** `intensity_level` among them. This is the same rule the catalog
  HTTP contract uses (`services/catalog_http/mapping.py` `facets()`), so the portal, the CRM and catalog.http.v1 agree
  on one tour. The cover is the tour's **position-1 photo** (`shared.v_tour_photos` order: manual match first, then
  file name), served on the public photo route `/content/photos/{id}?size=small|large`.
- **Closed vocabulary for the filter, graph codes only.** `catalog.http.v1` also folds in the free-text
  `raw_tours.activities` names from the source sheet. They are not a usable filter (free text, per-tour spelling), so
  the pool uses the graph codes only (`geo.tour_place` CHECK `tour_place_activity_check`, 8 codes). The answer lists
  the accepted values in `facets`, so the portal builds its options from the API.
- **Intensity names are the tenant ones** (`leisurely -> easy`, `active -> challenging`), as in catalog.http.v1 and the
  CRM. `intensity=` filters on the exact level (the tour's hardest part), not "at most".
- **"Recently added" is `added_within_days=N`** (1..365) on `published_at`, the same date the list is ordered by.
- **Per-pool SQL.** The route runs on either pool (flag `aa859:t2_version_reads_pool`, ADR 0015 decision 3):
  - tenant pool (`aa_app_user`): reads `catalog.v_tour_component` and `catalog.v_tour_photo` (granted to it; no grant
    on `geo.*` or `shared.v_tour_photos`);
  - admin pool (`cis_app`): reads the views' own sources (`geo.tour_place` + usable `shared.destinations`,
    `shared.v_tour_photos`), the same rows by the same rule (migration 258 view text).
  An integration test checks that both pools give the same answer, and that the admin-pool SQL is refused (42501) on
  the tenant pool, which is why the two strings exist.
- **Two image URLs**: `cover_image_url` (`size=small`, card) and `cover_image_large_url` (`size=large`, drawer). Built
  with `services.photos.sync.public_base()`, like the admin photo routes; no host is hardcoded in the router.

## Changed (vs the issue text)

- Nothing dropped: the four missing pieces (activity filter, intensity filter, recently-added filter, cover image) are
  all served now. The card's activity tags use the same field.

## Tradeoffs

- A `LATERAL` aggregate per row (page size <= 100) instead of a materialised facet column: no migration, always
  current with the graph build, and the count only joins the facets when an activity / intensity filter is set.
  If the count with a facet filter gets slow on a large catalogue, a facet column on the catalog read model is the
  next step (needs a migration number).
- Live-tour rule: the catalog views only carry live tours (`catalog._live_tour`); the pool already filters to served
  Master tours with a live source (`_POOL_BASE_CONDITIONS`), so the two sets are the same rows.

## Should know

- Old clients are unaffected: new fields only, new optional query params; an unknown `activity` / `intensity` value
  answers 422 (FastAPI `Literal`).
- A tour with no graph components yet answers `activities: []`, `intensity: null`; with no matched photo,
  `cover_image_url: null`. The portal shows a placeholder and its theme tags in that case.
- Local check (S255): the local Postgres lacks the roles and pgvector, so the integration replay does not run there;
  both SQL branches were run against local stand-in catalog views in a rolled-back transaction (same answers, every
  filter case of the integration test). The integration test itself runs in CI.

## Follow-up S257: pool cover fallback to a place photo

### Decisions

- **Why the gap.** `cover_image_url` was the tour's position-1 row of `shared.v_tour_photos`, i.e. a `place_photo`
  matched to the tour itself (a per-tour Drive folder). Only tours with such a folder have one: S256 counted 162 of
  892 pool tours (China, Taiwan, Bhutan, Mongolia, South Korea, Sri Lanka). Destination photos
  (`shared.v_destination_photos`, the same matched rows by `destination_id`) were not used.
- **Fallback, read path only.** When a tour has no tour photo, the cover is a photo of its *primary place*: among the
  tour's graph components on usable destinations (the rows the facet join already reads: `catalog.v_tour_component`
  on the tenant pool, `geo.tour_place` + non-suspect, non-duplicate `shared.destinations` on the admin pool) whose
  destination has a photo, the one with the most distinct days, then the earliest day, then the destination id. One
  SQL template (`_POOL_COVER_SQL`) gives both pools, so they stay equal (tested).
- **Primary = most days, not first day.** Day 1 is usually the arrival city (Hanoi, Kathmandu, Beijing); the place a
  tour spends the most days in describes it better. Ties go to the earliest day.
- **Photo within the place: spread, deterministic.** `ORDER BY md5(tour_id || path)` — the same photo for a tour on
  every request, different photos for different tours of the same place, so a grid page of Hanoi tours does not
  repeat one picture (lesson S253, duplicate covers; `path` is already the canonical file per sha256, mig 290). The
  alternative, the destination's position-1 photo (manual matches first), was weighed: more "curated", but it would
  give every tour of a place the identical cover. One `ORDER BY` term to flip if the business prefers that.
- **Renditions.** Every row of the photo read views is a matched, served photo (`s3_key_large` set); the public route
  serves `small` (600), `medium` (960, falls back to large until backfilled) and `large` (1600). The fallback path is
  the same `/content/photos/<id>` shape, so `cover_image_url` / `cover_image_large_url` are built unchanged.
- **No migration, no new field.** `aa_app_user` already reads `catalog.v_tour_component` and
  `catalog.v_destination_photo`; `cis_app` reads `geo.tour_place`, `shared.destinations`, `shared.v_destination_photos`.

### Tradeoffs

- No `cover_source` field: the tenant sees one cover either way; adding a field would grow the public contract for an
  internal metric. Coverage can be measured with SQL (see Should know).
- Cost: a second per-row read of the tour's components (the facet join reads them once). The destination photo
  lookup is pushed into the view (`place_photo_destination_idx`, checked with EXPLAIN on a local cluster).

### Should know

- Tests: `tests/integration/test_aa671_pool_facets.py` — fallback picks the primary place (most days), skips a place
  whose photo has no rendition and a suspect place, never replaces a tour photo, equal on both pools, deterministic.
  Ran on a temporary Postgres 16 cluster: AA-671 + AA-859 pool files 28 passed; the new fallback test fails without
  the change.
- Live coverage after deploy (tenant pool view of it): count pool tours whose cover is non-null via
  `GET /v1/tours/pool?page_size=100` pages, or SQL on Dev comparing tours with a tour photo vs with a component
  destination photo. Tours whose places have no destination photo still have no cover; closing that needs photo
  matching (Drive folders per destination / `photo_sync` matching), not this read path.

## Follow-up S257 (2): photo -> destination matching (covers for tours without a photo folder)

### Decisions

- **Why the fallback added nothing.** On Dev every `shared.place_photo` row had `destination_id` NULL, so
  `shared.v_destination_photos` (and `catalog.v_destination_photo`, built on it) was empty and the pool cover fallback
  above found no place photo. The sync matched destinations only on request (`match_destinations`, off since S207:
  `shared.destinations` then still held the places of the tours published before the reset), and the request was never
  made again after the place pipeline (geo, AA-712 / AA-860) was rebuilt.
- **Candidates: the photo's own tour only.** A photo is compared with the places of the tour it is matched to — the
  `geo.tour_place` rows of the tour's source key (`COALESCE(source_group_id, tour_id)`, the catalog's key) plus the
  stops of the current graph build — never with every place of the country (S207 rule). Destinations that are merged
  duplicates (`duplicate_of` set) are not offered (`place_dedupe` repoints `place_photo.destination_id` on a merge).
  No country filter on the destination: a cross-border tour's place keeps its own country (memory: tour country as
  is); the tour scope is the guard.
- **Keyed by the raw tour, not the live tour.** The AA-860 `itinerary_places()` read was keyed by the live
  (published) tour of the country; a photo's `tour_id` is the raw tour the folder named. Keying by the source key
  covers both; `itinerary_places()` is replaced by `services/photos/destinations.tour_candidates()` (its AA-860
  integration test is replaced by `tests/integration/test_aa671_photo_destination_match.py`, same NOSUPERUSER /
  no-tripplanner reader check). The read pins `app.tenant_id` to the AA master like before (raw_tours is FORCE-RLS).
- **Names compared.** Both the itinerary spelling (`tour_place.name`) and the destination name, normalised with the
  place pipeline's own keys: `services.places.names.name_norm` (the destinations identity key: accents folded,
  leading articles dropped) and the place-card forms (`name_forms`: with/without the parenthetical; `core_key`: kind
  words at the edges dropped, never for a generic name).
- **Rules, strongest first; only unambiguous answers** (`services/photos/match.resolve_destination`): exact whole
  name -> core name -> a place name inside the label (nested names: the longest wins, "Olkhon" inside "Olkhon Island";
  two separate places in one label = ambiguous) -> a distinctive label inside exactly one place name. The first rule
  that names any place decides; a tie at that rule is `ambiguous` — no guessing, no fall-through to a weaker rule.
  Outcomes `matched / ambiguous / no_match / no_candidate / no_label` are counted and sampled.
- **At sync time too.** Every sync now fills an empty `destination_id` (new photos get theirs when they arrive);
  the SQL never changes a destination on a rejected row or a manual row that has one; `match_destinations=True` keeps
  its meaning of re-matching the automatic rows. A manual row's destination is looked up among the places of its
  kept (manual) tour.
- **Backfill = job kind `photo_destination_match`** (shared.job, ADR 0003; background, cap 1, 2 attempts, $0):
  DRY RUN by default (`dry_run` must be the boolean false to write), `limit` 1..5000 (default 5000 covers the whole
  table today), optional `country`. One guarded `UPDATE ... RETURNING` (only while the row is still matched, has no
  destination and the same tour), so it is idempotent and never overwrites. Not applied while a `photo_sync` runs.
  After an apply it fills empty destination covers (`fill_destination_covers`, the sync's own step). Audit: result
  with counts per outcome / rule / country, before/after counts of served photos and destinations with a photo,
  samples (30 each); one log line per written photo (`photo_destination_matched`) and per tied photo
  (`photo_destination_ambiguous`). Enqueue: `POST /admin/photos/destination-match` (PHOTOS_WRITE, one queued/running
  job at a time).
- **No migration.** `cis_app` already holds SELECT/UPDATE on `shared.place_photo`, SELECT on `geo.tour_place`,
  `geo.tour_stop`, `geo.graph_build`, `shared.destinations`, and the raw_tours policy (db-schema-reference, 29/10).

### Changed (vs the lane brief)

- Manual rows (234 on Dev, tour assigned by hand, destination empty) are matched too: the manual decision was the
  tour; the destination was never chosen. A destination set by anyone is never changed.
- The sync change makes destination matching the default on every sync (was opt-in); the brief asked for "new photos
  get destination_id at sync time".
- `match_destination("Paro", [("a","Paro"),("b","paro")])` used to return the first one listed; it now returns None
  (two places of one tour with the same name are ambiguous). The old unit test was changed accordingly.

### Tradeoffs

- `label_in_name` ("Taktsang" -> "Paro Taktsang") adds matches for short labels but could pick a wrong place when a
  label is a fragment of an unrelated name; it is limited to distinctive labels of >= 4 characters and to a single
  candidate, and its count is reported per rule so the dry run shows how much it contributes. One rule to drop if the
  samples look wrong.
- A manual row with an auto-filled destination sorts first in `v_destination_photos` (`match_source = 'manual'`
  first). Acceptable: its tour was chosen by a person; the pool fallback spreads by md5, not by position.
- `limit` re-reads the same first rows when fewer than are open (no keyset cursor): unmatched rows stay open by
  design. The default covers the whole table.

  `tests/unit/test_aa708_photo_sync.py` (sync now matches destinations, manual row uses its kept tour, ambiguous is
  counted, fail-open log, upsert clause), `tests/integration/test_aa671_photo_destination_match.py` (candidate SQL on
  real Postgres, job SQL guards, served view). Local: unit + acp suites pass (18,157) except
  `test_aa899_openapi_export` under the local FastAPI 0.110 venv; with the pinned FastAPI 0.161.1 / Pydantic 2.14.1
  (installed to a scratch path) it passes and `docs/api/openapi.json` was regenerated (additions only). The
  integration file ran against the local Postgres 16 with `--noconftest` (the full replay needs pgvector) and without
  its CREATE ROLE step (the local `cistest` lacks CREATEROLE); the reader-role check runs in CI.

  apply (`{"dry_run": false}`) -> count `shared.v_destination_photos` rows and pool covers.

## Follow-up S257 (2b): review fixes before the first apply

### Decisions

- **`label_in_name` is never written** (review: "Paro" -> "Paro Taktsang", "Thimphu" -> "Thimphu Dzong", "Bangkok" ->
  "Wat Arun Bangkok"). Town-name labels are common on the CON board, and the town's landmark is a different place. The
  rule now gives a separate outcome `weak` with a `suggestion` (the one place whose name holds the label): counted and
  sampled in the job result (`outcomes.weak`, `samples.weak`), counted by the sync (`destination_weak`), never written.
  A town label still matches the town itself through `exact` when the tour has it. Several hits at that rule stay
  `ambiguous`.
- **Provenance column, migration 303** (separate migration-only branch `feat/AA-671-photo-destination-source-migration`,
  merged and applied first): `shared.place_photo.destination_match_source` `auto | manual | NULL`. Chosen over
  "document that the job's writes on manual rows are frozen": without it, an automatic destination on a hand-assigned
  tour looks like a person's choice, so the sync would keep it forever and a folder-wide tour correction could not
  tell which destinations belong to the old tour. Backfill: rows with a destination get `manual` when their tour is
  manual, else `auto` (0 rows on Dev). `readiness.REQUIRED_CIS_SCHEMA = 303`.
- **Sync upsert rules (now `sync.UPSERT_SQL`, one constant run by the integration test):** rejected row or `manual`
  destination -> never changed; the automatic tour changes in the statement -> this run's answer for the new tour
  (the old place belonged to the old tour); re-match -> this run's answer; else keep an automatic destination and fill
  an empty one. The status keeps `matched` for a tourless row only while its destination is kept. Written answers are
  marked `auto`.
- **Re-match only where the places were read.** `destination_candidates` returns `None` on a read error (was `{}`);
  `$20` is now per row: `match_destinations AND this tour has candidates`. A failed read or a tour being re-extracted
  (no geo rows) keeps the existing destinations instead of clearing them. The sync result says
  `destination_candidates_unavailable`.
- **Folder-wide tour assignment** (`FOLDER_ASSIGN_SQL`): where a row's tour actually changes and its destination is
  not `manual`, the destination is emptied (with its source); the next sync or job run matches it against the new
  tour. A destination given in the assign call is marked `manual`; a tour-only assign empties the clicked photo's
  destination as before (now re-filled from the new tour).
- **Covers are opt-in in the job** (`fill_covers`, default false), like in the sync (`match_destinations`): the
  TripPlanner reads `shared.destinations.cover_image_url`. Every run, dry run included, reports `covers_preview`:
  `pending_now` (covers `fill_destination_covers` would change right now, same WHERE) and, for the planned
  destinations with no served photo yet, `new_empty` / `new_job_owned` (an upper bound: a planned photo without a
  stored rendition is not served).
- **Enqueue is atomic**: the active-job check and the insert run in one transaction under
  `pg_advisory_xact_lock(hashtext('photo_destination_match'))` (`queue.enqueue` accepts a connection).
- The job result also counts `written_manual_rows` (hand-assigned tours that got an automatic destination).

### Tradeoffs

- The migration makes the code PR wait for DB Migrate (303 needs 302 before it, strict prefix). Accepted: the
  alternative froze up to 234 automatic destinations and left the folder-correction case unsolvable.
- `weak` answers lose some true matches ("Taktsang" for a photo of Paro Taktsang). The dry run lists them with the
  suggestion, so staff can assign the good ones by hand; a curated alias list per place would be the systematic fix.
