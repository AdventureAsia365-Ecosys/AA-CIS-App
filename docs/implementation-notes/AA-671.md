# AA-671 — pool facets for the portal Marketplace (activities, intensity, cover photo)

The Marketplace redesign shipped in AA-Partner #109 without the activity / intensity filters and the card cover image,
because `GET /v1/tours/pool` had no fields for them. This change adds them to the pool API, from CIS data the catalog
already serves. No migration.

## Decisions

- **Where the facets come from.** Activities and intensity are the tour's **graph components**: the distinct
  `activity` codes of its places, and the **highest** `intensity_level` among them. This is the same rule the catalog
  HTTP contract uses (`services/catalog_http/mapping.py` `facets()`), so the portal, the CRM and catalog.http.v1 agree
  on one tour. The cover is the tour's **position-1 photo** (`shared.v_tour_photos` order: manual match first, then
  file name), served on the public photo route `/content/photos/{id}?size=small|large`.
- **Closed vocabulary for the filter, graph codes only.** `catalog.http.v1` also folds in the free-text
  `raw_tours.activities` names from the source sheet. They are not a usable filter (free text, per-tour spelling), so
  the pool uses the graph codes only (`geo.tour_place` CHECK `tour_place_activity_check`, 8 codes). The answer lists
  the accepted values in `facets`, so the portal builds its options from the API.
- **Intensity names are the tenant ones** (`leisurely -> easy`, `active -> challenging`), as in catalog.http.v1 and the
  CRM. `intensity=` filters on the exact level (the tour's hardest part), not "at most".
- **"Recently added" is `added_within_days=N`** (1..365) on `published_at`, the same date the list is ordered by.
- **Per-pool SQL.** The route runs on either pool (flag `aa859:t2_version_reads_pool`, ADR 0015 decision 3):
  - tenant pool (`aa_app_user`): reads `catalog.v_tour_component` and `catalog.v_tour_photo` (granted to it; no grant
    on `geo.*` or `shared.v_tour_photos`);
  - admin pool (`cis_app`): reads the views' own sources (`geo.tour_place` + usable `shared.destinations`,
    `shared.v_tour_photos`), the same rows by the same rule (migration 258 view text).
  An integration test checks that both pools give the same answer, and that the admin-pool SQL is refused (42501) on
  the tenant pool, which is why the two strings exist.
- **Two image URLs**: `cover_image_url` (`size=small`, card) and `cover_image_large_url` (`size=large`, drawer). Built
  with `services.photos.sync.public_base()`, like the admin photo routes; no host is hardcoded in the router.

## Changed (vs the issue text)

- Nothing dropped: the four missing pieces (activity filter, intensity filter, recently-added filter, cover image) are
  all served now. The card's activity tags use the same field.

## Tradeoffs

- A `LATERAL` aggregate per row (page size <= 100) instead of a materialised facet column: no migration, always
  current with the graph build, and the count only joins the facets when an activity / intensity filter is set.
  If the count with a facet filter gets slow on a large catalogue, a facet column on the catalog read model is the
  next step (needs a migration number).
- Live-tour rule: the catalog views only carry live tours (`catalog._live_tour`); the pool already filters to served
  Master tours with a live source (`_POOL_BASE_CONDITIONS`), so the two sets are the same rows.

## Should know

- Old clients are unaffected: new fields only, new optional query params; an unknown `activity` / `intensity` value
  answers 422 (FastAPI `Literal`).
- A tour with no graph components yet answers `activities: []`, `intensity: null`; with no matched photo,
  `cover_image_url: null`. The portal shows a placeholder and its theme tags in that case.
- Local check (S255): the local Postgres lacks the roles and pgvector, so the integration replay does not run there;
  both SQL branches were run against local stand-in catalog views in a rolled-back transaction (same answers, every
  filter case of the integration test). The integration test itself runs in CI.
