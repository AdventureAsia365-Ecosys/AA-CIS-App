# AA-1107 — fast catalog HTTP places read (`catalog.v_tour_place`)

Session S282, agent Claude Code, lane `l5-places`. Source: the C4.3 W47 review (root `.tmp-session` audit c43-w47):
the CIS catalog HTTP `places` read (`services/catalog_http/reader.py`, `catalog.v_tour_place` filtered by
`source_system = 'cis' AND tour_id = ANY($1)`, role `aa_app_user`) took 606 ms on Dev for 50 listed tours, all buffer
hits. Done-when: the same EXPLAIN on Dev at or under 200 ms, no per-row `name_norm` filter on `geo.tour_place`, no full
scan of `acp_contract.tour_atoms`.

## Decisions

- **Two migrations, one PR.** `431` (expand): a non-unique btree on `geo.tour_place (source_id, day_index,
  geo.name_norm(name))`. `geo.name_norm` is IMMUTABLE and PARALLEL SAFE (CIS 226), so an expression index is valid.
  The table is ~13.4k rows, under the 100k MIG-10 lock-risk line, so a plain `CREATE INDEX` in the transaction is
  allowed for an expand file (no `no-transaction` / CONCURRENTLY file needed; a SHARE lock for about a second).
  `432` (contract): a function and two view definitions change.
- **The stored `geo.tour_place.name_norm` column cannot serve the lookup.** It is `name_norm` of the component's LINK
  name (`services/places/components.py`, `Component.name_norm`), while the view compares `name_norm` of the itinerary
  spelling in `tour_place.name`. Hence the expression index, not the column.
- **`v_tour_place` atoms per tour.** The tour filter reached `catalog._live_tour` but not `tour_atoms`: PostgreSQL does
  not carry `= ANY` across the join's equivalence class (Data lesson S238). The `atom` step now reads the atoms in a
  `CROSS JOIN LATERAL (… WHERE ta.tour_id = t.tour_id … OFFSET 0)`; `OFFSET 0` stops the planner from pulling the
  subquery back up into the plain join (it would, and the plan would be the old one). The partial index
  `idx_tour_atoms_tour_id (tour_id) WHERE NOT deleted` serves it. Same predicates, same output columns; an inner
  lateral join drops a tour without placed atoms exactly like the JOIN did.
- **Two more fixes were needed to reach the target (measured, not guessed).** After 431 + the atoms change the local
  bench was still at 60 % of the original time:
  - `geo.name_norm` itself costs ~30 µs per call locally, ~23 µs of it in `translate()` over the 504-character accent
    table. The index removes the calls on the candidate rows, but the place name's key is still computed once per
    output row (the index condition's runtime key). 432 adds an ASCII fast path: when `octet_length(p) =
    char_length(p)` (no multi-byte character, UTF8 database) the input skips `translate()` and the six `replace()`
    calls. Every character of the accent table and of the replace patterns is non-ASCII, so on such an input they are
    the identity: same result by construction. NULL and non-ASCII inputs take 226's path unchanged. 5 µs per call on
    an ASCII name.
  - `catalog._tour_day_text` (289): subquery pull-up substituted the heading match `m` into every `m[1]` / `m[2]`
    reference (first_day, last_day CASE, the `m IS NOT NULL` filter), so `regexp_match` ran several times per chunk.
    432 moves it into a `CROSS JOIN LATERAL (SELECT regexp_match(…) AS m OFFSET 0) h`: once per chunk. The per-tour
    day text went from 1.16 to 0.33 ms per tour locally (Dev's evidence: 2.3 ms per tour).
- **Guards inside 432**, all RAISE (whole file rolls back): before/after md5 of every row of `v_tour_place`,
  `_tour_day_text` and `v_tour_day` as `catalog_owner` (row count + md5 in key order), before/after md5 of
  `geo.name_norm` over every distinct place string of the catalogue (`geo.tour_place.name`, `tour_atoms.place` and its
  btrim, `shared.destinations.name`, `acp_shared.place_card.display_name`), UTF8 encoding, column list and types,
  owner, security_barrier, consumer grants, `name_norm` still IMMUTABLE, 431 registered first.

## Tradeoffs

- **Function change vs. a stored normalised column.** A stored `spelling_norm` column on `geo.tour_place` would need
  every writer to keep it in sync and a table rewrite or backfill; it would also not help the place name side (the key
  of the atom spelling is computed at read time either way). The ASCII fast path speeds every caller of
  `geo.name_norm` and changes no result; the corpus md5 check proves it on Dev's data at apply time.
- **`OFFSET 0` as an optimisation fence** is a well-known PostgreSQL idiom but reads like a trick; both sites carry a
  comment saying why. An unfiltered read of the whole view stays fine: one index scan per live tour (~900).
- **Scope:** `catalog.v_tour_place_name` (298, Booking) has the same full `tour_atoms` scan in its own `atom` step; it
  gets the day-text and `name_norm` gains for free but its atoms scan is left for a follow-up (separate consumer,
  separate equality check).

## Should know

- Apply order: 431 (expand, auto-applied by Migration Apply) then 432 (contract; Migration Apply applies it once every
  job table is idle, root ADR 0017a). 432 refuses without 431 registered.
- 432 holds ACCESS EXCLUSIVE on `catalog._tour_day_text` and `catalog.v_tour_place` from the replace until COMMIT, while
  its closing checks read the whole catalogue once with the new plans (seconds); TripPlanner and catalog HTTP day /
  place reads wait that long.
- Local bench (scratch PostgreSQL 16, ~880 live tours, ~29k placed atoms, ~17.6k `tour_place` rows, the reader SQL
  for 50 tours as `aa_app_user`, JIT off as on Dev, best of 4): before 192 ms, with 431 139 ms, with 431 + 432 56 ms;
  the whole view (26,400 rows) identical. Dev ran the old plan at ~3x the local time, so the expected Dev figure is
  well under the 200 ms target; the live EXPLAIN after apply is the proof.
- The plan cost estimate of the view is large (the `regexp_split_to_table` / `generate_series` row estimates of
  `_tour_day_text`): with `jit = on` and default `jit_above_cost`, PostgreSQL would JIT-compile the query (~1.2 s
  locally). Dev's evidence plan shows no JIT; if a future parameter group turns JIT on, this read needs `jit = off` on
  the tenant pool or a cost fix.
