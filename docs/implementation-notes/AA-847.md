## Decisions
- **253, not 252.** 252 is taken by the parallel AA-816 lane (`252_admin_users_e2e_exception_removed.sql`). Re-check
  at merge; if it moves, renumber and redo the Infra byte copy.
- **One liveness view, flattenable.** `catalog._live_tour` (not barrier, not granted) carries 225's whole `live`
  projection, so `v_tour` is rebuilt on it with identical columns and every place / graph view joins it instead of
  `v_tour`. Inside a barrier view a non-barrier view is flattened and its unused columns pruned: the per-tour photo
  LATERAL, cover join, duration regex and md5 of `v_tour` are no longer computed for each graph read.
- **`_live_stop`** (internal, not barrier) instead of a CTE copied into three views: `v_tour_stop`, `v_graph_node`
  and `v_tour_junction` read the same definition. The junction view reads the distinct live stop destinations once
  (`MATERIALIZED` CTE) instead of two EXISTS over `v_tour_stop` per row.
- **`_tour_day_text` and `v_tour_photo` also moved to `_live_tour`.** Not in the plan's list, same pattern, same rows
  (fingerprint test); `v_tour_day` / `v_tour_place` per-tour reads get cheaper too.
- **`v_destination`: cover photo folded into the existing per-id LATERAL** (`array_agg(path) FILTER (WHERE position
  = 1)`), instead of a hash join over the window of every matched photo per call. Per-id shape kept (lesson S238);
  no grouped shape until the probe shows it wins.
- **Kept for the probe to decide (255+):** `security_barrier` off on the graph views, the `catalog.graph.v1.1` columns
  on `v_tour_component`, an expression index on `raw_tours (COALESCE(source_group_id, tour_id)::text)`.
- **`v_component_embedding` has the filter columns** (`activity`, `intensity_level`, `season_months`) besides the
  plan's four: TripPlanner's `vector_topk` keeps `scan_where` inside the index-ordered scan, and those filters are
  component columns. Liveness inside the view (EXISTS over `_live_tour`); usable destination stays on the reader
  (`keep_where` over `v_tour_component`). Granted to `tripplanner` only. Created only where pgvector exists.
- **Closing check compares with counts taken at the start of the file** (as the file's role, `cis_owner` on Dev),
  not after switching back: the recipe's `SET LOCAL ROLE cis_owner` comes after the views, and the conftest replay
  (superuser) cannot run the `cis_owner` steps anyway.
- **conftest skips 253** like 244/245/246; `test_aa847_migration_253.py` applies it as `db_migrator` under the switch
  after 245/246 (errors not swallowed) and restores the 225/228/235 definitions at teardown.

### Slice C — content-validity gate, place fixes, /admin/places
- **One deterministic report, four checks, fixed reason codes** (`services/places/validity.py`): V1 duration
  (`ranged_heading`, `missing_day_numbers`, `duration_text_vs_days`, `extra_days`), V2 same place (`same_destination_names`,
  `near_duplicate`), V3 not a pin (`linear_feature`, `area_feature`), V4 day text (`no_day_text`,
  `day_text_not_naming`). Read as `cis_app` with the AA master tenant named in the SQL (cis_app's policies are
  `USING (true)`), the v_tour liveness rule on the base tables (no catalog read from CIS code).
- **Same-place rule** (V2b): same country, same distinctive name (geomatch tokens minus kind words; also the same
  letters run together, "Kuangsi" = "Kuang Si", "Mount Phousi" = "Phou Si Hill" with the local kind words kept),
  ≤ 2 km, ≤ 5 km when either point is the model's or an area. Clusters are cut at the keeper (no chaining through a
  third place, lesson S239). Keeper: geoapify point, then most live components, then id. Pinned by 12 labelled
  pairs (6 merge / 6 keep), false merges measured first (lesson S245 / AA-779). Extend the pair set from the probe's
  section 4 output and every admin fix.
- **Linear features hidden, area features drawn as areas** — the proposed answer to Nghiệp's display decision
  (`validity_fix.LINEAR_FEATURES_HIDDEN`, `locate.Located.hidden`): a linear feature is stored `suspect` +
  `review_reason='linear_feature'` + `area`, so no catalog view returns it and TripPlanner draws nothing; the name
  stays in the day text. If Nghiệp prefers a circle, flip the constant (store and fix both read it through
  `Located.hidden` / the constant) — no migration.
- **Pipeline (deploy before the paid run, slice D):** `geomatch.feature_kind` (extends geomatch, no new module) feeds
  `Located.precision` and `hidden` even for a Geoapify-confirmed point; `place_extract` maps in-tour duplicates to
  one keeper per tour (component ids unchanged — they come from the itinerary spelling); the store lookup and
  `upsert_destination` follow `duplicate_of` to a usable keeper, so a merged key never comes back as a new row.
- **Catalog-wide merge only through the admin fix**, dry run by default, same country, scoped by `country` and/or
  `source_id`; apply repoints `geo.tour_place`, `geo.tour_day`, `geo.place_name`, `acp_shared.place_card`,
  `shared.place_photo`, sets `duplicate_of`, writes the audit row LAST (CIS 248 chain lock) with every prior value;
  `undo=<audit id>` restores exactly those rows if they still hold the fixed values (409 otherwise, and on a second
  undo). Booking / TripPlanner rows are counted (or "not readable as the CIS runtime"), never written.
- **No day-parser change** (plan §C.4): ranged headings are listed with `ranged_heading`; fixing
  `itinerary_utils.parse_canonical_itinerary_days` / `catalog._tour_day_text` is a separate catalog-recipe migration
  + content issue, to propose to Nghiệp.
- **Trend:** each `tour_graph_build` stores `validity.stats_counts` in `geo.graph_build.stats['validity']` (a report
  failure is recorded as `{"error": …}`, never fails the build). `GET /admin/places/validity` caches the report 60 s
  per country (the whole catalog is ~1k tours, cheap, but a page flip should not re-run it).

## Tradeoffs
- Before/after evidence in CI is a fingerprint (row count + md5 of the ordered rows, read as `tripplanner`) of every
  contract view under 253 and under the restored old definitions, on seeded live / trashed / superseded tours,
  suspect and duplicate places, photos, atoms, a current and an old build. Dev evidence is the probe's fingerprint
  section before and after the apply (root audit folder).
- `ANALYZE` in the migration: cheap on these sizes, fixes stale `reltuples`; takes ShareUpdateExclusive until
  COMMIT (does not block reads).
