## AA-751 (X6): job table template, shape comparator, migration 242 (PR C1)

Plan: `AA-Ecosys/docs/audits/2026-10-16-S240-aa751/aa751_plan.md` §2 C1, §2.1. ADR 0003a decision 2.

### Decisions
- Template `shared/jobs/job_table_template.sql` is the plan text. `render()` drops full-line `--` comments
  before filling placeholders, so the header can name `{{schema}}` etc. without them being substituted, and
  the rendered SQL is statements only. It validates every value (schema `^[a-z_][a-z0-9_]*$`, no quote in the
  kind pattern, `extra_statuses` only `, 'a', 'b'`, `max_attempts_default` int >= 1) because the result is
  executed, and raises on an unknown or unfilled placeholder.
- Comparator `shared/jobs/job_table_shape.py`: the §2.1 API (`render`, `read_shape`, `compare`) plus
  owner kind-pattern constants, `load_template()` and `split_statements()` (for the statement-count test).
  `read_shape` pins `search_path = pg_catalog` with `set_config(..., true)` inside a transaction/savepoint
  and **restores the caller's path** before leaving: an asyncpg nested transaction is a savepoint whose
  RELEASE keeps a `SET LOCAL`, which would have changed the path for the rest of the caller's transaction.
- `compare()` also gets `allow_extra_columns=()` (beside the plan's `allow_extra_indexes`), and checks a few
  things the plan left implicit: trigger enabled (not `D`), no WHEN clause, no `UPDATE OF` column list;
  owner extra triggers / constraints are diffs. Trigger function config: owner ⊇ template (plan wording).
- Comparator formatted with AA-Booking's ruff config (line 120, its `ruff check` rule set passes,
  `ruff format` clean) so B2 can copy it byte for byte and Booking's `ruff format --check .` stays green.
  CIS flake8 passes too.
- 242 guards in the 237/239 style instead of the plan's bare `ADD CONSTRAINT`:
  - guard 1a: table exists, runner is a member of its owner (ALTER TABLE needs the owner on RDS);
  - `LOCK TABLE shared.job IN ACCESS EXCLUSIVE MODE` before counting, so no row changes between the count
    and the ALTERs, and no lock upgrade happens later in the file;
  - guard 1b: counts rows breaking each new CHECK and raises with counts + up to 5 ids per rule
    ("fix them first, nothing was changed"); an existing constraint with one of the three names must have the
    template definition, else it stops (drift);
  - guard 2 (shape after) and guard 3 (behaviour: `bk_`/`tp_`/bad names, running without lease,
    attempt -1 rejected; an UPDATE sets `updated_at` — each probe in a sub-block whose rows roll back, the
    trigger probe via a custom SQLSTATE `AA242`).
- The superseded 174 CHECK `(max_attempts >= 1)` is dropped **by definition** (dynamic `DROP CONSTRAINT %I`
  over every CHECK whose `pg_get_constraintdef` is exactly `CHECK ((max_attempts >= 1))`), not by the name
  `job_max_attempts_check`: no dependency on the auto-generated name (the plan asked to confirm the live
  name from the pre-check; this removes the need, the pre-check still reports it).
- `statement_timeout = '120s'` added (small table; the runner's default is 15 min).
- Status CHECK not renamed (`job_status_check` from 174 vs template `job_status_chk`): names are not part
  of the shape; renaming would only add a lock step.

### Changed (vs the plan)
- Plan said "use plain ADD CONSTRAINT"; the task asked for NOT VALID + VALIDATE or a pre-check guard. Chosen:
  the in-file pre-check guard (above). NOT VALID + VALIDATE buys nothing in one transaction: ADD takes ACCESS
  EXCLUSIVE until COMMIT anyway. Plain ADD CONSTRAINT stays as the last backstop.
- Integration test does more than the three plan cases: also `read_shape` restores the path, comparator
  mutation checks (NOT VALID constraint, missing trigger / index, extra index / column, wrong default,
  missing reloption, status set), 242 on the pre-242 shape (what Dev runs) + re-run no-op, guard refusals for
  each bad-row rule, refusal of a drifted same-name constraint.
- `CONTEXT.md` job runner: a "Table shape" bullet (template, comparator, the three CHECKs, trigger,
  reloptions, test-helper lease rule).
- No app runtime code changed.

### Tradeoffs
- Behaviour probes inside a migration write (then roll back) rows in a hot table; acceptable because the
  file already holds ACCESS EXCLUSIVE and runs only when every job table is idle (I1). They catch a CHECK
  that exists by name but does not do its job (lesson S236: check by behaviour).
- `compare()` reports owner-only columns / triggers / constraints as diffs (stricter than "template ⊆
  owner"): conformance should be exact; real owner extras are allowed explicitly (`allow_extra_*`).

### Should know
- conftest swallows migration errors; `test_242_is_registered` + `test_shared_job_matches_the_template` are
  what catch a 242 that failed in CI.
- F16 test helpers fixed: `test_aa727_waves._job`, `test_aa825_retention_jobs.job`,
  `test_aa797_tenant_admin` running insert now set `locked_by='test'`, `locked_until=now()+5 min`.
  Mutation check: without those fixes 4 tests fail with `job_lease_chk` under 242.
- Grep of every kind literal / `KIND =` constant in `services/`, `shared/`, `api/`, `tests/`: all match the
  CIS pattern. The live data is checked only by the pre-check
  (`AA-Ecosys/docs/audits/2026-10-16-S240-aa751/c1_precheck.py`, read-only ECS exec, mandatory before merge).
- Migration lint: `run_migration.py --inspect` on 242 → no errors, not destructive (DROP CONSTRAINT is not
  in the destructive regex).
- PG 14+ is needed (`CREATE OR REPLACE TRIGGER`); Dev and CI are PG 15.
- Rollback = migration 243 (SQL in the 242 header).

### Review fixes (c1 review, S240)
- `read_shape` no longer restores `search_path` in a `finally`: after a failed catalog query the
  transaction is aborted and the restore raised `InFailedSQLTransactionError` over the real error
  (reproduced on PG16: `read_shape(conn, 'nope')` gave "current transaction is aborted"). The restore now
  runs only on success; on error the savepoint rollback undoes the transaction-local pin. The table is
  resolved first with `to_regclass`; a missing `<schema>.job` gives an empty Shape, so `compare()` reports
  "table not found or has no columns" (B2's first Booking run, or a wrong schema name). Integration cases:
  missing schema, and an injected failing catalog query surfaces its own `UndefinedColumnError` with the
  caller's transaction and path intact (both fail on the old code).
- `compare()` reports a trigger whose `tgenabled` is not `O`/`A` ("trigger not firing in origin sessions
  (tgenabled=R|D)"), matching 242 guard 2 (`O`); `A` (ALWAYS) is accepted because it fires in every session.
  Unit cases for O/A/D/R. The old message "trigger disabled" is gone.
- Unit test: every kind in `registry.kinds()` (after `import services.jobs`, the worker's import),
  `ops_alerts.KIND` and the retention kinds matches `CIS_KIND_PATTERN` with `re.fullmatch`, so a new kind
  that `job_kind_chk` would reject fails CI, not the first enqueue on Dev.
- The C1 pre-check (`AA-Ecosys/docs/audits/2026-10-16-S240-aa751/c1_precheck.py`, not in this repo) now
  also requires CREATE on schema `shared` and, if `shared.job_set_updated_at()` already exists, that the
  runner is a member of its owner. 242 itself is unchanged (byte copy in AA-CIS-Infra): a missing privilege
  there still fails the whole file cleanly with a permission error.

# AA-751 — C3: remove the readers of the dropped `acp_shared.acp_runs`

Plan: `AA-Ecosys/docs/audits/2026-10-16-S240-aa751/aa751_plan.md` §6 (fact F8). Other AA-751 PRs in
this repo (C1: job template + migration 242) may add their own section to this file.

## Decisions

- **Nothing moves to `shared.job`.** The readers point at a table CIS migration 121 dropped; any call
  fails with "relation does not exist". Stuck work is already covered by the `shared.job` reaper and
  the admin Jobs page.
- **`services/acp_shared/cost_utils.py` deleted as a whole file**, not only `record_stage_cost` /
  `finalize_run_cost`. The plan said "the whole file if nothing else is in it"; the two remaining
  helpers (`calc_bedrock_cost`, `extract_usage_from_response`) have no importer anywhere in the repo
  (git grep for the module and both names: 0 hits outside the file). LLM cost now comes from the
  Model Gateway (`shared.llm_call_log`), so keeping two dead helpers had no value.
- **`infrastructure/canary/` is kept.** It is Terraform (`aws_scheduler_schedule
  aa-cis-dev-acp-canary-weekly`, IAM role `aa-cis-dev-canary-scheduler-role` + inline policy) with
  no backend block, so whether it was ever applied is unknown from the repo. Per the task brief it is
  not deleted until the orchestrator confirms the live schedule is absent. Note its
  `account_id = "[acc1 id]"`: it targets **acc1**, so the check must run on acc1
  (`pqnghiep-admin`) as well as acc2 (review c3: plan §6 names only the acc2 command). Both must
  return ResourceNotFound / NoSuchEntity before `infrastructure/canary/` is deleted:
  `aws scheduler get-schedule --name aa-cis-dev-acp-canary-weekly --group-name default --profile pqnghiep-admin --region us-west-1`,
  `aws iam get-role --role-name aa-cis-dev-canary-scheduler-role --profile pqnghiep-admin`, and the
  same two with `--profile aa365-admin`.
- **Guard scans `api/`, `services/`, `shared/` and `worker/`** (`worker/` added to the plan's three
  dirs; it is runtime code too). `*.py` only, so `.sql` migrations are not scanned; `tests/` is not
  scanned, so the integration conftest FK stub stays legal.
- **Guard scans the whole file text, not line by line** (review c3): SQL in triple-quoted blocks
  often splits `FROM` and the table name across lines, which a per-line scan misses. Line numbers
  come from the match offset. The regex also catches the bare `acp_runs` (schema-less) form, since
  a `search_path` could resolve it; the tree has 0 hits for it today.
- The guard also self-tests its regex (SQL forms caught; FK comments, `acp_v2_runs` and prose
  "written to shared.acp_runs" ignored), self-tests the multi-line scan, and asserts the scanned dirs exist, so a rename cannot turn
  it into a silent no-op.
- The regex covers `shared.acp_runs` too: that look-alike table (migration 009) was never dropped,
  has no reader, and is the Dead Table Registry candidate in plan R1.

# AA-751 — C2: in-process ops metrics sampler (AA/RDS + AA/Jobs/CIS), AA-832 chain removed

Shared contract approved by Nghiệp in S240 (~US$1.75/month CloudWatch for AA-832 + AA-751 together):
the AA-832 chain "EventBridge every 5 min -> ops-probe Lambda -> POST
/admin/job-runner/rds-role-connections/schedule -> shared.job row -> CIS worker -> PutMetricData" is
replaced by a loop inside the api, and the job backlog metrics of plan §5 are added. Infra (alarms,
IAM, schedule removal) and Booking are separate PRs.

## Decisions

- **Sampler lives in the api, not the worker** (`api/core/ops_metrics_sampler.py`, same shape and
  lifespan placement as `aa859_main_pool_gauge.py`): the job metrics must not depend on the worker
  they measure. First tick 30 s after start (the app finishes starting; a restart costs < 1 sample),
  then every 300 s. Off when `ENVIRONMENT == "test"` (no new env var: underscore env vars are edited
  by hand, the global rule).
- **One PutMetricData per namespace per tick**, each part in its own `try`: a DB error or an
  AccessDenied on `AA/Jobs/CIS` (before the Infra IAM change) never stops `AA/RDS`, and the reverse.
  Failures go into the tick's `ops_metrics_sampled` line (`rds_error` / `jobs_error`, level warning);
  nothing is raised. The CloudWatch client is built once in a thread (rebuilt next tick if that
  failed) with `Config(connect_timeout=3, read_timeout=5, retries={"max_attempts": 1})`.
- **AA/RDS names, units and dimensions unchanged** (`RoleConnections` Count, `RoleConnectionLimitPct`
  Percent, `Role`), so the existing AA-832 per-role and sampling-stopped alarms keep working.
  `ROLE_CONNECTIONS_SQL`, `role_samples`, `metric_data` moved into the sampler module verbatim.
- **Backlog logic in `shared/jobs/backlog.py`**: four read-only queries on one connection (DB clock +
  last-freed time, due queued rows per kind, running rows, `shared.job_worker`), then a pure
  `backlog_sample(queued, running, workers, kinds, now, last_freed_at)`. Uses each live worker's
  **registered caps** (`shared.job_worker.caps`) for "would it claim", and this process's registry
  only for `background` and `expected_seconds` (loaded with `load_kinds()` in a thread).
- **`claim_caps_for(max_parallel, caps, free_slots, running_background, background)`** extracted from
  `Worker.claim_caps` (the plan's signature plus `background`: the pure function cannot read the
  registry). `Worker.claim_caps` delegates; a parity test runs both over max_parallel 1-8, free 0-8,
  running background 0-2. `background_reserve_for` / `background_kinds` extracted the same way.
- **Yielding workers are not claimers**: a live worker of an older task revision, while a newer one
  has beaten within `NEWER_WORKER_SECONDS`, stops claiming (AA-711); counting its free slots would
  read a deploy's drain as starvation.
- **F18**: `queue.claim()` now also sets `progress = coalesce(progress,'{}') ||
  jsonb_build_object('attempt_started_at', now())`. Handlers already merge progress; the only reader of
  `ctx.job.progress` keys besides the Jobs page are `retention_job.run_spec` (`cursors`,
  `deleted_total`) and `s1_rewrite_job` (`version_id`) — unaffected. The sampler parses the key in
  Python (bad value -> falls back to `started_at`), so one odd row cannot fail the query.

## Changed (vs. plan §5)

- **Publisher**: §5 put the CIS sample inside the `/rds-role-connections/schedule` handler; the S240
  contract replaced that with the in-process loop and **removed** the endpoint, the
  `ops_rds_role_connections` kind (`services/jobs/ops_rds_role_connections_job.py`), its unit test file
  and its integration test (rewritten as `tests/integration/test_aa751_ops_metrics_sampler.py`).
- **Starvation age is bounded by when capacity last freed (deviation, for review).** §5 reports
  `now - run_after` of a starved row. For case (b) ("a live worker would claim it now") that pages on
  a normal wave: the worker polls every 5 s, so in the seconds between an `s1_rewrite` finishing and
  the next claim the kind is under its cap with a free slot, and the next row may have waited 40 min.
  At ~15 finishes per 5 min that is ~12 % of samples, and the alarm fires on 1 datapoint. So the age
  is `now - max(run_after, freed)`, where `freed` is the latest job finish (`max(finished_at)`, on
  `job_finished_idx`) or re-queue (`max(updated_at)` of queued rows with `attempt > 0`), or the
  claiming worker's `started_at`; with several claiming workers, the one free the longest. For
  "no live worker" the age runs from the last time any worker was seen (a crash pages after 15 min,
  not instantly for an old wave row); for an unregistered kind (no live worker has it in `caps`) it is
  plain `now - run_after`, so the Window B `x6_probe` (run_after now - 20 min) still fires on the next
  sample.
- `deploy_gate_exempt` stays as a registry flag and router behaviour; tests now use a test-only kind
  (`aa751_test_exempt`), and `exempt_kinds` is `[]` today. Comments in `registry.py`,
  `admin_job_runner.py` and `.github/workflows/deploy-dev.yml` updated.

## Tradeoffs

- The global "last freed" signal can hide a starvation bug of one kind while other kinds keep
  finishing jobs; it shows once traffic stops, and a stuck slot still shows as overdue-running. A
  per-kind/per-worker freed time would need locked_by on finished rows (cleared today). Accepted:
  the alarm's job is "the queue is stuck", and a false page in every wave would get it ignored.
- No extra state across ticks (a "claimable at two ticks" rule): it still pages on two transient hits
  and loses its memory on every restart.
- Two api tasks (rolling deploy, autoscaling) both publish: the alarms use Maximum / SampleCount, so a
  duplicate changes nothing; PutMetricData requests double (cents).

## Should know

- **Rollout order (CIS side) — Infra schedule removal first, the only allowed order.** The new
  worker has no handler for `ops_rds_role_connections`, so a queued row would sit forever — starved
  (`unregistered`, queue-age alarm) and blocking the next Deploy Dev (no longer exempt). "Deploy CIS
  between two 5-min ticks" does NOT work: deploy-dev rolls api and worker together, the old worker
  yields (`newer_worker_alive`) as soon as the new one is fresh, while the old api keeps serving the
  schedule endpoint for the 2-5 min roll, so a Lambda tick in that window enqueues a row nobody claims.
  Safety net (review fix): `shared.jobs.registry.RETIRED_KINDS` + `queue.cancel_retired_kinds` — every
  sampler tick cancels queued/running rows of a retired, unregistered kind (error
  `kind removed (AA-751)`, `retired_cancelled` in the log line) before the backlog sample, so a
  leftover is gone within one tick (<= 5 min, under the 900 s queue-age threshold). Verification after
  the deploy stays manual: `GET /admin/job-runner/jobs?kind=ops_rds_role_connections&status=queued`
  (and `running`) is empty. Until the Infra schedule is gone the Lambda gets a 404 from the removed
  path; its handler logs non-2xx and does not raise. Drop the `RETIRED_KINDS` entry in a later PR.
- Until Infra adds `AA/Jobs/CIS` to `cis_ecs_task_put_metric_aa_rds`, every tick logs `jobs_error`
  AccessDenied (warning). AA/RDS keeps flowing.
- The AA-832 `rds-role-connections-sampling-stopped` alarm (45 min) covers the gap between the last
  Lambda sample and the first in-process one.
- Live verify after deploy: CloudWatch Logs `/ecs/aa-cis-dev`, stream prefix `api/`, filter
  `ops_metrics_sampled` (one line per 5 min with `roles`, `oldest_queued_age_seconds`,
  `overdue_running_jobs`, no `*_error` after the IAM change); `get-metric-statistics` on `AA/RDS`
  RoleConnections (Role=aa_app_user) and `AA/Jobs/CIS` OldestQueuedAgeSeconds.
- Tests: `tests/unit/test_aa751_ops_metrics_sampler.py` (mocked pool/boto3), integration
  `tests/integration/test_aa751_ops_metrics_sampler.py` (real shared.job / shared.job_worker rows,
  role creation needs SUPERUSER as in CI).

## Review fixes (S240)

- **Retired-kind sweep instead of a migration / post-deploy step.** A one-off migration cleans only at
  the moment it is applied (DB Migrate runs before the roll, and the leftover appears during it) and
  needs an Infra copy; a deploy-dev step has no DB access and would need a new admin endpoint. The
  sampler already ticks every 5 min in the new api, so it sweeps after the roll with no new surface.
  Only kinds listed in `RETIRED_KINDS` and not registered are touched; the lock is cleared so an old
  worker still finishing the row cannot overwrite `cancelled` (`_finish` matches `locked_by`).
- **Per-part timeout.** `PART_TIMEOUT_S = 60` via `asyncio.wait_for` on each of the 3 parts (and on
  the first registry load); 3 x 60 s < the 300 s interval. Chosen over `timeout=` on each
  fetch/acquire so `backlog.sample` keeps a plain signature and every await of a part is covered.
  asyncpg releases a connection whose acquire/query is cancelled.
