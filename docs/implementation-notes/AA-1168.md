# AA-1168 — EU AI Act Art. 50: disclosure and machine mark on every publish channel (CIS)

Lane l8-ai-act-marking, S286. Builds on AA-1040 (`AA-1040-marking.md`): the HTML mark (`data-ai-*` on `<article>`,
`<meta name="ai-*">`), the `X-AI-*` download headers and `piece.ai` in the tenant JSON were already live. The root
AI Use Register (v1.15) records the channel table and the register guard; this file covers the CIS code only.

## Decisions

- **One wording everywhere:** `ai_marking.DISCLOSURE_TEXT` = "This content was created with the help of AI." It is
  shown to the public reader of a tenant's post, so it names no product and does not say who reviewed it (a
  "human-edited" variant would claim a review the system cannot prove; the machine mark carries `human_edited`).
  English only: `acp_shared.content_piece` has no language column and every T9 prompt writes English today.
- **WordPress and the HTML exports:** the disclosure is the last paragraph inside the `<article>`
  (`<p class="ai-disclosure" data-ai-disclosure="true"><em>…</em></p>`), added by
  `render_content_text_to_fragment()` whenever a mark is passed, so the published post, the embed fragment and the
  downloadable document all show it. `class`, `data-*` and `<em>` survive `wp_kses` for every WordPress role. Placed
  at the end, not the top: the first paragraph is what search engines and social cards quote.
- **WordPress post meta:** the REST call also sends `meta` keys `ai_generated`, `ai_generator`, `ai_model`,
  `ai_generated_at`, `ai_human_edited`, `ai_digital_source_type` (string values, no leading `_`, which would make them
  protected meta). WordPress stores a key only when the site registered it (`register_post_meta(..., ['show_in_rest'
  => true, 'single' => true, 'type' => 'string'])`) and silently ignores the others, the same way the Yoast keys
  already travel. So the post meta is a best effort for sites that opt in; the HTML mark stays the one every site
  keeps. No JSON-LD `<script>`: WordPress strips `<script>` for users without `unfiltered_html`, and the HTML
  sanitizer of AA-1167 will strip it on the publish path too.
- **Facebook:** the Graph API Page feed has no metadata field for a text post. The message is the piece text, a
  blank line, the disclosure and the `#AIgenerated` hashtag (the token software can find in the text).
  `dispatch.facebook_message()` builds it for both the post and the AA-726 retry lookup (`find_remote`), and it does
  not read the mark, so a later edit stamp or a filled-in model never changes the text the lookup searches for.
- **Plain-text export:** a saved `.txt` keeps no HTTP headers, so the body now ends with `---`, the disclosure line
  and one machine-readable line: `AI-Content: ai-generated=true; ai-generator=…; ai-model=…; ai-generated-at=…;
  ai-human-edited=…; digital-source-type=<IPTC trainedAlgorithmicMedia URI>` (the same names as the meta tags;
  `;` and line breaks inside a value are replaced so the line always parses). The `X-AI-*` headers stay.

## Changed

- `services/acp_content_writing/ai_marking.py`: `DISCLOSURE_TEXT`, `SOCIAL_DISCLOSURE_TAG`, `TEXT_MARK_LABEL`,
  `disclosure_html`, `social_message`, `text_mark_line`, `text_with_disclosure`, `wordpress_post_meta`.
- `services/acp_content_writing/export.py`: the fragment ends with the disclosure when `ai` is given (no `ai` keeps
  the AA-613 output byte for byte); new `render_content_text_to_plain`.
- `api/routers/v1_content_writing.export_piece`: `format=text` body through `render_content_text_to_plain`.
- `services/acp_s4_blog/cms/base.BlogContent.meta` (default empty) and `wordpress.create_post` merges it into the
  REST `meta` next to the Yoast keys.
- `services/acp_publish/dispatch.py`: blog posts carry `meta=wordpress_post_meta(mark)`; `facebook_message()` for
  the post and the retry lookup. The publish functions are otherwise unchanged (AA-1167 adds the sanitizer there).
- Tests: new `tests/unit/test_aa1168_ai_disclosure.py`; `test_aa1040_ai_marking.py` (the Facebook message and the
  text export body now carry the disclosure, by design).

## Tradeoffs

- A disclosure in the tenant's own post changes their text. The alternative (mark only, no visible line) leaves the
  Art. 50 duty to each tenant with no help; the tenant AI Schedule [●].4(b) still lets them add whatever a channel
  requires. Making the line switchable per tenant would be a setting with legal weight: left to the tech lead and
  counsel (follow-up), not invented here.
- The hashtag is a weak machine mark (people can type it too), but it is the only token a Facebook text post can
  carry; the strong record stays in the piece (`writer_input.ai_provenance`) and its `publish_log` row.

## Should know

- No migration, no new setting, no new route (openapi unchanged).
- A Facebook publish retried across this deploy (first attempt before, retry after) would not find the earlier post
  by message and could post twice; the AA-726 window is minutes and Dev has no live tenant posts in flight.
- Live check after deploy: publish one blog piece to the WordPress test site and read the post with REST
  `context=edit`: `content.raw` ends the `<article>` with the disclosure paragraph and keeps `data-ai-generated`;
  `meta` shows the `ai_*` keys only if the test site registered them (it does not by default). Publish one Facebook
  piece to the test Page and read it back with the Graph API (`message` ends with the disclosure and
  `#AIgenerated`). Download one `format=text` export: last line starts with `AI-Content: ai-generated=true`.
