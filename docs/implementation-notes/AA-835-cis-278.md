# AA-835 S5 — CIS migration 278 (supply content storage + catalog.v_supply_content)

Slice S5 of AA-835 (root ADR 0004a). Storage only; the consumer, draft job and review API are S6
(`AA-835-s6.md`). Key 278 per SCHEDULE S250 §1 (the plan said 275).

## Decisions

- **Explicit grants, no default ACL.** The plan let cis_app get DML from the cis_owner default ACL. SCHEDULE §5
  point 3 (AA-859 invariant, the 272 / 276 pattern) asks for an explicit REVOKE from PUBLIC, cis_app, aa_app_user
  and catalog_owner, then exact grants. cis_app gets SELECT/INSERT/UPDATE on four tables and SELECT/INSERT on the
  inbox (append-only). Nobody gets DELETE: the DM-7 rows (S250 R2) are still "proposed", so no retention runs yet.
- **Version content is immutable in the DB.** A BEFORE UPDATE OR DELETE trigger refuses any change to a version's
  text, photos or provenance, allows only draft -> approved | rejected | superseded and approved -> superseded, and
  refuses a delete unless the version is rejected / superseded and older than 180 days (the proposed DM-7 window).
  An edit is always a new `human` version. One approved version per entity (partial unique index).
- **`published_version_id` is a composite FK** `(id, published_version_id) -> supply_content_version (entity_id,
  id)`, so an entity can never point at another entity's version. It is kept after an unpublish (base for the
  next diff).
- **`llm_job_id` instead of `llm_call_id`.** `shared.llm_call_log` rows already carry `job_id` (bound by the
  worker), so the job id links a draft to its cost rows without a second id column on the log.
- **Photo URLs are stored, not built in the view.** The CDN base is an env setting in code
  (`services/photos/sync.cdn_url`, `PHOTO_CDN_BASE`); the view cannot read env. S6 writes `url_1600` / `url_600`
  when it copies a rights-cleared photo, and the view serves `url_1600` only for media with `usage_rights`,
  `active` and a copy. A CHECK keeps the copy columns all-set-or-all-NULL and the URLs `https://`.
- **The view shows text only when it is safe.** `description`, `highlights`, `good_to_know` and `photo_urls` come
  from a LEFT JOIN that requires `content_status = 'published'`, `active` and an `approved` version. Any other row
  has NULL text, so a stale or unpublished entity can never leak old text into a proposal.
- **`content_version`** is the published version's number while published, else the newest version's number (NULL
  when none), so the Booking badge can show progress.
- **Read-back view columns** match what AA-Booking S4 (`app/supply/content.py`, PR #86) feature-detects:
  source_system, source_id, entity_type, content_status, content_version, description, highlights, photo_urls,
  edit_url. Two extra columns: good_to_know and published_at.
- **SELECT on the view to booking only**, not tripplanner or aa_app_user (nobody else reads it). Covered by the
  existing `catalog.*:booking` contract (owners.yaml cis consumer_grants, rls_catalogue_rules rule g); verified on
  Infra main before relying on it.
- **Stage + budget seeded here:** `supply_content_writer` (writer, claude/sonnet, acc3, no fallback, no shadow) and
  `bedrock / job:supply_content_draft` ($0.10 per run, $1.00 per day, hard stop). Both ON CONFLICT DO NOTHING.
- **The conftest replay applies part A only** (as 274): the catalog recipe of part B needs 245's owners.
  `tests/integration/test_aa835_migration_278.py` applies the whole file the DB Migrate way on the RDS-like state.

## Changed (vs the plan)

- File name and key: `278_supply_content.sql` (plan: 275).
- `supply_event_inbox`: outcome `applied | skipped_older | missing` (no `duplicate` row: a duplicate key is an
  `ON CONFLICT DO NOTHING`, counted by the consumer). `missing` = the entity is gone from the Booking facts view.
  Columns `supply_version` (the event's) and `facts_supply_version` (the facts row read with it).
- `supply_entity` gains `title` and `country_code` (admin list), `supply_media` gains `active`, `content_type`,
  `width`, `height`, `url_1600`, `url_600` and `copied_sha256` (copy integrity: the bytes copied must match
  Booking's sha256).
- `rls_catalogue_rules.py` rule g: the four `booking.v_supply_*:cis_app` contract grants of bk-023 (the Infra copy
  of this file must be refreshed in the 278 copy PR; Infra #357 left them out on purpose).

## Tradeoffs

- No in-file behaviour probe (276 has one). The view logic is covered by the integration test instead; the
  closing check in the file only asserts that no non-published row carries text.
- No EXPLAIN gate for the `source_id = ANY(...)` read: Dev has a handful of hotels and services; the filter is on
  the base table column (pushed down through the security barrier, texteq is leakproof).

## Should know

- Apply order: 275, 276, 277, then 278 (no gaps). The S6 code PR must not deploy before 278 is applied.
- Booking's read-back turns on by itself once the view exists with the booking grant.
