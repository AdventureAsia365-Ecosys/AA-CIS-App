Linear AA-979 (card CRM-P2, root ADR 0010 §6). Stage P2a moves `portal/` into
`AdventureAsia365-Ecosys/AA-Partner/portal` with its history, on the same Vercel project (`aa-cis-portal`) and the
same tenant API-key sign-in. This file covers the AA-CIS-App side (P2a-3); the move itself, the Partner deploy

agent Claude Code.

## Decisions

- **Cut** = `d1e0eb43` (main after #980). `portal/` tree at the cut: `ba736844f356f5d13aa40e4fc378c460e5efbfb7`,
  118 files. AA-Partner's imported `portal/` has the identical tree id.
- **Freeze guard, not deletion.** `portal/` stays here, unchanged and undeployed, until P2b + 7 days (ADR 0010 §6), so
  a rollback to the CIS-built deployment stays possible. `tests/unit/test_aa885_portal_split.py`
  `test_portal_copy_is_frozen` pins the tree id: any commit that changes a byte under `portal/` fails Unit Tests,
  with a message that says to make the change in AA-Partner.
- **No CIS workflow deploys the portal any more**: `vercel-deploy-portal.yml` and `ui-smoke-portal.yml` are deleted,
  and the test that checked them is inverted ("no CIS workflow deploys the portal or calls its smoke").
- **Portal smoke moved**: `tests/e2e/smoke-portal/` and the Playwright projects `smoke-portal-setup` / `smoke-portal`
  are removed (the specs live in AA-Partner `e2e/smoke-portal/`).
- **Dependabot**: the `/portal` npm entry is removed (a security PR against a frozen copy would fail the freeze guard).
- **Byte-copy tests of the vendored kit dropped** from `test_aa885_portal_split.py`: the frozen copy cannot follow a
  kit change here (the freeze guard would fail), and AA-Partner's "Vendored CIS copies" check now compares its
  `portal/` kit with `frontend/` on CIS main. A kit change here is copied into AA-Partner `portal/` afterwards.
- **`test_aa760_muted_contrast.py`** checks `frontend` only, and the "admin and portal share the muted palette" test
  is gone: an admin palette edit must not force an edit of the frozen copy. AA-Partner checks the portal tokens.
- **Kept**: "Portal Build" (the frozen copy still builds; it is a required check, removed with `portal/` in the
  deletion step by the admin login), "Portal Lint" (non-required), the admin-side tests (308 to the portal host, gate
  and rbac staff-only, tenant proxy staff-only) and the other tests that read portal files (aa820, aa886, aa911,
  aa760 metering, login cross-links): they read frozen files, so they stay green and still describe what is live
  until the Partner deploy replaces it.

## Tradeoffs

# AA-979 P2b: Content studio sign-in with the partner pool (CIS side)

Session S252, agent Claude Code. Branch `feat/aa-979-tenant-session-exchange`. Design:
`AA-Ecosys/.tmp-session/s252/aa979/design.md` §2.6 (critic-fixed); root ADR 0010a (same session). This phase ships
everything up to, but not including, the DNS cutover of `portal.` and the `/trip` slice.

## Decisions

- **Own verifier for the partner pool** (`api/core/partner_identity.py`): PARTNER x {partner-web}, Dev pool and
  client ids as code constants with an env override, exactly like `identity_config.py` / `m2m_auth.py`, so the ECS
  task definition needs no new variable (critic S3; the S250 template-drift lesson). It is never added to
  `cis_staff_issuers()`; a test pins that. Its issuer must differ from the WORKFORCE and M2M issuers (503 otherwise).
- **Foreign tokens answer 403, not 401** (card R reads as a refusal): a token whose unverified `iss` is the WORKFORCE,
  the M2M or any other Cognito pool is `forbidden`; only the status code depends on that peek, never a grant.
- **Exchange answers from `shared.tenant_members` only**: active rows of `(iss, sub)` on active, not offboarded
  agencies. One row -> session; several and none chosen -> 409 `choose_tenant` (the portal's chooser reads
  `GET /auth/tenant-memberships`); the CRM role plays no part (ADR 0010 §7).
- **The minted token is the existing tenant JWT plus four claims**: `client=portal` (unmetered, AA-760), `amr=partner`,
  `mid`, `csr`; `exp = min(now + 15 min, access token exp)`. Every `/v1/*` route and `/auth/verify-tenant` accept it
  unchanged, so no route changed.
- **Throttle per identity** (12-hex fingerprint), 30 per minute, Redis, fail open (critic S2: all portal calls leave
  through one NAT address on Fargate).
- **Role enforcement is one middleware** (`api/middleware/tenant_role.py`), not a change in each dependency: the
  tenant JWT is accepted by `v1_tours.get_tenant`, inline checks in `v1_tours` and `admin_atoms`, and the tenant
  branch of `/admin/brand-identity`. The middleware reads `csr` from any valid tenant JWT on `/v1/*` and
  `/admin/brand-identity`: viewer = read methods only; editor = no non-read call under `/v1/integrations`,
  `/v1/account`, `/v1/webhooks`; owner and API-key tokens (no `csr`) unchanged; unknown `csr` = viewer.
- **Fix round 2 (review): role check fails closed on the header shape, and the dependencies check too.** The routes read
  the token with FastAPI `HTTPBearer` (scheme compared case-insensitively, value stripped on the pinned 0.161), so
  `bearer <t>` or `Bearer  <t>` reached the route while the first middleware (exact `Bearer <t>` only) skipped it:
  a viewer copying their own token could write. Now the middleware checks every credential it can find in every
  Authorization header (the HTTPBearer-style value, plus each whitespace part, at most 8) and refuses when any tenant
  JWT with `csr` is refused; and `v1_tours.get_tenant` and `admin_pipeline._resolve_brand_tenant_id` call
  `tenant_role.enforce(request, payload)` on the token they accepted (403 `studio_role_forbidden`). `request` is a
  new trailing `Request = None` parameter, so the existing direct calls in tests keep working without a check.
- **Activation** is `POST /tenant/membership/v1/invitations/{invitation_id}/activate`, M2M scope
  `cis.tenant/activate` (contract `tenant.membership.v1` 1.1, additive). The identity must be of the partner pool.
  Same identity again = 200 `changed: false` (the CRM's retry); another identity / removed / a second live membership
  = 409 with `reason`. One transaction + audit `tenant.member_activated` (fingerprint only).
- **Staff invite through the CIS relay** (critic S4): `POST /admin/tenants/{id}/members/invitations` creates the
  `invited` row (audit `tenant.member_invited`), then relays `{email, cis_invitation_id, locale}` to the CRM
  `crm.ops.v1` `POST /tenants/{id}/studio-invitations` with the staff member's own Cognito token
  (`crm_console.crm_ops_call`, path allow-listed). The e-mail is never stored or logged in CIS. A failed delivery
  still answers 201 with `delivery.status = failed`; `.../members/{membership_id}/invitation/send` sends it again.

## Changed

- Design §2.3 / §6 had an optional `crm_role` on the studio invitation. Dropped: a CRM role passed through CIS would
  be "a CIS event granting a CRM role", which ADR 0010 §7 and design §8 forbid. A person who also needs a CRM role
  gets the CRM's own invitation (owner Team page, or the AA L1 first-owner invite).
- `/trip/*` 307 and `TRIP_PAGE_BASE_URL` are NOT in this PR (orchestrator: the `/trip` slice comes after cutover).

## Tradeoffs

- 15-minute studio sessions mean the portal BFF re-exchanges often; that is the price of "a removed member loses the
  studio within 15 min" without a revocation list.
- Middleware AND dependency (round 2): two places check `csr`; the middleware still covers routes that read a tenant
  token in some new way, the dependency covers header shapes the middleware did not foresee. Cost: one more HS256
  decode per tenant call. The local venv has FastAPI 0.110 (no strip); the dependency test reads
  `get_authorization_scheme_param` and expects 401 for `Bearer  <t>` there, the role result on the 0.161 pin.
- Middleware vs dependency: a middleware decodes the HS256 token a second time per tenant call (microseconds) but
  cannot be forgotten by a new route.

## Should know

- No CIS migration and no task-definition change. Deploy is gated by `shared.job` / wave as usual.
- The CRM must request `cis.tenant/activate` in its own token request, and AA-CIS-Infra must add the scope to the
  `cis.tenant` resource server and grant it to the CRM M2M client (Infra PR-1) BEFORE the CRM's activation job runs;
  until then the CRM's call is 403 and its job retries.
- Contract: root `docs/contracts/tenant.membership.v1.openapi.yaml` 1.1 is the source; this repo's copy is
  byte-identical and pinned by sha256 in `test_aa978_tenant_membership_contract.py`. Merge the root PR first or in
  the same window.
- Verify live after deploy: `POST /auth/tenant-session` without token 401; a `cis-admin` Cognito token 403; an M2M
  token without `cis.tenant/activate` on activate 403.

## Contract 1.2: `is_synthetic` on getTenantMembers (S252, A10b-1 hardening)

- Decisions: `TenantMembers.is_synthetic` = `shared.tenants.is_canary IS TRUE` (CIS 058; CIS 281 made the column
  nullable, so NULL is served as false and the field is never null). Read in the same `TENANT_SQL` row as
  `tenant_state`; no new query, no migration, no grant (cis_app already reads `shared.tenants`).
- Changed: the snapshot body and so its ETag carry the flag; flipping `is_canary` moves the ETag (a CRM holding an
  old tag gets a fresh 200).
- Tradeoffs: a required field in a minor (contracts rule 2 allows it); the only consumer that reads it is the CRM's
  A10b check, which refuses a 1.1 answer without it, so CIS must deploy 1.2 first.
- Should know: the copy in `docs/contracts/` is the root 1.2 file byte for byte (sha256 pinned). `docs/api/openapi.json`
  was edited by hand for the two `is_synthetic` lines only: the local venv (FastAPI 0.110, pydantic 2.13) exports a
  different document from the CI pin, so a full local re-export would churn unrelated schemas.
