# AA-859 PR-D3 (W3): angle-gate choose and reopen on the tenant pool

Flag: `ANGLE_GATE_DECIDE_FLAG` = Redis `aa859:angle_gate_decide_pool` (declared in PR-S). Needs migration 241
(applied on Dev 16/10/2026). Plan: root `docs/audits/2026-10-16-S240-aa859/aa859_plan.md` § PR-D3.

## Decisions
- The transaction is opened by the router (`v1_angle_gate._decide`), the service functions take `conn`
  (plan: "functions take `conn` and `tenant_id`"). New signatures: `choose_angle(conn, tenant_id,
  request_id, idx) -> None`, `reopen_request(conn, tenant_id, request_id) -> None`. The only caller is the
  router (grep of api / services / shared / worker / scripts).
- Same pattern as `v1_integrations._disconnect`: `acquire_scoped_conn(..., fail_closed=True)`; on the tenant
  pool the transaction is acquire_scoped_conn's own (GUC LOCAL), on the main pool (flag off) the route opens
  `conn.transaction()` itself.
- The new single-transaction SQL runs on BOTH paths (flag on and off), as PR-A did for disconnect. Status
  codes and error texts are the old ones for every sequential call; only the race outcome changes (see
  Changed).
- Lock statement: `SELECT status ... FOR UPDATE` read with `fetchval` (status is NOT NULL, so None means
  "no row" = 404).
- Reopen has no lock statement: one conditional `UPDATE ... AND status = 'approved' RETURNING`; 0 rows ->
  re-read status on the same connection -> 404 or 409 (plan).
- Choose backstop: the approve UPDATE keeps `status IN ('pending_choice','reusable')`; 0 rows (only possible
  if the FOR UPDATE was not taken) -> `WrongStatusError` "changed while choosing" (409) with
  `aa859_angle_gate_choose_status_changed` logged at ERROR, and the transaction rolls the option change back.
  The concurrent integration test asserts the loser's message is the lock-step one, so removing the FOR
  UPDATE is caught even though the backstop keeps the data right.
- Error precedence kept from the old code: 404 (not this tenant's) -> 409 (status) -> 422 (idx out of
  0..2, before any option SQL) -> 422 (no option row for that idx).
- One log event per request, logged inside the scoped block right after acquire (so also for 404/409):
  `aa859_angle_gate_choose` / `aa859_angle_gate_reopen` with `tenant_id`, `request_id`,
  `used_tenant_pool`.
- `tenant_id = UUID(tenant["sub"])` stays at the top of each handler (old behaviour). The JWT `sub` is a
  uuid we signed, so acquire_scoped_conn's malformed-id 503 is unreachable here; a malformed `sub` fails at
  `UUID()` before any pool is touched (unit-tested).

## Changed
- `_OPTION_CHOOSE_SQL` is one statement `SET chosen = (idx = $2) WHERE request_id = $1` instead of the two
  UPDATEs (`chosen = true` for idx, `chosen = false` for the others). Same end state; it writes only
  `chosen`, the one column 241 grants UPDATE on.
- Old choose read the request (no lock) on one connection, then wrote on another: two concurrent chooses
  both succeeded (last write wins on `chosen`). Now the second waits for the first's lock and answers 409.
  Old reopen did read-then-UPDATE without a status guard; now a double reopen answers 200 then 409 (it was
  200/200 before, or 409 when sequential).
- `test_aa449_angle_gate_service.py` (TestChooseAngle, `_StatefulAngleOptionConn`), `test_aa497_reopen_angle.py`
  and `test_aa449_v1_angle_gate.py` (TestChoose / TestReopen now patch `fetch_request` and give the request a
  Redis that says "off") follow the new signatures.

## Tradeoffs
- Re-read on MAIN after commit instead of on the tenant connection: fetch_request reads `acp_shared.subject`,
  `acp_contract.atom_segment` / `route` (no aa_app_user grant until 243) and `shared.job` (no tenant column).
  D2 exception "fetch_request re-read after choose/reopen (until wave 4)". Cost: one extra main-pool acquire
  pair per decision, as before (the old code re-read on the main pool too).
- Kept the router-level orchestration (instead of a `request=` parameter on the service, as
  `fetch_latest_piece_for_request` does) because the decision and the re-read need different pools and the
  service would otherwise import the tenant-pool module.
