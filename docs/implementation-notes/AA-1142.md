# AA-1142 — Ecosystem status P2 (S292)

The four P2 features the S285 review picked for the Ecosystem status page (`/admin/overview`, items 9-12 of root
`docs/audits/2026-11-19-S285-session/ops-overview-v2-review.md`): SLO and error budget burn, the incident record with a
timeline, external synthetic checks, and the per-agency drill-down. Migrations CIS 485 (expand: three tables) and CIS
486 (contract: eleven settings) ship first as one migration-only PR; this code PR follows (readiness requires 485 and 486).
The root PR carries the External checks workflow, the DM-7.1 retention rows and the catalogue entries.

## Decisions

- **1. SLO per app, request-based where CloudWatch measures requests.** Availability = 1 - 5xx / requests over
  `cis.ops.status_slo_window_days` (30); objective `cis.ops.status_slo_target_pct` (99.5); budget left = 1 - (bad share
  / budget share). Burn rate = bad share of a window / budget share, over the fast window
  (`cis.ops.status_burn_fast_window_min`, 60) and the slow window (`cis.ops.status_burn_slow_window_hours`, 6). Fast
  burn above `cis.ops.status_burn_fast_factor` (14.4) = SEV2 Needs-attention item `slo-fast-<app>`; slow burn above
  `cis.ops.status_burn_slow_factor` (6) = SEV3 `slo-slow-<app>` (SRE Workbook: page / ticket). A window with fewer
  events than the CIS 475 `cis.ops.status_min_requests` is shown, not judged ("few events"), as for the traffic tiles.
  The budget bar turns amber at `cis.ops.status_slo_budget_warn_pct` (25 %) left or less and red when spent; the
  warn line is a setting served in `sections.slo.rules.budget_warn_pct` (review fix: it was a `< 25` literal in
  `lib/opsStatusP2.ts`), and the card's note names it.
  Sources: CIS and Booking API Gateway Count / 5XXError, TripPlanner's two Lambdas Invocations / Errors (the golden
  signal metrics); the partner CRM (no request metrics CIS may read) by its 5-minute health samples
  (`acp_shared.ops_sample` kind `app_health`; ok / warn good, degraded / down bad), basis "health samples".
- **SLO reads.** Two GetMetricData calls of 8 metrics: the burn windows on a 5-minute period (cached 5 min in Redis), the
  budget window on an hourly period (cached 1 h); never without Redis (the section says the cache is offline). At most
  about 2,500 metrics a day when a page stays open all day (0.025 USD a day), nothing when nobody looks. A new key
  (`cis.ops.status_slo_target_pct`) rather than the CIS 475 runtime uptime objective: that one judges sampler uptime per
  runtime, this one the share of requests without a server error per app.
- **2. Incident record = `acp_shared.ops_incident` + `acp_shared.ops_incident_update`** (CIS 485; CIS-private, DM-1.5,
  next to `ops_event`). No incident table existed (AA-1154 A0 stores nothing; AA-1140 has only `ops_event`), so this is
  the minimal record the S285 assistant advisory names (`ops_incident`: SEV, status, owner, open / resolved); the
  assistant's runs can carry `incident_id` later. "Declare incident" picks one of the open Needs-attention items (or
  none): the API checks the item is on the page now (as the ack route does) and refuses a second unresolved incident
  of the same item (409 with its id; partial unique index). Status investigating / identified / monitoring /
  resolved; `resolved_at` set exactly when resolved (CHECK), cleared on reopen. Owner = the person who declared it
  until someone "takes over". Every write: one `ops_incident_update` row per change + an `acp_shared.audit_log` row
  (`ops_incident_declared` / `ops_incident_updated`). Writes are `ops.write` and never the business owner (the ack
  route's rule, fails closed); the page shows the controls when `viewer.can_ack` is true (same policy).
- **Timeline** = the incident's own updates + `acp_shared.ops_event` rows (deploys, failed rollouts, alarms, service
  drops) of its app and `shared` (every app for a shared incident) from `cis.ops.status_incident_lookback_min` (60)
  before it was declared until resolved + the acks of its item. The `ops_event` kind CHECK stays as it is (no contract
  migration to add an `incident` kind); incident updates live in their own table.
- **"Write lesson"** links the lesson log of the public root repo (`skill/aa-lessons/lessons.md` on GitHub) and offers a
  draft line in the log's format to copy (`<principle> — <title> (SEV, app) → <cause> (incident N, date). Catch with:
  <guard>.`). The page cannot write to the root repo; a person finishes the line with a guard.
- **3. External checks run on GitHub Actions of the public root repo** (workflow `External checks`, cron every 15
  minutes, 0 USD; no Route 53 health check, no new AWS service): `tools/ops/external_checks.py` checks DNS, a verified
  TLS handshake with the certificate's end date and one GET of the health path (no redirects followed; a sign-in
  redirect counts as up) for each public Dev host of `tools/ops/external_checks.json`, and uploads the run with the
  existing Docs sync role to `docs-reader/ops/external-checks.json` (the Delivery metrics path: no new secret, no new
  IAM). No ingest endpoint: CIS reads the object under its existing docs reader grant. The 5-minute status sampler
  gains a part `external` that copies a run it has not seen into `acp_shared.ops_external_check` (CIS 485, ON CONFLICT
  (target, checked_at) DO NOTHING) with the state it derives with its own settings (down: DNS, TLS or the request
  failed; degraded: an unexpected status or a certificate within `cis.ops.status_cert_crit_days` (7); warn: within
  `cis.ops.status_cert_warn_days` (21)). The page shows an "External checks" card right under Services (the internal
  strip) with the strip of the range, the certificate days left (recomputed with today's settings) and the feed's
  age; a feed older than `cis.ops.status_stale_factor` x 15 minutes greys the card and is one SEV3 item; a failing
  target or a certificate at its critical days is a SEV2 item.
- **4. Per-agency drill-down** (`GET /admin/overview/status/tenants`, ops.read): without a filter three rankings of at
  most `cis.ops.status_tenant_top_n` (10) agencies over the page's range (AI spend and calls from
  `shared.ai_usage_hourly` live traffic, failed AI calls = status not ok, failed jobs from `shared.job` by `payload ->>
  'tenant_id'`) plus the platform's own share; with `tenant` (URL key `tenant`, an agency id) that agency's AI by app x
  stage, failed AI calls by error class and failed jobs by kind (no error text: a job error may quote tenant content).
  Names from `shared.tenants`.
- **Burn alert proof on Dev**: `GET /admin/overview/status/slo/drill` (ops.read, Dev only: 404 on another environment)
  answers 503 on purpose; `scripts/ops/slo_error_burst.py` calls it N times with a staff bearer token, then `--check`
  reads the status page and looks for `slo-fast-cis`. The unit test
  `test_a_synthetic_error_burst_fires_the_fast_burn_alert_and_the_verdict_lists_it` proves the same path offline.

- **External target state.** A target whose name resolves but gives no TLS handshake (`tls_ok` null: the connection
  timed out or was refused) is `down` in both modes (review fix: a TLS-only target, the staff sign-in host, read `ok`
  because it has no HTTP status to fall back on). Nothing checked at all (DNS and TLS both null) stays `unknown`.

## Changed (against the issue)

- External checks: a GitHub Actions run every 15 minutes publishing to the docs reader prefix instead of an ingest
  endpoint (the issue allows either); no new secret is needed.
- Server errors per agency and the partner CRM's jobs per agency: **not measured** (no per-agency request log; the
  crm.ops.v1 contract has no tenant breakdown); the card says so.
- The new Needs-attention items (`slo_burn`, `external_*` message keys) read in English in both languages for now: the
  phrase table of `lib/opsStatusText.ts` is shared with the assistant lane of this wave and was left untouched; the
  title is the API's English fallback (follow-up).
- Settings use the CIS settings registry (CIS 486, maker-checker, EN + VI guides, `shared/ops_status_thresholds.py`).

## Tradeoffs

- The fast alert stays up to one fast window after a burst ends (no short confirmation window of the full SRE
  multiwindow recipe): simpler, and on Dev a lingering alert is acceptable; adding a 5-minute confirmation window
  would be one more setting.
- The CRM's fast window (12 health samples) is under the default minimum of 50 events, so its fast burn is never
  judged with the defaults; its slow window (72 samples) is. Same rule for every app, no special case.
- The sampler, not the page, copies the external runs: the strip has no holes when nobody looks, at the price of one
  S3 GET every 5 minutes on the worker (about 8,600 a month, under 0.01 USD).
- A drill route that answers 503 exists on Dev; it needs a staff sign-in with ops.read, reads and writes nothing, and
  is 404 elsewhere. It also fires the CIS 5xx CloudWatch alarm during a drill (expected).

# AA-1142 follow-up (S293, lane e-external-checks) — external checks from the CIS worker, per-agency server errors, VI text

Finding (measured S293): the root workflow `.github/workflows/external-checks.yml` (cron `7,22,37,52 * * * *`, merged
25/11 04:10Z) had 0 scheduled runs, only pull_request / workflow_dispatch; the other root crons start up to 10 h late.
A GitHub schedule cannot feed a 15-minute check.

## Decisions

- **The CIS worker runs the checks itself** (job kind `ops_external_check`, `services/jobs/ops_external_check_job.py`):
  AA-1178 monitoring lane (`background=True, monitor=True`), `deploy_gate_exempt`, `max_attempts=1`,
  `concurrency=1`. The api's ops metrics sampler queues one run per bucket of `cis.ops.external_check_interval_min`
  minutes (buckets aligned to the UTC hour, idempotency key `ops_external_check:<bucket start>`), the same pattern as
  `ops_status_sample` / `compliance_db_checks`. A run that starts more than one interval late writes nothing (the next
  bucket is the retry). $0: no new AWS service, about 8 public requests per run from the worker's NAT egress.
- **Same checks as the root tool** (`api/services/ops_status/external_probe.py`, standard library): DNS
  (`getaddrinfo`), a verified TLS handshake (system trust store, host name checked, TLS 1.2+) and the certificate end
  date, one GET of the health path without following redirects. Targets in parallel, one thread each; a target that
  outlives 3 x the step limit is reported with its timeout error (a resolver that never answers cannot hold the run).
  The result rows have the shape of `external.parse`, so the state is derived and stored by one function
  (`external.store_run`) for both sources.
- **Settings, not literals** (CIS 493, area ops, maker-checker, EN + VI guides): `cis.ops.external_check_sources`
  (worker, github; default both), `cis.ops.external_check_interval_min` (5-60, 15), `cis.ops.external_check_timeout_s`
  (2-30, 10), `cis.ops.external_check_targets` (json list; default = the eight hosts of root
  `tools/ops/external_checks.json`). `shared/ops_external_settings.py` reads them with the seeded default as fallback
  and validates the target list (a bad entry is skipped and named in the job result, never checked).
- **Source per row** (CIS 492): `acp_shared.ops_external_check.source` (`github` default, `worker`), unique
  `(source, target, checked_at)`. Inserts use a bare `ON CONFLICT DO NOTHING` so they work with both the old
  `(target, checked_at)` key and the new one.
- **Page**: one row per target and source ("Checked from": CIS worker / GitHub Actions), a sources line (interval, last
  run, stopped), a stopped source's rows grey; the card and the SEV3 "feed stopped" item only when **every** source in
  use is older than `cis.ops.status_stale_factor` x its own interval (worker: the setting; GitHub: its 15-minute cron).
  Needs attention: at most one SEV2 item per target from the fresh sources only, naming every fresh source that sees it
  fail (`msg.sources`).
- **Server errors per agency** (`tenants.py`): `shared.tenant_api_usage` already logs every metered `/v1/*` call of an
  agency's own systems with its status (`actor_type = 'tenant'`, kept `cis.retention.tenant_api_usage_days`, 90).
  Ranking: 5xx count, calls, share, last 5xx; one agency: totals and the endpoints (route templates) that answered
  5xx, cut at `cis.ops.status_tenant_top_n`. No new setting, no new grant (cis_app has SELECT).
- **Vietnamese text**: the AA-1142 Needs-attention items now carry structured messages the page words in EN or VI:
  `slo_burn` (+ `minutes`), `slo_burn_detail` (new detail_msg), `external_fails` (+ `code`, `status`, `sources`),
  `external_cert`, `external_stale`, `external_stale_detail` (new detail_msg); source label "the external check". AA-1178
  added no page or alert string (its changes are the claim rule, settings and the job runner summary's `lane` field,
  which the page does not show), so nothing to translate there.

## Changed (against the S292 notes)

- External checks: the GitHub workflow is now an optional second vantage point; the worker is the main producer.
- Server errors per agency: measured (partly, see Should know); `not_measured` keeps only the CRM's jobs per agency and
  the answer adds `server_errors_scope`.
- The new items no longer read in English in Vietnamese mode.

## Tradeoffs

- Worker egress, not a third party: the check leaves through the NAT and the public internet like a customer, but it
  shares AWS's region and network with the hosts, so a regional outage can hide itself. The GitHub source stays for
  that reason (when it runs).
- The old unique index `(target, checked_at)` stays until a later contract file drops it (the code on main names it in
  `ON CONFLICT (target, checked_at)`; dropping it in 492 would break the GitHub copy between the migration and the
  code deploy). While both exist, a worker row and a GitHub row of one target at the same instant would collide on it;
  the worker keeps its run time at full precision (GitHub runs are whole seconds), so they never meet in practice
  (local integration run caught the collision with whole-second worker times). Follow-up: a contract file that drops
  `ops_external_check_target_at_key` once this code is live.
- No new HTTP-level setting for redirects or body size: one GET, `READ_BYTES` 64 KiB technical constant (the status is
  what counts), not a threshold.
