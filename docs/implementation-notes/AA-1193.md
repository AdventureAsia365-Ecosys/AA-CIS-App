# AA-1193 — Auto-rollback of the API deploy (AA-CIS-App part)

Whole picture, the other repos and the drill: root `docs/implementation-notes/AA-1193.md` (S297, lane l5-rollback;
S295 Well-Architected review OPS06). Same mechanism as the web deploys' rollback (AA-1119).

## Decisions

- **Where**: `deploy-dev.yml` gets two conditional jobs after `verify`, as `deploy-admin-dev.yml` has: `rollback` (only
  on main, after a successful `deploy` and a FAILED `verify`) and `report` (the `deploy-smoke-red` issue). `result` does
  not wait on them; a rolled-back run stays red through `verify`.
- **api and worker together, all or none**: they run one image. `.github/scripts/ecs_api_rollback.py rollback` dry-runs
  every target through the AA-1119 rules of `ecs_smoke_rollback.py` first; one refusal (unknown or template revision,
  image gone from ECR, deployment in progress, service moved since, desired 0) writes nothing. Then api, then worker,
  each with update-service, services-stable and the running-image check, then `/health` must answer the previous
  commit (`git_sha`, the tag without `dev-`). The dry run also refuses when the two previous revisions are different
  builds (a worker left behind on an older build after a failed or hand-rolled worker deploy): rolling back would
  bring api and worker back split while `/health`, which reads only the api, looked green (review finding, S297).
- **Revision numbers only as job outputs** (`api_rev`, `worker_rev`): the family names equal the `ECS_SERVICE` secret,
  and GitHub drops a job output that contains a secret value (the AA-725 part 5 trap). The rollback job rebuilds
  `family:rev` from the secret; its `outcome` output has the service names replaced by `api` / `worker`.
- **Deploy gate**: the rollback re-asks `/admin/job-runner/deploy-gate` with `deploy_job_guard.sh` and the run's
  `override_running_jobs` reason, like the roll. A held gate (open wave, deploy-blocking job, ECS exec heartbeat, gate
  unreachable) rolls nothing back; the alert and the issue say "held by the deploy gate" and point at the hand
  runbook (root `docs/ops/runbooks/rollback-cis.md`).
- **Alert**: `ecs_api_rollback.py alert` publishes one message on the alerts SNS topic, read from the api task
  definition's `ALERTS_TOPIC_ARN` (no GitHub setting; never printed). It needs `sns:Publish` on the deploy role
  (AA-CIS-Infra PR of this lane); until then it logs "not sent" as a warning and the issue still opens.
- **Failing checks**: `post_deploy_verify.sh` appends each failed check name to `VERIFY_FAILED_FILE`;
  `post-deploy-verify.yml` returns them as the workflow output `failed_checks` (names only).
- **Drill**: dispatch input `drill_force_smoke_fail` (boolean, default off). The verify runs every real check, then
  its step "Drill — force the post-deploy verify red" fails on purpose, so the real rollback, alert and issue run. The
  deploy job refuses the drill before the roll when Dev already runs this commit (nothing older to go back to).

## Changed

- `deploy-dev.yml`: input `drill_force_smoke_fail`; deploy step "Record the revisions before this deploy (rollback
  targets)" before `Deploy api`; jobs `rollback`, `report`.
- `post-deploy-verify.yml`: call input `drill_force_fail`, output `failed_checks`, steps for the drill and the names.
- `post_deploy_verify.sh`: `VERIFY_FAILED_FILE`.
- New `.github/scripts/ecs_api_rollback.py` + `test_ecs_api_rollback.py` (byte copies in AA-Booking and AA-Partner);
  Workflow Lint runs the test.
- Tests: `tests/unit/test_aa1193_api_rollback.py` (wiring + the rollback step's shell against stubs),
  `tests/unit/test_post_deploy_verify.py` (wiring, failed-file).

## Tradeoffs

- A flaky verify now rolls back a good build (the AA-1119 trade-off, accepted): the next deploy of main brings it back.
- The health retry count / delay of the rollback are CLI defaults in the script (CI timing, like `VERIFY_TRIES` of the
  verify), not admin settings: the CI runner has no settings store. Follow-up only if the tech lead wants them editable.
- No rollback of the schema: migrations only move forward (out of scope in the issue). A build that needs a newer
  schema can still roll back, because expand migrations keep the old code working (ADR 0017).

## Should know

- Never a loop: the rollback is an update-service to an existing revision. It builds, pushes and dispatches nothing.
  A re-run finds both services back (no write).
- The drill needs main ahead of what Dev runs: merging this PR does NOT deploy CIS (workflow files are outside the
  push paths), so right after the merge Dev still runs the previous commit and the drill can run at once.
