# AA-1089 — CRM small add-ons (CIS part)

The CRM add-ons from the Odoo study (ranks 45-53). Two items remain; CIS owns one and helps the other:

1. A "Booking confirmed" starter message template (EN + VI) in the AA content seed.
2. The source AA tour on the CRM trip header links the public tour page; the CRM knows a tour only by its catalogue
   key, so `/v1/trip/{id}` now answers a catalogue key too.

## Decisions

- **New seed group `template-booking-confirmed`** (kind `starter_template`, EN "Booking confirmed", VI "Xác nhận đặt
  tour"), inserted after the two AA-977 starters in `data/aa_content/seed_v1.json`. Hand-written, no LLM, no link.
  The seed is now 15 groups x EN + VI = 30 items (10 prep packs, 3 starter templates, 2 campaign blocks).
- **Merge fields: only the ones the CRM fills in a message.** The CRM merges a message template with
  `text_render.MERGE_FIELDS` (traveller_first_name, trip_name, agency_name, agent_name, destination, departure_date,
  proposal, payment_amount, payment_due_date). `{{cancellation.policy}}` is a field of the booking terms text
  (e-sign merge), not of a message: its regex (`[a-z_]`) does not even match a dotted name, so it would reach the
  client with the braces. The template says in words that the client accepted the booking terms, including the
  cancellation policy, and can reply for a copy. A unit test pins every starter's fields to the CRM list.
- **Catalogue key on the public trip page.** The CRM caches tours by `source_id` = `COALESCE(source_group_id,
  tour_id)` (catalog.http.v1); for a versioned tour that is the source group, not a tour id, so `/trip/<key>` was a
  404. `_gone_or_moved` now, when no raw tour has the id, looks the id up as a key in
  `gold_aa_internal.v_tour_liveness` (AA catalogue only): served = 301 to the key's current version (the page then
  308s to it), retired = 410, otherwise 404. No new table, no schema change; the view is already granted to `cis_app`.

## Changed

- `data/aa_content/seed_v1.json`: one group (2 items).
- `tests/unit/test_aa977_seed.py`, `tests/integration/test_aa977_seed_script.py`: counts 28 -> 30 (27 -> 29
  published), plus two tests (the starters use only the CRM message fields; the new group in both languages).
- `api/routers/v1_trip_page.py`: `_KEY_SQL` and the fallback in `_gone_or_moved`.
- `tests/unit/test_aa482_trip_page.py` (served key 301, retired key 410, unknown 404),
  `tests/integration/test_aa986_l3_tenant_served.py` (the source group key of a versioned tour 301s to its current
  version on real Postgres).

## Tradeoffs

- A contract change (`page_tour_id` in catalog.http.v1 and the CRM cache) would give the CRM the current page id
  directly, but needs a CRM migration and a resync. The key redirect costs one indexed view read on a miss only and
  keeps one link for the life of a tour (a later version still resolves).
- The key lookup runs only after both the page and the raw-tour lookups miss, so a normal page read is unchanged.

## Should know
