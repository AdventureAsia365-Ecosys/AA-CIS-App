# AA-1180 — the usage rollup keeps the ledgers' cost precision

`GET /admin/usage-explorer/rollup/check` answered `ok: false` on Dev for every window with Jev calls: the Jev ledger
(`shared.decision_log.cost_usd`, numeric(12,8)) holds 8 decimals (7-day total 0.06664078 USD) while the rollup's
`shared.ai_usage_hourly.cost_usd` (CIS 372) was numeric(18,6), so each hourly row was rounded (rolled 0.066641). The
check compares exactly and stays exact.

## Decisions

- **numeric(20,8), not numeric(18,8).** Scale 8 is the widest of the four source ledgers (llm_call_log 10,6;
  decision_log 12,8; dfs_call_log 12,6; geocode_call 10,6). Precision 20 keeps the 12 integer digits numeric(18,6) had,
  so the change never narrows the integer range (18,8 would have cut it to 10 digits; harmless today but a narrowing
  ALTER for no gain). Unbounded `numeric` was the other option; a fixed scale keeps the column's meaning explicit and
  the integration test pins it against the ledgers' own types.
- **Two PRs (MIG-4).** CIS 494 is a contract file (ALTER of an existing table, root ADR 0017 d3): a migration-only PR
  (applied by Infra Migration Apply once every job table is idle), then the code PR. The code works on either column
  type, so there is no readiness raise.
- **The check stays exact.** No tolerance was added to `compare()`; the fix is the stored precision.
- **`COST_SCALE = 8` in `api/services/usage_rollup.py`.** Not a threshold (tech lead S279 rule does not apply): it is the
  column's scale, fixed by the migration. The explorer rounds its cost figures (`cost_usd` of a group and of the time
  series, `cost_per_tour`, `cost_per_piece`, the invoices tab's `ledger_usd`) to this many decimals instead of 6, so a
  sub-micro-dollar Jev cost no longer reads as 0 and an explorer total matches the ledger sum. The provider's own
  figure (`provider_usd`) keeps 6 (it is not a ledger sum).

## Changed

- CIS 494 (migration-only PR): `ALTER COLUMN cost_usd TYPE numeric(20,8)` + column comment + registration. No view,
  rule or function depends on the column (catalog dump 25/11), so nothing is dropped or recreated.
- Code PR: `usage_rollup.COST_SCALE` and the docstring; `usage_explorer` cost rounding 6 -> `COST_SCALE`. The rollup SQL
  itself needed no change: it already sums per-row costs as unbounded `numeric` (a unit test now guards that no
  fixed-scale cast or `round()` enters `insert_sql()`, `raw_totals_sql()` or `ROLLUP_TOTALS_SQL`).
- Tests: `tests/unit/test_aa1180_rollup_cost_scale.py` (pure: no fixed scale in the rollup SQL, exact compare at 8
  decimals, sub-micro-dollar survives the explorer), `tests/integration/test_aa1180_rollup_precision_db.py` (rollup
  totals equal ledger totals with 8-decimal Jev costs; a 0.00000001 USD row alone is not rounded away; skipped until
  494 is on the tree), `tests/integration/test_aa1180_migration_494.py` (in the migration PR: type, scale covers every
  ledger, exact storage, re-run is a no-op).

## Tradeoffs

- The ALTER rewrites the table (about 4.6k rows / 2.4 MB on Dev) under ACCESS EXCLUSIVE; well under a second, with
  `lock_timeout = 5s`. Fine at this size; at a much larger size the same change would want a new column + backfill.
- Hours rolled before 494 keep their 6-decimal values until re-rolled. The 15-minute schedule re-rolls only the last 6
  hours, so the orchestrator queues one manual re-roll of the last 8 days after apply (audited endpoint, $0). Older
  hours stay at 6 decimals (they are outside the windows the check is read for; a backfill re-roll fixes them if
  ever needed, within the 175-day raw window).
