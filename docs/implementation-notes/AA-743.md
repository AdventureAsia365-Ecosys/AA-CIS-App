# AA-743 — scoped tour removal + one debounced platform recompute

## Decisions
- **Tour removal = supersede, not delete.** `remove_tour_from_caches()` sets `superseded_at` on the
  tour's current `atom_ranking` and `route` rows. Every reader already filters
  `superseded_at IS NULL` (AA-532 / AA-734), so the tour leaves the Slate in one transaction
  (milliseconds). Reactivation needs no special case: route detection already handles a fully
  superseded identity (AA-723 next-free-version logic), ranking writes a new version.
- **Debounce is sliding with a cap.** Each platform enqueue folds into the oldest QUEUED platform
  job (one `UPDATE … FOR UPDATE SKIP LOCKED`): Segment scope is unioned, `run_after` moves to
  now + debounce but never past `created_at + 20 min`, and never earlier than it already was.
  A3 uses 180 s, status changes 60 s. A long wave therefore gets a pass at most every ~20 min and
  a final one ~3 min after the last atomize.
- **The platform pass re-lands questions only for the Segments that changed** (the union carried
  in the payload) plus brand-new Segments (NULL `questions_count`, as before). The whole-platform
  re-land (`segment_ids=None`) is kept for backfills.
- **`a3_atomize` concurrency stays 1 in this PR.** The issue allows raising it once the per-tour
  platform pass is gone, but the lessons log says measure first (S218). Raise it after measuring a
  wave with this change.

## Changed
- `services/export/handler.py` — `tour_segment_ids()`, `remove_tour_from_caches()`,
  `recompute_rankings_and_routes(segment_ids=…)`; `_run_a3_atomize_background` runs segment
  matching, then enqueues the debounced platform job (job result shows `segments`,
  `score_route_job`, `score_route_job_reused`).
- `services/jobs/recompute_job.py` — `_COALESCE_SQL`, `enqueue_recompute(segment_ids, debounce_s)`,
  job passes `segment_ids` and reports `coalesced` / `segments_relanded`.
- `api/routers/admin.py` — `_recompute_after_status_change` removes the tour's rows right away
  (inactive / trashed) and enqueues a scoped, debounced platform pass.
- `scope="tour"` (atom delete in admin_atoms) is unchanged.

## Tradeoffs
- Between an atomize and the debounced pass (≤ 3 min after the burst, ≤ 20 min in a long wave)
  the new tour has Segments but no ranking/route yet. Before, it was ranked right after its own
  atomize — but the wave paid a full platform pass per tour (India: 236 passes).
- A queued recompute with a future `run_after` counts as an active job for the deploy gate
  (`active_count`), so a deploy right after a wave may wait up to the debounce.
- Hubs are not cleaned up here (no `superseded_at` on `hub`); the 394 orphan hubs stay for a
  separate cleanup.

## Should know
- Done-when "trashing one tour … no platform-wide recompute in the logs": the immediate step is
  scoped; a debounced platform pass still runs ~60 s later to re-score the Segments the tour
  shared (recurrence changed). Its landing is scoped to those Segments; ranking itself
  (`run_atom_ranking`) still rebuilds each market as a whole — changing that is the ranking
  formula's code, out of this issue's scope.
- Wave report per-tour counts (scope 4) live in the audit scripts (`s218_recon.py`), not here.
