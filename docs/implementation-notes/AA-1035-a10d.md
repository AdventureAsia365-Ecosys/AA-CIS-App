# AA-1035 A10d (S270, lane aa1035-a10d-cs-e2e-identity) — the Dev-only read-only E2E customer_success identity

Root ADR 0006a A10d. A fifth WORKFORCE E2E identity, `e2e-cis-cs@e2e-mail.lumiguides.it.com`, staff groups exactly
`cis-customer_success`, Dev only, read-only with **no** write allow-list, its tenant book synthetic tenants only. It lets
the orchestrator prove the AA-1035 Done-when "a customer_success E2E user sees only the assigned tenants (403 on another
tenant)" with a real Cognito session. Infra half: AA-CIS-Infra `docs/implementation-notes/AA-1035-a10d.md`; Partner
half: AA-Partner `docs/implementation-notes/AA-1035-a10d.md`.

## Decisions
- **Two identity flags.** `StaffIdentity.e2e_read_only` now means "any Dev-only CIS E2E identity"
  (`e2e_staff.DEV_ONLY_E2E_STAFF_ROLES`: A10b admin, A10d customer_success) and caps the session at reads. A second
  flag, `e2e_allowlisted_writes`, is True for the A10b address only, and only when no side (row email or token email)
  is the A10d address; `StaffPrincipal` carries it only together with `e2e_read_only`. Every A10b exception keys on it:
  - the bearer middleware allow-list (`staff_bearer.py`, `is_allowed_e2e_write_path`);
  - `staff_authz.denial_reason` (`is_allowed_e2e_write_route`) and `docs_owner_read_via` (`"e2e_dev"`);
  - the route-level checks: `admin_view_as._refuse_e2e`, `admin_tenant360._refuse_e2e_invitation` /
    `_refuse_e2e_resend_role`, `admin_content_quality._refuse_e2e_mode`.
- The route-level checks **fail closed** for a read-only E2E identity without the A10b flag: they refuse it outright
  (403 `e2e_read_only`, logged reason `not_allowlisted`) instead of letting it through as "any other staff member". The
  middleware and `denial_reason` refuse it first; these are the third layer.
- The checks that only *restrict* the A10b session (`_sees_every_session`, `members_access`, the send-again "address
  required" rule) keep reading `e2e_read_only`: they narrow, so applying them to A10d too is the safe side.
- **Synthetic-only book.** `PUT /admin/tenants/{id}/assignments/{staff}` answers 409
  (`E2E_REAL_TENANT_REFUSED`) when the staff row is a Dev-only E2E address (A10b or A10d) and the tenant is not
  synthetic (`e2e_staff.is_synthetic_tenant`: `is_canary IS TRUE` and not the pilot), before any row or audit write.
  `ASSIGN_STAFF_SQL` also reads `email`.
- The module-level constant `E2E_CIS_CS_TEST_STAFF_EMAIL` exists (not only the map key): the live precheck finds the
  deployed address by scanning the module's upper-case str constants.
- Migration 378 is its own migration-only PR (MIG-4: a replaced CHECK is contract). This code PR raises readiness
  (`REQUIRED_CIS_ABOVE_GAP` + 378) and is stacked on it.

## Tradeoffs
- A second flag instead of keying exceptions on the role (`role == "admin"`): a role check would let any future
  read-only E2E admin inherit the allow-list; the flag names the one identity the ADR allows.
- The 409 also covers the A10b row: its writes were already synthetic-only, and a real tenant in its book would widen
  its reads for no reason.
