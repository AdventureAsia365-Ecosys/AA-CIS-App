# AA-1088 — Pre-pilot quick fixes (CIS part: M3, held piece publish)

S278 system audit item M3: a held blog / social piece could be published through `POST /v1/publish-log/{id}/publish`
with no word to the agency (`api/routers/v1_publish.py` accepted `held` like `approved`, AA-770). The other three items
of the issue live in AA-Booking (M13) and AA-Partner (M6, M9, and the studio side of M3).

## Decisions

- **Refuse, then let the owner choose.** A held piece answers a typed 409 `content_needs_final_check` on its first
  publish. The account owner may send `{"publish_anyway": true}`; an editor may not (`can_publish_anyway: false`, the
  sentence asks for an account owner). The owner is studio role `owner`, or a token without a role (the role
  middleware treats that legacy shape as owner too). AA staff are not in the loop: the agency operates its own
  channels (ADR-2026-038 §0.2), AA monitors after the fact (Content quality, the audit log).
- **Audited before, fail closed.** The choice is an `acp_shared.audit_log` row `content_piece.published_anyway`
  (channel, membership id, studio role, revision key) written on MAIN before `claim()`. A write error is a 503 "try
  again", never a post without the record. The later `content_piece.published` row also carries
  `published_anyway: true`. The tenant Activity feed lists the choice ("Chose to publish a post after a final read").
- **Tenant-safe sentence.** No score, gate, held reason or "review": "we could not confirm every detail in it against
  the trip (dates, places, what is included)". A unit test walks the sentence for internal words.
- **Response shape.** `JSONResponse` with top-level `detail` (the sentence, so every studio build already shows it),
  `code` and `can_publish_anyway`, plus `X-Error-Code` (the studio BFF does not forward headers, so the body carries
  the code too).

## Changed

- The issue text names `needs_review` too: `acp_shared.content_piece.status` has no such value (CHECK: processing,
  approved, held, failed). `needs_review` is a T2 tour-version status, and T2 versions are not published through this
  route, so only `held` is checked.
- `/pending` is unchanged (no new field): the studio learns about the check from the 409, so a held piece still sits
  in Ready to publish like before.

## Tradeoffs

- A tenant edit does not clear `held` (the edit keeps the status), so an edited held piece still needs the owner's
  click. Clearing on edit would let any editor bypass the check with a one-character change.
- Put back online (`/put-back`) is not checked: the page was live once already and only returns from draft.
