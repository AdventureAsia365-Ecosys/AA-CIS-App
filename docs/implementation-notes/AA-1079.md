# AA-1079 — Debate rank only, brand-fit calibration format, serving model first on judge routes

Lane l6 of S277 (Claude Code, orchestrated). Source: root audit `docs/audits/2026-11-10-S276-aa741-phase3/` §4.3,
§5, §7.2, §9.3. The agent-panel first pass of brand labels is not in this lane (the orchestrator runs it).

## Decisions

### Part 1 — Debate advisory, rank only
- **Setting**: env `T7_DEBATE_MODE` (`rank` | `cut`), read per call by `debate.debate_mode()`. Unset or any other
  value is `rank`, so the change needs no task-definition edit; `cut` brings back the AA-631 cut exactly
  (same cap, same worst-first order, no flags attached). An env flag, like `T9_FAQ_LLM_FILTER`, rather than a key
  in `services/quality/thresholds.yaml`: that file holds score cut-offs with calibration records, not modes.
- **Judgement split from the decision**: `assess_candidates()` returns one `DebateSignal` per candidate (flags,
  severity, judge score, contested, where the brand-fit score came from); `apply_signals()` is pure and decides
  (rank or cut). The paid path is unchanged: brand fit is asked only when `contested` did not flag, cache first,
  Jev pre-filter, then the judge with its `record_call(**billed_fields)`.
- **How rank orders**: `Candidate.debate_flags` / `debate_severity` ride on the candidate; `_choose_slate()` sorts
  each Channel queue by `(flagged, score, id)`: every unflagged candidate before any flagged one, rank-sum order
  inside each group. Severity is recorded but not used for the order: the judge is not calibrated (the point of
  this issue), so its magnitude should not reorder the rank-sum; only the binary flag moves a candidate down.
- **Where the flags are recorded**: the `t7_slate` job result (`debate.segments` / `debate.routes`:
  candidates, kept, dropped, flagged, flagged_by, the worst 300 flagged ids with flags and severity). Not in
  `acp_shared.subject.cleared_bar_reason`: the tenant Slate read returns that column as is, and judge signals are
  admin-only (tenant sees content only). No migration.
- **The $0 replay** (`scripts/quality/replay_aa1079_debate.py`): today's candidate pools of each tenant through
  the production slate code, judged only from what Debate stored (`atom_segment.contested`,
  `debate_brand_fit_cache`, newest brand version per candidate: `assess_candidates(cache_only=True,
  any_brand_version=True)`), then `_choose_slate` twice (cut / rank). Read-only sessions
  (`default_transaction_read_only`), no Jev, no LLM, no cache write. `scripts/` is not in the image: the
  orchestrator ships the file and runs it with `PYTHONPATH=/app` after the deploy (it needs this branch's debate).

### Part 3 — serving model first on the judge routes
- **As route-control data, not a migration**: a third preset `serving_first` (`api/services/llm_route_control.py`)
  for `t2_judge`, `t7_debate_judge`, `t10_judge`. Applied with the existing `POST
  /admin/ai-gateway/route-control/presets/serving_first`: validated, audited, saved as a new route config version,
  one-click revert. No CIS migration number taken.
- **What it computes**: the live `resolve_stage` of each of the three stages (the same $0 resolver as the preview,
  refused deployments skipped). A stage moves only when its serving model is not its primary AND every rung ahead
  of it is closed (`CLOSED_REASONS`: refused by the account, a connection access state, circuit open). A rung
  switched off, out of scope, over budget or role-skipped is an admin decision and blocks the move. New chain =
  serving model + the rest in their order (the closed rungs stay, so a revert is the only step when acc3 opens).
  On Dev today (route doc of 09/11): `gpt-5.6-luna`, `gpt-6-luna` (acc3, access_denied) then `gpt-6-luna-openai`
  → `gpt-6-luna-openai`, `gpt-5.6-luna`, `gpt-6-luna`.
- **Rule exemption, scoped**: putting a vendor-only model first breaks `vendor_last_resort` / `vendor_not_last`
  (S235 / T-3: outside AWS only as the last resort). For the stages this preset moves, those two rules become a
  warning naming the closed rungs (`exempt: true`); every other rule (judge family, attempt cap, scopes, pii, no
  live model) still blocks, and the same chain saved by hand is still refused. The tech lead's AA-1079 scope is
  the approval for this exception; the warning keeps it visible in the preview and the audit row.
- **Evidence**: a judge chain change needs D7 evidence; the preset goes through the same `route_evidence.require`
  (eval run id or break-glass reason) as any save.
- Frontend: the preset card comes from the API list; added its EN / VI copy and the key in `PRESET_KEYS`, and the
  presets help no longer says "the chains do not change".

### Part 2 — brand-fit calibration
- **Label store: the golden item's `label` jsonb, no new table.** `label.brand` = {rubric `aa1079-brand-v1`,
  brand_fit `fits|partly|off`, core_idea `present|absent|unclear`, reason, source `agent_panel|tech_lead`, status,
  votes, approved_by, labelled_at} (`services/quality/brand_labels.py`). A brand label set version is a fixture
  version, written by `scripts/aa729/brand_labels.py apply` and imported by the existing
  `services/golden_set/importer.py` (it passes `label` through), exactly as the content labels are. Considered and
  rejected: `shared.eval_claim_label` (claim spans of <= 2000 chars, `claim_class` from the policy taxonomy and
  violation / ok / unsure labels: a whole-text brand judgement would be a fake span and would leak into the claim
  agreement reports) and `shared.eval_claim_proposal` (FK to a disagreement-queue item). The Writing Lab staff API
  can show `label.brand` later without a schema change.
- **Which items**: T2 versions and T9 blog / social pieces (tenant voice), never A1 (no tenant brand) or an
  injection trap. The pack shows the brand pack and the text only (no pipeline verdict, score, gate ledger, flags).
- **Agreement maths** (`services/quality/brand_agreement.py`): FAIL (off-brand) is the positive class; strict
  (only `fits` passes) and lenient (`partly` passes too); Cohen's kappa; a threshold sweep 4.0-9.5 for scored
  instruments. Decision bar = writing policy D9's bar for a brand judge (kappa >= 0.6 on >= 40 pairs) plus >= 5
  of each class; below it the proposal is "keep rank only".
- **Instruments measured** (`scripts/quality/measure_aa1079_brand_fit.py`, $0, read-only DB): the T2 judge's
  `brand_fit` and `mission_present` (`tenant_tour_versions.judge_breakdown` by `refs.version_id`), the stored
  `quality_score` (the 9.9-10 the audit questioned) and the T10 F9 brand-voice gate of T9 pieces (last
  `F9_brand_style` entry of the frozen gate ledger). `--judge-scores` merges values from another run.
- **Overlap check** (`services/quality/brand_overlap.py`): word 5-gram Jaccard per brand pair of one tour (the
  audit's method), plus the Jaccard of what is NOT in the source text, so Master wording kept by both brands is
  told apart from brand-to-brand copying; identical texts (>= 0.95: the policy hold) are reported, not warned.
  Warn line `t2.cross_brand_overlap_warn` = 0.35 in `thresholds.yaml`, uncalibrated (the audit's 8 rewritten tours:
  mean 0.18, max 0.37).

## Changed
- `apply_debate()` keeps its signature (callers and test doubles unchanged); the judge call moved into
  `assess_candidates()`, so the LLM call-site registry (`tests/unit/test_aa927_llm_call_site_registry.py`) names it.
- The AA-631 / AA-700 unit tests that assert the cut now run with `T7_DEBATE_MODE=cut`.
- The route-control preset list grows from two to three (API state, integration assertion, frontend keys / copy).

## Tradeoffs
- Rank by the binary flag, not by severity: with 499 / 502 flagged the flag barely reorders anything; using the
  uncalibrated severity would let the judge reorder the rank-sum, which is the cut by another name.
- A preset instead of a migration for the judge routes: no deploy-time data change, the version history gives a
  one-click revert when acc3 opens, and the move is computed from the live refusals instead of hard-coding model keys
  (a migration would bake today's three keys in and still need a revert migration later). Cost: one admin call with
  D7 evidence (break-glass reason) after the deploy.
- Brand labels inside `label` jsonb: no migration and no new erasure / retention row, at the price of a new golden
  set version per label batch (the existing content-label flow already works this way).
