# AA-1056 — recompute after tour retire / restore: diagnostic, sweep, latency measure, release delay and lock

Source: root `docs/audits/2026-11-08-S273-session/system-picture/system-picture.vi.md` section 3 (row "Recompute
sau bật/tắt không có lưới quét") and section 5 items 3 + 8. Lane l6-recompute-sweep of S274.

## Decisions

1. **Diagnostic first, read only.** `scripts/aa1056/recompute_lag_diag.py` reads `gold_aa_internal.tour_lifecycle_event`
   and `shared.job` around the 05/11 pair and prints, per event, which after-commit effects ran (the
   `tripplanner_purge` job's `payload.trigger`: `after_commit` or `sweep`), which recompute rows were created, folded
   or queued around it, and the first finished recompute after it. It ends each event with one verdict line. It needs
   no code from the image (asyncpg only), so the orchestrator runs it with `tools/ecs/ecsx.sh` before or after the
   deploy. No ids or names are printed beyond 8-character prefixes of job / tour ids.
2. **One measure for "event to finished recompute".** `services/recompute/lifecycle.py` holds the SQL
   (`LAG_SQL`): for every `retired` / `paused` / `restored` event of the window, the first `finished_at` of a
   succeeded `recompute` job (any scope: a tour-scope run also redoes the platform Score and Route) that STARTED after
   the event. It replaces the S273 audit metric `events_not_followed_by_recompute`, which asked "did any recompute
   finish after the event", so a recompute 74 hours later still counted as "followed". The same SQL feeds the ops
   sampler (alert) and the Data coverage page (rows), so the two never disagree.
3. **Alert = an event still waiting after 30 minutes.** The ops check `recompute_lifecycle_lag` (shared/ops_checks.py,
   bell + one e-mail a day) fires while an event of the last 30 days is older than 30 minutes and no recompute has
   finished since. 30 minutes = the 20-minute debounce cap (`MAX_WAIT_S`) plus a slow run (p95 291 s, max 543 s).
   A late event that has since been followed is history: it shows on the page, it does not page anyone.
4. **Sweep every 2 hours, from the api ops sampler loop.** Same place as the TripPlanner purge and fan-out sweeps
   (`api/core/ops_metrics_sampler.py`), on the loop's own monotonic schedule like the Jev credit check (no module
   state, first sweep on the first tick after start). It enqueues ONE platform recompute (through the shared
   `enqueue_recompute`) for every event of the last 7 days, older than 5 minutes, with no queued platform recompute
   and no recompute running or finished since; the Segment scope is the union of the swept tours' Segments (the same
   scope the status-change path uses), so it re-lands only those. Two api tasks sweeping at once cost one no-op: the
   second sees the queued job.
5. **Lock and release delay reuse the a3 code.** The session advisory lock body of `a3_tour_lock` moved into a generic
   `job_session_lock(lock_class, key, ...)` in `services/export/handler.py`; `a3_tour_lock` is now a thin wrapper
   (same SQL, same connection helper, same behaviour and tests). The recompute job takes
   `job_session_lock("recompute", "platform")` for its whole run: both scopes rebuild the platform-wide Score and
   Route, so one key. The release delay constant moved to `shared/jobs/registry.WORKER_STOP_TIMEOUT_SECONDS` (120 s,
   the worker's ECS stopTimeout); both kinds read it.
6. **Stop at a stage boundary.** `run_stages` takes an optional `should_stop` (checked before every stage, raises
   `RecomputeStopped`) and `on_stage` (names the running stage). The recompute job sets its stop event when its
   handler is cancelled (deploy release, admin cancel, lost lease), like a3_atomize; progress writes after that are
   dropped. Other callers pass nothing and are unchanged.
7. **Fixed error codes** (`services/recompute/errors.py`): `recompute_bad_payload` (NonRetryable),
   `recompute_lock_timeout` (another run held the lock longer than the kind's expected 1,800 s; retryable),
   `recompute_stopped` (log only: the cancelled handler is released, not failed), `recompute_stage_failed` (any other
   exception, with the stage name; retryable). The job error text contains the code, so a Jobs-page search finds it.

## Diagnostic: how to read it

Each event prints `e<n>.purge=trigger=...`. `after_commit` means the request ran `run_after_commit`; then a missing
recompute row near the event points at a failed enqueue (log event `aa713_recompute_enqueue_failed`). `sweep` means
the request never ran its effects (a path or a script that skips `run_after_commit`, or the api died between commit
and effects): the TripPlanner purge and fan-out have sweeps, recompute had none until this change. Checked locally on
a seeded copy of that shape (purge from the sweep, no recompute near, first finished run ~74 h later): the verdict
line names the second cause.

## Tradeoffs

- **Sweep cadence 2 h, alert at 30 min.** The issue asks for a 2-hour sweep; the alert fires sooner, so a lost
  enqueue is seen at 30 minutes and fixed by the next sweep (at most ~2 h + the run). Sweeping every tick would close
  the gap faster but fights the after-commit path for no gain on Dev.
- **Any recompute scope counts as "followed".** The S273 script counted platform runs only. A tour-scope run also
  rebuilds the platform Score and Route, so it does clear the stale caches; counting it avoids a false alarm.
- **One lock key for the whole kind.** Two recompute runs never overlap, whatever their scope. a3_atomize's own
  inline Segment / Score / Route step does not take this lock (it holds the tour lock); serialising the two would slow
  waves and is left as a follow-up.
