# AA-1038 — R5 multi-tenant TripPlanner, the CIS side

The TripPlanner side of R5 is in AA-TripPlanner-Web `docs/implementation-notes/AA-1038.md`. This file covers what CIS
owns: slice 2 (S271), migration `api/migrations/379_tenant_tripplanner_catalog_view.sql`.

## Decisions

- **One contract view for TripPlanner**, `catalog.v_tenant_tripplanner_v1`, like Booking's `v_tenant_account_v1` (357)
  and `v_tenant_billing_v1` (377): TripPlanner reads the control plane through catalog views only (USAGE on
  `catalog`, never on `shared`). It is part 4 of `tenant.entitlements.v1` (1.4, root contract file).
- **Rows = tenants with a TripPlanner subscription (any status), kind internal excluded.** A Content-only tenant has
  no row, so TripPlanner never learns the slug and name of every agency; a suspended or canceled subscriber keeps a row
  with `served = false`, which TripPlanner answers 404 the same way.
- **`served` = `in_service` AND the live `tp.hosted` entitlement** (from `shared.v_tenant_entitlement_resolved`, so a
  trial, an override or a canceled add-on is handled by the resolver). Apps check feature keys, never plan names: no
  `plan_key` column.
- **Theme and locale live in a new table** `shared.tenant_tripplanner_site`, not in `shared.tenants` (they are
  TripPlanner settings, not account data) and not in plan data (they are per tenant, not sold). The CHECK accepts only
  `{"<token>": "#rrggbb"}` (lower-case hex, token `^[a-z][a-z0-9-]{0,39}$`, 4 kB), so no value can inject CSS when the
  kit maps it onto `--aa-*`. TripPlanner filters again on its side.
- **A bound tenant reads AA master rows only** (asked by the lane brief): already true structurally, because
  `catalog._live_tour` keeps `published_tours.tenant_id = <master>` in its WHERE; the GUC policies can only add rows
  that the view then removes. Recorded in the view comment and the contract; the tenant's own text is
  `catalog.v_tenant_tour_v1`, a later slice with its own rule.
- **The demo tenant row** is seeded here (TripPlanner tp-025 already uses its id as a soft key):
  `00000000-0000-0000-0000-000000000002`, slug `aa-tripplanner`, kind `demo`, `plan_tier` `internal` (the
  `content.internal` plan has no price, so Booking's SaaS draft writes a contract-price line of 0, not 299 USD), plus a
  `tripplanner.hosted` subscription and an empty site row. Seeded only when absent; a different tenant already holding
  the id or the slug fails the file (guard).
- **Grants**: the consumer grant (SELECT to `tripplanner`) is in this file (contracts rule 5); the Infra probe registry
  names it with `expected_from` 379.

## Tradeoffs

- **Table vs. a JSON column on `shared.tenants`**: a table costs a retention row and an allowlist entry, but keeps the
  account table free of product settings and gives the kit brand token editor its own audited write path later.
- **No admin editor yet**: the demo row is empty (kit defaults). The editor belongs to the kit brand token slice;
  until then a theme is set by a DB Migrate run-script if needed.

## Should know

- The demo tenant appears in the CIS tenant directory and in Booking's projection like the other demo tenants. CIS's
  `tenant_billing_tick` moves only demo tenants on Dev, so an issued and overdue invoice for it would suspend it (and
  TripPlanner's `/aa-tripplanner/plan` would 404); none is issued today.
- Teardown of the test deletes the demo tenant's event rows with `session_replication_role = replica` (superuser,
  test only): the account event guard refuses deleting events of a live tenant.
- Retention row (DM-7.1) for `shared.tenant_tripplanner_site`: root data standards Part B, in a root PR that is on
  root master before the Infra bot copy PR of 379.
- **Follow-up (not in this slice): reserved slugs.** TripPlanner serves a tenant on `/{slug}` of its host, so a slug
  equal to one of its static top-level paths can never be served (the static route wins). TripPlanner refuses them in
  its resolver (AA-TripPlanner-Web `frontend/lib/tenantSite.ts` `RESERVED_TENANT_SLUGS`: every top-level route folder
  of `frontend/app` and every top-level entry of `frontend/public`; today `api`, `brand`, `destinations`, `hero`,
  `plan`, `privacy`, `sign-in`, `terms`, `tours`, `trips`; a test keeps the list equal to the folders). CIS tenant
  creation and slug rename should reject the same list later, so an agency never gets a slug whose site is a 404.
  Not changed in this pass.
