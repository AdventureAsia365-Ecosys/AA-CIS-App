# AA-845 — `a1_claim_supported` ground truth (option c) + keyword floor write-up

Owner decision (S245, 20/10/2026, root `docs/audits/2026-10-20-S245-m2a-decisions/` §3):
**(c)** — a one-off agent-panel label set of ~100 grey sentences now (~60 with p ≤ 0.20, ~40 in
0.20–0.85, Nghiệp approves the set), then the reviewer per-sentence "unsupported" action as the
long-term truth loop. **Scope item 2 changed:** a Review reject scores the whole version, so it never
writes truth=False for every sentence; truth=False is written only for a sentence a reviewer marks.
**Keyword retune approved** (`a1_keyword_about_tour` accept 0.65 / reject 0.40), applied in the
measurement wave after the "zone → system action → quality change" write-up.

This PR is the code half of (c) plus the write-up. Nothing paid ran; nothing live was changed.

## Decisions

- **Per-sentence label = one subject key.** The reviewer labels a grounding unit; the API maps it to
  the same `subject_key(unit_source(tour, unit), sentence)` the S1 run asked Jev with (the key the
  approve path already uses). One helper (`grounding.review_units`) builds units + keys for the
  approve path, the label path and the sample, so the three cannot drift.
- **Label endpoint takes the subject key, not free text.** `POST /admin/review-queue/{id}/claims/label`
  `{subject_key, unsupported}`: the key must be one of the review's current units (else 404), and it
  must have a logged `a1_claim_supported` verdict (else 409 — nothing to label: the sentence was
  edited after the check, or the row aged out). The server never trusts a sentence string from the
  browser.
- **Undo clears only the reviewer's own label** (`unsupported: false` → `outcome = NULL` where the
  stored source is `review_sentence_unsupported`). An approve label (`review_approve`, truth=True) on
  the same subject is never cleared by an undo.
- **Approve no longer overwrites a reviewer's "unsupported".** `record_outcome(keep_sources=…)` skips
  the whole subject when any of its rows carries an outcome from `review_sentence_unsupported`, so
  "mark this sentence, then approve the rest of the version" keeps the sentence's truth=False. The
  reverse (mark after an approve) overwrites truth=True with truth=False on every row of the subject:
  the explicit per-sentence act wins.
- **The label belongs to the sentence (subject), not to single rows** (independent review finding).
  `decide()` logs a new row every time a later S1 run (Regenerate, rewrite) asks Jev about the same
  sentence, cache hits included (`cached=true`, outcome NULL). A first version guarded and read per
  row, so after such a re-ask (1) the claims panel and the claim-sample read the outcome from the
  newest row and showed the sentence as unmarked, and (2) an approve stamped truth=True on the new
  row next to truth=False on the old one, so one sentence held both truths and
  `/outcomes/summary` counted it as agree and disagree. Fixed in two places: the keep guard is a
  `NOT EXISTS` over the subject, and `latest_verdicts` takes the verdict from the newest row but the
  label from the newest row that has an outcome (`LEFT JOIN LATERAL`). Covered by the integration
  test `test_mark_survives_a_newer_unlabelled_row_and_a_later_approve`.
- **Not copied onto new rows** (the review's optional (c)). Copying the reviewer label onto rows
  logged after the mark would need either a change to `decide()`'s hot insert path or a second write
  in the approve path, and it adds nothing the subject-level read and guard do not already give; it
  would also add duplicate rows to the row-level `/outcomes/summary` counts. Marking the sentence
  again (idempotent) stamps every row, newer ones included.
- **Reject still writes nothing** (scope change). No `record_rejected_outcome` for the whole version.
  The name in the issue is kept for the per-sentence writer: `grounding.record_rejected_outcome`.
- **`by` in the outcome JSON.** The label writes `{"truth", "source", "ref", "at", "by"}` with `by`
  = the reviewer's admin user id (header), so a label can be traced to a person. Additive key; the
  summary query reads only `truth`/`source`.
- **The panel sample is an endpoint, not a script.** `GET /admin/decisions/claim-sample` rebuilds
  sentences + per-unit sources from the latest master version of a seeded random set of active
  tours, joins each unit's latest `a1_claim_supported` (+ `a1_promise_unsupported`, for AA-803)
  verdict and returns a stratified, reproducible sample (seed). $0 (no Jev, no LLM). Reason:
  `decision_log` stores only the subject key (no sentence, no source), so the sample must be rebuilt
  from content; a read endpoint makes it repeatable and avoids an ECS-exec script (`scripts/` is
  gitignored, lessons).
- **Strata default to the memo:** `low_max=0.20`, `high_max=0.85` (current accept floor), 60/40,
  at most 3 sentences per tour, numeric hits flagged (`numeric_hit`) but kept — the calibration
  record says the reject side only matters for non-numeric sentences, so the panel report must
  split by it.
- **No new migration.** `decision_log.outcome` (TEXT JSON) already exists; no new column.

## Tradeoffs

- **Undo sets NULL, not the previous outcome.** If a sentence carried an approve label before the
  reviewer marked it, undo leaves it unlabelled rather than restoring truth=True. Rare (approve then
  mark then undo) and the safe direction (no label beats a stale one).
- **Labels live on `decision_log` rows**, so a sentence with no logged verdict cannot be labelled
  (409). The UI disables the button for those rows and says why. A separate label table would keep
  them, but such labels could not be compared with a Jev verdict anyway.
- **Sample is per latest version**, not per review row. Older versions' sentences are not sampled;
  the grey population of the current master content is what a reject ceiling acts on.

## Should know

  anyone labels.
- **Keyword floors (write-up in `docs/calibration/a1_keyword_about_tour.md`):** on the S224 labelled
  sample, reject ≤ 0.40 is 38/41 = 92.7% precise, but **accept ≥ 0.65 is only 26/37 = 70.3%**
  (≥ 0.80 was 20/20). The approved 0.65 came from the grey-share measurement only. The write-up
  recommends applying reject 0.40 now and keeping accept at 0.80 until a relabel, and states what
  each zone does downstream. **Accept 0.65 must not be applied on the S245 approval alone** (that
  approval came from the grey-share number, before the 70.3% was known): the orchestrator takes the
  write-up back to Nghiệp and records his revised answer on AA-845 before the PUT. Until then only
  reject 0.40 (accept stays 0.80) may be applied. The orchestrator applies the PUT, not this PR.
- The 402 investigation (scope 5), the reject ceiling (scope 3) and the measurement wave are not in

# AA-845 (S246) — Jev credit alerts: low credit (Q845-2) and 402 exhausted (Q845-3)

Scope (Nghiệp, S246 quality decisions Q7 = a): only the low-credit alert and the 402 alarm. Q845-4 (shadow
calibration of `a1_promise_unsupported`) is **cancelled** and not built. Background: the S246 panel report
(root `docs/audits/2026-10-21-S246-eval-panels/aa-845.md` §6) found the prepaid TypeSafe credit ran out twice
(03/10, 10/10), the only signal was an admin bell, the daily 402 sweep was blind (`'%402%'` vs the
`credit_exhausted` text decide() writes) and about $8.19 was left against about $6.42 per full A wave.

## Decisions

- **Both alerts live app-side, on the existing AA-828 operator e-mail path** (`ops_alert_email` job, SES, the
  recipients of Platform › Alert recipients), not on a new CloudWatch alarm. Reasons:
  - The low-credit estimate exists only in the DB (top-ups − logged spend); CloudWatch cannot see it without a new
    published metric, an IAM namespace grant and an alarm.
  - A log-metric alarm on the 402 lines (the panel's draft HCL) would flap: after a 402 each process skips TypeSafe
    for the 15-minute breaker cooldown, so the metric goes quiet, the alarm goes OK (and, under the S241 D-20
    ALARM+OK rule, e-mails "OK" while the credit is still empty), then the next call after the cooldown fires it
    again. That is the "paging on a blip" pattern to avoid. Dropping `ok_actions` would break D-20.
  - The app path reaches the same people: the alert recipients are the e-mail subscribers of the SNS alerts topic
    (AA-913), and `SES_FROM_ADDRESS` / `ALERT_EMAIL_TO` are already set on the api and worker task definitions.
  - So: **no AA-CIS-Infra change, no new AWS resource.**
- **402 → e-mail rides on the AA-720 bell.** `maybe_alert_jev_credit` queues one `jev_credit_exhausted` e-mail
  only when it writes a new bell (one unread per 24 h, advisory-locked since AA-756), and the job key allows one
  per UTC day. The e-mail is queued after the bell's transaction, best effort, so a mail failure never loses the
  bell and never fails the stage. All three callers get it: decide() (first 402 of a process), the daily canary,
  and the daily sweep.
- **One 402 is enough to alert.** A 402 `billing_error` is not transient (it means the prepaid credit is gone), so
  there is no "N in a row" rule; the protection against noise is the throttle (one bell and one mail per episode,
  not one per call or per process).
- **The sweep fix is included** (panel patch (a)/(b)): `_JEV_402_SWEEP_SQL` matches `credit_exhausted%` as well as
  `%402%`. Without (a) the daily backstop never sees the real 402 path. Patch (b): a failed decide() now logs
  `<ExceptionType>: <message>` (only the type when the message is empty, 120 empty error rows on 08/10) for
  **every** failure, not only the empty ones. Nothing else compares `decision_log.error` text, and `%402%` still
  matches.
- **Low credit: estimate below $3** (`shared/jev_credit.LOW_CREDIT_THRESHOLD_USD`), bell
  `platform.jev_credit.low` + `jev_credit_low` e-mail, same throttle shape (one unread bell per 24 h, mail only
  with a new bell, one per UTC day). No top-up recorded = no estimate = no alert. The estimate only falls between
  top-ups, so it cannot flap; a recorded top-up lifts it and the next check is quiet.
- **Checked every 30 minutes by the api ops sampler** (`api/core/ops_metrics_sampler.py`), not only by the daily
  06:15 probe: a full wave (~$6.42) can take $8 to $0 within one day, so a daily check would usually fire after
  the 402. The check runs after the metrics tick, outside `sample_once`, under its own 60 s timeout; the schedule
  is a local of the loop (no module clock to reset — S246 test lesson). It sums the provider-typesafe rows of
  `llm_call_log` since the first top-up: 48 reads a day instead of 288.
- **Threshold is a code constant.** There is no platform settings row (the only per-provider table,
  `shared.spend_budget`, holds per-run / per-day spend caps, not a balance floor) and no env var (underscore env
  vars are set by hand only). Editable-in-Settings needs a migration (a column or a small settings table): left as
  a follow-up, not built here, because CIS 253–258 are in flight on AA-847.
- **Live verification without faking an outage:** `POST /admin/decisions/jev-credit/check` (staff `spend.write`,
  was `ops.write` before the S246 review)
  with `{"threshold_usd": 1000, "test_exhausted_alert": true}` sends one `[TEST]` low alert and one `[TEST]`
  exhausted alert through the same functions as the real ones. Test bells carry `payload.test = true` and are
  excluded from both real throttles; test e-mails have their own job key (`...:test:<day>`). So a verification run
  can never hide a real alert. A "Send test alerts" button on Settings › Jev Credit calls it. With `{}` the route
  runs the real check.

## Tradeoffs

- **No DB-independent alarm.** If the DB itself is down the bell and the mail cannot be written; but then decide()
  cannot log either and the RDS / API alarms already page. A CloudWatch alarm would add a second channel at the
  cost of the flapping above.
- **The estimate can be wrong** (a top-up not recorded, or the S224 reconcile backfill rows counted as spend); the
  mail says it is an estimate and the 402 alert remains the hard signal.
- **One e-mail per UTC day while low** (if nobody tops up and the bell stays unread, the bell is re-written after
  24 h and the next day's mail goes out). A reminder per day felt right for a prepaid account; per top-up epoch
  would be quieter.
- **Sampler-only cadence.** The check runs in the api; the worker (where waves spend) does not run it. A stopped
  api already pages through `*-sampling-stopped`.

## Should know

- **Cost:** no new AWS resource ($0/month in AWS). Each alert e-mail is one SES message (about $0.0001). The
  30-minute spend sum is a few hundred milliseconds of RDS time. No LLM or Jev call is added (the test route
  does not call TypeSafe).
- **Underscore env vars:** none new. The existing `SES_FROM_ADDRESS`, `ALERT_EMAIL_TO`, `SES_CONFIGURATION_SET`,
  `ALERTS_TOPIC_ARN`, `ALERT_BOOTSTRAP_EMAIL` (already on api + worker) are what the mail needs; nothing to set.
- **Reverses the S224/AA-756 "no running-low alert" rule**, as the S246 panel recommended and Nghiệp's S246
  decisions kept in scope (Q845-2/3).
- **The real 402 trigger is not exercised live** (that would need an empty TypeSafe account). It is covered by
  unit tests (`_decide` → breaker → `maybe_alert_jev_credit` → e-mail) and was seen live on 10/10 (4 bells); the
  live test send covers everything from the bell on.
