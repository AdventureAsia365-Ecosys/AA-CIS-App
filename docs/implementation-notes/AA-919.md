## Decisions

- **Migration 284** (S252 renumber). 282 is `282_supply_writer_sonnet_5_5.sql` (AA-835) and 283 is
  `283_admin_users_e2e_cis_admin_email.sql` (AA-816 A10b, applied on Dev), both on main. The first attempt (S251) was
  283; the file, its registry row, its guard / probe names (`ZZ284`, `zz284_*`), the Infra copy and every test
  reference now say 284. Guard 1 requires **281, 282 and 283** registered (critic 17: the readiness check reads
  `max(version)`, which would hide any missing predecessor once 284 is in). The S251 attempt required only 281 and
  let 282 apply in either order; with 282 and 283 both on Dev there is no reason left to allow a gap.
- **One migration does storage only.** No request path reads or writes the new tables, so
  `api/core/readiness.py` `REQUIRED_CIS_SCHEMA` stays at 280; the importer is a CLI run after the apply.
- **Three tables + a widened `prompt_eval_runs`** (plan §2 with the critic's fixes):
  - `eval_golden_set`: platform table (no tenant column, no RLS). `shared_inputs` holds **only `s1:*` brand packs**
    (a CHECK with `jsonb_path_exists` refuses any other key). `source_uri` is `s3:<key>` or `file:<name>`; a CHECK
    refuses `s3://`, `arn:` and any 12-digit run, so no bucket or account lands in the row (critic 35).
    `item_count` is the import-time count, not kept in step with the erasure (critic 37, documented on the column).
    One active version per name (partial unique index).
  - `eval_golden_item` (RLS ENABLE + FORCE): `post_edit boolean` replaces the plan's `output_post_edit jsonb` (critic
    10: the fixture field is a boolean); the `post_edit` tier must equal the flag (CHECK). `trap = (split = 'trap')`
    and `trap = (injection_spec IS NOT NULL)`; `injection_spec` keeps the AA-729 canary / attack fields WM-19's probe
    needs. `pick_reason` (the AA-729 quota tag) is kept. `pii:free_text` on `input`, `control_output`, `label`,
    `pipeline_verdict` (critic 13).
  - `eval_item_result` (RLS ENABLE + FORCE): `phase` probe / tune / holdout and `scored_result_id` (critic 24); unique
    key `(run_id, item_id, arm, mode)` so one baseline run per writer can carry both modes (critic 15). **No release
    back-link and no UPDATE grant**: results are immutable; a release names its eval run (critic 16).
  - `prompt_eval_runs`: `run_kind` regression | baseline_import | r0_replay | r1 | r2 | reverify | probe | shadow
    (critic 24), `writer`, `release_id` (no FK until WM-18), `golden_set_id` (FK, RESTRICT), `tiers`, `stop_reason`,
    `verdict`, `cost_cap_usd`, `judge_kappa`, `judge_counts` (CHECK: counts only with kappa >= 0.6) (critic 25),
    `fingerprint`, `finished_at`. The existing NOT NULL columns of a writing-memory run (critic 14): `prompt_version` =
    the writer prompt hash, or `aa729-frozen@<fixture version>` for a baseline import; `tour_count` = items in the run;
    `regression_detected` = false; `triggered_by` = the job or the importer's actor.
- **A trigger, not only CHECKs, on results** (`shared.eval_item_result_guard`, BEFORE INSERT OR UPDATE, invoker
  rights, `search_path` pinned, EXECUTE revoked from PUBLIC): the copied writer / scope / tenant_id must equal the
  item's (RLS and erasure rely on it), `phase` must match the item's split (a holdout item is never scored in the tune
  phase), a score_only **control** never scores a post_edit item, the run must be a writing_memory run of the item's
  writer **and of the item's golden set** (`golden_set_id` = the item's `set_id`; review fix), a control is
  regenerated only in a baseline_import or reverify run (critic 24), a rejudge scores a result of the same item. These
  rules span tables, which a CHECK cannot.
- **The run ledger freezes what the result trigger checked** (review fix): `shared.prompt_eval_runs_freeze`, BEFORE
  UPDATE on `prompt_eval_runs`: once a run has an `eval_item_result` row, its `pipeline`, `writer`, `run_kind` and
  `golden_set_id` cannot change (cis_app keeps UPDATE for `finished_at` / `verdict` / `stop_reason` / cost). Invoker
  rights: the EXISTS reads results under the updater's RLS policy (cis_app / cis_owner: `USING (true)`); the legacy
  `regression.py` path never updates the run.
- **Grants**: set S/I/U (supersede), item S/I/D (immutable: a relabel is a new version; D for the AA-839 erasure),
  result S/I/D. `prompt_eval_runs` grants unchanged (Dev: cis_app S/I/U/D from 244). Nothing for `aa_app_user` or
  `catalog_owner`; the `tenant_isolation` policy is the floor if a tenant grant ever appears.
- **Derivation rules** (`services/golden_set/derive.py`, pure):
  - writer: s1 → a1, t2 → t2, t9_blog → t9_blog, t9_linkedin → t9_social; an injection sample follows its host stratum.
    The T9 channel is the sample's and must equal `input.context.channel`.
  - kind (critic 11): s1 / t2 / t9 → real, injection_s1 / injection_t9 → synthetic; anything else is refused.
  - tenant: `refs.tenant_id`, equal to `input.tenant_id` and `input.context.tenant_id`; an inj-t9 sample takes its
    host's (critic 11). Every tenant must exist in `shared.tenants` and not be offboarded (`cancelled_at`), else the
    import is refused (critic 11 / 37).
  - split: stratified by (writer, label verdict), order `sha256("<seed>:<sample_id>")`, holdout =
    round_half_up(0.300 × n) in **Decimal** (a float makes 0.3 × 5 = 1.4999…); injection samples are `trap`.
  - tiers: the fixture tags, `long_9d` (days ≥ 9; NULL days is not long, critic 12), `post_edit`, and `fact_dense` =
    the top round_half_up(0.3 × n) non-trap a1 / t2 items by (numbers + schedule + places of
    `services.quality.s1_facts.build_fact_table`) per 100 source words (`TEXT_FIELDS`); the cut, k and n per writer
    are stored in `tier_rules`.
  - tenant brand packs are inlined on the items that reference them, only when the pack's slug is the item's tenant
    slug (`t2:<slug>`); an unreferenced tenant pack is dropped and reported, never stored at set level.
- **Baseline (critic 10 / 15)**: one `baseline_import` run per writer. Without score files the control rows are the
  fixture's frozen pipeline verdict (mode score_only, arm control, phase from the split); items without a pipeline
  verdict (the traps) get none; post_edit items are never a score_only control. With `--baseline` AA-729 score files
  (`aa729-score`, final, same fixture version), the score-only file replaces the fixture verdicts and the regenerate
  file adds regenerate rows (with the output). The run's `cost_usd` is the import's ($0); the paid AA-729 cost goes
  to `details.source_cost_usd`.
- **$0 guard (critic 7)**: `services/golden_set/llm_guard.install()` makes `LLMClient.generate` / `_generate`,
  `bedrock_satellite.invoke_claude` / `get_satellite_client` and `embed._call` raise in the importer process, before
  it reads anything. Patched by name, so the AA-927 call-site registry sees no `.generate` load.
- **CLI, not a script dir**: `python -m services.golden_set.importer` (the image copies `services/`, not `scripts/`).
  DRY RUN by default; `--apply` = one transaction with an advisory lock per set name; idempotent on (name, version) +
  `source_sha256`; a new version supersedes the active one **only when it is semver-greater** (review fix: importing
  1.0.0 after 1.1.0 is refused unless `--allow-downgrade`); re-importing an existing (superseded) version reports
  `exists` and supersedes nothing. Fixture and score files as a path or `s3:<key>` (bucket from `BRONZE_BUCKET`); an
  `s3://bucket/…` argument is refused.
- **Scores read as numbers from strings** (review fix): the AA-729 fixture stores `pipeline_verdict.score` as `"8.00"`
  (all 50 s1, all t2) and score files can carry DB numerics as strings. `derive._num` accepts int / float / Decimal /
  numeric string and drops bool, NaN, infinity and anything else; without it every a1 / t2 frozen control had
  `score = NULL`, and a baseline run is written once per writer per set, so the NULLs would have stuck.
- **`label_history` is tagged `pii:online_id`** (review fix, DM-6.1): it is copied from the fixture and holds
  `approved_by` (a staff handle). Kept as is (it is the label provenance), not mapped to a role.
- **No-tenant-text CI guard (critic 34-36)**: `services/golden_set/text_guard.py` (stdlib only) + a Lint step in
  `ci.yml`. Two checks: (1) fixture-shape markers (the JSON schema value of the AA-729 fixture, or its three top-level
  keys together), no key needed; (2) **keyed** fingerprints: `.github/golden_text_fingerprints.txt` holds 64-bit
  keyed BLAKE2b digests of normalised 8-word shingles (per text leaf: the smallest max(3, shingles / 20) digests) of
  every golden item's text and the tenant brand packs. **Keyed, not salted**: a plain or publicly salted list in a
  public repo is a membership oracle for guessed sentences (critic 36); with the key in the CI secret
  `GOLDEN_GUARD_KEY` the list says nothing. The file carries a key id (`# kid:`), so a scan with another key fails
  instead of passing. The step requires the key on this repo's own pushes / PRs; forks and Dependabot run markers only.
  Findings print path and count, never text (public CI logs).
- **Short brand phrases** (review fix): a tenant's brand text under 8 words (brand name, brand type, a short CTA or
  style line, 3-7 words) gives no shingle, so it is fingerprinted **whole** (domain-separated digest), from the tenant
  brand packs and the T9 `brand_audience` only. Left out on purpose: `forbidden_words` (AI-tell phrases AA's own
  lexicons also hold), `voice` adjectives, and every other short leaf of the fixture (ids, gate names, SEO keywords,
  place names: ~2 700 leaves that are not tenant text and would fail CI on ordinary code, with no way to see why).
  The scan checks every 3-7-word window only when the file's `# short:` header is non-zero. With fixture 1.1.0 the
  rule finds 5 such phrases, and all 5 are already public in this repo (migration 018's demo-tenant seed and the
  voice tests), so `--exclude-tracked` leaves 0 short digests today; the rule covers the next fixture version.
  1-2-word pieces (most CTAs in the packs are "Book now"-style) stay uncovered: a known limit.
- **Pre-existing text is left out of the fingerprints** (`--exclude-tracked`): at generation, 5 589 golden digests
  were already in the tracked tree (`origin/main` e5c82e9d), so they were excluded and the guard is green on main.
  Most are platform text (AA master tour itineraries and names, atom texts, SEO questions, gate messages, channel-style
  boilerplate); some are demo-tenant text already in tests and code comments (see Should know).

## Tradeoffs

- The trigger costs two indexed lookups per result row; results are written in batches of ≤ 100 by CLIs and jobs.
- `item_count` drifts after an erasure; a derived count would need a view or a trigger for little value.
- Excluding pre-existing digests means a pasted fragment made only of text that was already public before the guard is
  not caught. The alternative (fail on main) would block every PR until the old test text is rewritten.
- Fingerprint sampling (≥ 3 per leaf, 1 per 20 shingles) catches a pasted 40-word fragment about 85% of the time and a
  whole item always; a denser file costs repo size (the file is ~170 kB now).
- The A1 baseline is v1-writer output (before S250) and the T9 one predates #1015 (AA-790): baseline runs are recorded
  as they are; WM-20 marks the releases built on them `reverify` (plan Q8, critic 32).

## Decisions

- **Migration 287** (latest on `origin/main` and applied on Dev: 286). Guard 1 requires 284, 285 and 286 registered

- **Three tables.** `shared.writing_memory_release` (RLS ENABLE + FORCE, ids only: rules by id), `shared.writing_memory_shadow`
  (RLS ENABLE + FORCE, the output is tenant text; `input_source` never `golden_item` [C26]; scope / tenant = the
  INPUT's owner) and `shared.writing_memory_writer` (platform, no RLS: `memory_enabled` kill switch, default off, and
  `train_closed_month` [C28]; 4 rows seeded).
- **"Activate requires eval", twice** (WM-18 scope 2, ADR 0010 decision 1):
  - DB: CHECK `writing_memory_release_evidence_check` (presence of the refs per content class) + trigger
    `writing_memory_release_guard` (the refs are finished writing_memory runs of the same writer with the right kind
    and verdict: `r0_replay` pass — and for an `empty` release `details.byte_diffs = 0` over `details.inputs >= 20`
    as JSON numbers; eval `r2` pass, or `baseline_import` baseline for `empty`; shadow `shadow` pass; rules of the
    release's writer and owner with matching kinds, approved / active on the first activation).
  - API: `services/writing_memory/releases.evidence_problem` (pure, the same cases) on the locked row inside the
    write transaction → 409 with a code. When only the DB refuses, the route answers 409 `db_refused` (proof the
    second layer fired; integration test with a blinded mirror).
- **Empty releases skip shadow** [C23]: nothing to shadow; ADR 0010 decision 1 amended in this branch. Spec
  deviation from WM-18 scope 2 ("active requires eval refs and a shadow ref, except lexicon-only").
- **Transitions** draft → evaluated | rejected, evaluated → approved | rejected | draft, approved → active |
  rejected, active → retired, retired → active (rollback target) — nothing else. A same-status update changes only
  the reverify bookkeeping, notes and `previous_release_id` → NULL (the ON DELETE SET NULL of an erasure) [C18];
  identity / content are fixed after draft, evidence / approval after approval. A release retired by a rollback
  (`retired_reason` `rollback: …`) is never re-activated [C19]: `retired_reason` is not a bookkeeping column, so it
  cannot be edited to dodge that.
- **Pointer, rollback, train.** One active release per (writer, scope, tenant) (unique partial index). Activate
  retires the current one (`superseded`) and sets `previous_release_id`. Rollback: active → retired (`rollback:`),
  previous → active on its own evidence (rule status not re-checked: a rollback is never blocked by an expired rule);
  release 0 → 409 `no_previous` (the switch is the answer). Train [C22]: one `regular` release per writer and owner
  per month, `train_month` set at the first activation (unique index), refused for a closed month; ADR 0010
  decision 6 amended. Emergency [C20]: `emergency_reason` hard_stop_1..3 + `emergency_ref`; the API requires the ref
  to be a finished run of the owner's active release that stopped on `hard_stop`.
- **Reverify** [C21]: `reverify_scan` compares each active release's fingerprint (golden set name@version, the
  writer and judge stage routes, `registry.TAXONOMY_VERSION`) with now and flags it (keeps serving); a re-run needs
  `reverify_run_id` + approval (CHECK). Callers: the golden-set importer after a supersede (same transaction), the
  two llm-config PATCH routes for a writer stage or `writing_memory_eval` (own transaction after the change, never
  fails the route), the worker start (taxonomy), `POST /releases/reverify-scan`.
- **No FK `prompt_eval_runs.release_id` → release** (284 announced one; decided against): the AA-839 erasure planner
  turns every non-tenant FK child of an erased table into a cascade node, so a SET NULL key from the platform run
  ledger to a tenant release would make an erasure DELETE platform run rows (seen: the planner put
  `prompt_eval_runs` last, after `shared.tenants`). Guard 2 asserts the FK is absent. The release names its runs
  (RESTRICT). Same pre-existing planner trait for `shared.place_photo` (SET NULL → cascade) is left as is (AA-839's
  call; listed under Should know).
- **The insertion path** (`services/writing_memory/insertion.py`): one view per write = the platform pointer + the
  tenant pointer (explicit `tenant_id = $2`), fails open (any error / table missing / switch off → None, the writer
  runs exactly as without memory). Slots: A1 `a1_house_rules` in `s1_writer_v2.w_system_prompt` after the
  forbidden-words line (the S1 writer v2 only, plan Q12: the v1 / batch append stays frozen); T2 `t2_block` at the end
  of `build_t2_system_prompt` (before `t2_dashless`); T9 `t9_platform` appended to `SYSTEM_PROMPT` and `t9_tenant`
  lines right after the brand words line of `build_user_prompt`. Every slot renders "" for release 0; a release with
  content renders "" too (logged, stamp `ignored: true`) and the API refuses to activate it (`content_not_wired`)
  until WM-23 / 24 / 25.
- **Stamps from the writer that consumed the view** [C29]: A1 = `s1_writer_v2_live.write` returns
  `writing_release` (with `writer_version`), carried through graph state (declared in `ContentState`), `_rewrite_tour`

  `rejudge` rows (`scored_result_id` = the stored row). `eval_checks.control_mode` allows `regenerate` only for
  `reverify` runs (the 284 trigger refuses it too). A human-edited frozen output (post_edit) is never a control
  (critic 10): skipped and counted. Traps have no control.
- **Judge calibration** (scope 4): kappa of the judge vs the golden labels (pass / fail) on the FROZEN labelled outputs,
  needs >= 10 pairs and >= 0.6 (`judge_kappa`, `judge_counts` on the run; the 284 CHECK refuses counts with kappa <
  0.6). Without it the run is informative: hard stop 1 does not count, it stops after tune (no holdout money) and cannot
  pass. Calibration is separate from the control arm (review fix): every run (r2 and reverify, whatever release supplies
  the control) re-judges the frozen output of EVERY labelled non-trap, non-post_edit item of the writer and owner
  against the baseline_import run's control/score_only row, not only the planned items. See "Review follow-ups".
- **The judge** (`eval_judge.py`): one structured-output call per output on the judge route; rubric = the qtax-v1
  definitions of the reader-text classes (fact.*, scope.persona_promise, scope.framing, struct.leaked_instruction,
  struct.truncated); unknown classes dropped; a fact class forces fail; `judge_version` = sha256 of the system prompt.
  Hard stop 1 = a hard fact class (`registry.hard_fact_classes()`) on the candidate that the item's control lacks.
- **Sequence** (scope 1): calibrate (all planned controls, ~$0.002 each) -> probe (<= 3: traps first, filled with tune
  items, which keep phase `tune` in their rows because the trigger ties phase to split) -> tune -> holdout only when
  tune passes. Stops: any hard stop (a trap that obeyed its injection, a QA artefact, an isolation leak, hard stop 1)
  at once; futility at the end of tune; never on success. `goal`: `non_inferior` (empty release, code train) or
  `improve` (rules / repair_hint: fixed > new). Verdicts: pass / fail / informative (uncalibrated, or `--limit` used:
  a truncated run never passes) / invalid (cap, > 20% errors).
- **Affected tiers** (scope 1, 7): the operator names them (`--tiers`); A1 / T2 always add `fact_dense` + `long_9d`;
  none named = every item of the writer. Mapping a rule to tiers automatically is not specified anywhere; left open.
- **Writer paths** (`eval_writers.py`): A1 `_rewrite_tour` (the S1 graph; writer v2 per the worker's env), T2
  `_rewrite_tour(tenant)` + `run_t3_qa_gate`, T9 `write_content` only. The full T9 loop (`run_write_background`) writes
  the piece row at every step and is not safe to drive from an eval, so a T9 candidate is a first draft compared with a
  final control: conservative (it can only look worse). Recorded as `details.t9_first_draft_only`.
- **Isolation probe**: every OTHER tenant's brand name, or >= 2 DISTINCTIVE 6-word runs of its brand pack text, minus
  anything in the output's own source and brand. Distinctive = >= 3 content words (function words and generic travel
  phrasing are a stop-list) and held by no other foreign tenant's pack. One such run is reported (`weak_tenants`), not a
  stop. The F10 embedding check (>= 0.92) is not run (cost and an embed call per output).
- **Seeded fault** (Done-when "a seeded failing candidate stops at tune"): `--seed-fault qa_trace | unsourced_claim`
  appends a fault to the stored control text, makes no writer call (judge cost only), skips traps, is refused with a
  release, never ends `pass` (a fault the judge misses ends `informative`), and cannot be attached: the evidence check
  requires the run's release_id to be the release's (API + CIS 292).
- **Shadow** (WM-21): `shadow_size` = 20 (A1, blog, LinkedIn / other social), 50 (T2, Facebook), 70 for a t9_social
  rules release with no `--channel` (50 Facebook + 20 other channels, `shadow_quota`: its one shadow run is the evidence
  for every channel), <= 10 repair_hint-only, 0 lexicon-only and empty; `--size` only lowers it; `--force-size` runs an
  empty release as an operator check (Dev has no release with content: WM-23..25 are not built). A lowered or forced
  size, or a bucket short of its quota, is `informative`, never `pass`. Inputs: recent real (90 days), golden items
  excluded by row id AND by tour (A1 `tour_id`) / published tour (T2), so a newer version of a golden tour is excluded; T9 targeted by the rules' classes -> gates on the final gate ledger, then filled with the most recent; A1
  (writer v2 rows) and T2 (newest succeeded t2_rewrite per tour + tenant; input id = its tenant_tour_version) most
  recent only. Tenant release: + 2 inputs of another tenant written WITH the candidate's view (`probe`). Stops at the
  first fail; verdict pass needs as many real inputs as the size (else informative). Cap default and max $7.
- **Cross-tenant probe rows** (the WM-18 open item): kept. A probe row belongs to the probed tenant and cascades with the
  other tenant's release; either erasure deletes it, never keeps tenant text. Documented in `shadow.py`.
- **Jobs, not exec sessions**: `writing_memory_r2` and `writing_memory_shadow` (background, cap 1, max_attempts 1,
  expected 5400 s). The CLIs are DRY RUN by default (plan + estimate, $0) and `--enqueue` queues the job. No admin

## Judge calibration diagnosis (S255): why step D got kappa -0.073

R2 step D (writer t9_social, 17 items = 15 labelled LinkedIn texts + 2 traps; 13 calibration pairs after the 2
post_edit items) ended informative / completed / tune with `judge_kappa = -0.073`, `judge_counts = false`.

### Finding

- **Not a computation bug.** `cohen_kappa` is the standard formula; pairs are `(item.label_verdict, judge verdict)`
  (kappa is symmetric in the raters and in pass / fail, so an inverted mapping cannot change it); `same_row`
  calibration uses the item's own label. Kappa over the golden labels of t9_social (fixture 1.1.0: 10 pass, 3 fail
  among the 13) equals -0.073 for exactly one confusion matrix: **the judge passed 2 of the 10 pass-labelled texts and
  failed 8; it failed 2 of the 3 fail-labelled texts.** Judge pass-rate 3/13 against a label pass-rate 10/13: the
  judge is far stricter than the labels, not inverted. (Derived from the stored kappa and the fixture labels; `kappa_diag.py` checks it on the live rows.)
- **Root cause: the judge answered a different question from the labels.** The golden labels use the AA-729 panel
  rubric (`scripts/aa729/labels.RUBRIC`): pass = publishable as is **or after a light edit**. Every pass label in the
  golden set is grade `light` (s1 6, t2 3, t9_blog 6, t9_linkedin 10; no `as_is` at all). The judge prompt said
  "verdict = fail when ... the text would not be publishable as is" and `parse_verdict` forced fail on ANY fact class,
  including block-severity `fact.embellish` / `fact.self_contradiction`. A light-edit text (one embellished phrase, one
  off-topic title field) is therefore a judge fail by construction. Same pattern as the AA-729 baseline gates on these
  texts (false fail 7 of 13, false pass 0) and lesson S248 ("a judge that never passes makes kappa meaningless").
- **Contributing: the T9 SOURCE lacked the brief.** `eval_writers.source_text` gave the judge the seed, facts, CTA and
  brand but not the scope line or the angle brief (`chosen`) the writer was told to follow; the panel read the full
  input and accepted wording that came from the brief, and the judge cannot check scope without the scope line.
- **Fragile gate.** With 3 fail labels, one item moves kappa by ~0.2 (leave-one-out range in the script); a one-class
  label set gave kappa 1.0 to a constant judge and counted.

### Decisions

- Fix the instrument, not the labels: the golden labels (approved S245, fixture 1.1.0 is the measuring standard) define
  what pass means; the judge now uses the same rubric text (`eval_judge.LABEL_RUBRIC`, test-pinned equal to
  `labels.RUBRIC`). Classes are reported whatever the verdict ("also when the verdict is pass") and no class forces
  fail; hard stop 1 still reads the classes (`hard_fact_classes`), so a NEW hard class still stops a calibrated run.
- Score scale tied to the label grades: 9-10 as is, 7-8 light, 4-6 heavy, 0-3 rewrite.
- T9 SOURCE adds `SCOPE:` and `BRIEF:` (angle `name`, `formula_fit`, `best_final_style`; not the search questions or
  ids), for both stored shapes (golden `context`, live `writer_input`).
- `judge_counts` also needs `MIN_KAPPA_PER_LABEL` (3) pass and 3 fail labels; the run stores `details.kappa_labels`
  and the DRY RUN prints `calibration_labels`. Current golden sets meet it (a1 6 pass / 44 fail, t9_blog 6 / 7,
  t9_social 10 / 3); t2 (8 pairs) was already below `MIN_KAPPA_PAIRS`.

### Changed

- `services/writing_memory/eval_judge.py` (prompt + `parse_verdict`; `JUDGE_VERSION` changes, so new results are only
  compared with new results, as designed), `eval_writers.py` (`T9_BRIEF_KEYS`, source), `eval_checks.py`
  (`label_counts`, `judge_counts(..., labels)`), `config.py` (`MIN_KAPPA_PER_LABEL`), `r2.py` (wiring, DRY RUN).
- Tests: rubric equality + prompt wording, `parse_verdict` keeps the judge's verdict, T9 source holds scope + brief,
  `judge_counts` per label, runner: a one-class label set never calibrates, `kappa_labels` recorded. The runner
  fixture now carries 3 fail-labelled holdout items with a frozen text the fake judge fails.

## Calibration pair review (S256): labels and rubric of the 13 t9_social pairs

After CIS #1096 the re-run (`de6265e6`) moved kappa from -0.073 to 0.235 (still < 0.6). With 10 pass / 3 fail labels,
0.235 is reachable by one matrix only: the judge passed 4 of the 10 pass labels and failed all 3 fail labels. This
lane read the 13 frozen texts with their source, scope, brief and panel votes (fixture 1.1.0, root
`docs/eval/aa729/`). The per-pair table, with the text evidence, is in the root audit
`docs/audits/2026-10-28-S256-aa919-calibration/README.md` (texts are quoted there, never in this public repo).

### Finding

- **The panel applied its rubric inconsistently on one-phrase claims.** The rubric says pass = a light edit
  "(minutes, no fact or structure change)" and fail = "an invented or wrong fact, a promise the source does not make".
  A one-clause trip promise is both "minutes" and "a promise": three texts with one such flaw were labelled heavy
  (t9l-002 meta description, t9l-009 opening line, t9l-010 one sentence promising time), two texts with the same kind
  of flaw were labelled light (t9l-001 SEO title promising a product the trip lacks, t9l-003 one sentence promising an
  activity the itinerary does not list). A judge that follows the rubric text cannot agree with both groups.
- 2 labels wrong (t9l-001, t9l-003: pass -> fail heavy), 6 pass labels right but borderline enough that a strict judge
  may fail them (wording, reflection, brief-asked content), 5 labels right and clear.

### Decisions

- **Relabel the two inconsistent panel labels** in a new fixture version, **1.2.0** (labels are immutable per
  version; a relabel is a new version, as WM-17 designed). New `scripts.aa729.labels relabel` path: takes a review file
  (`from` verdict must match, verdict and grade must agree, a reason is required), touches `agent_panel` labels only
  (`RELABEL_SOURCES`; edit-based, hand and synthetic labels are other evidence), keeps the old label in the new label's
  evidence (`previous`) and logs `source: calibration_review` in `label_history`. Approved under the S256 session plan.
- **Settle the rubric instead of leaving it to each rater**: `labels.RUBRIC["rules"]` (5 lines) and the same tuple in
  `eval_judge.LABEL_RUBRIC["rules"]` (test-pinned equal; rendered in the judge prompt and the panel pack). A claim the
  source does not support, or a trip promise the itinerary does not make, fails even when one phrase would fix it, in
  any customer-facing field; wording, garbled-but-true phrasing, reflection and brief-asked content do not. This is
  the stricter reading of the existing text, and the product rule (never promise what the source lacks).
- The judge prompt line "a flaw a light edit removes (one phrase, one field)" became "a flaw a wording fix removes": the
  old wording told the judge a one-phrase fact flaw is light, against the rules.
- `JUDGE_VERSION` changes (the prompt changed), so new results compare only with new results, as designed.
- No threshold change: `MIN_KAPPA` stays 0.6, `MIN_KAPPA_PER_LABEL` 3.

### Changed

- `scripts/aa729/labels.py` (`RUBRIC["rules"]`, `RELABEL_SOURCES`, `relabel()`, `relabel` CLI, rules in the pack),
  `services/writing_memory/eval_judge.py` (`LABEL_RUBRIC["rules"]`, prompt).
- Tests: `test_aa729_golden_set.py` (+9: relabel applies to panel labels only, keeps the previous label, refuses a
  stale / inconsistent review, needs approver + review ref, pack carries the rules), `test_aa919_eval_checks.py`
  (rubric equality incl. rules, the one-phrase rule is in the prompt).
- Root (not this repo): `docs/eval/aa729/fixture-1.2.0.json` (2 labels changed, nothing else; built by the CLI above)
  and the review file `docs/audits/2026-10-28-S256-aa919-calibration/relabel-review.json`.

### Tradeoffs

- Relabelling after seeing the judge risks fitting labels to the judge. Guarded by: only labels that contradict the
  panel's OWN heavy labels on the same flaw were changed; the six pass labels the judge may still fail were kept
  (the rubric was clarified instead), and one disputed label the business owner decided in S245 was kept.
- The stricter rule moves t9_social to 8 pass / 5 fail, which also makes kappa less fragile (3 fail labels made one
  item swing kappa by ~0.2). It can lower a1's pass recall slightly; a1 is 44 fail / 6 pass, so the effect is small.
- Expected kappa is not guaranteed >= 0.6: with 8 / 5 labels the judge must pass at least 6 of the 8 pass labels and
  fail all 5 fails (0.698); 5 of 8 gives 0.562. If it stays low, the next lever is the judge's SOURCE (the brand
  idea is still not shown to it, while the panel saw the whole writer input), not the threshold.

## S256 — judge source parity (R2 eval judge only)

Run cc0f75cf (golden set aa729@1.2.0, 8 pass / 5 fail t9_social labels): kappa 0.316. The judge failed all 5 fail
labels and passed only 3 of 8 pass labels; the 5 disagreements (t9l-004/005/011/013/015) were mostly `fact.embellish`,
while the panel's full-source verifier had found every flagged fact in the writer input. The judge read the seed, the
scope, three angle fields and the brand NAME (~4.3k chars); the panel read the whole input (~8k chars for LinkedIn).

### Decisions

- New `eval_judge.judge_source_text(writer, inp, shared_inputs)`: the R2 judge's SOURCE. For T9 it is the whole
  stored writer input in labelled sections, in order: SEED, ROUTE, SCOPE, TRIP (trip name, destination, places on the
  itinerary), ANGLE BRIEF (name, formula, why it works, how to write it), GOAL (name, description,
  logic), BRAND PACK (name, type, core idea, audience, mindset, voice, style guide, on-brand examples, forbidden words),
  CHANNEL (style, structure, avoid), WRITER ASKS (CTA, keyword, lead focus, search questions on a blog), FACTS last.
- Bounded and deterministic: each section has a fixed cap (`T9_SOURCE_SECTIONS`), cut by `clip()` at a line, else a
  word, boundary with a visible `[... cut for length]` mark; FACTS takes the space left; the whole is
  <= `SOURCE_CHARS` (raised 14000 -> 24000) so `build_user_prompt` never cuts it mid-section. On the 1.2.0 fixture:
  every t9_social source is whole (6.1-8.4k chars); 12 of 15 t9_blog sources are whole, 3 cut only in the seed
  (19.4k -> 16k).
- ROUTE only carries a route moment the seed does not already hold: a T9 blog's seed IS its joined route moments, and
  the old source carried them twice (40k chars for a 19k seed).
- Left out on purpose: the brand's own `system_prompt` (writer instructions, an injection surface), `sibling_openers`
  (other pieces' first lines), ids, `brand_rubric_text` (the same brand pack, composed), `facts_pending`.
- A1 / T2: `judge_source_text` returns `eval_writers.source_text` unchanged (only `SOURCE_CHARS` grew, so a long tour
  is cut later).
- The judge also returns `unsupported_claims` [{class, claim, why}] (lessons S232: a fact judge that must quote the
  claim stops flagging text the source holds). The prompt says a class it cannot tie to a quoted OUTPUT phrase is not
  reported. Evidence only: no code rule reads it; R2 stores it in `eval_item_result.details.judge_claims` (and in
  `details.calibration.judge_claims` when the calibration text differs from the control). No migration (jsonb).
- `judge_version()` = sha256 of the system prompt AND the source layout (sizes, sections, keys, cut mark, reply schema),
  so a change in what the judge reads is a new judge version even when the system prompt stays the same.
- `MAX_TOKENS` 600 -> 1200 for the claims.

### Changed

- `services/writing_memory/eval_judge.py` (source builder, claims, version, prompt), `services/writing_memory/r2.py`
  (judge source = `judge_source_text`; claims into result details), `services/writing_memory/eval_writers.py`
  (docstring only: `source_text` is the isolation probe's allowed text, kept as it was).
- Tests: `tests/unit/test_aa919_judge_source_parity.py` (new: panel fields present, both stored shapes, route dedupe,
  bounded + deterministic + never cut by the prompt, clip boundaries, `source_text` unchanged and A1/T2 identical,
  version covers the layout, strict schema, claims parse, only `r2.py` imports `eval_judge`, R2 passes the parity
  source and stores the claims); `test_aa919_eval_checks.py` (parse result now carries `claims`).

### Tradeoffs

- Parity can also make the judge more lenient on a fail label (t9l-001's seo_title "…Bhutan Meditation Retreat"):
  rule 5 still fails a trip promise the itinerary does not make, and TRIP now lists the itinerary's places, but if 001
  flips to pass the gain on the pass side is cancelled (6/8 pass + 4/5 fail = 0.530).
- Independent review (S256), fixed before the paid run: the first cut also showed the judge two things the WRITER
  never got. (1) The angle's `answers` (T8's ranking claim of the search questions it answers; the writer prompt shows
  only name / why it works / formula / best final style): on the fixture it put "Is there a meditation center in
  Bhutan?" next to t9l-001's "Meditation Retreat" title, the exact leniency risk above. (2) Search questions on a
  social piece: the writer prompt shows them on a blog only, but a social job's context keeps the tour's raw People
  Also Ask (t9l-011 carried 4 questions its writer never saw). Now: no `answers`; questions only for `t9_blog`, from
  `search_questions` (live writer_input) else `people_also_ask` (golden context, set to the writer's by
  select_samples); `real_questions` (the unfiltered candidate chain) is never read. The rule is part of the source
  layout, so the judge version moved (74e27ab5cc1b -> 73e641a99aca).
- Still in, though not in the writer prompt: TRIP's places on the itinerary / route hub (what the T10 gates ground
  against; rule 5 needs the itinerary) and the full `trip_name` (a golden context drops the scoped `writer_trip_name`,
  so the judge may see out-of-scope places in the trip name).
- Judge input roughly doubles for LinkedIn (~4.3k -> ~8k chars) and output grows by the claims: at the judge route's
  list price (0.20 / 1.20 USD per Mtok) about +0.001 USD a call, ~+0.02 USD a t9_social run.
- No threshold change (MIN_KAPPA 0.6) and no label change in this step.
