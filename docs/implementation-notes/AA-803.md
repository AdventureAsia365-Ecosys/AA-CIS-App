# AA-803 — Claude Haiku 5.5 / Sonnet 5.5 in the Model Gateway (S246)

Scope of this slice: catalog rows for the two newest Claude models on Bedrock, a request builder that
does not get a 400 from them, and dropping the LEGACY Sonnet 4.5 acc2 profile from the `sonnet` row.
No stage route changes; moving stages is a separate, measured A/B.

## Decisions

- **Migration, not the admin API.** `PATCH /admin/llm-catalog/{model_key}` only edits price / enabled
  (`catalog._CATALOG_EDITABLE_FIELDS`); new rows and profile ids are a code + migration change (ADR 0005).
  Migration 259.
- **acc3 + acc1 profiles, no acc2.** acc2 refuses every Claude call (channel-program account, AA-843), and
  the Converse path never calls acc2 anyway.
- **`sonnet` acc2 key removed** rather than repointed at Sonnet 4.6: any acc2 Claude profile only adds an
  attempt that always fails (the TripPlanner gateway tries acc2 last).
- **Prices: Anthropic first-party list prices**, recorded as such in `price_source`, with the note that
  Bedrock is partner-priced and the AWS pricing page must confirm before a stage moves (admin PATCH).
  Haiku 5.5's > 100K-token prompt tier is not modelled (single price per row).
- **Forced tool choice → `auto` + instruction** for structured output on models matched by
  `_NO_FORCED_TOOL_CHOICE_MARKERS` (Sonnet 5.5, Opus 5.5, Fable 5.1, Mythos 5.1), matched on the
  Bedrock profile id. **Haiku 5.5 keeps the forced tool**: it accepts `any` / `tool` (the response then
  starts with the tool call, no thinking block), which costs fewer output tokens and gives a reliable
  schema on the 9 high-volume Haiku stages. A first draft listed Haiku 5.5 too; the review against
  Anthropic's Haiku 5.5 migration guide corrected it before the migration PR. Any other model that answers a forced tool choice with a ValidationException is
  switched at runtime, retried once (not billed) and remembered per process.
- **Capability as code, not a new catalog column.** A `supports_forced_tool_choice` column would make the
  catalog SELECT fail on any process that deploys before the migration (catalog unreadable = every
  non-legacy route fails). The marker list lives in `shared/llm_client` only.

## Changed

- `shared/llm_client/client.py`: `_forced_tool_choice_ok`, `_use_auto_tool_choice` (instruction as a second
  system block so the first block — the cache prefix — is unchanged), `_converse_with_param_downgrades`
  (temperature downgrade as before + tool-choice downgrade), `_first_tool_input(allow_text_json=)` accepts a
  JSON object answered as text under `auto`.
- `api/migrations/259_llm_catalog_haiku_sonnet_5_5.sql` (+ Infra byte copy needed in
  `AA-CIS-Infra/db/migrations/cis/`).
- Tests: `tests/unit/test_aa803_claude_5_5_request_shape.py`, `tests/integration/test_aa803_migration_259.py`.

## Tradeoffs

- `auto` tool choice is less strict than forced: a model may answer in text. Covered by the text-JSON
  fallback, then the existing AA-714 schema retry, then the route's next model.
- No `thinking` field is sent: the new models run adaptive thinking at their default effort (Haiku 5.5
  `medium`, Sonnet 5.5 `high`). Thinking tokens count against `maxTokens`; a stage with a tight
  `max_tokens` could see more `max_tokens` stops. The A/B per stage will show it; effort control is a
  later change if needed.

## Should know

- Order: Infra copy of 259 → DB Migrate check/apply → smoke script (one call per model and account,
  stage `adhoc_s246_models`) → merge/deploy the app PR → only then route a structured-output stage to
  either model.
- `opus-5-5` (already in the catalog, eval only) also matched the forced-tool 400; it gets `auto` now too.
- The TripPlanner gateway's Converse call sends no temperature and no tool config, so it needs no change.

## Meal claims from the source (Jev question review, before J04/J05 go OFF)

A second AA-803 slice. AA-803 also reviews which Jev questions earn their cost (S246 report in the private root
repo, `docs/audits/2026-10-21-S246-jev-question-eval/`); Nghiệp approved every proposal on 21/10/2026.

`a1_claim_supported` (J04) and `a1_promise_unsupported` (J05) go OFF in one step. Before that, a meal claim the
source itself states must stop raising `ITINERARY_MEAL_TIME_INVENTED`: until now only an enforced Jev accept on
`a1_claim_supported` cleared it. The read-only replay `aa803-j04` found the code cleared by Jev on 71 of 914
tours, and the samples were the source's own meals (the same meal on the same source day, or in INCLUSIONS).

### Decisions

- **New module `services/content_generation/meal_claims.py`**, called from
  `brand_audit_node.meal_time_claims_supported` before Jev. A meal-claim sentence is sourced when every meal it
  claims is covered for its day:
  - the same source day names the meal, not negated: a meal word (`picnic lunch`, `evening meal` = dinner,
    `picnic/packed meals` = lunch), a code list (`Meals: B, L, D`, `Meals  B D`, `(L, D)`, `B/L`), or
    `all meals` / `full board` (B, L, D) / `half board` (B, D);
  - or INCLUSIONS covers it for every day. Only an unqualified daily form does: `daily breakfast`,
    `breakfast every morning`, full or half board, `all meals` not tied to the itinerary, or a count that
    reaches the tour length (`11 breakfasts` on 11 days; on N days with N-1 nights, N-1 breakfasts cover days
    2..N and N-1 dinners days 1..N-1). On a one-day tour every meal INCLUSIONS names is that day's.
  - A qualified INCLUSIONS mention (`Welcome dinner`, `1 lunch`, `Lunch on Day 2`, `Chinese lunch`,
    `8 dinners` on 11 days) covers nothing by itself: it counts only through the same day's own text.
  - "Meals [included] as per / in / specified in / as mentioned in / where indicated in the itinerary" and a
    code legend (`B = Breakfast, L = Lunch, D = Dinner`, two or more pairs) are removed before meals are read,
    so they add nothing. They are never read as three meals every day.
- **A day's structured list is authoritative** (`Meals: B`, `Meals included: Breakfast | Dinner`,
  `Meals Included: • Breakfast, Lunch`, `(B)` in the title). INCLUSIONS and passing mentions ("after lunch,
  we...") do not add a meal the list leaves out. The only exception is the same day saying in so many words
  that the meal is provided ("A picnic lunch on the Wall is provided"): operators' lists miss these.
- **Negation blocks, in tiers (source side).**
  - HARD, an exclusion in so many words (`not included`, `own expense`, `own account`, `payable`, `self-pay`,
    `excl.`, `for purchase`): it negates every meal of its comma segment within `HARD_WINDOW` = 12 words, and
    reaches back over the clause when its segment is a bare predicate ("Dinner at the hotel restaurant, which
    is famous for its wine, is not included").
  - EXPLICIT, the meal is the traveller's to arrange (`optional`, `on own`, `own choice`, `can be arranged`,
    `on request`, `upgrade`, `recommend`, `suggest`, `purchase`, `unless`): within `NEG_WINDOW` = 6 words.
  - WEAK (`not`, `no`, `never`, `except`, `without`) within 6 words, and SOFT (`free time`, `at leisure`,
    `available`, `tomorrow`, `next day`, `if you`) within 6 words before the meal or 1 word after it.
  - HARD and EXPLICIT always block. WEAK and SOFT give way to the same day's structured list or "provided"
    statement: "Enjoy dinner then an evening at leisure ... Meals Included: Breakfast, Dinner" keeps dinner.
  - A bracket that holds a cue and names no meal negates the comma segment before it and closes it:
    "lunch at a local restaurant (own account)", "lunch at a ... 5-star hotel (optional, not included)" are
    negated, while "[No cycling] After breakfast ..." leaves the breakfast alone. A bracket that names a meal
    is its own clause ("(Lunch is not included)" negates only lunch). Any other bracket is read inline.
  - Generic forms ("No meals included today", "Meals: None") negate all three. "No extra charge" / "free of
    charge" are positive. A meal named in EXCLUSIONS is blocked; a generic exclusion ("meals not mentioned in
    the itinerary", "drinks with meals") blocks nothing.
  - Clauses split on `. ; ! ?`, newlines and `but / however / whereas / while`, not on commas, `|` or bullets:
    "Breakfast, lunch and dinner are not included" negates all three.
- **Output side: a meal leaves the claim only on an explicit exclusion** next to it (HARD in its segment, or
  `optional` / `on your own` / `no lunch` within 3 words). Any other "not" / "no" keeps it, so "Breakfast is
  included, and dinner is served at a restaurant not far from the river" still claims dinner and needs it in
  the source. A meal named next to a generic "No meals are included except ..." is claimed.
- **Times are never inferred.** The existing am/pm check runs first, unchanged (whole source). A meal sentence
  with a time (am/pm, 24-hour `19:30` / `19h30`, `noon`, `midnight`, `7 o'clock`, `half past seven`) is
  unsourced unless the same source day or INCLUSIONS states that time (the whole source when the day is
  unknown). "Midday" and "afternoon" are parts of the day, not times, and are not checked.
- **Day matching.** The sentence's day comes from its "Day N" title, and the source day from
  `grounding._source_days` (the one splitter). No neighbouring days, unlike `unit_source`. When the source
  cannot be split (parser fallback on a multi-day tour) or the sentence has no day, only INCLUSIONS can cover
  it. A one-day source (no marker past Day 1) is its own day.
- **Short and title-line claims are now checked.** `grounding.sentence_units` drops sentences under
  `MIN_WORDS` (4) and day-title lines, so "Lunch is included." or "Day 3 — Hue (B, L)" never had a unit, and
  the code fired on them whether or not the source had the meal. The rule now reads every sentence
  (`meal_claims.itinerary_sentences`, same split as `sentence_units`). A short or title-line claim the rule
  does not source keeps the code: Jev is never asked about it.
- **Jev stays the fallback while the questions are on.** Only sentences the rule does not source go to
  `judge_units`, with the same per-unit sources and subject keys as before (so a cache hit as before). Once the
  question is off, `decide()` returns `skipped`, nothing is enforced, and the code stays on any unsourced
  claim: fail-closed.

- **Review round 3: day matching is trusted only when it lines up (fail-closed).** A probe found 23 ways the
  rule still cleared a meal the source does not provide (the rule runs before Jev, and once
  `a1_claim_supported` is off nothing checks what it clears). The fixes all go the safe way: when it is not
  clear that the meal is provided on that day, the meal is not sourced.
  - Output days must be the source days one to one (`unit_meal_sourced(..., out_days)`). A writer that split
    or merged a day shifts every later day (output Day 5 checked against source Day 5, another day). A grouped
    source header (`DAY 11 & 12 - Ella`, `Day 8, 9 and 10`, `Days 1-3`) is one block filed under its first
    number: it still matches when the writer kept it as one day; when the writer gave each of its days an
    output day, the other days match and the block's days do not.
  - A source block whose text names another `Day N` is not one day: an inline `Day 3:`, a quoted `"Day 5 /`
    header the marker regex does not read, an `Extra Day 01` extension, `on day two` of a two-night block.
  - A one-day source is its own day only when the output is one day too (`OVERNIGHT TRIP` has no markers and
    no day count, but the writer wrote two days). `n_days` for INCLUSIONS is at least the output's last day.
  - A tour-wide count in a day's text (`Meals included: 7 breakfasts, 3 lunches` after the last day) is not
    that day's meal. Plural meal words only, so `a three course dinner` stays.
- **Review round 3: INCLUSIONS.** A scoped board covers no day: `All meals during the trek`, `Full board on
  safari days`, `All Meals while on trek (Veg) from day 1st dinner to day 8th breakfast`. The scope check reads
  the item before the clause split, because `while` splits clauses. `throughout the tour/trip/stay` stays
  whole-tour; `throughout the trek` no longer does. A daily cue covers only its own meal: the meals between the
  cue and the meal must be a plain list, and no day qualifier may follow the meal (`Daily breakfast and lunch
  on Day 3` covers breakfast only; `Breakfast daily, dinner on Days 3-5` breakfast only).
- **Review round 3: source-side cues.**
  - A bracket that says "no meals" (`(Overnight stay・No meal provided)`, `(Meals: None)`) is its own clause, so
    the generic negation sees it and blocks INCLUSIONS for that day.
  - A strong negating bracket (hard, explicit or clause cue) reaches its whole comma segment, up to
    `BRACKET_WINDOW` = 25 words, but not back over a `Meals included: ...` list. A weak-only bracket
    (`(no cycling)`) stays a 12-word hard cue. The rewrite tokens contain no plain `not`, so a bracket never
    reads as a weak cue on the meal after it.
  - A comma segment with no meal that opens with a cue reaches back over the clause (`, optional in your tour
    package`, `, at own expense`), and so does a short last segment that is only a condition (`, if time
    permits`). A condition that goes on (`and if you have enough free time, visit a factory`) does not.
  - HARD gains guest-paid forms: `expense` (passenger's / guest's / your), a final `own` / `extra`
    (`(own)`, `Lunch: Own`, `(extra)`), a price (`USD 10`, `$8`, `500 baht`), `self-arranged` /
    `self-catered`, `pay direct` / `paid locally`.
  - EXPLICIT gains `if time / if you / if desired`, `time permitting`, `should you`. After the meal it counts
    only inside the meal's comma segment.
  - PRE, only before the meal: `opt for / opt to`, `free to`, `tips`, `grab`, `find`, `choose`
    (`After breakfast, choose a hike` keeps the breakfast).
  - CLAUSE, the whole clause: `those who`, `for those`, `guests on / who / taking`, `depending on`,
    `subject to`, `on the deluxe option`, `premium package`.
- **Review round 3: output side.**
  - The claim regex (`ITIN_MEAL_INVENTED`) also reads plural and future forms (`Lunch and dinner are
    included`, `dinner will be served`), a meal noun up to four words before its verb (`meals on board the
    junk are prepared`), `All meals`, `full board` / `half board`, `Evening meal included`, and feast / BBQ /
    picnic / brunch. A gap word may not be `not` / `no` / `optional` / `recommendations`, so `Lunch is not
    included` and `Dinner recommendations are provided` stay out.
  - A meal leaves the claim only on an exclusion in its own comma segment, within 3 words. Every output
    bracket is its own clause. So `(drinks not included)`, `for purchase` seven words on, or `after an
    optional kayak, lunch` no longer drop the meal.
  - A bare plural `meals` claims all three, unless a list right after it says which (`meals (breakfast and
    dinner) are provided`, `Meals: B, L`) or it refers to the day's list (`as listed`).
  - Nouns that name no meal: feast / BBQ / banquet claim the meal of the clause's time of day (evening =
    dinner), else lunch and dinner. A bare picnic claims lunch, and a singular `a meal` claims its time of day
    (else it stays a generic claim). `brunch` is breakfast and lunch, on both sides; `luncheon` is lunch.
  - Code lists also take `and`, `|`, `·`, `•` (`Meals: B, L and D`, `B | L | D`).
  - A sentence about another day is not sourced (`tomorrow`, `next morning`, `the following day`, a `Day N`
    that is not its own day): reason `other_day_reference`.

### Changed

- `brand_audit_node.meal_time_claims_supported`: the rule runs first; Jev gets only the unsourced, askable
  sentences; an unsourced short or title-line claim keeps the code without a Jev call.
- Before, a tour could clear the code through Jev on its long sentences while a short unsourced "Dinner
  included." was never checked. Now that short claim keeps the code. This is stricter than main, on purpose.
- Q0 harness (`tests/unit/quality/chain.py`): a case can set `brand_audit.pre_audit: true` to run the real
  `pre_audit_checks` inside the stubbed brand audit, and then the pre-audit codes count as observed. This
  is a harness change, so the PR needs the `q0-relabel` label and an independent review
  (`.github/scripts/q0_red_on_base.py`). It adds an option and changes no existing case: the 68 earlier
  cases pass unchanged.
- New Q0 cases (`cases/a1_meal_claims.json`, all `no_fire`, Jev `none` = question off): same-day word,
  INCLUSIONS "all meals", day code list, and a short sentence. All four are red on `origin/main` (checked
  locally with the red-on-base script: code fires, flag_fix makes an unscripted call).

- Review round 3: `unit_meal_sourced` takes the output's day numbers (`output_day_numbers`, day 0 ignored),
  passed by `meal_time_claims_supported`. Without them (the offline replay as written), the alignment check is
  skipped and only days on or after a grouped block are unmatched. The unit-test helper now writes a full
  itinerary (one output day per source day), as the writer does. `Full board on the trek` moved from the
  sourced list to the scoped, not-sourced list.

### Tradeoffs

- **Strict per-day matching** keeps the code when a writer moves a meal one day ("overnight on half board"
  on day N, with the breakfast in the source on day N+1), or when the source names it only as "a home-cooked
  meal". The replay shows these are a minority. They go to flag_fix like before, and nothing is published
  with an invented meal.
- **Structured list over narrative** keeps the code on cases where the source contradicts itself (list says
  B, narrative says "we will enjoy our lunch in a local restaurant"). Jev accepted a few of these. The rule
  does not, because the list is the operator's statement of what is included.
- **A narrative mention counts as sourced** when the day has no structured list ("enjoy lunch at a local ger
  camp" sources "Lunch is served at a local ger camp"). This matches what Jev accepted and is the approved rule.
  It can clear a claim that the meal is included when the source only says it happens ("Lunch break in
  town" sources "Lunch is included."). The risk is accepted because the meal itself is in the source; the
  mentions that say the meal is NOT provided (on own, free time, can be arranged, payable, ...) are cues.
- **More cues, more kept codes.** The tiered cues keep the code on a few sourced meals in scraped text with no
  punctuation ("Back to Campsite for Breakfast At leisure in the Campsite" reads "at leisure" right after
  the breakfast). Fail-closed, 1 case in the replay window.

- **Review round 3 cost (offline replay, same data as below).** Of the 167 versions that had a meal claim and
  supported clocks before, 127 clear now (139 before round 3). The 12 newly kept: 5 day matches no longer
  trusted (writer dropped or split days, a split grouped block, quoted headers on 6bf91a8b), `grab a local
  Hunter's Box lunch` (PRE cue, kept on purpose), and real catches the old regex never saw (`All meals are
  included` on a B/L day, `Full board.` on a day with no lunch). The broader claim regex adds 90 versions
  that were never checked before. 53 of them clear. The 37 kept are mostly `full board` / `all meals` on trek
  or lodge days whose source day names no meal (prod INCLUSIONS may cover some, but `Full board on the trek`
  no longer does), half board on an arrival day, and vague generics (`meals arrangements follow the standard
  included basis`). All are fail-closed (flag_fix, then `manual_check`), none publishes an invented meal.

### Should know

- **Numbers after OFF.** `grounding.classify` raises `UNSUPPORTED_NUMBER` unless the verdict is an enforced
  accept. With the question off the verdict is `skipped`, so a novel number always raises it (fail-closed) and
  goes to repair/flag_fix, with `manual_check` if the repair fails. A unit test pins this
  (`test_unsupported_number_stays_fail_closed_with_jev_off`).
- Offline replay (S246, $0, local data only: the J04 result plus the AA-925 export of source and published
  itineraries; no INCLUSIONS in that export except the 160-character cut the J04 samples carry). After the
  review fixes:
  - J04 `sample_meal_waivers`: only 6 of the 71 waivers carry text. 3 of 3 replayable cleared (one through
    "all meals specified in the itinerary" + the same day, one through "11 breakfasts" on 12 days with 11
    nights, one through "Chinese lunch" on a one-day tour). The other 3 are versions that are not published,
    so their day is unknown; each sentence is sourced by at least one source day.
  - J04 `missed_waiver_sample`: 16 of 17 replayable cleared (3 versions not in the export). The one left keeps
    the code by design: its day list says "Meals Included: Breakfast" and the narrative says only "we will enjoy
    our lunch".
  - The whole window (published and latest versions in the 30 days with a meal or clock hit): 139 of 167
    versions with a meal claim and supported clocks cleared (141 before the review fixes), against 0 with Jev
    off on main. The two new kept ones: "(lunch will be included in activities / activities not included
    yet)" (a real ambiguity) and the "Breakfast At leisure" scraped text above. Most of the 28 left
    are real: dinner invented against a `Meals: Breakfast, Lunch` list, an "optional dinner" said to be
    included, "Meals: Breakfast on Day 2 onwards" against "Meals: not included", meals shifted by a day. A few
    would clear with INCLUSIONS, which the export does not carry.
  - The definitive count is a re-run of `aa803-j04` in the container after deploy (expected: M, the tours
    whose only cleared code was the meal waiver, drops to about 0). Then J04 and J05 go OFF in one step.
- **Review round (S246).** An independent review found three ways the first version cleared a meal the
  source does not provide, all fixed with regression tests (real source sentences where available):
  B1 a negation in brackets was split off (`(optional, not included)`, `(own account)`, `(own expense)`);
  B2 INCLUSIONS covered every day too easily ("Meals included as per itinerary" read as full board, a code
  legend, "Welcome dinner", "Chinese lunch", "8 dinners" on 11 days); B3 any "not" / "no" near a meal in
  the OUTPUT dropped it from the claim, so an invented dinner rode along with a sourced breakfast ("dinner
  is served at a restaurant not far from the river").
- **Review round 3 (S246, 23 confirmed false clears).** All fixed with a regression test each, red on the
  previous commit (62 new cases fail there). Cases left as they are, on purpose:
  - `Grab a local "Hunter's Box" lunch` keeps the code (`grab` is a PRE cue, needed for `great places to grab
    a local dinner`). This is a fail-closed miss on one replay tour.
  - A singular `a meal` with no time of day (`A home-cooked meal is served by the host family`) is still a
    generic claim: sourced when the day has any meal. It names one meal, and guessing which would fire on most
    of them.
  - The offline replay script calls `unit_meal_sourced` without `out_days`, so its per-unit lines skip the
    alignment check. The version verdicts (`fires_with_jev_off`) go through `meal_time_claims_supported` and
    include it.
- **What the rule does not judge.** Only which meal, not its details: "Lunch is served at a 5-star rooftop
  restaurant" clears when the day has lunch. Once `a1_claim_supported` is off nothing checks the venue; that
  belongs to the decision to switch the question off, not to this rule.
- **No Q0 case pins the fail-closed direction.** A `fire` case (an unsourced meal with Jev off) is green on
  base, where the code already fires, so `q0_red_on_base.py` cannot accept it, and the `red_on_base: false`
  exemption is only for a negative twin of a new positive case. The unit tests pin it instead (B1/B2/B3,
  the not-provided mentions, times in words, same-day clock times).
- **JSON itineraries.** When `generated["itineraries"]` is a list or dict, `pre_audit_checks` serialises it
  to one line, so no sentence has a day and only INCLUSIONS can cover a meal: fail-closed.
- The rule is code-only, so it runs for tenant rewrites as well. The tenant guard (no tenant id means the
  text is never sent to Jev) still applies to the sentences that do reach Jev.
