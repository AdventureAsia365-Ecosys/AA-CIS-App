# AA-922 — Weekly KPIs, soft-stop rollback and the disagreement queue (WM-30, WM-31)

Session S260 (Claude Code, lane L5). Design: root `docs/audits/2026-10-20-S245-writing-learning-loop/` (README §8,
`issues/README.md` Group 8); app ADR 0010. Stacked on AA-921 (CIS 313); built on AA-920's post-activation check.

## Decisions

- **One weekly job, $0** (`writing_memory_kpi_weekly`): read-only SQL over tables that exist (content_piece,
  content_piece_label, writing_signal, writing_rule, llm_call_log, tenant_tour_versions, generated_content,
  prompt_eval_runs / eval_item_result). No model call; the golden-set part of hard stop 1 stays in R2 (paid).
- **Counts first, rates derived** (`kpi.derive`), so per-tenant numbers add up to the writer's. A writer or tenant with
  no data gets `None` for a rate, never 0; the UI prints "—". T9 is the only writer with a gate ledger and labels, so
  re-flag, repeat errors, light-edit share and minutes to fix are T9-only; T2 / A1 show writes, edits, capture and
  cost.
- **Soft stops compare a release's own writes** since activation with the same owner's 28 days before it. Minimum
  samples (20 writes, 5 labels per side) and the Wilson lower bound for the re-flag stop keep noise from rolling back
  a release. Thresholds are constants in `kpi.py` (a reviewed code change, like `config.py`).
- **"Rollback unless a reason to keep"**: a soft stop acts at the weekly run unless a keep row covers it
  (`shared.writing_memory_keep`, codes or all, at most 30 days). Dev has no real traffic, so no grace window: the admin
  sees the coming stops with Measure now (dry run) and records a Keep before the run if wanted.
- **One out-of-service path**: the post-activation pointer move was extracted into `post_activation.move_pointer`
  (rollback, else retire a tenant release alone, else memory off; audit row; bell + e-mail through `_alert`), reused
  with audit action `writing_memory.release_soft_stop`. Post-activation behaviour is unchanged (its tests pass).
- **Rule expiry**: candidates / approved rules expire as before (`rules.expire_stale`). An *active* rule past
  `expires_at` is re-confirmed (+60 days) when a human pass signal of its owner joined its cluster after it was
  approved (`mining.labels_of`, the miner's own labels; a preference summary: any fresh human edit of that tenant and
  writer); else it expires. The release that holds an expired rule keeps serving the approved text (its items hash is
  fixed) until the next release, which cannot hold it (activation needs approved / active rules).
- **Project stop (P3)**: per writer, the two latest regular platform releases; "improved" = re-flag down, else tenant
  edit rate down, over >= 20 writes. Two `False` in a row flags the writer in the report. Nothing is switched off by
  the flag (the design says "the report flags it").
- **Disagreement queue** (`shared.writing_memory_disagreement`): two sources that exist today — R2 control verdicts vs
  the golden label (calibration disagreements) and T9 labels vs the gates (passed but heavy / reject, held but as_is /
  light). Up to 10 new items a week, unique per source row; resolution is stored and audited, and changes nothing by
  itself (it is the labelled evidence for later calibration).
- **Scheduling**: the api ops sampler enqueues one job per ISO week (idempotency key = the week's Monday), like the
  hourly post-activation part. The report row is unique per scheduled week.

## Changed (vs. the issue text)

- "Soft stop → rollback unless Nghiệp records a reason to keep": the keep can be recorded by any admin with ai.admin
  (the same rule as every release action); the reason is required and audited.
- "Trend written to docs/audits/ once": the trend is rendered by `scripts/writing_memory/wm30_kpi_trend.py` from the
  stored reports; committing its output to the root repo is a live step (needs two stored reports first).
- The edit-pair replay hit rate is read from the R0 results already stored on the rules (`lint.r0.signals`:
  explained edits over usable edits), not recomputed.

## Tradeoffs

- The report table is a platform table that can hold tenant ids (as JSON keys) next to numbers: no text, like the
  run ledger; an erasure leaves those ids (dangling). Keeps and disagreement items have a tenant column, RLS forced and
  are erased with the tenant.
- A platform release's soft stops are measured over every tenant's writes of the writer (it serves all of them).
- After a soft-stop rollback the restored release's window starts at the rollback, not at its first activation: the
  release guard (CIS 287 / 292) resets `activated_at` on every move to active. So it is judged on its own writes only
  and rollbacks do not chain (S260 review finding; integration test with A then B backdated, B rolled back, A not
  stopped on the next run). Its 28-day baseline then covers the bad release's period: lenient for the relative stops
  (never a false fire); the absolute re-flag stop is unaffected. Stamp-based counting (the release stamp each write
  carries) was not needed: with the guard the time window already holds only the serving release's writes, and the
  baseline (before activation) has to be counted by time anyway.
- The weekly job runs the per-release windows sequentially (one release at a time); Dev has a handful of releases.

## Live-evidence layout fix (S260 F3)

- **Finding** (root `docs/audits/2026-10-30-S260-evidence/`, item 7): at 1440 the Metrics tab was 1,413 px wide in
  the 1,204 px admin frame (`main` scrollWidth 1,449), so "Run the weekly job now", the spend tile's edge and the last
  KPI columns sat off-screen; at 390 both Exemplars and Metrics left `main` 400 px wide (10 px sideways scroll).
- **Cause 1 (1440):** the tab root was `display: grid` with no template, so its one implicit `auto` track grew to the
  KPI table's min-content width (tableMinWidth 1100 plus the nowrap headers). The kit DataTable already scrolls inside
  its own wrapper (`data-kit-scroll`); the track just has to stop growing. `minWidth: 0` on the grid box did not help
  (it is the track that grows). Fix: `gridTemplateColumns: "minmax(0, 1fr)"`, the pattern ReleasesTab and the
  Signals tab already use. ExemplarsTab had the same root and fits today only because its table is empty, so it got
  the same fix. The spend tile's auto-fit track is now `minmax(min(100%, 170px), 1fr)`.
- **Cause 2 (390, every tab):** not the tabs. The page's own summary tile "Next automatic run" shows the hint
  "automatic mining is off (<env switch name>)"; the switch name is one unbreakable token wider than a half-width
  tile, so it stuck 10 px out. Fix: the page-local `Stat` tile wraps (`overflowWrap: "anywhere"`) and its minimum is
  `min(150px, 100%)`. Reproduced in headless Chromium with the same flex rules: `main` 400/390 before, 390/390 after.
- **Not changed:** the kit `KpiTile` (core) — its hint has no `overflowWrap` either, but core edits go through the
  kit-sync lane; no tile here passes it a long token.
- **Guard:** `frontend/lib/writingMemoryLayout.test.mjs` (in `npm run test:unit`): every Writing memory tab with a grid
  root sets `minmax(0, 1fr)`, no auto-fit / auto-fill track has a bare px minimum, and `Stat` wraps. It fails on the
  pre-fix source (3 of 4 tests).
- **Should know:** the real 1440 / 390 measurement on `main` still needs the admin session, so it is a live step after
  the Vercel deploy (the orchestrator), not a local test.
