# AA-687 — Jobs observability

Split into 3 PRs: (1) backend, (2) `/admin/jobs` UI, (3) links from domain pages.

## Decisions
- **Worker liveness in Postgres** (`shared.job_worker`, migration 178), Nghiệp's choice over a
  Redis TTL key: same place as `shared.job`, and reaper history survives a Redis restart.
- The worker writes the row at start, about every 15 s (`beat_every_seconds`), right away when a
  reap changed jobs, and at shutdown (`stopped_at`). Rows older than 7 days are pruned at start.
- Every write goes through `Worker._liveness()`, which only logs on error. The queue logic never
  reads this table, so a missing table or a failed write cannot stop jobs.
- "Alive" = not stopped and seen in the last 60 s (`queue.WORKER_ALIVE_SECONDS`, 4× the beat).
- Per-kind **`expected_seconds`** on `@job_kind` (default 600): t2_rewrite 300 (live ≈ 35 s),
  t9_write 600 (≈ 190 s), a3_atomize 1800 (≈ 5 min after AA-688), segment_research 3600. It only
  flags a job on the page, it never stops one.
- `/summary` also returns `max_releases` so the UI can flag a job close to `MAX_RELEASES`.
- `GET /jobs/{id}` adds `links` (tenant tour versions / content pieces with this `job_id`, plus
  `payload.tour_id` / `version_id`). A missing table gives an empty list (fresh test DB).
- `job_succeeded` log now prints `handler_cost_usd`, `llm_cost_usd` and the total. The LLM part
  is read from `llm_call_log` right after completion, so a late fire-and-forget log row can be
  missing from this log line (the page sums on read and is exact).

## Changed
- `api/migrations/178_job_worker.sql` (new).
- `shared/jobs/queue.py`: `worker_register/beat/stopped`, `worker_health`, `llm_calls`,
  `domain_links`.
- `shared/jobs/worker.py`: liveness writes, cost log.
- `shared/jobs/registry.py` + the 4 kinds: `expected_seconds`.
- `api/routers/admin_job_runner.py`: `GET /workers`, `GET /jobs/{id}/llm-calls`, `links`,
  `max_releases`, `expected_seconds`.

## Tradeoffs
- One UPDATE every 15 s per worker (1 worker on Dev) is negligible next to the 5 s claim poll.
- No per-reap history table: the row keeps totals + the last non-empty reap. Enough to answer
  "did the reaper do anything, and to which jobs"; CloudWatch still has every `job_reaped` line.

## Should know

  `job_worker_liveness_write_failed` and the health panel stays empty.
