Full spec, STEP0, and 3 rounds of `/grill-with-docs` (with confirmed decisions) live on the

## Decisions

1. **Segment identity backfill: NO rehash of existing rows.** The grill's Q1 fixed the FORMULA
   for segments minted *going forward* (`sha256(place|verb)`, no `tour_id`/`tenant_id`) — it did
   not require retroactively recomputing the 23 existing `atom_segment.segment_id` values. Doing
   that would need re-deriving each row's canonical `Key` (tokenized place + stemmed/synonym verb)
   from its member atoms' `_key()` output — not reproducible as a plain SQL `UPDATE` (tokenization/
   stemming/synonym-mapping is Python logic). Since `atom_segment.segment_id` is an opaque TEXT PK
   with no format contract downstream ever inspects (only equality-compared), and
   `reconcile_ids()`'s own stated philosophy is "an id, once minted, is held" regardless of what a
   fresh derivation would produce — the existing 23 rows keep their current (old-formula-shaped)
   string values unchanged forever. Only genuinely NEW segments (minted by the redesigned
   incremental matcher from this point on) use the new formula. This is strictly safer than a
   forced rehash and requires no `atom_segment_alias` bridging.
   **Consequence, disclosed**: this makes the grill-round-2 finding ("`angle_gate_request.
   route_segment_ids`'s 1 real approved row will dangle after migration") **moot** — its 16
   snapshotted segment_id strings are never touched by this migration, so they keep resolving
   with zero code change. Flagged explicitly in the Linear report; not silently dropped.
2. **`route`/`hub`: existing 2 rows superseded, not rewritten in place.** Both existing route rows
   (tenant `...0001`/`...0002`, same `tour_id`/day-range) are tenant-scoped artifacts built from
   what were, pre-redesign, two DIFFERENT tenants' independently-computed Segment sets (16 vs 17
   members) — neither is trustworthy as "the" platform-wide row once Segment itself becomes
   genuinely shared. The migration marks both `superseded_at = now()` (AA-532's own supersede-
   never-delete contract — the 1 real `subject.route_id` FK keeps resolving regardless of which of
   the 2 it points to) rather than trying to pick a "winner" or hand-merge their conflicting
   `ordered_segment_ids`. The live-verify step's platform-wide `run_route_detection()` run then
   mints a fresh, correct version-1 row from the real (already-redesigned) Segment/Score data.
3. **`_run_ranking_pipeline()` (v1_tours.py, tenant-rewrite-triggered) removed; Segment/Score/
   Route move to A3 (`services/export/handler.py::_run_a3_atomize_background()`)**, per Q2's
   locked decision. `run_segment_research()` (search-demand purchase decision) is explicitly
   OUTSIDE this issue's 4-layer scope (`segment_matching.py`/`atom_ranking.py`/
   `route_detection.py`/hub only) — its trigger point and per-tenant-market cost profile are left
   completely unchanged, still called from the same tenant-rewrite flow it always was. The one
   REQUIRED (non-optional) touch to `segment_research.py` is dropping its
   `atom_segment WHERE tenant_id = $1` filter — that column no longer exists after this migration,
   so the query would otherwise error outright; this is a structural necessity, not a scope
   decision.
4. **Score's per-market computation runs for all 6 `DFS_LOCATION_MAP` markets at A3**, not the
   researching tenant's own `target_market` list (STEP0 Q3's answer) — independent of whether
   `search_demand` already has data for a given market yet. A market with no bought keywords yet
   degrades via `_demand_ranks()`'s own pre-existing median-fallback (unmeasured Segments take the
   middle rank) — not a new gap this build introduces, an already-built-in behavior.
5. **Hub tie-break for `canonical_places`/naming** (Q3's condition 3, delegated to build time):
   most member segments first, then alphabetically by `route_id` — market-independent, replacing
   the old `min(candidates, key=score)`.
6. **`v1_route_hub.py` (`GET /v1/routes`/`/v1/hubs`, mounted but 0 real frontend traffic —
   confirmed via grep before touching)**: fixed to not reference the dropped `tenant_id`/`score`
   columns (would otherwise 500 on the next real call) — scoped to tours the tenant has actually
   picked (same `tenant_tour_versions` join `segment_matching.py` already uses) and applies the
   same read-time `AVG(total_rank)`-by-market Q3 already approved for Slate, rather than leaving
   this second, lower-traffic reader on a different, ad-hoc fix.

## Should know

- `services/acp_contract/segment_matching.py`'s incremental matcher (Q2) works by building a
  *virtual pool* — the triggering tour's real new atoms, plus one synthetic pseudo-atom per
  EXISTING platform `atom_segment` row (reconstructed from its stored `canonical_place`/
  `canonical_action`, which are exactly the raw text whose derived `Key` equals that segment's own
  canonical Key) — and running the existing, unmodified `_connected()`/Jaccard logic over that
  much smaller pool (new atoms + number of EXISTING SEGMENTS, not existing ATOMS). This is
  sub-quadratic in the full atom catalog because segments deduplicate many atoms into few
  representatives. A new atom touching 0 existing segments mints fresh; touching exactly 1 extends
  it (existing canonical label is kept as-is — not re-optimized even if the new atom's phrasing
  would be more "economical," a disclosed simplification); touching 2+ merges them (lexicographic-
  smallest existing id survives, matching `reconcile_ids()`'s own "content, not by order" tie-break
  in spirit; the others get `atom_segment_alias` rows).
- Full live-verify evidence (before/after EXPLAIN ANALYZE for Q3, 2-tenant-share-1-route proof,
  `subject.route_id` FK check) is in the Linear report, not duplicated here.
