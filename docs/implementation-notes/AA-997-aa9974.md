# AA-997 — strict rule `aa997.4`: the day-evidence guard (S261 lane l4-places-aa9974)

Part 6 of AA-997 (parts 1-5 in `AA-997.md`). Input: the S261 read-only audit of the aa997.3 relocate chain (labelled
sample, `L chain_wrong` lines): of the rows the S254 audit labelled CORRECT on the model's point, six were moved by an
aa997.3 `confirmed` outcome to a different feature with the same name. Four shapes:

| shape | move | why aa997.3 took it |
|---|---|---|
| a temple of the same name in the next overnight town of the itinerary | ~142 km | both points on the route; an exact-name full match overrules an on-route model point (`hint_disagree` "strong") |
| a same-name temple near the base city of a day trip | ~118 km | the model's point (the day-trip town) is off the route, the candidate (base city) on it: the route decides |
| another fort of the same name in the same city | ~4.3 km | inside the 25 km bake-off radius: never questioned |
| another gurudwara of the same name in the same city | ~5.2 km | same |

Labelled chain stats at the time: `confirmed` 28/38 correct, kept `llm_point` 57/92. The orchestrator runs relocate
`recheck` on the 1,197 aa997.1-flagged rows next; this rule must be in place first.

## Decisions

- **The evidence is the use DAY itself.** Neither the route (overnight stops of days d-1..d+1) nor the model's point
  can tell two same-name features of one itinerary apart. What can: the day's OTHER places that a geocoder already
  located (`geo.tour_place` rows of the same `(source_id, day_index)`, trusted points only — same filter as the route
  anchors) and the day's own overnight stop. A temple placed among the day's other sites is backed; a same-name temple
  140 km away near another night is not.
- **New rule `aa997.4` = aa997.3 + `StrictParams.day_guard`** (`geomatch.STRICT_PARAMS[ACCEPT_RULE_V4]` =
  `replace(aa997.3 params, day_guard=True)`). New strict reason `day_disagree`, checked last in `strict_reason`, only
  with the model's point (without it: listed in `unjudged`, never a refusal, never makes a re-judge `kept_unjudged`).
  aa997.2 / aa997.3 are byte-identical: they never read the new route attributes and never produce the new reason.
- **`geomatch.day_disagree` (pure)**, a move ≤ `DAY_MIN_MOVE_KM` (2 km) is never judged:
  1. the day's other located places: refused when the model's point has one within `DAY_SUPPORT_KM` (3 km) and is
     "clearly nearer" to them than the candidate (≤ half the distance and ≥ `DAY_MARGIN_KM` 1.5 km less). When they are
     clearly nearer the CANDIDATE the move is taken outright (the model put the site in the wrong place; the day's
     sites are around the right one). Centroid exemption: a NEAR move (≤ bake-off radius) from a model point that sits
     on the day's overnight town point (`DAY_CENTROID_KM` 0.5 km) is not judged by rule 1 — the model gave the town and
     the site is often out of town (waterfall, cave);
  2. own stop only (no sibling evidence either way): a FAR move (> bake-off radius) from a model point within
     `DAY_OWN_STOP_KM` (15 km) of the day's own overnight stop to a candidate within the bake-off radius of ANOTHER
     stop of the route (a stop farther than that radius from every own stop) is refused — the orchestrator's "model
     point on the anchored day stop, chosen feature near a different route stop". A far candidate near no stop (an
     excursion) is not judged by it.
- **Several same-name candidates**: no separate "nearest to the model point" sort. The guard refuses per candidate, so
  `accept` goes on to the next of the top 3 and takes a same-name feature the day backs (test
  `test_a_same_name_candidate_near_the_model_point_is_taken_after_the_far_one_is_refused`). Without day evidence the
  first-pass order is aa997.3's.
- **Outcome `kept_model` (far refusals only).** When a relocate search under aa997.4 refused a candidate as
  `day_disagree` (a FAR move) and nothing else confirmed, the row keeps the model's point, `hide_unconfirmed` is
  ignored for it, the outcome is not in `HIDE_FLAGGED_OUTCOMES`. Stamp `{outcome: kept_model, refused: day_disagree,
  review_reason, accept_rule, route_km, geocoder}`. Any other unconfirmed result keeps the old `llm_point` / `off_route`
  flags. Reason (`relocate._kept_model_reason`, review fix 2):
  - only a relocate-owned flag (`RELOCATE_REASONS` = none / llm_point / off_route / weak_confirm) on a row that is
    shown or hidden by a hide POLICY becomes `same_name_elsewhere` (not in `HIDE_REASONS`, so neither `hide` nor
    `hide_flagged` takes it); a policy-hidden row is then shown again (`unhidden_by = relocate:kept_model`);
  - any other flag (`unconfirmed_hard_type`, `centroid_fallback`, `non_place:*`, `linear_feature`) is kept: the guard
    judged the geocoder's move, not what that flag is about; a row hidden for it stays hidden, policies select it as
    before;
  - a row hidden by another rule (outlier, an earlier `hide_unconfirmed`: suspect with no policy stamp) keeps a hideable
    flag (its own, or llm_point when it had none), so it is never hidden under a "never hidden" reason that no hide /
    unhide selection matches.
- **Near refusals are weak evidence (review fix 1).** Inside one city the day's sites cluster around the model's point
  whether the model is right (the 4-5 km fort / gurudwara regressions) or wrong (review case A: the model's point in
  the old town, the real palace 5 km out of town). No geometry of the day separates the two. So a NEAR refusal has its
  own reason `day_disagree_near` and relocate treats it like any other unconfirmed row: flagged llm_point / off_route,
  hideable, `hide_unconfirmed` honoured, the stamp records `refused: day_disagree_near`. A wrong near refusal costs the
  status quo before aa997.3 (flagged, hideable), never a shown wrong pin. Only a FAR refusal (another town of the
  itinerary, strong evidence) becomes `kept_model`. A far refusal on another search of the same row wins.
- **Near moves judged more narrowly (review fix 1).** Besides the centroid exemption, rule 1 judges a near move only
  when the model's point is a site of its own among the day's places: not within `DAY_COPIED_KM` (0.3 km) of another
  located place of the day (review case C: the model copied a sibling's point — the usual model slip) and with at
  least `DAY_NEAR_SUPPORT_N` (2) located places of the day within `DAY_SUPPORT_KM` (one site nearby is no evidence in
  a city). Far moves are unchanged. The two audited near regressions (synthetic shapes) still refuse (dm 0.67 / 0.72
  km, 2 / 3 supporting places).
- **Gate before the 1,197-row apply (review fix 1).** A read-only replay (`replay_day_guard.py`, orchestrator, ECS exec
  after deploy) replays `geomatch.day_verdict` on every aa997.3 chain confirmation (model's point = stamp `prev`,
  candidate = current point, routes = `relocate.routes_by_destination(day_places=True)`) and scores it against the
  S254 labels as the S261 audit did: correct confirmations refused (cost, far / near) vs wrong ones refused (the 6
  regressions). GATE PASS when ≤ 2 correct confirmations are refused; FAIL → no apply, retune first.
- **Route reader**: `guards.TourRoute` gains `own` (the use day's own stop, from the anchor rows already read — no
  extra query) and `day` (the day's other places). `store.route_anchors(..., day_places=True)` runs one more query
  (`_DAY_PLACES_SQL`) only when asked; `relocate.routes_by_destination` asks only for aa997.4 (`relocate._day_kw`),
  `pipeline.geocode_pending` only when `GEOCODER_ACCEPT_RULE=aa997.4`. Earlier rules read exactly what they read before.
- **No new RULE_VERSION** (`relocate.RULE_VERSION` stays aa997.2), as for aa997.3: the accept rule is a payload choice
  recorded in each stamp, and bumping the version would refuse the queued chains.

## Tradeoffs

- **A wrong `kept_model` is not hideable.** Only far refusals reach it now. Ambiguous by nature: the model put a site
  at the day's overnight town and the real site is a far namesake near another night with no other place of the day
  located (rule 2) — the model's point is kept and listed (`same_name_elsewhere`), not hidden. Accepted for far moves:
  the day evidence there is another town of the itinerary. Near refusals stay hideable (above).
- **Recorded loss (review case A)**: a near correction from an old-town model point to a site out of town is refused
  (`day_disagree_near`, table case `loss_old_town_point_palace_out_of_town`): the row stays flagged and hideable, as it
  was before aa997.3 — the correction is missed, no wrong pin is shown. Accepting it would also accept the same-city
  regressions. The replay counts how often this happens on the labelled chain (`correct_refused.near`).
- **Near moves from a town point** are exempt (centroid rule) only when the model's point is within 0.5 km of the stop's
  stored point. A model town point 1-2 km off the geocoder's town point is judged as a site; if the day's other sites
  sit in town, an out-of-town waterfall 5-10 km away would then be refused (kept on the town point, listed). The
  regressions the guard exists for were 1-1.6 km from their city points, so a larger exemption would let them through.
- **Day-trip shape needs located siblings.** The 118 km day-trip case is caught only by rule 1 (the day's other sites
  in the day-trip town are located); with none, aa997.4 behaves as aa997.3 there.
- Thresholds (2 / 3 / 1.5 / 0.5 / 15 km) are set from the four audited shapes and the synthetic genuine moves, not
  swept on the labelled sample (that needs the live DB: the orchestrator's re-audit after the apply measures it).
- One more read query per relocate run under aa997.4 (indexed by `tour_place_source_idx` (source_id, day_index)).

## Should know

- **Replay gate script** (not in this repo: it embeds the S254 labelled rows, like the S261 `audit_relocated.py`):
  built from `replay_day_guard.src.py` + `build_replay.py` in the lane scratch folder; run with `tools/ecs/ecsx.sh`
  after the aa997.4 image is deployed (it aborts with exit 2 on an older image). Read-only, $0.
- **The dry run cannot show the guard's effect**: a relocate dry run makes no geocoder call, so the aa997.4 dry run of
  `recheck [llm_point, off_route]` must give the SAME counts as the S261 aa997.3 dry run (1,197 rows, 1,648 requests).
  The effect shows in the apply results (`kept_model` count, samples) and in the re-audit. A `recheck: ["confirmed"]`
  dry run does not preview it either: the only confirmations it selects are aa997.1 ones, which stored no model's
  point (`meta.hint`), so the guard is listed `unjudged` there, never a refusal.
- **The six S261 regressions are not undone by this rule.** They are stamped aa997.2 `confirmed` (located_by geoapify),
  so no relocate selection takes them again; their stamps keep `prev` (the model's point). Restoring them is a separate
  step (admin fix on `/admin/places`, or a small revert tool reading `relocate.prev`).
- The new SQL was executed on a scratch local Postgres 16 with a hand-made minimal schema (columns as in
  `docs/architecture/db-schema-reference.md`): own stop read, siblings of the same day only, suspect / model-located /
  self rows excluded, other days excluded. Not covered by the integration suite (the full migration chain needs
  pgvector, absent locally).
- `GEOCODER_ACCEPT_RULE=aa997.4` for new names (⚠️ underscore env name, task definition) is not part of this lane; do
  it only after the relocate apply + re-audit show the guard refuses no more correct rows than it saves.
