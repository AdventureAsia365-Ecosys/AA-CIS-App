# AA-646 + AA-647 — DFS research scope/trigger + cache-poisoning fix

Branch `fix/aa-646-647-dfs-research-scope-and-cache`. Evidence and root cause: Linear AA-646 / AA-647,
root repo `docs/architecture/ecosystem-review-2026-09.md` §10.1.

## Decisions
- **Removed the tenant trigger outright (AA-646).** `_run_research_only()` is deleted from
  `api/routers/v1_tours.py`; a tenant T2 rewrite no longer calls `run_segment_research()` at all. It
  is not rescoped to "the tour just rewritten": tenant rewrites operate on Master Content tours that
  already went through A3, so their places are platform places. Buying demand for them is an admin
  decision about the platform, not a side effect of one tenant's click.
- **New admin entry point**: `POST /admin/segment-research/preview` (free: scope + stale count +
  upper-bound task estimate) and `POST /admin/segment-research/run` (admin secret, explicit markets,
  explicit scope, mandatory `max_places` cap ≤ 200). Runs in-process in the background, the same
  mechanism as before, until the job runner (AA-650) exists.
- **Scope options**: `places` (explicit canonical places) or `tour_ids` or `country`
  (via `atom_segment_member → tour_atoms → raw_tours.country`), or none (whole platform, still capped).
- **`run_segment_research()` signature** changed from `(tenant_id, target_market, pool)` to
  `(target_market, pool, *, places=None, tour_ids=None, country=None, max_places=None, dry_run=False)`.
  `tenant_id` was unused inside the function; the only production caller was the removed trigger.
- **AA-647: failures are no longer answers.**
  - `DataForSEOClient` gains `DFSCallError(fatal=...)`. `fetch_volumes_bulk` and `fetch_keyword_ideas`
    take `raise_on_error=False` (default keeps the old swallow-and-return behaviour for the other
    callers). Task-level `status_code != 20000` in an HTTP-200 body is now also treated as a failure.
    `_serp_advanced` now raises `DFSCallError` on a task-level error as well; its existing callers
    already wrap it in try/except.
  - Fatal = HTTP 401/402/403, or DFS status codes 401xx/402xx (auth/payment families). Anything else
    is a transient failure of that one call.
  - In research: failed keywords are not written to `search_demand`; a place whose purchases failed
    does not get a `segment_research_log` row (so it stays stale and is retried next run); a fatal error
    trips a run-level circuit breaker — remaining places are skipped before their first LLM call.
  - `run_segment_research()` reports `aborted`, `abort_reason`, `places_failed`.

## Changed vs issue
- Cache-hit logging to `dfs_call_log` (AA-647 item 4) is **not** in this PR: the research path's cache
  lookup is a DB read per keyword and logging each would add thousands of rows per run with no cost
  signal. Left for AA-648, where the two-phase batch job can log one aggregated row per phase.
- The data repair of 25/09 is a one-off ECS-exec script, **not in the repo**: `scripts/` is gitignored
  here, so it lives in the workspace `.tmp-session/aa647_repair.py`. It is dry-run by default and is
  committed only after Nghiệp approves.
  - **Dry-run result (28/09):**
    - cutoff = the last paid bulk call, `2026-09-25 08:51:02 UTC`;
    - would delete 16,311 NULL `search_demand` rows;
    - would delete 5,859 `segment_research_log` rows (1,953 places);
    - would reset the `questions_count` / `contested` caches on 2,870 segments.
  - After the repair: 3,474 rows, of which 2,163 NULL are genuine "no data" answers from before the
    cutoff.
- PR: AA-CIS-App #451.

## Tradeoffs
- Keeping `raise_on_error=False` as the default avoids touching the T2 `process_seo` / `fetch_all`
  path in a P0 fix. The price is two behaviours in one client; AA-648 will move research onto its own
  bulk/Standard-mode client methods anyway.
- The run is still an in-process background task (lost on deploy). Acceptable for P0 because it is
  now admin-triggered, capped and resumable: aborted/failed places stay stale and are picked up by the
  next run.

## Should know
- DFS status codes: 20000 = OK. The fatal classification (401xx/402xx + HTTP 401/402/403) is a
  conservative reading of the DFS error-code families; any unknown code is treated as non-fatal but
  still not cached.
- Tests updated: `test_aa526_a3_atomize_trigger.py` (removed-function test replaced by a
  "rewrite never researches" test), `test_aa469_viec1_t4_t5_split.py` (drops the research-trigger
  expectation).
