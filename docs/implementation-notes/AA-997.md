# AA-997 — Geocode accuracy (S254 audit fix plan, generic steps)

Source: AA-Ecosys `docs/audits/2026-10-28-S254-geocode-audit/README.md` §7–§8. About 75 % of resolved pins are right;
Geoapify-placed rows ~91 %, model-placed rows 53–60 %; ~half of the 1,621 unresolved names are not places. This branch
does the pure-code steps of the fix plan (1, 2, 4, 5, part of 6) and gives the orchestrator a job kind to re-process
the existing model-placed rows (dry run first). No migration.

## Decisions

- **Coordinates come from the geocoder only (step 1).** `locate._resolve` per name: (a) the name searched in the
  model's country, accepted against the tour route (below) or, with no route, against the model's point with the
  S236 bake-off radius; (b) else the TOWN the model names (new answer element) searched as a settlement → the town's
  point, `geo_precision='area'`, `review_reason='centroid_fallback'` (step 5, explicit centroid); (c) else no point,
  reason `unconfirmed_by_geocoder`, **final** (status `unknown` at once). The model's point is only a hint: Geoapify
  `bias`, and the distance reference when no route exists. `model_only` (tests / emergency switch) still stores the
  model's point, flagged `llm_point` (or `unconfirmed_hard_type`).
- **Model null → one geocoder-only search** (audit §7 "geocoder-only fallback") of the name in the item's country,
  only when the name has a route to check the answer against. Otherwise, and when that search finds nothing, the null
  is final (the audit: retrying the same prompt returns null again — stop-after-first-null, step 6).
- **Route-coherence guard (step 2)**: `guards.route_km` = distance from a point to the polyline of the located
  overnight stops of days d-1..d+1 of every tour using the name (`store.route_anchors`; only geoapify / manual /
  mapbox anchors, not suspect, not merged, not lines). ≤ 50 km for a site, ≤ 100 km for a long feature
  (`geomatch.radius_km` words). Segments, not only stops, so a site on a long transfer day passes. With a route the
  route decides (`off_route` rejects a candidate near a wrong hint — the Beijing Bell Tower on a Xi'an tour; a right
  candidate 70 km from a wrong hint passes — Kong Lor). A name used by several tours passes when it is near any one.
- **Day-trip second choice (review fix).** A hard 50 km route radius rejected well-known day trips from a base town
  (Ayutthaya ~75 km from Bangkok, Mutianyu ~70 km from Beijing, Kanchanaburi ~130 km) — and with
  `unconfirmed_by_geocoder` final, such a name would never get a point. `geomatch.reference_km` now returns
  `day_trip` for a candidate off the route radius but within `guards.DAY_TRIP_KM` (150 km) of the route AND within the
  bake-off radius of the model's point; `accept` / `_accept_native` take it only when no candidate passes outright
  (an on-route candidate later in the list still wins). The homonym class (Beijing's Bell Tower for Xi'an, ~900 km)
  stays `off_route`.
- **Non-place pre-filter (step 4)**: `services/places/name_filter.py`, pure, run in `geocode_pending` before any paid
  call. Causes: `route_segment`, `lodging`, `activity` (activities, food, shows, people, transport), `region`,
  `generic_kind`, `descriptive`, `annotation_only`. Such a name is marked `unknown` at once with
  `last_error = 'non_place:<cause>'` — **no new status value** (the audit suggested `non_place`; the reason prefix gives
  the same information without a CHECK change / migration). The cleaned query ("Yali La Pass (4820 m)" → "Yali La
  Pass", "the village of Gogina" → "Gogina") is what the model and the geocoder see.
- **Narrow rules, measured** on the audit's labelled names (fixture `tests/unit/fixtures/aa997_place_names.json`,
  names only, built from `verified.json` + `unresolved_classified.json`): verified-correct names dropped 3/439
  ("Muslim quarter", "the Himalayan ranges", "the largest Buddhist stupa"); real-place unresolved groups 11/706;
  verified not-a-place 25/28; unresolved route legs 195/222; overall ~430 of the ~805 non-places the audit counted.
  Compounds, "kind in <Town>" phrases, dash pairs and Capitalised kind names are deliberately kept (many were
  verified correct). Tests pin these rates.
- **Hong Kong / Macao (step 6)**: a China search filters `countrycode:cn,hk,mo`; a confirming result in HK / MO
  agrees with "China" (`guards.same_country`); a point inside the HK / MO polygon is stored as Hong Kong / Macao
  (`guards.refine_country`), also for the model's hint (whose "China" point fails China's polygon otherwise).
- **Lenient country reader (step 6)**: `guards.lenient_country` ("Tibet, China" → China; "India and Pakistan" stays
  unknown).
- **Re-processing = job kind `place_relocate`** (`services/places/relocate.py`, `services/jobs/place_relocate_job.py`),
  queued by `POST /admin/places/relocate` (ops.write). `dry_run` (default): no call, no write; counts (non-place,
  on/off route, no route, HK/MO-as-CN), by country, samples, and the Geoapify estimate. `apply`: refused (409) unless
  the latest succeeded dry run has the same rule version / located_by / country; ≤ 400 rows a run, re-enqueues itself;
  per row: non-place → `review_reason non_place:<cause>`; geocoder confirms → point rewritten (`located_by geoapify`,
  review cleared, HK/MO country fixed when the key is free); else point kept and flagged `off_route` / `llm_point`
  (an existing reason such as `unconfirmed_hard_type` is kept unless off-route). `hide_unconfirmed=true` also sets
  `geo_status='suspect'` + names `suspect` (hidden from the catalog) — default OFF: owner's call. Every row is stamped
  `geocoder_meta.relocate = {v, outcome, at}`; a rerun skips stamped rows. Nothing is deleted; ids unchanged.
- **Relocate re-reads each row under the destinations lock** (review fix): a row an admin fixed (`manual`), that
  `place_dedupe` merged, or whose `located_by` changed after the run read its selection is `skipped` — no write, no
  stamp — so a job never overwrites an admin fix made during a run. Overnight towns are selected first, so once
  confirmed they are route anchors for the sites of the following runs.
- **Water words (review fix)**: sea / ocean / strait / gulf / Himalayas make a name a `region` only in lower case, as
  the last word or before "of" — "Ocean Park" (Hong Kong) and "Tanah Lot Sea Temple" stay places.
- **Relocate makes no model call** (no new town element for old rows): unconfirmed old rows are flagged, not moved to
  a guessed town.
- **Credits**: the relocate job's daily limit = `GEOAPIFY_DAILY_CREDIT_LIMIT` (2,500) − 1,000 reserve = 1,500/day, so
  `place_geocode` keeps 1,000 credits for new names; on the limit it re-queues itself for the UTC reset.

## Changed

- `geomatch.accept(..., routes=, iso_codes=, settlement=)` and `geomatch.reference_km`; `GeoapifyGeocoder.confirm(...,
  routes=, settlement=)` (lat / lng may be None), `params(..., codes=, bias=)`; a name with neither a hint nor a route
  makes no request (`skipped_no_reference`).
- `locate`: prompt asks `[lat, lng, country, town]` (+ native name last for TW / KR); `Proposal.town`; `Item.routes`;
  `Outcome.final`; reasons `unconfirmed_by_geocoder`; review reasons `llm_point`, `centroid_fallback`, `off_route`.
- `store.mark_name(final=)`, `store.route_anchors`.
- `pipeline.geocode_pending`: pre-filter, routes, result keys `non_place`, `non_place_by`, `no_point_by`,
  `centroid_fallback`, `with_route`.
- Tests updated where the old contract was asserted: an unconfirmed name no longer keeps the model's point
  (`test_aa712_place_pipeline`), the China filter (`test_aa712_geoapify`), model-only review reason, the background
  kinds list (`test_aa737`), the staff route snapshot, and the integration retry test (a null is now final; the 3-try
  loop is tested with a malformed answer).

## Tradeoffs

- **Fewer resolved names for new tours, more correct ones.** A name the geocoder cannot confirm and whose town it
  cannot confirm either now stays unresolved instead of getting a 53–60 %-right model pin. The audit's choice; the
  town fallback keeps most of them on the map as an area.
- **Town fallback costs one more Geoapify request** for unconfirmed names (≤ 2 requests a name, + 1 native for TW /
  KR). Free plan: $0; it only uses daily credits.
- **Route anchors only from trusted points**: a tour whose nights are all model-placed has no route yet, so its names
  use the hint rule (as before) until its towns are confirmed (the relocate job selects overnight towns first, as
  towns geocode well).
- **`hide_unconfirmed` off by default**: hiding ~1,500 flagged rows would remove places from TripPlanner maps; the
  flag alone puts them on the review list.

## Should know

- **No migration.** `review_reason` has no CHECK; `place_name.status` keeps its four values.
- **Order to run** (orchestrator): deploy → `POST /admin/places/relocate {"mode":"dry_run"}` → read the job result
  (`GET /admin/job-runner/jobs/{id}`) → apply per country or all (`{"mode":"apply"}`), watching
  `geo.geocode_call`. Estimate before the dry run: ~3,770 llm rows × ~1 request = ~3,800 credits ≈ 3 days at
  1,500/day, $0 on the Free plan (a paid plan: requests × `GEOCODER_COST_PER_REQUEST_USD`). Model cost $0.
- The relocate job shares the Geoapify advisory lock with `place_geocode` / `place_shape` and is a background kind
  (cap 1). It writes `shared.destinations`; DM-11.4 applies (no deploy while it runs — it is not exempt).
- Not done here (not pure code or needs a migration): `name_norm` keeping a leading "An" (SQL twin
  `geo.name_norm` + re-key, step 6); higher-resolution coastal polygons (data); splitting route legs into their
  endpoints and compounds into parts (changes component ids that TripPlanner pins); context-aware landmark
  disambiguation from the day text (step 3 beyond what the route guard gives); `dup_coords` rework (an audit rule,
  not pipeline code); content fixes (step 7); the re-measure (step 8, after apply).

## Second review fixes (S255 orchestrator)

- `relocate.apply` re-raises `BudgetExceeded` so the job's `stopped_budget` status and alert run; before, the per-row
  handler counted it as a row error and the chain could re-queue.
- `POST /admin/places/relocate` in apply mode reuses a queued or running apply job (`reused: true`) instead of starting
  a second chain.
- A row flagged `linear_feature` keeps that reason when relocate flags it off_route / non_place: `_write_point` un-hides
  it on that reason once a geocoder line lands.
- The job refuses an apply (`refused_no_credit_share`) when `GEOAPIFY_DAILY_CREDIT_LIMIT` leaves no share after the
  place_geocode reserve, instead of re-queueing once a day for ever.
- Should know: `hide_unconfirmed` is a one-time choice per rule version — rows stamped by an apply without hiding are
  skipped by a later apply with hiding; hiding afterwards needs a new `RULE_VERSION`.

## Part 2 — geocode accuracy v2 (S257 lane, rule version `aa997.2`)

Input: the S257 interim audit (AA-Ecosys `docs/audits/2026-10-29-S257-aa997-interim/`): 77.7 % correct on the 600
verified rows (S254: 75.4 %), relocate-touched rows 57.8 → 64.3 %, `confirmed` only 18/29 correct, `llm_point`
84/132, Geoapify-native rows ~90–93 %, model rows ~62 %.

### Decisions

- **Why `confirmed` is only ~62 % right (code reading, no live call):** the relocate path accepts a candidate with
  (1) a ROUTE radius of 50 km (100 km long features) — 2–4× the bake-off's 25 km hint radius and 10× the audit's site
  tolerance (4 km); (2) "near ANY route": one destination key (name, country, locality — locality is empty on ~99 %
  of rows) is shared by every tour that uses the name, so a generic landmark ("city wall", "bell and drum tower",
  "grand canal", "chinatown") passes when the candidate sits near ANY of those tours' routes — one pin cannot be right
  for Xi'an and Beijing tours at once; (3) result types: only country / state / county / postcode are refused and
  `city` only for a feature name, so `suburb` / `district` (Angkor Thom commune, Annapurna rural municipality) and
  a city for a non-feature site word ("Urumqi Airport" → Ürümqi, sim 0.5) pass; (4) `rank.match_type` is recorded,
  never read (a `match_by_city_or_disrict` fallback can pass); (5) name similarity is one-directional — the query's
  tokens found in the candidate — so "Terelj Hotel" passes for "Terelj valley", "Phi Phi Resort" for "Koh Phi Phi
  village" (bake-off rows labelled R); (6) the model's point is ignored once a route exists: a candidate 40 km from an
  on-route hint is taken on a partial name match.
- **Why the geocoder misses (`llm_point` 62 % of outcomes):** (1) no proximity bias without a route (the docstring
  promises the model's point as bias; `route_bias` returns None) — Geoapify then ranks the most prominent homonym in
  the country first and the right one may fall outside `limit=3`; with a route the bias is the middle stop of the
  FIRST route, arbitrary for a name used by many tours; (2) one query only: "X in Y" / "X, Y" context is cut or kept
  in the similarity ("Kumbum Monastery in Qinghai" needs the token "in" in the candidate), no town context for a
  homonym; (3) transliteration joins fail the token match ("Konglor" vs "Kong Lor", "Pingan" vs "Ping'an": difflib
  ratio < 0.85 per token); (4) "Mt" is not a stop word ("Mt Palay-Palay" vs "Mount Palay-Palay").
- **Stricter acceptance = rule `aa997.2`, behind a switch** (review fix — first cut had it always on; see "Review fixes
  round 2"), each a new reject reason in `Verdict.reasons`: `site_type` (was `type`) (site query: suburb / district refused like city; site words include airport /
  station / museum … for this rule only, FEATURE_WORDS unchanged), `match` (fallback match types for a site query),
  `kind` (candidate names a different kind of POI that merely contains the name: lodging, food, shop, office,
  transport, road), `ambiguous_route` (≥ 2 routes: the candidate must not be farther than AMBIGUOUS_ROUTE_KM = 300 km — a homonym —
  from more than one route per 5),
  `hint_disagree` (route reference, hint on the route, candidate beyond the bake-off radius of the hint: only an exact
  name, non-admin, non-street, full-match candidate may overrule the model).
- **Recall changes are behind `strategy = "v2"`** (job payload / `confirm(strategy=)`, default `v1`): bias = the
  model's point when there is no route or the point is on it; extra queries on a miss (context from "X in/near/at Y",
  ", Y", "(Y)", " or " compounds, and for relocate the overnight town of the day); similarity on the bare name, never
  on the context; compact token match (Konglor = Kong Lor); `mt`/`mount`/`in`/`at`/`near` ignored in similarity.
- **Query plan v2 (revised after an offline pass over the S254 verified names):** (1) a name's own "X in / at / near
  <Proper>" disambiguator is searched FIRST ("Gandhi Ashram, Sabarmati"), then bare X; when X alone is generic
  ("Great Wall at Mutianyu") the whole name is searched and judged (as v1), then "<Context> X" ("Mutianyu Great
  Wall") — the first cut sent nothing for such names (`normalise("Great Wall")` = []), a regression vs v1, fixed;
  (2) a parenthetical that names a site is an ALIAS, searched and judged on its own ("Palace of the Winds (Hawa
  Mahal)" → "Hawa Mahal"; "the White Temple (Wat Rong Khun)"; "National Museum (Hor Kham or Royal Palace)" →
  "Hor Kham palace" — the first cut produced the broken text "National Museum (Hor Kham palace"); any other
  parenthetical / ", part" is a context ("Hanok Village (Jeonju)" → "Hanok Village, Jeonju"); (3) a context or alias
  needs a proper word ("north square", "fort", "4820 m" are dropped); (4) the relocate overnight-town context comes
  last. ≤ 3 requests a name (`V2_MAX_QUERIES`).
- **`GEOCODER_STRATEGY` env (default `v1`)** picks the strategy for NEW names in `place_geocode` (⚠️ underscore env
  name — task definition / Terraform, set by hand). The kwarg is sent only when `v2`, so a geocoder object written
  before v2 keeps working. The town fallback stays a plain settlement search. place_relocate takes the strategy from
  its payload. Recommendation: switch it to `v2` after the relocate re-run's re-audit confirms the gain.
- **Mapbox as a second geocoder: NOT implemented (decision, with sources).** The S236 research
  (AA-Ecosys `docs/audits/2026-10-14-S236-design-review/aa712/04-geocoder-research.md` §2, 14/10/2026): Mapbox
  Temporary results may not be stored (Product Terms §2.7.2) — the 289 legacy `mapbox` rows (~89 % right) came from
  TripPlanner's Temporary calls and are themselves due for re-confirmation (design §4(b)); Mapbox Permanent has no
  free tier ($5 / 1,000, "contact sales") and §2.7.3 forbids showing the coordinates on a public map. Adding it would
  be a paid new service and a terms breach for TripPlanner's public map, so the "second geocoder on a miss" is done
  inside Geoapify instead (alias / context / bias variants). The `mapbox` rows can go through the chain with
  `located_by: ["mapbox"]` (dry run first) — recommended only after the `llm` rows, since they are already ~89 % right
  and an unconfirmed one would be flagged (and hidden if the hide policy is on).
- **Hide policy reasons:** default `llm_point`, `off_route`, `unconfirmed_hard_type`, `weak_confirm`. `non_place` is
  opt-in (`reasons: [..., "non_place"]`, a prefix match on `non_place:<cause>`): the pre-filter drops 3/439
  verified-correct names, so hiding those pins is an explicit choice.

## Review fixes round 2 (S257 orchestrator review of the v2 commit)

### Decisions

- **`ambiguous_route` counts a route as missed only beyond a homonym distance** (`geomatch.AMBIGUOUS_ROUTE_KM` =
  300 km), one miss still allowed per 5 routes. The first cut used the 50 km site radius for every route (150 km only
  when the candidate was a day trip from ALL routes), so a candidate near one tour failed while one far from all
  passed: Wat Chaiwatthanaram (Bangkok day trip ~65 km + Ayutthaya overnight 0 km) and Siem Reap on flight legs
  (~126 / ~48 km) were refused although v1 accepts them. The homonyms the rule exists for are ~900 km (Bell Tower
  Xi'an / Beijing) and ~1,000 km (Princess Street Mumbai / Kochi) — both still refused. Trade-off: two same-named
  landmarks < 300 km apart both used by tours are not caught by this rule (the per-candidate route radius still
  applies).
- **Strict acceptance is OFF by default** (`accept(strict=False)`): `GeoapifyGeocoder.confirm(strict=)`,
  `_accept_native(strict=)`; place_geocode switches it on with env `GEOCODER_ACCEPT_RULE=aa997.2` (default `v1`,
  ⚠️ underscore name, task definition), applied to the name search, the model-null search and the town fallback alike;
  place_relocate with payload / endpoint field `accept_rule` (`v1` default | `aa997.2`). Every accepted answer records
  `geocoder_meta.rule` (`v1` / `aa997.2`) and, since this fix, `geocoder_meta.hint` (the model's point it was judged
  against) so a later re-judge has the hint. The relocate stamp records `accept_rule`.
- **A strict refusal stays final but is recorded**: when the strict rule refused a candidate and nothing else
  confirmed, the reason is `unconfirmed_by_geocoder:strict=<reasons>` (or `unknown_to_model:strict=…` on the
  model-null path) → `geo.place_name.last_error`, so dropped names are found with
  `last_error LIKE 'unconfirmed_by_geocoder:strict=%'` and re-queued if the rule is relaxed. Not made retryable: the
  same search returns the same answer, so a retry only spends credits. `Outcome.final` reads the part before `:`;
  pipeline's `no_point_by` key is unchanged.
- **Hint-dependent checks are not judged without a hint** (`strict_reason(..., unjudged=, hint_km=)`): the street-for-
  site and `kind` checks exist only with their 5 km access-point exemption, which needs the model's point. With no
  point they are skipped (listed in `unjudged`), never a refusal — this also fixes the model-null path ("Ba Dinh
  Square" street result) and the re-judge. When only the distance is known (an aa997.1 relocate stamp's `moved_km` =
  distance from the model's point to the confirmed candidate; aa997.1 stamps did not store `prev`), that distance
  judges them.
- **Re-judge outcomes**: `kept` (all checks judged), `kept_unjudged` (passes, but a street / kind check that could
  refuse it was not judged, or no stored answer `no_meta`) — both no call, no flag — and `refused` → re-search. A
  `hint_disagree` that cannot be judged (no hint) is listed but does not make a row `kept_unjudged` (else every native
  row would be).
- **Re-search hint**: the stored `meta.hint`, else the current point (never None any more); the route, when there is
  one, still decides.
- **`geoapify` recheck is dry-run only** (`RECHECK_DRY_RUN_ONLY`): the endpoint refuses it in apply (422), the job

- **Request cap from the log**: the endpoint gives each apply chain a `chain_id`; each run reads the chain's spent

  says it excludes 429 / 5xx retries; relocate sends no native-script query (no native name), so the plan length is the
  per-row count. A run may still pass the cap by ≤ V2_MAX_QUERIES − 1 (checked before each row).
- **Unhide keeps the record**: `geocoder_meta.hidden.unhidden_at` is set instead of deleting the key; a later hide
  moves the previous stamp into `hidden.log` (append-only). Only rows whose `review_reason` still equals
  `hidden.reason` are reverted (`kept_reason_changed` counts the others).
- **Reconfirmation move cap + HK / MO**: a re-search answer farther than `guards.route_radius(name)` (50 / 100 km)
  from the stored point is not written — the row is flagged `weak_confirm` with `move_refused_km`, `move_cap_km` and

## Part 3 — strict rule `aa997.3` (S258 lane: offline P4 tune)

Input: the S257 v2 re-audit, part P4 (AA-Ecosys `.tmp-session/S257/aa997v2/reaudit-out.txt`, summarised in
`docs/audits/2026-10-29-S258-aa997-p4-tune/` of the root repo): `relocate.rejudge` with live routes over the S254
verified rows now located by Geoapify refused **34 / 251 correct** rows (13.5 %, gate ≤ 2 %) and 5 / 30 wrong rows.
Correct refusals by reason: `off_route` 17, `ambiguous_route` 10, `site_type` 4, `name` 3 (samples: Malabar Hill,
Chawri Bazaar, Delhi Airport, Pingyao, Karol Bagh — off_route; Hong Kong, Mount Kailash, Dolma La, Doi Tung —
ambiguous_route; Horombo Hut — site_type; "agricultural flatlands surrounding Yangpyeong" — name).

### Decisions

- **Root cause (code reading): the route is not evidence when it lacks the place's own day stop.** A route is the
  located nights of days d-1..d+1 of a tour day that uses the name (`store.route_anchors`), with the row itself
  excluded. When day d has no located night of its own — the departure / arrival day (Delhi Airport: the route is the
  previous night in Jaipur, ~240 km), a flight or overnight train (Pingyao), trek nights at unlocated huts (Kailash
  kora: the route is Saga / Lhasa, 400–1,000 km), or the place IS that night's stop and is excluded (Hong Kong: the
  route is the nights before and after, hundreds of km away) — the polyline measures travel, not where the place is.
  aa997.2 refuses such rows as `off_route` (re-judge, > 150 km) or `ambiguous_route` (> 300 km from more than 1 in 5
  routes). The homonym class the checks exist for (Bell Tower Xi'an vs Beijing, Princess Street Mumbai vs Kochi) has
  the day's own night in the route.
- **New rule `aa997.3` = aa997.2's checks with knobs (`geomatch.StrictParams`, `STRICT_PARAMS`)**, chosen as:
  `anchored_only=True` (route checks use only routes whose use day has its own located night;
  `guards.TourRoute.anchored`, set by `store.route_anchors` from the `anchor_day = day_index` rows it already reads),
  `rejudge_off_route_km=500` (re-judge off-route distance; the S258 live P4 sweep chose 500 over the first cut's 300),
  `rejudge_v1_checks=False` (the re-judge lists v1's name / type checks as `v1_name` / `v1_type` unjudged — they were
  passed when the answer was accepted; a re-judge fails them only when it cannot rebuild the judged text, e.g. the
  native-script query of a Korean name), `site_admin_named=True` (an admin-type answer named with the query's site word,
  "Horombo Hut", passes `site_type`; this also applies to new names when `GEOCODER_ACCEPT_RULE=aa997.3`). aa997.2 keeps
  its exact behaviour (`StrictParams()` defaults; a plain tuple route counts as anchored).
- **Same switch, new value**: `accept_rule` (`place_relocate` payload / endpoint, pattern `v1|aa997.2|aa997.3`) and
  `GEOCODER_ACCEPT_RULE` (new names). `strict=` now also takes a rule name (`geomatch.strict_rule`: True = aa997.2);
  locate and relocate pass the rule name; `geocoder_meta.rule` records `aa997.3`. Default stays `v1`.
- **`relocate.RULE_VERSION` stays `aa997.2`.** The accept rule is a payload choice recorded in each stamp; bumping the
  version would also refuse every chain queued under aa997.2. (The aa997.1 chain still queued from S256 is refused by
  the deployed aa997.2 code already — see Should know.)
- **Knobs the tune script sweeps but the preset does not use**: `per_tour` (count tours, not (tour, day) uses),
  `ambiguous_km`, `ambiguous_miss_div`. Live P4 sweep (S258, commit `9b1365c0`): correct rows refused 3/251 (1.2 %),
  wrong rows refused 4/30 (aa997.2: 34/251, 5/30); lost catch: Huashan, China.

### Changed

  `evidence_routes`, `_site_named`; `route_cover(per_tour=)`; `strict_reason(params=)`; `accept(strict=True | rule)`.
- `guards.TourRoute` (a tuple subclass: `tour`, `anchored`; pickles); `store.route_anchors` returns them.

  `_rule_kw` sends `strict=<rule>`; dry run / confirmed recheck re-judge with the payload's rule.
- `geocoder.GeoapifyGeocoder.confirm(strict=)` / `_accept_native(strict=)` take the rule name; `locate._rule_kw`
  sends `strict=<rule>` (was `True`) — `test_locate_sends_strict_only_when_switched_on_town_fallback_too` updated.

- **Off-route at 500 km** keeps a correct day-trip / transfer site 150–500 km from an anchored route; a wrong site in
  that band is kept too. The homonyms measured so far are ~900–1,000 km.
- Not judging v1 checks on a re-judge cannot let a new wrong answer in: no new answer is accepted by a re-judge, it
  only decides whether a stored one is re-searched.

## Part 4 — `hide_flagged` and served-pin accuracy (S260 lane L11)

Input: the S260 interim audit (30/10 08:25Z, root `.tmp-session/S260/aa997/audit-out-mid.txt`): labelled accuracy
78.4 % flag-stratified (bar 90 %), projection ~80 % when the chain ends. The largest error cells are rows the chain
left on the model's point (`llm_point` / `off_route`, ~65 % right, ~2,000 rows) and untouched `llm` rows (58 %, the
chain still takes them). The `hide_unconfirmed` switch of the apply would hide such rows, but the running chain does
not use it, and a later apply cannot add it (stamped rows are skipped).

### Decisions

- **A new mode `hide_flagged`, scoped by the relocate stamp, not by review_reason.** The existing `hide` takes every
  row with a hide reason — including the ~600 `unconfirmed_hard_type` rows the chain has not reached yet (a later
  confirmation would then write a point that stays hidden, see below). `hide_flagged` takes only rows a relocate run
  already processed and left on the model's point: `geocoder_meta.relocate.outcome` in `outcomes` (default
  `llm_point`, `off_route`; `weak_confirm` opt-in), optional stamp versions / accept rule, still flagged
  (`review_reason` set, not `linear_feature`), still on the judged point (`located_by` llm / mapbox; weak_confirm:
  geoapify), `geo_status = 'ok'`, not merged. The write is `_FLAG_SQL`'s hide (`suspect` + names `suspect`).
- **Report → confirm, bound to the report's rows** (reworked in the round-2 review fixes below). The report stores
  the sorted `ids` and a digest each; the endpoint passes the latest report as `dry_run_job` (+ its id count as
  `max_rows`) and the job hides only the report's rows still selected with the same digest. Each row is also
  re-checked unchanged (reason, stamp outcome, located_by) in its UPDATE; changed rows are counted
  (`changed_since_report`, `dropped_ids`), not hidden.
- **Audit:** one `acp_shared.audit_log` row per batch of 100 (action `places.relocate.hide_flagged`, resource type
  `places_relocate`, the ids, the selection, the job), written last in the batch's transaction with the hides (the
  table trigger takes a lock). Plus the per-row stamp `hidden = {by: "aa997.3-flagged", reason, outcome, stamp_v, at,
  job, actor}` (an earlier stamp moves into `hidden.log`, as `hide`).
- **Reversal:** `unhide` now takes `by` (the policy stamps to revert; default both `aa997.2-policy` and
  `aa997.3-flagged`) and `destination_ids` (≤ 500; the single-row restore — there is no point-edit screen in
  `/admin/places` today), writes `unhidden_by` next to `unhidden_at` (`restore:<actor>` for an id restore,
  `unhide:<actor>` for a bulk one — round-2 fix), and is audited (`places.relocate.unhide`).
- **A hidden row the geocoder later confirms is shown again.** `store._write_point` keeps `suspect` unless forced, so
  a relocate `confirmed` / `reconfirmed` on a policy-hidden row used to write the geocoder's point and leave the row
  hidden for good (true for the old `hide` too). The relocate paths now read the hide stamp under the lock
  (`_CURRENT_SQL`), and after the write set `geo_status = 'ok'`, names `resolved`, and the stamp back with
  `unhidden_by = relocate:<outcome>` (`_write_point` replaced `geocoder_meta`). Only policy stamps; a row the outlier
  rule or `hide_unconfirmed` hid stays hidden. The apply result counts `unhidden`.

  `created_by`. A hide / unhide that changed rows queues `tour_graph_build` (as before).

### Tradeoffs

- **Coverage for correctness.** Hiding ~2,000 flagged rows takes their pins off TripPlanner maps, CRM tour bodies and
  the Tour Graph (a `v_tour_leg` with a suspect stop is dropped until the graph rebuild the job queues). The pins stay
  on the review list and come back with `unhide`. Rough effect from the S260 cells (estimate, not a measurement): served
  pins ≈ 83 % if the hide ran now; ≈ 87–88 % after the chain ends and its new flags are hidden too; ≈ 90 % only if the
  opt-in non_place pins (~155) are hidden as well. The `rl_confirmed` cell (~75 %) is the next drag.
- `hide_flagged` does not touch untouched `llm` rows: the chain still gets to confirm them first. Run it again after
  the chain ends (rows a person restored meanwhile stay shown, see the review fixes below).
- **A restore lasts until a new judgement** (review fix). The alternative was an `include_restored` switch; not added:
  a bulk undo by mistake leaves its rows shown until the next relocate pass re-judges them, which is the safe side.

### Review fixes (S260 fix pass)

### Review fixes round 2 (S260 second adversarial review)

## Part 5 — readers of hidden and merged destinations (S260 lane L12)

The readers listed in Part 4 "Should know" served a hidden (`geo_status = 'suspect'`) or merged destination's point.
This part changes the CIS one; TripPlanner and Booking ship their own PRs (same issue, notes in each repo).

### Decisions

- **`GET /catalog/v1/destinations/{id}` (CRM, M2M).** A suspect row answers 200 with `lat` / `lng` null and the
  time zone of its country alone (`destination_body`: no zone from an unconfirmed point either). A merged row answers
  404 `not_found` ("This destination was merged into another one."), no `reason` (the contract's `reason` is for
  tours only, "absent otherwise"). Both are v1.2 shapes (`lat` / `lng` already nullable, 404 declared), so no
  contract change and no root PR. The CRM finds the keeper's id in the tour bodies (`v_tour_place` names keepers).
- **Merge state from the main pool.** `catalog.v_destination` keeps a merged row and `catalog.v_destination_redirect`
  is granted to `tripplanner` / `booking` only, not to `aa_app_user` (the tenant-pool role the catalog reads use).
  `reader.merged_into` reads `shared.destinations.duplicate_of` on the main pool (`cis_app`, which holds SELECT), the
  view's own predicate, after the catalog read; only when the destination exists. No main pool configured → not
  merged; a pool / statement error → 503 (an unknown merge state is not served).

### Changed

- `services/catalog_http/reader.py`: `DESTINATION_SQL` selects `geo_status`; `MERGED_INTO_SQL`, `merged_into()`.
- `services/catalog_http/mapping.py`: `HIDDEN_GEO_STATUS`; `destination_body` drops the point of a suspect row.
- `api/routers/catalog_http.py`: the merge check (404), the served log line adds `merged` / `hidden`; docstring.
- No migration, no contract change, OpenAPI unchanged (no route signature changed).

### Tradeoffs

- **A second pool for one lookup vs a grant.** `GRANT SELECT ON catalog.v_destination_redirect TO aa_app_user`
  would keep the read on the views, but a grant is a contract-class migration (ADR 0017: `relacl`) → MIG-4
  (migration-only PR, manual DB Migrate apply, then code) plus the catalog-recipe replay test. The CRM does not call
  this route yet, so the direct read (same predicate) was chosen; switch to the view if the grant is ever made.
- 404 rather than serving the keeper's body under the old id: a body whose `destination_id` differs from the path
  would be cached by the CRM under the wrong key; v1 has no redirect status. A v1.3 could add one (root contract).

### Should know

- Other readers: TripPlanner `/browse/destinations/{id}` (merged → 301, suspect → 200 without location fields,
  `location_hidden: true`); TripPlanner country covers unchanged on purpose (photo + caption, no point); Booking staff
  screens keep both kinds visible with `hidden_from_customers` / `hidden_reason` and the supplier picker drops merged
  places. None needs a CIS view change.
- Tests: unit `tests/unit/test_aa976_catalog_http.py` (suspect → null point + country zone, shown row keeps it, merged
  → 404, unknown id never reads the merge state, lookup failure → 503, the SQL predicate),
  `tests/unit/test_aa976_catalog_http_contract.py` (both answers validate against v1.2); integration
  `tests/integration/test_aa976_catalog_http_reader.py::test_hidden_and_merged_destinations` (real views and
  `shared.destinations` as `aa_app_user` / `cis_app`). Local: 327 unit passed (the AA-899 OpenAPI drift test fails on

## Part 6 — P15: the three open defects of #1178 (S262 lane w11)

The S261 report (root `docs/audits/2026-10-31-S261-aa997-report/README.md`, row P15) left three small defects of
CIS #1178 open; the tech lead asked for them fixed before `hide_flagged` is confirmed on Dev (TL-25).

### Decisions

- **(1) A reversal restores only what its hide changed.** Both hides (`hide`, `hide_flagged`) now stamp
  `hidden.prev_geo_status` ('ok' — every hide takes 'ok' rows only) and `hidden.names` (the `[name_norm,
  country_norm, locality_norm]` keys of the names it set from 'resolved' to 'suspect', written by one statement,
  `_HIDE_POLICY_NAMES_SQL`, a data-modifying CTE). Unhide / restore / the relocate reveal set geo_status back to
  `prev_geo_status` and only the stamped names back to 'resolved' (`_UNHIDE_NAMES_SQL`, JSONB containment). A name
  suspect for another reason (the outlier rule's `apply_suspects`, an earlier `hide_unconfirmed`) stays suspect.
- **Never show a row the outlier rule hides.** The unhide / reveal UPDATE carries the `guards.is_suspect` rule in SQL
  (`_OUTLIER_TPL`: ≥ 2 outlier tours, or ≥ 1 when `located_by = 'llm'`, from `geo.place_outlier`). Such a row is let
  go by the policy (stamp closed: `unhidden_at` / `unhidden_by` + `kept_suspect: 'outlier'`) but stays 'suspect' with
  its names — exactly what `store.apply_suspects` would do on its next run. Counted `kept_outlier` (unhide result,
  unhide audit row `kept_outlier_ids`, apply result).
- **(2) Audit of the relocate paths.** `apply()` collects the rows it shows again (`unhidden`, `kept_outlier`) and the
  rows whose hide stamp takes a new reason (`_flag` now returns `{hidden_reason: {from, to, by}}` when
  `_HIDDEN_REASON_SQL` moved it) and writes `acp_shared.audit_log` rows `places.relocate.reveal` /
  `places.relocate.hidden_reason`, resource `reveal|hidden_reason:<country|*>:<job>`, one per `HIDE_BATCH` (100) rows,
  details `{country, job, batch, rows, destination_ids, changes[]}`. `apply()` takes `actor` / `job_id`; the job passes
  `created_by` / its id, as for hide.
- **(3) The confirm's write re-checks what it read.** `_HIDE_FLAGGED_ROW_SQL` also compares the stamp's `v`,
  `accept_rule`, `at` and the row's country with the values the confirm's SELECT read (it read them under the
  report's selection, so equality = still selected, and `at` = not re-judged since). A mismatch → the row is dropped
  (`dropped_ids`), like a reason change. The report → confirm digest (id | reason | outcome | located_by) is
  unchanged.

### Changed

- `services/places/relocate.py`: `_HIDE_FLAGGED_SQL` reads `stamp_at`; `_HIDE_FLAGGED_ROW_SQL` +4 checks ($6..$9);
  `_HIDE_POLICY_NAMES_SQL` (new), `_UNHIDE_NAMES_SQL` (stamped names only), `_UNHIDE_ROW_SQL` / `_REVEAL_CONFIRMED_SQL`
  (prev geo_status, outlier guard), `_UNHIDE_KEEP_OUTLIER_SQL` / `_REVEAL_KEEP_OUTLIER_SQL` (new);
  `_reveal_if_policy_hidden` returns "shown" | "kept_outlier" | None; `_flag` returns the moved reason; `apply()`
  split into `apply` + `_apply_rows` + `_RunAudit`; constants `AUDIT_REVEAL`, `AUDIT_HIDDEN_REASON`,
  `KEPT_SUSPECT_OUTLIER`.
- `services/jobs/place_relocate_job.py`: passes `actor` / `job_id` to `relocate.apply`.
- `api/routers/admin_places.py`: module docstring only. No route or model change → OpenAPI unchanged. No migration.

### Tradeoffs

- **Audit rows of the relocate paths are written after the rows commit, not in their transaction.** Each relocate
  row commits on its own (minutes of geocoder calls between rows), so a batch of 100 cannot share one transaction
  like hide's. The pending batch is written as it fills and in a `finally` when the run ends or raises; a process
  killed between a row commit and the flush loses that audit row, but the row's own `geocoder_meta.hidden`
  (`unhidden_by 'relocate:<outcome>'`, `reason_was` / `reason_by`) still records the change. Per-row audit rows in the
  row transaction were the other option (atomic, but one audit row per reveal and not "one per batch" like hide).
- **Legacy stamps.** A hide stamp written before this change has no `names`: its reversal keeps the old behaviour
  (every suspect name of the row), still never while the row stays suspect. No policy hide was ever confirmed on Dev
  (S261 report §4.7), so no such stamp is expected live.
- The outlier guard uses the row's current `located_by`: a reveal after a geocoder confirmation (now 'geoapify') needs
  ≥ 2 outlier tours, the same rule `apply_suspects` applies to that row next run.

### Should know

- Deploy before the hide_flagged confirm: a confirm run by the old code would stamp no `names`, and its later unhide
  would set every suspect name of those rows resolved again (defect 1).
- New result keys: unhide `kept_outlier`; apply `kept_outlier`, `hidden_reason_changed`, `audit_rows`. No UI reads
  these results by key.
- Tests: integration `tests/integration/test_aa997_p15_hide_unhide_pg.py` (9 cases; each fails on the code before
  this change — checked by running them against the old `relocate.py`): names restored per stamp (unhide by stamp,
  restore by id, plain hide), outlier row stays hidden + audited, relocate reveal / moved reason audited, one audit
  row per batch, the confirm drops a row whose `v` / `accept_rule` / `at` / country changed between its read and its
  write (a racing change injected through the destinations lock). Unit fakes updated in
  `test_aa997_hide_flagged.py`, `test_aa997_v2_accuracy.py`, `test_aa997_v4_day_guard.py`. Local: 1,496 unit
  (places / relocate / geo filter) passed; 107 integration (places, geo, AA-997, AA-990, AA-847) passed on a fresh
  PostgreSQL 16 cluster.
