# AA-995 — one photo, one URL (readers)

Migration 290 made `shared.v_tour_photos.path` / `shared.v_destination_photos.path` name the canonical
`place_photo` row of the same file (earliest matched, served row with that sha256, by `created_at, id`).
`photo_id` stays the row's own id. This follow-up makes the CIS readers honour that.

## Decisions
- `catalog_http.mapping.tour_body` dedupes photos by the served URL (built from `path`), keeping the first
  occurrence in `position` order and its alt text. Before it keyed on `photo_id`, which differs per copy.
- `photos.sync.fill_destination_covers` now reads the cover from `shared.v_destination_photos` (`position = 1`)
  instead of re-deriving it from `shared.place_photo`. The view is the one place that defines "canonical", so the
  cover cannot drift from what the catalog views serve.

## Changed
- Cover URL shape is unchanged (`<base>/content/photos/<id>?size=large`); only the id can change, to the canonical one.

## Tradeoffs
- Reading the view costs one lateral lookup per matched destination photo (a few thousand rows, index from mig 290);
  the job runs after a photo sync, so this is negligible.

## Should know
- A cover this job set earlier on a duplicate copy's id is rewritten on the next photo sync (same prefix guard as
  before). Covers set by anyone else are still left alone.
- To apply now without waiting for a sync: run the `photo_sync` job (or call `fill_destination_covers`) after deploy.

# AA-995 (S256) — 960 w "medium" photo rendition (mobile LCP)

Why: the TripPlanner destination hero is drawn ~850 CSS px wide on a phone, so it takes the 1600 w file and its
Lighthouse mobile LCP stays at 2.7–3.0 s; a 960 w file brought it to ~2.1 s in the S256 measurement. The photos CDN
serves stored files only, so the rendition has to exist in the bucket. TripPlanner already asks `?size=medium` and adds
the `960w` srcset entry once CIS redirects it (no TripPlanner deploy needed).

## Decisions
- **Migration 301** (own branch, shipped first): `shared.place_photo.s3_key_medium TEXT` NULL. `REQUIRED_CIS_SCHEMA`
  → 301 in the code PR (the route and the sync name the column).
- **`SIZES` gains `"medium": 960`**, so every file the sync downloads gets the 960 w file too. `make_sizes` takes an
  optional `sizes` map; the Booking supply copy passes its own two sizes, so its output is unchanged.
- **Route fallback** (`sync.SIZE_FALLBACK`): `medium` → `medium`, then `large`. Never the original (up to 14 MB, not a
  web image). Other sizes never fall back.
- **Backfill job `photo_medium_backfill`** (background, concurrency 1, 2 attempts, $0 — S3 GET/PUT and Pillow only):
  - source = the stored original (JPEG draft decode, same as the sync), else the 1600 w WebP (HEIC/TIFF originals);
  - bounded: `limit` rows per run (default 1500, max 5000); resumable: a row is done when its own UPDATE commits, and
    the next run picks the rows still missing (keyset over `(sha256, id)`, so a failed row is passed, not looped on);
  - one decode per sha256: the same Drive file synced into several tour folders (Dev: ~2,600 matched rows, ~1,120
    distinct files) is rendered once and written under each row's own key (`<file id>-960.webp`, like the sync);
  - skips rejected rows and rows without a 1600 w file;
  - stops (success, `stopped: photo_sync_running`) while a photo_sync job runs, checked before every batch; the UPDATE
    lands only while the row has the sha256 it was rendered from and no medium key (`changed` otherwise);
  - 10 failures in a row → NonRetryable (e.g. the task role lost `s3:PutObject` on `photos/*`).
- **Enqueue**: `POST /admin/photos/medium-backfill` `{limit?, country?, dry_run?}` (admin secret, `photos.write`); returns
  the queued/running job instead of a second one. `/admin/photos/summary` counts `with_medium` per country and total.

## Changed
- The sync's "unchanged file" check does not require the medium key: an old row is not downloaded from Drive again
  (Drive quota); the backfill renders it from S3.

## Tradeoffs
- **Fallback vs the TripPlanner contract.** The TripPlanner notes asked for a non-redirect (404/422) when a photo has no
  960 w file, so its srcset never lists the 1600 w file as `960w`. The brief for this lane asked for a fallback to the
  next size; it is kept because other readers get a picture instead of a 404, and the only cost on the TripPlanner side
  is a mislabelled srcset entry that downloads the same 1600 w file the browser takes today, and only until the
  backfill has run (every row with files then has a medium key). One-line switch if wanted: `SIZE_FALLBACK["medium"] =
  ("medium",)`.
- Rendering from the original (not the 1600 w WebP) avoids a second lossy encode; costs a larger S3 GET (in-region, no
  transfer charge) and ~1 s per distinct file on the worker.
- Each duplicate row gets its own S3 object (same bytes): ~2,600 PUTs (~$0.013) instead of sharing one key, so a later
  Drive edit of one copy can never change another row's picture.

## Should know
- Ship order: CIS migration-only PR (301) → Infra copy (`db/migrations/cis/301_place_photo_medium.sql`) → DB Migrate
  apply → this code PR → deploy → enqueue the backfill (dry run first) → TripPlanner measure.
- The worker needs `s3:GetObject` + `s3:PutObject` on the photo bucket's `photos/*` (it already reads/writes them for
  photo_sync, which also runs on the worker).
- A rendition PUT racing a photo_sync that re-downloads the SAME file within the same second could leave the older
  picture under the 960 w key; the sync-running check before every batch makes that window tiny. Re-running the sync
  for that file (or clearing its medium key and re-running the backfill) repairs it.
