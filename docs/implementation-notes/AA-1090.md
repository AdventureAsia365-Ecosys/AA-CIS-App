# AA-1090 — TripPlanner R8: a tenant's own domain for its TripPlanner site

Lane l12-tp-domain of S281. Root ADR 0019 b4 ("higher tier = custom domain plus API") and d10 ("custom domains come
later, each on its own trigger"); tech lead S278 decisions D10 / D13 (NEW-D). Four repos: AA-CIS-App (this note: table,
settings, editor, job), AA-TripPlanner-Web (Host routing), AA-CIS-Infra (IAM, edge changes, no apply), root (contract,
retention row, cost note).

## Decisions

- **Where the setting lives.** A tenant's TripPlanner site settings are staff-edited on Tenant 360 › Subscription (the
  lead route, S272); the agency's own portal only shows "Adventure Asia sets it up on your site with you". The own
  domains follow that pattern: a Tenant 360 section, staff add the host the agency asks for. A self-serve page in the
  CRM web is a follow-up (it needs a `/v1/account/...` route and the same service).
- **Owner of the state and the job: CIS.** The site row (`shared.tenant_tripplanner_site`) is CIS's, TripPlanner reads
  the control plane through catalog views only, and the job needs AWS rights on the edge: so the table
  (`shared.tenant_tripplanner_domain`, CIS 427), the job (CIS `shared.job` kind `tripplanner_custom_domain`) and the IAM
  grant (the CIS task role) are CIS's. TripPlanner reads `catalog.v_tenant_tripplanner_v1.custom_domains` (CIS 428).
- **Job kind name.** `tripplanner_custom_domain`, not `tp_custom_domain`: the `shared.job` CHECK (CIS 242) reserves
  `tp_` and `bk_` prefixes for the other owners' kinds.
- **An agency distribution of its own (review fix pass).** The first cut put agency hosts on the public TripPlanner
  distribution, so the edge certificate carried our own wildcard next to every agency host: one agency deleting its
  validation record would stop ACM renewing the certificate that serves `tripplanner.<zone>` too. Agency hosts now
  live on a second distribution (AA-CIS-Infra `aws_cloudfront_distribution.tripplanner_agency`: same origin, behaviours
  and site header, no alias of its own, CloudFront default certificate). The public distribution is Terraform's again
  (no `ignore_changes`). Env `TP_AGENCY_DISTRIBUTION_ID` only; the base certificate is no longer read at all.
- **One edge certificate.** A CloudFront distribution serves one viewer certificate, which must name every alias. So
  each host gets its own ACM certificate first (the agency's validation record proves ownership and is what Tenant 360
  shows), then the job requests the EDGE certificate naming every attached host. ACM reuses a name's validation record within one account, so the edge certificate issues as soon as
  each name is validated. Aliases and certificate change in one `UpdateDistribution`. The edge certificate the
  distribution serves (or one an earlier run requested, kept in the job's progress) is reused when it names exactly the
  wanted set: a sync never piles up certificates (ACM's idempotency token only holds for an hour).
- **Convergent edge sync.** `tp_edge.sync_edge` makes the agency distribution serve exactly the attaching / active
  hosts. Any other alias (a removed host, or a row the tenant erasure cascade deleted) is detached on the next run.
  With no host left the distribution goes back to no alias and the default certificate, i.e. exactly the Terraform
  state.
- **One agency never blocks another (review fix pass).** The shared edge certificate still couples the agencies: a
  re-issue (any add / remove) or ACM's managed renewal needs every agency's validation record. Two guards, both
  settings: (1) a re-issued edge certificate still PENDING_VALIDATION past `cis.tripplanner.custom_domain_edge_pending_hours`
  (default 6) fails and detaches exactly the hosts ACM names as not validated (`validation_record_gone`, staff alert
  `tripplanner_custom_domain_dns`) and is requested again without them; (2) a daily edge check (same job kind, payload
  `{"check": "edge_health"}`, queued by the ops metrics sampler once per UTC day) reads RenewalSummary: a host that
  blocks renewal raises the alert at once and, within `cis.tripplanner.custom_domain_renewal_grace_days` (default 30;
  ACM starts renewing 60 days before expiry) of expiry, is failed and detached so the rest renew. Same kind and
  concurrency 1, so the check never races a domain job on the distribution.
- **Retry restarts the window (review fix pass).** A retry (`RETRY_SQL`) sets `requested_at = now()` and clears
  `validated_at` / `active_at`; `SET_CERT_SQL` also sets `requested_at = now()` when a new host certificate is
  requested. Before, a retry after `validation_timeout` failed again on its first look (the window still counted from
  the original add). A stored certificate ACM can still issue is reused; a dead one (timed out, failed, gone) is
  deleted and replaced.
- **Removals can always be driven to the end (review fix pass).** Removing a row that is already `removing` queues a
  fresh job (key `remove:<updated_at ms>`, audited `requeued`). A removal that cannot finish (edge switched off while
  the host may be served, a CloudFront refusal, a job that ended) keeps the row `removing` with `failure_code` /
  `failure_message`; Tenant 360 shows the reason and a "Retry removal" button. A host the distribution does not serve
  skips the edge entirely (never waits for another agency's certificate). `certificate_arn` is cleared right after the
  host certificate is deleted, and `delete_certificate` treats AccessDenied like ResourceNotFound (IAM cannot read the
  tag of a deleted ARN under the tag-conditioned policy), so a re-run after EdgeBusy never fails on the same ARN.
- **Status machine** (pure `transition()`, tested as a full matrix): pending → validating → attaching → active; any of
  those four → failed (active only through `validation_record_gone`); failed → pending (retry); everything but removing → removing; the job deletes a removing row
  once the alias is detached and the certificate deleted. `active` waits for the distribution to report `Deployed`.
- **No RLS on the table**, like `shared.tenant_tripplanner_site` and the other control-plane tables: only CIS reads it
  (cis_app), TripPlanner through the view. The 244 guard keeps the set of RLS tables in the CIS schemas fixed, so FORCE
  RLS here would break the fixture replay; the rls catalogue rule-a allowlist names it (with the Infra byte copy).
- **Limits are settings** (tech lead S279), CIS 427: `cis.tripplanner.custom_domain_max_per_tenant` (default 1,
  per-tenant override: the tier lever), `cis.tripplanner.custom_domain_edge_max` (default 10: ACM's default names per
  certificate, no base names any more; maker-checker), `cis.tripplanner.custom_domain_validation_timeout_hours` (72,
  ACM's own limit), `cis.tripplanner.custom_domain_poll_seconds` (120), `cis.tripplanner.custom_domain_edge_pending_hours`
  (6), `cis.tripplanner.custom_domain_renewal_grace_days` (30). Seeded `enforced = false` until this code is
  deployed (the settings-lint rule); a later migration marks them enforced.
- **Validation polling within the runner's budget.** The runner fails a job after 600 reschedules; 72 h at 120 s
  would be 2,160. The validation wait is the poll setting but never shorter than the window / 300 (capped at the
  runner's 600 s): 72 h -> 600 s, 432 looks.
- **Reserved hosts.** The editor refuses our zone, `adventure.asia`, `cloudfront.net`, `amazonaws.com`, internal names,
  IP literals and bare domains (a CNAME cannot sit on an apex). The list is platform identity, not a threshold.

## Tradeoffs

- **SAN edge certificate on one agency distribution vs CloudFront SaaS Manager / one distribution per tenant.** One
  extra distribution costs nothing (pay-as-you-go CloudFront has no per-distribution fee) and isolates our public
  host; the SAN certificate caps the hosts at ACM's names-per-certificate quota (10 by default, raisable to 100),
  re-issues the edge certificate on every add / remove and couples agencies to each other's validation records (the
  two guards above bound that). A multi-tenant distribution (SaaS Manager, per-tenant certificates managed by
  CloudFront) scales further but is a new paid feature and a new distribution type; recorded in the root cost note as
  the scale trigger.
- **Aliases and the viewer certificate of the AGENCY distribution only leave Terraform's hands** (`ignore_changes` in
  AA-CIS-Infra): the job owns them. Terraform owns everything else, and the public distribution entirely.
- **Detaching a host vs letting the certificate expire.** Taking one agency's domain off line (with an alert first and
  30 days of grace on renewal) is the price of keeping every other agency on a valid certificate.
- Polling the Tenant 360 section every 15 s while the job works on a host (a cheap API read) instead of a push.

## Should know

- Nothing works on Dev until AA-CIS-Infra is applied (cost approval pending): the API answers 409
  `custom_domains_unavailable` while `TP_AGENCY_DISTRIBUTION_ID` is unset on the task.
- After the Infra apply, redeploy CIS (the deploy copies the latest task definition: lesson S279).
- The agency must keep the validation CNAME: ACM renews the edge certificate with it. If it does not, the alert
  fires at once and the domain is taken off line 30 days (setting) before expiry; the others stay valid.
- Tenant offboarding: remove the hosts on Tenant 360 before an erasure apply; the cascade deletes the rows, the next
  sync detaches an orphan alias, but a host certificate then stays (free, tagged `aa-managed-by`) until cleaned by hand.
- A host certificate is not attached to anything, so ACM does not renew it; it expires about 13 months after issue.
  Nothing reads it after `active` (the edge certificate renews on the same validation record).
- Follow-ups: the agency self-serve page; a migration that marks the six settings enforced; a clean-up job for
  orphan tagged certificates (and expired host certificates).
