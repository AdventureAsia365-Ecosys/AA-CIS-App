# AA-913 — Alert recipients managed from the CIS admin page (AA-CIS-App half)

Spec: S245 r2 `aa913/spec.md` (§3 CIS). The Infra half (topic policy statement for AWS Budgets, Budgets -> SNS
topic, the CIS task-role grant, `ALERTS_TOPIC_ARN` / `ALERT_BOOTSTRAP_EMAIL` on the api + worker task definitions) is
a separate AA-CIS-Infra PR and must be applied before this code is useful (without the env the page shows
"not configured" and every change answers 503).

Two commits on purpose (deploy order S237 D8): the migration-only commit (`251_alert_recipient.sql` + its integration
test) can go out as its own PR first, then the Infra copy + DB Migrate, then the code commit.

## Decisions

- **Table** `shared.alert_recipient` (CIS 251), CIS-owned, no RLS (platform table, no `tenant_id`, like
  `shared.spend_budget`). `cis_app` gets SELECT / INSERT / UPDATE only: removed rows are history, re-adding an address
  inserts a new row (partial unique index: one active row per address). The grants are explicit because the CI replay
  has no CIS 244/245 default privileges.
- **One list for every alert path** (spec D2): subscriptions on the SNS alerts topic + the confirmed rows for the
  CIS `ops_alert_email`. The Terraform bootstrap subscription (`ALERT_BOOTSTRAP_EMAIL`) is never stored, never touched,
  shown locked.
- **Ops e-mail recipients = confirmed rows ∪ `ALERT_EMAIL_TO`, always** (spec D6). This deviates from the Linear text
  ("falls back to `ALERT_EMAIL_TO` when the table is empty"): SNS always delivers to the bootstrap, so the ops path
  must too, or the locked row on the page would be true for one path only. Pending rows get no SES mail (no
  confirmation = no consent).
- **Who may change it**: new capability `alerts.write` (admin role) in `ROLE_PERMS` + the frontend mirror; add /
  remove / resend / test additionally need a verified Cognito session. That second check is in the router
  (`_actor`), not in `staff_authz.denial_reason`, because `POST …/refresh` needs `alerts.write` but not Cognito (it
  only mirrors SNS) and the policy table is keyed by capability, not by route. Reads are `ops.read`.
- **Add detects "already confirmed" without an extra call under the lock**: the topic's subscriptions are listed
  first (outside the advisory lock); inside the lock only `Subscribe` runs (spec §7: one AWS call under the lock).
  An address SNS already has confirmed (e.g. added in the console) becomes a `confirmed` row and is managed from then.
- **Remove**: `GetSubscriptionAttributes` first (to log what was removed and to treat `NotFound` as already gone),
  then `Unsubscribe`. A pending subscription that SNS refuses to delete (`InvalidParameter`) is left to expire after
  3 days; if its link is clicked later, reconcile finds an admin-removed address confirmed in SNS and unsubscribes it
  again (Done-when "a removed recipient receives nothing more"). Any other SNS error: 502, row unchanged.
- **Resend = `Subscribe` again** for the pending address (SNS re-sends the confirmation of a pending subscription;
  the console's "Request confirmation" does the same). The add's own confirmation counts towards the resend limits
  (1 per 10 min, 3 per 24 h per row), so "Resend" is disabled for 10 minutes after an add.
- **Reconcile** is pure (`plan_reconcile`) + one apply step: active rows locked `FOR UPDATE`, status changes audited
  (`alert_recipient.reconciled`), re-unsubscribes after the commit. A subscription missing right after `Subscribe` is
  given a 5-minute grace (SNS listing lag). Throttle + cache of the page summary (locked / unmanaged / when): Redis key
  `alert_recipients:reconcile`, 60 s, with an in-process fallback; `refresh=true` / `POST …/refresh` force it. An SNS
  error never fails the GET: the table is shown with `reconcile_error` (code only).
- **`removed_by` of a reconcile-removed row is `reconcile`** (or `job:ops_alert_email` when the job ran it), even when
  an admin's page view triggered the check: the recipient (or the console) removed it, not the admin. The audit row's
  actor is still the admin who triggered the check.
- **Test e-mail** enqueues `ops_alert_email` with the new `test` template (SES path only; idempotency key per UTC
  minute, 1 per 5 min from the audit log). No `sns:Publish` grant exists, on purpose; SNS delivery is checked with
  `aws cloudwatch set-alarm-state` on a harmless alarm (orchestrator, live verify).
- **The ops job reconciles first** (best effort, one `ListSubscriptionsByTopic`) so an address that unsubscribed via
  an alert's link also stops getting the SES mail. A reconcile or table-read failure is recorded in the job result
  (`reconcile_error` / `recipients_error`) and the mail still goes to whoever can be resolved (lesson: a best-effort
  step must leave a trace in the job result).
- **Region** for the SNS client: `AWS_REGION` (then `AWS_DEFAULT_REGION`, then us-west-1), per the task brief. The
  topic ARN is only read from `ALERTS_TOPIC_ARN`; `TopicConfig.__repr__` hides it; errors carry the AWS error code,
  never the message (which can contain the ARN). Responses carry `has_subscription`, never the ARN.

## Tradeoffs

- **One SES message with every recipient in `To`** (internal staff) instead of one message each: keeps the job
  at-least-once with one idempotent send; recipients see each other's addresses, acceptable for an internal list.
- **Rate limits from `acp_shared.audit_log`** (like `staff_invite`) instead of new columns: no extra schema, and the
  counters are the audit trail itself. Cost: one indexed audit query per write.
- **Pending detection on add by listing first** costs one extra `ListSubscriptionsByTopic` per add, but keeps the
  advisory lock around a single `Subscribe`.
- **No SNS publish from the app**: the test button cannot prove SNS delivery; the alternative (granting
  `sns:Publish` on a topic that carries security alerts) widens the task role for a test button.
- **`cis_app` without DELETE** means a mistaken row can only be removed by a migration; history beats convenience
  for a security-relevant list. If CIS 244 is ever re-applied it re-grants DELETE on all shared tables (its own
  guard requires it); 251's guard only checks its own result.

## Review round 1 (independent review, S245)

Seven findings; six fixed, one (Infra) fixed as defense in depth with a caveat. What changed and why:

- **Fail closed without the bootstrap address** (medium). `topic_config()` now returns None when
  `ALERT_BOOTSTRAP_EMAIL` is empty, so every write is 503 `not_configured` and nothing reconciles. Before, with the env
  missing, an admin could add the bootstrap address (SNS `Subscribe` on an already-confirmed endpoint returns the
  Terraform subscription's ARN), then remove it (unsubscribing the locked fallback), and reconcile would keep
  unsubscribing it each time Terraform recreated it. Extra guards: `remove()` never unsubscribes a subscription whose
  SNS endpoint is the bootstrap (`GetSubscriptionAttributes` `Endpoint`, else the topic listing; `sns = bootstrap_kept`,
  the row still goes), nor a row whose e-mail is the bootstrap; `plan_reconcile` plans no unsubscribe without a
  bootstrap; the reconcile apply loop re-checks each unsubscribe against `cfg.bootstrap_email`. AA-CIS-Infra adds a
  Deny on `sns:Unsubscribe` for the bootstrap subscription ARN (inert if SNS authorizes Unsubscribe against the topic
  ARN only; see the Infra notes).
- **Scheduled reconcile** (two medium findings, same root cause). A removed-while-pending address that confirms later
  was only unsubscribed when someone opened the page or a spend e-mail job ran. Now the api's in-process ops sampler
  (`api/core/ops_metrics_sampler.py`, AA-751, every 300 s) runs `shared.alert_recipients.periodic_reconcile` as a 4th
  part (own timeout, never blocks the metrics, no-op when not configured). Throttled like a page view. Maximum exposure
  after a late confirmation: one tick (about 5 minutes), plus SNS delivery lag. Chosen over a self-re-enqueueing job
  kind: no `shared.job` rows every 5 minutes (the sampler was introduced to remove exactly that, AA-751), nothing to
  bootstrap or keep alive, and it runs where the task role already has the SNS grant. Cost: one
  `ListSubscriptionsByTopic` per api task per 5 minutes (~9k requests/month, under the SNS free tier); with two api
  tasks during a rolling deploy both may run it, harmless (row locks, `NotFound` on a second unsubscribe). Actor /
  `removed_by`: `job:alert_recipients_reconcile` (shown as "Background job"; the column comment's `job:<kind>`
  wording is loose here, no constraint, migration unchanged). The UI copy now says "within 3 days; if the link is
  clicked first, the automatic status check (every 5 minutes) unsubscribes it again". A retry of `Unsubscribe` on the
  stored pending ARN was not added: `remove()` already tries it once, and repeating a refused call every tick only
  adds noise; the confirmed state is what reconcile acts on.
- **Retry-After through the BFF** (medium). The admin proxy (`frontend/lib/proxyResponse.ts`) forwards only
  Content-Type by design, so the browser never saw the header. 429 bodies now carry `retry_after_s`
  (router `_refused`); the page reads it first (`retryAfterSeconds`, header as fallback). The proxy is unchanged
  (shared by every admin route; forwarding one more header was not needed).
- **Redis summary after a change** (low). New `invalidate_cache(redis)` drops the in-process copy and the Redis key;
  `add` / `remove` call it with the request's `app.state.redis`. `clear_cache()` stays (sync, local only) for test
  fixtures.
- **Removed-while-pending shown as "added outside the page"** (low). `plan_reconcile` puts an admin-removed address
  that SNS still lists as pending into a new `leaving` list (page body `leaving`, section "Removed, waiting for AWS to
  drop the unconfirmed subscription"); `unmanaged` keeps only subscriptions really created elsewhere (an address
  removed for another reason and pending again stays unmanaged).

Runbook (root repo, orchestrator): `docs/ops/runbooks/alert-recipients.md` should state the exposure window above and
that the page refuses changes while `ALERT_BOOTSTRAP_EMAIL` is unset.
