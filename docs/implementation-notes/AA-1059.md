# AA-1059 — catalog leftovers: Masters without a Segment, review queue vs tours without a Master, JP/CN/TW routes, segment_gc retention

Source: root `docs/audits/2026-11-08-S273-session/system-picture/system-picture.vi.md` section 1 (funnel table, per-country
table) and section 5 item 10. Lane l9-platform-leftovers of S274. Numbers below are the S273 measures (08/11, Dev); the
diagnostic of this PR re-measures them with the cause per item.

## Step 1 — diagnosis by reading the code

### (a) 9 active Masters with atoms but no Segment

Code path:
- The `segment` stage (`services/recompute/stages.py` `_run_segment` -> `services/acp_contract/segment_matching.py`
  `run_segment_matching`) folds ONE tour's atoms into the platform Segment set. It runs on two paths only:
  1. inline in the `a3_atomize` chain (`services/export/handler.py` `_a3_atomize_chain`, `run_stages(["segment"], ...)`),
     right after atomize;
  2. in a tour-scope `recompute` job (`TOUR_STAGES`), enqueued only by an admin atom delete / undo
     (`api/routers/admin_atoms.py` `patch_atom`).
- The platform pass (`PLATFORM_STAGES` before this PR: landing -> score -> route -> segment_gc) never runs it. Every
  other trigger (lifecycle on/off `services/tour_lifecycle/effects.py`, research, the AA-1056 sweep, the a3 chain's
  debounced job) enqueues a PLATFORM recompute.
- The segment step of the a3 chain is best-effort: an exception is written into the job result as
  `segment_score_route: "failed: <Class>: <message>"` and the job still succeeds; nothing retries it (lessons log
  "Pipeline", S218: 566 tours lost their Segments that way).
- `run_segment_matching` reads atoms from `acp_contract.v_active_tour_atoms` (active Master + live source, mig 271). A
  tour atomized while its Master was paused / inactive reads no atom and writes no member; `restored` later enqueues a
  platform pass, which has no segment stage.
- Within a tour, an atom never forms a Segment when `forms_segment` says so (`classify_exclusion` = `unnamed_place`, or
  `transit` with `activity_type` transit / NULL), or when its `place` / `action` is NULL (pre-migration-129 atoms).

So a Master can sit without a Segment for these reasons, which the diagnostic tells apart per Master
(`segment_verdict`): `no_place_action`, `all_atoms_excluded` (by design), `no_atomize_job`,
`segment_step_failed:<Class>`, `segment_step_not_run`, `atomized_while_inactive`, `segment_ran_no_member`.
The first two need no code: a re-atomize (paid) or nothing. The rest are the same code gap: no path re-runs the
segment stage for a Master that missed it.

### (b) 25 pending S1 review items vs 25 live tours with no Master

Code path: an S1 version that does not auto-publish is enqueued by `api/routers/admin_pipeline.py` `_enqueue_review`
(`pending` only when the tour has no non-trashed Master and a live source; else `dismissed`; a newer version supersedes
the older pending row of the same tour). A staff approve (`api/routers/v1_pipeline.py` `approve_review`) runs the
approve gate (`services/quality/approve_gate.py` `blockers`: no_score, score_below_floor, hard_codes,
grounding_not_run, unsupported_sentences, brand_flagged_unfixed, manual_check), claims the row and exports the Master.
By construction a pending S1 item belongs to a tour with no Master, so the two sets of 25 are expected to be the same
tours; S273 did not join them. The diagnostic joins them and prints per tour the latest version, the pending item, the
gate's blocker CODES and one next step (`s1_next_step`). Every next step is a staff action (approve, edit + re-validate,
regenerate = paid S1 run, or dismiss a stale item): no code change, nothing approved by this lane.

### (c) Route coverage: JP 22/75 ranked, CN 82/120, TW 23/35

Code path: `services/acp_contract/route_detection.py` `run_route_detection` reads the current non-excluded
`atom_ranking` rows, one moment per (tour, Segment) at the Segment's FIRST itinerary day (`MIN(ta.itinerary_day)`,
atoms without a day dropped), splits a tour's moments into consecutive-day runs (`_runs`: a day with no ranked moment
breaks the run), cuts runs into <= 5-day spans (`_spans`) and keeps a span of >= 2 days and >= 2 distinct places
(`LEAST_DAYS`, `LEAST_PLACES`). There is no country rule anywhere in the route builder, the ranking or the hub step:
the gap is the shape of the data, not a country branch. The stage records totals only (routes_written / superseded /
unchanged / tours_ranked), no per-tour reason.

Candidate causes for a low country rate, all from the rules above: many transfer days (rail / flight days are transit
by rule and break the run), city-based itineraries where one Segment recurs on several days (counted on its first day
only, the later days look empty), atoms without `itinerary_day`. The diagnostic re-derives the reason per tour with the
new pure `route_gap_reason` (`no_ranked_moment`, `no_day`, `one_day`, `no_consecutive_days`, `one_place`,
`derivable`) plus `all_excluded` / `stale_ranking`, and a what-if: would a Route form if a Segment counted on every day it
occurs (`whatif_all_days`). Changing the first-day rule would re-version routes across the whole catalogue (every
tenant Subject on a route keeps its route_id, but the Slate changes), so it is a decision for after the numbers, not a
change in this PR.

### (d) segment_gc retention

Code: `services/acp_contract/segment_gc.py`. An orphan (no member on an atom of an active Master, no current ranking,
not on a current route) is DELETED only when nothing refers to it: no member on a live atom (`tour_atoms` not deleted,
not an empty-day marker, ANY Master state), no `atom_ranking` row, no alias row either side, no Subject, no brand-fit
cache row, not on a current route nor a Subject's route, not in an angle request route list. Its dead member rows go
first. `SEGMENT_GC_MODE` report | apply | off; apply holds above `SEGMENT_GC_MAX` (10,000). S273: mode apply, 1,067
orphans, 0 deletable, 1,067 kept. The rule never drops live data: a Segment with a live atom (also of a paused or
trashed Master, kept so a restore finds its Segments) or any reference is kept. What keeps the 1,067 is printed by
class (`kept_by`) and, for the live-member class, by the Master / source state of the member tours. Atoms of a trashed
or superseded tour are never soft-deleted, so their Segments are kept for as long as those atoms exist: that is the
retention rule as implemented (the atoms' own retention decides it). No change.

## Decisions

1. **Diagnostic script, read only, run by the orchestrator** (`scripts/aa1059/catalog_leftovers_diag.py`, force-added:
   `scripts/` is git-ignored). Read-only session, ssl=require, container `DATABASE_URL` (cis_app). Prints counts, ids
   (tour, review, job), fixed codes and ages; never names, places, actions, texts or error messages (exception class
   only). It imports app code (segment rules, route rules, GC SQL, approve gate) instead of copying it, so it needs the
   image of this PR; a missing import prints `ERR import <section>` and skips only that part.
2. **Code gap fixed: `segment_catchup`, the first stage of every platform pass**
   (`services/recompute/segment_catchup.py`). It picks the active Masters none of whose live atoms is in a Segment and
   that have at least one atom `forms_segment` accepts, and runs `run_segment_matching` for at most
   `SEGMENT_CATCHUP_MAX` (env, default 10, 0 = off) of them, each under the tour's A3 lock taken without waiting (a
   tour an `a3_atomize` job holds is skipped as `busy`; that job runs its own segment step). Failures are counted per
   exception class and never fail the pass. The touched Segments are handed to `landing` (ctx.data
   `catchup_segment_ids`), so they are landed, scored and routed in the same pass. Result key `segment_catchup` on the
   platform job result.
3. **Where:** a platform stage, not a new job kind or an admin button. Every trigger already ends in a platform pass
   (atomize, lifecycle, research, the AA-1056 sweep), so the gap closes on its own within one pass, and the 9 Masters
   need no hand step beyond one platform recompute.
4. **A helper to run the catch-up now** (`scripts/aa1059/enqueue_catchup_pass.py`, orchestrator only, one
   `shared.job` row through `enqueue_recompute`): there is no admin action that enqueues a platform recompute, and the
   next natural trigger can be hours away. Segment scope `[]`, never None (None re-lands every Segment, a backfill).
5. **`route_gap_reason` lives in `route_detection.py`** (pure, next to the rules it explains) rather than in the
   script, so a later Data coverage row can use the same function.

## Tradeoffs

- The catch-up spends what an atomize's segment step spends (Jev same-place pairs through `decide`, mostly cached;
  Cohere embeddings for the new Segments' landing). It only runs when a Master is missing its Segments; a tour that
  fails every pass is retried every pass, but at most 10 per pass and in a random sample when there are more, so one
  stuck tour cannot starve the others. The alternative (an admin "re-segment" button) would leave the gap to a person.
- Only Masters with ZERO Segments are caught up, not Masters with some atoms missing (a partial miss is what the a3
  path's own run already covers on the next atomize, and finding it would need the segment rules per atom in SQL).
- Not changed: the route first-day rule (catalogue-wide re-versioning, needs the numbers first), the GC rule (never drops
  live data), the review queue (staff decisions).
