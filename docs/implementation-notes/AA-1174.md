# AA-1174 — Privacy obligations on Platform › Compliance readiness

Session S288 (lane contract `.tmp-session/S288/lane-contract.md`, migration number 471). Plan and critique:
`.tmp-session/S288/plans/AA-1174.md` (private). Tech lead decision S287 close (Q14 changed): the Vietnam personal data
law and GDPR now, and every other law the applicability check marks "applies"; laws are a met / not met checklist with a
counsel flag, never a percentage.

## Decisions

- **Two CIS PRs (MIG-4).** `feat/aa1174-obligations-schema`: CIS 471 (`compliance.framework`, `compliance.applicability`,
  law columns on `requirement`, framework FKs instead of the 466 CHECKs, ten settings), `compliance_settings.py` naming
  the keys, `compiled_defaults.json`, the 466 test adjusted (7 tables; the unknown framework is now a FK violation).
  `feat/aa1174-obligations-page` (stacked on it; rebase on `main` after the migration merges): service, router, loader
  v2, frontend, readiness 471.
- **EU AI Act.** Seeded as kind `law` with `scored = true`: its card and trend stay exactly as today, and it is also
  listed on the Obligations tab. Dropping the card is a separate tech-lead call.
- **Scored frameworks come from the table.** `compliance.py` reads `compliance.framework` (scored, active, sort order)
  and hands the list to `compliance_score.evaluate(scored=...)`; snapshots and reference scores follow it; names and
  kinds reach the page as `framework_info`, so the Controls tab and its filter show law names. `FRAMEWORKS` stays only
  as the default and the frontend fallback.
- **Obligation state** (`compliance_score.obligation_state`): met = requirement met; not_checked = unmapped or every
  mapped active control has no automatic check; else not_met with `partly` for partial.
- **Legal pages graded on their own cycle.** The collector publishes `overdue` (pages past last_reviewed +
  review_every_days) per legal check, graded "max" against `cis.compliance.legal_docs_overdue_max` (default 0); a flat
  age limit would let a 30-day DPA annex read met 100 days late. The evidence also carries `doc_status` (all `draft`
  today), shown in the evidence cell so a draft agreement is not read as a signed one.
- **Retention evidence is two checks.** `retention_runs_recent` (the oldest of the newest succeeded runs per kind,
  any mode: the schedule runs) and `retention_live_enabled` (the oldest of the newest LIVE runs per kind, fact
  `live_last_date`, graded `age_days` against `cis.compliance.retention_live_max_age_days`, default 7; a kind with no
  live run at all makes the row `fail`). Both are required by the retention control.
- **Live retention graded on recency, not existence (review round 2).** `decide_mode` puts scheduled runs back to DRY
  RUN for good after any window change, and a held run deletes nothing either, so "has ever had a live run" read met
  while nothing was deleted. The first design (`never_live` count vs `cis.compliance.retention_never_live_max`) is
  replaced in CIS 471 itself (migration PR still open, not applied): key renamed to
  `cis.compliance.retention_live_max_age_days` (int days 1-90, default 7, maker_checker). The check id stays
  `retention_live_enabled` (stable for AA-1173 and the register's control mapping). A unit case pins the scenario:
  a live run 40 days old plus recent DRY RUN runs only fails.
- **Live sources only on Refresh** (lane contract rule 3). `cis_db` and `crm_ops` are collected only by
  `POST /refresh` (compliance.write), at most every 10 minutes per source (`LIVE_MIN_INTERVAL_S`, technical constant;
  append-only table). A GET never collects them, and under a read-only view-as session (`request.state.staff_view_as`,
  set by the AA-1157 staff auth) a GET skips the file ingest and the snapshot upsert too.
- **CRM evidence poisoning.** A 401 / 403 / no Cognito session from the CRM writes no evidence row (the newest real row
  keeps counting); a 404 / timeout / bad body is an `error` row (the evidence really is unavailable).
- **Heartbeat only for scheduled collectors.** `ScoreSettings.heartbeat_sources` = `{"root_daily"}`: an on-demand
  source never turns "silent"; its rows go stale after their validity window (72 h by default).
- **Loader format 2.** Law frameworks, their obligations and the matrix in the private register; standard / seeded
  frameworks and their requirements are never written; a law no longer listed is set inactive and its obligations not
  applicable (never deleted); applicability is a full replace; every source link must be https on an official host
  (`OFFICIAL_HOSTS`, technical constant); "compliant / complies / in compliance" and normative wording are refused;
  more than 5 active controls deactivated in one run needs `--allow-deactivate`.
- **Vietnam sources: gazette or legal database only (review round 2).** `OFFICIAL_HOSTS` no longer accepts every
  `gov.vn` / `chinhphu.vn` host: for Vietnam only `vbpl.vn`, `vbpl.moj.gov.vn`, `congbao.chinhphu.vn`,
  `congbaocdn.chinhphu.vn`, `vanban.chinhphu.vn`, `datafiles.chinhphu.vn` and `quochoi.vn` pass. The first private
  register linked a State Bank introduction document (Law 91) and a provincial justice department introduction (Law
  60), which the old allowlist let through and the page labelled "Official text". The private register now links the
  official gazette record of Law 91, Decree 356, Law 60 and Law 116; the Law 91 article refs were re-read on the gazette
  text. The page label is "Official source" (the allowlist also holds regulators' guidance pages, e.g. the CPPA
  threshold page, which are official but not the law's text).
- **Matrix conventions (review round 2, private register data).** The Vietnam law applies to a Vietnamese
  organisation for all personal data it processes (Law 91 Art. 1(2)(a)), so every traveller market row carries a
  `vn-pdpl:2025` verdict next to that market's own laws (AA is controller there). A market-neutral rule (PCI DSS:
  follows card payments, not the traveller's market) is filed under the market where AA is established (`VN`) with a
  note saying so; the schema keeps a two-letter market, no "all markets" code.
- **Campaign window is a CIS setting** (`cis.compliance.campaign_consent_window_days`), sent to the CRM as `days`
  (capped at 365 there): no CRM migration.
- **Every obligation has a link.** `doc_url` (our own GitHub docs page) on each law requirement, shown when no evidence
  row links. The loader refuses (format 2) an applicable law obligation with no `doc_url` and no mapping to an active
  control with a required automatic check, since the page would show it with nothing to open (review: 21 of 53 items of
  the first private register had neither; they now link the incident-response breach branch, the readiness packet's
  privacy and cookie section, the register's decisions log or records of processing, the DPA security annex, or the
  CRM campaigns section of the Partner CONTEXT.md).
- **Refresh always collects.** `sync(collect_live=True)` collects `cis_db` / `crm_ops` on every call, also when the
  published-file read is served from the process cache (a GET within 30 s fills it, so Refresh right after opening the
  page used to return the cached state with no `live` key). The cached state never carries `live`;
  `LIVE_MIN_INTERVAL_S` still bounds the write rate, one live collection at a time per process.
- **Live retention baseline = the job runner's.** `retention_live_enabled` (and the live count in detail) leaves out
  `trigger = manual_override` runs, the same filter as `services/jobs/retention_job.py` `_LAST_LIVE_SQL`: a Dev proof run
  with an explicit cutoff never switches the scheduled runs to live, so it is not evidence that retention deletes.
  A unit test pins the two SQL texts together.

## Changed

- Plan: `legal_doc_max_age_days` (flat age) → `legal_docs_overdue_max` (per-page cycle), per the critique.
- Plan: one retention check → two (`retention_runs_recent`, `retention_live_enabled`), so an all-DRY-RUN history does
  not read met.
- Review round 2: Vietnamese source links must be the gazette or a legal database (allowlist narrowed); the link
  label "Official text" → "Official source".
- Review round 2: `retention_live_enabled` fact `never_live` (count, "max") → `live_last_date` (date, "age_days"); setting
  `retention_never_live_max` → `retention_live_max_age_days`, in CIS 471 (unapplied) rather than a new migration.
- Plan: CRM-side window setting → CIS setting passed as a query parameter (no crm-086).
- Plan: CIS 470 → 471 (lane contract).
- Plan: "collect when someone opens the page" → collect only on Refresh (lane contract rule 3).
- Follow-up from the same page: the Refresh evidence button now reports its result (a toast and a status line under the
  header: rows read and new from the published file, then per live source rows / new, "collected a few minutes ago",
  "not collected (reason)" or an error).

## Tradeoffs

- On-demand collection keeps phase 2 (AA-1173: a daily worker job and the Object Lock store) separate; until then the
  `cis_db` / `crm_ops` evidence is only as fresh as the last Refresh. The check ids and source names stay stable for
  AA-1173.
- The CRM suppression history is approximate (a lifted suppression row is deleted); the consent half is exact.
- The matrix and the law checklists live in the private register (public repos); only the structure is in the
  migration. DDL comments carry nothing sensitive (the nightly schema dump publishes them).
