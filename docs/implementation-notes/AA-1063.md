# AA-1063 — Claim ground truth in the Writing Lab (review view, proposals, label set browser, re-label)

Lane l5 of S275 (Claude Code, orchestrated). Out of scope here: the Jev pre-filter (a separate lane).

## Decisions

- **Two new tables in one expand migration (CIS 394)** instead of new columns on `shared.eval_claim_label`:
  - `shared.eval_claim_proposal`: one row per (queue item, agent run); FK to the queue item (`ON DELETE CASCADE`), so
    the tenant erasure reaches it through the FK walk (`services/erasure/plan.py`) and no tenant column is needed.
  - `shared.eval_claim_relabel`: one row per correction of a final label; FK to an anchor row of the claim in
    `shared.eval_claim_label` (`ON DELETE CASCADE`). A chain per claim: `supersedes` names the correction it replaces,
    unique `(set_id, set_version, claim_hash, supersedes) NULLS NOT DISTINCT`, so a stale second click is refused (409).
    `supersedes` is a plain uuid (no self FK): a self-referencing FK is a cycle for the erasure planner.
  - Why not change `eval_claim_label`: its judgement key allows one tech-lead row per claim and version, and it has no
    UPDATE grant. Widening the key is a contract change (MIG-4: migration-only PR first) and would make every reader
    (`existing_judgements`, `pull_resolutions`, the importer's idempotency) handle several tech-lead rows. A side table
    leaves those paths as they are.
- **Append only in the DB**: an expand file cannot REVOKE the UPDATE that cis_owner's default privileges (CIS 245) give
  cis_app, so a `BEFORE UPDATE` trigger (`shared.eval_claim_review_append_only`, 42501) refuses UPDATE on both tables.
- **Effective rows** (`services/ground_truth/review.py effective_rows`): the label rows plus one synthetic tech-lead row
  per correction, tech-lead rows of a claim in time order, so `panel.final_labels` (`lead[-1]`) and
  `agreement_report` pick the newest decision without changing `panel.py`. The report's counts stay over the stored
  label rows (plus a `relabels` count); labels by class, contradictions, agreement and the manifest read the effective
  rows (a correction changes the manifest digest). The finals route reads the effective rows too.
- **One answer = resolve + label in one transaction** (`review.answer_item`): the label lands in
  `shared.eval_claim_label` right away (the Done-when), instead of waiting for `pull-resolutions`. Majority panels
  resolve `judge_right` / `human_right` / `unclear` exactly as before and the tech-lead row is the one
  `pull_resolutions` would build; a split or unsure-majority panel gets a tech-lead row with the answered label and is
  resolved `unclear` (the S275 `build_special` / `close_special` path, now in the API). `pull_resolutions` skips claims
  that already have a tech-lead row, so running it later changes nothing.
- **Class of the tech-lead row**: the most common class among the lenses that gave the answered label, else the class
  of the queue item's anchor panel row (what `pull_resolutions` uses).
- **Context and source come from the golden item, not the proposal**: the claim rows store the span only. The view
  rebuilds the field text, the context (300 chars each side, as the export), the evidence lines (`claims.align`) and
  the full source from `shared.eval_golden_item` by `sample_id`, choosing the item whose output's content sha (gate
  ledger and flags left out, as the panel saw it) equals the claim's `content_sha256`. Checked locally: all 1,602
  CL-1 export lines match fixture 1.3.0 this way. A claim with no golden item (a live T9 piece or T2 version) shows
  "source not stored" in the view.
