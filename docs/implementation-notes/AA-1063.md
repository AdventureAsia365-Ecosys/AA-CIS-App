# AA-1063 — Claim ground truth in the Writing Lab (review view, proposals, label set browser, re-label)

Lane l5 of S275 (Claude Code, orchestrated). Out of scope here: the Jev pre-filter (a separate lane).

## Decisions

- **Two new tables in one expand migration (CIS 394)** instead of new columns on `shared.eval_claim_label`:
  - `shared.eval_claim_proposal`: one row per (queue item, agent run); FK to the queue item (`ON DELETE CASCADE`), so
    the tenant erasure reaches it through the FK walk (`services/erasure/plan.py`) and no tenant column is needed.
  - `shared.eval_claim_relabel`: one row per correction of a final label; FK to an anchor row of the claim in
    `shared.eval_claim_label` (`ON DELETE CASCADE`). A chain per claim: `supersedes` names the correction it replaces,
    unique `(set_id, set_version, claim_hash, supersedes) NULLS NOT DISTINCT`, so a stale second click is refused (409).
    `supersedes` is a plain uuid (no self FK): a self-referencing FK is a cycle for the erasure planner.
  - Why not change `eval_claim_label`: its judgement key allows one tech-lead row per claim and version, and it has no
    UPDATE grant. Widening the key is a contract change (MIG-4: migration-only PR first) and would make every reader
    (`existing_judgements`, `pull_resolutions`, the importer's idempotency) handle several tech-lead rows. A side table
    leaves those paths as they are.
- **Append only in the DB**: an expand file cannot REVOKE the UPDATE that cis_owner's default privileges (CIS 245) give
  cis_app, so a `BEFORE UPDATE` trigger (`shared.eval_claim_review_append_only`, 42501) refuses UPDATE on both tables.
- **Effective rows** (`services/ground_truth/review.py effective_rows`): the label rows plus one synthetic tech-lead row
  per correction, tech-lead rows of a claim in time order, so `panel.final_labels` (`lead[-1]`) and
  `agreement_report` pick the newest decision without changing `panel.py`. The report's counts stay over the stored
  label rows (plus a `relabels` count); labels by class, contradictions, agreement and the manifest read the effective
  rows (a correction changes the manifest digest). The finals route reads the effective rows too.
- **One answer = resolve + label in one transaction** (`review.answer_item`): the label lands in
  `shared.eval_claim_label` right away (the Done-when), instead of waiting for `pull-resolutions`. Majority panels
  resolve `judge_right` / `human_right` / `unclear` exactly as before and the tech-lead row is the one
  `pull_resolutions` would build; a split or unsure-majority panel gets a tech-lead row with the answered label and is
  resolved `unclear` (the S275 `build_special` / `close_special` path, now in the API). `pull_resolutions` skips claims
  that already have a tech-lead row, so running it later changes nothing.
- **Class of the tech-lead row**: the most common class among the lenses that gave the answered label, else the class
  of the queue item's anchor panel row (what `pull_resolutions` uses).
- **Context and source come from the golden item, not the proposal**: the claim rows store the span only. The view
  rebuilds the field text, the context (300 chars each side, as the export), the evidence lines (`claims.align`) and
  the full source from `shared.eval_golden_item` by `sample_id`, choosing the item whose output's content sha (gate
  ledger and flags left out, as the panel saw it) equals the claim's `content_sha256`. Checked locally: all 1,602
  CL-1 export lines match fixture 1.3.0 this way. A claim with no golden item (a live T9 piece or T2 version) shows
  "source not stored" in the view.
- **Corrections ordered by their chain, not only by time**: two corrections in one transaction share `now()`, so
  `effective_rows` and `chain_head` order by (time, chain depth) and the relabel table's `created_at` defaults to
  `clock_timestamp()`. Found by the integration test (the first version picked the older correction).
- **One decision per claim, everywhere (review fix pass)**: a correction is allowed on an agreed panel claim whose
  audit-drawn queue item is still open, so the queue and the browser can meet on one claim. The decision is the
  newest effective tech-lead row (`review.newest_lead`: a stored row or a correction, the row `final_labels` reads):
  - `answer_item` refuses an answer that differs from it (409 `relabelled` after a correction, `labelled` after a
    stored row) and resolves an agreeing answer without writing a new row (a new stored row would be newer than the
    correction and silently become the final label);
  - `store.pull_resolutions` skips a claim with a correction (`store.relabelled_claims`, empty before CIS 394);
  - the browser's `decided_by` / `decided_at` / `why`, the queue card's `decision` (now with `relabel`) and a new
    correction's `previous_source` all come from that row; `relabelled` means the final label is a correction;
    `head_relabel_id` stays the chain head (the next correction must supersede it); history is in time order;
  - `relabel` and `answer_item` lock the claim's queue items first (`lock_claim_items`, FOR UPDATE), so the two
    paths run one after the other and the second reads the first.
  Chosen over refusing a correction while an item is open: the browser stays usable at any time, and the queue card
  shows the existing decision with a note before the tech lead answers.
- **Queue paging under answers**: the open list shrinks on the server as cards are answered, so Next steps back by
  the number answered on the page (`reviewPageOffset`) and refetches (the same offset can come back); the cards of
  the current page stay put until then. Progress and the accept count read a separate facets query, refreshed after
  each answer.
- **Writes are ai.admin (admin and ai_ops)**, like every other claim-label write and the queue resolve; every write
  needs a signed-in admin (`x-admin-user-id`, 403 `no_actor` without). Reads with text are Lab text reads
  (`LAB_TEXT_LOGGED`: ai_ops reads are logged first); the set counts carry no text (`_LAB_READ`).
- **Bulk accept takes item ids** (at most 500 per call). The page collects the ids of every open item with a proposal
  under its filters (`GET .../review?context=false`, 100 a page) and sends them in chunks; the count on the button
  comes from the facets. The second click is an in-page bar (no `window.confirm`); it closes by itself after 8 s.
- **Proposal import keys**: a line names its queue item by `item_id`, or by `claim_hash` within the body's
  `set_id` / `set_version`. A bad line refuses the whole file (422); a claim with no golden_claim item is counted
  `not_queued`; a second import of the same run is `unchanged` (unique item + run). DRY RUN by default.

## Changed

- New: `api/migrations/394_eval_claim_proposal_relabel.sql` (expand), `services/ground_truth/review.py`, routes in
  `api/routers/admin_claim_labels.py` (review list / context / answer / accept-proposals, proposals import, sets,
  claims, relabel), the Claim labels tab (`frontend/app/admin/lab/writing-memory/ClaimLabelsTab.tsx`,
  `claimLabels.messages.ts`, `frontend/lib/claimLabels.ts`) and its Guide section.
- `GET .../{set}/{version}/report` and `.../finals` read the newest correction (`effective_rows`); the report adds
  `relabels` and `evidence_sources`; its counts (`by_label`, `by_labeller_kind`, …) stay over the stored rows.
- `store.read_rows` also returns `created_at` (the correction order needs it; nothing else reads it).
- `GET /admin/writing-memory/disagreements` takes `exclude_source`; the Metrics tab leaves the golden_claim items
  out (they are reviewed on the Claim labels tab), as the issue asks ("replaces the opaque queue rows").
- Tests: `tests/unit/test_aa1063_claim_review.py`, `tests/integration/test_aa1063_claim_review_db.py`; the erasure test
  seeds a proposal and a correction and checks the DRY RUN counts and the apply deletes them through the FKs; the X1
  conftest lists know the two new FORCE-RLS tables.

## Tradeoffs

- Context from the golden item is rebuilt on every page (one `eval_golden_item` read per page, content sha per
  candidate). Cheap at 25 cards; a live T9 piece / T2 version claim has no context until a later slice reads those
  objects.
- The review answers resolve through `disagreements.resolve` (audited as before) and add one `audit_log` row of their
  own (ids, labels, no text). Proposals are append only; the view reads the newest by `created_at`.
- No readiness raise: like the other claim-label routes the new ones answer 503 `unavailable` until CIS 394 is
  applied, and the report / finals keep working without it (`read_relabels_soft`).

  `POST /admin/writing-memory/claim-labels/proposals/import` (`run_id`, `set_id: CL-1`, `set_version: 1.1.0`, lines by
  `claim_hash` or `item_id`; `label` ok / violation / unsure; `reason_vi` / `reason_en`; optional `bad_part`,
  `confidence` high / medium / low, `notes.claim_vi`, `notes.source_says_vi`, `notes.doubt_vi`). The S275 review data

# S276 lane l3 — the Jev pre-filter as code, the t2@2 enqueue, the Jev allow-list

## Decisions

- **The S275 rule, as code** (`services/ground_truth/prefilter.py`, `rule`): auto-ok only when Jev
  `a1_claim_supported` p >= 0.90 AND the panel majority (strict, as the queue's machine_verdict) is ok AND no lens that
  scored the claim violation / unsure gives the class `fact.misbinding`. An ok lens naming the class does not count
  (the S275 back-test: counting every lens kept 94 claims back for nothing). The reject side does nothing.
- **Same stage, question and subject key as S275** (`adhoc_aa1063`, `a1_claim_supported`,
  `aa1063:panel:<hash24>:<source sha10>`): a claim already answered under that key in `shared.decision_log` is read
  back, never asked again. The ask goes through `decide()` (one `llm_call_log` row per call, written by decide).
- **Machine labels are their own source**: the row is a tech-lead row (the DB CHECK only knows `agent_panel` /
  `tech_lead`; widening it would be a contract migration) with labeller `prefilter:jev090+panel`
  (`panel.PREFILTER_PREFIX`). `panel.final_labels` gives such a claim source `prefilter`; `release_evidence` never
  keeps it (even with `audit_ok`), and `agreement_report` does not count it as an audit adjudication. This is the
  S275 lesson "machine-chosen labels stay out of the R1 decision record" made a test.
- **Audit-drawn claims are never pre-filtered**: the audit draw measures the panel's error rate; a machine answer
  there would measure the panel against itself. (S275 cleared 22 audit claims by hand; with this change they read as
  source `prefilter` and drop out of the audit count, which is the honest number.)
- **Source = the bytes the panel read, in the S275 order** (`review.claim_sources`, review fix pass): per claim object
  (content sha, tenant, sample, piece, writer) the first candidate that gives a non-empty text wins:
  `golden_sha` (the claim's golden item by sample id whose panel-visible output has the claim's content sha),
  `live_sha` (the live T9 piece, `acp_shared.content_piece` by piece_id and tenant, whose object
  `content_text / seo_title / meta_description / slug` still has that sha; its writer context rebuilt by
  `review.live_t9_context`, then the panel's T9 sections), `golden_id` / `live_id` (matched by sample id / piece id
  only), `live_wi` (a live candidate whose context cannot be rebuilt: the writer_input snapshot). Never across tenants;
  trap items are never a source; a non-T9 claim has no live path. The answer carries `sources` (count per kind,
  `unmatched`, `source_error:<type>`), so the gap is measured, not assumed.
  Why: the first version only read golden items, and in the S275 run every eligible CL-1 1.1.0 claim took the live
  path (`live_sha` for all 11 pieces, 0 golden matches): on the T9 surface the rule was measured on, every candidate
  would have been `no_source`, Jev never asked and S275's answers never read back (the subject key hashes the source
  bytes). The first version's reason ("the rebuild is in `scripts/aa729`, not in the image") was wrong: it needs only
  `shared.job.payload` and `acp_angle_gate.service.fetch_request`, both in the api image. The rebuild now lives in
  `review.live_t9_context`; `scripts/aa729/select_samples.t9_context` calls it, so the freeze and the pre-filter build
  one context.
  Difference from S275 kept on purpose: `golden_sha` looks only at the golden items of the claim's sample id (the
  review view's lookup), where the S275 script indexed every T9 golden item of every set by output sha. On CL-1 1.1.0
  that index matched nothing, so the result is the same there.
- **Switch**: env `CLAIM_PREFILTER_MODE` on the api service: `enforce` turns writes on; anything else (default unset)
  is shadow. A write also needs `apply: true` in the call, and only the measured writers (`ENFORCE_WRITERS` = T9 blog /
  social) are written; other writers' auto_ok claims are reported as `auto_ok_shadow_writer`.
- **An admin endpoint, not a job kind**: `POST /admin/writing-memory/claim-labels/{set}/{version}/prefilter`
  (`ai.admin`, signed-in admin). One call asks at most `limit` (<= 100) claims at concurrency 8 and stops at `max_usd`
  (<= 0.50, default 0.05); S275 answered 303 claims in 12 s, so a call of 100 stays well inside the gateway timeout.
  Repeating the call continues where it stopped (the read-back). A job kind would need the kind registries for a
  tool run a few times a month.
- **Enforce writes**: one transaction per claim: lock the claim's queue items, re-read its rows, skip it when a
  tech-lead row, a correction or a resolved item appeared meanwhile, insert the row, resolve its open items
  `judge_right` with `resolved_by` = the labeller; one `audit_log` row per call (actor = the admin, the run id).
- **Enqueue (t2@2)**: the existing `POST .../{set}/{version}/enqueue` already queues the disputed and audit claims of
  a set version, idempotent (unique source + source_ref; claims with a tech-lead row left out). Added: a claim with a
  correction (`shared.eval_claim_relabel`) is left out too (`corrected` in the answer when any). The proposals then
  load through the existing `POST .../proposals/import` (#1419).

## Changed

- New `services/ground_truth/prefilter.py`, route `POST .../{set_id}/{set_version}/prefilter` (+ staff policy, the
  two route snapshots, openapi.json).
- `review.py`: `claim_sources`, `live_pieces`, `live_t9_context` (moved from `scripts/aa729/select_samples.py`, which
  now calls it); `golden_candidates` also returns `tenant_id` and `trap`.
- `panel.py`: `PREFILTER_PREFIX`, `is_prefilter`, source `prefilter` in `final_labels`, `agreement_report` reads human
  rows only. `review.SOURCES` and the claims filter know `prefilter`; a correction of a pre-filter label records
  `previous_source = tech_lead` (the column CHECK names the stored row kind).
- `store.queue_candidates(skip_claims=)`, `store.enqueue` leaves corrected claims out.
- Writing Lab: the Pre-filter source in the set table, the claims filter and the badge; one guide line (EN / VI).

## Tradeoffs

- Env switch over a DB setting: no migration; turning it on is an Infra task-definition change (a deliberate step).
- CL-1 1.1.0 counts change on deploy: the 182 S275 pre-filter rows move from `tech_lead` to `prefilter` (572 ->
  390 + 182), and the audit count drops by the audit claims among them. Done-when 2 still holds: the browser and the
  report read the same code.

## Should know

- **Jev allow-list** lives in the DB table `shared.jev_tenant_allowlist` (not code or config); decide() caches it
  20 s. The two demo tenants S275 added carry `added_by = 'aa1063-s275'`. No admin route deletes a row (offboarding
  does, which is not wanted here); remove them with one statement as cis_app (it has DELETE), through the S3-mediated
  ECS exec: `DELETE FROM shared.jev_tenant_allowlist WHERE added_by = 'aa1063-s275'` (the S275 `allowlist.py`
  `MODE=remove` does exactly this). After that, the pre-filter skips their claims (`tenant_not_allowlisted`), so run
  the shadow / enforce passes that need them first.
- t2@2: the rule was measured on T9 only, so T2 claims are shadow whatever the switch says; their source needs a
  golden item (`no_source` otherwise: a T2 claim has no live path). Nobody has checked yet how many t2@2 claims match
  a golden item: the first plan call after deploy (`{"writers": ["t2"]}`, no Jev call) gives the `sources` count.
- After deploy, a plan call on CL-1 1.1.0 (no Jev call) must show `sources.live_sha` > 0 and `verdicts.known` near
  the S275 answers (345 eligible, all answered in S275); a large `unmatched` or `no_source` there means the live
  rebuild differs from the S275 bytes and must be looked at before any shadow / enforce call.
