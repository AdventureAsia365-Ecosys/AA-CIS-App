### Việc 4 — create-page trip-selection field audit (investigation only, no UI changes)

Read `services/acp_planning/quarter.py:109-189` (`_score_reason`, `compute_quarter_plan`) to get
ground truth for every field on `/admin/quarter-plan/create`'s trip rows, then pulled v6's full
`trip_scores` array (763 rows — one per non-retired trip, not just the 8 chosen) from the live DB
to check real distributions rather than guessing.

| Field on screen | What it actually is | Notes |
|---|---|---|
| Trip name / Destination | `Trip.name` / `Trip.destination` | As shown, no surprise. |
| Numeric score (e.g. 1.73/0.73/0.00) | `TripScore.score` — a **composite**: `runway_fit*0.4 + richness*0.3 + distinctiveness_score*0.3 + (1.0 if forced else 0)`. Not a single metric. | Max for a non-forced trip is 1.0; forced trips can reach up to 2.0 (the +1.0 bonus is why 1.73 > any possible non-forced score). |
| "Manually added" reason text | Shown **exactly when** `forced=True`, i.e. the trip's name/destination fuzzy-matched one of the `specials` strings (populated when a human clicks the checkbox to add a trip N5 didn't auto-select). `_score_reason()` checks `forced` first and short-circuits — the 3-way score breakdown below is never computed/shown for a forced trip. | |
| "FORCED" badge | **The exact same `forced` boolean** as "Manually added." | Confirmed by reading both code paths — `create/page.tsx`'s `{t.forced && <Badge>forced</Badge>}` and `_score_reason`'s `if forced: return "Manually added"` both key off `TripScore.forced`. Currently the UI shows **two separate labels for one field** on the same row — redundant, not two different concepts. |
| "High runway fit (BOFU/MOFU window this quarter)" reason text | One of 3 possible labels, meant to name whichever of `{runway_fit*0.4, richness*0.3, dist*0.3}` is numerically largest for that trip (`max(contributions, key=...)` over a 3-entry dict). | **CONFIRMED BUG, not a placeholder illusion** — evidence: of the 763 trips in v6's live payload, 594 (78%) show this exact text, and of those, **562 have `runway_fit=0.0`** (real example: Bhutan trips "THIMPHU FESTIVAL" etc., `runway_fit=0.0, richness=0.0, distinctiveness_score=0.0`, reason still "High runway fit..."). Root cause: when all three weighted contributions tie at exactly `0.0` (the common case — most trips have neither a BOFU/MOFU runway window nor curated atoms yet), Python's `max()` on a dict returns the **first** key in insertion order, and `"High runway fit..."` happens to be listed first in `_score_reason`'s `contributions` dict (`quarter.py:117`). The label is not just uninformative for these rows, it is **factually the opposite of true** (claims high runway fit when the value is the minimum possible, 0.0). |
| "Rich atom pool" / "High-distinctiveness atoms" reason text | Same mechanism, chosen correctly when they ARE the max non-tied contributor — 136 trips in the same payload show "Rich atom pool" legitimately (their `richness*0.3` really was the largest term). | Not buggy on their own — only the tie-at-zero case is wrong. |

### Phần B — tenant filter investigation: CONFIRMED BUG, fixed (Nghiep decision)

STEP 0 for this round hypothesized this was likely correct behavior ("chưa
được cấp portfolio nên chưa có gì để chọn"). Live-DB investigation (S3-mediated
ECS exec, real RDS, aa365-admin) found the opposite — **this was a real filter
bug**, not by-design:

- `services/acp_planning/runway.py`'s `fetch_trips()` queried
  `acp_contract.v_trip_registry WHERE tenant_id = $1` — that column is backed
  by `raw_tours.tenant_id` (who *uploaded/owns* the tour row), not
  `acp_shared.tenant_atom_state` (who's been *licensed* the tour via N1 Gate
  A / Marketplace). Confirmed live: `raw_tours` has rows for **aa_internal
  only** (793/793) — no B2B ingestion pipeline has ever written a
  `raw_tours` row for any other tenant, so this filter returned 0 rows for
  every tenant except aa_internal, unconditionally.
- Proved this wasn't explainable by "tenant hasn't onboarded yet": tenant
  `TEST-N1-flow` (`6fbaf284-...`) has a REAL `acp_shared.tenant_onboarding`
  row with `approval_status='approved'` (Gate A passed, 2026-08-12) and 6
  real `tour_id`s in `acp_shared.tenant_atom_state` — all 6 verified to
  exist as valid trips in `v_trip_registry` (e.g. "CLASSIC LAOS", "Northern
  India: Riverside Safaris..."). Despite a fully completed real onboarding,
  `v_trip_registry WHERE tenant_id = 'TEST-N1-flow'` still returned **0
  rows** — the eligibility query simply never looked at the table N1
  onboarding actually writes to. No B2B tenant (including this one) has
  ever had a single `quarter_plan_version` row, confirmed live — eligible
  trips was always 0 for all of them.
- **Decision (Nghiep, confirmed directly, not inferred)**: this is still the
  development stage — product/UX quality takes priority over licensing
  gates right now. Rather than wire N5 eligibility to
  `tenant_atom_state`/Marketplace licensing (a bigger, product-judgment
  change — does a licensed portfolio *replace* scoring or filter it? can one
  platform trip serve multiple tenants concurrently in the same quarter?),
  every tenant TEMPORARILY reads the same full platform catalog (== today's
  aa_internal view, 763 trips) until Marketplace/N1 licensing (D3/D4, PRD
  ACP v2) is actually built and deliberately wired into eligibility.
- **Fix**: `fetch_trips()`'s query drops `WHERE tenant_id = $1` entirely
  (still takes `tenant_id` as a param — unused for filtering now, kept
  because every caller's signature and `RunwayMap.tenant_id` still need it).
  Marked `# TEMP (2026-08-13, Nghiep decision)` in code with the full
  reasoning inline, specifically so it doesn't read as final design to a
  future STEP 0. **Nothing else touched** — `tenant_atom_state`, Marketplace,
  N1 endpoints all untouched, per Nghiep's explicit scope limit.
- **Known residual gap, flagged not fixed (same scope boundary)**:
  `services/acp_planning/quarter.py`'s `fetch_atoms_by_trip()` has the
  *identical* `WHERE rt.tenant_id = $1` pattern (via its own `raw_tours`
  join) for pulling a trip's atoms — structurally the same bug, one level
  down. Left untouched per Nghiep's "chỉ riêng phần N5 eligible trips, không
  động vào logic khác" — but worth knowing: a B2B tenant now sees real trip
  *names* in the create-plan checklist, but `richness`/`distinctiveness`
  score straight to 0 and N6's slot atoms will be empty for them today,
  since atoms are still fetched tenant-scoped. Not materially different
  from many of aa_internal's own not-yet-atomized trips today (which also
  show richness=0), but this is the next thing to revisit alongside the N1

## Round 7 (2026-08-13) — same version, two different Slot Grids (real bug, fixed)

Nghiep's own real-browser verification (right after round 6, branch not yet
merged) found: viewing v6 (aa_internal, Q3 2026, approved, current) via
History tab's `?version_id=` link gave Week 1 with framework "PAS" / mostly
MOFU; viewing it via the plain "Preview Slot Grid (N6)" button on Atom
Curation (no `?version_id=`) gave "AIDA" / mostly BOFU — same version, no
edits in between, two different computed Slot Grids, with nothing on the
UI distinguishing them (both said "v6 ... APPROVED").

### Root cause — confirmed with live code + live data, not guessed

- Enumerated **every** entry point into `/admin/curation/preview`
  (`grep -rn "curation/preview" frontend/app`) — exactly 3, no others exist:
  `curation/page.tsx`'s "Preview Slot Grid (N6)" button (no `version_id`),
  and `quarter-plan/page.tsx`'s two "Slot Grid Preview" links (History row +
  Approved-detail, both pass `?version_id=`).
- Nghiep's leading hypothesis (the Atom Curation button being a pre-AA-323
  leftover that never reads real Gate B state) is **refuted by code**: its
  target route has no `version_id`, so it goes through
  `preview_slotgrid()`'s `else` branch, which — since AA-323 Gap 1, unchanged
  since before round 6 — already checks `fetch_approved_quarter_plan()`
  first and only falls back to the in-memory demo when that returns `None`.
  Round 5's live curl (this exact branch) already found `demo_mode: False`
  with `trip_ids` matching v6 byte-for-byte; round 7 re-confirmed live again
  (`quarter_plan.current_version_id` = v6's `version_id`, `is_current=True`)
  — the demo path was never the issue.
- **Actual root cause**: `preview_slotgrid()`'s two branches computed
  `month` independently and disagreed. The `?version_id=` branch used
  `month = (quarter - 1) * 3 + 1` (Q3 → July, always the quarter's first
  month). The no-`version_id` branch used `month = today.month` (August,
  2026-08-13's real month). Both agree on `year`/`quarter` (both Q3 2026)
  but NOT `month` — and `compute_slot_grid()` (`allocator.py`) computes each
  slot's `funnel_stage` via `runway.stage(dest, market, month)`, then picks
  `framework` from `FRAMEWORK_TABLE[(stage, "blog")]`
  (`MOFU→PAS`, `BOFU→AIDA`, `constants.py`). **Live-proven, not theoretical**:
  ran `runway.stage("South Korea", "US", 7)` and `(..., 8)` against v6's
  real trips/runway data (v6's 8 trips are 100% South Korea, confirmed live)
  inside the deployed ECS container — got `MOFU` for month 7, `BOFU` for
  month 8. Exactly reproduces what Nghiep saw: `?version_id=` (month 7) →
  MOFU/PAS; plain link (month 8) → BOFU/AIDA.
- This is a real regression introduced by round 6, Phần A: adding the
  `?version_id=` branch didn't re-check that its own `month` derivation
  agreed with the pre-existing default branch's — round 6's own tests only
  checked the version_id branch in isolation (a genuinely-historical
  different-quarter case), never a version_id that happens to BE the
  current one.

### Fix

- `api/routers/admin_atoms.py`: new `_preview_month_for_quarter(year,
  quarter)` — single shared function, now the ONLY place `month` is
  derived, used by both branches. Rule: if `(year, quarter)` is the real
  current quarter, use `today.month` (what should ship right now — matches
  what the default/no-`version_id` link has always shown); otherwise
  (a genuinely different quarter) use the quarter's first month, since
  "today" has no meaning for a plan outside the current quarter. This
  guarantees `?version_id=<the current version>` and no `version_id` at all
  always resolve to the identical `(year, quarter, month)` and therefore
  the identical `SlotGrid` — a version_id pointing at a truly historical
  (different-quarter) version keeps the prior "first month" behavior
  unchanged (round 6's own `test_approved_version_id_reads_that_specific_version`
  test, a 2024 Q1 case, still passes untouched).
- Demo path invariant (Nghiep's "must never run when current_version_id
  exists" requirement): confirmed **structurally already guaranteed** by
  `fetch_approved_quarter_plan()`'s own query (`qpv.version_id =
  qp.current_version_id AND approval_status = 'approved'`) — `demo_mode`
  can only be `True` when no such row exists. Not deleted (still the only
  path for a genuinely-unapproved-yet tenant/quarter) — documented inline
  and locked in with `test_demo_mode_never_true_when_current_version_id_exists`.
- 4 new tests (`test_aa300_admin_atoms.py`): `_preview_month_for_quarter`
  direct cases (current quarter vs. different quarter/year), and the core
  regression — `?version_id=<current>` vs. no `version_id` on identical
  mocked data must produce byte-identical `SlotGrid.slots` (excluding
  `reactive_hold`'s intentionally-random `slot_id`). This test genuinely
  exercises the bug: it failed on the pre-fix code (months 7 vs 8 diverge)
  and passes after the fix. 1174 unit tests total (was 1170), flake8 clean.
- Committed as a follow-up commit on round 6's still-open branch/PR (#143)

## Tradeoffs

- No new role gate for "who can create a pending plan" — the system has no Trang/Nghiep
  distinction today (only admin/reviewer/content/tenant), so `/admin/quarter-plan/create` sits
  under the same `roles: ["admin"]` prefix as Gate B review itself. Building a real
  Trang-vs-Nghiep role split was explicitly out of scope (decision #1) — flagged here, not
  invented.
- Gap 1's create-plan UI does not let a user edit markets/channels/capacity inline — those come
  read-only from the tenant's Planning config (Gap 3). Splitting "which trips" from "what
  campaign parameters" keeps each screen single-purpose; changing parameters mid-preview would
  also silently invalidate the score list shown, which seemed more confusing than a link to
  Tenants > Planning.
- `TripScore.reason` is a single dominant-factor label (e.g. "Rich atom pool"), not the full
  breakdown (`runway_fit`/`richness`/`distinctiveness_score` are still returned as separate
  fields in the API response for anyone who wants the raw numbers — the create-plan UI shows the
  numeric `score` plus the label, not a 3-column breakdown, to keep the checklist scannable).
- `excluded_trip_ids` exclusion is enforced by removing a trip from consideration entirely
  before ranking (never entering `eligible`), not by ranking it and then filtering — this means
  an excluded trip's capacity slot is backfilled by the next-highest-scoring eligible trip,
  which is the expected "remove and let the algorithm re-fill" behavior, not "leave a gap."
- Preview-slotgrid's real-vs-demo branch check (`fetch_approved_quarter_plan` first) adds one
  extra DB round-trip on every Preview page load/Recompute click even when no approved plan
  exists (the common case for a fresh tenant). Accepted — this is a low-traffic admin preview
  endpoint, not a hot path, and the alternative (a separate flag/endpoint) would fragment the
  single source of truth for "is there a real plan" logic that `allocate_month_from_db` already
  owns.
