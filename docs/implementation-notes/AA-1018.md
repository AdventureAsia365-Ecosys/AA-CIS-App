# AA-1018 — AI gateway reliability, part 1 (no migration)

Slice B2 of the S262 gateway plan: connection-level circuit, alerts on open, job backoff jitter, bulk re-queue of
`llm_access_denied` jobs, a report-only failure-domain invariant, a daily probe job (switched off), the provider
section of the OPS-12 digest, and Bedrock client settings from the connection row. No migration, no route change,
no paid call.

## Decisions

- **The connection-level circuit is derived, not stored.** The plan names a `shared.llm_provider_health` row with
  `model_key='*'`, but `llm_provider_health.model_key` has a foreign key to `shared.llm_model_catalog` (migration 309),
  so a `'*'` row is refused by the database. Writing it would also push the breaker into its per-process fallback for
  `DB_RETRY_S` on every failure. Adding a `'*'` catalog row would change the Q0 route hash. So the connection circuit is
  computed from the deployment rows the breaker already shares across tasks (`breaker.connection_health`). It is shown
  everywhere with `model_key "*"`. A later migration (registry v2 `access_state`) can persist it.
- **What trips it (account-wide signals only):** a deployment of the connection in a non-closed circuit with class
  `credential` or `quota_exhausted` (one is enough), or `access_denied` on at least 2 distinct models. A single model's
  refusal never trips it, so an acc2 refusal of one Claude model cannot stop acc2 Cohere embeddings.
- **Only signals newer than the connection's last answered call count.** Any success on any deployment of the
  connection proves the account answers, so it closes the connection circuit at once. The per-deployment circuits
  stay as they are.
- **OPEN blocks every deployment of the connection; HALF_OPEN blocks nothing.** While the newest open period of the
  tripping rows runs, `deployment_plan` and `breaker.admit` (every `guarded` call: routes, embeddings, aliases) skip
  every deployment of the connection, including ones that never failed. After that the per-deployment circuits decide
  alone (their own half-open probe). A failed probe reopens its row for twice as long, so the connection is OPEN
  again. A connection opened by mistake therefore costs one open period, never a stuck connection (same principle as
  S4).
- **Alert on the transition to OPEN.** `record_failure` compares the connection state before and after the write. On
  closed→open it writes one admin bell (`shared.notifications`, `event_type 'llm_circuit_open'`, entity
  `llm_connection:<key>`, at most one unread per entity per 24 h, the `cost_guard` throttle) and queues the ops e-mail
  (`ops_alerts.TEMPLATE_LLM_CIRCUIT_OPEN`, idempotency key per connection, class and UTC day), only when a new bell row
  was written. Best effort, never raises; the DB write uses its own connection and never sets the breaker's DB
  back-off.
- **Re-queue rule (`queue.retry_by_reason`).** Only `failed` jobs whose `error` starts with the reason
  (`llm_access_denied` by default) and finished at or after `since`. A job is skipped when its kind refuses retries
  (`JobKind.retry_refusal`), when its kind is not registered, or when the connection it was refused on is still
  blocked. The job error rarely names a connection, so: a job whose error names a registry connection key is checked
  against that connection; a job that names none is held while any connection is blocked with the same class
  (access_denied or quota_exhausted). "Blocked" (`breaker.connection_refusing`) = the connection circuit is tripped
  at all, OPEN or HALF_OPEN of any class: `connection_health` already drops refusals older than the last answered call,
  so a tripped circuit means nothing has answered since (review S262: the first rule only held a half-open circuit
  for `quota_exhausted` / `credential`, so an acc3 `access_denied` block stopped holding after 5 to 30 minutes with
  nothing answered). The hold lifts on any answered call on the connection: a real call, the admin's Test connection
  or the probe. Dry run by default (lists up to 500); an apply reads at most 50 rows per call
  (`RETRY_REASON_APPLY_LIMIT`, the "paid runs: subset" rule), re-checks each row in its own guarded UPDATE
  (`status = 'failed'`) and spreads `run_after` over 60 s.
- **Alert text is masked (review S262).** The bell payload and the ops e-mail carry the last provider answer through
  `errors.redact_ids`: every ARN becomes `arn:aws:<redacted>`, every other 12-digit run `<account-id>`. An IAM / STS
  refusal (`not authorized to perform: sts:AssumeRole on resource: arn:aws:iam::<acc3>:role/...`) is `access_denied`
  and would otherwise put both account IDs and both role names into every recipient's mailbox and into
  shared.notifications. `render_llm_circuit_open` masks again, so a payload queued before the fix is safe too. The
  stored `shared.llm_provider_health.last_error` is not masked (admin-only, needed to diagnose).
- **Invariant failure domain** = `kind:account:data_scope`, where account is the row's `account_id`, else its
  `account_id_env` name, else the connection key (acc2's task role and acc3's assumed role are different accounts).
  Until migration 321 adds `failure_domain` this is the derivation.
- **Probe job** reuses `api.services.llm_connections.test_connection` per deployment (same adapters, same ledger row,
  same audit row, a success closes the circuit). Only enabled connections without policy problems and enabled text
  deployments; at most `MAX_PROBES` (30). The schedule needs `LLM_DAILY_PROBE=on` (default off). A dry run lists the
  deployments with an estimated cost and makes no call; a live manual run is refused while the switch is off.
- **Bedrock client settings.** `native_runtime` and the satellite runtime client take `timeout_s` (read timeout) and
  `max_retries` (+1 = total attempts) from the connection row only when the column is non-NULL. Every row is NULL on
  Dev today, so the clients are built exactly as before (same `Config`, same cache key; the satellite client still has
  no `Config` at all).

## Tradeoffs

- Derived vs stored connection circuit: derived needs no migration and is consistent across tasks for free (the rows
  are already shared), but its open period is the newest tripping row's, not its own, and it cannot hold a lasting
  `quota_exhausted` state beyond the deployment rules (300 s doubling to 30 min). The lasting state belongs to
  migration 321 `access_state`.
- HALF_OPEN does not block calls. A blocking half-open would need a connection-level probe lease, which needs a
  stored row. The cost is at most one call per never-failed deployment per open period. It does block the bulk
  re-queue, the "unfunded" count of the invariant and the digest attention line (`connection_refusing` = tripped at
  all): those act on many jobs at once, so they wait for a real answer. The price: a connection nobody calls keeps its
  jobs held until someone runs Test connection on it (or turns the probe on).
- Masking the alert, not the stored error: the row in `llm_provider_health` keeps the raw text for diagnosis (admin
  only); everything that is pushed to people (bell, e-mail) is masked.
- Re-queue matching by connection key in the error text. A Bedrock "Error 002" names no connection, so such a job
  waits while ANY connection refuses with the same class. On Dev this is conservative but correct (only acc3 has
  access_denied rows).
- The probe reuses `test_connection` (one audit row and, on success, one ledger row per probe). That is more rows than
  a dedicated probe path, but it is the same code the admin trusts and it already passes `billed_fields`.
- `deploy_gate_exempt` on the probe kind changed two "no kind is exempt" tests (AA-751, AA-725); the gate has not
  blocked on queued rows since AA-993 G5, so this only keeps the probe out of the information count.
