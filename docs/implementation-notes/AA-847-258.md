# AA-847 — migration 258: a stored live-tour join key (CIS side)

Plan: the step-18 gate decision memo of S246 (section 2.3, "CIS 258"), approved by the orchestrator. Kept in its own
notes file so the parallel AA-847 lanes do not edit the same file (lesson S242); `AA-847.md` has a one-line pointer.
Branch `feat/aa-847-258-live-source-key` (from `main` after #896). Infra byte copy on `feat/aa-847-cis-258-copy`.

## Decisions
- **A stored generated column, not an expression index.** `raw_tours` has FORCE RLS. 253's `_live_tour` join key
  `COALESCE(source_group_id, tour_id)::text = gp.source_id` is not leakproof (`CoalesceExpr`, the uuid → text I/O
  cast), so under the RLS quals it can never become an index condition: every read that joins `_live_tour` per
  component scans `raw_tours` (per loop on the search count, once per call on destination detail, and the HNSW
  liveness probe can only be a Join Filter). An expression index on the same expression is ignored for the same
  reason (refuted in the memo). `source_key text GENERATED ALWAYS AS ((COALESCE(source_group_id, tour_id))::text)
  STORED` turns the join into a plain `text = text` (leakproof), so it is an index condition under RLS.
- **Non-partial btree `raw_tours_source_key_idx`.** About 1k rows; usable whatever predicate the planner can prove.
  The memo's 50k evidence used a partial index, so the 50k run was redone with the index as shipped (see Should know).
- **`_live_tour` keeps column name, type and position** (`rt.source_key AS source_id`, text): every view on it
  (`v_tour`, `_tour_day_text`, `v_tour_place`, `v_tour_photo`, `v_tour_day_route`, `_live_stop`, `v_tour_leg`,
  `v_graph_edge`, `v_component_embedding`) picks the new key up without being restated.
- **`v_tour_component`: the per-row LATERAL of 256 becomes a plain left join on the current build.** The LIMIT 1 could
  only ever return one row (`tour_segment_pkey` = all four join columns, `graph_build_one_current_uq` = at most one
  current build), so the rows are the same; the planner can now remove the join when a reader selects no segment
  column (tiles) and hash it otherwise. Alias `seg` kept, select list unchanged.
- **256's `v_tour_place` LATERAL is not touched** (memo item d dropped): not on a failing reader.
- **Preconditions name 253, 256 and 257 in `shared.schema_versions`** (memo), plus `_live_tour`, `geo.tour_segment`
  and the 245 schema owner; a pre-existing `source_key` that is not a stored generated text column is refused
  (`ADD COLUMN IF NOT EXISTS` would keep it silently).
- **Closing checks, stricter than the memo's counts:** row counts of `_live_tour`, `_live_stop`, `v_tour_component`,
  `v_tour_place`, `v_destination`, `v_component_embedding` (as `catalog_owner`, as 256 does; kept as one jsonb in the
  literal setting `aa847.expected_258_counts`, because the Infra role lint refuses a `set_config()` whose name is not
  a literal) and an md5 of `_live_tour`'s `(tour_id, source_id)` set; then, as `cis_owner`, the column is `attgenerated = 's'`, the index
  exists, and no row has `source_key IS DISTINCT FROM COALESCE(source_group_id, tour_id)::text`.
- **Test plan checks are structural** (seq / bitmap scans and hash / merge joins off, plus `enable_sort = off` for
  the HNSW clause): on a test-size table the planner may read all of `raw_tours` anyway (a seq scan, or a bitmap scan
  of `uq_raw_tours_active_per_group` once other modules left statistics: seen in a full-suite run), which says
  nothing; with those off every join is a nested loop and the plan shows whether `raw_tours` CAN be probed by key,
  which the leaky key made impossible. Tiles is checked without forcing (the
  join removal is deterministic) and against the pre-258 plan of the same transaction (which has `tour_segment`).
- **CI has no pgvector**: the test adds a stand-in `embedding float8[]` column before 253 so 253 / 256 / 258 build the
  same shapes; the HNSW clause runs only where pgvector exists (it ran locally on PG 15.17 + pgvector 0.8.1).

## Tradeoffs
- The column add rewrites `raw_tours` (about 5 MB on Dev) under ACCESS EXCLUSIVE for well under a second, inside the
  DB Migrate apply that already waits for idle job tables.
- A generated column is visible to every `SELECT *` reader of `raw_tours` (see Should know); the alternative (a
  separate key table kept by a trigger) is more moving parts for the same planner effect.

## Should know
- **50k local evidence** (root `.tmp-session/aa847/258-50k-evidence.txt`, real DDL on the integration replay with
  Dev-like owners and FORCE RLS incl. `tenant_isolation`): after 258 the forced HNSW plan's liveness probe is
  `Index Scan using raw_tours_source_key_idx` (Join Filter gone; 84 → 13.5 ms), detail 2.3 → 0.12 ms, tiles 93 → 22 ms
  (no `tour_segment` node), the search count probes the key index. **Not reproduced: the natural top-k plan still
  picks an exact top-N sort at 50k** (~180 ms), with the non-partial index, with the memo's partial index, and with
  `app.tenant_id` set. Cause: under FORCE RLS each of `raw_tours` / `published_tours` is estimated at ~0.5 of its rows
  (the PUBLIC `tenant_isolation` policy ORed with `catalog_owner_aa_master_read`), so liveness looks 4x more
  selective than it is and HNSW 4x costlier. 258 fixes the key, not the estimate; the revised step-18 wording makes the
  natural plan report-only. A fix for the estimate is a separate decision (policy shape, or TripPlanner forcing the
  index order at scale).
- Readers of `SELECT *` on `raw_tours` gain a `source_key` key: `shared/repository/raw_tour_repository.py`
  (`dict(row)`), `migrate_to_schema_v3.py` (one-off generator), `api/routers/admin_pipeline.py` (reads named keys),
  `services/content_generation/s1_batch.py` (named keys), `api/routers/v1_tours.py` tour-full. In tour-full the admin
  `safe(raw)` shows the new field, and so does the tenant branch: `project_raw` is a deny-list (`_without`), not an
  allow-list. It exposes nothing new (it is derived from `source_group_id` / `tour_id`, which the tenant branch
  already returns). Every INSERT into `raw_tours` names its columns (a generated column cannot be written).
- `tripplanner`'s column grant on `raw_tours` (`country`, `tour_id`) and the RLS policies are unchanged.
- Rollback: re-run 253's `_live_tour` and 256's `v_tour_component` statements under the catalog recipe, then
  `DROP INDEX silver_aa_internal.raw_tours_source_key_idx`, `ALTER TABLE silver_aa_internal.raw_tours DROP COLUMN
  source_key`, and delete the 258 row of `shared.schema_versions`.
