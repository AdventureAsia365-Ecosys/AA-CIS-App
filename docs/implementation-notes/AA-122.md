## Critical Bug: s2_keyword_research.keywords always empty

`planner.build_compact_packet` reads:
```python
keywords = run_context.get("s2_keyword_research", {}).get("keywords", {})
```

But `synthesize.py` writes to `acp_run_context.s2_keyword_research`:
```python
"s2_keyword_research": {
    "top_opportunities": [...],
    "content_gaps": [...],
    "recommended_actions": [...],
}
```

No `keywords` key is ever written to run_context. The 200-keyword DataForSEO payload is stored in S3 at `acp/s2/{run_id}/keywords.json` (key returned as `keywords_s3_key` in state) but `keywords_s3_key` is NOT written to acp_run_context by synthesize.py.

Result: `top_18` is always `[]` → skeleton prompt receives zero keywords → LLM invents keywords not from the research → anti-cannibalization, country-check validators are meaningless.

**Secondary bug (out-of-scope for AA-122)**: Even if keywords were loaded from S3, format mismatch exists. `build_compact_packet` expects:
```python
{"keyword_str": {"vol_m1": int, "vol_m2": int, "competition": str, "cpc": float, "intent": str}}
```
But DataForSEO S3 payload has `keywords` as a list of objects with `search_volume` (no vol_m1/vol_m2). Needs a separate conversion fix (AA-???).

## AA-122 Implementation Plan

### Root cause
`keywords_s3_key` (from dataforseo.py state) is never persisted to `acp_run_context`. S3 Lambda has no way to load the keyword data.

### Fix (this ticket)
1. **Migration 060** — ADD COLUMN `s2_keywords_s3_key TEXT` and `s2_report_s3_key TEXT` to `acp_run_context`
2. **api/schemas/run_context.py** — Add both fields as `Optional[str] = None` to RunContext and S2StagePayload
3. **api/services/run_context_db.py** — Add to s2 stage columns (TEXT, not JSONB)
4. **services/acp/s2/tools/synthesize.py** — Include `s2_keywords_s3_key: state.get("keywords_s3_key")` in write_run_context_stage call
5. **services/acp_s3/run_context.py** — Read new fields from DB row
6. **services/acp_s3/handler.py** — Add `S3_THRESHOLD_BYTES = 512_000`, `load_context_field`, and size check in handler()

### What is NOT fixed here
- DataForSEO format conversion (list → dict with vol_m1/vol_m2) — separate ticket
- `_SONNET` naming/cost bug in planner.py — low priority, separate fix
- H-3 confidence threshold enforcement — backlog

### Decisions
- `s2_report_s3_key` added to schema for completeness (s2_visibility_report is currently small, no write-path wired)
- `s2_keywords_s3_key` wired end-to-end: synthesize → run_context → S3 Lambda
- Size guardrail: check AFTER reading inline context, before passing to build_compact_packet
- Graceful fallback: if no s3_key → use inline value (no crash)

### Changed vs original requirement
- Task spec used `s2_keywords_blog` / `s2_competitor_urls` — these don't exist. Mapped to `s2_keyword_research` / no competitor write-path to run_context.
- `s2_competitor_urls` offload not implemented — competitors_s3_key is not passed to run_context today; deferred.

### Tradeoffs
- Loading 200 keywords (~100KB) from S3 adds ~10ms Lambda latency vs potential OOM on 500KB+ payloads. Safe tradeoff.
- Could embed keywords inline in s2_keyword_research (avoids migration) — rejected because inline JSONB would grow unbounded with DataForSEO data.

### Should know
- The 500KB guardrail fires AFTER reading from DB. For large keyword sets, the DB read itself is fine (just JSONB retrieval) — the OOM risk is in the Bedrock prompt construction which serializes the whole run_context.
- Migration 060 needs to run before feature is active. Guard: synthesize.py writes s2_keywords_s3_key only if state has it — existing runs without the column keep working.
