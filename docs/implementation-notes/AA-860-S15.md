## Decisions
- **`itinerary_places` reads schema `geo`** (CIS place pipeline, migration 226): `geo.tour_place`
  (`tour_id`, `destination_id`, only rows with a resolved destination) `UNION` `geo.tour_stop` of the
  **current** graph build (`geo.graph_build.is_current`; `swap_graph` keeps the current + 2 previous builds,
  so a build filter is needed). `tour_stop` has only `source_id`; it is mapped to the live tour with the same
  liveness SQL `services/places/store.py` uses (`_LIVE_SQL`: AA master tenant, `master_status = 'active'`,
  not soft-deleted, raw source active), inside `_catalog_fetch`, which pins `app.tenant_id` to the master
  tenant for that transaction (published_tours / raw_tours are FORCE-RLS). Imported, not copied, so the
  liveness rule has one definition.
- `JOIN shared.destinations d … WHERE d.country = $1` kept as before. The return value is unchanged in shape:
  `{str(tour_id): [(str(destination_id), name)]}`.
- Fail-open kept (destination matching is an opt-in extra of the photo sync and must not stop a folder), but
  the log line is now **ERROR** with the country: after X1 S18 a privilege error here would otherwise look like
  "no itinerary".
- Docstring of `api/core/aa544_tenant_pool.py`: the admin pool was described as "aa_cis_admin, BYPASSRLS",
  which was never true (lesson S236: `rolbypassrls = false`; the master reads FORCE tables because it is in
  `rds_superuser`). Now: the CIS runtime role, aa_cis_admin today, cis_app from S18 with CIS 244's parity
  policies.

## Changed (vs the plan text)
- Plan S15 also lists "CI as the RDS shape" (a non-superuser replay job) and the standing ENABLE-only check.
  The standing check moved into S16's test file (`test_x1_cis_app_privileges.py`), where it covers ENABLE-only
  **and** FORCE tables (S243 FORCE correction). The non-superuser CI replay job is not in this PR: the S16 test
  models the RDS shape per migration (as 226/243 tests do); a CI-wide non-superuser replay stays a follow-up
  for S21 (245), where ownership actually changes.
- The `uq_raw_tours_active_per_group` unique index means one active raw tour per source group, so a
  `tour_stop` source maps to at most one live tour; the test covers the realistic cases only.

## Tradeoffs
- `geo.tour_place` rows are not re-filtered by liveness (they are rebuilt per source and keyed by the live
  tour at build time); `tour_stop` rows are, because they are keyed by source only. Same coverage as the old
  TripPlanner query, which had no liveness filter at all.
- The new query only sees places the CIS pipeline extracted. If geo lags the frozen TripPlanner tables for a
  country, fewer destination matches appear. The Infra read-only run-script
  `db/scripts/x1_photo_itinerary_parity.py` (S15b) prints old vs new pair counts per country before this
  matters (S15c, main session).

**Worst case per task set (1 api + 1 worker, Dev today):**
- api: main pool 10 + ad-hoc connects held by concurrent admin requests (one per request at a time; ~6
  realistic) ≈ **16**.
- worker: pool 10 + per-job pools with 8 slots — recompute 5 (cap 1) + S1 ingest Jev 4 (cap 1) + grounding
  2 × the 6 remaining slots (rewrite kinds: s1_rewrite cap 6, t2_rewrite cap 4) = 21 — + ad-hoc connects from
  the LangGraph executor threads (`2 × max_parallel` = 16 threads, one connection each at most) ≈ **47**.
- one task set ≈ **63**; × 2 for the 200 % deploy overlap (the old worker drains for 120 s while the new one
  claims) ≈ **126**.
- Autoscaling bounds (theoretical, also true for the master today, which has no limit): api max 7 tasks,
  worker max 3 → far above `max_connections` 181. Not a cis_app-specific risk.

**Measured:** whole-instance `DatabaseConnections` daily max 28 over 05–18/10 (busiest day 15/10), every role
included. The S15b snapshot script adds per-`usename` / `application_name` samples (S15c).

**Proposal (flag, Nghiệp decides in S15c):** keep **90** (rl-001). The theoretical worst case (126) exceeds
it, but every term of it is a simultaneous peak of independent pools that the measured 28 never approached,
and 53300 on `cis_app` becomes visible through the S18 log-metric alarm plus the existing
`RoleConnectionLimitPct` alarm at 80 %. The budget ceiling is ~105: `max_connections` 181 − tripplanner 30 −
booking 15 − aa_app_user 15 − db_migrator 5 (S20) − ~11 for superuser-reserved slots and master break-glass.
If S15c snapshots show more than 45 `cis_app`-equivalent sessions (half of 90), raise with an Infra
`roles/003` file (`rl-003`, `ALTER ROLE cis_app CONNECTION LIMIT 105`) before S18, never a CIS file — or,
better, move the grounding / Jev / export per-job pools onto the worker pool (plan XD6 fallback).
