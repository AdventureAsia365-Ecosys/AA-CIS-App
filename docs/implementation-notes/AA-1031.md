# AA-1031 — Staff page grants CRM roles (multi-select) and a "Platform owner" preset

Lane `staff-crm-roles`, S263 (Claude Code, orchestrated). Linear AA-1031.

## Decisions

- **Storage: a new table `shared.staff_crm_grant` (migration 330, expand), not a wider `shared.staff_app_grant`.**
  `staff_app_grant` is one role per `(person, app)` (PK `(admin_user_id, app)`); CRM roles are a SET (a person can be
  Operations and Support). Widening it would ALTER the PK and both CHECKs of an existing table (contract, MIG-4, two
  PRs) and change the meaning of a table the Booking flow reads. A new table with PK `(admin_user_id, role)` is an
  expand file (new object, FK to `admin_users` only adds the RI triggers), ships in this one PR and keeps the same
  shape as the Booking grant: one row per granted role, FK ON DELETE CASCADE, `created_at`.
- **Role codes** `platform_admin`, `ops`, `support` map to the WORKFORCE groups `crm-platform-admin`, `crm-ops`,
  `crm-support` (root ADR 0006b decision 6) through an explicit table (`CRM_ROLE_GROUPS`), not string building: the
  group name has a hyphen the code does not. UI names: Agency admin, Operations, Support.
- **No readiness raise.** CIS 328 / 329 (AA-1026) are pending on Dev; raising `REQUIRED_CIS_SCHEMA` to 330 would make
  every deploy wait for them (strict prefix). Instead every reader and writer checks `to_regclass(
  'shared.staff_crm_grant')` first (one cheap catalog read, safe inside a transaction, unlike catching
  `UndefinedTableError`, which aborts it). Missing table: lists show no CRM roles and `crm_roles_available: false`,
  a write that sends CRM roles answers 503 `crm_unavailable`, sync / create-over-existing leave CRM groups alone
  (never strip a group the directory cannot see), and the reconcile skips the CRM comparison.
- **Sync now owns CRM groups.** With the table present, `sync_staff` and the create-over-an-existing-user path add the
  granted CRM groups and remove the other CRM groups, like CIS / Booking. `change_roles` only touches the groups that
  changed (add new, then remove old).
- **Platform owner preset** = `PATCH …/roles {"preset": "platform_owner"}`: CIS `admin`, Booking `admin`, and CRM
  `platform_admin` added to the roles the person already has (Operations / Support are kept). One transaction, one
  `staff.roles_changed` audit row with `"preset": "platform_owner"` in its details. `preset` cannot be combined with
  `role` / `booking_role` / `crm_roles` (400). It does NOT set the owner flag (`is_owner` stays a scripted, audited
  step, migration 247); the UI says so. Only an existing platform owner can apply it, because every directory write
  already re-reads the actor as an active owner + CIS admin (`_require_owner`); the preset only raises roles, so the
  self-change guard (no self demotion) is untouched, and self CRM changes are allowed exactly like self Booking
  changes are today.
- **E2E scopes (root ADR 0006a):** the two directory E2E addresses (A10 reviewer, A10b CIS admin) may hold no CRM role
  (`require_e2e_test_scope` refuses, 400 `e2e_test_scope`), matching the WORKFORCE trigger. The A10c CRM staff E2E
  account (`e2e-crm-staff@…`, crm-ops + crm-support) is never in the CIS directory; the reconcile now lists it under
  `known_e2e_exceptions` (Dev only, exact address and exact groups) instead of reporting it as "no staff account".
- **Audit:** `staff.created` carries `crm_roles`; `staff.roles_changed` carries `crm_roles: {before, after}` (sorted
  lists), exactly like `booking_role`.

## Tradeoffs

- One extra catalog read per staff read / write for the missing-table fallback. Cheap (a handful of staff rows) and
  removable once 330 is everywhere (raise readiness then and drop the guard).
- The preset keeps existing CRM roles rather than replacing them: "platform owner" is additive; removing Operations /
  Support is a separate, explicit change.
- The invitation e-mail still lists CIS + Booking only (follow-up: add the CRM line).
