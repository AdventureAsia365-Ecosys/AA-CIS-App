# AA-680 — CIS issues staff JWTs for AA-Booking (CIS side)

Root ADR 0004, decision O1: one staff store (`shared.admin_users`); CIS issues the JWT, Booking
verifies it with an asymmetric key published as JWKS and requires `aud=booking`.

## Contract (what Booking implements against)

`POST /auth/booking-token`
- Auth: CIS staff session JWT (`cis_admin_token`, HS256) as `Authorization: Bearer <jwt>` or the
  `cis_admin_token` cookie. Bearer wins when both are present.
- 200 `{"access_token": "<jwt>", "token_type": "Bearer", "expires_in": 900}`
- 401 no session / invalid or expired session / tenant token / unknown role / user missing or
  `is_active = false`. 503 signing key not configured. 503 "DB not ready" if the pool is down.

`GET /auth/.well-known/jwks.json`
- 200 `{"keys": [{"kty":"RSA","n":..,"e":..,"kid":..,"use":"sig","alg":"RS256"}, ...]}`, current
  key first, then `previous`, then pre-published `next`. `Cache-Control: public, max-age=600`.
  503 when the key is not configured.

Token
- Header: `alg=RS256`, `typ=JWT`, `kid=<current kid>`.
- Claims: `iss="https://api-cis.lumiguides.it.com"`, `aud="booking"`, `sub=<admin_users.id>`,
  `name` and `preferred_username` (both = `username`), `cis_role` (`admin|reviewer|content`),
  `iat`, `nbf`, `exp = iat + 900`, `jti` (uuid4).
- Booking verify recipe (PyJWT): fetch JWKS (cache ≤ 10 min; MUST refetch once on an unknown
  `kid`, rate-limited to about once per 60 s, then reject if still unknown — also in CONTEXT.md),
  `jwt.decode(token, key, algorithms=["RS256"], audience="booking", issuer=ISS,
  options={"require": ["exp", "iat", "sub", "iss", "aud"]})`. Never accept HS256 here.

## Decisions
- **Endpoints live on `app` in `api/main.py`** next to `/auth/admin-login` / `/auth/verify-admin`,
  like the other auth routes (the `/auth` router in `api/routers/auth.py` is not mounted). Key
  loading, minting and JWKS are a separate module `api/core/booking_jwt.py` so Booking-related
  logic stays out of the 300-line app file.
- **Session read from Bearer or cookie.** `/auth/verify-admin` takes the token in the JSON body;
  the task asked for cookie or Bearer, which fits both a BFF call (Bearer) and a direct
  same-site call (cookie). The API domain (`api-cis.*`) is not the cookie's domain (`aa-cis.*`), so
  in practice the CIS or Booking BFF forwards the token as Bearer.
- **Staff row re-read on every mint** (`is_active` filter, role from the row). The CIS session is
  24 h and stateless; re-checking here caps the window for a deactivated user or a demoted role to
  the 15 min Booking token lifetime. Cost is one PK lookup per mint (≤ 1 per 15 min per user).
- **`name` = username, no `email` claim.** `shared.admin_users` has only `id, username,
  password_hash, role, is_active, created_at, updated_at` (db-schema-reference.md). The task said
  "email, name (if column exists)" — email does not exist, so it is omitted rather than invented.
  `preferred_username` is added as the standard OIDC claim for the same value.
- **`nbf` added** (= `iat`). Harmless and lets Booking reject tokens minted with a skewed clock.
- **Key cache:** 10 min TTL for a good key (a rotation is picked up without a deploy); a failed load
  is remembered for 30 s so a missing secret does not call Secrets Manager on every request; if a
  reload fails while an older key is cached, the older key keeps serving.
- **No startup check.** The key is loaded lazily on first use; a missing secret gives 503 on both
  endpoints and never stops the API (unlike `JWT_SECRET`, which is fail-fast because every route
  needs it).
- **Cache-Control on JWKS `public, max-age=600`** — the 10 min from the task.
- **Key load runs off the event loop (review fix).** The cache refresh is a blocking boto3 call; the
  endpoints call `await booking_jwt.get_signing_keys_async()` (`asyncio.to_thread`) and pass the
  keys into `mint_booking_token(keys=...)` / `jwks(keys)`. The sync `get_signing_keys()` stays for
  tests/scripts. The Secrets Manager client is built with `connect_timeout=2`, `read_timeout=3`,
  `max_attempts=2` (standard mode), so a stalled read holds one worker thread for seconds, not
  minutes. Other threads waiting on the cache lock are bounded by the same timeouts.
- **`next` key list (review fix).** Optional `next: [{kid, public_key_pem}]` in the secret is
  published in the JWKS but never signs, so a rotation can pre-publish the new key before any CIS
  task starts signing with it. Chosen in addition to Booking's refetch-on-unknown-kid; both are
  documented (belt and braces).
- **Blank or repeated rotation kid fails loudly (review fix).** A `previous`/`next` entry with an
  empty kid, or a kid already used (current or another entry), raises `SigningKeyUnavailable`
  instead of being skipped. Because the cache keeps the last good keys on a failed reload, a bad
  edit on a running service logs `booking_jwt_key_unavailable` and keeps serving; only a cold start
  with a bad secret returns 503.
- **Mint trail (review fix).** `booking_token_issued` now logs `jti` and `kid` (the endpoint
  generates the `jti` and passes it in), so a token Booking sees traces back to its mint.
  A refused mint whose session `sub` is inactive/unknown/demoted logs `booking_token_refused`
  at warning with `admin_id`, `session_role` and `reason`. No audit-table row (optional per review;
  structlog to CloudWatch is enough for Dev).

## Tradeoffs
- **Secrets Manager vs KMS asymmetric signing.** KMS keeps the private key out of process memory
  and gives free rotation, but adds a network call per mint and a custom JWS signer. Secrets Manager
  matches the existing pattern (shared/secrets.py, typesafe key) and the task; revisit if Booking
  moves to prod with stricter key-custody needs.
- **No revocation list.** A leaked Booking token is valid up to 15 min; `jti` is present so Booking
  can add a deny-list later if needed.
- **Unauthenticated JWKS** is intentional — it holds public keys only (`d`/`p`/`q` never emitted;
  a test checks `d` is absent).

## Should know
- The secret must exist on acc2 before the endpoints return 200; until then both return 503 (the
  rest of the API is unaffected).
- The ECS task role's existing policy (`AA-CIS-Infra/modules/ecs/main.tf`, `ecs_task_policy`)
  already allows `secretsmanager:GetSecretValue` on `Resource = "*"`, so no IAM change is needed for
  the read. If that statement is ever narrowed, add `arn:aws:secretsmanager:us-west-1:005097885195:
  secret:aa-cis/dev/booking-jwt-signing-key-*`.
- Edge routing: `/auth/*` already reaches the API through API GW `4ylo382khg` (admin-login works
  live); verify `/auth/.well-known/jwks.json` is not swallowed by any `.well-known` rule after deploy.
- Rotation procedure (three steps, so no verifier sees an unknown kid):
  1. Add the new public key under `next`; wait ≥ 20 min (CIS key cache 10 + Booking JWKS cache 10).
  2. Secret becomes `{"kid": new, "private_key_pem": new, "previous": [{"kid": old,
     "public_key_pem": old_pub}], "next": []}`.
  3. After ≥ 25 min (CIS key cache 10 + token 15) drop the `previous` entry.
- The only IAM grant covering the read is the task policy's `secretsmanager:GetSecretValue` on
  `Resource = "*"`; it should be scoped to the CIS secret prefixes later (separate Infra issue).
- Live verify after deploy: `curl -s https://api-cis.lumiguides.it.com/auth/.well-known/jwks.json`
  → 200 with one key; `POST /auth/booking-token` without auth → 401; with a staff session → 200.

## Provisioning (orchestrator / Nghiep runs; single-line commands, from the workspace root)

1. Confirm the account (AA-517 wrong-account writes): `aws sts get-caller-identity --profile aa365-admin`
   must print `005097885195`.
2. Generate the key: `openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 -out .tmp-session/bk.pem`
3. Build the secret JSON: `jq -n --rawfile k .tmp-session/bk.pem '{kid:"bk-2026-10",private_key_pem:$k,previous:[],next:[]}' > .tmp-session/bk.json`
4. Create the secret: `aws secretsmanager create-secret --name aa-cis/dev/booking-jwt-signing-key --description "AA-680 RS256 key CIS uses to sign AA-Booking staff tokens" --secret-string file://.tmp-session/bk.json --profile aa365-admin --region us-west-1`
5. Delete the temp files: `shred -u .tmp-session/bk.pem .tmp-session/bk.json`
6. No IAM change: `ecs_task_policy` (AA-CIS-Infra `modules/ecs/main.tf`) already allows
   `secretsmanager:GetSecretValue` on `*`. No env var change needed either (default secret name).
7. After deploy: `curl -s https://api-cis.lumiguides.it.com/auth/.well-known/jwks.json` returns 200
   with one key, `kid=bk-2026-10`. API GW `/auth/{auth_proxy+}` ANY already routes this path.
