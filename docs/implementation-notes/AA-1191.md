# AA-1191 — USD only: one "Enabled currencies" setting, VND hidden across CIS, Booking and Partner

Lane l4-usd of S297. CIS part (this repo): the setting, the Booking contract view, the CRM HTTP read, the admin and
Content studio surfaces. Booking and Partner have their own notes file under the same name.

## Decisions

- **One key, CIS-owned**: `cis.billing.enabled_currencies` (CIS 497), list, allowed `["USD", "VND"]` (the CIS 435
  CHECK values), default `["USD"]`, area billing, maker-checker, impact high. A `cis.billing.*` key so the existing SQL
  reader `shared.v_setting_billing_effective` (CIS 435) serves it without new grants.
- **USD is always enabled.** The registry validates list items only (no "must contain" rule), so the readers add USD
  back (`currency.normalise`, and the same rule in the 498 view and in the Booking / CRM readers). The guide says so.
- **Effective currency instead of conversion.** A tenant stored with `billing_currency = VND` while VND is disabled is
  served, quoted and invoiced in USD from the USD columns. Its stored value stays (`billing_currency_hidden` tells the
  UI), so re-enabling VND restores the VND billing with no data step. The DRY RUN counts these rows; any conversion is a
  later reviewed step.
- **What a "write in a disabled currency" is**: setting `billing_currency` or `agreed_currency` to it, or setting /
  changing a VND plan price. Re-sending a stored value unchanged, and clearing a VND price, are accepted (an edit of an
  unrelated field must not fail because the plan still holds a VND price).
- **Booking read path**: `catalog.v_billing_currencies_v1` (CIS 498, catalog recipe, SELECT to `booking` only, one
  row). Booking reads the CIS control plane only through catalog views, so no HTTP and no secret.
- **Partner read path**: `GET /catalog/v1/currencies` on `catalog.http.v1` (1.5). The CRM holds no grant on any CIS
  schema (root ADR 0010 decision 4), and it already reads `catalog.http.v1` with its M2M client. The answer carries
  `cache_s` (the key's own cache window) so the CRM's cache length is the setting's, not a CRM literal.
- **Commercial terms**: the API leaves out `fx_vnd_per_usd` and `vnd_price_review_months` (still edited on Platform ›
  Settings) and nulls the VND review / drift while VND is disabled; the frontend hides the two VND columns.

## Changed

- Migration-only PR (batch cis 497-498): the key, the view, `compiled_defaults.json`, `currency.py` (the settings-lint
  reader of the key), integration tests, the conftest replay skip for 498.
- Code PR: `billing_terms` (refusals, effective currency in the details and the quote), `quote` (effective currency, no
  reference in a disabled currency), `plans` (VND price refusal, reviews without VND), `admin_plans` (enabled
  currencies in the list and terms responses), `v1_tours` billing (USD for the studio), `catalog_http` (`/currencies`),
  the two contract copies (catalog.http.v1 1.5, tenant.entitlements.v1 1.12), the frontend pages.
- `currency.py` is in both PRs, byte-identical (an identical add merges cleanly); its readers fall back to USD only
  when the compiled defaults do not know the key yet, so the code PR is safe before 497 is merged.

## Tradeoffs

- A per-key "must contain USD" rule in the generic registry validator was not added: it would change `validate()` and
  the SQL `shared.setting_value_problem` together for one key. The readers enforce it instead.
- The API keeps returning the stored VND values in `GET /admin/plans` (the UI hides them). Nulling them in the API
  would make an edit round-trip clear them.
