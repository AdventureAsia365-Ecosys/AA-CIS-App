# AA-660 — Jev decide() seam (re-scoped S203: enforce, not shadow-only)

Design: `docs/architecture/at-series-v2-design.md` §3.

## Decisions
- **Plain HTTP, no SDK.** `typesafe-sdk` 0.7.2 pulls in `httpx2` and `pydantic>=2.12`, which risks conflicts with the App's pins. The wire format was taken from the SDK source (`_core/endpoints.py`, `_schemas/models.py`, generated from TypeSafe's `openapi.json`):
  - `POST /v1/systemone` with `Authorization: Bearer`;
  - body `{state, model, questions: {name: {type, instructions, criteria?}}}`;
  - answers `noul` / `choice` (+ `confidence`, `probabilities`) / `score` (+ `confidence`, `probabilities`);
  - `usage.input_tokens`.
- **Questions are data** (`shared.decision_question`): wording, kind, mode, floors, `threshold_version`, `calibration_ref`. A stage names question keys only. A DB CHECK refuses `enforce` without a calibration record and at least one floor.
- **Zones.**
  - Noul: `p ≥ accept_floor` → accept; `p ≤ reject_ceiling` → reject; otherwise grey.
  - Choice/score: `confidence ≥ accept_floor` → accept (the pick is trusted); otherwise grey.
  - A missing floor never yields that zone.
  - `Decision.accepted()` / `rejected()` are True only for an enforce-mode, confident verdict. Shadow verdicts are recorded but never act.
- **Fail-open.** Missing tables, an unknown question, a timeout, HTTP errors or a missing answer → `zone='error'`, and the stage keeps its rule. `decide()` never raises.
- **Tenant guard (C2).** Tenant content goes to TypeSafe only for `shared.jev_tenant_allowlist` tenants. Platform (`aa_internal` / None) is always allowed. Seeded with `wanderlux-travel`, `exploreasia-co` and `test-1`, the only non-internal tenants on Dev, all AA-created. A skipped verdict is still written to the ledger.
- **Logging.**
  - `decision_log`: one row per question, all probabilities kept, `job_id` from the current job.
  - `llm_call_log`: one row per call (provider `typesafe`, role `validate`, `tokens_in` = input tokens, cost from the catalog row `jev-latest`, $0.042/1M).
  - Nothing is billed on error.
- **Key.** `shared.secrets.get_typesafe_api_key()` reads env `TYPESAFE_API_KEY`, otherwise the secret `SECRET_TYPESAFE_ID` (default `aa-cis/dev/typesafe`), which may hold the bare key or `{"api_key": ...}`. The ECS task role already has `GetSecretValue` on `*`, so no Infra change is needed.
- **Sync wrapper.** `decide_sync()` is for S1 graph nodes, which run in a worker thread. Called on a thread that runs an event loop, it fails open instead of blocking.

## Tradeoffs
- Per-question cost in `decision_log` is the call cost split evenly across the questions asked, because TypeSafe bills per call. `llm_call_log` holds the exact call cost.
- The config cache TTL is 20 s (same as `llm_role_config`), so a mode change in admin takes up to 20 s to apply.

## Fix (S203) — pool deadlock under concurrent decide()
- **Found** during the AA-661 shadow pass on Dev: 200 decides, 8 in parallel on a 4-connection pool, hung until timeout. With a pool, `decide()` held one connection for the whole call (config → Jev HTTP → logs), then `record_call_with_pool` asked the same pool for a second one. Four tasks each held one and waited for another.
- **Fix:** `_decide(db, …)` acquires only while reading config and while writing each log. It never holds a connection across the HTTP call and never holds two at once. The no-pool path wraps its single connection in `_SingleConn` (same `acquire()` interface).
- **Test:** `test_concurrent_decides_on_a_tiny_pool_do_not_deadlock` (a 1-connection pool, 4 concurrent slow decides, 5 s timeout).
- Not yet exposed in production: no call site used `decide()` concurrently. #486 (A3 research gates, 8 in parallel on the API pool) was held until this fix lands.

## Part 3 (S204, 30/09/2026) — Verdict cache + wording hash (migration 184)
- **Cache:** before calling Jev, `decide()` looks for the newest non-error Verdict with the same question, the same **wording hash**, the same subject and tenant, within 180 days. A hit is served without a call and without cost (`cached = true` in `decision_log`), and its Zone is recomputed with **today's** Floors, so moving a Floor never needs a new call. `use_cache=False` forces a fresh call (calibration runs).
- **Wording hash:** `decision_question.question_hash` is a DB-generated md5 of kind + instructions + criteria, so the app never reproduces JSON formatting. Every Verdict logs the hash it was produced under. A change of wording → new hash → no reuse, and the Calibration Record must be redone (Q12).
- **UI:** "Answers" → **"Verdicts"** everywhere (glossary, Q7); a "Cached" column per question and a cache count in the KPI; the Guide defines Verdict and Cached.
- **Not done, deliberately: batching several subjects into one call** (Ms. Thư's "several asks per request").
  - Our calibrated question was measured with a one-subject state `{place, keyword}`. A multi-subject state is a different input and could shift the probabilities, so the Calibration Record would have to be redone.
  - The saving is negligible: 200 calls cost $0.003, and 8 run in parallel at ~150 ms each.
  - Revisit if Jev volume grows by orders of magnitude.
- **Step 1 of the order (transit rule) was found already in place:** `precompute_question_landings()` skips Segments that `classify_exclusion()` marks transit (856 of 3,362 on Dev), and a question lands only on atoms of its own Segment. What remains: 192 atoms that atomize typed `transit` but the rule did not catch ("cross into China", "journey by long boat"), in 127 Segments holding 564 of 9,471 counted questions (6%). That is the rule-vs-atomize disagreement the planned `a3_activity_type` question covers.
