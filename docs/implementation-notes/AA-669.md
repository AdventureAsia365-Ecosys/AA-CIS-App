# AA-669 — My Content list: the piece's live post (CIS side)

The portal's My Content table (AA-Partner `portal/`, branch `feat/aa-669-my-content-table`) needs a **Published**
status and a **published at** column. This CIS change adds both to `GET /v1/content-writing/reviews`. Session S251,
agent Claude Code.

## Decisions

- **Three fields on each review item**, `published_at` (ISO, or null), `published_url` (the post link, or null)
  and `published_piece_id` (the piece whose post is live, or null), from the newest `acp_shared.publish_log` row
  with `status = 'published'` of **any piece of the request** (a `LEFT JOIN LATERAL ... LIMIT 1` through
  `content_piece.angle_gate_request_id`). A `failed`, `requested` or since-`unpublished` attempt is not
  "published": the same rule `/v1/publish-log/pending` uses to keep a piece publishable.
- **Request-wide, not latest-piece only (independent review, S251).** The first version read the live post of the
  latest piece only. After "Write again" on a published piece the new piece is the latest, so the row dropped back
  to Ready, lost its post link and offered Publish again: a second live post for the same request. Reading the
  request's live post keeps the row Published until that post is unpublished; `published_piece_id` != `piece_id`
  tells the portal the live post shows an earlier version. The portal also refuses Write again on a published row.
- **Tenant bound on both joined tables.** The lateral names `pl.tenant_id = $1` and `pp.tenant_id = $1` (the piece
  that carries the request id), on top of the RLS of the tenant pool (`REVIEWS_FLAG` path) and the
  `cp.tenant_id = $1` of the list itself: a publish row that names this tenant's piece under another tenant id, or a
  piece of another tenant pointing at this tenant's request, never marks the row published (integration test).
- **No server-side refusal added to `POST /v1/publish-log/{piece}/publish`.** AA-726 deliberately lets new text be
  published as a new post ("Editing the text gives a new key, so a deliberate re-publish of new text still works",
  services/acp_publish/idempotency.py). Refusing a second live post per request in the API would change that
  contract for every caller; the portal's rule (no Publish / Write again while the request has a live post) covers
  My Content. Open choice for a later issue: enforce "one live post per request" in the API.
- **No server paging or filter params.** The list is one row per request (tens to a few hundred per tenant), the
  portal's DataTable filters, sorts and pages client-side like every other portal table, and the response stays one
  call. Revisit when a tenant passes ~1,000 requests (the payload carries the full text of each ready piece).

## Changed

- `services/acp_content_writing/service.py`: `_TENANT_REVIEWS_QUERY` + `fetch_review_list()` (three keys). No route,
  schema or OpenAPI change (the route has no response model).

## Tradeoffs

- The link is the tenant's own post URL (already returned by `GET /v1/publish-log`), not gate data: the tenant-safe
  projection (no gate ledger, held reason, repair log, last_error, idempotency key) is unchanged.

## Should know

- Tests: `tests/unit/test_aa450_content_writing_service.py` (fields, join shape), `tests/integration/

## S251 kit DataTable: aria-sort and `compact` (portal UI check D4 / D1)

- `frontend/app/_kit/DataTable.tsx`: a sorted header carries `aria-sort="ascending|descending"` (unsorted headers get
  none, as WAI-ARIA advises); new opt-in prop `compact` (cell padding 10 px a side instead of 16 px) for a wide table
  that must fit its page. Default off: no admin table changes look.
- Why here: the file is vendored byte for byte into AA-Partner `portal/app/_kit/DataTable.tsx` (CI "Vendored CIS
  copies"). The tenant portal's My Content uses `compact` to fit 1440 px without a sideways scroll (AA-Partner
  `fix/portal-content-table-s251`, which carries the identical copy). Merge this PR first, then the AA-Partner one.
- The frozen `portal/` copy in this repo is not touched (its CI guard fails on any change). AA-Booking
  `frontend/ui/DataTable.tsx` is its own fork (local aria-labels), not a byte copy, so it is not changed here.
