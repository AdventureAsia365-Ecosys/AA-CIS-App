# AA-669 — My Content list: the piece's live post (CIS side)

The portal's My Content table (AA-Partner `portal/`, branch `feat/aa-669-my-content-table`) needs a **Published**
status and a **published at** column. This CIS change adds both to `GET /v1/content-writing/reviews`. Session S251,
agent Claude Code.

## Decisions

- **Two fields on each review item**, `published_at` (ISO, or null) and `published_url` (the post link, or null),
  from the piece's `acp_shared.publish_log` row with `status = 'published'` (a `LEFT JOIN LATERAL ... LIMIT 1` on
  the latest piece of each request). A `failed`, `requested` or since-`unpublished` attempt is not "published": the
  same rule `/v1/publish-log/pending` uses to keep a piece publishable.
- **Tenant bound twice.** The join names `pl.tenant_id = $1` next to `pl.piece_id`, on top of the `publish_log`
  RLS of the tenant pool (`REVIEWS_FLAG` path) and the `cp.tenant_id = $1` of the list itself: a publish row that
  names this tenant's piece under another tenant id never marks it published (integration test).
- **No server paging or filter params.** The list is one row per request (tens to a few hundred per tenant), the
  portal's DataTable filters, sorts and pages client-side like every other portal table, and the response stays one
  call. Revisit when a tenant passes ~1,000 requests (the payload carries the full text of each ready piece).

## Changed

- `services/acp_content_writing/service.py`: `_TENANT_REVIEWS_QUERY` + `fetch_review_list()` (two keys). No route,
  schema or OpenAPI change (the route has no response model).

## Tradeoffs

- The link is the tenant's own post URL (already returned by `GET /v1/publish-log`), not gate data: the tenant-safe
  projection (no gate ledger, held reason, repair log, last_error, idempotency key) is unchanged.

## Should know

- Tests: `tests/unit/test_aa450_content_writing_service.py` (fields, join shape), `tests/integration/
  test_aa802_pending_latest_piece.py` (live / failed / unpublished, cross-tenant row). The wave-4 tenant-pool test
  (`test_aa859_wave4_pool_routes.py`) still passes with the join (aa_app_user reads `publish_log` under RLS).
- The portal reads the new keys as optional, so either side can deploy first.
