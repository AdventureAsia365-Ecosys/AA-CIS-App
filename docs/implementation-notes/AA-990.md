# AA-990 — T9 write on a replaced atom: typed 409 `atom_replaced` (S251 slice)

Seen live on 25/10/2026: `POST /v1/content-writing/requests/{id}/write` answered HTTP 500 "atom_id='…' not found
(deleted, or not a live platform/tenant atom)" for two angle-gate requests whose atom a later atomize run had replaced.
This slice only names the condition. Carrying old requests over to the new atoms (the data side) is AA-990 proper and
is not in this branch.

## Decisions

- **One shared definition**: `services/acp_shared/atom_replaced.py` holds the code (`atom_replaced`), the tenant and
  admin sentences, a mixin `AtomReplaced` (status 409, `detail` = "atom_replaced: <sentence>", header
  `X-Error-Code: atom_replaced`) and `atom_is_live()` (the same live-atom filter T8 and T9 use when they read the atom).
  The shape copies `shared.tour_liveness.TourNotServedError` (AA-986 L3), so the portal can treat both the same way.
- **`AtomReplacedError(ContentWritingError, AtomReplaced)`** in the content-writing service: it stays a
  ContentWritingError, so every existing `except ContentWritingError` (and the existing service tests) keeps working;
  the router catches it first and answers 409.
- **Two raise sites**: the single-atom read (`_fetch_atom_text`) and the Route read when every Segment was rebuilt away
  (`_fetch_route_segments`, which was the same 500 with a "refresh the Slate" text). A Route request with no trip id
  stays a plain ContentWritingError (500): that one is a data bug, not a replaced atom.
- **Admin path** = `POST /admin/content-quality/requests/{id}/regenerate-angles`. It cloned the request with the same
  atom and enqueued `t8_angles`, which could only fail on a replaced atom. A single-atom request whose atom is not
  live now answers 409 `atom_replaced` before anything is written or enqueued. Route requests already answered 409
  when no Segment is left (AA-914), unchanged.
- **App-level handler**: `api/main.py` registers the AA-986 handler for `AtomReplaced` too, so a future raise outside a
  router `try` is still a 409 and not the generic 500 handler.

## Changed

- Tenant message: "atom_replaced: Adventure Asia has updated the part of the tour this post was planned from, so this
  post can't be written from it any more. Pick this part of the tour again in Social Content to start a new post."
  The brief said "pick the angle again", but in the tenant API that is `/reopen` + `/choose` on the same request,
  which keeps the same `atom_id`, so the next write would 409 again (S251 review). The way out is a new post from
  Social Content (the Slate), which makes a new request on the current atom. The admin sentence says the same.
- Logging (S251 review): the ids never reach the tenant, so both paths log a `warning` `aa990_atom_replaced` with
  `path` (`t9_write` / `admin_regenerate_angles`), `tenant_id`, `request_id`, `atom_id` (or the Route
  `segment_ids`) and the internal message. That log line is the list of affected requests for AA-990 proper. The
  ids ride on the error through `AtomReplaced.about(atom_id=…, segment_ids=…)`, not constructor kwargs, so the
  exception keeps the plain signature (flake8-bugbear B042).
- `tour_not_served_handler` docstring says it also serves `AtomReplaced` (it only reads status_code / detail /
  headers).
- No data change, no migration.

## Tradeoffs

- The t8_angles job itself (`set_goal_and_generate`) still raises `AtomNotFoundError` for a replaced atom; it runs on
  the worker, not in a request, and the tenant already sees `generation_failed`. Left for AA-990 proper.

## Should know

- The tenant UI lives in AA-Partner now (portal moved, AA-979). It shows `detail` as-is today; reading
  `X-Error-Code: atom_replaced` to offer a "pick the angle again" action is a Partner follow-up.
- `tests/unit/test_aa899_openapi_export.py::test_committed_document_is_current` fails on the local venv only
  (fastapi 0.110.1 there vs 0.161.1 in requirements); no route or schema changed here.

# AA-990 proper (S252) — saved TripPlanner pins and angle requests after the S1 v2 re-sync

Live Dev 25–26/10: 371 pins (add_component) in 103 trips, 322 with no `geo.tour_place` row (99 trips), none on a
retired/paused tour. The AA-989 rebuild of 123 tours kept an id only on an unambiguous one-to-one pair
(ids_carried 223, ids_dropped 1200). 14 angle-gate requests (all single-atom) point at soft-deleted atoms.

## Decisions

- **Redirects, not wider carry-over.** `carry_over_ids` stays one-to-one and unambiguous (a served id is never a
  guess). Every previous row it could not keep gets a redirect (`components.redirect_dropped`): destination → place
  card → itinerary spelling + country → link name + country, any day, nearest day first, then same activity, then the
  smaller id. Many old ids may point at one component (a v2 rewrite merges days).
- **Where the redirects live: `geo.tour_build.counts.id_redirects` (no migration).** CIS has no grant on
  `tripplanner.*` (tp-017: `tripplanner` SELECT, INSERT only) and no catalog view exposes a component redirect, so
  CIS cannot hand the map to TripPlanner at runtime without a migration. The map is cumulative per source
  (`merge_redirects`: an older redirect whose target was dropped now follows this build's redirect; an id served again
  is removed; cap 1000, newest kept) and AA-CIS-Infra `db/scripts/aa990_component_id_backfill.py` (master,
  run-script) copies what saved trips need into `tripplanner.component_id_map`, the AA-847 path.
- **Angle requests: re-point to the unique live atom of the same place** (`services/acp_shared/atom_repoint.py`):
  same source (every version of the tour), platform or the request's tenant, not an empty marker; same
  `name_norm(place)` then same place card, narrowed by day then activity type; several equal candidates →
  `ambiguous` (never falls to the weaker card rule). The one-time run is an ECS-exec script (cis_app) in the root
  `.tmp-session/s252/aa990/` runbook, DRY RUN first, restore file at a fixed S3 key before the apply.
- **Generic names redirect within the same locality only (review round 2).** A kind-only name ("Night Market",
  "Old Quarter", "Base Camp") names a different place in every town, so its spelling / link-name key carries the
  locality (the `geo.tour_place.locality_norm` of the row, the place card's locality or the day's overnight town): the
  dropped Chiang Mai "Night Market" never redirects to the Chiang Rai one left in the tour. When either side has no
  locality (`locality_norm` '?' or a generic spelling on a card-linked row) there is no name key: the id stays
  unredirected and is counted in `ids_unredirected_generic` — never guessed by day distance. Generic = the name is
  kind-only (`is_generic`), or, for the link name, the row's `locality_norm` is set (it is set iff the link name was
  generic at build time). The destination and card rules are unchanged (a destination / card is one place already).
- **No status change for a request with no unique replacement.** `angle_gate_request_status_check` allows only
  pending_goal / pending_choice / approved / reusable; none means "atom replaced", and T8/T9 already answer the typed
  409 `atom_replaced` with the "start a new post from Social Content" sentence. A real state needs a decision (below).

## Changed

- `services/places/components.py`: `REDIRECTS_KEY`, `REDIRECT_RULES`, `redirect_dropped`, `merge_redirects`.
- `services/places/pipeline.py`: redirects after the carry-over; counters `ids_redirected`, `ids_redirected_by`,
  `ids_unredirected`, `ids_redirects_lost`, `ids_redirects_total`; the map itself only in the build counts (the job
  result keeps the counters).
- `services/places/store.py`: `existing_places` also reads `country_norm`, `locality_norm`, `activity`.
- `components.UNRESOLVABLE_LOCALITY` ("?") is now the one constant; `pipeline.UNRESOLVABLE_LOCALITY` points at it.
- `shared/jobs/queue.py`: job detail shows the build counts without `id_redirects`.
- `services/acp_shared/atom_repoint.py` (new) + `tests/unit/test_aa990_pins_angle_requests.py` (new).
- `CONTEXT.md`: places paragraph.

## Tradeoffs

- **No migration vs an automatic contract.** A CIS table `geo.component_redirect` + `catalog.v_component_redirect`
  (the `v_destination_redirect` precedent) read by TripPlanner `shared/component_ids.py` would make a rebuild's
  redirects live at once; it needs CIS 285 and a TripPlanner reader change. Without it the copy is a run-script after
  each place re-sync wave (runbook step). Proposed as a follow-up decision.
- **Generic names: fewer redirects, never a wrong city.** A pin on a generic stop with no known locality stays
  dangling (the traveller sees it as removed) rather than moving to a same-named stop in another town.
- **AA-989 carry-over has the same homonym gap (not changed here).** `carry_over_ids` keeps an id on a unique
  one-to-one pair, and its any-day `link_name` / `spelling` passes compare the name only: if the Chiang Mai
  "Night Market" is dropped and the only new unmatched component of that name is the Chiang Rai one, the Chiang Mai
  id is carried onto it (the served id moves city). Fix = the same locality key in `_carry_key`; left as a follow-up
  decision because it changes which ids are served, not only redirects.
- **A redirect may land on the wrong activity of the right place** (nearest day wins). The traveller still sees the
  same place; preferred over a silent drop.
- The re-pointed request keeps its angles (written from the old atom's text about the same place).

## Should know

- The first rebuild after deploy writes `id_redirects` only for ids dropped by THAT rebuild. The S252 drops are
  recovered by the Infra script (uuid5 re-derived from the soft-deleted atoms, plus the trip_drafts snapshot).
- Merge/deploy CIS first (the angle script imports `atom_repoint`), then run the scripts (root runbook).

## Decisions

- **D1 — redirects are a table and a catalog contract, not build counts.** CIS 285 adds `geo.component_redirect`
  (old_id PK, new_id, source_id, rule, created_at; CHECK old ≠ new, rule ∈ the four redirect rules; no RLS — platform

- **Chains instead of a cumulative map.** A later rebuild that drops a redirect target writes target → newer id; the
  readers (TripPlanner `component_ids.id_map`, the Infra reader checks / backfill) follow up to 5 hops, cycle-safe.
  So CIS never rewrites an older row (simpler than the old merge, and the history stays).

  re-reads, through `_read_request`), `/v1/content-writing/reviews` and `/requests/{id}/review`.
- **D4 — carry-over keys generic names by town.** `_carry_key` takes the same `_name_locality` as the redirects:

# AA-990 scope 5 (26/10/2026) — tenant version older than the Master: `master_newer`

Scope item 5: "Tenant versions older than Master: tenant informed, nothing silently overwritten." Live Dev on
26/10: of the latest tenant version per tenant + tour, 2 were made before Adventure Asia last changed that tour's
Master text, and nothing told the tenant. The AA-986 lifecycle events cover retired / paused / restored /
superseded only, not "Master text updated".

## Decisions

- **Two read-only fields per version** on `GET /v1/tours/my-versions` (every row) and `GET /v1/tours/versions/{id}`:
  `master_updated_at` = `gold_aa_internal.published_tours.updated_at`, and `master_newer` = `master_updated_at` is
  strictly later than the version's `created_at`. Equal timestamps, or either side missing, are `false`.
- **The time source** is `published_tours.updated_at` (CIS 273, AA-645 d06): only the Master publish upsert and the
  admin promote move it. Lifecycle changes (`master_status` deactivate / trash / restore) do not, so a pause or a
  retirement never reads as "Master updated" (those keep their own `served_notice`, AA-986 L3).
- **Computed at read time**: the two queries select `pt.updated_at AS master_updated_at`; `project_version()`
  (`api/routers/_tenant_projection.py`, the one place that shapes a tenant version) adds `master_newer` through the
  pure `master_newer()` helper whenever the row carries `master_updated_at`. No migration, no write, no job.
- **Per version, not per tour**: each row says whether the Master moved after *that* version. The portal reads it on
  the latest version per tour, which is the case the scope item names.
- **Additive contract change**: no response model on these routes, so the OpenAPI document only changes in the two
  route descriptions, which name the fields; `docs/api/openapi.json` regenerated with the pinned FastAPI 0.161.1 /
  Pydantic 2.14.1 (a scratch overlay over the local venv, which has an older FastAPI).

## Changed

- `api/routers/v1_tours.py`: `_MY_VERSIONS_ROWS_SQL` and `_VERSION_SQL` select `pt.updated_at AS master_updated_at`
  (tenant pool and flag-off path share the text); route docstrings name the fields.
- `api/routers/_tenant_projection.py`: `master_newer()`; `project_version()` adds `master_newer` when
  `master_updated_at` is present. Version history rows (no such column) are unchanged.
- `tests/unit/test_aa859_t2_version_reads.py`: the flag-off "pre-AA-859 SQL" texts gain the new column line.
- `tests/unit/test_aa990_master_newer.py`: newer / older / equal / missing / naive-vs-aware, projection, both routes on
  both pools, and the route reads only.
- `docs/api/openapi.json`: the two descriptions.

## Tradeoffs

- `GET /v1/marketplace` (the Tour overview) does not carry the flag: the notice belongs where the tenant opens and
  rewrites its text (My Tours list + drawer). Adding it there later is the same one-column change.
- No notification / lifecycle event row for "Master updated": the flag is derived and always current, so it needs no
  backfill and cannot drift; the cost is that it says *that* the Master changed, not *what* changed.

## Should know

- A Master rewrite wave (AA-645) moves `updated_at` on every rewritten tour, so after a wave most older tenant
  versions will show the notice. That is the intended reading ("Adventure Asia updated this tour after your version").
- The keys pass the tenant key rule (`TENANT_FORBIDDEN_KEY_RE`); they say nothing about gates or scores.
- Portal half: AA-Partner `portal/`, branch `feat/aa-990-master-newer-notice` (a notice in My Tours when the field is
  `true`, nothing when it is absent).

# AA-990 / AA-905 — place geocoding stalled after the Geoapify daily credit limit (S252 slice)

Seen on Dev 26/10/2026: the AA-905 lots ended around 15:10Z with the 2,500-credit guard tripped; about 3,956 names stayed
pending and due with no job to pick them up after the 00:00Z reset. Analysis (AA-Ecosys root repo):
`docs/audits/2026-10-26-S252-aa990-parity/geocode-stall-analysis.md` (RC1–RC6). Not related to T2/T9.

## Decisions

- **Resume after the reset (RC1)**: `place_geocode` ending `stopped_credit_limit` with names still due calls
  `enqueue.enqueue_after_credit_reset`: `run_after` = next 00:00 UTC + 10 min + 0–5 min jitter, idempotency key
  `place_geocode:credit_reset:<reset day>`. Any geocode job already queued is moved to that time instead of adding a
  second row (it would wake every ≤ 20 min, find no credits and relink for nothing: the "names 400, resolved 0" runs,
  RC2). Later debounced enqueues coalesce into the queued row and `GREATEST()` keeps its `run_after`. Result keys
  `next_job`, `next_run_after`; `status` stays `stopped_credit_limit`. `stopped_geocoder_unavailable` still queues
  nothing (an operator must fix the key).
- **Deploy gate horizon**: a queued row due > 1 h ahead (`queue.DEPLOY_GATE_HORIZON_S`) is not counted by
  `active_count` and is reported as `scheduled_later`. Without it the reset row would block every Deploy Dev from the
  credit stop until 00:10Z. Old rows are still all counted (no lower time bound); every other `run_after` in the
  runner is ≤ 20 min, so only the reset row is affected.
- **Stall flag**: data coverage row `geo.names_stalled` (kind `must`, defect): pending names with
  `next_retry_at <= now() - 24 h`, read in the existing `geo` source. No new CloudWatch metric: the AA/Jobs/CIS
  metrics measure the queue, and a new metric would need a new Infra alarm.
- **Tolerant locate answer (RC4)**: `locate.json_object` strips code fences and takes the first JSON object that
  `raw_decode` reads from any `{` (prose before or after, braces in the prose); a one-key wrapper (`{"places": {...}}`)
  is unwrapped unless its key is a label. An answer with no object (empty, refusal, cut at `max_tokens`) raises
  `AnswerUnreadable`; a batch of ≥ 2 names is then asked once more as two halves (≤ 2 extra calls) before its names
  count a try.
- **Honest reasons (RC3)**: `locate.read_answer` returns a Proposal or a reason per label: `unknown_to_model` (null),
  `missing_in_answer`, `malformed_answer`, `not_aa_country:<country>`. Keys match exactly, then by `name_norm`, then by
  the plain name for a "Name (Locality)" label when no other label of the batch shares it. `parse_answer` keeps its
  signature (None for every non-Proposal).
- **Card multi-country strings (RC5)**: `pipeline.canonical(country, tour_country)` turns "Nepal and China" /
  "India, Pakistan" / "Myanmar (Burma)" into an AA country (the tour's when listed, else the first AA one), so the
  name key matches destinations other tours resolved. Component ids are unchanged (they use the tour country).

## Changed

- The analysis' Fix B said a missing name and a still-unreadable batch should not count a try, and a non-AA country
  should be terminal at once. Here each still counts one normal try (unknown after 3): a name the model always drops
  or a batch that is always unreadable would otherwise be asked (and paid) forever, and `not_aa_country:Pakistan`
  would turn Pakistan / Philippines names terminal if this ships before the guard-list fix
  (`fix/aa-990-country-lists`). The reason is what changed, so the next reset can target exactly those rows.
- `services/places/guards.py` is untouched (another branch edits its country lists); the multi-country split lives in
  `pipeline.aa_countries_in` and follows whatever `guards.canonical_country` accepts.
- Not done: the place-card write normalisation (`place_cards.py`), Fix E (`due_names` only for names a tour still
  uses: RC6 is not verified yet, run the analysis' S6 first), skipping the relink / outlier pass after an all-deferred
  run.

## Tradeoffs

- A far-future queued row versus a timer: the runner has no recurring slot, and the api's 5-min sampler could queue the
  run instead (AA-917 pattern) without any long-lived row. The brief asked for the durable runner's idempotent enqueue
  with `run_after`, so the row it is; the gate horizon keeps it from blocking deploys.
- The jitter makes `run_after` differ between two stops the same day; the key is per reset day, so it is still one row.

## Should know

- **DB Migrate `apply`** (AA-CIS-Infra `db/run_migration.py` `JOB_BUSY_SQL`) counts every queued row today, so the
  reset row would make `apply` wait or refuse from each credit stop until 00:10Z. The paired Infra change
  (`fix/aa-990-busy-horizon`: `BUSY_HORIZON_S` = 3600, mirrors `DEPLOY_GATE_HORIZON_S`) must merge BEFORE this CIS

## Review follow-ups (second commit, `fix: review follow-ups`)

### Decisions

- **Dead or self reset row (blocker 1)**: `queue.enqueue` returns the row of a used key whatever its status. After an
  operator cancels the reset row, or after an admin retry / release runs it early with no credits left, the next stop
  the same day got that dead row (or itself) back and queued nothing. `enqueue_after_credit_reset` now takes
  `caller_job_id` (the job passes `ctx.job_id`) and, when the key's row is not `queued` or is the caller, enqueues
  again with `place_geocode:credit_reset:<day>:<caller job id>`, then with no key as a last resort (a retried attempt
  of the same job whose suffixed row is dead too). Keyless is safe: place_geocode runs at concurrency 1 and the
  queued-row check before the insert already keeps it to one queued row. The first key is kept (not dropped) so two
  stops racing on the same day still meet on one row.
- **DB Migrate horizon (blocker 2)**: paired AA-CIS-Infra commit on `fix/aa-990-busy-horizon` (local, not pushed):
  `JOB_BUSY_SQL` counts a queued row only when `run_after <= now() + 1 h`; running rows always count; rows beyond are
  reported as `later=<n>`. Merge order: Infra PR first, then this CIS PR.
- **Run across UTC midnight (should fix)**: the job records `started` just before reading `geocoder_requests_today`
  and passes `now=started`. The count is that day's, so its reset is the midnight after `started`; when that time has
  already passed at the stop, the row is due at once and the next run reads the new day's count. Before, a run that
  started 23:58Z and stopped 00:01Z on yesterday's count queued for the midnight after next (~24 h late).

### Changed

- `services/places/enqueue.py` (`enqueue_after_credit_reset`: `caller_job_id`, `_STATUS_SQL`, key fallback),
  `services/jobs/place_geocode_job.py` (`_utcnow`, `started`, both new arguments).
- Tests: `tests/unit/test_aa990_geocode_stall.py` (+7: day-key row cancelled / failed / succeeded → new queued row
  under the suffixed key; the caller running under the key → new row; both keys used → keyless row; a still-queued
  key row reused; start 23:58 / stop 00:01). New `tests/integration/test_aa990_geocode_reset_sql.py` (CI Postgres):
  `active_count` horizon (+2 h → `scheduled_later`, +30 min → active), the queued geocode row moved to the reset with
  no second row, a cancelled reset row followed by a new suffixed queued row.

### Tradeoffs

- Suffixed key over dropping the key: the key makes the common case (one stop per day) idempotent even if the
  queued-row check and the insert race; the suffix and the keyless fallback handle only the dead-row cases.

### Should know

- The integration file was collected locally but not run (needs the CI Postgres); CI's Integration Tests job runs it.
- Unit tests were run with AWS pointed at a closed local endpoint (`AWS_ENDPOINT_URL=http://127.0.0.1:9`, no
  profile) so `init_sentry`'s Secrets Manager lookup fails fast instead of prompting for MFA when `services.jobs` is

## N3 day guard (S252)

Live case: a 12-day Japan bike tour was republished by the S1 writer v2 with Days 1-4 only (score 10.0, revalidate
passed, approved); A3 then atomized 4 days. The brief suspected a step after the day-count gate (brand audit fix pass,
revalidate, truncation, `itinerary_compression`).

### Decisions

- **Root cause is the source day parser, not a step after the gate.** The source's Day 5-12 lines start with the
  spreadsheet cell's opening quote (`"Day 5 / -Stage 4- ...`). `day_parse._DAY_MARKER_RE` accepted bullets but not a
  quote, so the source read as Days 1-4 and Day 4's block swallowed Days 5-12. Every consumer agreed with the wrong
  oracle: the writer v2 `day_plan` asked for 4 days, validate's AA-329a check compared 4 with 4 (no
  ITINERARY_DAY_COUNT_MISMATCH), and the day oracle filed "12 DAYS vs 4 markers" as SOURCE_DAY_CONTRADICTION, which by
  design suppresses DAY_COUNT_VS_DURATION and is shadow anyway. Evidence: the stored v2 metadata carries exactly that
  SOURCE_DAY_CONTRADICTION finding; replaying the stored source through `source_day_markers` gives 4 markers before
  the fix and 12 after. Fix: the leading class also takes the quote characters `" ' “ ” ‘ ’ „ « »`.
- **Quotes only, no opening brackets** (review follow-up). A first cut also took `(` and `[`; review reproduced a
  phantom: `(Day 14 optional extension available)` in a 2-day source gave the v2 plan [1, 2, 14], so the writer was
  told to write a Day 14 and a correct 2-day page got ITINERARY_DAY_COUNT_MISMATCH (a v2 hard block). Only the quote
  shape has evidence (the Japan row). If a bracket heading is ever needed, accept it only in closed form
  (`(Day 3)` / `[Day 3]`, the close right after the number or range).
- **Final day guard anyway** (`graph.final_day_guard`, run inside `_apply_grounding_recheck`, the last step of the A1
  graph): validate checks days once per draft; the grounding repair, flag_fix and the post-revalidate sentence
  re-repair edit the text after it, and a revalidate passthrough re-runs no validate. The guard re-runs the SAME check
  (`itinerary_day_gap`, now shared with validate) on the text that is persisted. A gap puts
  ITINERARY_DAY_COUNT_MISMATCH on `failure_codes` (existing code: publish gate, review reason and HARD_CODE_REPAIR
  unchanged); on a v2 draft (`hard_block_codes`) it also sets `revalidate_passed = False`.
- **Fix pass structure: keep the existing revert, no new mechanism.** flag_fix (generic pass and the per-day nudge)
  and the grounding repair already run the repair contract, whose `days_kept` invariant (AA-645, S249) reverts any
  field whose "Day N" blocks were dropped, added or renumbered. Rejecting the field's output (revert to the pre-repair
  text) was chosen over "forbid the fix pass to touch itineraries": meal-line and title fixes inside a day are
  legitimate and common. The new test pins the Japan shape (a fix returning 4 of 12 days is reverted).
- **`itinerary_compression` cannot run on v2.** It is a metadata record (AA-353 per-day ratios) of the v1 writer's

## AA-990 N1 (S254) — self-propelled journeys typed `transit` are pinned

Measured live (S254 N1): two multi-day tours had every overnight town resolved and still `match: none` on the
TripPlanner tour page. Their place build skipped almost every atom as `transit`: the 14-day Seoul-to-Busan road
cycling tour (atoms 11, skipped transit 10, one `geo.tour_place` row) and the 2-day Oze-to-Nikko walk (atoms 8,
skipped transit 8, no row). The graph had stops (the overnights) but no component to pin, so the S236 rule (a route
pins at least half of its days) refused both routes.

### Decisions

- **Root cause.** `services/places/components.py` dropped every atom whose `activity_type` is `transit`. A3 atomize
  types the ride or walk between two towns `transit` (its prompt files "getting from one place to another" under
  transit). On a cycling, walking or paddling tour that ride is the day's activity, not logistics.
- **The rule reads the action, not the place.** A transit-typed atom whose action is self-propelled is kept and mapped
  like a bike or trek atom (`journey_activity`): cycle, bike, pedal and ski become `adventure_sport`; walk, hike,
  trek, snowshoe and scramble become `trekking`; paddle, kayak, canoe and raft become `water_activities`. The check
  looks at the opening verb (optionally after continue, set off, then and similar words) or at the means: by bike,
  on foot, by kayak, or "ride … bikes". Motorised transport stays skipped (drive, transfer, fly, train, bus, ferry,
  cable car). The place alone cannot decide this, because "Gurye to Hadong" names a ride and a drive alike.
- **Same handling as bike and trek atoms.** A kept journey's place ("Seoul to Siheung") is linked and geocoded the way
  a bike-typed "A to B" atom already is. No special link to the arrival town: that would change the AA-847 line and
  segment behaviour for trek and bike atoms. Pinning does not need a destination, because TripPlanner pins any
  component of the day that has an embedding.
- **The logistics-noun rule still wins.** A ride to "Hadong Bus Terminal" stays `logistics_place`.
- **No change on the TripPlanner side.** The S236 half-pinned rule is untouched. The fix gives those tours enough
  pinnable days to meet it.
- **Rule version in `components_hash`** (`COMPONENTS_RULE_VERSION = 2`). It works like the AA-989 atom-id change:
  every built tour becomes stale once. The next place_extract (an `only_stale` backfill or any automatic trigger)
  rebuilds its components. Days and vectors are reused, so the rebuild only pays for new names (geocode) and new
  texts (embedding). Without the bump, the two tours would rebuild only with `force`, which also recomputes days.

### Changed

- `components.py`: added `journey_activity`, `atom_action` (the `action` column, else the text after "place — "),
  and `COMPONENTS_RULE_VERSION`. `skip_reason` and `map_activity` take an optional `action`; old calls behave as
  before. `build_components` counts `transit_journeys`.
- `store.py`: `ATOMS_SQL` also selects `a.action` (the view column exists).
- Tests: `tests/unit/test_aa990_transit_journeys.py`, covering the verb table both ways, the skip and mapping rules,
  the text fallback, the 14-day cycling shape (at least half of the days get a place) and the hash version.

### Tradeoffs

- A deterministic verb rule, not the ranking's final verdict (lessons: an exclusion must match the next step's final
  decision). Ranking resolves transit disputes with a Jev call per Segment and per market. The place build has no

  atoms whose action names a self-propelled verb.

## AA-990 N1 (S255) — tour-level transit rule: a transit tour is routed on its legs

The two N1 tours #1089 could not fix: the 14-day Seoul-to-Busan ride (10 of 11 atoms typed `transit`, verbs "go",
"continue", "move … by transportation") and the 2-day Oze-to-Nikko drive (8 of 8 atoms `transit`, verbs "start",
"continue for approx. 13 km", "travel to"). Their transit atoms are the itinerary: the legs' places are the towns and
sights of the route. The per-atom verb rule cannot keep them, because "go to Busan" on a ride and "go to the airport"
on a city tour read the same.

### Decisions

- **The rule is per tour, and its bar is TripPlanner's.** `route_leg_days()`: when the components that the per-atom
  rules keep cover fewer than `ROUTE_MIN_DAY_SHARE` (0.5, the same value as TripPlanner's S236
  `PLACES_MIN_DAY_SHARE`) of the tour's days, and the transit legs of the uncovered days lift the tour to that share,
  those legs are pinned, one component per leg, on the uncovered days only. In every other case, nothing changes and
  the legs stay skipped. This follows the lesson that an exclusion must match the next step's final decision: the
  rule only fires for a tour that would otherwise get no route, and only when it produces one.
- **A covered day keeps its place.** A leg on a day that already has a sight never becomes a component. A normal
  tour's transfers do not turn into planner experiences.
- **Linking.** A leg links to its place card when it has one, which is the case for all 18 legs of the two tours. A
  leg without a card links to the arrival of "A to B" (`days.a_to_b`, the same pattern as the day-title rule), so
  "Kathmandu to Pokhara" resolves Pokhara and not the phrase. The itinerary spelling stays the component's name,
  which keeps the uuid5 id stable.
- **Activity.** A leg's activity comes from its own words (the `other` keyword map: "… National Park" →
  wildlife_nature, "Senjogahara Walk" → trekking), else `local_immersion`. It never comes from the transport mode.
- **Logistics and unnamed places stay skipped.** `skip_reason` runs first. Only atoms skipped for the reason
  `transit` are leg candidates.
- **Day count.** `build_components(..., tour_days=)` takes the tour's day count. The pipeline and the backfill
  estimate pass `pipeline.tour_day_count()` (review fix, below). Without the argument, the count is the highest day
  seen in the atoms and `day_towns`.
- **`COMPONENTS_RULE_VERSION = 3`.** As with #1089, every built tour is stale once. The next place_extract rebuilds
  the components while reusing days and vectors. For a tour the rule does not touch, the components are unchanged,
  so nothing is paid for that tour except the hash write.
- **No `geo.tour_segment` row.** That table is for line destinations (rivers, trails) and its basis CHECK has no
  value for a road leg. A "transit segment" here is the leg's component on its day. TripPlanner draws the polyline
  between the day stops, as for any route. No migration.

### Changed

- `services/places/components.py`: `ROUTE_MIN_DAY_SHARE`, `route_leg_days()`, `leg_link_name()`,
  `build_components(tour_days=)` (two passes: the per-atom rules first, then the legs of the uncovered days), and
  the counters `transit_route_legs` and `route_leg_days`. Rule version 3.
- `services/places/days.py`: public `a_to_b()` (no behaviour change for days).
- `services/places/pipeline.py`: passes `tour_days`. The build `counts` also record `transit_journeys`,
  `transit_route_legs` and `route_leg_days`.
- `services/places/backfill.py`: the estimate passes `tour_days`.
- Tests: `tests/unit/test_aa990_tour_transit_rule.py`. Fixtures copy the two live tours' atoms (place, action,
  card). There are negative cases: a normal tour, legs that cannot lift the tour, a covered day, and logistics
  legs.

### Tradeoffs

- Pinning a motorised leg means a "Busan city — move … by transportation" component can be offered as a planner
  experience at Busan. The gate keeps this to tours that have no route otherwise. The other choice was a new
  destination-type rule, or a model call per leg. Both cost more and would still need this gate.
- The rule is all or nothing per tour. A tour that the legs cannot lift to half its days gets no legs. Partial legs
  would add planner experiences without giving the tour a route.

  is the duration text's number first ("10 Days"). The first cut used only the highest day record, so a tour whose
  duration text is longer than its itinerary text (the V1 `duration_text_vs_days` finding) could pass the CIS bar and
  still fail TripPlanner's. Its legs would then become planner experiences without giving it a route, which is the
  case the rule is meant to exclude. `store._LIVE_SQL` now also reads `rt.duration` (the column `catalog._live_tour`
  feeds to `v_tour`; additive, cis_app already reads raw_tours). `pipeline.tour_day_count(duration, itinerary,
  highest_day)` = max(highest day record, `validity.duration_days` (the v_tour rule)). `backfill.estimate` uses the
  same helper.
