# AA-986 — tour retirement propagation

Source of the problem and the target rule: root repo audit S248, "tour deletion propagation" memo (section 2 matrix,
section 3 target rule, section 4 slices L1–L7, section 5 open questions Q1–Q10). This file covers the CIS slices;
each slice adds its own section.

## L1 — close the A-side leak (one "served" rule for atoms, publish gates)

### Decisions
- **One rule, one copy in Python.** `shared/tour_liveness.py` holds the predicates (`live_master_sql`,
  `live_source_sql`), the inner joins (`served_tour_joins_sql`) and an `EXISTS` form (`live_source_exists_sql`).
  The two former hand copies of the view rule (`services/acp_shared/subject_seed._MEMBERS_SQL`,
  `services/acp_shared/route_guard._TRIP_MEMBER_SQL`) now build their joins from it. They cannot read the view
  itself: it runs with its owner's rights and the tenant pool is not granted it (CIS 241).
- **The view gets the catalog's source half.** CIS 271 is `CREATE OR REPLACE VIEW acp_contract.v_active_tour_atoms`
  with the same 24 columns (listed explicitly: 208 created it with `ta.*`, frozen to those columns) plus
  `JOIN raw_tours rt ON rt.tour_id = pt.tour_id AND rt.source_status = 'active' AND rt.deleted_at IS NULL`, the same
  predicates as `catalog._live_tour` (CIS 258). A unit test checks the migration text and the Python fragments agree.
  Inner join is safe: `tour_atoms.tour_id` has an FK to `raw_tours` (CIS 079), so no atom lacks a source row.
- **409 shape.** `detail` is a plain string that starts with the code: `"source_not_live: cannot approve this review:
  the source tour was deleted (trashed) in S0/A0. Restore the source tour first ..."`, plus header `X-Error-Code: source_not_live`. The
  admin UI shows `body.detail` only when it is a string (`frontend/app/_kit/api.ts`), so a dict detail would render
  as "[object Object]"; this keeps the UI readable with no FE change and keeps a stable machine code.
- **Review list: hide, not a "source deleted" state.** A pending review whose source is not live is hidden from the
  admin list (`/admin/review-queue`, facets and totals too) and from `/v1/pipeline/review-queue`. Reason: the row
  cannot be acted on (approve is now 409), L1 has no FE work, and a visible row with a dead Approve button is noise.
  Closed rows (approved / rejected / dismissed / superseded) stay visible with a new `source_live` boolean, so the
  history is intact and the FE can badge it later (L2 UI).
- **`_enqueue_review`** files a review of a dead source as `'dismissed'` (row kept, traceable), the same pattern
  AA-653 uses for a tour that already has a live Master.
- **`process_export`** refuses before any publish write with `SourceNotLiveError` (a `ValueError`, code
  `source_not_live`). Every publish path goes through it: the review approve and the S1 auto-export.
- **Review round (orchestrator finding): a refused version leaves `'approved'`.** On the refusal `process_export`
  does exactly one write, `generated_content.status 'approved' → 'hitl'` (guarded `AND status = 'approved'`), then
  raises. Reason: an `'approved'` version with no Master is what the S248 probe layer
  `generated_content_approved_unpublished` counts as a violation ("process_export would still publish it"). Done in
  `process_export`, not in each caller, so the S1 auto-export, the approve race and the (never invoked) legacy
  Lambda are all covered. `'hitl'` is the value `_is_publishable` already gives a version that needs a human
  (`content_status_enum`). Consequence for L7: that probe layer keeps `expect = zero` and its text stays true; no
  change to its expect or description is needed.
- **S1 auto-export catches `SourceNotLiveError` on its own** (before the generic `except`): log
  `s1_export_refused_source_not_live` at warning level (an expected refusal, so no Sentry event; the generic branch
  still logs `export_failed` at error level), then file the attempt with `_enqueue_review(...,
  failure_summary=str(err))`, which enters `'dismissed'` for a dead source. The row keeps the reason
  (`source_not_live: ...`) instead of a quality summary, since that version passed every gate. `_enqueue_review`
  gained the optional `failure_summary` argument for this.
- **Restore bug (admin.py `restore_source_tour`): fixed here** — it was a one-liner. The post-commit recompute is
  told `"active"` when a Master came back (before: always `"inactive"`, which superseded the restored tour's ranking
  and route rows again and skipped its place extraction), `"inactive"` when no Master came back. The other half of
  the restore bug (it re-activates every `inactive` Master, including one staff deactivated on purpose) needs a
  reason column and stays in L2.

### Changed (vs. the issue / memo text)
- Approve on a dead source is refused **before** the claim (the claim `UPDATE` carries the live-source condition), so
  nothing changes: the review stays `pending`, the version is not flipped to `approved`. It is hidden from the list,
  so it does not nag; L2's lifecycle service will dismiss such rows when it supersedes / retires a tour.
- If the source is trashed between the claim and the export (a race): nothing is published, `process_export` moves
  the version to `'hitl'`, the claimed review row goes `'approved' → 'dismissed'`, a warning
  `approve_export_source_not_live` is logged and the reviewer gets the same `409 source_not_live` as a dead source
  caught before the claim. (First L1 commit answered `approved` / `exported: false` and left both rows saying
  "approved"; changed in the review round.)

### Tradeoffs
- Two string forms of the rule exist (SQL in CIS 271, Python fragments). A migration cannot import Python; the unit
  test `test_view_uses_the_shared_predicates` is the guard that they stay identical.
- Guards in 271 (columns, owner, table and column ACLs, row arithmetic) make the file longer, but a view swap under
  owner rights and RLS is the place where a silent change would hurt most (lesson from 266 / 270).

### Should know
- Depends on Q1–Q10 only lightly: L1 treats `trashed`, `superseded` and "deleted_at set" sources as not served,
  which every proposed answer agrees with. Supersede (Q2) is "not served for this version" here: the new version's
  Master is what serves the tour. If Nghiệp decides otherwise for supersede, change `live_source_sql` and CIS 27x
  together (the unit test pins them to each other).
- Order: the code does not need 271 applied (it reads `raw_tours` columns that exist). Merge the CIS PR, then the
  Infra copy (its `check_migration_copies` compares with CIS `main`), then DB Migrate `check` → `apply`.
- Probe S248 (CIS half): no trashed / superseded tour has live atoms on Dev today, so 271 is expected to drop 0 rows
  (its NOTICE prints the numbers).
- Other readers of the full rule already exist (`services/places/store.py`, `services/places/validity.py`); they
  were not switched to the shared module in L1 (no behaviour change, scope).
- Not in L1 (memo section 4): pool / tenant routes, Master activate 409, staging replace cascade, notifications to
  tenants, Booking / TripPlanner signals.

## L2 — one tour lifecycle service (ADR 0015 decision 2, Accepted S248)

### Decisions
- **Two PRs, migration first.** The service reads `gold_aa_internal.v_tour_liveness` and writes
  `tour_lifecycle_event` / `master_status_reason`, so the code cannot deploy before CIS 272 is applied. PR A carries
  CIS 272 and its tests only; PR B (on top of A) carries the service, the routers, the admin UI.
- **CIS 272.** `published_tours.master_status_reason` (CHECK: `staff_deactivated`, `staff_trashed`,
  `source_deleted`, `superseded`; NULL = active or pre-L2), `gold_aa_internal.tour_lifecycle_event` (append-only:
  cis_app INSERT + SELECT, UPDATE / DELETE / TRUNCATE revoked even from the Dev default ACL, a BEFORE UPDATE OR DELETE
  trigger; catalog_owner SELECT; no RLS: no tenant column, actor is a label) and `gold_aa_internal.v_tour_liveness`
  (owner-rights view, SELECT to cis_app, aa_app_user, catalog_owner). The view groups by
  `COALESCE(source_group_id, tour_id)::text` written out, not the stored `source_key`: the CI replay skips 258, and
  the value is the same (258 guards it). Guard 3 checks the view's served keys equal the `catalog._live_tour` rule.
- **aa_app_user on the view → AA-859 invariant v3.** The tenant-pool grant the ADR asks for is a privilege on a
  relation without RLS, which invariant v2 (265 / 266) refuses. The view holds no tenant data (the state of AA's own
  catalog keys), so 272 adds it as the one new allowlist entry: `NO_PRIVILEGE_WITHOUT_RLS_SQL_V3` (guard 4, same text
  in `tests/integration/_rls_fixture_helpers.py`). Tests that re-apply 241 / 262 / 265 / 266 on the migrated DB revoke
  that grant first (`revoke_tour_liveness_read`, also called by `revoke_platform_reads`), the 244 lesson.
- **One service, every writer.** `services/tour_lifecycle`: `retire_source`, `restore_source`, `supersede`
  (replace / update / keep_both / create_new), `set_active`, `pause_master`, `activate_master`, `trash_master`,
  `restore_master`, `publish` (the Master insert of `process_export`), `insert_new_sources` (ingest of new keys).
  Routers: `PATCH /admin/tours/{id}/trash|restore`, `DELETE /admin/raw-tours/{id}` (same retire; it answered 409 for a
  published tour before), `POST /admin/upload-staging/{id}/decide`, `POST /admin/raw-tours/{id}/set-active`,
  `PATCH /admin/master/{id}/status|activate|deactivate|trash|restore`.
- **The cascade is generic.** After its own status write, every action runs the same steps in its transaction:
  switch off every active Master of the key whose source is not live (reason `source_deleted` / `superseded`: never
  two active Masters, also for leftovers written before L2), recompute the derived state from the view, dismiss
  pending reviews of dead versions (all of the key's when its Master is trashed), write the lifecycle event when the
  derived state changed, cancel queued T2 / T8 / T9 jobs when the key is retired or paused by staff, notify tenants.
  Events: `retired` / `paused` with the view's reason; `restored` (reason = the action) when a retired / paused key is
  served again; `superseded` (reason `replaced`, `replaced_by_tour_id`) per replaced version, written only for a key
  that was ever served (a key without a Master has no state, ADR decision 1).
- **Restore re-enables only what the service switched off** (`master_status_reason = 'source_deleted'`); a Master
  staff deactivated stays off and the key is `paused`. `set_active` brings back a Master switched off with reason
  `superseded`.
- **Tenant notifications (Q10).** `tour.discontinued` when the key becomes `retired`, to every tenant (not AA) with a
  derivative: a T2 copy, a Slate subject on one of the key's routes or on a Segment left with no served member, an
  angle-gate request (trip or atom of the key), a piece of such a request, a publish-log row. Payload carries the
  reason, the derivative counts and `live_posts` (Q3: mentioned, never unpublished). A tenant whose latest warning for
  the key is still a `tour.discontinued` is not warned twice. `tour.reinstated` when the key is served again, to
  exactly the tenants still holding a warning (latest of the two events per tenant / tour). Pause (Q1) and supersede
  (Q2) notify nobody. Staff events (`tour.source.trashed`, `tour.master.*`) are still written by the service.
- **Jobs.** Queued only (the AA-797 offboarding pattern): `status = 'cancelled'`, `cancel_requested`, error says why;
  after commit `run_terminal_hook` marks the T2 version / T9 piece failed and clears the T8 goal. A running job
  finishes; L3's 409s stop new ones.
- **Q6 re-upload of a deleted tour.** A key is "deleted" when no version is live and one was trashed. Staging lists
  `matched_deleted` / `matched_deleted_at`; replace / update / keep_both on it answer 409 `source_deleted`; new
  decisions `restore` (restores the key's newest trashed version, incoming discarded) and `create_new` (incoming
  becomes a new key). The near-duplicate check now sees trashed rows of dead keys (a live duplicate wins); a near-
  duplicate of a deleted tour is staged instead of skipped. The Upload preview says "deleted on <date>".
- **Q8.** Retiring a tour whose key was ever published needs `master.admin` (checked in the trash and DELETE
  routes; a tour still only in S0/A0 keeps `content.write`). Dry run: `GET /admin/tours/{id}/lifecycle-preview?
  action=retire_source|trash_master|pause_master` runs the real action in a transaction it rolls back, so the counts
  cannot drift from the action. POLICY: `content.read`.
- **409 shapes.** `LifecycleError.detail` = `"<code>: <sentence>"` + header `X-Error-Code` (the L1 shape: the admin kit
  shows a string detail); a 404 keeps its old plain sentence.
- **Admin UI.** Master Content: a "Retire" button (source retire) and the existing "Trash" both open
  `RetireTourDialog` (dry-run counts, bookings note, then the PATCH). Upload › Duplicate Review: a red "deleted on"
  banner and the Restore / Create a new tour choices for a deleted match; failed decisions show the backend sentence.

### Changed (vs. the issue / memo / ADR text)
- **Q4 staff notification for Booking is not in L2.** CIS cannot read `booking.*` (X1: the CIS roles are denied the
  Booking schema), so CIS cannot know a confirmed booking. The dry run returns `bookings: null` with a note; the staff
  notification belongs to L5 (Booking reads the L4 tombstone and flags / notifies its own staff).
- The ADR's guard covers INSERT too: the guard test fails any `INSERT INTO raw_tours / published_tours` outside the
  service and the two repositories, and any call of the repositories' insert paths (`PublishedCatalogRepository(`,
  `.insert_batch(`) outside the service.
- `pause_master` / `activate_master` refuse a trashed Master (409 `master_trashed`, "restore it first"); before L2
  "Set Active" on a trashed Master made it active with `deleted_at` still set.
- Tenant-facing reading of the notifications, the badges and the tenant 409s stay in L3 (the service only writes).

### Tradeoffs
- The view groups all ~1k raw_tours rows per call (a key filter is pushed into the grouped subquery, but the key is
  an expression, not the indexed column). A few ms on Dev; switch to `source_key` once the CI replay applies 258.
- Dry run by rollback takes the same row locks as the action for a moment; preferred over a second "count" code path
  that could drift.
- Supersede does not cancel tenant jobs (Q2: invisible to tenants); a T2 job queued on the old version still runs.

### Should know
- Order: PR A (CIS 272) → Infra copy → DB Migrate check / apply → schema-reference PR → PR B. PR B's code fails at
  the first lifecycle action without 272 (the view does not exist).
- `master_status_reason` NULL on rows switched off before 272 is treated as "not the service's": restore leaves them
  off. Dev 23/10/2026 has no non-active Master (probe), so nothing is stranded.
- Unit tests that drive `process_export` with a faked connection use the `plain_publish` fixture
  (tests/unit/conftest.py): the repository insert only.
