# AA-986 — tour retirement propagation

Source of the problem and the target rule: root repo audit S248, "tour deletion propagation" memo (section 2 matrix,
section 3 target rule, section 4 slices L1–L7, section 5 open questions Q1–Q10). This file covers the CIS slices;
each slice adds its own section.

## L1 — close the A-side leak (one "served" rule for atoms, publish gates)

### Decisions
- **One rule, one copy in Python.** `shared/tour_liveness.py` holds the predicates (`live_master_sql`,
  `live_source_sql`), the inner joins (`served_tour_joins_sql`) and an `EXISTS` form (`live_source_exists_sql`).
  The two former hand copies of the view rule (`services/acp_shared/subject_seed._MEMBERS_SQL`,
  `services/acp_shared/route_guard._TRIP_MEMBER_SQL`) now build their joins from it. They cannot read the view
  itself: it runs with its owner's rights and the tenant pool is not granted it (CIS 241).
- **The view gets the catalog's source half.** CIS 271 is `CREATE OR REPLACE VIEW acp_contract.v_active_tour_atoms`
  with the same 24 columns (listed explicitly: 208 created it with `ta.*`, frozen to those columns) plus
  `JOIN raw_tours rt ON rt.tour_id = pt.tour_id AND rt.source_status = 'active' AND rt.deleted_at IS NULL`, the same
  predicates as `catalog._live_tour` (CIS 258). A unit test checks the migration text and the Python fragments agree.
  Inner join is safe: `tour_atoms.tour_id` has an FK to `raw_tours` (CIS 079), so no atom lacks a source row.
- **409 shape.** `detail` is a plain string that starts with the code: `"source_not_live: cannot approve this review:
  the source tour was deleted (trashed) in S0/A0. Restore the source tour first ..."`, plus header `X-Error-Code: source_not_live`. The
  admin UI shows `body.detail` only when it is a string (`frontend/app/_kit/api.ts`), so a dict detail would render
  as "[object Object]"; this keeps the UI readable with no FE change and keeps a stable machine code.
- **Review list: hide, not a "source deleted" state.** A pending review whose source is not live is hidden from the
  admin list (`/admin/review-queue`, facets and totals too) and from `/v1/pipeline/review-queue`. Reason: the row
  cannot be acted on (approve is now 409), L1 has no FE work, and a visible row with a dead Approve button is noise.
  Closed rows (approved / rejected / dismissed / superseded) stay visible with a new `source_live` boolean, so the
  history is intact and the FE can badge it later (L2 UI).
- **`_enqueue_review`** files a review of a dead source as `'dismissed'` (row kept, traceable), the same pattern
  AA-653 uses for a tour that already has a live Master.
- **`process_export`** refuses before any publish write with `SourceNotLiveError` (a `ValueError`, code
  `source_not_live`). Every publish path goes through it: the review approve and the S1 auto-export.
- **Review round (orchestrator finding): a refused version leaves `'approved'`.** On the refusal `process_export`
  does exactly one write, `generated_content.status 'approved' → 'hitl'` (guarded `AND status = 'approved'`), then
  raises. Reason: an `'approved'` version with no Master is what the S248 probe layer
  `generated_content_approved_unpublished` counts as a violation ("process_export would still publish it"). Done in
  `process_export`, not in each caller, so the S1 auto-export, the approve race and the (never invoked) legacy
  Lambda are all covered. `'hitl'` is the value `_is_publishable` already gives a version that needs a human
  (`content_status_enum`). Consequence for L7: that probe layer keeps `expect = zero` and its text stays true; no
  change to its expect or description is needed.
- **S1 auto-export catches `SourceNotLiveError` on its own** (before the generic `except`): log
  `s1_export_refused_source_not_live` at warning level (an expected refusal, so no Sentry event; the generic branch
  still logs `export_failed` at error level), then file the attempt with `_enqueue_review(...,
  failure_summary=str(err))`, which enters `'dismissed'` for a dead source. The row keeps the reason
  (`source_not_live: ...`) instead of a quality summary, since that version passed every gate. `_enqueue_review`
  gained the optional `failure_summary` argument for this.
- **Restore bug (admin.py `restore_source_tour`): fixed here** — it was a one-liner. The post-commit recompute is
  told `"active"` when a Master came back (before: always `"inactive"`, which superseded the restored tour's ranking
  and route rows again and skipped its place extraction), `"inactive"` when no Master came back. The other half of
  the restore bug (it re-activates every `inactive` Master, including one staff deactivated on purpose) needs a
  reason column and stays in L2.

### Changed (vs. the issue / memo text)
- Approve on a dead source is refused **before** the claim (the claim `UPDATE` carries the live-source condition), so
  nothing changes: the review stays `pending`, the version is not flipped to `approved`. It is hidden from the list,
  so it does not nag; L2's lifecycle service will dismiss such rows when it supersedes / retires a tour.
- If the source is trashed between the claim and the export (a race): nothing is published, `process_export` moves
  the version to `'hitl'`, the claimed review row goes `'approved' → 'dismissed'`, a warning
  `approve_export_source_not_live` is logged and the reviewer gets the same `409 source_not_live` as a dead source
  caught before the claim. (First L1 commit answered `approved` / `exported: false` and left both rows saying
  "approved"; changed in the review round.)

### Tradeoffs
- Two string forms of the rule exist (SQL in CIS 271, Python fragments). A migration cannot import Python; the unit
  test `test_view_uses_the_shared_predicates` is the guard that they stay identical.
- Guards in 271 (columns, owner, table and column ACLs, row arithmetic) make the file longer, but a view swap under
  owner rights and RLS is the place where a silent change would hurt most (lesson from 266 / 270).

  Master is what serves the tour. If Nghiệp decides otherwise for supersede, change `live_source_sql` and CIS 27x
  together (the unit test pins them to each other).

- Probe S248 (CIS half): no trashed / superseded tour has live atoms on Dev today, so 271 is expected to drop 0 rows
  (its NOTICE prints the numbers).

  were not switched to the shared module in L1 (no behaviour change, scope).
