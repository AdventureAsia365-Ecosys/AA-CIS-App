# AA-1076 — gateway Batch lane for the direct APIs (Anthropic first, then OpenAI)

Lane l2-cis-1076 of S277 (Claude Code). Code: `shared/llm_client/batch_lane.py` (the lane),
`shared/llm_client/adapters/anthropic_batches.py` + `openai_batches.py` (the providers), `services/llm_batch/consumers.py`
(S1 attempt 1, A3 re-atomize, ad hoc), `services/jobs/llm_batch_job.py` (the durable driver), `api/services/ai_gateway_batches.py`
+ `GET/POST /admin/ai-gateway/batches*` (admin), the Batches tab of `/admin/ai-gateway`.

## Decisions

- **One job row per batch, rescheduled, not a chain of poll jobs.** A new `registry.Reschedule(delay, progress)` exception puts
  the running row back to `queued` with `run_after = now() + delay`, the attempt not counted (`attempt - 1`, like a release),
  the state merged into `progress`. The batch is one row on the Jobs page and survives every worker restart: nothing waits in
  process (ADR 0003a runner, no new table). Caps: delay <= 600 s (the deploy gate assumes scheduled `run_after` <= 20 min),
  600 reschedules (then the job fails). An admin cancel asked meanwhile wins.
- **No migration.** `pricing_mode '<basis>+batch'` is already allowed by the `llm_call_log` CHECK (migration 312); the batch
  state lives in `shared.job.progress`; spend per batch is read from `llm_call_log.quality_signal->>'batch_id'` (bounded by
  stage + `created_at >= submitted_at`, the stage index). So no MIG-4 chain: one code PR.
- **Target = the stage's route, model first, on its first direct-API deployment.** `resolve_target` walks
  `[model_id, *fallback_model_ids]` and each model's `vendor_route.deployment_plan` (data scopes, served roles, the pii rule,
  circuits, connection budgets: the same plan an on-demand call gets) and takes the first deployment on an `anthropic` or
  `openai` connection. A route with none cannot batch (refused, run on demand). The same model as on demand, the cheaper way in.
- **Byte-identical requests by construction, checked at use.** The batch body is built by the on-demand adapters' own builders:
  `anthropic_messages.build_params` (effort / thinking / structured output / `cache_system_prompt` from the deployment) and a new
  `client.openai_chat_body` (moved out of `_call_openai` unchanged). The hand-off is keyed on `prompt_sha(stage, system, user)`:
  a reply is used only when the prompt the caller builds at run time is the same bytes; otherwise the call runs live
  (`llm_batch_reply_not_used`). No "assume the prompt did not change".
- **Hand-off through a context variable, not new parameters through five layers.** The consumer job (`s1_rewrite`,
  `a3_atomize`) binds its replies (`batch_lane.bind_replies`) around the normal run; the two call sites ask
  `batch_lane.prefetched(...)` before their live call: the S1 writer v2's writer call on attempt 1 (no validate feedback) and
  A3's per-day read on attempt 1. LangGraph nodes and `asyncio.to_thread` copy the context, as for `stream_sink.bind`.
- **Retries and fallbacks stay outside the batch.** A failed / expired / cancelled / missing item, a refused or cut reply, a
  reply that is not JSON, and a stale prompt all mean "no reply bound" -> the same job runs the call on demand. Graph retries
  (feedback) always write live. Proven in `tests/unit/test_aa1076_batch_fallback.py`.
- **S1 seeds the writer v2 only.** The S1 writer v2 is the live A1 writer (S250). The lane batches its WRITE call (the big one);
  the meta call, its retry, validate, judge, flag fix, grounding run on demand as today. With the v2 switch off the lane refuses
  (the v1 seed path stays Bedrock Batch's `s1_batch.py`, unchanged).
- **One ledger row per request at the batch rate.** `ledger_rows`: billed result -> `pricing.quote(Usage(batch=True))` on the
  deployment (price overrides first) -> `pricing_mode` `catalog+batch` etc., `**billed_fields(resp)` of the reply built for it,
  status ok / truncated / billed_unusable; nothing billed -> 0 USD error row (`expired` -> error_class `deadline`).
  `quality_signal`: `batch`, `batch_id`, `provider_batch_id`, `custom_id`, `consumer`, `batch_outcome`; `unit_kind
  batch_request`. The caller writes NO row for a prefetched reply (`provider_requests = 0` marks it; `already_ledgered`).
- **Cost cap per batch, checked before submit, with the gateway's estimate.** `estimate_usd` = the gateway's own
  `estimate_call_usd` (prompt chars / 4 in, the whole max_tokens out, after the stage x model params and the token floor) per
  request x `BATCH_DISCOUNT`; refused above the caller's cap (required, 0 < cap <= 100 USD) and through
  `central_budget.check`. Also refused: the lane switch `LLM_BATCH_LANE=off`, tenant stages (`t<n>_*` stay synchronous), a
  switched-off stage, the app's AI switch off.
- **Submit is fenced.** `progress.phase = submitting` is written before the provider call; a run that finds it again fails
  ("submit outcome unknown") instead of paying twice.
- **Polling**: 60, 60, 120, 120, 300, 300, then 600 s. 25 h after submit the batch is cancelled (the providers end it at 24 h);
  what it did not finish ends canceled / expired and runs on demand.
- **Waves**: the payload names its tours in a top-level `tour_ids` list, so the wave report (`llm_batch` added to
  `WAVE_JOB_KINDS`, the jobs CTE reads `tour_ids`) shows the tours `running` while the batch is out and counts the batch's
  ledger rows in the wave's cost; the wave quality check already reads `tour_ids` (S272). Wave rules unchanged (3 -> <= 50 ->
  per country, RDS snapshot, no deploy while a wave is open). `MAX_TOURS` 200 per batch.
- **Admin**: Batches tab (kit only, English copy): per batch status / phase, provider and model, requests, outcomes, estimate
  vs cap, spend (ledger), the same requests at the standard price, saved; Send (ai.admin) and Cancel (ai.admin). Reads are
  spend.read like the rest of the page. POST is ai.admin only: the role matrix forbids the content side any ai-gateway route.
- **Live fallback drill**: `drill_withhold: 1` withholds the first usable reply at hand-off, so that tour is rewritten on demand
  exactly as an expired item is (its ledger row stays real). Cancel on a sent batch is the second live path (canceled items).

## Changed (vs the issue text)

- OpenAI Batch is wired for kind `openai` connections only (Azure batch deployments are another product).
- Ad-hoc backfills use the lane from scripts (`consumer: adhoc`, a `stage` named `adhoc_<issue>` for the ledger and a
  `route_stage` for the model); the page sends only S1 and A3 waves.
- Prompt caching inside a batch follows the deployment's `cache_system_prompt` (off on anthropic-direct today) or the send's
  `cache_system`; the S276 follow-up (measure the stable-prefix share per stage, then switch caching on per connection) is
  not done here.
- `llm_model_deployment.batch_capable` is not used as a gate: every seeded row is `false` and there is no admin editor;
  gating on it needs a contract migration (follow-up).

## Tradeoffs

- Contextvar hand-off vs explicit parameters: less plumbing through `_run_tour_safe -> _execute_run_tour -> _rewrite_tour ->
  initial_state_for -> generate_node`, at the cost of an implicit dependency; mitigated by the sha check and the tests.
- A3 day replies travel in the `a3_atomize` job payload (a few KB per day): no new table, at the cost of a larger payload row.
- The A3 consumer re-reads the served Master at ingest; a Master changed in between means a version mismatch -> the days are
  read live (correct, paid twice for those days).
