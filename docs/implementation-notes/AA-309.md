### assigned_angle vocabulary proposed and used
7 angles (`api/routers/admin.py::ASSIGNED_ANGLES`): `culinary_people` (Ẩm thực & Con người),
`physical_terrain` (Thể lực & Địa hình), `culture_craft` (Văn hoá & Thủ công), `nature_wildlife`
(Thiên nhiên & Hoang dã), `luxury_leisure` (Sang trọng & Nghỉ dưỡng), `family_group` (Gia đình &
Trải nghiệm nhóm), `wellness_spiritual` (Tâm linh & Chữa lành). Reasoning: 3 from the issue's own
illustrative examples + 4 more, sized for headroom above AA-332's cited ~3-5-tenant-per-destination
ceiling (some destinations won't fit every angle equally well, so slack beyond the exact ceiling
matters); each is a generic cross-destination narrative lens, not tied to one country. TEXT + CHECK
constraint (migration 098), matching `tour_atoms.distinctiveness`'s own existing convention — not a
native Postgres enum, so extending the list later doesn't need an `ALTER TYPE`.

### Migration 098 — `acp_shared.tenant_atom_state` + `acp_shared.tenant_onboarding`
Grain is `(tenant_id, tour_id)` — NOT `(tenant_id, atom_id)` as this issue's own STEP 0 proposal had
suggested; the build task's explicit column spec uses `tour_id`, followed exactly. `cooldown_until`
is a single nullable `TIMESTAMPTZ` here (not the `{channel: date}` JSONB shape `tour_atoms.
cooldown_until` uses) — also per the build task's explicit spec. `tenant_onboarding` mirrors
`quarter_plan_version`'s approval shape (`approval_status`/`approved_by`/`approved_at`) but is NOT
versioned — onboarding happens once per tenant, no re-planning need, so `tenant_id` is the primary
key directly rather than a separate version table.
Migration comment explicitly flags: `cooldown_until`/`usage_log` seed empty, N1 writes nothing real
into them — the real writer belongs to a future N7/N8-scoped issue. Repeating this note here since
AA-330 STEP 0 already found the platform-level `tour_atoms.cooldown_until` has zero writers anywhere
despite being read by the allocator — the per-tenant equivalent must not silently repeat that gap.

### API — `api/routers/admin.py`
- `POST /tenants` (AA-63, modified): `is_active` now `false` at creation (was `true`); response model
  gained an `is_active` field so callers can see it. Docstring records that this function never
  touched `raw_tours` itself — no code to remove there — the "tenant owns raw_tours" assumption
  N1 must not extend lives only in `list_tenants()`/`get_tenant_details()`, untouched here.
- `POST /tenants/{id}/seed-atoms` (new): takes `portfolio_id`, requires `status='finalized'` (400 if
  not), inserts one `tenant_atom_state` row per tour (`ON CONFLICT DO NOTHING`, safe retry). Rejects
  (409) a second call with a *different* portfolio_id than the one already used — prevents silently
  mixing two portfolios' tour lists into one tenant.
- `PATCH /tenants/{id}/angle` (new): validates against `ASSIGNED_ANGLES`, updates every
  `tenant_atom_state` row for the tenant at once (denormalized — angle is a per-tenant decision
  repeated on every tour row, not a separate 1-row-per-tenant table). 404 if seed-atoms never ran.
- `GET /tenants/{id}/mirror` (new): fresh `COUNT(*)` against `tour_atoms` for the tenant's seeded
  tour_ids (never reads `marketplace_portfolios.atom_snapshot` — confirmed not even queried, see
  test). Calls `runway_months()` directly with `posts_per_week` from `POSTS_PER_WEEK_BY_PLAN_TIER`.
  Upsell suggestion: computes atoms needed to sustain the *same* runway at the next plan_tier's
  cadence, additional tours needed via the tenant's own real atoms-per-tour ratio — verified this
  reproduces the issue's own worked example exactly (87 atoms/12 tours/3→5 posts-per-week → "~8
  tour" — see test and live-verify sections).
- `POST /tenants/{id}/gate-a/approve` (new): mirrors `approve_quarter_plan_version()`'s pattern
  exactly (`SELECT...FOR UPDATE`, reject non-'pending' with 409, `approved_by`/`approved_at`).
  Additionally requires `assigned_angle` already set (400 if not) — step 3 must precede step 6. Only
  on success does `shared.tenants.is_active` flip to `true`.
- `GET /tenants/{id}/gate-a/status` (new): read-only status check, 404 if seed-atoms never ran.

### Real pre-existing bug found and fixed (not introduced by N1)
Live-verifying `create_tenant()` against the real dev DB failed immediately:
`NotNullViolationError: null value in column "brand_name" of relation "tenant_brand_rules"`.
`shared.tenant_brand_rules.brand_name` is `TEXT NOT NULL` with no column default (confirmed via
`information_schema`), but `create_tenant()`'s existing `INSERT INTO shared.tenant_brand_rules
(tenant_id) VALUES ($1)` has never supplied it — meaning this reused AA-63 endpoint has likely never
successfully created a tenant against the current schema, only discoverable by actually running it,
not by reading the code. Fixed minimally: `INSERT INTO shared.tenant_brand_rules (tenant_id,
brand_name) VALUES ($1, $2)` using `body.name` (already-available real data, not a placeholder) — the
real brand-brief upload flow (`upload_brand_brief()`) overwrites this later if one happens. In scope
to fix here because N1 categorically depends on `create_tenant()` succeeding.
