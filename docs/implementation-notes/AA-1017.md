# AA-1017 — Registry v2 (with AA-1016 tenant AI budget table and AA-900 prompt register table)

Slice A3 of the S262 AI gateway plan (Wave 3). Three migrations and one code PR. No route change, no paid call.

## Decisions

- **Migration numbers: 321 and 322 swapped against the plan.** The plan wanted "one PR with 320 + 322, a separate one
  for 321 (risky)". The CI Migration preflight refuses a PR whose file is not `main max + 1`, so 320 + 322 without 321
  cannot pass, and a 321-only PR first cannot either. The risky connection migration is therefore the LAST number:
  `320_llm_registry_v2_families_params.sql` + `321_tenant_ai_budget_prompt_registry.sql` (one migration-only PR), then
  `322_provider_connection_v2.sql` (its own PR, stacked on the first, independent review). Every mention uses the new
  numbers (invariant.py's comment said "321" for failure_domain: now 322).
- **Family = the maker** (ADR 0009 §3): `shared.llm_model_family` keyed by `anthropic`, `openai`, `cohere`, `typesafe`
  plus `amazon`, `meta`, `moonshot` (no catalog row yet). `llm_model_catalog.family` is nullable, backfilled from
  `vendor`, FK NOT VALID then VALIDATE; code reads `coalesce(family, vendor)` (`CatalogModel.family_key`). Not NOT NULL:
  older tests and TripPlanner insert catalog rows without it.
- **Capabilities stay on the catalog row** (they already existed, migration 304, never read). Keys read:
  `forced_tool_choice`, `prompt_cache`, `cache_min_tokens`, `effort_default`. Unset = the old marker rules. No
  family-level capabilities and no per-deployment override yet (one source is enough while every row is `{}`).
- **stage_model_params precedence**: call site (fields in `LLMRequest.model_fields_set`) -> row -> protocol default;
  `min_output_tokens` raises only a non-explicit max_tokens. Applied once in `_call_catalog_model`, so every catalog
  path (plan, S2 vendor, catalog fallback) sees it. Empty table -> the same object (identity), proven byte-identical by
  the golden tests. Effort goes to the Anthropic Messages API as `effort_by_stage[stage]` on a copy of the deployment's
  request_defaults; Converse / OpenAI send no effort or reasoning field (AA-803: a probe must prove the field first) and
  say so once (`stage_params_not_applied`). Legacy keys (haiku / sonnet) read nothing.
- **Provider kinds kept out of LLM dispatch at the module boundary**: `fetch_connections(conn, llm_only=True)` default,
  so the cache behind `registry_rows_sync` / `get_connection_sync`, the reconcile, the probe job and the admin LLM
  listing see LLM kinds only; `resolve_api_key` refuses a provider row; `llm_availability` and `invariant` filter by
  kind in SQL. Provider clients read their own row with `connections.provider_connection(db, key)` (never raises).
  `BUILTIN_PROVIDERS` mirrors the 322 seeds (a test compares them with the SQL); it is separate from
  `BUILTIN_CONNECTIONS` so `connection_or_builtin` never returns a provider row.
- **Per-kind secret guard**: LLM kinds keep `^aa-llm/<env>/<name>$`; typesafe / dataforseo / geoapify accept only
  `^aa-cis/<env>/<kind>$` (their existing secrets, any env), bedrock_guardrails none. Hosts per kind in code and in the
  CHECK (the LLM hosts were code-only before). `credential_env` is now only on an openai row (was a code rule).
- **D9**: `secret_name`, `base_url` (and `credential_env`) UPDATE revoked from cis_app; `access_state`, `last_probe_at`
  (gateway writes, AA-1018 part 2) and `daily_credit_limit`, `low_balance_usd` (admin limits) granted. The PATCH body
  keeps `secret_name` / `base_url` fields only to refuse them with a readable 422; catalog prices: `set_catalog_price`
  raises `CatalogPriceReadOnly` (422) before opening a connection; `enabled` stays editable.
- **Provider settings precedence row -> env -> constant**: Jev (`decide.jev_endpoint`: base_url + `/v1/systemone`,
  timeout_s, max_retries + 1 attempts; loaded with the question config, 20 s TTL, own query, never raises), Jev low
  credit (`jev_credit.low_credit_threshold`), DataForSEO low balance (`admin_llm_ops.dfs_balance_threshold`), Geoapify
  daily credits (`geocoder.daily_credit_limit` / `refresh_daily_credit_limit`, refreshed by place_geocode,
  place_relocate, place_shape, the admin shape estimate and the Providers page). Seeds equal today's constants (3 s,
  3 attempts, $3, $10, 2500); no Terraform env overrides these (checked in Infra `main`).
- **Provider rows on the Providers page** (`GET /admin/ai-gateway/providers`): the Jev / DataForSEO / Geoapify rows keep
  their sources (estimate, snapshot, geocode log) and take the registry row's key, label, enabled, failure_domain,
  access_state, balance_source (`from_registry: true`); a row switched off in the registry shows `disabled`. Geoapify's
  `enabled` stays "is the configured geocoder".
- **TRUNCATED**: `errors.TRUNCATED`, `TRUNCATED_STOP_REASONS`, `reply_class()`; call_log imports the set from errors.
  Not a failure: no circuit count, no raise; the ledger already writes status / error_class `truncated` (319).
- **Readiness 322** (strict prefix 320-322). Each new read also falls back when its column is missing
  (UndefinedColumnError -> the old SELECT), so a deploy before the apply degrades to today's behaviour instead of
  failing; readiness reports it.
- **tenant_ai_budget**: `monthly_usd` NULL = unlimited, `alert_pct` 100, `approval_pct` 150 (>= alert), `hard_stop`
  false; FK to `shared.tenants` ON DELETE CASCADE; cis_app SELECT/INSERT/UPDATE/DELETE; in the erasure inventory
  (delete) and the RLS catalogue allowlist (CIS only). `approval_pct` is an addition to the plan's column list
  (AA-1016's 150 % approval step), so the enforcement slice needs no migration.
- **prompt_version**: (stage, version) PK, `prompt_sha256` hex, `source_path` (no `..`), UNIQUE (stage, sha);
  cis_app SELECT only (rows by migration / the AA-900 gate).

## Changed

- Migration 320 also adds `llm_role_config.route_deadline_s` (NULL, 1..3600, migration-only) and the deployment
  `api_style` CHECK (the catalog's list).
- `api_style` on a deployment is honoured in `_dispatch_target` (NULL = the catalog's).
- The LLM connection listing shows the 322 fields and `editable_fields`; provider rows can be PATCHed by key for
  `timeout_s`, `max_retries`, `notes`, `daily_credit_limit`, `low_balance_usd` only (no switch: their clients do not
  read `enabled`).
- Tests updated for the new contract: s4 admin connection tests (secret edits now refused), s2 grant test (322 revoke
  / grant), 304 / 306 / 309 integration tests (322 in LATER, re-revoke after re-running 310, provider rows moved aside
  before a 304 re-run because 304's closing guard refuses non-`aa-llm/` secrets), 304 closed-lists unit test (LLM kinds),
  catalog price audit test (switch only), providers API stubs (async thresholds).
- `docs/api/openapi.json` regenerated with fastapi 0.161.1 / pydantic 2.14.1 (the pinned versions).

## Tradeoffs

- Kept `vendor` (free text now) instead of dropping it: TripPlanner reads the catalog and the admin shows it.
- No family-level capability table: one place (the catalog row) until a second model of a family needs the same value.
- Effort / reasoning_mode not sent on Converse: the request shape for Bedrock is unproven without a paid probe; the
  table can hold it and the log says it was not applied.
- `served_roles` backfilled but not enforced: enforcing it is the D10 route change (account_route removal), not here.
- Provider rows are enabled at seed (they are in use); `enabled` is informational for them in this slice.
- The PATCH body keeps `secret_name` / `base_url` (refused) so the current admin form shows a clear error until the
  C4 UI makes the fields read-only.
