# AA-1025 H2 — capacity S12 (lines, TPM limiter, backpressure, wave pause)

Lane l2-h2-capacity, S265 (03/11/2026). Plan row: root `docs/audits/2026-11-01-S263-gateway-gap-audit/plan.md` H2
(RW-12 S12); design source: the approved capacity plan `docs/audits/2026-10-31-S261-llm-capacity-plan/README.md`
§2.2-§2.3, §5.1 and root ADR 0009 decisions 4-5.

## Decisions

- **Three lines, assigned by job kind.** `prod` (tenant work, anything outside a job), `bulk` (waves and catalogue
  backfills), `dev` (stage `adhoc_*`, eval runs, the probes). One explicit table `capacity.KIND_LINES` lists every
  registered kind (None = no LLM call); a unit test fails when a new kind is registered without an entry, so an LLM
  kind cannot bypass the backpressure silently. Classification read from each job module's imports; a wrong entry is
  benign either way (a held non-LLM kind only waits during an incident; an unheld LLM kind only misses backpressure).
- **TPM limit = data per connection or per (connection, model)** in a new table `shared.llm_capacity_limit` (348),
  not columns on `llm_provider_connection` / `llm_model_deployment`: a new table is an expand file, and the model level
  is the unit AWS meters. `model_key '*'` = the connection.
- **Reservation = prompt chars / 4 + max_tokens** (the capacity plan's "TPM giữ chỗ"; the same estimate as the central
  budget). Reservations stay in the 60 s window (not refunded with the real usage): conservative, simple.
- **Waiting, not failing.** A call that does not fit waits until older reservations leave the window: prod / dev up to
  65 s (one window + margin: request N+1 always gets through), bulk up to 180 s. Only past that `LimiterSaturated`
  (throttled: the route moves on, a job retries with backoff) — the existing limiter's error, so no new error path.
- **Bulk yields to prod** two ways: bulk may hold at most `bulk_pct` % (default 50) of a limit, and a bulk (or dev)
  call waits while a prod call waits on the same limit.
- **Tokens reserved before the concurrency slot** (`breaker.limit`), so a call waiting for tokens holds no semaphore.
- **No estimate, no reservation**: embeddings (metered by requests: `rpm_limit`) and the admin's connection test (a
  probe must never wait).
- **"Prod circuit" is explicit**: `prod_guard` on a limit row names the connection (its derived connection circuit)
  or one deployment (its circuit). Not "any open circuit": acc3 has been refusing since 29/10 (Error 002) and the
  routes fall back; holding on any circuit would stall every LLM job on Dev. No row is seeded, so nothing changes on
  Dev until the tech lead marks a guard.
- **Hold rules** (`capacity.Hold.lines`): guard OPEN → prod + bulk kinds wait; guard still refusing (half-open,
  nothing answered since) or `bulk_paused` or a staff-paused wave → bulk kinds wait; this process's TPM waits → that
  line's kinds wait 30 s (prod pressure holds bulk too). Only a reservation that really slept counts as a wait
  (review fix: two monotonic reads always differ, so `now - started > 0` made every covered call hold claims). Dev kinds (the probes) are never held, and prod kinds are
  released at half-open, so a real call can still close the circuit.
- **Backpressure in the claim = filtering the caps** passed to `queue.claim` (same seam as the background-kind rule,
  `claim_caps_for`); `queue.claim` SQL is unchanged. Held jobs stay `queued`.
- **Wave pause as columns, status stays `open`** (349: `paused_at`, `paused_by`, `pause_reason`). A new status would
  have made the deploy gate, the retention scheduler and the writing-memory miner (all `status = 'open'`) treat a
  paused wave as gone. The wave check does not end a paused wave (its jobs wait in the queue).
- **Auto pause / resume by the worker** on each refresh of the DB hold (10 s): pause every open, unpaused wave while a
  guard refuses or the bulk pause is on (one bell per wave), resume only the waves `paused_by 'capacity'`. A staff
  pause (`POST /admin/waves/{id}/pause`) is never resumed by the worker.
- **The backlog sampler** reads the same DB hold and skips held kinds when it computes starved queued jobs (otherwise
  the queue-age check would page during every hold). It cannot see the workers' TPM pressure (per process).

## Changed (vs. the plan row)

- `booking.job` / `crm.job` not touched: Booking has no AI; the CRM's AI is serialized per agency and its own gateway
  (H1c / F-series). Noted as "if applicable" in the plan.
- No UI card in this slice: the API (`GET /admin/ai-gateway/capacity`) shows the rows, the hold, the held kinds and
  this task's windows; `capacity` is not in `PAGE_WRITES` until a card uses it (the frontend access test requires
  every PAGE_WRITES key to have a control). Follow-up: a Capacity card on AI providers and a paused badge on Waves.
- Dev live proof uses a stub path (`scripts/aa1025_h2_tpm_drill.py`): the real limiter path (`breaker.limit`) on a
  drill model key no route uses, so no provider is called and no real traffic is limited.

## Tradeoffs

- Per-process limiter (like `rpm_limit`): each ECS task enforces its own share; the plan's option (a). A shared bucket
  (DB / Redis) only on its trigger (a service with > 2 tasks, or 429 despite the split).
- Reservations not corrected with the real usage: over-reserves when `max_tokens` is far above the reply length; the
  cheapest fix is the per-stage `max_tokens` (capacity plan §5.4).
- One condition variable for all windows (simple, no lock ordering); contention is low (a reservation is a few list
  operations).
- Holding at kind level, not per wave: a paused wave holds every bulk kind (waves carry no wave id on their jobs).
