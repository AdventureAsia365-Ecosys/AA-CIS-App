# AA-741 — T-series audit: implementation notes

Backlog G1–G15: `AA-Ecosys/docs/architecture/t-series-audit-and-plan.md` §7.

## G1 — tenant_id on every LLM call (S231)

### Decisions
- Tenant travels in a ContextVar (`call_log._current_tenant_id`, `bind_tenant()`), bound by the
  job worker next to `bind_job()` — the same propagation the job id already uses (tasks,
  `asyncio.to_thread`, LangGraph executors copy the context). No signature changes down the graph.
- The worker reads the tenant from the job payload (`job_tenant_id()`): top-level `tenant_id`
  (T2, S1, s1_seo_prefetch) or `context.tenant_id` (T9). `shared.job` has no tenant column.
- **The platform tenant (aa_internal) is never bound.** A-series rows keep `tenant_id` NULL as
  before, so platform dashboards, the Jev verdict cache (keyed by tenant) and existing reports
  behave exactly as today.
- An explicit `tenant_id=` from the caller always wins over the binding.
- `decide()` resolves the tenant the same way, so the Jev allow-list guard, cache scope,
  `decision_log` and Jev's `llm_call_log` row see the real tenant.

### Changed
- `shared/llm_client/call_log.py`: `PLATFORM_TENANT_ID`, `bind_tenant`, `current_tenant_id`,
  `resolve_tenant`; both inserts use `resolve_tenant(tenant_id)`.
- `shared/jobs/worker.py`: `job_tenant_id()`, bind around the handler task.
- `shared/llm_client/decide.py`: `_decide` starts with `tenant_id = resolve_tenant(tenant_id)`.
- Removed `tenant_id=None` at 8 call sites (graph, judge_node, brand_audit_node, flag_fix_node ×2,
  grounding, source_facts, quality_gates t10_judge) and the stale "tenant_id=None on purpose"
  comments. The plan's "9 sites" counted `itinerary_nudge`, which already logs via graph.py, and
  `f10_embed`, which never passed `tenant_id` (it now inherits the binding).
- Not changed: `api/middleware/rate_limit.py` (API usage log, not an LLM call);
  `acp_angle_gate/generate.py` default `tenant_id=None` (its only caller passes the tenant).

### Tradeoffs
- HTTP path (T7 debate / T8 angles run inside the request) is not bound: both already pass
  `tenant_id` explicitly at every LLM/Jev call. Binding in the auth dependency would not work
  anyway — `get_tenant` is a sync `def` run in the threadpool, so its ContextVar set does not reach
  the endpoint. G5 moves T7/T8 into the worker, where the binding applies.

### Should know
- Behaviour change in Jev: inside a tenant job, a decide() on an A-stage question (e.g. the S1
  judge's Jev questions reused by T2) is now gated by the tenant allow-list. Before, it went to
  Jev as "platform" content even for a non-allow-listed tenant (a DPA leak). All 4 active brand
  tenants are on the allow-list, so the pilot is unaffected.
- A T-stage decide() deep in a tenant job that forgot `tenant_id=` is now asked (allow-listed
  tenant) instead of skipped with "tenant stage called without tenant_id".
- Tests: `tests/unit/test_aa741_g1_tenant_binding.py` (15), real-Postgres
  `tests/integration/test_aa741_g1_tenant_attribution.py` (fails with the worker binding removed).

## Pilot finding — intermittent ALB 502 (S231)

### Decisions
- `--timeout-keep-alive 105` in the Dockerfile CMD (ECS api task def has no command override;
  the worker overrides with `python -m worker`, unaffected). 105 > ALB idle timeout 100 s.

### Should know
- Evidence: 1/12 pilot T2 calls → HTML 502 in 0.65 s, nothing in API logs; ALB
  `HTTPCode_ELB_502_Count` 39 (07/10), 1 (09/10), 1 (10/10).
- Linear free-plan issue limit reached in S231, so this is tracked here + an AA-741 comment
  instead of its own issue.

## G1 follow-up — shadow calls lost job + tenant (S231 pilot)

### Should know
- Pilot (T7 slate): 29 `s1_judge` rows with tenant NULL, all `quality_signal.shadow=true`. The
  shadow model runs on a plain `threading.Thread` (deliberately no contextvars, so it never
  writes to the live stream sink) → its `llm_call_log` row had no job_id and no tenant, in jobs
  too. Fix: `_start_shadow` captures `current_job_id()` / `current_tenant_id()` and the thread
  re-binds just those two. HTTP-path shadows (T7/T8 in the request) still have no tenant until
  G5 (AA-764) moves them to the worker.

## Pilot finding — T2 never used the tenant's market keywords (S231)

### Decisions
- `tenant_market_seo` adds the tour's active platform atom places (`v_active_tour_atoms.place`,
  ≥4 chars) to the title places as match terms. segment_research buys demand per atom place, so
  those are the names `search_demand` keywords contain.

### Should know
- Evidence: all 12 pilot T2 runs → `seo_source = admin_us_fallback`, incl. terra-family (UK).
  `tour_spec` takes places from the TITLE only: "CULINARY GEMS OF BHUTAN" → `["culinary"]`, 0 rows
  matched in any market while search_demand has 139 US keywords naming Bhutan places. Trial with
  atom places on the 3 pilot tours: US 69 / UK 51 / DE 21 demand rows for Bhutan, real per-market
  top keywords (DE differs from US/UK). Some noise remains ("national library", "flights to
  ulaanbaatar") — ranked by `rank_keyword_ideas`, judged later by the T2 judge.
- Integration DB never had role `aa_app_user` → migration 203 (`v_active_tour_atoms`) and ~50
  GRANTs failed silently in every integration run, so no test ever ran against that view.
  conftest now creates the role (CI's postgres user is a superuser; a local non-superuser DB
  skips it).

## S270 max_tokens

Phase-0 finding (S270, live on Dev): since route v6 serves Sonnet 5.5 / Haiku 5.5, the tenant writing stages stop on
their token ceiling and the cut replies are billed but unusable. Ledger, last 7 days: `t8_angle_gen` (sonnet-5-5)
7/9 calls `stop_reason=max_tokens` at 2048 (5 billed_unusable, "Expected exactly 3 angles" / "Angle 2 missing required
field(s)"; 2 of 4 live T8 requests ended `pending_goal` with 0 angles); `t9_write` 1/9 at 8000; `t9_repair`
(haiku-5-5) 1/1 at 2048; `t9_faq_filter` (haiku-5-5) 1/1 at 3000.

### Decisions
- One module owns the ceilings and the retry: `services/acp_shared/token_budget.py`. One named constant per stage:
  `T8_ANGLE_GEN_MAX_TOKENS` 4096, `T9_WRITE_BLOG_MAX_TOKENS` 12000, `T9_WRITE_DEFAULT_MAX_TOKENS` 4096 (short
  channels, was 3000), `T9_REPAIR_MAX_TOKENS` 4096, `T9_FAQ_FILTER_MAX_TOKENS` 6000. A ceiling costs nothing on a
  complete reply; only a reply that would have been cut (and thrown away) costs more.
- The retry: a reply whose stop reason is in the gateway's TRUNCATED set (`max_tokens`, `length`,
  `model_context_window_exceeded`), or a provider refusal of a cut reply (gateway class `truncated`, nothing billed),
  is asked ONCE more with `retry_budget()` = double, capped at 24000 (the gateway still caps at the catalog's
  `max_output_tokens` per model). Never a third call.
- The helper takes the caller's `LLMClient().generate` (a callable), not the client, so the AA-927 AST call-site
  registry still finds the `.generate` load in each caller, which writes the rows. No registry entry changed.
- The retry request is `request.model_copy(update={"max_tokens": ...})`: it keeps temperature / model_tier /
  json_schema and marks max_tokens as set by the call site, so a `shared.stage_model_params` row never overrides it.
  (The old T9 `_generate_full` retry built a new LLMRequest and dropped those fields; the writer requests set none of
  them, so no behaviour change there.)
- A cut reply is retried even when json_repair could salvage it (T8 had 2 such): the salvaged last field may be cut
  mid-word. Plain parse failures that are not cuts are NOT budget-retried (T8 keeps its own contract retry).
- Still cut after the retry = a clear failure per caller: T8 raises `AngleGenerationError` ("cut ... twice"),
  FAQ filter raises `FaqFilterReplyError` (the writer falls back to the deterministic list), sentence repair raises
  `SentenceRepairError` (the caller falls back to the full rewrite), FAQ regeneration returns no pairs (old FAQ kept,
  F16 reports it), SEO fit returns no values (the writer's own kept), the T9 writer returns the cut text and the
  F0_complete gate holds the piece (as before).
- No migration: `shared.llm_role_config` has no max_tokens column. `shared.stage_model_params.max_tokens` exists
  (migration 320) but a call site's explicit max_tokens wins over it by design, so the ceilings stay in code.

### Changed
- `services/acp_angle_gate/generate.py`: 2048 -> `T8_ANGLE_GEN_MAX_TOKENS`; `_generate_once` runs through
  `agenerate_with_budget_retry` (gateway call still in `asyncio.to_thread`); the cut reply's row via `record_call`;
  the returned cost covers both calls.
- `services/acp_content_writing/generate.py`: channel ceilings from token_budget; `_generate_full` uses the helper
  (factor 1.5 / cap 16000 -> x2 / cap 24000); `repair_sentences_detailed`, `fit_seo_fields`, `write_faq` (t9_repair)
  use it too, `_MAX_TOKENS` 2048 -> 4096. `_record_t9_write_call(truncation_retry=)` -> `signal_extra=`.
- `services/acp_content_writing/faq_filter.py`: `MAX_TOKENS` 3000 -> 6000 (the contract smoke job imports it), helper.
- `api/routers/admin_content_quality.py`: admin sentence suggestion (stage t9_repair) 400 -> `T9_REPAIR_MAX_TOKENS`.
- Tests: new `tests/unit/test_aa741_s270_max_tokens.py` (floors per stage, retry_budget, helper: ok / cut->ok / cut
  twice / retry raises / truncated refusal once / twice / other error, every stage's path); budget asserts updated in
  test_aa768_s233_completeness, test_aa790_t8_round8, test_aa769_sentence_actions, test_aa802_silent_correction.
- CONTEXT.md: the budget retry is two responses and two rows.

### Tradeoffs
- `attempt_no` is NOT overridden on the retry row. It is the gateway's attempt position inside one request and
  route_watch reads `attempt_no > 1` as a fallback rung; writing 2 there would show every budget retry as a fallback.
  Each of the two requests is its own gateway request (its own `request_id` / `route_trace`); the pair is linked by
  `quality_signal.budget_cut` (first) / `truncation_retry` + `max_tokens` (second) and the same request ids.
- Ceilings not measured per channel: one 5.x head-room step (x1.5-2) over the S270 ledger, then the retry covers the
  tail. Re-measure after a week of 5.x traffic (count `quality_signal ? 'budget_cut'` per stage).
- FAQ filter has a 60 s step timeout (`TIMEOUT_S`); a retry on a slow model can run into it, and then the writer gets
  the deterministic list, as on any other filter failure.

### Should know
- Cut rows carry `budget_cut: true, max_tokens, retry_max_tokens` and no ok-rate key; their status is derived from the
  stop reason (`truncated`). A reply still cut after the retry is logged by the caller's usual path (T8 / FAQ filter:
  `billed_unusable` row).
- `faq_answer_fit` (t9_faq_answer_fit) and the T10 judge were not in the S270 ledger finding and are unchanged.
