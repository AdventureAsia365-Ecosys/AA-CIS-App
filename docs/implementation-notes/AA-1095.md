# AA-1095 — Bedrock chat models served from acc1 while AWS blocks acc3

Tech lead decision S278 (12/11/2026): AWS refuses the gateway's chat models on acc3 at account level; acc1 answered
every one of them through its `global.` inference profile. Serve Bedrock from acc1, keep acc3 configured behind it.
Root ADR 0001a, Note S278. Three PRs in this repo's wave: the migration (406, its own PR, MIG-4), the code (this
notes file), and an AA-CIS-Infra PR (role + env); the route switch is a root run-script.

## Decisions

- **acc1 is data, never a key in code.** The connection `acc1` is a registry row (migration 406: assume role
  `AA1-Bedrock-Invoker`, ExternalId, region us-west-1, account ID from the task env `BEDROCK_ACCT_PAYER`). The code
  change is the env allowlist (`connections.ACCOUNT_ID_ENVS`) plus the account directory / cost pages reading the
  registry for other assume-role Bedrock connections. `tests/unit/test_aa998_no_acc1_runtime.py` stays as it is.
- **No catalog `bedrock_profile_ids["acc1"]`.** Routing reads the deployment rows (`vendor_route.deployment_plan`);
  the older replay tests pin exact catalog profiles (367); TripPlanner, which reads the profiles, never calls acc1.
- **Seeded off, priority 90.** Behind every live deployment (Dev 10-30) and ahead of the Anthropic API rows at 100
  (376's re-run guard refuses an AWS row sorting after them). Each acc1 row's `enabled` = catalog AND the acc3 row,
  so no candidate model becomes routable by the migration.
- **Route order per family, one route-control version** (`api/services/llm_family_order.py`, pure):
  Claude = Anthropic API, then acc1, then the other AWS rows (acc3); GPT on Bedrock = acc1, then acc3; order mode
  `model_first`. A Bedrock GPT model has no OpenAI API deployment of its own (an OpenAI connection serves only
  provider='openai' rows), so the earlier "OpenAI API group" was always empty and is removed (review fix pass). The existing preset `prefer_anthropic_api` cannot express it (it
  would give anthropic, acc3, acc1 and leaves GPT alone). The run-script that saves it is in the root repo
  (`tools/llm/aa1095_acc1_route_order.py`), so no CIS script names the connection.
- **Replay tests of 366 / 376 / 383**: their bodies check `attempt_cap`, which counts every deployment row on or
  off; after 406 those re-runs count acc1 rows that did not exist on Dev when they ran. Narrowest fix: each replay
  sets later deployment seeds aside inside its transaction (`tests/integration/_later_deployments.py`), guarded by
  `tests/unit/test_aa1095_later_deployment_seeds.py`. Applied migrations and the runtime rule are untouched.

## Tradeoffs

- The static `attempt_cap` count grows by one per model with an acc1 row, so some chains report more than 6
  possible attempts. The route control treats them as existing warnings (the rows exist before the save), never a
  blocking error. At run time a refused acc3 row is skipped by the circuit at 0 USD and is not an attempt, so a Claude
  model makes at most two real attempts (Anthropic API, acc1).
- GPT in model-first order: Bedrock acc1, then acc3 (skipped at 0 USD while it refuses), then the OpenAI API twin on
  the chain. If acc3 starts answering again it is tried before the OpenAI API (AWS preferred); revert the
  route-control version or switch acc3 back to first when its case closes. This differs from the tech lead's wording
  ("acc1, the OpenAI API, then acc3 behind or disabled") once acc3 recovers. Rejected for this wave: switching the acc3
  GPT deployments off (the literal "disabled"). There is no audited per-deployment switch today (only connection
  switches and route-control versions), a raw UPDATE would bypass the audit and the one-click revert, and while acc3
  refuses the two orders make the same calls. Recorded in root ADR 0001a Note S278 and in the PR body for the tech
  lead's OK; a follow-up can add an audited deployment switch if he wants acc3 GPT off.
- acc1 has no Cost Explorer reader (left out: no new paid or cross-account read); its spend line is the ledger
  estimate.

## Should know

- Order: Infra apply (acc1 root locally, aa365 by CI) -> migration 406 -> this code PR deployed -> root run-script
  (preview by default, `APPLY=1` to save). Before the run-script the connection is off and nothing changes on Dev.
- Rollback: revert the route-control version (one click), switch `acc1` off; a forward migration deletes the rows.
- The account directory reads the registry (cached); with the registry unreadable the satellite shows as
  "Retired account" exactly as before.
