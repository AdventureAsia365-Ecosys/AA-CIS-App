# AA-1002 — LLM gateway slice S1: connection registry + model deployments

Design: the S258 "AI / LLM gateway" section (approved), slice S1: "connection registry + deployment table (schema +
backfill) + open CHECKs, every new path disabled, no behaviour change". Refs AA-642 (gateway epic).

Two PRs, in this order (S237 D8, migration-file-only PR first):

1. `feat/aa1002-llm-registry-migration` — `api/migrations/304_llm_connection_deployment.sql` only.
2. `feat/aa1002-llm-registry-read` (stacked on 1) — read side, admin listing, tests, these notes.

## Decisions

- **One contract file, not an expand file.** Widening three CHECKs on existing tables and the guard DO blocks are
  contract by the AA-993 classifier, and no CIS file uses the `-- migrate: expand` header yet. Splitting into an
  expand file (tables + backfill) and a contract file (CHECKs) was weighed: two numbers for a small, rarely-written
  set of tables is not worth it. Consequence: DB Migrate `apply` by hand with the job tables idle (no auto-apply).
- **No account ID, no ARN in the data.** The repo is public. The acc3 connection stores `account_id_env =
  'BEDROCK_ACCT_PRIMARY'` (the env var the code already reads) and `role_name` instead of a role ARN; the ARN is built
  at runtime (`ProviderConnection.role_arn()`). `account_id` (12 digits, CHECK) is for a later admin edit (the DB is
  private).
- **The OpenAI key stays in the task-definition env until S9.** The correction list requires `secret_name` to be
  `aa-llm/%`; today's key is not an `aa-llm/` secret. Instead of a prefix exception, the row names
  `credential_env = 'OPENAI_API_KEY'` from a closed list (CHECK + `connections.CREDENTIAL_ENVS`). S9 copies the key
  to `aa-llm/dev/openai-direct` and drops the env.
- **Secret name pattern is stricter than `LIKE 'aa-llm/%'`:** `^aa-llm/<env>/<name>$` with lower-case letters,
  digits and hyphens (no `..`, no ARN, no extra path level). Same regex in the CHECK and the code (parity test).
- **base_url**: the CHECK only requires a plain https URL and NULL for bedrock / mock; the host allowlist per kind
  is a code constant (`BASE_URL_ALLOWLIST`), so adding Azure resources or a Foundry host is a code review, not a row.
- **Deployment key = (model_key, connection_key)**, no surrogate id: one wire id per model per way in, idempotent
  backfill with `ON CONFLICT DO NOTHING`, and an admin edit is never overwritten by a re-run.
- **FK model -> catalog is ON DELETE CASCADE**: integration tests (259, 240) delete and re-insert catalog rows; a
  RESTRICT FK would break them, and a deployment of a deleted model means nothing. Connection FK is RESTRICT.
- **Deployment `enabled` = "today's code takes this path"**, not a copy of the catalog's `enabled`: the catalog row
  stays the model switch (gpt-4.1 is retired in the catalog; its openai-direct deployment is enabled). acc2
  deployments are enabled only for embed rows (converse on acc2 is refused by `_call_catalog_model`; legacy
  acc2-native Claude runs only with `LLM_LEGACY_ACC2_NATIVE=on`).
- **Legacy haiku / sonnet deployments come from the code constants**, inserted before the profile backfill, because
  `_legacy_chain` never reads the catalog's profiles. A unit test pins the SQL constants to
  `bedrock_satellite._PROFILE_ID_*` / `pricing.BEDROCK_*`.
- **New paths seeded disabled**: `anthropic-direct` (secret `aa-llm/dev/anthropic-direct`, no adapter before S2) and
  `bedrock-llm-org` (role `AA-LLM-Invoker`, account and ExternalId unknown until S1-infra). No `azure_openai` row:
  the kind exists in the CHECK, a row is added when there is an endpoint.
- **`capabilities jsonb` added empty.** The code still holds the facts (`_NO_FORCED_TOOL_CHOICE_MARKERS`,
  `supports_temperature`); seeding a second copy now would drift. S2 / S3 fill it with the code that reads it.
- **`family` column not added** (listed in the design table): nothing reads it before S3; S3 adds it with the
  legacy-key alias work.
- **Grants: cis_app SELECT only.** The S4 PATCH (admin only, audit_log) adds UPDATE on the connection table in its own
  migration. No tripplanner grant.
- **Admin listing is admin-only** (`ai.admin` POLICY entry, like the catalog / route writes): it names secrets,
  roles and endpoints. It reads no secret and no key env value (only whether the env var is set).

## Changed (vs. the design's S1 file list)

- Not done in S1, on purpose (each changes behaviour or output, which S1 must not):
  - `call_log` passing `provider` / `account` explicitly — changes the logged values; moves to S2 (adapter) / S6.
  - `shared/cost_guard.py` `PROVIDERS += anthropic, azure_openai` — the admin overview and budgets endpoints iterate
    `PROVIDERS` (new keys in their output, and `day_spend` has no SQL for them). The DB CHECK is widened now so S2 / S10
    can add the code without a migration.
  - `docs/generated/llm-routes.md` — no such file or generator exists in the repo; the route snapshot proof is the
    integration test `test_first_enabled_deployment_is_the_path_the_gateway_takes_today`.
- Jev (`typesafe`) stays outside the registry in S1 (no connection kind for it in the CHECK).

## Tradeoffs

- Env-var columns (`account_id_env`, `credential_env`) are two extra columns with closed lists, instead of a prefix
  exception in the secret CHECK or an account ID in a public file. Adding a new env name needs a migration + code.
- A data-driven backfill (from `bedrock_profile_ids`) follows whatever Dev holds today rather than a hand list, so the
  file cannot disagree with Dev; the post-guard refuses the apply if a catalog path ends up without a deployment.

## Should know

- **Apply order**: PR 1 (migration only) merges; the migration-sync bot opens the Infra copy PR (do not copy by hand,
  AA-993 M3); DB Migrate `check` then `apply` of `cis/304_llm_connection_deployment.sql` with `shared.job` /
  `booking.job` idle (contract file); then PR 2. PR 2 is safe before the apply too (the listing answers
  `schema_ready: false`), but follows the D8 order.
- **No behaviour change**: `tests/unit/test_aa1002_no_behaviour_change.py` — static (no call-path module imports
  `connections` / `deployments`; a new gateway module must be classified) and runtime (a Converse call and a legacy
  haiku call produce byte-identical provider requests and responses with an empty vs a contradictory registry, and the
  registry loader is never called).
- **TripPlanner**: `bedrock_profile_ids` / `account_route` untouched; `capabilities` is a new column on a table TP
  SELECTs by column name (no `SELECT *` in the TP gateway).
- Integration tests ran on a temporary superuser cluster (lesson S246): `test_aa1002_migration_304.py` 25 passed;
  with the X1 / RLS standing checks (244/245/246, x1 privileges, RLS catalogue) 126 passed. 18 errors in
  `test_aa835_migration_278` / `test_aa847_migration_257` appear when they run after the other catalog tests, with or
  without this change (pre-existing ordering interaction; both pass alone).
- Infra lints run locally on the file: `db/run_migration.py --inspect` (no errors, no warnings) and
  `db/check_migration_ownership.py` (clean).

# Slice S2 — Anthropic Messages API adapter

Design: S258 "AI / LLM gateway" section, slice S2 + the correction list (forced tool / temperature on 5.5 models,
effort explicit, cache tokens folded into `tokens_in`, refusal billed, no server-side `fallbacks`, timeout / retries
per connection, 529 throttled). Branches (local, stacked): `feat/aa1002-s2-migration-306` (migration only, from
`origin/main` after #1159 / #1161) and `feat/aa1002-anthropic-messages-adapter` (306 + code).

## Decisions

- **Selection rule (S2): first enabled deployment wins, and only Anthropic is registry-driven.**
  `vendor_route.vendor_deployment_for(model)` takes the model's enabled deployments whose connection is enabled,
  ordered by `(priority, connection_key)`; when the first is on an `anthropic` connection the adapter serves the
  model, otherwise today's code runs unchanged (a Bedrock / OpenAI row ahead means "today's path", not a
  registry-driven call: spreading a route over every deployment is S3). One way in per model per attempt; a failed
  Anthropic attempt moves the route to its next MODEL, as today (no same-model fallback before S3).
- **Pinned probe**: `model_tier = "<model key>@<connection>"` calls that one deployment (deployment and connection
  enabled). Stage routes cannot carry a pin: `_call_route` skips any key the catalog does not know. This is how the
  tech lead probes the key without moving any stage.
- **Kind name**: the connection kind is `anthropic` (migration 304's CHECK); the issue text's "anthropic_api" is the
  same thing. No new kind.
- **Seed behind Bedrock (migration 306)**: one `anthropic-direct` deployment per Anthropic Converse catalog row,
  wire id derived from its acc3 profile (`global.anthropic.claude-sonnet-5-5` -> `claude-sonnet-5-5`), priority 100
  (acc3 is 10), enabled; the connection stays disabled. So the admin switch alone never moves a route (tenant data
  scopes are S5's decision); making the API primary for a model is a deliberate priority change. Legacy keys get no
  row (S3 aliases them).
- **The admin switch** `PATCH /admin/llm-connections/{key}` takes `{"enabled": bool}` only (`extra=forbid`), only on
  `anthropic` connections (the gateway reads no other kind's flag before S3, so flipping acc3 would mislead), refuses
  a policy problem or an unreadable secret when enabling (the resolver reads the key and drops it), writes the row and
  one `acp_shared.audit_log` row (`llm_connection_changed`, before/after, secret NAME and base URL) in one
  transaction, then drops this process's caches. Migration 306 grants cis_app UPDATE on `enabled`, `updated_at`,
  `updated_by` only (column grant; a parity test ties the grant to the UPDATE statement).
- **SDK, not raw HTTP**: `anthropic==2.3.0` (2.x sends API version 2026-10-21, which refuses temperature / top_p /
  top_k on every model, so the adapter never sends them). `base_url` is always passed explicitly (an
  `ANTHROPIC_BASE_URL` env cannot redirect the key) and the key explicitly (never `ANTHROPIC_API_KEY`).
- **Timeout / retries**: per connection; NULL = 300 s read / 10 s connect and 1 retry (the Bedrock client's
  values), never the SDK's 600 s / 2. The SDK honours `retry-after(-ms)` on its retries; the final error carries
  `retry_after_s` for the S4 breaker.
- **Errors**: `AnthropicAPIError` sets `llm_error_class` from the status, in this order (review S258): 429 / 529
  or `rate_limit_error` / `overloaded_error` -> throttled (never read from the text, so a rate limit whose message
  says "billing" keeps its retries); 402 / `billing_error` -> quota_exhausted; on 400 / 402 / 403 only, the credit /
  spend-limit wording -> quota_exhausted, read through `errors.classify_text` (one pattern list); 401 / 403 ->
  access_denied; else other. The errors.py patterns gained the Anthropic error types and that wording
  (`authentication_error`, `permission_error`, `billing_error`, `credit balance is too low`, `api usage limit(s)`,
  `spend(ing) limit`, `rate_limit_error`, `overloaded_error`), so a stored job error classifies the same, including a
  workspace spend-limit 400 ("You have reached your specified workspace API usage limits", tested). Two edge cases
  differ in the stored text only (the in-process class, which the job runner reads, is right): a 403 whose text also
  has the spend-limit wording (in process quota_exhausted, stored access_denied: both account-level), and a 429 whose
  text says "spend limit" / "API usage limits" (in process throttled, stored quota_exhausted, since the stored
  patterns check quota before throttling; Anthropic's rate-limit messages do not use that wording). A 401 also drops
  the cached key + SDK client (`forget_connection`).
- **Credential env per kind** (review S258): `connections.CREDENTIAL_ENV_KIND` ties each allowed env key to its
  kind (`OPENAI_API_KEY` -> openai); `policy_problems` refuses a credential env of another kind, and the adapter
  refuses any Anthropic row without `secret_name` or with a `credential_env` before reading anything. So an
  anthropic row naming `OPENAI_API_KEY` (writable only by the DB owner) can never send the OpenAI key to
  api.anthropic.com.
- **Structured output**: `output_config.format` json_schema; the schema sent is closed (`additionalProperties:
  false` on every object) with the unsupported keywords removed (min/max, lengths, maxItems, minItems > 1 ...); the
  reply is still conformed to the caller's FULL schema (`_checked_json`). A schema the API cannot express (open map,
  object without properties) falls back to the S251 instruction in the system prompt.
- **Effort**: always explicit when the model takes one: `request_defaults.effort_by_stage[stage]` ->
  `request_defaults.effort` -> the family default (Sonnet 5.5 / 5 / 4.6, Opus 5 / 4.x, Fable: high; Opus 5.5,
  Haiku 5.5: medium), which is what Bedrock Converse runs today (no effort sent there). Haiku 4.5 / Sonnet 4.5 get
  none (a 400). An unknown family with nothing configured sends none and warns once.
- **Logging / cost**: `model_used = "anthropic-api-<model key>"`; `call_log._normalize_model_provider`,
  `catalog.get_model_sync` and `pricing._catalog_rates` strip the prefix, so every caller that logs
  `model=resp.model_used` writes `model = <key>`, `provider = 'anthropic'` without code changes. `account` stays NULL
  (the vendor-API convention, as OpenAI; the cost pages bucket non-Bedrock rows by provider). **Deferred to S6**
  (review S258): the design table gives provider / account = anthropic / anthropic-direct, but every admin page
  reads `llm_call_log.account` as an AWS account key (`accounts.account_name`, `frontend/lib/awsAccounts.ts`:
  anything but acc2 / acc3 shows "Retired account"), so writing a connection key there today would mislabel the
  LLM availability card and the jobs drawer. S6 (cost parity) records the connection with the label change; until
  then one Anthropic connection exists and provider `anthropic` identifies it. `tokens_in` = uncached +
  cache read + cache write; cost = `calc_cost(model_key, …)` (catalog price, cache rates). The model the API reports
  is `LLMResponse.provider_model` (new optional field) and in the `llm_success` log line with the connection, wire id,
  effort and request id. It does NOT reach `llm_call_log` for ordinary callers (they log `model=resp.model_used`
  only); the S2 probe script adds it to `quality_signal` by hand. A column or a gateway-side default is S6 (review
  S258); until then "the model that really answered" is evidence in CloudWatch (`llm_success`) only.
- **Refusal** (`stop_reason == "refusal"`), empty content, invalid JSON or schema mismatch -> `BilledUnusableReply`
  with the billed usage (the gateway's billed_unusable row; the route moves on), a plain RuntimeError when nothing
  was billed.
- **Thinking**: no `thinking` field is sent (model default: adaptive on the 5.5 models, as on Converse today).

## Changed (vs. the design's S2 file list)

- `requirements.txt`: `anthropic` pinned; `openai` NOT pinned here (changing the OpenAI client version is its own
  risk; left for S9 with the OpenAI key move).
- Streaming always (one code path; long outputs never hit a read timeout); live text only for non-structured
  requests, as on every path.
- Deployment price overrides are not applied yet (S6 cost parity); Haiku 5.5's >100K tier, 1-hour cache writes and
  `inference_geo` pricing are not modelled (S6).
- `capabilities` (catalog) is still not read: effort defaults and the no-forced-tool list stay code constants; the
  catalog SELECT does not depend on migration 304 (S3 reads `capabilities` with the alias work).
- `routing_uses_registry` in the admin listing is now `true`.
- Not done (later slices): breaker / limiter (`max_concurrency`, `rpm_limit` unused), data-scope policy (S5),
  `cost_guard.PROVIDERS += anthropic` (S10 — see Should know), admin UI for the switch (S4 ConnectionsTab).

## Tradeoffs

- A registry read on every catalog-key attempt (two in-process caches, 5 min TTL; a failed load negative-cached
  60 s and the last good registry kept) vs. an env kill switch: the issue asks for "one admin toggle", which a task
  definition env var is not. The read never raises (`vendor_route` swallows and logs), so a registry problem can
  only mean today's path.
- Seeding the API deployments behind Bedrock costs one priority change per model before the API carries real
  traffic, but keeps the admin switch harmless and leaves the tenant data-scope decision (S5) open.
- **Registry reload under load** (review S258): both caches reload single-flight (`_load_lock`): when the TTL
  runs out, the first thread reloads and the others wait for it and re-check, instead of each LLM thread opening two
  DB connections. A hung DB therefore holds the waiting threads up to the load timeout (10 s) once per 60 s failure
  window, the same bound a lone thread had.
- **Admin switch lock order** (review S258): enabling reads the secret before the transaction opens (plain SELECT,
  then `resolve_api_key` in a thread); the transaction re-reads the row `FOR UPDATE` and refuses (422 "changed while
  its secret was checked") when kind / auth_mode / secret_name / credential_env / base_url moved in between. A slow
  Secrets Manager call no longer holds the row lock or an open transaction.
- The conftest of `tests/unit` now makes the registry empty by default (no unit test opens a DB connection for it,
  no cross-test cache state); registry tests patch `connections.run_sync` themselves.

# Slice S3 — route spread over deployments, legacy-key aliases, accounts as data (incl. embed)

Branch `feat/aa1002-gateway-s3-route-deployments` (S259). Plan: root
`docs/audits/2026-10-29-S258-aws-org-blueprint/blueprint.json` `ai_gateway.build_slices` S3.

## Decisions

- **Two rollback switches, read per call (ECS env):** `LLM_DEPLOYMENT_ROUTING` default ON (proved identical for every
  Dev stage with today's rows), `LLM_LEGACY_ALIASES` default OFF. Aliases are byte-identical in tests too, but they
  have not run live (every provider is blocked, S259) and the blueprint asks for a live check of one legacy stage
  first: switch it on after that check (`LLM_LEGACY_ALIASES=on` on the api + worker task definitions, AA-CIS-Infra).
- **Plan semantics** (`vendor_route.deployment_plan`): the model's CALLABLE rows (a connection kind + api_style the
  gateway has an adapter for; Anthropic rows only for Anthropic non-legacy models; OpenAI rows only for provider=
  'openai' catalog rows so the S235 gate stays keyed on the catalog row; API-key rows without a policy problem). No
  callable row, or an empty registry = `None` = today's path (S2 code). Callable rows that are all disabled / on a
  disabled connection / circuit-open = `[]` = the model is refused and the route moves on: once the registry describes
  a model it is authoritative (a switched-off acc3 must not be called "because of the fallback").
- **Data scope before S5:** a `vendor_direct` connection is used only when it is the FIRST enabled callable row (the
  admin's deliberate S2 choice); it is never a same-model fallback behind an `aws_only` row. Decided on the candidates
  BEFORE the circuit filter, so an open acc3 circuit cannot promote the Anthropic API row. This closes the S2 "forward
  constraint" (306 seeds enabled Anthropic rows behind acc3 for every Anthropic model, tenant ones included) without
  waiting for S5. A vendor row put first still falls back to acc3 (content moves into AWS, never out).
- **Same model first:** `_call_plan` tries every deployment of the model, then `_call_route` moves to the next model.
  One deployment = its call with its own exception, untouched (byte-identical errors). Several, all down =
  `_all_failed` (LLMAccessDenied when every one was refused at account level). An `UnusableReply` (billed) is the
  model's answer: raised at once, never retried on another deployment (also keeps the AA-927 one-row-per-billed-call
  bookkeeping simple).
- **Breaker hook:** `vendor_route.circuit_open(connection_key, model_key)`, a no-op until S4 sets it.
- **Aliases without contract SQL:** root ADR 0017 makes any INSERT into an existing table (catalog rows, deployments)
  and any constraint change on an existing table CONTRACT, which blocks the auto-apply chain for later expand files
  (lane "reports" owns 308). So 307 is expand only: a NEW table `shared.llm_model_alias` whose targets are the existing
  legacy catalog rows: `haiku` → [haiku], `sonnet` → [sonnet, haiku] (the chain's T1.5a → T2.5a order). A target that
  is a legacy key keeps the legacy wire format (api_style anthropic_native = the InvokeModel Messages body with the
  prompt cache), so the alias path sends exactly what `_legacy_chain` sends; repointing the alias to logical Converse
  rows later is an UPDATE (data), not code.
- **Alias all-or-nothing:** any target the catalog / registry cannot describe → `_legacy_chain` for the whole call;
  `LLM_LEGACY_ACC2_NATIVE=on` → `_legacy_chain` (its acc2-first order is the chain's own). A disabled catalog target
  is skipped. `fallback_used` = served model ≠ the alias's first target (as the chain: Sonnet degraded to Haiku).
  The chain's final error and the S235 GPT-4.1 tail are shared (`_legacy_last_resort`).
- **gpt-6-luna-openai: no alias row.** With deployment routing it already resolves through its catalog row and its
  `openai-direct` deployment; pointing it at `gpt-6-luna` would bypass the S235 gate (keyed on the provider='openai'
  catalog row) or put OpenAI behind a Bedrock model. Leave it to S5 (scopes).
- **Accounts as data:** `bedrock_satellite._SATELLITE_ACCOUNTS` / `_INFERENCE_PROFILES` and `catalog.SERVING_ACCOUNTS`
  are gone. A satellite "account" is the key of an assume-role Bedrock connection; sessions are cached by
  (connection_key, role_arn, external_id, region). `connections.BUILTIN_CONNECTIONS` mirrors the enabled 304 seed rows
  (acc3, acc2, openai-direct; a test compares it with the SQL) and is used ONLY to reach a connection when the
  registry is unreadable, has no row, or the row breaks the policy — never to route. `serving_accounts()` ignores
  `enabled` on purpose: it feeds the no-registry / rollback path (`account_for`), which must stay today's.
- **Embed:** `_targets` = the plan's (connection, wire_id) per model (spread, same model first), else the catalog
  profile on `account_for` (one account per model, as before). `_runtime_for(connection_key)` builds the client from
  the connection: task_role → `bedrock_satellite.native_runtime(conn, read_timeout=30, max_attempts=1)` (the AA-862
  one-attempt client), assume_role → `get_satellite_client`. Body (input_type, output_dimension) unchanged. A second
  deployment of the same model answering is not a route fallback (`fallback_used` stays false).
- **acc2 converse:** a task-role deployment of a converse model runs on `native_runtime` (300 s / 2 attempts, like
  `LLMClient._bedrock`) and answers as provider `bedrock`, model `<key>` (no `satellite-` prefix), as the legacy T1/T2.
- **Wire-id drift guard (review S259):** with routing on, CIS sends `llm_model_deployment.wire_id`, while
  TripPlanner (until S8) still calls `bedrock_profile_ids` / `wire_model`; nothing in the DB ties the two after 304.
  Two guards, no schema change: (1) `tests/integration/test_aa1002_deployment_wire_drift.py` runs after EVERY
  migration in CI: an enabled Bedrock deployment = the catalog profile for its connection (a missing profile is drift
  too), legacy rows = the chain constants, an enabled OpenAI deployment = `COALESCE(wire_model, model_key)`, a 306 seed
  Anthropic row = the acc3 profile without region prefix / version suffix. Mutation-checked with a throwaway
  migration changing `sonnet-5-5`'s acc3 profile and `gpt-6-luna-openai`'s wire_model: 3 of 5 tests fail with the
  drifted rows named. (2) `vendor_route.deployment_plan` logs `llm_deployment_wire_drift` (warning, once per process
  per model/connection/wire/profile) for an enabled Bedrock row whose wire_id differs from the catalog profile of
  the same connection; the call still uses the deployment row (the registry is authoritative). No warning when the
  catalog has no profile for that connection (a new account's row).

## Tradeoffs

- Routing default ON vs OFF: ON gives the registry its meaning now (S4's breaker and the new LLM account need it) and
  the snapshot proves identity for today's rows; the env switch is the rollback. Aliases default OFF: the identity is
  proved only with fakes, and a legacy writer regression would hit 20+ stages at once.
- `[]` (refuse) vs `None` (today's path) when every callable row is off: refuse makes the registry switch real; the
  cost is that a mis-edited registry fails loudly instead of silently using acc3 (`LLM_DEPLOYMENT_ROUTING=off` undoes).
- The built-in mirror keeps a DB outage harmless (lessons: safe defaults must run without the DB) at the price of
  three connection rows living in code; the test pins them to 304.
