# AA-894 scope 2: live interactive ERD in the CIS admin (`/admin/data-model`) — Refs AA-894

Part 1 (AA-CIS-Infra) made the nightly DB Schema Dump produce `erd.json`. This branch adds the reader and the page.
The Infra half of scope 2 (S3 key, IAM read grant, upload on by default) is AA-CIS-Infra `feat/erd-cis-read-grant`.

## Decisions

- **Route `GET /admin/data-model`**, own router `api/routers/admin_data_model.py`, `dependencies=[Depends(staff_policy)]`
  (secret or verified staff Bearer, then POLICY). POLICY `("GET", "/admin/data-model")` = `ops.read`: admin role only
  (viewer, reviewer, content, tenant and the machine principal get 403). `ops.read` because the model is system
  internals (every schema of the shared RDS, owners, RLS, PII tags), like `/admin/infra/status`.
- **Page `/admin/data-model`**, nav Platform › Developer next to API Docs; not under `/admin/platform/*` because
  the Developer pages already live outside it (`/admin/api-docs`). PAGE_RULES admin, BFF `API_READ_RULES` `data-model`
  admin (refused before the backend for any other role).
- **Storage**: bronze bucket (`shared/aws_client/bronze.py`), key `data-model/erd/latest.json` and `previous.json`
  (env `DATA_MODEL_S3_PREFIX`, default `data-model/erd`, no Terraform env needed). The Infra branch moves the upload
  there from part 1's `db-schema-dump/erd/` and grants the task role `s3:GetObject` on exactly those two keys.
- **Errors**: `latest.json` missing (`NoSuchKey`) → 404 "No data model has been published yet"; any other read
  failure, non-JSON, or not format 1 → 503 (the raw error is only logged, by class name). `previous.json` missing or
  unreadable → 200 with `diff: null` (a diff is not worth failing the page). Errors are not cached.
- **Cache**: module-level, per process, 5 min TTL, one `asyncio.Lock` so a burst reads S3 once; `?refresh=1` (the
  page's Reload) re-reads only when the copy is older than 30 s, so it cannot drive an S3 loop. boto3 runs in
  `asyncio.to_thread`. Object size capped at 20 MB (today ~650 KB).
- **Diff** (server side, `diff_models`): tables added / removed / changed; per table columns added / removed /
  changed (type, NOT NULL, DM-6.1 tag, PK / FK / UK flags), PK, FKs added / removed, RLS; FK edges added / removed keyed
  `schema.table:constraint` (constraint names are unique per table only). Same fingerprint → no diff.
- **Response**: `{model, previous: {fingerprint, generated_at, migrations_latest_per_owner} | null, diff, loaded_at,
  cache_ttl_s}`, `Cache-Control: private, no-store` (the browser keeps nothing; react-query holds it per tab).
- **UI** (kit only, in `KIT_CLEAN_FILES`): search over table and column names (every word must match; column hits
  shown on the row), schema filter (`<select>` with `maxWidth: 100%` / `minWidth: 0`, lesson S221), "Show changed
  only", "Table +1" (list narrowed to the selected table and its one-FK neighbours), a diff summary card (removed
  tables / FKs listed by name since they cannot be clicked), the table list with new / changed / PII / RLS markers,
  and the detail: owner app + role, kind, RLS, PK / UK, the change box, a neighbour map (referenced by → table →
  references, each neighbour clickable, cross-app / cross-schema / NOT VALID badges, NOT VALID drawn dashed) and the
  column rows. Desktop: two columns; phone (< 768 px): list, detail in the kit Drawer.
- **Public repo**: tests use an invented model (schemas `alpha` / `beta`); no real table or schema name in code,
  tests or this note.

## Tradeoffs

- **No graph library** (no React Flow / d3 / Mermaid in the bundle): the useful question on a 300-table model is
  "what is this table and what touches it", which the +1 neighbour map answers; a full force-directed graph of every
  schema is unreadable (part 1 already saw that with Mermaid on GitHub). The per-schema Mermaid pages stay the
  whole-schema picture.
- **Diff on the server**, not in the browser: the browser gets one model plus a small summary instead of two
  ~650 KB models.
- **In-process cache, not Redis**: the object is small, reads are rare (admin only) and stale for at most 5 min; two
  api tasks read S3 at most twice per 5 min.
- **Selection is not in the URL** (no `?table=`): `useSearchParams` would need a Suspense boundary on a static page;
  can be added when someone needs to share a link to a table.
- **List capped at 400 rendered rows** (more than the whole model today); the search narrows the rest.

- `previous.json` appears only after the first structural change following the first upload; until then the diff card
  says there is nothing to compare with.

# AA-894 Done-when "a bot PR shows an FK change as a diff": migration 268 (S247) — Refs AA-894

The FK change the DB Schema Dump bot PR (and the `/admin/data-model` diff card) shows is a real, useful one, not a
throwaway: `gold_aa_internal.published_tours.quality_score_id -> silver_aa_internal.quality_scores(id)`.

## Decisions

- **Which FK.** A scan of every `*_id` column in the CIS schemas without an FK in the live schema reference found
  this one as the clearest real gap: schema v2 (002) declared `REFERENCES quality_scores(id)`, schema v3 (003, which
  created the live tables) wrote a plain `UUID`, so the key was lost. Both tables are CIS-owned (KEY-1 allows and
  DM-4.1 asks for in-owner FKs). Other candidates were left alone on purpose: `geo.*.tour_id` (geo is keyed by
  `source_id` by design, ADR 0007), `shared.llm_call_log.*` (262k-row log, retention job), `notifications.tenant_id`,
  `angle_gate_request.atom_id` (atoms are rebuilt), job ids on logs.
- **ON DELETE SET NULL**, not NO ACTION: a revalidation DELETEs a version's `quality_scores` rows and INSERTs new ones
  (`admin_pipeline.py` revalidate, `revalidate_job.py`). With NO ACTION that DELETE would fail for a published
  version; with SET NULL the pointer becomes NULL instead of dangling.
- **Repair before VALIDATE** (step 1): a dangling pointer is re-pointed to the version's current score row (same
  `generated_content_id`, latest `evaluated_at`, the row the admin tour view reads), else NULL. The stored
  `quality_score` number is left as published. The read-only dry run (root `.tmp-session/aa894_fk_orphans.py`)
  counts exactly what this step would do; expected a no-op on Dev.
- **Index** `idx_published_tours_quality_score_id` (QRY-2; SET NULL looks rows up by it on every score delete).
  Plain build: the table is ~900 rows (MIG-10).
- **Lock-safe**: `SET LOCAL lock_timeout '5s'` / `statement_timeout '15min'` (MIG-9), ADD ... NOT VALID then
  VALIDATE in a second statement (MIG-11). DB Migrate sends the file as one transaction, so the ADD's SHARE ROW
  EXCLUSIVE lock lasts to COMMIT, through a millisecond scan; readers never wait.

## Changed

- New `api/migrations/268_published_tours_quality_score_fk.sql`, `tests/integration/test_aa894_migration_268.py`
  (9 tests: replay state, pre-268 + twice, dangling repair (re-point / NULL / valid left alone / no pointer), FK
  refuses a missing score, score delete nulls the pointer, guards: different constraint under the name, a second FK
  on the column, non-uuid column, file rules).
- No code change: no writer sets a pointer to a missing row (export takes the id from `quality_scores` in the same
  query); no reader needs 268, so no `REQUIRED_CIS_SCHEMA` bump.

## Tradeoffs

- Re-pointing a dangling id vs nulling it: re-pointing keeps "the accepted score row of this version" answerable
  through the column, which is what it is for; the cost is that the stored `quality_score` number may differ from the
  new row's `score_overall` (it stays the number that was published).
- Revalidation still nulls the pointer of a published version instead of moving it to the new row. Moving it would be
  a code change in two revalidation paths; left as a follow-up, the FK keeps the column honest meanwhile.

## Should know

- Order: copy the file byte-identical to AA-CIS-Infra `db/migrations/cis/`, merge that, DB Migrate `check` → `apply`
  (jobs idle), then the DB Schema Dump opens the bot PR with the new FK line and ERD edge; `latest.json` /
  `previous.json` then give the admin page a non-empty diff (`fks_added`, `edges_added`).
- Apply 268 only after 265, 266 and 267 are applied on Dev: readiness compares max(version) with
  `REQUIRED_CIS_SCHEMA`, so an early 268 would hide a missing 265-267 (review, S247).
- With the FK, a revalidation that deletes the score row between the export's SELECT and INSERT makes that export
  fail with a foreign key violation (it used to store a dangling id); running the export again fixes it.
- Local integration runs need `app.tenant_id` set for the test rows when the test role is not a superuser (CI is).
- Page evidence for the other Done-when line (S247), kept outside this repo: the refusal is captured live on the
  production admin host with the E2E Cognito staff user (role reviewer): the page redirects 307 to `/admin/review`,
  the BFF answers 403 "Only an admin can do this", the API 403 "lacks the 'ops.read' permission". The owner view at
  1440 / 400, light / dark is a local `next dev` render of main with the data call answered by interception with the
