# AA-1168 follow-up — the AI disclosure wording as a setting (CIS)

Lane l11-ai-disclosure-setting, S286 (settings-rule audit). AA-1168 (`AA-1168.md`) shipped the disclosure line as a code
constant, English only. The tech lead's standing rule (S278 / S279) is that every customer-visible wording or policy
value is editable on an admin page, seeded and audited, never a code literal or an env var. Two PRs in this repo,
MIG-4 order: the migration-only PR (CIS 463 + 464, the setting module, compiled defaults), then this code PR.

## Decisions

- **One json setting, `cis.content.ai_disclosure`** (area content, platform scope, impact high, maker_checker,
  enforced): `{"text": {"en": ..., "vi": ...}, "social_tag": "#AIgenerated"}`. The registry already supports json
  values and a JSON text area on Platform › Settings, so no schema change to the registry; only the seed row (CIS 463,
  contract: a config INSERT). The default keeps today's English wording byte for byte and adds a Vietnamese line
  ("Nội dung này được tạo với sự hỗ trợ của AI.").
- **The line is a code invariant, the wording is not.** Every channel function (`disclosure_html`, `social_message`,
  `text_with_disclosure`) always appends a line; the setting can reword it, add languages or change the tag, never blank
  or switch it off. `ai_disclosure_setting.value_problem` refuses: not an object, an unknown field, no `en` line, an
  empty / multi-line / over-200-character line, a language code that is not two lowercase letters, an empty tag or a
  tag that is not one `#` + 2–50 letters, digits or `_`. The settings API runs it on a proposal (422) and again on
  approval (409) through `settings_registry.shape_problem` (a key → check map, empty for every other key).
- **The reader never trusts the stored value blindly.** `ai_disclosure_setting.config()` validates what
  `shared.settings.get` returns and serves the seed default on any read error or refused value (logged). A refused
  value can only exist if it was written past the API (or approved before this code deployed): the generic json check
  of the registry accepts any object.
- **Language.** The piece language picks the line (`vi`, `VI`, `vi-VN` → `vi`), English when there is no line for it.
  `acp_shared.content_piece` has no language column and every T9 prompt writes English, so `dispatch.piece_lang()`
  reads a `language` key only when a read selects one; today every piece gets the English line. The agency studio
  export picks by `rewrite_language` of its versions (AA-Partner PR).
- **Facebook retry (AA-726) matches the message actually sent.** New column `acp_shared.publish_log.sent_message`
  (CIS 464). `claim()` stores the text on a new row before the remote call; on a prior attempt (stale `requested`, or
  a `failed` row of the same revision) it keeps the stored text and returns it (`Claim.prior_message`). The route
  looks the feed up for the stored text and the text rebuilt now (one feed read, `find_recent_post(*candidates)`); if
  nothing is found and the new text differs, `record_sent_message()` replaces the stored text right before the post,
  so an attempt that dies between the lookup and the post never loses the earlier text. Rows older than 464 have no
  stored text: the rebuilt message is the only candidate, as before. The post is sent as the stored text
  (`publish_to_channel(..., message=)`), so the row and the post never differ.
- **Agency studio read:** `GET /v1/content-writing/ai-disclosure` (tenant token, response model `AiDisclosure`,
  settings snapshot only, no DB read, no tenant data). The Partner export reads it instead of its hand copy.

## Tradeoffs

- **Store the full message vs only the disclosure used.** The full text costs a copy of the piece text per Facebook
  row (a few dozen rows), but it survives any future change to how the message is built, not only the wording. The
  text is tenant marketing copy, the same class as `content_piece.content_text`, and goes with the tenant through the
  existing `publish_log` erasure entry.
- **A tolerant feed match (piece text + any trailing line) would have needed no migration**, but it could match a post
  the tenant typed by hand; matching exact stored text keeps the AA-726 rule "the exact message".
- **The 200-character bound is a validator shape (technical constant), not a policy value**: it only keeps the line a
  line. No admin need to tune it was found; if one appears, it becomes its own setting.
- **The setting module is in both PRs (byte-identical).** The migration PR needs a code reference to the enforced key
  (settings lint) and the code PR must import it without being stacked on the migration branch; identical additions
  merge cleanly when the code PR takes main.
