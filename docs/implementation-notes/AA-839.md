# AA-839 — Data erasure runbook: "now" slice (offboard wording)

Scope of this PR: only the "now" slice of AA-839. The tested erasure job and tenant data erasure
(scope item 2) are later slices.

## Decisions
- The tenant offboard endpoint (`POST /admin/tenants/{tenant_id}/offboard`) is soft and restorable
  (AA-797). Calling it "GDPR offboarding" claimed a legal erasure it does not perform, so the wording
  now says "tenant offboarding" and points to tenant data erasure as a separate, approved step after a
  retention window — the same terms as the root repo's data-subject requests and erasure runbook
  (`docs/legal/dsar-erasure-runbook.md`, section 4).
- Changed: section comment, OpenAPI `summary`, docstring, and the 400 detail for a blank reason
  ("reason is required for the offboarding audit trail").
- Also aligned the two places that repeated the claim: `CONTEXT.md` (tenant admin section) and the
  comment above `OffboardModal` in `frontend/app/admin/tenants/page.tsx` (comment only, no UI change).

## Changed
- Migration `042_tenants_gdpr_quota.sql` is untouched on purpose: its column comment and
  `schema_versions` label are history, and the file has a byte-identical copy in AA-CIS-Infra
  (Copy Guard). Other historic mentions (migrations 085/097, `docs/claude_audit/`, AA-797 notes) are
  also left as written.

## Tradeoffs
- The summary dropped "(soft, restorable)" to stay within the 120-character line limit; the docstring
  (OpenAPI description) carries the soft/restorable detail.

## Should know
- No behaviour change: same route, status codes and SQL. Only the 400 detail text changed; no caller
  matches on it (the admin UI shows `detail` as-is).
- Tests: `tests/unit/test_aa797_tenant_admin.py` gains a blank-reason 400 test and an OpenAPI check
  (`main.app.openapi()` path `/admin/tenants/{tenant_id}/offboard` → no "GDPR" in summary/description).
- Pre-existing, unrelated: running `test_aa797_tenant_admin.py` alone fails
  `TestListTenants::test_default_is_active_only_and_status_derived` (KeyError `daily_publish_limit`) on
  `origin/main` too — `daily_limit.override_column_exists` caches per process and the AsyncMock
  `fetchval` is truthy when the file runs in isolation. CI (full suite) is green on main.
