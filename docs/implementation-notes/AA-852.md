# AA-852 — X1 (per-app DB owner roles): CIS side

Plan: `AA-Ecosys/docs/audits/2026-10-17-S241-x1/x1-plan.md` (revision 2). The Infra side (owner registry,
`roles/` dir, live-owner role switch, lint) is in `AA-CIS-Infra/docs/implementation-notes/AA-852.md`.

## Step S4 — migration 243 (`api/migrations/243_x1_owner_role_grants.sql`)

What `bk_owner` / `tp_owner` need from CIS once DB Migrate runs Booking / TripPlanner files as them
(XD8): USAGE on schema `shared`, SELECT + INSERT on `shared.schema_versions`, and a BEFORE INSERT key
guard so each owner role can register only its own key prefix.

### Decisions
- **Number 243** — `main` ends at 242; no open branch or worktree carried a 243 (checked 17/10).
- **Trigger, not RLS** (plan review A6): RLS on the registry would also filter non-owner readers
  (`cis_app` after S18, `booking.v_schema_versions`). The trigger checks `current_user`, which is the
  owner role under the runner's `SET LOCAL ROLE` while `session_user` stays the login role.
- **`NOT LIKE 'bk-%'` / `'tp-%'`** exactly as the plan says (not a stricter `^bk-[0-9]{3}$`): the aim is
  "never another owner's key"; the number shape is MIG-3 / Copy Guard's job.
- **SQLSTATE 23514 `check_violation`** with a HINT naming CIS 243, so a refused Booking/TP apply reads as a
  rule, not as a missing grant (42501 would look like the USAGE/INSERT problem 243 fixes).
- **Refuse by default** (review 17/10, problem 1, replaces "only bk_owner / tp_owner are restricted"):
  members of the registry's owner (`pg_has_role(current_user, relowner of TG_RELID, 'MEMBER')`: the master
  today, `cis_owner` / `db_migrator` after S20/S21) insert any key; `bk_owner` only `bk-`, `tp_owner` only
  `tp-`; every other role nothing. Reason, reproduced on a scratch PG16 cluster before the fix: bk-014 makes
  `bk_owner` the owner of `booking.v_schema_versions`, a simple auto-updatable view; an INSERT through it is
  checked on the base table as the view owner (`bk_owner`, which 243 grants INSERT) while `current_user`
  inside the trigger is the caller (`booking`), so the old prefix-only rule let `booking` register `'246'`
  once a later file handed it INSERT on the view (stray `GRANT … ON ALL TABLES IN SCHEMA booking` or a
  TABLES default ACL, which covers views). The owner is read at fire time, so CIS 245 needs no change.
- **EXECUTE on the trigger function revoked from PUBLIC** (SEC-4; a firing trigger does not check EXECUTE,
  the owner keeps it for CREATE OR REPLACE TRIGGER). Guard 1 asserts it.
- **Guard 1 checks "read and insert only" fully** (problem 4): no grant option on SELECT / INSERT, no
  UPDATE / DELETE / TRUNCATE / REFERENCES / TRIGGER, and no column-level UPDATE / REFERENCES
  (`has_table_privilege` ignores column grants). A grant option would let `bk_owner` pass INSERT on.
- **Guard 0 refuses a missing or LOGIN owner role** with "apply rl-001 first" instead of the bare
  "role does not exist"; the grants themselves stay unguarded (schema-ownership rule 5, MIG-8).
- **No behavioural guard inside the file.** Exercising the trigger needs `SET LOCAL ROLE bk_owner`, which
  the X1 role lint refuses in `cis/` (allowlist: `catalog_owner`, `cis_owner`, `cis_app`). Behaviour is
  proven by the CI test and, on Dev, by the S9 probe files `bk-015` / `tp-014`. The in-file guard checks
  the shape: privileges (incl. no UPDATE/DELETE/TRUNCATE), exactly one user trigger with `tgtype = 7`
  (ROW | BEFORE | INSERT), enabled, calling the function, function not SECURITY DEFINER.
- **`SET LOCAL lock_timeout = '5s'` + `statement_timeout = '15min'`** after `BEGIN` (MIG-9 literal values;
  the runner sets the same defaults since N5).

### Changed (vs. the plan text)
- Plan S4 item 3 says the trigger restricts `bk_owner` / `tp_owner`; it now refuses every role that is
  neither a member of the registry owner nor that owner role with its own prefix (review 17/10).
- Added: the LOGIN check in guard 0, the privilege-shape assertions of guard 1, and the `cis_app` role in
  the CI conftest now (plan: "and `cis_app` for S16"), with rl-001's attributes (`LOGIN NOSUPERUSER
  NOCREATEDB NOCREATEROLE NOBYPASSRLS CONNECTION LIMIT 90`, no password).
- `tests/integration/test_aa791_migration_231.py`: its runner registered 231 through a plain INSERT grant
  on `shared.schema_versions`, the path the guard now closes. It now owns the registry for the module, as
  the master does on Dev (REASSIGN at teardown hands it back).

### Tradeoffs
- The CI test hands schema `shared` and the registry to a NOSUPERUSER stand-in of the master for the
  module (lesson S236, as `test_aa791_migration_231`), then `REASSIGN OWNED` back. Slightly invasive, but
  it is the only way to prove the file runs as a plain owner (the conftest replay is a superuser).

- Refuse-by-default could block an inserter nobody listed. Checked: on Dev every registry write today is
  a migration run by the master (owner); the full integration suite only needed the 231 fixture change.

### Should know
- **Merge / apply order** (review 17/10, problem 5; plan S8 is one train PR, the branches are separate):
  (1) this CIS PR → `main`; (2) Infra rl-001 PR merged and applied; (3) Infra copy of 243 merged and applied;
  then bk-014 and tp-013 copies. Copy Guard on the 243 copy is red until (1). The Booking/TP migration
  freeze starts at the first of these merges. 243 applied before rl-001 fails harmlessly at guard 0.
- **CIS 244 (S16):** `GRANT EXECUTE ON ALL FUNCTIONS IN SCHEMA shared TO cis_app` would hand it
  `shared.schema_versions_key_guard()` for no reason: skip it or REVOKE it again (problem 3).
- **S2 probe:** mirror guard 1's owner-role checks in its owner-role cell (no grant option, no column
  UPDATE) — not on this branch.
- **Cross-owner FKs (problem 7, plan-level):** the dump has **10** FKs `tripplanner.* → shared.destinations`
  (the plan said 12). RI checks run as the referenced table's owner, but re-adding such an FK (ALTER COLUMN
  TYPE on the FK column, DROP + ADD CONSTRAINT, NOT VALID included) checks REFERENCES for the current role
  (`checkFkeyPermissions`); from tp-014 that is `tp_owner`, which has none → "permission denied for table
  destinations" (reproduced on the scratch cluster). No grant here; a TP lint rule from tp-014 (S7) should
  refuse those statements and point to X4 decoupling or a `roles/` break-glass file.
- **Apply order (S8 train):** `roles/001` (rl-001) → `cis/243` → `booking/014` → `tripplanner/013`.
  243 fails at guard 0 if rl-001 is not applied. 243 runs as `aa_cis_admin` (owns `shared`, no switch).
- **Rollback** is a forward file (in the header), valid only before bk-014 / tp-013: after them the Booking
  readiness view (`booking.v_schema_versions`, owner rights) and DB Migrate's registration as the owner
  roles depend on these grants. The runner refuses a switched file (exit 8) without them.
- The function count in the schema reference goes from 15 to 16; CIS 245 (S21) transfers
  `shared.schema_versions_key_guard()` to `cis_owner` with the other `shared` functions.
- A BEFORE INSERT row trigger fires before the ON CONFLICT check, so a wrong key raises even when that
  key is already registered (tested), never a silent DO NOTHING.
