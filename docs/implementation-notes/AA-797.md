# AA-797 — Admin tenants: status toggle, plan_id, offboard + restore, audit, /usage 500

Session S235, Lane B (Claude Code subagent). Branch `fix/aa-797-admin-tenants`.

### Decisions
- **plan_id backfill is not redone.** S234 already mapped the 5 tenants (audit rows
  `tenant.plan_id_backfill`). This PR only stops new NULLs: create and PATCH now set `plan_id`.
- **Offboard is restorable (Nghiệp, 14/10/2026):** "restore to quickly recover that tenant's
  data and settings". This replaces the earlier Gate-1 default that made offboarded terminal.
  - Three states derived from two columns: `offboarded` = `cancelled_at IS NOT NULL`,
    `suspended` = `is_active = false` and not offboarded, else `active`.
  - suspend <-> active is reversible through `PATCH {is_active}`.
  - offboarded -> active only through `POST /admin/tenants/{id}/restore`. PATCH and
    generate-key on an offboarded tenant stay 409; the message points to restore.
  - **Offboard is soft state only.** It UPDATEs `shared.tenants` (cancelled_at,
    cancellation_reason, is_active=false, api_key_hash='REVOKED_<id>'), cancels QUEUED jobs, and
    deletes one row: the Jev allow-list entry (AA-741, content must not reach Jev while
    offboarded). That row is a setting, so offboard copies it into the `agency.offboard` audit
    details (`jev_allowlist: {reason, added_at, added_by}`) and restore re-inserts it. Nothing
    else is touched: plan_tier/plan_id/rate_limit_rpm/posts_per_week, tenant_brand_rules (+
    versions), acp_shared.tenant_config (markets/channels), tenant_tour_versions, content
    pieces, users all stay. A unit test asserts the offboard SQL set; the integration test
    compares a settings snapshot before offboard, while offboarded and after restore.
  - **Restore** (admin-only; BFF prefix `tenants` covers it, backend re-checks `x-admin-role`):
    409 unless offboarded; clears `cancelled_at` + `cancellation_reason`, sets is_active=true,
    re-adds the allow-list row from the latest offboard snapshot, issues a NEW key (shown once,
    like generate-key; the old key is never un-revoked), writes `tenant.restored` with
    previous offboard time + reason, what was restored and the jobs not re-run.
  - **Cancelled jobs are not re-enqueued.** Restore returns the jobs the offboard cancelled
    (`shared.job` with `error = 'cancelled: tenant offboarded'`, this tenant, `finished_at >=`
    the offboard time, so an earlier offboard cycle's jobs are not listed again) so the admin
    can re-run them.
  - Offboard cancels the tenant's QUEUED `shared.job` rows (never running ones). See Tradeoffs.
  - Tenant writes are admin-role only. The BFF rule lives in `frontend/lib/rbac.ts` (diff handed
    to the orchestrator); the backend re-checks the forwarded `x-admin-role` like AA-769 does.
  - GDPR S3 deletion is a follow-up, not this PR.
- **PATCH takes a JSON body** (`UpdateTenantRequest {plan_tier?, is_active?}`). The UI always sent
  a body; the route read query params, so the toggle returned 200 and changed nothing. An empty
  body is 422.
- **One plan lookup helper** `_resolve_plan_id(conn, plan_tier)` reads
  `shared.membership_plans WHERE plan_name = $1 AND is_active`. No active row -> 400, so a new
  tenant can no longer get a NULL plan_id (the S234 bug: quota/price showed 0/inf).
- **Audit actor** is `admin:{x-admin-user-id}` (`admin:unknown` without the header), the same
  shape as admin_content_quality.py. New `AdminTenantAuditAction` constants in
  `services/acp_shared/audit_log.py`; the two older inline rows (`agency.onboard`,
  `agency.offboard`) keep their action strings but now go through `write_audit_log` with the
  real actor instead of the literal `admin_api`.
- **Suspend takes effect at once:** each status write deletes the Redis `tenant_meta:{id}` key
  (best effort) so the 30 s rate-limit cache does not keep a suspended tenant alive.
- **/usage reads live columns only.** The old query selected `month/total_calls/...` from
  `shared.v_tenant_monthly_usage`, which are migration-007 names; the live view has
  `billing_month/api_calls_used/...` instead (db-schema-reference.md). The monthly series is now
  computed straight from `shared.tenant_api_usage` (same columns in repo migration 007 and live),
  so the endpoint works on both the live DB and the 007-shaped CI DB. The view itself is AA-798
  (migration 223), not touched here.
- `tours_published` in /usage was always 0 (tenants never own `published_tours`). Replaced by
  `t2_versions` / `t2_tours` from `gold_aa_internal.tenant_tour_versions`.
- **GET /admin/tenants `include_inactive`** is opt-in (default false keeps the old active-only
  list for atom-curation, tenant-activity and the command palette). Rows now carry
  `cancelled_at` and a derived `status`.
- **The bare `DELETE /admin/tenants/{id}`** (unaudited soft delete, no key revoke) is removed.
  The UI uses Suspend (PATCH) or Offboard instead.
- **The AA internal tenant cannot be offboarded** (400): it owns the master catalogue.

### Tradeoffs
- **Queued-job cancel on offboard.** `shared.job` has no `tenant_id` column; tenant kinds
  (t2_rewrite, t7_slate, t8_angles, t9_write) carry it at the top of `payload` (the worker binds
  it from there, G1). `queue.request_cancel()` is per job and also flags RUNNING jobs, so it is
  not reused as is. The offboard transaction runs the queued branch of `request_cancel()` scoped
  by `payload->>'tenant_id'` and `status = 'queued'` (a job claimed concurrently fails the
  re-checked WHERE and is left alone), then calls the existing `registry.run_terminal_hook()`
  per cancelled job after commit, exactly as `POST /admin/job-runner/jobs/{id}/cancel` does, so
  t2/t9 rows are marked failed. If the orchestrator prefers a queue-module helper, move the SQL
  into `shared/jobs/queue.py` (outside Lane B's ownership).
- **Backend role check is strict** (`x-admin-role` must be `admin`). The BFF always forwards it,
  so the UI is unaffected; direct curl calls with only the admin secret now need
  `-H 'x-admin-role: admin'` for tenant writes. Reads are unchanged.
- **config PUT audit** is written after `save_tenant_planning_config()` commits (that helper owns
  its own connection), so it is not in the same transaction. Every other new audit row is.
- **Restore issues a new key instead of reviving the old one.** The old hash is already
  overwritten by `REVOKED_<id>`, and a key that was revoked for a reason (often a leaving
  customer) should never silently work again. The cost: the tenant must be given the new key.
- **The allow-list snapshot lives in the audit row**, not a new column or table, so no
  migration is needed. If the offboard predates this change (no snapshot), restore skips the
  allow-list and says so (`jev_allowlist_restored: false`); an admin re-adds it by hand.
- **Terminal hooks still run on cancelled jobs** (T2 version / T9 piece pending -> failed, T8
  goal cleared). Those rows were in flight, not finished content; the failed state is what
  shows Retry in the portal after restore. Finished content is never touched.
- Brand-identity audit stores the new version number and the list of non-empty fields, not the
  prompt text itself (the rules table keeps every version).
