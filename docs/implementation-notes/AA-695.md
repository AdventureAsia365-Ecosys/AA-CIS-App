# AA-695 — A3-7 Segment matching: country guard + Jev "same real-world place?"

Design: `docs/architecture/at-series-v2-design.md` §4.2 A3-7 ("measure the borderline count first").

## Measured first (S205, Dev)
- 384 of 3,337 Segments hold atoms naming different places; 65 span more than one country.
- 40-Segment sample: about a quarter were wrong merges — Bukchon vs Jeonju Hanok Village, Wat Saket (Bangkok) vs Wat Si Saket (Vientiane), different trek legs (Namche → Lukla / → Tengboche / Phakding → Namche), "local restaurant" across China, Korea and Thailand. Cause: the subset rule and Jaccard ≥ 0.5 on generic names.

## Decisions (Nghiệp, 30/09: do both, rebuild Segments from scratch in the rerun)
- **Country guard (deterministic):** `SegmentAtom.country` (the tour's `raw_tours.country`); atoms of two known, different countries never join. Existing Segments get their member tours' most common country for the incremental pass.
- **Segment id folds the country in** when known: `sha256(place|verb|country)`. Without it the same generic moment in two countries would mint one id. No country → the origin formula, unchanged. Existing ids are held by `reconcile_ids` as before.
- **Jev `a3_same_place`** (migration 192, shadow): asked in `run_segment_matching()` for place pairs the moment rule would join although written differently, same country (or unknown), with at least one new atom. An enforced, confident no puts the pair in `apart`, which `derive_segments()` respects. The Verdict is cached per wording + pair, so reruns regroup the same way (ADR 0002).
- **Rebuild from scratch** is a runbook step for the rerun (AA-653): Segments are UPSERT-only, so old wrong merges do not undo themselves.

## Tradeoffs
- `apart` vetoes a direct pair only; two places can still meet through a third member (union-find). Rare, and the country guard removes the worst cases.
- Pairs are only asked when a new atom is involved, so one tour's pass costs O(new atoms × Segments) key comparisons and a handful of Jev calls.

## Regression fix S218 (08/10/2026) — Segment merge aborted on atom_segment_member_pkey

### What happened
- `run_segment_matching()` re-pointed a losing Segment's members with
  `UPDATE atom_segment_member SET segment_id = target WHERE segment_id = was`. When an atom was
  already a member of `target` (or of two losers merging into one target), the UPDATE hit the PK,
  the whole transaction rolled back, and `export/handler.py` swallowed it as a warning.
- The failed merge is never persisted, so every later tour derives the same merge from the
  pseudo-atoms and fails again. First failure 30/09 07:27 (right after #510); no Segment created
  after 05/10. Live on 08/10: 566 tours / ~16.5k atoms (India, Sri Lanka, Nepal, Japan, Laos,
  Philippines, Pakistan, Vietnam, most of Thailand) had no Segment, Score row or Route, while every
  `a3_atomize` job reported success.

### Decisions
- Re-point as `INSERT … SELECT … ON CONFLICT DO NOTHING` then `DELETE` the loser's rows
  (`_repoint_members`). Keeps one row per (segment, atom); no schema change.
- Keep the step best-effort (atomize must not fail because of it) but log at error level and put
  `segment_score_route: ok | failed: …` in the `a3_atomize` job result, so a wave report sees it.

### Should know
- Backfill needed after deploy: run `run_segment_matching` for each un-segmented tour, then one
  platform Score + Route recompute (Jev same-place calls only, no LLM).
- Integration test `tests/integration/test_s218_segment_alias_repoint.py` reproduces the collision.
- Second bug surfaced during the backfill (240/633 done, 7 failed): ForeignKeyViolation on
  `atom_segment_member_segment_id_fkey` / `atom_segment_alias_segment_id_canonical_fkey`. A merge
  target can be a NEW id whose only members this run are pseudo-atoms, so it is not in `to_write`
  and its `atom_segment` row was never created, and the re-point ran before any segment upsert
  anyway. Fix: upsert every alias target (plus `to_write`) first, then re-point, then members and
  aliases. Unit test `test_s218_segment_alias_target.py` fails on the old order.
- Perf (S218, Nghiệp approved): per-tour segment matching loaded every platform Segment and ran a
  quadratic grouping over all of them — 5 s → 36 s per tour as the backfill grew the set.
  Now: (1) SQL loads only same-country (or unknown) Segments that still have members, plus the
  tour's own prior Segments; (2) `_candidate_pseudo_atoms` keeps only those sharing the verb and a
  place word with a new atom (a necessary condition of `_looks_like_one_moment`); (3)
  `derive_segments(..., involving=new_ids)` skips existing–existing pairs. Decision: two existing
  Segments merge only when a new atom bridges them; standalone re-merging of old Segments belongs
  to the AA-695 periodic merge job (it only re-derived already-applied merges — ~187 phantom
  aliases per run). Tests: `test_s218_segment_matching_scope.py` (filtered pool gives the same
  components for new atoms; old–old merge needs a bridge).

## GO item 1 (S223) — transit / unnamed-place atoms never form or join a Segment

The S223 comment (go/no-go decided with Nghiệp) supersedes the S219 scope. This change is GO
item 1 only: transit and unnamed-place atoms stay atoms but never form or join a Segment. The
empty / transit Segment cleanup (GO item 2), the single-tour-share metric (item 3) and the Jev
`a3_same_moment` merge (item 4, AA-756) are out of scope here.

### Exclusion rule (does NOT use `classify_exclusion` alone)
Ranking rescues rule-"transit" moments as experiences — `atom_ranking.exclusion_after_pick` /
`resolve_exclusions` (AA-694) let Jev's `a3_activity_type` keep a rule-transit atom whose
`activity_type` says otherwise, and 199 live Segments ride on that ("Nanta — attend a nonverbal
show", "Negombo beach — attend a private candle-lit dinner"). Using `classify_exclusion` alone
here would delete them. So, to stay deterministic (no Jev call in segment matching) while matching
ranking's FINAL verdict, an atom is excluded only when:
- `classify_exclusion(place, action) == "unnamed_place"` (never a moment), or
- it is rule-`"transit"` AND the atom's own `activity_type` is `"transit"` or NULL.

A rule-transit atom typed anything else (`culture`, `trek`, `stay`, `food`, `bike`, `other`, … —
there is no literal "experience" type) still forms/joins Segments. This is exactly what
`atom_ranking.atoms_say_transit([type])` decides for a single atom (an untyped atom does not vote
itself transit), so both halves below reuse that helper rather than copying it.

### Where
`services/acp_contract/segment_matching.py`:
- `forms_segment(atom)` — the small named function, one atom in, keep/exclude out. Four cases, unit
  tested in `tests/unit/test_aa695_no_transit_segments.py`.
- `_existing_forms_segment(row)` — the Segment-level counterpart for the join-candidate
  pseudo-atoms, over a Segment's canonical place/action + its member atoms' types.
- `run_segment_matching`: the atom query now also selects `ta.activity_type`; the existing-Segment
  query loads `member_types` (`array_remove(array_agg(ta.activity_type), NULL)`). This tour's atoms
  are filtered through `forms_segment` before `derive_segments` (an excluded atom gets no
  `atom_segment_member` row); existing Segments are filtered through `_existing_forms_segment`
  before becoming pseudo-atoms (a new atom cannot glue onto a Segment that should never have
  formed).

### Idempotent cleanup, scoped
A re-atomize that used to include an atom now excluded removes that atom's `atom_segment_member`
rows — but only for THIS tour's atoms, only the member rows. No `atom_segment` row is ever deleted
here (migration 129's FK reasoning: `atom_segment_alias.segment_id_old` references it), and no
other tour is touched. The platform-wide empty / transit Segment deletion is the separate approved
DRY RUN of GO item 2, done by Claude Code — not this code path.

### Import cycle
`atom_ranking` imports only `atom_matching` / `ranking_reference` / `decide`, none of which import
`segment_matching` (the one importer of segment_matching is `recompute/stages.py`, which
atom_ranking does not touch). So `from services.acp_contract.atom_ranking import atoms_say_transit,
classify_exclusion` at module top is safe — checked S223, nothing moved.

### Not changed
`classify_exclusion` itself, ranking, routes, the `a3_same_place` logic. No migration (both columns
already exist on `tour_atoms` / `v_active_tour_atoms`).
