# AA-1126 — Gateway spend controls per environment: G1, G2, G4 (S283, lane l15-gateway-caps)

Tech lead policy S283 (root `docs/audits/2026-11-17-S283-session/ai-caps-gap.md`): Dev keeps hard caps on the AI
connections; prod is pay per use, where a connection cap alerts and fails over but never blocks a customer, only an
anomaly breaker may stop calls, and internal batch runs keep a hard cap per run. One code path for every environment:
each environment's settings registry (its own database) picks the behaviour, so going to prod is a settings change.

Tech lead requirement (S283): every new threshold, mode or cap is a settings registry key, shown and edited on
Platform › Settings (app CIS, area Spend), and shown consistently where the AI gateway page already shows caps
(Budgets tab). One source of truth that the code reads; no constant, no env-only value.

PRs (MIG-4 chain): migration-only PR CIS 446 (contract: settings seed rows + ALTER TABLE) -> Infra copy + Migration
Apply -> the code PR. No new table (no DM-7.1 retention row).

## Decisions

- **Eight settings, area `spend`, platform scope, maker-checker, enforced, EN + VI guide** (CIS 446):
  `cis.llm.connection_cap_mode` (`hard_stop` default | `failover_continue`), `cis.llm.anomaly_breaker_mode` (`off` |
  `alert` default | `enforce`), `cis.llm.anomaly_multiple` (4, 1.5-100), `cis.llm.anomaly_floor_usd` (25, 0-10000),
  `cis.llm.anomaly_baseline_days` (14, 7-60), `cis.spend.run_cap_s1_rewrite_usd` (2, 0.05-20),
  `cis.spend.run_cap_eval_usd` (10, 0.05-50), `cis.spend.run_cap_adhoc_usd` (5, 0.05-50).
  `shared/llm_client/caps_settings.py` is the only reader; it ships in the migration PR too (the settings lint needs
  a reader for every enforced key) and is byte-identical in the code PR.
- **Defaults = today's Dev behaviour.** A key the compiled defaults do not have (code before 446) or an unreadable /
  unknown value reads as: hard stop, breaker off, no run cap. The seeded breaker default is `alert` (a bell, never a
  refusal), so Dev changes only by one possible admin bell per app per day.
- **G1 `failover_continue`** wraps the whole route call (`connection_budget.run_with_cap_mode` around
  `LLMClient._call_chain`): the first pass is today's rule (an over-cap hard-stop connection is left out while another
  rung answers). Only when the pass fails and a connection cap took part (`ConnectionBudgetExceeded` in the cause chain
  or among the route failures) does it alert (bell + ops e-mail, scope `llm:connection_continue`, one per 24 h) and
  run the route once more with the caps lifted (a ContextVar; `stops` answers None), so the call goes to the first
  healthy rung. A connection whose own cost policy is alert only stays alert only. The per-connection 80 % / 100 %
  alerts are the existing ones.
- **G2 anomaly breaker** (`shared/llm_client/anomaly_breaker.py`): per app (`cis`, `tripplanner`, `crm`; the ledger's
  `app`, else `quality_signal.app`, else cis — the platform_cost rule). Today = rows since
  `max(UTC midnight, profile.anomaly_reset_at)`; normal day = the median of the app's daily spend over the baseline
  days before today (rolled-up days from `shared.llm_call_daily`, raw days not rolled up yet; a day with no spend = 0).
  Trips when today > `max(multiple x median, floor)`. `enforce` refuses with `AnomalyBreakerTripped` (a
  `BudgetExceeded`: job `stopped_budget`, 0 USD refused/budget ledger row). The CIS gateway checks its own app on
  `generate`, `embed` and the batch lane; the admin status reads every app so TripPlanner and the CRM can read the
  same verdict later.
- **Reset**: `POST /admin/ai-gateway/anomaly-breaker/{app}/reset` (ai.admin; refused to a tighten-only role, a reset
  loosens a stop), writes `shared.llm_app_profile.anomaly_reset_at/_by` (CIS 446) and an audit row
  `llm_anomaly_breaker_reset` with the verdict it cleared. The day rolling over ends a trip by itself.
- **G4 run caps** (`shared/llm_client/run_cap.py`): a call belongs to an eval run (eval label bound or stage
  `writing_memory_eval`), an ad-hoc run (stage or label `adhoc_*`) or an S1 rewrite job (bound job kind
  `s1_rewrite`); anything else reads nothing. The run is the bound job, else the eval run id, else the ad-hoc stage
  since this process first called it. Cap = the job payload's `cap_usd` (bound by the worker) else the class's
  setting. New `s1_rewrite` jobs get `cap_usd` stamped at enqueue (`shared/jobs/registry.enqueue`), so a job keeps the
  cap it was queued with. Spend reached cap -> `RunCapReached` before any attempt, bell `llm:run:<class>`.
- **Admin, one source of truth**: Budgets tab › "Spend controls of this environment" (`SpendControlsSection.tsx`,
  `GET /admin/ai-gateway/spend-controls`, its own router `api/routers/admin_ai_gateway_spend.py`) lists every key with its value in force, default and source, each linking to
  its row on Platform › Settings (`?app=cis&area=spend&key=<key>`); it never edits a value. The connection tier's
  "at the cap" text follows the mode ("Fails over at the cap"). The Connections editor hint names the setting.
  Platform › Settings already renders area `spend`; `USD/day` and `x` got their Vietnamese unit names.

## Changed (vs the issue / gap file)

- The gap file proposed a per-connection flag in Providers › Connections; the lane brief asked for a per-environment
  setting. Built as the environment setting; the per-connection hard_stop / alert-only policy is kept and composes with it.
- The gap file named the setting `platform.llm.anomaly_multiple`; CIS keys are `cis.*` (registry rule).
- G3 (TripPlanner / CRM app caps), L1-L4 and the TripPlanner / CRM gateways calling the breaker are other lanes.

- **G1 wraps `LLMClient.generate`** (`connection_budget.run_with_cap_mode(lambda: self._generate(request))`): the
  retry re-enters the whole request (gates, attempt scope, deadline) with the caps lifted; the gates passed the first
  time, so they pass again. The gates now share one helper `LLMClient._refuse` (0 USD refused row, then raise), which
  keeps `client.py` within its code-health size baseline.
- **The Budgets tab reads the connection cap mode from the spend-controls read** (`useAtCapText`, the same react-query
  key as the section), so the Budgets read (`api/services/ai_gateway.py`) is unchanged.

## Tradeoffs

- G1 re-runs the request instead of threading "last rung" logic through `_call_route` / `vendor_route`: one wrapper,
  no change to the plan code, and the first pass keeps today's ledger rows (the budget skips are honest refused rows
  before the successful call).
- Decide (Jev) is not behind the anomaly breaker: Jev fails open by design and is budgeted on its own.
- Fail open everywhere (an unreadable spend never refuses), the gateway's rule for every budget read; the run cap of
  a job is also fail open, unlike the writer proof's own gate (which stays as it is).
- The breaker's today read is cached 60 s and the run spend 5 s per process: a runaway passes the line by at most the
  calls already running plus one cache window.
- An eval run outside a job counts rows since this process first saw the run (a restarted script starts a new count);
  the writing-memory / W5 runners keep their own stricter caps.
