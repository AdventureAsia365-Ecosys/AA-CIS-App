# AA-891 — release-please and the release version on /health (AA-CIS-App)

Branch `feat/aa891-release-please`. Refs AA-891, AA-901 (the `aa-ecosys-ci-bot` GitHub App).

## Decisions
- **Manifest mode, one root package.** `release-please-config.json` + `.release-please-manifest.json`, package `"."`,
  `release-type: simple` (the repo has no Python/Node package whose version matters: `package.json` files are private
  tooling at 0.1.0/1.0.0 and stay untouched). `bump-minor-pre-major: true`, `include-v-in-tag: true`,
  `include-component-in-tag: false` (tags are `v0.4.0`, not `aa-cis-app-v0.4.0`), `changelog-path: CHANGELOG.md`.
  CHANGELOG.md is created by the first release PR, not by hand.
- **One version for api + worker + admin + portal.** They ship from one repo and one merge; the admin and the portal
  do not show a version yet. Per-component versions would need three packages and three tags for no reader today.
- **The version in code lives in one file, `api/version.py`** (`__version__`, marked `x-release-please-version`),
  listed in `extra-files`. It used to be written twice in `api/main.py` (FastAPI `version=` and the `/health` body,
  the "CIS version lives in 2 places" of AA-891); both now import `__version__`, so release-please bumps one file.
  A separate file (not markers inside `api/main.py`) so Deploy Dev can ignore exactly that file.
- **How the image carries it:** `COPY api/` already copies `api/version.py`, so no new build arg. The git SHA keeps
  its build arg (`GIT_SHA` → `APP_GIT_SHA`) because it is not in the tree; the version is.
- **First version = v0.4.0 without `release-as`.** The manifest holds the current version `0.3.0` (what `/health`
  reported before) and `bootstrap-sha` is the `main` tip this branch started from, so the first release PR reads only
  the commits after it. This PR's own squash commit is a `feat:`, and with `bump-minor-pre-major` a feat (or a
  breaking change) on 0.3.0 gives exactly **0.4.0**. No `release-as` means no follow-up PR to remove it.
  `bootstrap-sha` is only read while no release exists; it can stay or be deleted after v0.4.0 (harmless either way).
- **Release workflow** (`.github/workflows/release-please.yml`): push to `main` + `workflow_dispatch` only; job in
  environment `release` (main-only deployment policy, holds `AA_CI_BOT_PRIVATE_KEY`); top-level
  `permissions: contents: read`; the App token from `actions/create-github-app-token@v3` (`vars.AA_CI_BOT_APP_ID`,
  scoped by default to this repo, and narrowed like AA-Booking's to `permission-contents`, `permission-pull-requests`
  and `permission-issues` write) does every write through `googleapis/release-please-action@v5`. Both actions are
  pinned to their current released major (v3.3.0 and v5.0.0 at the time, both Node 24). `app-id` is deprecated in v3
  in favour of `client-id` but still supported (a deprecation warning in the log); kept, because the variable holds
  the numeric App ID. Reason for the App token: a PR opened with `GITHUB_TOKEN` triggers no workflow, so the 5
  required checks would never report.
  `concurrency` queues runs so two pushes do not race on the release branch.
- **Deploy guard:** Deploy Dev's `paths` never listed `CHANGELOG.md` or the manifest; `'!api/version.py'` is added
  after `'api/**'` (GitHub evaluates path patterns in order). Vercel workflows watch only `frontend/**` / `portal/**`,
  so they are untouched. CI (`pull_request` to main, no path filter) runs on the release PR.
- **Deploy smoke** now also asserts `/health` `.version` equals `.release-please-manifest.json` of the deployed commit.

## Changed
- New: `api/version.py`, `release-please-config.json`, `.release-please-manifest.json`,
  `.github/workflows/release-please.yml`, `tests/unit/test_aa891_release_version.py`.
- `api/main.py`: FastAPI version and `/health` `version` read `api.version.__version__` (no hardcoded `0.3.0`).
- `.github/workflows/deploy-dev.yml`: `'!api/version.py'` path negation; smoke checks `version`.
- `CONTEXT.md`: one bullet "Release version (AA-891)" under the health section.

## Tradeoffs
- **Release merge does not redeploy.** After a release PR merges, the running image still reports the previous
  version until the next code merge deploys (that image then reports the new one). Accepted per AA-891 (no deploy on a
  version-only commit). If a deployed version is needed right away, run Deploy Dev by `workflow_dispatch` on `main`.
- **Static text tests, not a YAML parser.** PyYAML is not in `requirements.txt`; the workflow tests follow
  `test_aa725_image_pin.py` / `test_aa879_ci_gates.py` and match text. A reformatting of the workflows may need the test
  strings updated.
- No `release-as`: relies on the PR title (squash subject) staying `feat: …`. If it were merged as `chore:`/`docs:`,
  release-please would open no release PR until the next `feat`/`fix`; then the first release could be 0.3.1 (fix only).

## Should know
- Needs (outside this repo): repo variable `AA_CI_BOT_APP_ID`, secret `AA_CI_BOT_PRIVATE_KEY` in environment
  `release`, and the `aa-ecosys-ci-bot` App installed on this repo with contents / issues / pull_requests write. Without
  them the job fails at "Mint the CI bot App token" (no harm to anything else).
- Never edit `api/version.py`, the manifest or `CHANGELOG.md` by hand; merge the release PR. The unit test fails if
  `api/version.py` and the manifest disagree.
- The release PR is a normal PR (5 required checks). Merge it like any other (squash); release-please then tags
  `vX.Y.Z` and creates the GitHub release on that push.
- Not in scope: showing the version in the admin / portal UI, Sentry `release` (stays the git SHA).
