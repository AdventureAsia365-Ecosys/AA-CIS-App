# AA-1077 — T9 blog length contract

Lane l5 of S277. Source: AA-741 phase 3 report (root `docs/audits/2026-11-10-S276-aa741-phase3/`, §4.5 and §9.5).
28 phase 2 blog pieces: 20 held, 13 of them on F4 and all 13 too SHORT (median 652 words); the writer asks for
900–1,300 words but 25 of 28 came in under 900; the short side was repaired by a full rewrite (F4 fixed on 6 of 18,
a new hold gate on 9 of 18, about 1.02 USD); the post-loop normalizer shortened text after F4 had measured it, so 3
of the 7 approved pieces are stored under the floor.

## Decisions

- **One owner: `services/acp_content_writing/length_contract.py`.** It holds the F4 blog band
  (`BLOG_FLOOR_CHARS` 4,700 / `BLOG_CEILING_CHARS` 13,000, tag-stripped), the measured `CHARS_PER_WORD` (5.8), the
  extend target and the side helpers. `quality_gates._BLOG_MIN_CHARS/_BLOG_MAX_CHARS` now read it (names kept for
  their importers: length trim, the blog truth-cut refusal).
- **The writer's word target stays the literal in `prompts.py`.** `_BLOG_WORDS` / `_BLOG_WORDS_MAX` are hashed
  symbols of the registered t9_write prompt (v2/v3): changing their source text needs a prompt version bump plus a
  migration that registers it, for a prompt that renders byte for byte the same. `length_contract.writer_words()` reads
  them (lazy import), so the number is still written once. A test pins the relationship: writer floor × 5.8 ≥ F4 floor
  × 1.08 and writer max × 5.8 ≤ ceiling. Only comments in `prompts.py` changed (the "tags included" claim was wrong);
  `scripts/prompt_registry_check.py` reports 0 problems.
- **F4 codes.** The gate name stays `F4_extreme_length` (taxonomy, route table, writing memory and old ledgers all key
  on it). The blog violation now starts with its side and states words and target:
  `length_short: content is only 3947 chars (about 652 words), under the blog floor of 4,700 chars (about 810 words);
  the writer aims for 900-1,300 words` / `length_long: content is N chars (about W words) — far beyond the blog
  ceiling …`. "only N chars" and "far beyond" are kept on purpose: the audit scripts' regexes and
  `service._F4_OVER_RE` keep working. The other 7 channels keep their wording byte for byte.
- **Hold reason codes.** `gate_eval.hold_reason_codes` gives `length_short` / `length_long` for F4, read from the
  violation (`length_contract.code_for`), so an old ledger re-read gets the split code as well. `length` stays the code
  of an F4 failure whose side does not read and is what labels stored before this change carry: readers group with
  `gate_eval.reason_family()` / `LENGTH_CODES` (backward-compatible reading in views and reports).
- **Re-check after the normalizer** (`service._recheck_length`, the last step of `_normalize_final_text`, blog only):
  F4 runs on the text that is stored. A fresh failure replaces the ledger's F4 entry and holds an APPROVED piece
  (`held_reason` "F4_extreme_length: length_short: …"; its stop label then reads `length_short`). A fresh pass never
  turns a held piece approved (the hold was decided on the gated text). Every blog gets `writer_input.length_trace`
  (admin-only; not a repair-log entry, so `repair_log[-1]` stays the last repair or label): chars after each normalizer
  step (`loop`, `stock_cut`, `authenticity_cut`, `faq_answer_fit`,
  `final_integrity`), the floor, the words and the verdict — the report asked to measure which step cuts.
- **FAQ answer fit is floor-aware** (normalizer only): a drop that would take a blog that was at or over the floor
  under it is not made; the record says `floor_kept`, the admin flag says why. A non-answer FAQ pair is a warning; a
  blog under the floor is a hold. The stock-line cut was already floor-aware (it re-runs F4 and refuses).
- **Extend repair** (`length_extend.py` + `generate.extend_sections`). Attempt 2 of a blog whose F4 failure is the
  short side, with ≥ 1 body section and ≥ 1 seed fact sentence the post does not tell yet
  (`quality_gates.unused_source_facts`, as AA-788's F14 floor rewrite). Up to 3 thinnest body sections (never the
  opening, never the FAQ) get ONE new paragraph each, sized from the deficit to `extend_target_chars()` = floor + 520
  (the largest normalizer cut seen on the phase 2 holds was 557; 5,220 chars ≈ the writer's own 900-word floor).
  Passing sections are never sent to the model. Each paragraph is checked in code: plain prose (no heading, list,
  question, tag, CTA), at most 2× the words asked, `repair_contract.new_specifics` (no number / time / ordinal /
  position / pace word the source lacks — the source-fidelity rule), and a clean seam (`sentence_repair._integrity`).
  Then the attempt runs its deterministic fixes and every T10 gate on the whole text; the AA-528 guard keeps attempt 1
  when the added text broke a passing gate (truth before length).
- **Routing.** The F4-short entry is set aside (`set_aside: length_extend`) and the other failures route as before:
  quoted findings → the sentence repair, then the extend in the same attempt (`repair_mode`
  `sentences+length_extend`); a gate that needs the full rewrite (CTA, F2 lexicon, …) → the full rewrite as before and
  no extend; no plan (no section / no untold fact) → the full rewrite as before. A sentence-repair failure still falls
  back to the full rewrite. An extend call error keeps the text (the gates then hold on length), never a second call.
- **Stage.** The call runs on `t9_write` (the writer, Sonnet 5.5 today), like the attempt-2 sentence repair, with
  `quality_signal.mode = length_extend`, `content_piece_id` set, `record_call_sync(..., **billed_fields(resp))`.
  Registered in `docs/llm/prompt-register.md` as `t9_write.extend` (version `git`, like the other generate.py
  prompts); no manifest bump, so no migration.
- **Default off.** `T9_LENGTH_EXTEND=on` turns it on (worker env, or one audit-tenant job through
  `quality.trial_flags`, now in `ALLOWED["t9_write"]`); unset = main's full rewrite, byte for byte. Reason: the lesson
  "a change of the writing loop that has not had its review rounds ships behind a flag whose default is main" (S272).
  The issue's own order is: trial on 3 pieces, then the 9 length-only pieces, then switch. The switch is classified in
  `writing_memory.config_fp.MODE_FLAGS["t9_blog"]`.
- **Scripts.** `scripts/aa1077/remeasure_length.py` ($0, read-only session): per piece stored chars / words, the
  ledger's F4 reading, chars before (length trace, else the F4 reading) / after the normalizer, the contract's
  verdict and the status the re-check gives; summary `approved_under_floor_stored` / `_after` (must be empty),
  `held_by_recheck`, `length_only` (the trial's input). `scripts/aa1077/extend_trial.py` (paid, `CAP_USD` hard cap,
  read-only session for reads): base gates on the stored text ($0), the extend exactly as the loop runs it, gates
  after with a live F9 judge (`F9=stored` for $0), "would be approved" and new hold gates; it never writes a piece.
  The trial runs on stage `t9_write` (not `adhoc_aa1077`) so it measures the production route; its rows are found by
  `content_piece_id` + `quality_signal->>'mode' = 'length_extend'` in the run window.

## Tradeoffs

- **Hold vs ship an approved piece the normalizer shortened.** Holding is honest (the floor is the contract) and a
  held piece still reaches the tenant (AA-770). The FAQ-fit floor rule removes the most likely cause, so fewer pieces
  should hit the re-check.
- **Append-only extension vs section rewrite.** Appending one paragraph per section cannot break the existing text
  and is checkable sentence by sentence; a section rewrite reads more naturally but brings back the rewrite risks.
- **One call for up to 3 sections vs a call per section.** One call is cheaper and keeps the voice consistent; a bad
  paragraph is dropped alone.
- **Extend target 5,220 chars, not the writer's 900–1,300 words.** The aim is to clear the floor with the normalizer's
  margin, not to pad to the writer's target.

## Decision for the tech lead

The floor question: 12 of the 27 phase 2 seeds were ≤ 991 words and 9 of those 12 pieces were held on F4 (1
approved); of the 15 seeds ≥ 1,210 words, 4 were held on F4 and 6 approved. Length follows the seed (r = 0.424), not
tour days (0.098).

| Option | What changes | For | Against |
|---|---|---|---|
| A. Floor by seed size | F4 floor drops for a thin seed (e.g. 3,500 chars under ~1,000 seed words) | No held piece for a thin seed | Thin articles ship; two floors to explain; SEO value of a 600-word guide is low |
| B. Floor by brand style | The brand pack declares short / standard / long; F4 reads it | The agency decides; fits a short-sentence brand (trail: 5 of 5 holds on F4) | A new brand field + UI; every brand can pick "short"; does not fix a thin seed |
| C. T7 minimum seed for Blog | The T7 Blog Bar also needs a minimum seed (words and untold fact sentences) before a Blog Subject is ready | Fixes the cause; no T8/T9 spend on a piece likely held; one floor stays | Fewer Blog Subjects on thin tours; a T7 change |

**Recommendation: C, with the single 4,700 floor kept and the extend repair as the fix inside T9.** The extend repair
can only add what the seed states, so a seed without enough untold facts cannot honestly reach the floor; that is a
T7 decision, not a T10 one. Set the minimum from the trial: if the extend rescues ≥ 7 of the 9 length-only pieces, a
low bar (≈ 600 seed words with ≥ 3 fact sentences) is enough; if not, ≈ 1,000 words. B stays a later option for the
target and the ceiling only, never below the floor.

## S278 — the length margin (lane l8)

Live evidence (12/11, CIS 318a7982, 9 new blog pieces on 3 audit tenants after the T7 600-word seed floor,
`remeasure_length.py`): 5 of 9 `length_short`. Three at the floor's edge: 7b80e4ca 4,699 chars (799 words),
3612fd6a 4,696, e083d9c2 4,696 at the end of the loop, the last cut to 4,455 by the normalizer; two thin pieces
(fbc75fe7 4,007 → 3,869, f97aeb18 3,521 → 3,218) also held on other gates. Two held for length only. No approved
piece was stored under the floor (the S277 re-check works). Reading: the writer's word floor (900 words ≈ 5,220
chars) sat only 11 % above F4 and the model undershoots its own floor by about that much, and an F4-short rewrite was
told only the floor ("under the blog floor of 4,700 chars (about 810 words)"). A systematic edge miss, not a seed one.

### Decisions

- **One target, from the registry.** New threshold `t9.blog_length_target_margin` = 0.17 in
  `services/quality/thresholds.yaml`. `length_contract.target_chars()` = round(4,700 × 1.17) = 5,499;
  `target_words()` = 5,499 / 5.8 rounded UP to ten = 950. The floor is not lowered (4,700, a test says so).
- **Why 0.17, not the 0.15 first suggested.** 0.15 gives 5,405 chars → 932 → 940 words. Projected on the S278 edge
  pieces (the writer undershooting its floor by the same ratio), 940 words puts e083d9c2 at 4,904 and its 241-char
  normalizer cut takes it back to 4,663; 950 words gives 4,957 − 241 = 4,716. 0.17 is the smallest margin under which
  all three edge pieces clear the floor after their observed cut even when the cut is a mandatory step. The phase 2
  worst cut (557) is not covered by the margin alone; the floor guard and the re-check cover it.
- **The writer's word floor is the target, through the prompt literal.** `prompts._BLOG_WORDS` (900, 1300) →
  (950, 1300). It stays a literal (hashed in the t9_write manifest; a value read from thresholds.yaml would change the
  rendered prompt without changing its hash) and a test pins `_BLOG_WORDS[0] == length_contract.target_words()`, so
  a new margin fails CI until the prompt follows. That is t9_write **v6** and **migration 399** registers it
  (contract, MIG-4: migration-only PR → Infra copy → Migration Apply → code PR). The lane brief expected no
  migration; a prompt-literal change cannot ship without one (the prompt-registry gate fails).
- **The F4-short rewrite is told the target.** `service._f4_target`: a blog's under-floor F4 violation in the
  rewrite feedback gets "— lengthen the piece to at least 5,499 characters (about 950 words, never more than 1,600),
  not just to the floor: … never invented facts or filler" (the over-max side already got its cut target, AA-984).
  The violation text itself keeps the floor (it is the truth the ledger stores).
- **The extend repair aims at the target** (`extend_target_chars()` = `target_chars()`, was floor + 520 = 5,220).
  The switch stays off by default.
- **Normalizer floor guard** (`length_contract.floor_guard`, `NORMALIZER_STEPS`). An OPTIONAL step's edit is not
  made when it leaves the blog under the floor AND shorter: an in-band blog is not taken under the floor (as S277),
  and now a blog already under it is not cut further (the S277 rule let the FAQ fit cut 4,696 → 4,455 because the
  blog was already short). Optional = the FAQ answer fit (the stock-line cut already refuses on its own and runs only
  for a channel with a spec). Mandatory = the usage-policy cut and the final integrity pass (duplicates, a second
  CTA, fragments): truth and integrity before length, the re-check holds the piece. The ledger note: the F7 flag line
  names the drop ("4,696 → 4,455 chars"), the FAQ fit record gets `floor_kept_chars`, and `length_trace` gets
  `floor_kept` and `target`.
- **Change control.** `gates` (thresholds.yaml) and `prompt_registry` (manifest) accepted with break-glass evidence
  (a decided change ahead of its measurement; the measurement is the next audit-tenant blog run).

Live evidence (S278 paid 3-piece trial on an audit tenant, t9_write v6, CIS main 22c250a8): 1 of 3 approved
(fd26d633, 4,955 chars after one repair). 73e6a233: first draft 3,957 chars (~693 words); attempt 2 carried the F4

floor: the word band alone is not obeyed.

### Decisions (round 2)

- **Writer section plan (t9_write v7, CIS 405).** The LENGTH AND EFFORT block gets "PLAN THE LENGTH BEFORE WRITING":
  an opening of about 130 words, 5 sections (one under the cap of 6) with the richest about 200 and the other four
  about 130, the FAQ at least 3 pairs of 40+ words (about 120); budgets add up to 970 ≥ the 950 floor; "with fewer
  sections, their words go to the richest section and the opening". No new length number: `_blog_length_plan()` reads
  `_BLOG_WORDS[0]`, `_BLOG_SECTIONS_MAX` and two restatements of numbers the format bullets already give
  (`_BLOG_FAQ_PLAN` = the low ends of "3-4 Q/A pairs" / "40-60 words per answer", `_BLOG_RICHEST_SHARE` = "half as long
  again"), pinned to that text by a test; shares round UP to ten so the total never falls under the floor. All four
  new symbols are hashed in the v7 manifest entry (a value read from the policy would change the prompt without its
  hash). The 1,600 ceiling is unchanged. The block's one-pass bullet now says "decide … which seed facts go in each and
  its word budget".
- **No source label without the rule.** `length_contract.NO_SOURCE_MENTION` ("never mention where a fact comes from
  (no "the source", "the notes", "the seed", "the facts" or "the itinerary says"): state the fact itself") is in the
  short rewrite target, the F14 floor feedback line (was "source facts this post does not tell yet"), the blog block
  and (as a sentence) every rewrite footer in `build_user_prompt` (all channels; only rewrite prompts change), and in
  `_EXTEND_SYSTEM`. The short rewrite target no longer names CONTENT SEED / Place background / FACTS lines.
- **F13_leak patterns.** `hygiene.LEAK_RE` also matches the itinerary / source(s) / notes as the subject of a
  PROVENANCE verb ("the itinerary says / names / notes / mentions / states / records / calls (not 'calls for')", "our
  sources say", "the notes mention"), "source facts / text / lines" and "facts lines". "The itinerary includes …", "the
  source of the river", "the notes of the bell" stay clean (tests); see the review fix below for what was narrowed. No frame trim was added for the new phrases
  ("The source notes name deer …" minus its frame is a fragment): they block as F13_leak and are sentence-repaired.
- **Rewrite feedback order (default on).** For a blog whose F4 failure is the short side, `_repair_feedback` lists
  every other failure first, each cut-type one ("cut it", "or cut", "remove", "delete": `is_cut_violation`) with
  `REPLACE_NOT_DELETE` ("the piece is short: if you cut this sentence, fill its place in the same section with another
  fact you were given, never leave the section shorter"), and the F4 line LAST, saying "after every fix above, the
  piece must still be at least 5,499 characters". A blog in band and every other channel keep the ledger order and no
  hint. This is feedback data, not a hashed prompt: it is on for everyone, like round 1's `_f4_target`.
- **The expand step after every short repair round (behind `T9_LENGTH_EXTEND=on`).** Round 1 sized the extend on
  attempt 1's text BEFORE the sentence repair, and never ran one after a full rewrite. Now `plan_for` only routes
  (sets the short F4 entry aside so the other failures go to the sentence repair), and after the attempt-2 repair —
  the sentence repair's splice, a seo-fields-only pass or the full rewrite — `plan_after_repair` plans on the text the
  repair left whenever it is under the floor: deficit to the target from that text (the cuts included), sections the
  repair shortened first (`_holes`: chars lost per heading against attempt 1's text), then the thinnest. The model
  sees "a repair cut text here" on those sections. On a short blog, the sentence repair's cut-type problems carry
  `KEEP_NOT_CUT` ("prefer the fix that keeps the sentence (say it is optional, or say only what is true) over deleting
  it"): the repair prompt itself is unchanged (no t9_repair bump). `repair_mode` reads `sentences+length_extend` or
  `rewrite+length_extend`.
- **Net length record and the refusal.** `repair_log[-1].length_net` = {before, after_repair, after_expand, floor,
  target, repair, expand (the plan reason: expand / at_or_over_floor / no_untold_facts / no_sections),
  shrank_under_floor}. "Refuse a repair that drops length below the floor without an expand" is read as: the loop
  never accepts a short repair round without trying the expand; when no grounded material is left
  (`no_untold_facts`) the round is recorded `shrank_under_floor: true` and F4 (re-run on the whole text every
  attempt) holds the piece. Reverting the repair instead would put back the F17 / F9 sentences it fixed (truth before
  length); the AA-528 guard still picks the better attempt by gates.
- **Why behind the switch.** Lesson S272: a writing-loop change without its review rounds and a measured trial ships
  behind a switch whose default is main. The switch already exists for exactly this path (`trial_flags` allows it on
  one audit-tenant job), so the orchestrator's 3-piece trial sets `trial_flags: {"T9_LENGTH_EXTEND": "on"}`. The
  prompt v7 and the feedback/leak changes are not switchable (a prompt version, a gate pattern) and are on for all.
- **FAQ as expand material: not added.** The FAQ already has its one regeneration per writer text
  (`_enforce_faq_contract`) and F16 caps the pairs; a new pair from a fact the body tells would be dropped by
  `drop_restated_faq`. The expand uses the untold seed / Place background / Facts sentences
  (`unused_source_facts` on the grounding text).

### Review fixes (round 2, S278 independent reviewers)

- **LEAK_RE narrowed (2 findings, accepted).** The first round-2 pattern took any reporting verb (gives / shows / adds
  / lists / describes / explains / confirms) after "the / this / our itinerary" and "the / our sources / notes /
  facts", plus "source material" and "facts section / block". That flagged reader-facing copy ("The itinerary gives

## Round 3 — S279: topic selection sized from the length floor, and the blog repeat drop

Facts from S278 trial 2 (t9_write v7, 3 audit-tenant tours): one piece held `F4_extreme_length` at 4,425 chars / 748
words from a Subject whose seed cleared the flat `T7_BLOG_MIN_SEED_WORDS=600` (the extend step on the stored short
piece returned 11 tokens: no grounded material left); one held `F13_repeat` at 5,724 chars for one repeated sentence.

### Decisions

- **Sized floor, supplementing the flat one.** `blog_seed.seed_floor()` = `max(flat, ceil(BLOG_FLOOR_CHARS /
  chars_per_seed_word))`, applied only while the flat Blog minimum seed is on (> 0). A deployment without the flat
  setting is unchanged (default = main for every env that never set it); Dev (flat 600) gets the sized floor on the
  deploy, so the live replay and the paid trial measure it without an Infra change.
- **The ratio is configuration, not code.** Env `T7_BLOG_CHARS_PER_SEED_WORD` (read per call, 0 = no sizing) over the
  registry threshold `t7.blog_chars_per_seed_word` (services/quality/thresholds.yaml, `calibrated: false`). There is no
  CIS table for pipeline business values yet; a staff page for these values is a follow-up (see Should know).
- **Default 5.8 chars per seed word = one written word per grounded seed word** at the measured 5.8 chars/word
  (`length_contract.CHARS_PER_WORD`). Reason: the v7 writer does not invent (S278 extend step), so the article cannot be
  longer than its material in words; this gives a sized floor of 811 words, the word count of the F4 floor itself.
  The live ratio could not be measured from this lane (no DB access): `scripts/aa1077/seed_floor_replay.py` measures it
  ($0, read-only) from the MATERIAL-BOUND pieces (stored under the F4 floor) of the newest writer version and prints
  the env value. Pieces at or over the floor are not used for the ratio: they show the writer's target, not what the
  seed could carry (censored data; with them the ratio would drop to ~2 and the floor jump to ~2,300 words).
- **The replay sizes the floor conservatively (review fix).** First draft: the MEDIAN chars / seed word of those
  pieces. A median-sized floor leaves a seed sitting at the floor short about half the time, and with 2-4 v7 pieces it
  can keep the Galle piece itself when that one has the lowest ratio. Now: per material-bound piece `needed` =
  ceil(seed_words x 4,700 / chars) (printed as NEEDED lines), the recommended ratio = their LOWEST ratio (the floor =
  the largest `needed`) under 4 pieces, else their 25th percentile (one outlier does not set the floor), cut down to 3
  decimals (a rounded-up ratio could size the floor one word under a piece's need). At the minimum every material-bound
  piece of the sample is skipped. The median is printed for reference only. TARGET lines (env TARGET_TOURS, default the
  Galle tour ac574bfe; TARGET_PIECES) print each target Subject's verdict per arm, and SUMMARY `target.<arm>.
  all_short_skipped` is what the live step asserts for `at_measured`.
- **Per-Subject skip report.** `blog_coverage.skipped` (admin job result only): per Bar-clearing Blog candidate the
  slate did not propose for its seed, `reason` = `thin_walk` / `seed_below_min` / `seed_below_length_floor`, its place,
  tours, seed words and the floor it missed. `blog_coverage.seed_floor` holds the parts (flat, sized, ratio, F4 floor);
  `min_seed_words` is now the effective floor. `tenant_blog_topics` is unchanged (the tenant never sees it).
- **Repeat drop (`repeat_drop.py`), blog only, deterministic.** After the length trim and before the gates: the later
  copy of a sentence the F13 gate quotes is deleted when it is a near-exact copy of an earlier prose sentence (ordered
  Dice share of copy words >= `t9.repeat_drop_near_exact` 0.9; 1.0 = exact) AND the piece stays >= the F4 floor AND
  the existing invariants hold (no orphaned pronoun, every fact token kept, `integrity_problems` empty, then the step
  contract). Else nothing changes and F13 holds as today. Switch `T9_REPEAT_DROP=off`.

### Changed

- `services/acp_shared/blog_seed.py`: ratio setting, `sized_min_seed_words`, `seed_floor`, `skip_reason`, reason codes.
- `services/acp_shared/slate.py`: `_fetch_short_blog_seeds` takes the floor and returns the measured words;
  `blog_skipped_subjects`; `propose_slate` adds `seed_floor` / `skipped` to `blog_coverage`.
- `services/acp_content_writing/repeat_drop.py` (new) and its hook in `service.run_write_background`.
- `services/quality/thresholds.yaml`: `t7.blog_chars_per_seed_word`, `t9.repeat_drop_near_exact`; change-control lock
  `gates` accepted with a break-glass reason (decided fix ahead of its measurement; live measure = replay + trial).
- `scripts/aa1077/seed_floor_replay.py` (new, $0, read-only).

### Tradeoffs

- One global ratio instead of a per-Subject history rule ("this seed already produced a short piece"). The history
  rule would skip the Galle Subject for certain but needs a version filter (v5 pieces undershot whatever the seed) and
  says nothing for new Subjects; the global ratio covers both and the replay shows the Galle verdict.
- The default ratio is not calibrated. If the replay's recommended ratio is lower than 5.8 (a stricter floor) or the
  Galle Subject is kept under `configured`, the orchestrator sets `T7_BLOG_CHARS_PER_SEED_WORD` on the worker (Infra)
  to the printed value.
- Low quantile vs median: the low quantile costs topics (a Subject with a seed between the median-sized and the
  low-quantile-sized floor is skipped); the replay prints `approved_skipped` per arm so the cost is visible before the
  env is set. The alternative skips fewer topics but lets about half of the floor-level seeds come out short, which is
  the hold this slice removes.
- The repeat drop deletes words the final pass would keep (a near-exact copy's one or two changed words). Facts are
  never among them (fact invariant); style words can be. The alternative, holding a 5,700-char article for one
  repeated sentence, costs a whole topic.

## Round 5 — S280: one lengthen pass after the normalizer (lane aa1077b)

Gap left by round 4: the in-loop expand runs only inside the repair rounds. When a MANDATORY normalizer step (the
usage-policy cut or the final integrity pass: truth and integrity before length, `length_contract.NORMALIZER_STEPS`)
takes a blog the loop APPROVED under the floor, the re-check holds it `length_short` and nothing lengthens it.

### Decisions

- **New module `length_recheck.py`, not service.py.** `service.py` sits at its file-size baseline (3,992 lines) and
  `run_write_background` at its complexity baseline (71). The F4 re-check (`_recheck_length`, unchanged) moved there
  with the new pass; service keeps the names (`_recheck_length`, `LENGTH_TRACE_STEP`) as aliases, so every test that
  patches `service._recheck_length` still works. service.py is now 3,971 lines; `run_write_background` stays 71 (the
  new call has no branch: the voice string and the embedding guard are built inside the module).
- **Where it runs.** `length_recheck.lengthen_after_normalizer(norm, …)` right after `_normalize_final_text` and
  before its result is unpacked (`norm = …`; `content_text` is still assigned only from `norm[...]`, the AA-1047
  chain-order guard holds). A new chain-order test pins it: extend → `final_pass` → every gate inside the pass, and the
  pass between the normalizer and the final contract.
- **Eligible only when all hold** (`eligibility`): the re-check turned the loop's `approved` into `held`
  (`length_trace.held`; so F4 short is the one hold reason); the trace shows the text at or over the floor after the
  loop and the step that crossed the floor is MANDATORY (`crossing_step`, trace order; an optional step is
  floor-guarded and cannot cross); the piece's pinned switch is `on` (same value as the in-loop expand, resolved once
  per piece, S280 round 4); and the piece has an attempt left.
- **Cost cap = the piece's attempt budget, plus one call.** "The existing per-piece budget" read as the setting
  `cis.t9.max_attempts` (attempts per piece, default 3): the pass counts as the piece's next attempt and runs only when
  `max_attempts() - attempt > 0` (it is logged with `attempt = loop attempt + 1`). There is no per-piece USD cap in
  T9 today; adding one would be a new setting (migration + guide) for a single call. The pass is ONE
  `extend_sections` call (output capped by its `max_tokens`, T9_REPAIR_MAX_TOKENS 8,192; S277/S278 measured
  0.0045–0.02 USD per call) plus the gate re-run, whose F9 judge only reads sentences it has not passed before
  (`f9_passed` memory, same object as the loop). The call goes through the gateway, so the tenant AI budget applies: a
  budget approval stop or an unreadable counter is re-raised (`_guarded`), never swallowed by `length_extend.extend`'s
  catch-all, so the job ends `stopped_budget` / retries as for any T-stage call.
- **Planning reuses `plan_after_repair`** on the stored text with `before` = the loop's text: the sections the cut
  shortened come first (`hole_chars`, "a repair cut text here"), facts = the seed's untold fact sentences, target =
  `extend_target_chars()`. Each paragraph is code-checked by `length_extend.extend` (plain prose, size, no new
  specific, no source label, clean seam).
- **Re-run everything on the result.** `text_integrity.final_pass` (the normalizer's last mandatory step) first; a
  residue (a repeat it cannot delete) keeps the hold. Then EVERY gate: the loop's own `run_quality_gates` arguments
  through one `functools.partial` (`gates`) that the loop now uses too (no second copy of the argument list), with
  `stock_blocking=False` (attempt > 1) and the last attempt's SEO fields and cannibalization match. Accepted only when
  `outcome["passed"]`: status `approved`, the re-run ledger, its warn flags plus the normalizer's admin-only flags of
  gates the re-run does not produce, the embedding re-made (tenant pieces, as `_after_cut`; the summary is kept: the
  text only grew). Anything else returns the normalizer's result byte for byte (held `length_short` as before); the
  call's cost is still added to the piece's cost.
- **Record.** `writer_input.length_trace.post_normalizer` = {reason, crossed_at, attempt, plan, extend (the extend log),
  cost_usd, chars_after, outcome (`approved` / `held:nothing_added` / `held:integrity` / `held:gates` /
  `held:<plan reason>`), failing}. Written for every blog the re-check held (switch off included: reason `off`), so
  the $0 replay counts how many pieces the pass would reach. On approval the trace's `held` / `verdict` read
  `False` / `in` and `chars.post_normalizer` the new length. Not a repair-log entry (`repair_log[-1]` stays the last
  repair or label, as round 1 decided for the trace). The llm_call_log row carries `quality_signal.step =
  post_normalizer` (new optional `step` argument of `generate.extend_sections`).
- **Switch off = main.** No plan, no call, no gate re-run; only the trace record `{"reason": "off", …}` is added.
