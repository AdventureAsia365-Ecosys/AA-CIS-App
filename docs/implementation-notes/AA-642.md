# AA-642 S0 — step 1 zero-cost gateway fixes (AI gateway v2)

Scope: slices A1a and A1b of the S262 gateway plan (root design `docs/audits/2026-10-31-S261-ai-gateway-design-v2`,
root ADR 0009, step 1). No route change: `shared.llm_role_config`, `llm_model_deployment`, `llm_provider_connection`
and the catalog are not touched by code or by migration 318. No paid call was made; every provider is mocked.

## Decisions

- **acc2 attribution (fix 1).** A task-role (acc2) reply now carries `connection_key` = the deployment's connection
  key (`acc2`); `satellite_account` stays `None`, because `silver_aa_internal.generated_content.satellite_account` has
  a CHECK that only allows satellite account keys (`acc1`, `acc3`). `call_log._row_account` already stores the
  connection key as `account` when the caller passes none, so the ledger row gets `account='acc2'` and
  `cost_guard.connection_month_spend` (`account = ANY(...)`) sees it. Same for the legacy `_call_bedrock`
  (InvokeModel on the task-role client): new keyword `connection_key` (default `ACC2_CONNECTION_KEY`), and the
  task-role `anthropic_native` deployment path passes its own connection key. Provider stays `bedrock`
  (ledger `bedrock-native`).
- **Anthropic spend cap (fix 2).** Keyed on the structured `error.details.error_code ==
  "enforced_spend_limit_reached"` read from the SDK's `APIStatusError.body`, checked before the THROTTLED branch.
  Fallback: that exact code string in a 429's text. The code is also put in the head of the wrapped
  `AnthropicAPIError` message, so a stored job error (text cut at 300 chars) still classifies as QUOTA_EXHAUSTED
  through `errors._PATTERNS` (new pattern, QUOTA is matched before THROTTLED). Plain 429 rate limits (including the
  "billing words in a 429" case) stay THROTTLED.
- **Jev daily cap (fix 3).** `decide._decide` asks `jev_budget_blocks(db)` only when something is left to ask (after
  the memo, the DB verdict cache and the credit breaker). It reads `cost_guard.load_run_budget(db, "jev", "decide")`
  (the `jev/global` row, plus `jev/job:decide` if anyone ever seeds one) at most once per 60 s per process; between
  reads the process charges its own asks into the cached budget. Over a hard cap: verdicts `error` /
  `budget_exceeded`, `to_ask` emptied (no TypeSafe call, no llm_call_log row), decision_log rows still written.
  `hard_stop=false` = alert only. Alerts: `cost_guard.maybe_alert` on each refresh (80 % or stop reason; it throttles
  to one bell per provider per 24 h).
- **Jev budget unreadable.** Keep the last value read; before the first good read fail open (logged
  `jev_budget_unreadable`), like `connection_budget`. Reason: the config read just before it already proved the DB is
  reachable, and failing closed would silently disable every Jev gate on a DB blip.
- **Refresh concurrency.** A non-blocking `threading.Lock`: one coroutine / thread refreshes, the others use the last
  value and never wait (decide_sync runs loops in threads, so an asyncio lock is not usable).
- **`cost_guard.day_spend('jev')`** uses exactly the admin Overview filter (`lower(provider) IN ('typesafe','jev')`),
  so the live check "cost_guard jev = overview jev" holds by construction.
- **Jev canary (fix 4).** Writes one llm_call_log row through `record_call_with_pool`: stage `adhoc_jev_canary`
  (the `adhoc_` prefix every probe uses, e.g. `adhoc_conn_test`), role `validate`, provider `typesafe`, cost from
  the new `decide.jev_usage(data)` (also used by `_decide`, same arithmetic). A 402 writes no row (not billed). No
  `billed_fields(...)`: the reply is a TypeSafe dict, not an `LLMResponse` (same as decide.py's own row; the S6 AST
  guard only looks at `model=<x>.model_used`).
- **Migration 318** is **contract** (ADR 0017: config-row inserts are not expand, no `-- migrate: expand` header,
  no auto-apply), so it follows MIG-4 (ADR 0017 d1, review fix pass): its own migration-only PR
  (`feat/aa-642-s0-migration-318`, file + its integration test) merges first, then the byte copy in AA-CIS-Infra,
  then a manual DB Migrate `check` → `apply` with every job table idle, and only then this code PR. Values from step 0 (31/10): Jev p95 2.20 / max 3.84 USD per day → 5.00 per
  day hard, alert 80 %; DataForSEO p99 0.099 USD per tour → 0.50 per run hard for `job:s1_rewrite`. Both
  `ON CONFLICT DO NOTHING`. `'jev'` was already allowed by `spend_budget_provider_check`; no constraint change.
  Readiness requirement not raised: the code works without the rows (no row = no cap).
- **DataForSEO S1 job kind** = `s1_rewrite` (the job that calls `_execute_run_tour` → `process_seo`). The S1 batch
  prep (`s1_batch._load_prompt_state`, one tour each) uses the same kind: it is the same per-tour work.
- **process_seo budget (A1b).** New `budget` and `budget_kind` parameters. The budget is loaded only when a live
  fetch is about to happen (not on reuse / cache hit / disabled), on its own connection (`cost_guard.ConnAsPool`, a
  new one-connection adapter). No kind = `DEFAULT_BUDGET_KIND = "global"` (the dfs global row only), as planned. A
  budget that cannot be read raises: no live DataForSEO call without a budget (the S1 callers catch it as
  `seo_step_failed` and write without SEO, today's failure behaviour).
- **fetch_all stops** after `BudgetExceeded` or a fatal `DFSCallError` (any exception run through `as_dfs_error`;
  the single-seed `fetch_keyword_ideas` now runs with `raise_on_error=True` so a fatal status is seen). Non-fatal
  failures are skipped as before. The client records why in `last_stop`.
- **A stopped result is neither cached in Redis (7 days, shared by every tour of the same seed) nor persisted** as the
  tour's `seo_context` row (S1 would reuse it for `S1_SEO_REUSE_DAYS` instead of buying again). process_seo returns
  `status` `budget_stopped` / `dfs_stopped` with the partial data; a budget stop raises `maybe_alert`.
- **`s1_prefetch.prefetch()`** raises `ValueError` when no client is given (checked first, before any DB read). Its
  one caller (the s1_seo_prefetch job) always passes a budgeted client.

## Tradeoffs

- Jev cap per process with a 60 s cache vs. a query per ask: per-ask reads would add tens of thousands of queries on
  an A3 recompute and raise the single-connection contention risk (lesson S219). Overshoot is bounded by one minute
  of traffic per process (Jev p95 is about 2 USD a day, so cents).
- Not persisting a stopped DataForSEO result means a tour stopped by the cap is bought again on its next run. That is
  intended: the cap resets, and a half-empty row would otherwise be reused for days.
- The plan's literal `load_run_budget(pool, 'dfs', 'global')` default reads scope `job:global` (no such row) + the
  `global` row: the same caps as reading `global` alone. Kept literal.

## Should know

- A gpt-family model on the acc2 native Converse path has the plain label `gpt-…`, which
  `call_log._normalize_model_provider` maps to provider `openai` (a label heuristic, not new). No stage routes chat to
  acc2 today. The fix belongs to ledger v2 (A2), which stores `connection_key` and can derive the provider from the
  connection kind; it was left alone here to keep client.py to fix 1 only.
- The Anthropic SDK still retries a spend-cap 429 itself (up to the connection's `max_retries`), because it retries
  every 429. Those retries are refused, so they cost nothing; the gateway no longer treats the final error as a rate
  limit (the route moves on / the job fails as quota exhausted).
- The Jev budget refresh runs on the caller's pool or single connection. On `_SingleConnAsPool` paths with parallel
  decides (A3 recompute), a refresh can collide with another query ("another operation is in progress"): the refresh
  then keeps the last value and the other ask fails open, as every decide query already can.
- An admin change of the Jev row (`PUT /admin/budgets/jev/global`) reaches each process within 60 s.
- Migration 318 is contract: DB Migrate `apply` waits for every job table to be idle (DM-11.4). Order: CIS
  migration-only PR → Infra copy PR (Copy Guard needs 318 on CIS `main` first; if the migration-copy bot opens
  `bot/migration-copy/cis-318` first, merge one of the two and close the other) → manual DB Migrate apply → this
  code PR. While 318 sits on CIS `main` unapplied, Migration Apply stops at it and applies no later CIS expand file
  (319+), so the manual apply runs right after the Infra copy merges.
- The code PR does not depend on the rows: with no row there is no cap (today's behaviour), so merging it first
  would be safe, but MIG-4 keeps the schema-before-code order.
