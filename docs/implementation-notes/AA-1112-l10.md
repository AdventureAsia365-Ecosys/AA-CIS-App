# AA-1112 — RLS allowlist cleanup and stale-entry guard (lane l10, S284)

Lane `l10-aa1112`, S284 (2026-11-18), Claude Code. Part of the AA-1112 Done-when "the allowlist has no stale
entries". The Dev-side check and the retention-row rule are in AA-CIS-Infra (same lane).

## Decisions

- **The stale list comes from the live Dev dump.** The nightly DB Schema Dump of 18/11/2026 (root
  `docs/architecture/db-schema-reference.md`, section "RLS catalogue guard (X2)") listed 20 stale entries: rule a
  `acp_shared.acp_output_rules` (moved to `retired` by CIS 316) and the five AA-850 wave-1 tables in `retired`
  (dropped by CIS 296); rule e `tripplanner.*->shared.destinations` (the FKs left with X4); rule g the thirteen
  TripPlanner reads revoked by CIS 254, 270 and 351. All twenty are removed, with the reason constants that only
  they used (`_REVOKED_254`, `_REVOKED_270`, `_WAVE1_TENANT_TABLES`, `_QUARANTINED_294`).
- **Two places fail on a stale entry from now on.** The CIS replay builds only the CIS migrations, so it can judge
  only entries for CIS objects: `cis_side(rule, key)` (schema owned by CIS; for rule g also a grantee the replay
  creates, `CIS_REPLAY_GRANTEES`). `test_cis_side_entries_are_used` fails on a stale one in every PR. Every entry is
  checked against the live Dev dump by AA-CIS-Infra `db/check_rls_allowlist.py` (Migration Copy Guard, advisory job
  "Retention rows and RLS allowlist"): every entry nightly; on a pull request only when the PR changes the rules
  copy, and then not the entries that PR adds (their objects reach Dev with Migration Apply). Migration copy PRs
  never run it, so a Dev-side stale entry cannot stop the copy bot (review S284).
- **Replay misses.** Two CIS-side entries are used on Dev but not in the replay, because conftest builds the object
  differently: `retired.acp_output_rules` (no repo migration creates it; the X1 stand-in has no `tenant_id`) and
  `shared.tenant_tripplanner_site` (conftest skips 379). They sit in `REPLAY_MISSES` of the guard test with the
  reason; a second test fails when the replay starts using one, so the list cannot rot.
- `shared:tripplanner` stays (in use on Dev): its reason now names the `shared.llm_call_log` INSERT it serves, not
  the Model Gateway tables whose grants 351 revoked.

## Changed

- `tests/integration/rls_catalogue_rules.py`: 20 entries removed, docstring (stale is now fatal), `entry_object()`,
  `cis_side()`, `CIS_REPLAY_GRANTEES`.
- `tests/integration/test_rls_catalogue_guard.py`: `REPLAY_MISSES`, `test_cis_side_entries_are_used`,
  `test_replay_misses_are_still_missed`, `test_replay_misses_name_shared_cis_side_entries`.
- `tests/unit/test_rls_catalogue_rules.py`: `cis_side()` cases, a guard that the removed entries do not come back.
- `docs/implementation-notes/AA-825.md`: the Parquet deviation is marked resolved (DM-7.3 names gzipped JSON Lines since
  data standards v1.15); the archive code and its docstring already said JSON Lines.

## Tradeoffs

- A replay-wide stale test for every entry would fail on the Booking / TripPlanner / platform entries the replay
  never builds; the split keeps the per-PR test exact and leaves the rest to the Dev check.
- The Dev check runs on the latest successful dump, so a drop applied today shows the next night (or on the next
  Infra PR in the guard's paths). Adding it to the DB Schema Dump workflow itself was rejected: a red job there makes
  the run not "success", and Migration Apply, Migration Sync and Expand classify read the latest successful run.

## Should know

- The file is canonical here; the orchestrator copies it byte for byte to AA-CIS-Infra `db/rls_catalogue_rules.py`
  after this PR merges (Copy Guard). The Infra lane PR carries that copy.
- The PR that drops a table, revokes a grant or fixes an object removes its entry in the same PR. Until Dev applies
  it, the Dev reference shows the object as a violation (report only, never fatal).
